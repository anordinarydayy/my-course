02Core concept · Phase 0 · Redis

The Single-Threaded Event Loop

Lesson 01 gave Redis a shape: one dictionary of typed values. This lesson gives it a pulse. Every command runs on one thread, one at a time, to completion. That is why a GET costs almost nothing, why single commands are atomic without a lock, and why one careless O(N) command stalls every client at once.

Original study chapter. Written from scratch for backend and system-design interviews. Target behavior follows Redis Open Source 8.10 (latest stable patch 8.10.3, released 2026-10-26; 8.12 is still a release candidate as of 2026-11-21). The lab runs on Python 3.10+ with redis==8.1.0, plus the redis-cli and redis-benchmark that ship with Redis. Contains five original figures — three interactive (press Play, or step with Next). The RESP wire format lives in L03, expiry in L15, pipelining in L22, Lua in L24, and SLOWLOG and INFO in depth in L38.
00 Failure first

One slow command, everyone waits ▸

Start with an incident that looks like a network problem. A support dashboard runs KEYS user:8841:* to list one customer’s sessions. It returns three keys after about a tenth of a second and the page renders. In the same instant the checkout service sends a single GET for a cart, a command that costs the server well under a microsecond, and the request times out. Redis is not down and its log is empty. The only trace is one bump on a latency graph.

The cause is the first rule of this lesson: Redis executes commands on one thread, one at a time, each to completion. While KEYS runs, nothing else runs. The operating system keeps accepting bytes from every other client into socket buffers, but the one thread that could read them is busy. The request at the front decides when everyone behind it is served, which is called head-of-line blocking. Three symptoms give it away:

  • A latency spike on unrelated clients at the same instant. Each connection that sent a request during the stall waits out whatever is left of it.
  • Timeouts and retries with no Redis error. Clients give up and retry, which queues more requests behind the stall.
  • One long entry in SLOWLOG and a calm average. The slow log records the command’s own execution time (L38 covers it), and a CPU graph averaged over a minute hides a 140 ms stall.
A fast server is not a fair server

Redis does not make commands fast by running many at once. It makes each command so cheap that running them one at a time is fine, as long as every command stays cheap. The rest of the lesson explains why that bet is sound, how the loop carries it, what breaks it, and how to stay inside it.

01 Cost model

Why one thread is enough: where the time goes

The obvious objection is that servers have dozens of cores. The answer is in where a command’s time goes. A GET on an in-memory hash table is a hash, a short pointer walk and a copy into a reply buffer. Redis publishes two counters that split the loop’s busy time into executing commands and everything else: eventloop_duration_cmd_sum and eventloop_duration_sum in INFO stats. Reading them around a redis-benchmark run at three pipeline depths gives this picture:

Load styleLoop time per commandShare spent executing the commandOne-thread ceiling (1 ÷ loop time)
One request per round trip, 50 clients≈ 8 µs≈ 7%≈ 120,000 ops/s
Pipeline of 16≈ 1.0 µs≈ 20%≈ 1,000,000 ops/s
Pipeline of 100≈ 0.65 µs≈ 32%≈ 1,500,000 ops/s

Measured for this lesson: Redis 8.10.3 built from source, 8-core Apple-silicon laptop, loopback, redis-benchmark -t set -r 100000 -c 50, counters read from INFO stats before and after each run. Plain redis-benchmark runs without -r landed in the same ranges: roughly 120,000–140,000 ops/s unpipelined and 1.2–1.5 million with -P 16 (one repeated key is cheaper than random keys). The shape travels between machines; the exact numbers do not. The Build lab reproduces the table.

Two readings follow. First, the command is not the expensive part. Without pipelining, more than nine tenths of the thread’s busy time goes to the conversation around the command (reading and parsing the request, writing the reply, housekeeping), and even at depth 100 about two thirds does. Second, a million operations a second is a pipelining number. The Redis FAQ quotes it for exactly that case, and adds that CPU is rarely the limit because Redis is usually bound by memory or network. L22 does the round-trip arithmetic. Here the point is that a thread spending under a microsecond per command is fast because each command is tiny, not because anything runs in parallel.

Why not give every command its own thread anyway? Each reason below is a cost that parallel execution would add:

  • No locks. Dictionaries, skiplists and listpacks stay plain data structures: no mutexes or atomics guarding the data, no cache lines bouncing between cores.
  • No deadlocks and no torn multi-key work. MULTI/EXEC, scripts and commands such as SUNIONSTORE touch several keys at once. With one executor they need no lock ordering.
  • One order of commands. The replication stream and the append-only file are that order written down. Two concurrent writers would need reconciling before either could be replayed (L18, L27).
02 Mechanism

The reactor loop ▸

One thread can serve thousands of connections only if it never waits on any single one. A blocking design solves the same problem the other way round, and putting the two side by side shows what Redis chose:

Thread per connection (blocking I/O)

  • Each client gets a thread that blocks in read() until bytes arrive.
  • The OS scheduler provides concurrency and can preempt a long request.
  • Shared data needs locks; threads, stacks and context switches grow with connections.
  • The order of commands across clients is whatever the scheduler produced.

Event loop (Redis)

  • One thread asks the kernel which sockets are ready, then runs a short handler for each.
  • Concurrency is interleaving at command boundaries; nothing preempts a handler.
  • No locks on the dataset; an idle connection costs a socket and buffers, not a thread.
  • The order of commands is one sequence that can be logged and replayed.

The kernel feature behind the right-hand column is a readiness query: which of these sockets can I read or write right now? On Linux it is epoll_wait, on BSD and macOS kevent, on Solaris-family systems event ports, with select as the fallback. Redis wraps whichever the build supports in a small event library, ae.c, and INFO server reports the choice in multiplexing_api. Textbooks call the structure a reactor: a demultiplexer reports which handles are ready, and a dispatcher calls the handler registered for each.

Each pass through the loop does four things in a fixed order. The names below come from the 8.10 source (aeProcessEvents in ae.c, beforeSleep in server.c):

  • 1 · beforeSleep. Work that must happen before the thread may sleep: write the replies queued last turn, flush the append-only buffer, serve clients whose blocking call can now finish, run a quick pass that deletes expired keys.
  • 2 · Poll. Ask the kernel which sockets are ready, with a timeout equal to the time until the next timer. With no traffic the thread sleeps here, so an idle Redis uses almost no CPU.
  • 3 · File events. For each ready socket, run its handler: read without blocking, parse the request, run the command to completion, append the reply to that client’s output buffer.
  • 4 · Time events. If a timer is due, run it. The main one, serverCron, fires hz times a second (default 10, so every 100 ms) for incremental housekeeping: sampling for expired keys, resizing hash tables a little at a time, closing timed-out clients.

Three rules keep the loop honest:

  • Handlers never block on I/O. Sockets are non-blocking. A read with nothing to read returns at once, and the loop waits for the next readiness report.
  • A command runs to completion. There is no way to pause one command and serve another. The end of a command is the only scheduling point.
  • A slow reader costs memory, not time. If a client does not drain its replies, they wait in its output buffer and a writable-socket handler finishes the job later while the loop moves on. The cap is client-output-buffer-limit. Normal clients default to 0 0 0, which means unlimited. Replicas (256 MB hard, 64 MB soft for 60 s) and Pub/Sub clients (32 MB hard, 8 MB soft for 60 s) have limits.
03 Invariant

The command is the unit of scheduling

State the model as one sentence you can say in an interview: between two commands anything can happen; inside one command nothing can. Everything Redis promises about concurrency is a corollary.

  • Single commands are atomic. INCR, LPUSH and ZADD cannot be seen half-done, and two clients cannot interleave inside one.
  • MULTI/EXEC is a longer command. The queued commands run back to back, and no other client’s request is served in the middle of them (L23).
  • Scripts and functions are longer still. They are atomic by the same mechanism, so a script’s run time is every client’s wait. Redis will not abort a script that runs too long, because that could leave a half-written dataset. After busy-reply-threshold (5,000 ms by default) other clients start receiving BUSY errors. SCRIPT KILL works only if the script has not written yet; after a write the only exit is SHUTDOWN NOSAVE (L24).
  • Order is shared. The replication stream and the append-only file replay the same sequence the loop produced.

What the model buys

  • Atomic single commands with no locking code anywhere.
  • Transactions and scripts that are just longer commands.
  • One command order that replication and the AOF can reproduce.
  • Low, predictable latency while every command stays cheap.

What it costs

  • Head-of-line blocking: one slow command is every client’s latency.
  • A ceiling of one core for executing commands.
  • No protection between clients: the loop cannot tell a dashboard query from a checkout request.
  • Atomicity per command only: GET then SET from a client still races (L01).
Two meanings of “blocking”

BLPOP, BRPOP and BZPOPMIN are blocking commands: they park the calling client until data arrives or a timeout passes, and the loop keeps serving everyone else. A later push wakes the parked client during a following beforeSleep. INFO clients counts the parked ones in blocked_clients. KEYS and SMEMBERS on a huge set are slow commands: they hold the loop itself. The two names collide, and the effects are opposite.

04 Hazards

What holds the loop: the O(N) catalogue

Whether a command is safe is written on its page as a complexity line, and the N in that line belongs to your data. SMEMBERS on a 20-member set and on a 2-million-member set run the same code with a gap of five orders of magnitude between them, and nothing in your application changes. That is why O(N) commands pass in staging and fail in production: the data grew, not the code.

At a million keys the stall is a tenth of a second, a few hundred times a normal round trip. At ten million it reaches the range of a second. The bars scale two measured per-key costs, 40 ns from the KEYS documentation and 140 ns from this lesson’s lab, so read them as orders of magnitude. The same reasoning applies to every command in the table below.

CommandCost on its pageWhat holds the loopLoop-friendly alternative
KEYS pattern O(N), N = keys in the database Every key name is matched, even when only three match SCAN with MATCH and COUNT; or an index set you maintain
SMEMBERS, HGETALL, LRANGE k 0 -1, ZRANGE k 0 -1 O(N), N = size of the value Every element is visited and copied into one reply SSCAN, HSCAN, ZSCAN, or paged LRANGE / ZRANGE windows
SUNION, SINTER, SDIFF, SORT O(N) for SUNION and SDIFF, O(N*M) for SINTER, O(N+M*log M) for SORT The whole computation runs in one go Restructure the data, or run it on a replica
DEL on a big collection, FLUSHALL / FLUSHDB O(M) per key; O(N) over all keys Frees every element on the loop (the 8.10 default) UNLINK; FLUSHALL ASYNC
SAVE O(N), N = keys in all databases Writes the whole RDB file synchronously BGSAVE (L17)

Ask what N will be

Every command page opens with its complexity, and L03 shows how to read it. Before you ship a command you have not used, decide what N is a year from now: the whole keyspace, one collection, or the number of arguments in the call. A command that is O(N) in the arguments, such as a DEL or MGET naming a hundred thousand keys, holds the loop just as surely.

05 Fixes

Slicing the work: SCAN, UNLINK and replicas

If the end of a command is the only scheduling point, you schedule by choosing how big a command is. Cut a long job into slices and the loop can serve other clients between them. Figure 4 shows the same scan in both shapes.

SCAN is the standard slicing tool. Each call examines a small piece of the keyspace and returns a cursor. The client passes it back to continue, and a returned cursor of 0 means the walk is complete. The server keeps no iterator. Per a comment in the source, the cursor advances in reverse-binary order (its bits are reversed, incremented, then reversed back), which keeps the walk valid if the hash table grows or shrinks between calls. SSCAN, HSCAN and ZSCAN do the same inside one set, hash or sorted set.

A stateless cursor buys simplicity and costs guarantees. What you can rely on:

  • An element present for the whole walk is returned at least once, and one absent for the whole walk is never returned. Elements added or removed during the walk may or may not appear.
  • Duplicates are possible. Make the per-key work safe to repeat. UNLINK and idempotent writes are.
  • COUNT is a hint about work per call (default 10), not a page size. MATCH filters after the slice is fetched, so a selective pattern returns many empty pages. Stop on cursor 0, never on an empty page.
  • The full walk is still O(N) and, with a round trip per slice, takes longer than KEYS. What you buy is that no single call holds the loop longer than one slice.

DEL versus UNLINK. Lesson 01 introduced the pair. In 8.10, DEL and FLUSHALL free memory on the loop unless you opt in with FLUSHALL ASYNC or a lazyfree-lazy-* setting; all of those default to no. UNLINK unhooks the key at once and hands the freeing of a large value to a background thread. The source’s cutoff is a free effort above 64 allocations, so small values are still freed inline, which is cheap per key but not free in bulk. Deleting a million small keys still wants batches; the lab below uses a thousand keys per call.

Heavy reads belong on a replica. If a slow read is a real requirement, such as a report over a big set, run it on a replica so the primary’s loop never sees it. The Redis latency guide makes the same recommendation. The cost is replication lag (L27).

06 Threads

Where threads do help ▸

“Redis is single-threaded” is shorthand for “one thread executes commands.” A running Redis 8.10 has more threads than that, and each exists for a reason:

Thread or processExists whenWhat it doesWhat it never does
Main thread Always The event loop, every command, the timers. With io-threads 1 it also does all socket reads and writes. Nothing is off limits, so any slow command stalls everything
I/O threads io-threads above 1 (restart required) Read sockets, parse requests and write replies, each thread in its own small loop Execute commands or touch the dataset
Background threads Always: three of them Close files whose release is slow, fsync the AOF, free big values for UNLINK and async flushes Serve a client request
Forked child process During BGSAVE and AOF rewrite Writes the snapshot from a copy-on-write view of memory (L17) Serve clients. The fork call itself runs on the main thread, and a large dataset makes it take longer.

In this lab’s macOS build a default process showed four OS threads: the main thread plus three background workers. Builds with jemalloc, the usual Linux default, add an allocator helper thread (jemalloc-bg-thread), and loaded modules can add threads of their own. None of these change the rule that one thread executes commands.

Section 01 showed that most of the loop’s busy time is the conversation around a command. That is the part I/O threads take over. Redis 6.0 introduced them and 8.0 replaced the implementation. In the 8.x design the main thread assigns each client to an I/O thread. That thread reads the socket, parses the request and tells the main thread. The main thread executes the command and builds the reply, and the I/O thread writes it back. Each I/O thread runs its own small event loop over its own clients.

  • Off by default. io-threads defaults to 1, which means the main thread does everything. io-threads 4 means one main thread plus three helpers, and INFO threads then lists io_thread_0 (the main thread) through io_thread_3 with their client, read and write counts. The setting is immutable: CONFIG SET io-threads is refused, so edit redis.conf and restart. The cap is 128. In this lab’s io-threads 4 run under a benchmark, io_thread_0 stayed at reads=0,writes=0 while threads 1 to 3 each handled a few hundred thousand.
  • Reads and writes both move. io-threads-do-reads is still accepted but has had no effect since 8.0, because the new implementation always uses threads for both.
  • It helps when the main thread is pinned near 100% CPU by many clients, small commands or large replies, and cores are free. The shipped redis.conf advises it only on machines with at least four cores, leaving one spare, and only when Redis is genuinely CPU-bound. Redis measured 37% to 112% more throughput with eight threads on a multi-core Intel CPU, depending on the commands.
  • It does nothing for a slow command. The main thread still executes KEYS alone. I/O threads only let parsed requests queue up more efficiently behind it.
  • Not every client moves. In the 8.10 source, Pub/Sub subscribers, MONITOR clients, blocked clients and client-side-caching (tracking) clients stay on the main thread.
  • Benchmark fairly. A single-threaded load generator saturates before the server does. redis-benchmark --threads N exists for this reason.

If one core is still the ceiling after that, add processes instead of threads. The Redis FAQ suggests running several instances and treating them as separate servers, and Redis Cluster (L29) splits the keyspace across them for you. Replicas (L27) add read capacity, not write capacity.

What the interviewer probes next

1 · “Redis is single-threaded, so how does it serve 10,000 connections?” Non-blocking sockets plus one readiness query per loop turn. The thread sleeps in epoll or kqueue until some sockets are ready, then runs a short handler for each. An idle connection costs a socket and a buffer, not a thread.

2 · “Is that still true in Redis 8?” Command execution is. Optional I/O threads (since 6.0, reimplemented in 8.0) handle socket reads, parsing and writes. Three background threads handle file close, AOF fsync and lazy free, and a forked child writes snapshots.

3 · “Would io-threads fix our KEYS stall?” No. It shortens the conversation around commands, not the commands themselves. Fix the command: SCAN, a maintained index, or a replica.

4 · “We are at 100% of one core. What are the options?” First find out what the time is: one slow command (SLOWLOG) or sheer volume. For volume, pipeline, then try I/O threads on a box with spare cores, then shard with Cluster. For slow commands, slice them or move them.

Think it through

1 · Victim and offender

A probe pings on its own connection in a tight loop, so one PING is always in flight. Its slowest round trip is what an unlucky client feels. The command under test runs on a second connection.

2 · Same scan, two shapes

The pattern matches only 11 of the million keys, so replies are tiny and the cost is the server’s scan. KEYS is one command. SCAN with COUNT 1000 is about a thousand commands, with the client carrying the cursor.

3 · Three views of one stall

Expect the probe’s worst ping to equal the KEYS time, because it waited out the whole command. Expect SLOWLOG, the server’s own clock, to agree within a millisecond or two. Expect the SCAN run to take longer overall but show a worst ping near one slice, plus laptop noise.

4 · Where a command’s time goes

eventloop_duration_cmd_sum divided by eventloop_duration_sum, measured across a benchmark, is the share of busy loop time spent inside commands. Run it at three pipeline depths and the §01 table appears.

The code

python · redis==8.1.0 · event_loop_stall.py

import asyncio
import time
import uuid

import redis.asyncio as aioredis

HOST, PORT = "localhost", 6379
KEY_COUNT = 1_000_000
BATCH_SIZE = 1_000
SETTLE_SECONDS = 0.3
PREFIX = f"lab:loop:{uuid.uuid4().hex[:8]}:"
# The pattern matches only 11 keys, so the reply is tiny and any stall is the
# server's scan, not the client parsing a big reply.
PATTERN = f"{PREFIX}99999*"


async def seed_keys(server):
    pipe = server.pipeline(transaction=False)
    for number in range(KEY_COUNT):
        pipe.set(f"{PREFIX}{number}", number)
        if (number + 1) % BATCH_SIZE == 0:
            await pipe.execute()


async def ping_until(stop, probe):
    worst = 0.0
    while not stop.is_set():
        started = time.perf_counter()
        await probe.ping()
        worst = max(worst, time.perf_counter() - started)
    return worst * 1000


async def measure_stall(command, server, probe):
    stop = asyncio.Event()
    probing = asyncio.create_task(ping_until(stop, probe))
    await asyncio.sleep(SETTLE_SECONDS)
    started = time.perf_counter()
    await command(server)
    command_ms = (time.perf_counter() - started) * 1000
    await asyncio.sleep(SETTLE_SECONDS)
    stop.set()
    return command_ms, await probing


async def keys_matching(server):
    return await server.keys(PATTERN)


async def scan_matching(server):
    scan = server.scan_iter(match=PATTERN, count=BATCH_SIZE)
    return [key async for key in scan]


async def unlink_prefix(server):
    batch = []
    async for key in server.scan_iter(match=f"{PREFIX}*", count=BATCH_SIZE):
        batch.append(key)
        if len(batch) == BATCH_SIZE:
            await server.unlink(*batch)
            batch.clear()
    if batch:
        await server.unlink(*batch)


async def slowlog_ms(server, command_name):
    for entry in await server.slowlog_get(10):
        if entry["command"].startswith(command_name):
            return entry["duration"] / 1000


async def main():
    server = aioredis.Redis(host=HOST, port=PORT, decode_responses=True)
    probe = aioredis.Redis(host=HOST, port=PORT)
    try:
        await seed_keys(server)

        keys_ms, keys_worst = await measure_stall(keys_matching, server, probe)
        scan_ms, scan_worst = await measure_stall(scan_matching, server, probe)
        print(f"KEYS: command {keys_ms:6.1f} ms | worst PING {keys_worst:6.2f} ms")
        print(f"SCAN: command {scan_ms:6.1f} ms | worst PING {scan_worst:6.2f} ms")
        keys_server_ms = await slowlog_ms(server, b"KEYS")
        print(f"SLOWLOG: the server timed KEYS at {keys_server_ms:.1f} ms")

        assert keys_worst > 0.8 * keys_ms
        assert scan_worst < keys_worst
    finally:
        await unlink_prefix(server)
        await server.aclose()
        await probe.aclose()


asyncio.run(main())

shell · redis-cli and redis-benchmark 8.10 · loop_counters.sh

# prints three numbers, in the order INFO lists them: commands run,
# microseconds the loop was busy, microseconds spent inside commands
loop_stats() {
  redis-cli INFO stats | tr -d '\r' | awk -F: '
    /^total_commands_processed:/    { printf "%s ", $2 }
    /^eventloop_duration_sum:/      { printf "%s ", $2 }
    /^eventloop_duration_cmd_sum:/  { printf "%s ", $2 }
    END { print "" }'
}

for depth in 1 16 100; do
  before=$(loop_stats)
  redis-benchmark -t set -r 100000 -n 1000000 -c 50 -P "$depth" -q > /dev/null
  after=$(loop_stats)
  echo "$depth $before $after" | awk '{
    commands = $5 - $2; busy_us = $6 - $3; exec_us = $7 - $4
    printf "pipeline %3d: %.2f us per command, %.0f%% of it executing\n",
           $1, busy_us / commands, 100 * exec_us / busy_us }'
done

Explain it aloud in an interview

“Redis executes commands on one thread. It multiplexes thousands of non-blocking sockets with epoll or kqueue, runs a short handler for each ready socket, and never preempts a command. That gives me atomic commands without locks and one command order for replication, and it means the thread’s time is mostly socket work, so pipelining or I/O threads are the throughput levers. The cost is head-of-line blocking: an O(N) command such as KEYS, a huge SMEMBERS or a long script is every client’s latency. In production I use SCAN with a count, UNLINK for big deletes, paged reads and bounded scripts, and I run slow analytics on a replica. If one core is still the ceiling after I/O threads, I shard.”

Follow-ups to anticipate: why io-threads does not fix a slow command, what SLOWLOG does and does not measure, why SCAN can return duplicates, and what a BUSY error means.

Self-test

1. How can one thread serve thousands of connections without blocking on any of them?

Sockets are non-blocking and the thread makes one readiness query per loop turn (epoll_wait, kevent, event ports or select). It runs a short handler for each ready socket, then polls again. An idle connection costs a socket and buffers, not a thread, and a client that is slow to read leaves its reply in an output buffer instead of stalling the loop.

2. Why are single Redis commands atomic without locks, and what does that not cover?

Only one command executes at a time and each runs to completion, so none can be observed half-done. The same holds for MULTI/EXEC and scripts, which run as one uninterrupted unit. It does not cover a read-compute-write sequence a client spreads over separate commands: other clients’ commands can run between them (L23, L24).

3. KEYS 'user:42:*' returns three keys instantly in a test. Why is it still dangerous in production?

Its cost is O(N) in the number of keys in the database, however many match. Every key name is tested against the pattern while no other command runs. The test database was small and production’s is not. Use SCAN with MATCH and COUNT, or keep a set of each user’s keys.

4. In terms of blocking, how do BLPOP and SMEMBERS on a huge set differ?

BLPOP is a blocking command: it parks the calling client and the loop keeps serving everyone else (counted in blocked_clients). SMEMBERS over millions of members is a slow command: it holds the loop while it visits every element, so every client waits.

5. What do I/O threads parallelize, and what does io-threads 4 mean in Redis 8.10?

Socket reads, request parsing and socket writes, with each I/O thread running its own small event loop over its clients. Commands still execute one at a time on the main thread. io-threads 4 means the main thread plus three I/O threads (INFO threads lists io_thread_0 to io_thread_3). The default is 1 and the setting is immutable at runtime. It helps only when the main thread is CPU-bound on I/O with cores to spare, and it does nothing for a slow command.

6. What does SLOWLOG measure, and why can a client see more latency than it shows?

Only the command’s execution time on the main thread, against a default threshold of 10,000 µs. It excludes reading the request, writing the reply, network time and, above all, the time the request waited behind other commands. A client stuck behind a 140 ms KEYS can see up to about 140 ms while its own GET never appears in the slow log.

7. What does SCAN guarantee, and how do you handle its duplicates?

An element present for the whole walk is returned at least once, and one absent for the whole walk is never returned; elements that appear or disappear mid-walk may or may not be returned. Duplicates can occur, so make per-key work idempotent (UNLINK, set-style writes) or deduplicate on the client. COUNT is only a hint and MATCH filters after fetching, so empty pages are normal. Stop when the returned cursor is 0.
