05Concept · Phase 1 · Redis

Hashes

Changing a display name should not require replacing a whole JSON document. A Redis hash makes flat object fields visible to the server: read a projection, patch one attribute, or increment one counter. The engineering choice is the unit of access—and the boundary over which your invariant must hold.

Original study chapter. Targets Redis Open Source 8.12.0, GA on 22 November 2026. The lab pins redis==8.1.0 and uses Python 3.10 or newer. Contains four original SVG figures, two interactive. This Phase 1 concept lesson covers flat object modeling; L06 opens lists, L15 expiration/eviction internals, L23–L24 transactions/scripts, L33 Redis JSON, and L37 memory tuning.
00 Failure first

Updating one attribute should not replace the whole object ▸

Your service stores {"name":"Linh","visits":7} as a string. A profile worker changes the name while a request worker counts a visit. Both read the same JSON, edit their own copy, and SET it back. Each write is atomic; the second write still erases the first worker's change. Atomic assignment does not make a read–edit–write sequence atomic.

A hash gives Redis visibility into the object's fields. A name update can be HSET user:73 name Mai; a visit can be HINCRBY user:73 visits 1. Neither command sends back the other worker's stale fields. The useful invariant is specific: a field operation touches the fields it names. Two writers assigning the same field can still overwrite one another.

What the interviewer probes next

“Does choosing a hash solve every race?” No. It removes unrelated-field clobbering. HGET visits followed by HSET visits old+1 still loses increments. The operation, not just the container, must match the invariant.

01 Object model

One key, an unordered map, byte-string values

Creating three top-level keys for each user's name, locale and visit count repeats the key prefix and separates a single object's lifecycle. A hash groups those attributes under user:73. Its fields are unique, unordered byte strings; its values are byte strings too. "8" becomes an integer only when a numeric command parses it. There are no automatic nested objects, booleans, required fields or schema migrations.

HSET user:73 name Linh locale vi visits 7
HSET user:73 name Mai
HMGET user:73 visits name missing
HDEL user:73 locale

The first HSET returns 3, the number of new fields. The update returns 0 even though the name changed successfully. HMGET returns ["7", "Mai", nil] in the requested order. Missing key and missing field both read as null; a present empty string reads as "". Use HEXISTS when existence is the question.

Patch is not replacement

If the next version of your app omits legacy_flag from HSET, the old field remains. Delete obsolete fields explicitly. Keep a schema_version field when readers need to interpret evolving layouts; Redis will not enforce it.

A key holding a string makes HGET or HSET fail with WRONGTYPE. SET user:73 blob, however, can replace the entire hash. Give one component ownership of the key's type and field conventions.

02 Atomic operations

Move the increment into the server

Reading visits, adding one in your app, then writing it back costs two command exchanges and admits a lost update. HINCRBY user:73 visits 1 parses and adds inside one Redis command and returns the new integer. Two accepted increments against 7 produce 8 and 9 in some client order. A missing field starts at zero; a missing key is created as a hash.

The range is signed 64-bit, -2^63 through 2^63−1. A non-integer field or an overflowing addition is rejected without changing that field. A decrement is a negative delta. HINCRBYFLOAT handles approximate quantities; integer minor units fit exact amounts better, but using integers alone does not make a durable accounting system.

One operation is atomic

  • HINCRBY stock:73 available -1 cannot lose a concurrent increment.
  • HSET user:73 name Mai locale vi exposes the named changes together.
  • HSETNX combines the existence decision and one field write.

A business condition can span operations

  • “Decrement only if stock is positive” needs the check and write to share an atomic boundary.
  • HGET then HINCRBY leaves a race; inventory can become negative.
  • Several commands in a pipeline do not acquire that boundary. Transactions and scripts come in L23–L24.
A timeout is not an undo

If Redis applied an increment but its reply was lost, retrying applies the increment again. Command atomicity prevents interleaving inside the command; it does not deduplicate application retries or promise persistence across failure.

03 Costs & representation

Read what you need; bound the object you create

A profile starts at six fields, so HGETALL seems harmless. Later, someone adds every activity ID as a field and the same endpoint now downloads an ever-growing collection. The command visits the entire hash and produces every field name and value. Server work, reply bytes, client parsing and allocation all grow.

OperationDocumented timeWhat you must bound
HGET, HINCRBY, HLENO(1)Value size still affects copies and network bytes; the notation is not a latency promise.
HSET, HMGET, HDELO(k)k = supplied fields. Ask for the two fields the screen needs.
HGETALL, HKEYS, HVALSO(n)n = fields stored in the hash. Returned data also needs client space proportional to its bytes.
HSCANO(n) for a complete walkCursor-paced enumeration, not a snapshot or sorted pagination. COUNT is a hint; compact encodings may return everything in one call. Handle duplicates and concurrent changes.

The logical type does not dictate a single memory layout. Ordinary small hashes can use a listpack, packing pairs into a contiguous allocation and searching within a bounded small container. Larger ones use a hash table. Inspect OBJECT ENCODING and the instance's hash-max-listpack-* settings rather than hard-coding a layout into your application.

Redis 8.10 also introduced compact hashes that share field-name sets across many similarly shaped objects. They are opt-in through HIMPORT or conversion settings; ordinary HSET does not mean this feature is enabled. The hash commands retain their public semantics. Savings depend on repeated layouts and field churn, so “hash is always smaller than JSON” is not a defensible rule. Memory tuning and bulk import belong in L37.

Choose a hash when…

  • Fields are flat and updates usually touch a small subset.
  • You need server-side field counters or defaults.
  • One bounded entity fits one key and one shard.

Choose a JSON string when…

  • You normally fetch and replace a complete snapshot.
  • Nested shape belongs to the application's serializer.
  • You can manage concurrency for whole replacements. Redis JSON is another option for nested mutation, covered in L33.

A hash of all users, with user IDs as fields, becomes one hot, large key. Cluster routes the key as a unit; it does not distribute its fields across nodes. Prefer one bounded object per key when independent scaling and lifecycle matter.

04 Lifecycle

A key's TTL and a field's TTL are different clocks ▸

Updating a hash with HSET preserves its existing key expiration, unlike replacing a value with bare SET. But a new hash has no key TTL unless you attach one. Splitting initial HSET and EXPIRE still leaves a crash gap if your invariant requires expiring the entire object; the transaction/script treatment comes later.

Individual hash fields can expire too: HEXPIRE and HTTL arrived in Redis 7.4. HSETEX, since 8.0, writes named fields and their expiration together. These commands set field lifetimes; they do not give the hash key a TTL. If the key expires first, every field goes with it.

HEXPIRE user:73 60 FIELDS 1 visits
HTTL user:73 FIELDS 2 visits missing
HSETEX user:73 EX 60 FIELDS 1 badge active
HSETEX user:73 KEEPTTL FIELDS 1 badge renewed

HTTL returns a per-field array: nonnegative remaining seconds, -1 for an existing persistent field, -2 for an absent field. HSET overwriting a field clears that field's TTL even if its new value is identical; HINCRBY preserves it. Use HSETEX ... KEEPTTL for an assignment that must retain a field's clock. HSETEX returns 1 when the fields were set, not the new-field count returned by HSET.

Lifecycle is part of the model

An expired/deleted key can be recreated by the next HSET or HINCRBY, without the old key TTL. An empty hash cannot serve as a durable “user exists” marker. Keep these facts in the contract before using a hash for sessions or object existence; L15 covers expiration and eviction in depth.

python · hashes_probe.py

import uuid
import redis

server = redis.Redis(host="127.0.0.1", port=6385, decode_responses=True)
profile = f"lab:hashes:{uuid.uuid4().hex}:profile"
empty = f"{profile}:empty"

try:
    assert server.info("server")["redis_version"] == "8.12.0"
    assert server.hset(profile, mapping={"name": "Linh", "visits": 7}) == 2
    assert server.hset(profile, "name", "Mai") == 0
    assert server.hmget(profile, ["visits", "name", "absent"]) == ["7", "Mai", None]
    assert server.hsetnx(profile, "locale", "vi") == 1
    assert server.hsetnx(profile, "locale", "en") == 0
    assert server.hgetall(profile) == {"name": "Mai", "visits": "7", "locale": "vi"}

    first_read = int(server.hget(profile, "visits"))
    second_read = int(server.hget(profile, "visits"))
    server.hset(profile, "visits", first_read + 1)
    server.hset(profile, "visits", second_read + 1)
    assert server.hget(profile, "visits") == "8"
    assert server.hincrby(profile, "visits", 1) == 9
    assert server.hincrby(profile, "visits", 1) == 10
    assert server.hincrby(profile, "new_counter", -2) == -2

    server.expire(profile, 600)
    server.hset(profile, "name", "An")
    assert 0 < server.ttl(profile) <= 600
    assert server.execute_command("HEXPIRE", profile, 120, "FIELDS", 1, "visits") == [1]
    server.hincrby(profile, "visits", 1)
    assert 0 < server.execute_command("HTTL", profile, "FIELDS", 1, "visits")[0] <= 120
    server.hset(profile, "visits", 11)
    assert server.execute_command("HTTL", profile, "FIELDS", 1, "visits") == [-1]
    assert server.execute_command("HSETEX", profile, "EX", 120, "FIELDS", 1, "badge", "active") == 1
    assert server.execute_command("HSETEX", profile, "KEEPTTL", "FIELDS", 1, "badge", "renewed") == 1
    assert 0 < server.execute_command("HTTL", profile, "FIELDS", 1, "badge")[0] <= 120
    assert server.execute_command("HTTL", profile, "FIELDS", 1, "absent") == [-2]
    assert 0 < server.ttl(profile) <= 600

    server.hset(profile, "max", 2**63 - 1)
    try:
        server.hincrby(profile, "max", 1)
    except redis.ResponseError as error:
        assert "overflow" in str(error)
    else:
        raise AssertionError("overflow must be rejected")
    assert server.hget(profile, "max") == str(2**63 - 1)

    server.hset(empty, "blank", "")
    assert server.hget(empty, "blank") == ""
    assert server.hdel(empty, "blank") == 1
    assert server.type(empty) == "none"
    print("verified: patch replies, projections, increments, key/field TTLs, overflow, empty hash")
finally:
    server.unlink(profile, empty)
    server.close()
Explain it aloud

“The hash lets me update the name without replacing a stale copy of the visit count. I use HINCRBY for the count itself, because two field assignments would still race. I bound the object and use HMGET for projections. Each command is atomic, but a stock check followed by a decrement needs a wider boundary, and retrying an increment is still non-idempotent.”

Dry-run: missing key, empty string, an overwritten field, last-field deletion, numeric overflow, key expiry followed by recreation.

Six takeaways

01Expose the unit of changeField operations avoid sending stale unrelated attributes back to Redis.
02HSET patchesUnmentioned fields remain; its integer reply counts newly added fields.
03Use arithmetic operationsHINCRBY is atomic. A separate read and assignment is not an increment.
04Bound collection workHMGET names the fields; HGETALL loads the object. One hash stays on one shard.
05Two expiration scopesHSET keeps key TTL but clears an overwritten field's TTL. Choose the matching write.
06The representation follows accessHashes serve flat partial access; strings serve whole snapshots; nested path access is a different model.

Self-test

1. HSET returned 0. Did the write fail?

No. HSET counts new fields, so updating existing fields can return 0. A command error is a separate reply.

2. Can a hash prevent two workers losing a visit increment?

Only with the right operation: HINCRBY. HGET plus HSET still exposes a read–modify–write race. Assignments to separate fields avoid clobbering one another's unrelated fields.

3. What distinguishes an empty string, an absent field and the last field being deleted?

A present empty value reads as an empty string; an absent field reads as null. HDEL of the final field removes the whole key, so TYPE becomes none.

4. Why can HGETALL become a latency incident?

It walks all stored fields and returns all pair bytes. Its cost follows object growth, not how few fields the endpoint uses. Bound object size; use HMGET for projections and HSCAN for paced enumeration with its cursor caveats.

5. Does HSET preserve an existing expiration?

It preserves the hash key's TTL but clears the TTL on each field it overwrites. HINCRBY preserves an existing field TTL. HSETEX with KEEPTTL retains a field's expiration during assignment; EX sets a new field duration.

6. Does atomic HINCRBY mean an inventory decrement can never oversell or run twice?

No. A positive-stock condition must share the atomic boundary with its update. A lost reply can also cause a client to retry an already applied decrement. Atomicity, idempotency and durability are separate requirements.
