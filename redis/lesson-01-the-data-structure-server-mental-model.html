01Concept · Phase 0 · Redis

The Data-Structure Server Mental Model

Lesson 00 showed why Redis keeps hot data in memory. The next trap is treating that memory like a dumb key → bytes shelf. Inside the server sits one flat dictionary per logical database mapping binary-safe keys to typed, self-contained data structures whose mutations execute in place — eliminating read–modify–write races, wasted bandwidth, and client-side re-sorting.

Original study chapter. Written from scratch for backend and system-design interviews. Target behavior follows Redis Open Source 8.10 (latest stable GA patch line 8.10.3 as of late 2026; 8.12 in RC), and runnable examples target Python 3 with redis==8.1.0 and redis-cli. 00 Failure first

The dumb-cache trap: when key → bytes breaks ▸

Start with the mistake almost every team makes on their first Redis integration. Because developers meet Redis as “a fast cache,” they serialize a whole user profile or shopping cart to JSON, stash it under a string key with SET, and ship every update as GET → parse JSON → change one field → SET. That turns a data-structure server into an opaque byte bucket — and three bugs follow immediately.

  • Lost updates under concurrency — two application servers call GET cart:42 at the same instant, read {"apples": 1}, increment locally to 2, and both write SET back. One increment vanishes silently.
  • Network and CPU amplification — incrementing one 4-byte integer inside a 4 KB JSON payload ships 4 KB down the socket, spends app CPU deserializing and re-serializing every untouched field, and ships 4 KB back.
  • Stale client-side algorithms — maintaining a unique tag set or a top-100 leaderboard by dragging an array out over TCP, deduplicating or sorting in app RAM, and writing the whole list back breaks both freshness and throughput.

Redis was designed to flip that direction of travel. Instead of moving the data over the network to your code, you send a small operation to the data and let the server mutate the structure in place.

The paradigm shift

A dumb cache stores values you replace from the outside. A data-structure server exposes the container’s native mutators — HINCRBY, LPUSH, SADD, ZADD — so updates travel as tiny commands, run against the live structure in RAM, and never overwrite neighboring fields.

01 The map

One flat keyspace of typed values

Hang your mental model on four nested concepts: Instance → Logical DB → Flat Keyspace Dict (+ Expires Dict) → Typed Value Object. Everything you ever inspect, expire, shard, or debug lives somewhere in those four boxes.

  • Logical DB (default 0) — a standalone Redis instance ships with 16 numbered logical databases (0–15, selected via SELECT), each holding its own independent keyspace. Crucially, Redis Cluster supports only database 0 and rejects SELECT with an error. Treat DB 0 as the single place data lives; isolate environments or tenants with separate instances or ACL key prefixes, not logical DB numbers.
  • Flat keyspace dictionary — inside DB 0, keys live in one flat hash table with no engine-level tables, folders, or schemas. Keys are binary-safe byte sequences up to 512 MB (even an empty string or raw bytes works, though keeping keys short and readable avoids costly byte comparisons). Because there are no tables, teams use colons by convention — cart:42 or user:1000:tags — purely for human clarity. The one syntax Redis itself parses inside a key is curly braces {hashtag}, which pin related keys to the same hash slot in Redis Cluster.
  • Parallel expires dictionary — key expiration metadata is stored in an auxiliary hash table mapping expiring keys to millisecond timestamps rather than polluting the value payload itself. (Hash fields can also carry independent per-field TTLs via HEXPIRE, added in Redis 7.4.)
  • Typed value object (redisObject) — every key points to a value tagged with both a logical type (string, hash, list, set, zset, stream, vectorset, …) and an internal memory encoding (int, embstr, raw, listpack, hashtable, intset, quicklist, skiplist). Redis picks and automatically upgrades the compact encoding behind the scenes without changing any command you send.
A keyspace is not a relational table

In Postgres you ask WHERE email = 'a@b.com' and the planner picks an index. In a core Redis keyspace, every O(1) lookup starts from the exact key. There are no foreign keys, no server-side JOINs, and no ad-hoc value scans unless you maintain explicit secondary-index keys (for example, a set or zset per attribute) or use the built-in Query Engine (FT.CREATE, covered in Phase 7).

02 Runtime rules

Type dispatch, WRONGTYPE, and the empty-key invariant ▸

Because values carry their own type tag, every command follows a strict runtime path before touching bytes in memory:

  • 1 · Lookup + lazy expiry gate — Redis hashes the key into DB 0’s keyspace dictionary. If the key appears in the expires table with a timestamp already in the past, Redis removes it immediately on access and treats the key as non-existent (TYPE returns none).
  • 2 · Strict type enforcement (no coercion) — commands belong to a data type. Send LPUSH cart:42 item when cart:42 holds a hash, and Redis will not convert or wrap it — it fails immediately with WRONGTYPE Operation against a key holding the wrong kind of value. Subtlety: storing "42" via SET gives a string encoded internally as int, so INCR works on it because integer parsing is part of the string type, not a separate numeric type.
  • 3 · Auto-create & auto-delete invariant — you never declare a container up front. Running HSET, LPUSH, SADD, or ZADD on a missing key creates it automatically. Equally important, removing the last element deletes the key itself from the keyspace (HDEL, LPOP, SREM, ZREM → EXISTS drops to 0). Streams are the deliberate exception: deleting every entry with XDEL or trimming to length 0 leaves the empty stream key alive (EXISTS == 1) so consumer groups and pending-entry state are not silently wiped.
  • 4 · Synchronous DEL vs. non-blocking UNLINK — both remove keys from the keyspace immediately, but DEL frees every element’s memory synchronously on the main command thread (O(M) work for an M-item collection), whereas UNLINK detaches the key pointer in O(1) and reclaims the underlying memory asynchronously on a background thread.
03 The Redis 8 suite

Core five and the unified platform data types

Starting in Redis 8.0 and continuing through Redis 8.10, capabilities that previously lived in add-on modules sit natively inside core Redis Open Source. You do not need to memorize every command today — what belongs in the mental model is knowing which container shape solves which data problem so you never flatten an object or leaderboard into a plain string.

The Core Five (string, hash, list, set, zset) drive most workloads and occupy Phase 1. Around them sit Phase 2’s specialized structures — stream (append-only consumer-group log), bitmap/bitfield (bit ops inside strings), geospatial (stored atop zset), and probabilistic structures (HyperLogLog on string encoding up to 12 KB, plus native Bloom, Cuckoo, Count-Min Sketch, Top-K, and t-digest) — and Redis 8’s modern platform layer: JSON (ReJSON-RL), TimeSeries (TSDB-TYPE), native Vector Sets (vectorset via VADD/VSIM, introduced in Redis 8.0 for HNSW vector similarity), and Arrays (array via ARSET/ARGET, added in Redis 8.8 for sparse O(1) index-addressed string sequences).

One design decision appears on nearly every backend project: how to store a structured record such as a user session or product item. Three choices live in the keyspace, and their trade-offs show why “just stringify JSON” is only occasionally right:

04 Trade-offs & boundaries

What this model buys — and where it stops

Putting Redis next to a plain byte cache and a relational database makes the boundaries unambiguous. Each engine trades away generality in a different place:

Dimension Plain byte cache (Memcached) Data-structure server (Redis) Relational DB (PostgreSQL)
Keyspace organization Flat key → opaque bytes Flat key → typed container (DB 0) Schemas, tables, rows, foreign keys
Mutation unit Replace whole blob (+ CAS version) In-place container operation (HINCRBY, SADD, ZADD) Multi-row SQL UPDATE inside ACID tx
Atomicity boundary Per single key set/CAS Per single command (MULTI/Lua for multi-step) Arbitrary multi-table ACID transactions
Querying Exact key lookup only Exact key + container ops (or FT.* secondary indexes) Ad-hoc SQL, joins, aggregations
What the interviewer probes next

1 · “If Redis commands are atomic, why did two GET/SET calls race?” Single-command atomicity covers one command running to completion inside Redis. Between two separate network round trips (GET, then your app computes, then SET), another client’s command interleaves cleanly. Multi-step read–branch–write logic needs MULTI/EXEC + WATCH (L23) or server-side Lua / Redis Functions (L24).

2 · “Why does TYPE return string on a Bitmap or HyperLogLog?” Bitmaps and Bitfields manipulate bits inside a standard string value, and HyperLogLog stores its up-to-12 KB registers inside a string-encoded value (so raw GET/SET can even serialize and restore it). By contrast, Geospatial coordinates are stored in a zset.

3 · “Should we put staging in SELECT 1 and prod in SELECT 0?” No. Redis Cluster rejects SELECT (DB 0 only), all logical DBs share one process’s memory limit, eviction pressure, and single-threaded CPU, and FLUSHALL wipes every DB. Isolate environments by instance, or separate teams on one instance using ACL key prefixes in DB 0.

05 Build

Probe the mental model live

This self-contained script exercises every rule from §01–§03 against a local server: inspecting runtime TYPE and OBJECT ENCODING across containers, mutating a single field on a hash atomically, catching a strict WRONGTYPE rejection, proving the empty-key contrast between a set and a stream, and cleaning up with non-blocking UNLINK.

Verification checkpointRunnableRedis 8.10 · redis==8.1.0
Inspect types, encodings, WRONGTYPE, and empty-key lifecycles

Run against a local Redis 8.10 server on localhost:6379 (pip install redis==8.1.0). Uses an isolated prefix and cleans up via UNLINK.

Think it through

1 · Keyspace & encodings

Store an integer string, a short text string, a small hash, and an integer set; read both TYPE (logical contract) and OBJECT ENCODING (physical RAM layout).

2 · Partial in-place write

Increment one field on the hash via HINCRBY and read only that field back with HGET — sibling fields stay untouched.

3 · Type safety & empty keys

Send a list command to the hash key to observe WRONGTYPE, then empty both a set and a stream to confirm EXISTS drops to 0 for the set and stays 1 for the stream.

The code

python · redis==8.1.0

import uuid
import redis

r = redis.Redis(host="localhost", port=6379, db=0, decode_responses=True)
p = f"lab:m1:{uuid.uuid4().hex[:8]}"
k_cnt, k_txt, k_cart, k_tags, k_evt = (
    f"{p}:views", f"{p}:banner", f"{p}:cart", f"{p}:tags", f"{p}:events"
)

try:
    # 1. Populate different logical types and check internal encodings
    r.set(k_cnt, 42)                              # string -> int encoding
    r.set(k_txt, "hello-redis")                   # string -> embstr (<= 44 B)
    r.hset(k_cart, mapping={"apples": 1, "note": "gift"})
    r.sadd(k_tags, 101, 202)                      # small integer-only set

    assert r.type(k_cnt) == "string" and r.object("encoding", k_cnt) == "int"
    assert r.type(k_txt) == "string" and r.object("encoding", k_txt) == "embstr"
    assert r.type(k_cart) == "hash" and r.object("encoding", k_cart) == "listpack"
    assert r.type(k_tags) == "set" and r.object("encoding", k_tags) == "intset"

    # 2. Atomic server-side partial update without reading the whole hash
    new_qty = r.hincrby(k_cart, "apples", 2)
    assert new_qty == 3 and r.hget(k_cart, "note") == "gift"

    # 3. Strict runtime type gate: no silent coercion
    try:
        r.lpush(k_cart, "bad")
        raise AssertionError("Expected WRONGTYPE")
    except redis.exceptions.ResponseError as exc:
        assert str(exc).startswith("WRONGTYPE")

    # 4. Empty-collection invariant: Set auto-deletes, Stream stays alive
    r.srem(k_tags, 101, 202)
    assert r.exists(k_tags) == 0 and r.type(k_tags) == "none"

    eid = r.xadd(k_evt, {"item": "apples"})
    assert r.xdel(k_evt, eid) == 1
    assert r.exists(k_evt) == 1 and r.type(k_evt) == "stream"
    print("verified:", p)
finally:
    # Non-blocking keyspace detachment (frees memory asynchronously)
    r.unlink(k_cnt, k_txt, k_cart, k_tags, k_evt)

Explain it aloud in an interview

“Think of Redis as one flat dictionary in DB 0 where keys are binary-safe names and values are typed in-memory containers — strings, hashes, lists, sets, sorted sets, streams, and Redis 8’s built-in JSON, time-series, vector-set, and array types. Instead of doing a GET, deserializing JSON, and writing the whole blob back — which races under concurrency — I send the mutation directly to the container, like HINCRBY on a hash field. Redis checks TTL lazily, enforces the value’s type with WRONGTYPE, mutates in place, and automatically drops empty core collections when their last item leaves.”

Follow-ups to anticipate: why DEL on a huge hash blocks while UNLINK detaches in O(1), why Streams stay alive when emptied by XDEL, and why multi-command logic still needs Lua or MULTI/WATCH.

Self-test

1. Why does storing an object as JSON in a string and using GET → modify → SET lose updates?

Because GET and SET are two separate network round trips. Two concurrent workers can read the same old snapshot, modify it in their own RAM, and overwrite each other’s changes when writing back — while also paying full-object serialization and wire cost.

2. What is inside a keyspace entry, and what is the maximum key size?

DB 0 holds a flat hash table mapping binary-safe keys (up to 512 MB) to typed value objects (redisObject), paired with an auxiliary expires dictionary for keys carrying TTLs.

3. Why should new applications ignore SELECT 1..15 and keep everything in DB 0?

Redis Cluster supports only database 0 and rejects SELECT. Even on a standalone server, logical databases share one process’s memory limit, eviction, and single-threaded CPU, and FLUSHALL clears all of them.

4. What happens if you run LPUSH on a key already holding a hash, or INCR on SET k "42"?

LPUSH on a hash fails immediately with WRONGTYPE Operation against a key holding the wrong kind of value — Redis never coerces between types. INCR on "42" succeeds because "42" is already type string (internally int-encoded), and integer increments are native string operations.

5. Which data type breaks the “empty containers are automatically deleted” rule, and why?

Streams. Emptying a list, set, hash, or zset deletes its key automatically (EXISTS → 0). Deleting all entries from a stream with XDEL leaves the empty key alive (EXISTS → 1) so consumer group cursors and pending-entry state remain intact until an explicit DEL or UNLINK.

6. When should you reach for UNLINK instead of DEL, and what is the difference between TYPE and OBJECT ENCODING?

Use UNLINK when deleting large multi-element keys: DEL frees elements synchronously on the main thread (O(M)), whereas UNLINK removes the keyspace entry in O(1) and reclaims memory in a background thread. TYPE reports the public logical container (string, hash, set, zset, stream, vectorset), while OBJECT ENCODING reveals the internal RAM representation (such as int, embstr, listpack, intset, or skiplist).
