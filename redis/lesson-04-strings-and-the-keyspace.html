04Concept · Phase 1 · Redis

Strings & the Keyspace

Phase 1 opens the five core data structures one by one, starting with the primitive that every key name and every simple value shares: the binary-safe string and the single global keyspace around it. A Redis string is not a null-terminated text buffer — it is an up-to-512 MB byte sequence that transparently morphs between a 64-bit integer (int), a single-cache-line allocation (embstr), and a preallocated dynamic buffer (raw), while a single SET command folds existence guards, compare-and-set checks, old-value reads, and TTL control into one atomic step.

00 Failure first

Three ways a “simple SET and GET” breaks in production ▸

Because SET and GET look like variable assignment in any programming language, engineers reach for them first and compose multi-step workflows out of separate calls. Under concurrency, restarts, or expiration, three production bugs appear immediately:

  • 1 · The two-step SETNX + EXPIRE crash window — a worker claims an idempotency key or job lock with SETNX lock:invoice:77 worker-a and follows up with EXPIRE lock:invoice:77 30. If the process crashes, pauses in GC, or drops its TCP socket between the two commands, the key stays in RAM with TTL = -1 forever and deadlocks every future run.
  • 2 · Bare SET silently strips an existing TTL (and overwrites any type) — a session key created with a 15-minute expiration has 400 seconds left. Another handler updates the payload with plain SET sess:99 <new_json> — and Redis discards the remaining TTL (TTL becomes -1), turning a bounded cache into an immortal memory leak unless KEEPTTL or a new EX/PX is passed. Worse, bare SET clobbers the key even if it previously held a hash, set, or zset, with no WRONGTYPE warning.
  • 3 · Client-side counter races (GET → +1 → SET) — two API threads read "99", add 1 in application memory, and both write "100" back. One increment vanishes (and if the counter had a TTL, bare SET wipes that too), whereas INCR parses, increments, and stores the 64-bit integer atomically in place while preserving the existing TTL.
The single-command rule for strings

Whenever a string write depends on whether the key exists, what value it currently holds, returning its prior value, or setting/keeping its TTL, express all of those requirements inside one command (SET with flags, INCR, GETEX, or GETDEL). Two commands mean two scheduling turns on the event loop (L02).

01 Mechanism

The Swiss-Army SET, GETEX, GETDEL & why SETNX/SETEX were retired

Early Redis added a new command every time users needed a twist on SET: SETNX (set if not exists), SETEX (set with seconds expiry), PSETEX (set with milliseconds expiry), and GETSET (set and return old value). None of those could be combined — you could not do SETNX and PSETEX together. Starting in Redis 2.6.12 and culminating in Redis 6.0, 6.2, 7.0, and 8.4, Redis deprecated those standalone wrappers and folded every dimension into orthogonal modifier slots on SET:

SET key value [NX | XX | IFEQ val | IFNE val | IFDEQ digest | IFDNE digest]
              [GET]
              [EX seconds | PX milliseconds | EXAT unix-sec | PXAT unix-ms | KEEPTTL]

Read the signature as three independent questions answered inside one atomic event-loop turn:

  • 1 · When should the write proceed? (Condition slot) — by default, SET always writes (and overwrites any existing key, even a non-string container). Adding NX writes only if the key does not exist (returning nil on abort); XX writes only if the key already exists. Starting in Redis 8.4, four compare-and-set conditions let a single SET perform lock-free optimistic concurrency control on existing strings without WATCH or Lua: IFEQ <val> and IFNE <val> compare the current value directly, while IFDEQ <digest> and IFDNE <digest> compare the current value’s 64-bit XXH3 hex digest (returned by DIGEST key) so you can verify a large cached blob hasn’t changed without resending the old blob over the network. (Pair with DELEX key IFEQ|IFNE|IFDEQ|IFDNE ..., also added in 8.4, to delete a key conditionally — such as releasing a lock only if you still own it.)
  • 2 · Should the previous value come back? (GET slot) — adding GET (Redis 6.2+) returns the old string value stored at the key before overwriting it (or nil if the key was absent), replacing deprecated GETSET. Starting in Redis 7.0, SET key val NX GET is legal: if the key already exists, the write is skipped and the current holder’s value comes back in the same round trip. Unlike bare SET, passing GET enforces type safety and aborts with WRONGTYPE if the existing key is not a string.
  • 3 · What happens to the key’s expiration? (TTL slot) — without a TTL modifier, SET removes any existing expiration (TTL → -1). Pass EX (seconds) or PX (milliseconds) for relative durations, EXAT or PXAT (Redis 6.2+) for an exact Unix timestamp so client retries remain idempotent, or KEEPTTL (Redis 6.0+) to preserve whatever remaining TTL the key already carried.

Two read-side companions added in Redis 6.2 complete the single-key atomic toolkit: GETDEL key fetches a string and immediately deletes the key (ideal for one-time verification codes or OAuth state nonces), and GETEX key [EX s | PX ms | EXAT ts | PXAT ms-ts | PERSIST] fetches a string while sliding or clearing its expiration in one call.

02 Under the hood

Binary safety, SDS, and the three string encodings (int, embstr, raw) ▸

In C, a string is a pointer to characters terminated by a zero byte (\0). If Redis used raw C strings, storing a PNG image, a Protobuf message, or UTF-8 text containing \x00 would truncate the value early, STRLEN would cost an O(N) scan, and every APPEND would force a fresh malloc. Instead, Redis builds every string buffer on SDS (Simple Dynamic String): a compact struct packing explicit len (used bytes), alloc (allocated capacity), a 1-byte header flag, and the raw byte array (followed by a hidden \0 so C library functions still work). Because len is stored explicitly, STRLEN is always O(1) and any byte sequence up to 512 MB is valid.

Above SDS sits the 16-byte redisObject header (L01). Whenever you write a string, Redis inspects the payload and chooses one of three physical encodings (visible via OBJECT ENCODING key):

  • 1 · int (8-byte integer packed inside the pointer) — if the string is a base-10 integer that fits in a signed 64-bit integer (-9,223,372,036,854,775,808 to 9,223,372,036,854,775,807, ≤ 20 digits), Redis skips SDS allocation entirely and casts the 64-bit integer directly into the 8-byte ptr field of redisObject. Small integers 0..9999 even share a preallocated pool (OBJ_SHARED_INTEGERS) when the active maxmemory-policy does not need per-key LRU/LFU timestamps.
  • 2 · embstr (single-allocation cache-line string, ≤ 44 bytes) — for non-integer strings of 44 bytes or fewer, Redis allocates the 16-byte redisObject, the 3-byte sdshdr8 header, up to 44 payload bytes, and the 1-byte \0 terminator in one contiguous block of ≤ 64 bytes (16 + 3 + 44 + 1 = 64). Sixty-four bytes matches a standard CPU cache line and a single jemalloc size class: one allocation, one free, zero pointer-chasing.
  • 3 · raw (two allocations with greedy SDS preallocation, > 44 bytes or mutated) — once a string exceeds 44 bytes, Redis allocates the redisObject and the SDS buffer separately. Furthermore, embstr has no spare capacity and is treated as read-only: calling APPEND or SETRANGE on an int or embstr key automatically promotes it to raw (even if the resulting length is still under 44 bytes) and preallocates extra space — doubling capacity up to 1 MB and adding 1 MB chunks above that — so sequential APPEND calls run in amortized O(1).

Four byte-slice commands work directly on the SDS buffer: STRLEN key returns the byte count in O(1); APPEND key suffix appends bytes in amortized O(1) and returns the new byte length; GETRANGE key start end (which replaced the deprecated SUBSTR alias) extracts a slice in O(N) where N is the returned slice length, supporting negative offsets from the end (-1 is the last byte); and SETRANGE key offset value overwrites bytes starting at offset, zero-padding any gap with \x00 bytes if the key was shorter or empty. Need to diff two strings server-side? Redis 7.0+ includes LCS key1 key2 [LEN] [IDX] [MINMATCHLEN n] to compute their Longest Common Subsequence (for example, comparing two cached config revisions or biological sequences without pulling both blobs to the client).

Watch the SETRANGE zero-padding trap

Running SETRANGE buf 104857600 "x" on a missing key allocates a 100 MB SDS buffer filled with \x00 bytes and zeroes it on the main command thread — stalling the event loop while memory spikes. Always validate caller-supplied offsets before passing them to SETRANGE (or SETBIT in L10).

03 Counters & batches

Atomic counters (INCR, INCRBYFLOAT) and multi-key strings (MGET, MSETNX, MSETEX)

Because the event loop executes one command at a time (L02) and recognizes integer-formatted strings natively, Redis strings double as lock-free distributed counters:

  • 64-bit integer counters (INCR, INCRBY, DECR, DECRBY) — each command runs in O(1), returns the new integer reply, and obeys two key invariants: (1) if the key does not exist, Redis creates it as "0" before applying the delta (so INCR page:views on a missing key returns 1), and (2) if the key already exists with a TTL, INCR preserves that TTL untouched. If the stored value cannot be parsed as a strict base-10 signed 64-bit integer (for example, "12.5", " 42 ", or a value overflowing 9,223,372,036,854,775,807), Redis makes no change and returns ERR value is not an integer or out of range.
  • Floating-point counters (INCRBYFLOAT key delta) — parses the value as a double-precision float, adds delta (positive or negative), formats the result up to 17 digits after the decimal point (trimming trailing zeroes), and stores it back as an embstr/raw decimal string while preserving any TTL. It rejects inf and nan. Because binary floating-point arithmetic accumulates rounding drift (0.1 + 0.2), never use INCRBYFLOAT for currency balances — store integer minor units (cents, satoshis, VND) and use INCRBY.
  • Multi-key reads & writes (MGET, MSET, MSETNX, MSETEX) — when fetching 20 user avatars or writing a batch of string keys, firing 20 sequential GET calls pays 20 network round trips. MGET k1 k2 ... fetches all of them in one O(N) call and returns a positionally aligned array with nil for any missing key (and, interestingly, returns nil rather than failing with WRONGTYPE if one of the keys happens to hold a non-string container!). MSET k1 v1 k2 v2 ... writes every pair atomically (clearing any prior TTLs on those keys). MSETNX k1 v1 k2 v2 ... is an all-or-nothing guard: it sets all keys and returns 1 only if none of the keys exist; if even a single key is already present, it aborts and sets zero keys (returning 0). And starting in Redis 8.4, MSETEX numkeys k1 v1 [k2 v2 ...] [NX|XX] [EX|PX|EXAT|PXAT|KEEPTTL] sets multiple string keys atomically with a shared expiration and condition in a single call.

INCRBY (signed 64-bit int)

  • Exact 64-bit integer math (-2^63 to 2^63 - 1).
  • Keeps compact int encoding in RAM (16 B object, 0 SDS bytes).
  • Dedicated INCR, DECR, INCRBY, DECRBY commands.
  • Use for rate limiters (L26), sequence IDs, inventory counts, and money in minor units (cents).

INCRBYFLOAT (IEEE 754 float)

  • Approximate base-10 float rounded to 17 decimal places.
  • Converts value encoding from int to embstr/raw text.
  • Decrement by passing a negative increment (INCRBYFLOAT k -1.5).
  • Use for scientific scores, sensor averages, or weights — never for exact currency ledgers.
04 Keyspace design

The single global keyspace: naming conventions, {hashtags} & lifecycle hygiene

Every string, hash, list, set, sorted set, and stream in DB 0 shares one flat keyspace dictionary (L01). There are no tables or namespaces enforced by the engine: if the checkout team and the marketing team both write to campaign:42, the second write silently overwrites the first. Good Redis architecture treats key naming as schema design:

  • 1 · Hierarchical colon prefixes (human convention) — structure keys from broadest domain to specific identifier and attribute: <domain>:<entity>:<id>[:<field>], such as shop:cart:8841, auth:otp:99201, or rate:login:192.0.2.9. Redis attaches no special meaning to : — it is a human convention that makes SCAN 0 MATCH shop:cart:*, ACL key rules (~shop:cart:*, L39), and memory attribution tools readable.
  • 2 · Curly-brace hash tags {...} (engine routing rule) — the one character sequence Redis does parse inside a key name is the first non-empty pair of curly braces {...}. In Redis Cluster (L29), the keyspace is partitioned across 16,384 hash slots via CRC16(key) mod 16384, and multi-key commands (MGET, MSET, MSETNX, MSETEX, RENAME, LCS) fail with CROSSSLOT Keys in request don't hash to the same slot unless every key in the command maps to the same slot. Wrapping the shared entity ID in braces — shop:user:{42}:profile and shop:user:{42}:prefs — tells Redis to hash only the bytes 42 (which maps to slot 8000), co-locating both keys on the same shard even before you migrate from standalone Redis to Cluster.
  • 3 · Key-name byte budget at scale — every key name is stored as its own SDS string in the keyspace hash table. At 10,000 keys, verbosity costs nothing; at 100 million keys, a 70-byte key name consumes ~7 GB of RAM before storing a single value byte. When a dataset scales into tens of millions of keys, shorten prefixes systematically (u:{42}:prof) or group sibling attributes into fields of a single hash key (HSET user:42 profile ... prefs ..., covered in L05).

Alongside string operations, a handful of generic keyspace commands manage any key regardless of its data type. Figure 4 maps which command to reach for across a key’s lifecycle, and the table below pins down their edge cases:

What the interviewer probes next

1 · “What happens to a key’s TTL when you run SET versus INCR or APPEND?” A plain SET key val replaces the key’s value object and clears its TTL to -1 unless you explicitly pass KEEPTTL or a new EX/PX. By contrast, in-place string mutators — INCR, INCRBY, DECR, INCRBYFLOAT, APPEND, and SETRANGE — modify the existing string value and preserve the existing TTL.

2 · “Why is the embstr cutoff 44 bytes specifically?” A redisObject is 16 bytes, an sdshdr8 header is 3 bytes, and SDS appends 1 null terminator byte (16 + 3 + 1 = 20 bytes of overhead). That leaves exactly 64 - 20 = 44 payload bytes inside a single 64-byte jemalloc allocation and CPU cache line. At 45 bytes Redis switches to two allocations (raw). Calling APPEND on an embstr also converts it to raw because embstr is immutable.

3 · “How do you distinguish a key with no expiration from a missing key using TTL?” Since Redis 2.8, TTL (and PTTL/EXPIRETIME) returns -1 when the key exists but has no associated expiration, and -2 when the key does not exist at all.

4 · “Why did MGET user:42:name user:42:email work on our local Docker Redis and fail with CROSSSLOT in production Cluster?” Standalone Redis keeps all keys in one hash table; Redis Cluster partitions keys across 16,384 hash slots by hashing the full key name unless curly braces {...} are present. Rename the keys to user:{42}:name and user:{42}:email so Cluster hashes only 42 and places both keys in slot 8000.

The code

python · redis==8.1.0 · strings_keyspace_probe.py

import uuid
import redis
from redis.crc import key_slot

r = redis.Redis(host="localhost", port=6379, db=0, decode_responses=True)
p = f"lab:s4:{uuid.uuid4().hex[:8]}"
k_enc, k_short, k_bin, k_ttl, k_lock, k_otp = (
    f"{p}:enc", f"{p}:short", f"{p}:bin", f"{p}:ttl", f"{p}:lock", f"{p}:otp"
)
k_u1, k_u2 = f"{p}:user:{{42}}:profile", f"{p}:user:{{42}}:prefs"

try:
    # 1. Three string encodings: int -> embstr (<= 44 B) -> raw (>= 45 B)
    r.set(k_enc, "42000")
    assert r.object("encoding", k_enc) == "int"

    r.set(k_enc, "a" * 44)
    assert r.object("encoding", k_enc) == "embstr" and r.strlen(k_enc) == 44

    r.set(k_enc, "a" * 45)
    assert r.object("encoding", k_enc) == "raw" and r.strlen(k_enc) == 45

    # APPEND on a short embstr promotes it to raw (embstr is read-only)
    r.set(k_short, "hello")
    assert r.object("encoding", k_short) == "embstr"
    new_len = r.append(k_short, "!")
    assert new_len == 6 and r.object("encoding", k_short) == "raw"
    assert r.getrange(k_short, -2, -1) == "o!"

    # Binary safety with embedded null bytes (\x00)
    r.set(k_bin, "ab\x00cd")
    assert r.strlen(k_bin) == 5 and r.get(k_bin) == "ab\x00cd"

    # 2. TTL behavior: INCR and KEEPTTL preserve TTL; bare SET wipes it to -1
    r.set(k_ttl, 10, ex=120)
    assert r.incrby(k_ttl, 5) == 15 and r.ttl(k_ttl) > 0

    r.set(k_ttl, 20, xx=True, keepttl=True)
    assert r.get(k_ttl) == "20" and r.ttl(k_ttl) > 0

    r.set(k_ttl, 99)  # bare SET without KEEPTTL or EX/PX
    assert r.ttl(k_ttl) == -1  # -1 = exists with no expiration!
    assert r.ttl(f"{p}:missing") == -2  # -2 = key does not exist

    # 3. Atomic claim with SET NX PX + conflict inspection with NX GET
    assert r.set(k_lock, "worker-a", nx=True, px=30000) is True
    holder = r.set(k_lock, "worker-b", nx=True, px=30000, get=True)
    assert holder == "worker-a" and r.get(k_lock) == "worker-a"

    # One-time token consumption with GETDEL
    r.set(k_otp, "839201", ex=60)
    assert r.getdel(k_otp) == "839201" and r.getdel(k_otp) is None

    # 4. {hashtag} slot co-location & all-or-nothing MSETNX
    # CLUSTER KEYSLOT errors on a standalone server, so compute the slot client-side
    slot1, slot2 = key_slot(k_u1.encode()), key_slot(k_u2.encode())
    assert slot1 == 8000 and slot2 == 8000

    assert r.msetnx({k_u1: "ada", k_u2: "dark"}) is True
    # Second MSETNX fails entirely because k_u1 already exists
    assert r.msetnx({k_u1: "overwrite", f"{p}:user:{{42}}:new": "x"}) is False
    assert r.mget(k_u1, k_u2) == ["ada", "dark"]
    print("verified:", p, "slot=", slot1)
finally:
    r.unlink(k_enc, k_short, k_bin, k_ttl, k_lock, k_otp, k_u1, k_u2)

Explain it aloud in an interview

“A Redis string is a binary-safe byte array up to 512 MB backed by Simple Dynamic Strings, so STRLEN is O(1) and payloads with null bytes work safely. Under the hood Redis picks one of three encodings — int for 64-bit integers inside the pointer itself, embstr for strings up to 44 bytes in a single 64-byte cache-line allocation, and raw with preallocation above 44 bytes or after APPEND. On the command side, modern SET replaces deprecated SETNX, SETEX, and GETSET by combining NX/XX/IFEQ, GET, and EX/PX/KEEPTTL in one atomic turn — and I always remember that bare SET strips an existing TTL while INCR preserves it.”

Self-test

1. Why are SETNX, SETEX, PSETEX, and GETSET considered deprecated, and what replaces them?

They could not be composed with one another (leading to racy two-step calls like SETNX then EXPIRE). Modern SET replaces all four via composable flags: NX/XX/IFEQ, GET, and EX/PX/EXAT/PXAT/KEEPTTL.

2. What is the difference between how SET key val and INCR key treat an existing expiration?

A plain SET key val strips any existing TTL (resetting TTL to -1) unless you pass KEEPTTL or a new EX/PX. INCR (along with INCRBY, DECR, INCRBYFLOAT, APPEND, and SETRANGE) modifies the string in place and preserves the existing TTL.

3. When does Redis use int, embstr, and raw encodings for a string, and why is the cutoff 44 bytes?

int is used for base-10 integers fitting in a signed 64-bit integer; embstr is used for strings ≤ 44 bytes (because a 16-byte redisObject + 3-byte sdshdr8 + 44 bytes + 1-byte \0 = 64 bytes, fitting one cache line and allocator chunk); raw is used for strings > 44 bytes or any string modified by APPEND/SETRANGE.

4. What happens if you call INCR on a missing key versus a key holding "3.14" or "9223372036854775807"?

On a missing key, INCR initializes the key to 0 and increments it to 1. On "3.14" it fails with ERR value is not an integer or out of range; at the maximum signed 64-bit integer (2^63 - 1) the stored value parses fine but the add would wrap, so it fails with ERR increment or decrement would overflow. Either way the key is left unchanged.

5. What does MSETNX k1 v1 k2 v2 do if k1 is missing but k2 already exists?

Nothing is written and it returns 0. MSETNX is atomic and all-or-nothing: if even one key in the argument list already exists, none of the keys are modified.

6. What do TTL return values -1 and -2 mean, and what hazard does RENAME src dst carry?

TTL returns -1 when the key exists without an expiration, and -2 when the key does not exist. RENAME src dst silently executes an implicit synchronous DEL dst if dst already exists — which can clobber data or block the event loop if dst held a huge container. Use RENAMENX to guard against overwriting.

7. Why should paired keys use shop:user:{42}:profile and shop:user:{42}:prefs instead of shop:user:42:profile?

Curly braces define a Cluster hash tag: Redis hashes only the substring inside the first non-empty {...} (42 → slot 8000), ensuring related keys live on the same hash slot so multi-key operations like MGET, MSETNX, and MSETEX never fail with CROSSSLOT.
