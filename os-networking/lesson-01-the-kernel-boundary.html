The Kernel Boundary: User Space, Kernel Space & System Calls

Your runtime can parse a request in ordinary user-space code, then ask the kernel to read a socket, manage a mapping or wait for input. That boundary provides protection and a precise return contract. Understanding when you cross it—and when a library avoids crossing it—is the foundation for explaining both correctness bugs and avoidable overhead.

00 Failure first

One function call in your code, several different paths below it

A service calls clock_gettime() a thousand times, yet strace shows no matching syscall. Another service calls read() once and waits a second. A third reports “one context switch per syscall” and blames the scheduler. These observations become useful only after separating three events: calling a library function, entering the kernel, and switching which thread runs.

A system call is a controlled request to the kernel through its binary interface. It is not an ordinary jump to an arbitrary privileged function. Your thread supplies an operation number and arguments; the processor enters a configured kernel entry point; the kernel decides whether and how to perform the request. The same thread can then return immediately, without another thread ever running.

The invariant to keep

Crossing the privilege boundary changes what code may do. A scheduler switch changes which task is executing. A syscall always requires the first transition when it actually enters the kernel; it does not require the second.

This chapter stays at the level you use to debug services: permissions, call paths, return contracts and avoidable crossings. L02 supplies the latency ladder; L03 traces a whole request; L04–L07 open processes and scheduling. You do not need to memorize entry assembly to explain a slow read.

01 Protection

User space and kernel space are protection domains

If any application could program devices, replace page tables or read another process's memory at will, a bad pointer in one service could corrupt the machine. The CPU's privilege rules and memory permissions let Linux expose selected operations while keeping control of shared resources.

User mode is where your application, runtime and libc normally execute. They use the memory mappings they are allowed to access. Kernel mode permits the kernel's privileged instructions and protected mappings. On conventional x86-64 Linux these correspond to ring 3 and ring 0; on AArch64 the usual host application/kernel distinction is EL0/EL1. Those names are architecture-specific, not extra processes on the machine.

Being root does not turn a normal load instruction into a permitted read of kernel memory. Credentials and capabilities influence checks the kernel performs; they do not move the application's instructions into kernel mode. Containers also run ordinary user-space code against a kernel, with additional resource and policy boundaries.

What runs without a syscall

  • Arithmetic, parsing and ordinary function calls on accessible memory.
  • Many allocator operations satisfied from a user-space arena.
  • Some time reads through the vDSO fast path.

What needs kernel involvement

  • Requesting I/O, creating a socket or changing memory mappings.
  • Enforcing permissions and resolving a descriptor to a kernel object.
  • Handling a hardware exception such as a page fault—even though it was not a syscall request.
What the interviewer probes next

“Does touching a fresh memory page call malloc in the kernel?” No. A load/store can fault and enter the kernel through an exception path. A library allocator, a mapping syscall and a page fault are different events. L11–L13 unpack that chain.

02 Mechanism

Follow one read across the boundary ▸

Calling read(fd, buf, 8) begins as a C function call to a user-space wrapper. The wrapper puts the syscall number and arguments into the architecture's prescribed registers, then executes the entry instruction. On x86-64 that instruction is syscall; on AArch64 it is svc #0. The address in buf remains an address in the calling process's virtual address space; passing it is not transferring ownership of a C object.

Hardware and Linux's entry code establish the privileged execution state, save the return state and register context needed by the entry path, and establish the kernel stack/frame. Entry work may include tracing, security filters and accounting. The dispatcher selects the implementation; the implementation checks the descriptor and accesses user memory through the kernel's user-access machinery. Bad input must produce a controlled failure rather than a trusted arbitrary kernel pointer.

The kernel executes this syscall in the calling thread's context. It is not sending every request to a separate “kernel process.” If data is already available, the read may complete on this path without blocking. If a blocking socket has no data, the thread can sleep; the scheduler may run another task. Once data arrives and the thread gets CPU time again, its kernel path finishes and returns toward user mode. Signals and scheduling work may be handled before the final return.

EventWhat changedWhat you cannot infer
Syscall entry / returnPrivilege domain and execution path, with entry/exit bookkeeping.That another thread ran, a disk was touched, or the requested operation fully completed.
Scheduler context switchThe current runnable task on a CPU.That it was caused by a syscall; preemption can happen for other reasons.
Page fault / interruptControl enters a kernel handler for an exception or hardware event.That the application explicitly called a system-call wrapper.

Syscall numbers and register conventions vary by architecture. Use libc wrappers or SYS_* constants from <sys/syscall.h> for an experiment. In the lab, syscall(SYS_clock_gettime, ...) is itself a libc helper that performs the real kernel entry; it is not a portable replacement for the high-level API.

03 The return contract

A successful call can still leave work for you

A server asks read for eight bytes, receives three, and treats the reply as a broken connection. The kernel did what the API promised: a read requests up to a count. The call's result is progress, not your application's message framing. TCP and application framing come later; this return contract already matters for pipes and files.

ResultMeaning for this I/O callApplication decision
read returns n > 0Exactly n bytes were read, possibly fewer than requested.Advance by n; decide whether the logical record needs more.
read returns 0With a positive requested size on an ordinary file/pipe/stream socket, end of input.Handle EOF; don't reinterpret it as “try again when readable”. Zero-length datagrams have different semantics.
-1 with EAGAIN/EWOULDBLOCKA nonblocking descriptor would need to wait.Arrange readiness notification, then retry. A busy retry loop wastes CPU.
-1 with EINTRA signal interrupted the read before bytes were transferred.Apply cancellation/retry policy. Some calls restart automatically under documented signal rules.
-1 with EBADF / EFAULTInvalid descriptor / inaccessible buffer address.Fix the handle or memory-lifetime bug; repeating the same request won't repair it.

For the usual libc wrappers, an error becomes -1 plus a thread-local errno. On x86-64 the raw kernel ABI uses negative error numbers, and libc translates them. Other architectures may use an error flag/register. The libc syscall() helper also performs error translation, so calling it does not give you the raw negative kernel error code.

Read errno only after the return value indicates failure, and save it before another library call can change it. Success does not promise to clear a stale errno. Apply the same progress discipline to write: a positive short write needs the remaining bytes handled. A successful write is also not an application-level receipt or a disk-durability promise.

What the interviewer probes next

“Why didn't the kernel fill all eight bytes?” Because availability and your desired logical message are separate contracts. Explain the return count, EOF and would-block behavior before suggesting a loop; a loop must also handle cancellation and backpressure.

04 Shortcut

The vDSO: kernel-supplied code that can run in user mode ▸

Entering the kernel for every timestamp in a hot loop would repeat the boundary work even when the answer can be derived safely from information already exposed to the process. The vDSO—virtual dynamic shared object—is a small kernel-provided ELF library mapped into the process. libc can resolve supported functions there and call them like user-space functions.

For a supported time-read fast path, this code combines kernel-maintained timing data with an appropriate clocksource reading. It does not grant user space permission to change kernel time. A clock_gettime(CLOCK_MONOTONIC, ...) call can therefore complete in user mode, while explicitly invoking syscall(SYS_clock_gettime, ...) takes the kernel route.

This is why a working time-read loop can be absent from strace. The vDSO path never made that syscall. The library can fall back to kernel entry when the function, requested clock or environment cannot use the fast path. A mapping named [vdso] proves the object is present; it does not prove a particular call used it.

Keep the shortcut behind the API

Call clock_gettime normally. Resolving vDSO symbol names and versions yourself adds architecture and ABI dependencies that libc already handles. The vDSO is a carefully chosen fast path, not a general way to perform arbitrary protected I/O without the kernel.

The reusable diagnostic lesson extends beyond clocks: printf can buffer many writes in user space, and an allocator can reuse an arena. Library-call count and syscall count need not match in either direction. Conversely, not seeing a syscall is not evidence that a function failed to execute.

05 Costs & trade-offs

Pay for a boundary when it buys useful work

One byte per write repeats the syscall entry and exit for every byte. Collecting a bounded chunk before writing can do the same useful I/O with fewer crossings. The reason is structural: a normal function call changes control flow within one protection domain; a syscall also pays for entry/exit state, dispatch and policy checks, plus whatever work the implementation performs.

On systems using page-table isolation, entry and exit can also change page-table context. Architecture, CPU mitigations, active tracing, cache state, kernel configuration and the syscall itself affect the cost. Do not say every syscall flushes the entire TLB, copies a payload, performs disk I/O or takes the same fixed number of nanoseconds.

Fewer crossings can help

  • Bounded buffering amortizes entry/exit across several small records.
  • Normal libc time APIs can use the vDSO.
  • Measure call frequency and useful bytes per call before changing the design.

Batching has a price

  • Waiting to fill a batch adds delay to early records.
  • Buffers consume memory and need backpressure.
  • Long blocking waits are not explained by entry overhead alone. Find what the operation was waiting for.

strace -T gives elapsed time between observed entry and return, with tracing overhead. It can include time the thread spent waiting. It is not a pure CPU instruction-cost measurement. A low syscall count can coexist with expensive user-space parsing, lock contention or waiting for the scheduler. L02 supplies orders of magnitude; L33 covers deeper performance diagnosis.

1 · Predict the trace

Both modes call a clock API exactly 1,000 times. Only the syscall mode forces 1,000 real clock syscalls. The normal libc mode may use the vDSO; leave its fallback visible rather than asserting a universal zero.

2 · Make progress observable

A pipe contains three bytes and its writer is closed before an eight-byte read. Expect three, then EOF. An invalid descriptor must report -1 with EBADF.

C11 · boundary_probe.c · compile with assertions enabled

#define _GNU_SOURCE
#include <assert.h>
#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <sys/auxv.h>
#include <sys/syscall.h>
#include <time.h>
#include <unistd.h>

int main(int argc, char **argv) {
    if (argc != 2 || (strcmp(argv[1], "libc") != 0 &&
                      strcmp(argv[1], "syscall") != 0)) {
        fprintf(stderr, "usage: %s libc|syscall\n", argv[0]);
        return 2;
    }
    const int force_syscall = strcmp(argv[1], "syscall") == 0;
    const int clock_calls = 1000;
    struct timespec timestamp;
    for (int call = 0; call < clock_calls; call++) {
        long status;
        if (force_syscall) {
            status = syscall(SYS_clock_gettime, CLOCK_MONOTONIC, &timestamp);
        } else {
            status = clock_gettime(CLOCK_MONOTONIC, &timestamp);
        }
        assert(status == 0);
    }

    int channel[2];
    assert(pipe(channel) == 0);
    assert(write(channel[1], "abc", 3) == 3);
    assert(close(channel[1]) == 0);
    char buffer[8];
    ssize_t received = read(channel[0], buffer, sizeof buffer);
    assert(received == 3);
    assert(memcmp(buffer, "abc", 3) == 0);
    assert(read(channel[0], buffer, sizeof buffer) == 0);
    assert(close(channel[0]) == 0);

    ssize_t status = read(-1, buffer, sizeof buffer);
    int saved_errno = errno;
    assert(status == -1 && saved_errno == EBADF);
    printf("clock_mode=%s calls=%d vdso_mapping=%s\n", argv[1], clock_calls,
           getauxval(AT_SYSINFO_EHDR) ? "present" : "absent");
    printf("short_read=%zd eof=0 invalid_fd=-1 errno=EBADF\n", received);
    return 0;
}

Use only this small experiment with assertions enabled; compiling with -DNDEBUG would remove the calls placed in assert. In io.trace, look for the pipe's "abc" read and the read(-1, ...) error; loader startup can contribute other reads. Do not expect numeric descriptor values to be fixed.

On a machine using the vDSO for this clock, the two clock trace files have 0 and 1,000 lines respectively. These are conditional expected counts from the program, not latency measurements. If libc also makes clock syscalls, inspect the architecture/kernel/clock environment before concluding the tracer is wrong. Both modes must still pass the I/O assertions.

Local verification: this chapter's probe was run in Debian 13 user space on a Docker Linux 6.10.14-linuxkit kernel. It passed the assertions and showed the vDSO fast path. The current 7.3.6 / 6.18 contracts above were checked against the official documentation; this run does not claim to be a test boot of either kernel.

Explain it aloud

“My library call may stay in user space or enter through the syscall ABI. Actual entry executes controlled kernel code on behalf of my thread, checks the request, and returns a result. It can block and cause a task switch, but entry alone does not require one. I check progress and errno at the return boundary. For time reads, libc can use a kernel-supplied vDSO function without leaving user mode.”

Follow-ups: root versus kernel mode, short reads, syscall retry policy, vDSO fallback, and elapsed syscall time versus CPU work.

Six takeaways

01Privilege is not identityUID 0 is still user-space code until it enters a privileged kernel path.
02The ABI is a controlled gateOperation numbers and argument conventions select defined kernel services.
03A mode switch is not a task switchThe caller can enter and return without another thread running.
04Results describe progressShort reads/writes, EOF and errno are part of the contract, not exceptional trivia.
05vDSO code can stay in user modeA normal libc time call can avoid an actual syscall and be absent from strace.
06Amortize with limitsFewer crossings help when they remove real overhead; batching adds delay and memory.
? Active recall

Self-test

1. Is a root process executing in kernel mode?

No. Credentials affect permission checks; the application's normal instructions still execute in user mode. Controlled entry changes the CPU's execution domain.

2. Must a syscall switch to a different process?

No. It enters privileged kernel code in the caller's task context. Blocking or preemption can cause a scheduler switch, but the privilege transition itself does not require one.

3. Does an eight-byte read returning three mean an error?

No. Three is a successful progress count. Handle the remaining logical input according to framing. A later zero-size result for a positive-length read on a pipe indicates EOF; a nonblocking would-block result is -1 with EAGAIN/EWOULDBLOCK.

4. Why can syscall(SYS_read, ...) return -1 rather than a negative EBADF code?

syscall() is a libc helper. Like the ordinary wrapper, it translates the kernel's error convention into the library's -1 and errno convention. Only inspect errno when the return contract says the call failed.

5. Why might clock_gettime be absent from strace while the loop still works?

libc can call the mapped vDSO implementation, which answers in user mode on a supported fast path. The explicit syscall mode forces kernel entry. Fallbacks depend on architecture, clock and environment.

6. A read took 100 ms under strace -T. Is that 100 ms of syscall entry overhead?

No. It is traced elapsed time from entry to return and may include waiting, scheduling delay and tracing effects. Separate the operation's wait from the structural crossing cost before choosing a fix.
