00Concept · Core · Phase 0 · Foundations

Why OS & Networking Matter to a Backend Engineer

In your editor, an HTTP endpoint is ten clean lines of code: parse the request, query a database or read a file, serialize JSON, return 200 OK. In production, those ten lines never touch a network cable, a disk drive, a physical RAM address, or a CPU scheduler directly. Every byte crosses into the Linux kernel and out onto the network stack — and when tail latency spikes to 800 ms, connections fail with EMFILE or ECONNRESET, or a container vanishes with exit code 137, the bug lives below your code. This opening lesson walks one request across every layer so you can name the layer before you name the fix.

Original study chapter. Written from scratch for backend, infrastructure, and platform interviews — and for the production incidents behind them. Operating-system behavior targets Linux (the 7.x stable line and the 6.18 LTS kernel as of late 2026, including the EEVDF scheduler, cgroup v2, and epoll/io_uring); networking follows IETF TCP (RFC 9293), TLS 1.3 (RFC 8446), and HTTP/1.1–HTTP/3 (RFC 9110–9114); runnable code uses standard-library Python 3.12+. 00 Failure first

The 10-line handler lie: why your hardest bugs leave no trace in application code

Start with the incident every backend engineer eventually meets. Your checkout or order-lookup endpoint is ten lines of Python, Go, Java, or Node. Unit tests pass in two milliseconds. You deploy to Kubernetes, traffic ramps up, and four alarms fire over the next month — none of which point to a single buggy line in your repository:

  • 1 · The 800 ms tail-latency spike at “25% CPU” — average latency is 4 ms, database logs show every query finishing in 2 ms, and container CPU averages 25% of its limit. Yet p99 HTTP latency jumps to 800 ms. You profile your handler and find nothing slow — because the delay happens before your thread runs (throttled by a cgroup v2 cpu.max quota burst inside a 100 ms window, or waiting in the kernel’s EEVDF run queue) or on the wire (a dropped TCP segment waiting on a retransmission timer, or a filled TCP accept queue).
  • 2 · EMFILE: Too many open files when no files are open — a traffic burst arrives and your server stops accepting requests or opening database connections with errno 24 (EMFILE), even though your code never touches the filesystem. To the Linux kernel, every accepted client TCP socket, every outbound database connection, every pipe, and the event loop’s epoll instance itself is a file descriptor consuming a slot in the process’s descriptor table (bounded by RLIMIT_NOFILE).
  • 3 · The “non-blocking” write that suddenly stalls for 45 ms — appending an audit record or writing a response normally returns in microseconds because write(2) only copies bytes into kernel RAM (the page cache for files, or the socket send buffer sk_sndbuf for TCP). Under sustained write pressure or on an explicit fsync(2), the kernel blocks to flush dirty pages through the block layer to NVMe, or pauses the sender because the peer’s TCP receive window (rwnd) or your congestion window (cwnd) is full.
  • 4 · The pod that disappears with exit code 137 (OOMKilled) — your application metrics show heap usage well below the container limit, yet the pod dies abruptly with no exception and no graceful shutdown log. Exit status 137 is 128 + 9 (SIGKILL), delivered directly by the kernel’s OOM killer when the process’s resident anonymous pages, memory mappings (mmap), or cgroup-accounted page cache breach memory.max.

The thread connecting all four incidents is one architectural fact: your application process is an unprivileged tenant running in user space. By hardware design, user-space instructions cannot touch a network card (NIC), an NVMe disk controller, a physical memory frame, or a CPU core’s interrupt table. Whenever your code wants to communicate, store bytes, allocate physical pages, or wait for work, it must trap across the kernel boundary via a system call (syscall) and ask the operating system to act on its behalf.

The foundational mental shift

Your code does not “send an HTTP response” or “write to disk.” Your code mutates bytes in a virtual address space and issues system calls asking the Linux kernel to copy those bytes into kernel buffers, schedule threads onto CPU cores, and drive hardware queues over the network wire. If you only know the language runtime above the syscall line, everything below it looks like random weather.

01 Mechanism

One HTTP request, end to end: from the wire through the kernel to your handler and back ▸

To make the invisible layers concrete, trace a single request — GET /orders/42 — from the moment its packet reaches your server’s network interface card (NIC) to the moment the JSON response leaves the wire. Notice how many subsystems touch the request before and after your handler’s ten lines of code run:

  • 1 · Wire → NIC → Kernel RAM (DMA + NAPI poll) — electrical or optical signals arrive at the NIC as an Ethernet frame wrapping an IP packet wrapping a TCP segment. The NIC does not interrupt the CPU for every byte; it writes the packet directly into a pre-allocated ring buffer in kernel RAM using DMA (Direct Memory Access), raises a hardware interrupt (IRQ), and triggers Linux’s NAPI (NET_RX_SOFTIRQ) poll loop to drain bursts of packets without an interrupt storm.
  • 2 · Kernel Network Stack (L2 → L3 IP → L4 TCP → Socket Buffer & epoll) — the kernel strips the Ethernet and IP headers, matches the TCP 4-tuple (client_ip, client_port, server_ip, 443) to an open socket struct, verifies sequence numbers, queues an ACK, appends the payload bytes to the socket’s receive queue (sk_rcvbuf), and marks that socket’s file descriptor ready in the watching epoll instance.
  • 3 · Scheduler Wakeup & Syscall Crossing (epoll_wait + read) — marking the descriptor ready wakes your server process (moving its task from blocked/sleeping to runnable). Linux’s EEVDF scheduler assigns the thread to a CPU core. Returning from epoll_wait(2) into user space, your runtime calls read(fd, buf, len) (or recvfrom(2)), crossing back into the kernel to copy the HTTP bytes from sk_rcvbuf into your process’s virtual memory buffer.
  • 4 · User-Space Execution & Downstream Storage/DB I/O — now, and only now, your handler runs on the CPU core, translating virtual addresses to physical RAM through the hardware TLB and page tables. When it reads a local file or queries Postgres over a pooled socket, it crosses the kernel boundary again — hitting the page cache (or waiting on an NVMe block read / `fsync`) or transmitting a TCP request over another file descriptor.
  • 5 · Outbound Syscall → TCP Send Queue → Wire (write → DMA TX) — your handler serializes the JSON reply and calls write(fd, json, n). The syscall copies the bytes into the socket’s kernel send buffer (sk_sndbuf) and returns immediately to user space so your event loop can move on to the next client, while the kernel asynchronously slices the buffer into TCP segments (paced by the congestion window cwnd and peer receive window rwnd), prepends IP and Ethernet headers, and notifies the NIC to DMA the frames onto the wire.
Look at where the time and the state actually live

Count the boundaries in Figure 1: the packet enters via NIC DMA, climbs the kernel TCP/IP stack, wakes a thread in the EEVDF scheduler via epoll, copies across the syscall boundary into virtual memory, touches the page cache or another socket, and descends the entire stack in reverse. Your handler is the thin green slice at the top; the other 90% of the machinery is the operating system and the network.

02 The architecture map

The two halves of every backend system: the Machine and the Wire

Because every request splits its life between the server kernel and the network hops, this course is built around two halves that meet inside a running Linux server:

  • Half 1 · The Machine (Operating System internals, Phases 1–4) — how the Linux kernel multiplexes four finite hardware resources across competing programs: CPU cores (processes, threads, context switches, signals, and EEVDF scheduling in P1), shared state (atomics, mutexes, futex, condition variables, and deadlocks in P2), physical RAM (virtual memory, page tables, the TLB, minor/major page faults, mmap, copy-on-write, and the OOM killer in P3), and storage & descriptor I/O (file descriptors, the page cache, fsync durability, and non-blocking event loops with epoll and io_uring in P4).
  • Half 2 · The Wire (Network protocols, Phases 5–7) — how independent machines exchange bytes over links that drop, reorder, and delay packets: packet delivery (Ethernet frames, MAC/ARP, MTU, IPv4/IPv6 CIDR subnets, routing tables, and NAT in P5), reliable transport (the socket API, TCP’s 3-way handshake, SYN and accept queues, retransmissions, flow control vs. congestion control with CUBIC and BBR, and TIME_WAIT/CLOSE_WAIT in P6), and application protocols (DNS resolution, HTTP/1.1 keep-alive pools, HTTP/2 multiplexing and TCP head-of-line blocking, TLS 1.3 with hybrid post-quantum key exchange, QUIC & HTTP/3 over UDP, load balancers, and WebSockets/gRPC in P7).
  • Where the Two Meet · Linux in Production (Phases 8–9) — in production, your process runs inside a container (which is not a miniature virtual machine, but an ordinary Linux process isolated by namespaces and throttled by cgroup v2 limits), talks through virtual Ethernet (veth) bridges and Kubernetes Service rules (P8), and is debugged under pressure using the USE method, strace, ss, tcpdump, perf, and eBPF (P8–P9).
03 The diagnostic invariant

Name the layer before you name the fix ▸

Here is the rule that pays for the entire course, in both on-call postmortems and system-design interviews: never propose a fix until you can name the OS or network layer that owns the symptom.

Why? Because at the application dashboard, almost every infrastructure failure wears the same disguise: latency climbs, throughput drops, and timeouts fire. If you guess a fix at the application layer without checking the boundary below, your “fix” regularly makes the outage worse:

  • Invariant of a slow request: at any microsecond of wall-clock time, a request that has not finished is doing exactly one of five things: (1) executing instructions on a CPU core, (2) runnable in the kernel scheduler queue waiting for a CPU core or cgroup quota, (3) blocked on a synchronization primitive (futex/mutex), (4) blocked waiting on memory paging or storage I/O (page fault, page-cache flush, fsync), or (5) waiting on a socket buffer across the network stack (DNS, handshake, loss recovery, or remote peer).
  • Why blind tuning backfires: if requests are slow because threads are waiting on a cgroup v2 CPU quota or fighting over a mutex, doubling the worker-thread count only adds context-switch and lock-contention overhead. If requests are failing because outbound sockets are piling up in CLOSE_WAIT (your code forgot to call close(2) after the peer sent FIN), raising the client timeout just holds leaked file descriptors open longer.

04 Mental model vs. reality

What your code thinks is happening vs. what the kernel and wire actually do

Most bugs at the systems boundary come from a gap between the simplified mental model a high-level language gives you and the physical contract the kernel enforces. Line them up side by side:

What application code assumes

  • Memory is a flat array of bytes that already exists in RAM the moment malloc() or new returns.
  • write(fd, buf, n) sends data to the disk or to the client on the other side of the internet before returning.
  • Threads run simultaneously in smooth parallel steps at zero switching cost.
  • A TCP connection is a physical wire between two processes that immediately notices when the peer dies.
  • A container is a lightweight VM with its own dedicated kernel, CPU cores, and network stack.

What Linux and TCP/IP actually do

  • Virtual addresses are promises: physical RAM frames are wired lazily on first touch via minor page faults (P3).
  • write(2) is a memory copy into kernel buffers (page cache or sk_sndbuf); disk durability needs fsync(2) and network delivery needs peer TCP ACKs (P4, P6).
  • Context switches cost microseconds of direct CPU state save plus L1/L2/TLB cache pollution across cores (P0, P1).
  • TCP is silence-tolerant state in two kernels: if a middlebox or peer drops silently, neither side knows until a transmit or keepalive times out (P6).
  • A container is a normal process on the host kernel whose view is filtered by namespaces and metered by cgroup v2 (P8).
What the interviewer probes next

1 · “When your server calls send() or write() on a TCP socket and gets back a positive byte count, has the client received the data?” No. A successful return from write(2) or send(2) on a TCP socket only means the Linux kernel copied those bytes from your user-space buffer into the socket’s kernel send buffer (sk_sndbuf). The actual transmission happens asynchronously as TCP segments, and if the cable is cut a millisecond later, the client never sees those bytes even though your write() call succeeded.

2 · “What about calling write() on a local file — is that durable once write() returns?” No again. Normal buffered file writes copy bytes into the kernel’s in-memory page cache, mark the page dirty, and return immediately. If the machine loses power before the background writeback flush, the data is lost. Databases guarantee durability by calling fsync(2) or fdatasync(2) on their write-ahead log (WAL) before acknowledging a commit (L16).

3 · “Why do we say ‘everything is a file descriptor’ in Unix, and why does a stateless proxy hit Too many open files?” Because the kernel exposes files, directories, pipes, TCP/UDP sockets, Unix domain sockets, timers (timerfd), and event loops (epoll) through the same per-process integer table. A reverse proxy routing 10,000 clients to 10,000 backend connections holds at least 20,000 socket file descriptors open at once — immediately blowing past the traditional default 1024 soft limit unless RLIMIT_NOFILE is raised (L15).

4 · “Why can’t a single thread use blocking I/O to serve 10,000 idle keep-alive connections?” A blocking read(fd) puts the calling OS thread to sleep until bytes arrive on that one descriptor. Serving 10,000 connections that way requires 10,000 OS threads (tens of megabytes of stack RAM and heavy scheduler context-switching). Non-blocking sockets paired with epoll(7) (or completion rings in io_uring(7)) let a single thread sleep on all 10,000 descriptors at once and wake up only for the handful that actually have bytes ready (L17).

05 Build

Trace one live HTTP request across file descriptors, kernel socket buffers, and readiness notification

Before we unpack each subsystem in its own lesson, run this self-contained Python 3 script to see the operating system and networking primitives beneath a single HTTP request with your own eyes. Using only the standard library (socket, selectors, os, resource), it opens a non-blocking listening socket, registers it with the OS readiness multiplexer (epoll on Linux, kqueue on macOS), drives one full HTTP round trip on loopback, and asserts the kernel artifacts created along the way.

Verification checkpointRunnablePython 3.12+ · Linux 6.18 / 7.x & POSIX
Inspect file descriptors, TCP 4-tuples, kernel socket buffers, and selector readiness on one request

Run directly with python3 request_layer_probe.py — zero third-party packages required. On Linux it also reads live kernel context-switch and RSS counters straight from /proc/self/status.

Think it through

1 · Process & descriptor table

Query os.getpid() and resource.getrlimit(RLIMIT_NOFILE), then allocate three sockets (listener, client, accepted peer) and verify that each one is just a small integer file descriptor in the process table.

2 · Evented readiness & TCP 4-tuple

Register the sockets with selectors.DefaultSelector() (which wraps epoll(7) on Linux), perform the loopback TCP connection, and verify that client and server hold mirror-image 4-tuples (127.0.0.1, client_port, 127.0.0.1, srv_port).

3 · Kernel buffer handoff

Inspect kernel SO_RCVBUF and SO_SNDBUF sizes, send GET /orders/42, notice that send() returns as soon as the kernel queues the bytes in sk_sndbuf, and read the response back across the syscall boundary.

The code

python 3.12+ · standard library only · request_layer_probe.py

import os
import resource
import selectors
import socket

pid = os.getpid()
soft_nofile, hard_nofile = resource.getrlimit(resource.RLIMIT_NOFILE)

sel = selectors.DefaultSelector()  # EpollSelector on Linux, KqueueSelector on macOS
srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("127.0.0.1", 0))        # kernel picks an available ephemeral listening port
srv.listen(128)                    # kernel allocates SYN + accept queues (backlog=128)
srv.setblocking(False)             # non-blocking fd for event-loop multiplexing
sel.register(srv, selectors.EVENT_READ, data="listener")

srv_ip, srv_port = srv.getsockname()
cli = socket.socket(socket.AF_INET, socket.SOCK_STREAM)

try:
    # 1. Connect triggers the 3-way TCP handshake (SYN -> SYN-ACK -> ACK) in the kernel
    cli.connect((srv_ip, srv_port))
    events = sel.select(timeout=1.0)
    assert any(key.data == "listener" for key, _ in events)

    conn, peer_addr = srv.accept()
    conn.setblocking(False)
    sel.register(conn, selectors.EVENT_READ, data="accepted_conn")

    # Every open socket is an integer index in this process's file-descriptor table
    fds = (srv.fileno(), cli.fileno(), conn.fileno())
    assert all(0 <= fd < soft_nofile for fd in fds) and len(set(fds)) == 3

    # Verify the TCP 4-tuple matches across both endpoints
    assert cli.getsockname() == conn.getpeername() == peer_addr
    assert cli.getpeername() == conn.getsockname() == (srv_ip, srv_port)

    # 2. sendall() copies bytes across the syscall boundary into kernel sk_sndbuf
    req = b"GET /orders/42 HTTP/1.1\r\nHost: localhost\r\n\r\n"
    cli.sendall(req)

    # Selector wakes when the kernel moves segment bytes into conn's sk_rcvbuf
    events = sel.select(timeout=1.0)
    assert any(key.data == "accepted_conn" for key, _ in events)
    raw_in = conn.recv(4096)
    assert raw_in.startswith(b"GET /orders/42")

    # 3. Handler writes JSON response into conn's kernel send buffer
    body = b'{"order_id":42,"status":"paid"}'
    resp = b"HTTP/1.1 200 OK\r\nContent-Length: 31\r\n\r\n" + body
    sent = conn.send(resp)
    assert sent == len(resp)

    reply = cli.recv(4096)
    assert reply.endswith(body)

    rcvbuf = conn.getsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF)
    sndbuf = conn.getsockopt(socket.SOL_SOCKET, socket.SO_SNDBUF)
    assert rcvbuf > 0 and sndbuf > 0

    proc_info = {}
    if os.path.exists("/proc/self/status"):
        with open("/proc/self/status", encoding="utf-8") as f:
            for line in f:
                if line.startswith(("VmRSS:", "voluntary_ctxt_switches:")):
                    k, v = line.split(":", 1)
                    proc_info[k] = v.strip()

    print({
        "pid": pid,
        "selector": type(sel).__name__,
        "rlimit_nofile_soft": soft_nofile,
        "socket_fds": {"listen": fds[0], "client": fds[1], "accepted": fds[2]},
        "tcp_4tuple": (f"{peer_addr[0]}:{peer_addr[1]}", f"{srv_ip}:{srv_port}"),
        "kernel_sock_bufs": {"SO_RCVBUF": rcvbuf, "SO_SNDBUF": sndbuf},
        "proc_self": proc_info,
    })
finally:
    sel.close()
    conn.close()
    cli.close()
    srv.close()

Explain it aloud in an interview

“When a request hits my service, my code is the last stop, not the first. The packet is DMA’d from the NIC into a kernel ring buffer, polled by a NAPI softirq, validated through the IP and TCP layers into the socket’s sk_rcvbuf, and flagged ready on an epoll descriptor. Only then does the Linux EEVDF scheduler wake my worker thread to copy the bytes across the syscall boundary via read(). So whenever I debug a latency spike or connection error, I isolate the layer first — CPU scheduling and cgroup quotas, lock contention, virtual memory paging, file-descriptor and page-cache I/O, or TCP/TLS on the wire — before I touch application code.”

Follow-ups to anticipate: what write() actually guarantees on a file vs. a socket, why EMFILE hits stateless services, and how a container differs from a virtual machine.

Self-test

1. Trace an incoming HTTP request from the network cable to your handler function: which hardware and kernel components touch the bytes before your code runs?

The NIC receives the Ethernet frame and writes it into a kernel RAM ring buffer via DMA, raising a hardware IRQ that schedules a NAPI softirq poll. The Linux kernel validates the L2 Ethernet, L3 IP, and L4 TCP headers, matches the 4-tuple to an open socket, appends payload bytes to the socket’s receive buffer (sk_rcvbuf), and marks the descriptor ready in epoll. That readiness wakes the waiting process so the EEVDF scheduler places it on a CPU core, and your runtime issues a read(2)/recvfrom(2) syscall to copy the bytes from kernel space into your user-space virtual memory buffer.

2. When write(fd, buf, len) returns len on (a) a regular file and (b) a TCP socket, where are the bytes physically located?

In both cases, the bytes have only been copied from your user-space buffer into kernel RAM: for a regular file, into a dirty page in the kernel page cache (requiring fsync(2) or fdatasync(2) to force a flush to non-volatile storage); for a TCP socket, into the socket’s kernel send queue sk_sndbuf (from which the TCP stack transmits segments asynchronously and waits for peer ACKs).

3. Why can a service that never reads or writes files on disk crash with EMFILE (Too many open files)?

Because Linux represents sockets, pipes, event-loop instances (epoll), and open files uniformly as integer entries in the per-process file-descriptor table. Hitting the process’s RLIMIT_NOFILE soft limit on accepted client sockets or leaked outbound connections causes accept4(2) or socket(2) to fail with EMFILE.

4. How can a Kubernetes pod suffer 500 ms CPU scheduling delays when its 1-minute average CPU utilization is only 25%?

Under cgroup v2, CPU limits (cpu.max) are enforced over short accounting periods (typically 100 ms). If multiple worker threads burst simultaneously and consume the pod’s entire 100 ms CPU allowance in the first 15 ms, the kernel throttles all threads in the cgroup for the remaining 85 ms of the period (visible as rising nr_throttled and throttled_usec in /sys/fs/cgroup/cpu.stat), even if the pod sits idle for the rest of the minute.

5. What are the five states a slow request can be in at any given instant, and why must you distinguish them before tuning?

A request is either (1) running instructions on a CPU core, (2) runnable and waiting for a CPU core or cgroup quota, (3) waiting on a lock/futex, (4) waiting on memory paging or block disk I/O, or (5) waiting on the network stack/wire. A fix for one state (for example, adding more threads) actively worsens others (lock contention, context-switch overhead, and cgroup quota exhaustion).

6. What does container exit code 137 mean, and why doesn’t your application log a stack trace when it happens?

Exit code 137 is 128 + 9, indicating the process was terminated by signal 9 (SIGKILL), almost always from the Linux kernel’s OOM killer when cgroup memory usage hits memory.max. Because SIGKILL is handled unconditionally inside the kernel and cannot be caught, blocked, or ignored by user space, the process is reaped immediately before any application exception handler can run.
