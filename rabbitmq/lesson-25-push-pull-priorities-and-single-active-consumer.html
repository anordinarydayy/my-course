25Consumers & throughput

Push vs Pull, Consumer Priorities & Single Active Consumer

How work reaches a consumer — pushed to a long-lived subscription or pulled one message at a time — decides efficiency. Which consumer receives it, and whether exactly one does, decides continuity and order. This lesson separates basic.consume from basic.get, priorities from single active consumer, and queue SAC from the distinct stream feature.

Original study chapter. The scenario, selection model, figures, code, and SVGs are original. Stable behavior targets open-source RabbitMQ 4.3 (latest signed patch overlay 4.3.3; public release and docs pages still showed 4.3.2 when researched); runnable code uses Python 3 and Pika 1.3.2. This chapter contains three original figures, two interactive. Behavior described is stable 4.3; selection details follow the 4.3 documentation.
00 Failure first

A “real-time” consumer that mostly asks “anything yet?”

To feel responsive, a team writes a loop that calls basic.get as fast as it can, hoping to grab messages the instant they arrive. In production the queue is usually empty between bursts, so the loop spends its time issuing requests that come back empty. Each call is a network round trip. The client CPU is pinned, the broker logs a rising empty-get rate, and prefetch — which they carefully tuned — does nothing here, because polling ignores it. They built a busy-wait and called it streaming.

A second team wants a hot standby: a primary worker and a backup that only runs if the primary dies. They set a higher x-priority on the primary and assume the backup will stay dark until failover. Instead, whenever the primary’s window fills for a moment, work slides to the backup — because priority selects among consumers that can currently accept work, not a reservation that idles everyone else. Both teams reached for the right-sounding feature and got the wrong guarantee.

Delivery-path invariant

A long-lived basic.consume subscription lets the broker push messages as they arrive and amortizes setup across many deliveries. basic.get is a one-message request/response poll: a round trip each time, frequently empty, and unaffected by prefetch. Prefer push; reserve polling for narrow cases.

01 Mechanism

Subscribe once and be pushed; or poll and pay per message

With basic.consume the client registers a consumer, and RabbitMQ pushes deliveries to it as messages become available and credit allows. The cost of setting up the subscription is paid once and spread across every message that follows; there are no idle round trips when the queue is empty, because the broker simply has nothing to send yet. This is the normal, recommended data path.

basic.get is the opposite shape. Each call asks the broker for one message and waits for the response; if the queue is empty the response says so and the round trip was spent for nothing. There is a network round trip per attempt, no benefit from prefetch, and a tight loop of gets can generate substantial empty-get traffic. RabbitMQ explicitly recommends long-lived consumers and reserves polling for narrow situations — a typical example being an integration test that wants to fetch one message deterministically. PerfTest likewise treats asynchronous basic.consume as the optimal path and exposes polling only for comparison.

Interview framing

“I default to a long-lived basic.consume because it is pushed and amortizes setup. I only use basic.get for a deliberate one-off — say, pulling a single message in a test — never as a polling loop, which just burns round trips and ignores prefetch.”

02 Priorities

Priority selects among consumers that can accept work ▸

Set an integer x-priority argument on basic.consume; an omitted priority is 0 and larger numbers win. The highest-priority consumers that are currently active receive deliveries; a lower-priority consumer is used as soon as every higher-priority consumer is blocked. Consumers tied at the highest active priority round-robin among themselves. Classic and quorum queues support consumer priority; streams do not. Crucially, RabbitMQ does not hold work waiting for a blocked preferred consumer — step through what that means for a “hot standby.”

So consumer priority is a preference among the eligible, not a reservation. It is excellent for “drain the fast/local worker first, fall back to the remote one when it is busy,” and wrong for “keep this backup completely idle until the primary dies.” The idle-backup requirement is what single active consumer is for.

03 Queue SAC

Single active consumer: one works, the rest wait

Declare the queue with x-single-active-consumer=true. Several consumers may register, but only one is active and receives deliveries; the others are registered standbys that get nothing until the active one is cancelled or disconnects, at which point RabbitMQ promotes another. This is declaration-time behavior: SAC cannot be turned on later with a policy, and it cannot be combined with an exclusive consumer. Both classic and quorum queues support it.

The selection details differ by queue type, and the 4.3 documentation is specific. For a classic queue, the initial active consumer is chosen randomly, even when priorities are supplied — do not promise “first registered wins,” which an older generic passage implies and the queue-specific section contradicts. For a quorum queue, a newly registered higher-priority consumer can supersede the active one: deliveries pause, existing outstanding deliveries must be acknowledged, and then the higher-priority consumer becomes active.

Note also that AMQP 0-9-1 exclusive consumption is a different, classic-only thing: it prevents other consumers from registering but leaves replacement to the application and provides no standby promotion; quorum queues ignore the exclusive-consumer flag entirely. When your requirement is “exactly one active consumer with automatic failover,” reach for SAC, not exclusive consumers.

Selection trap

Writing an integration test that asserts the first consumer you registered becomes active on a classic SAC queue will be flaky: 4.3 documents random initial selection. Assert only that exactly one is active and that failover promotes another — not which one.

04 Stream SAC & order

Stream SAC is a different feature — and none of this orders side effects ▸

The x-single-active-consumer argument from an AMQP 0-9-1 queue declaration does not enable SAC on a stream. Native RabbitMQ Stream protocol clients form a SAC group by sharing the stream and a consumer name; one instance in the group is active and another takes over on failure. Super streams apply this per partition, so each partition has one active consumer while partitions run in parallel — order within a partition, parallelism across them. Step through failover and the caveat that surprises people:

Single active consumer narrows delivery concurrency: RabbitMQ will not dispatch new queue messages to several active consumers at once. It cannot, by itself, guarantee ordered side effects, because a client library may still hand callbacks to a thread pool and application work can finish out of order. A strict-ordering design pairs SAC with a concurrency of one (or an explicit application sequencing mechanism) and handles duplicates and redeliveries idempotently. SAC gives you a single stream; your callback discipline gives you order.

05 Decide

Pick the delivery mechanism from the requirement

Each requirement maps to a specific mechanism, and the failures earlier came from picking a neighbour. The map below states the requirement, the mechanism that satisfies it, and the caveat that keeps you honest.

The recurring caveat across all of them is that concurrency lives in two places — the broker’s delivery and the application’s processing — and only the delivery side is what these features control. Whenever the requirement is about the order or exclusivity of effects, the mechanism must be paired with disciplined, ideally single-threaded and idempotent, processing.

06 Build

Measure the cost of polling

The runnable checkpoint makes the push-vs-pull difference concrete by counting round trips. It publishes five messages, then drains them with basic.get, asserting that five polls returned messages in order and a sixth poll came back empty — one round trip per message plus a wasted empty poll. That empty poll is exactly what a tight polling loop multiplies. The comments mark where a long-lived basic.consume would replace all of it.

Polling-cost checkpointPython 3 · Pika 1.3.2

Every pull is a round trip; empties are pure waste

python · install pika==1.3.2 and run against localhost
import uuid

import pika

QUEUE = f"lab.pull.cost.{uuid.uuid4().hex[:10]}"
TOTAL = 5


def main():
    connection = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
    channel = connection.channel()
    try:
        channel.queue_declare(
            queue=QUEUE,
            durable=True,
            arguments={"x-queue-type": "quorum"},
        )
        channel.confirm_delivery()
        for sequence in range(TOTAL):
            channel.basic_publish(
                exchange="",
                routing_key=QUEUE,
                body=str(sequence).encode(),
                properties=pika.BasicProperties(delivery_mode=2),
            )

        # Pull one message per round trip. basic.get ignores prefetch entirely.
        polls = 0
        received = []
        while True:
            method, _properties, body = channel.basic_get(QUEUE, auto_ack=False)
            polls += 1
            if method is None:
                break  # an empty poll: the round trip returned nothing
            received.append(int(body))
            channel.basic_ack(method.delivery_tag)
            if len(received) >= TOTAL:
                # one more get to observe the wasted empty poll
                empty_method, _p, _b = channel.basic_get(QUEUE, auto_ack=False)
                polls += 1
                assert empty_method is None, "expected an empty poll after draining"
                break

        assert received == list(range(TOTAL)), received
        assert polls == TOTAL + 1, polls  # 5 hits + 1 empty round trip
        # A long-lived basic.consume would be PUSHED these instead, with no
        # empty round trips and with prefetch back-pressure applied.
        print({"queue": QUEUE, "received": received, "round_trips": polls})
    finally:
        channel.queue_delete(queue=QUEUE)
        connection.close()


if __name__ == "__main__":
    main()

The assertion polls == TOTAL + 1 is the whole lesson in one line: pulling five messages cost six round trips, and a real polling loop against a usually-empty queue would be almost all empties. Switch to a pushed subscription and those wasted trips disappear.

Self-test

1. Why is a basic.get polling loop a poor default for consumption?

Each call is a network round trip that frequently returns empty, it pins client CPU, and it does not benefit from prefetch. A long-lived basic.consume is pushed and amortizes setup; polling is for narrow cases such as integration tests.

2. Does a higher x-priority keep a backup consumer idle until the primary dies?

No. Priority selects among consumers that can currently accept work. When the higher-priority consumer is blocked, work goes to the lower-priority one. For a truly idle backup, use single active consumer.

3. On a classic queue with single active consumer, which consumer becomes active first?

The 4.3 documentation says the initial active consumer is chosen randomly, even with priorities. Do not assert first-registered wins; assert only that exactly one is active and failover promotes another.

4. How is single active consumer configured, and can a policy enable it?

It is a declaration-time argument, x-single-active-consumer=true, on the queue (classic or quorum). It cannot be enabled later by policy and cannot be combined with an exclusive consumer.

5. Does setting x-single-active-consumer on a stream declaration enable stream SAC?

No. Stream SAC is a separate feature: native Stream protocol clients form a group by sharing the stream and a consumer name. Super streams apply it per partition for order within a partition and parallelism across partitions.

6. Does single active consumer guarantee ordered side effects?

No. It narrows delivery concurrency to one active consumer, but the application can still process callbacks concurrently and finish out of order. Pair SAC with concurrency of one (or explicit sequencing) and idempotent redelivery handling.
