Topic Exchanges & Routing Keys

Exact labels stop scaling when subscribers need slices such as “all European orders,” “every created event,” or “everything under orders.” A topic exchange turns a dot-separated routing key into a small matching language. That power is useful only if the key shape is treated as a versioned application contract.

Original study chapter. All prose, routing matrices, code, and SVGs are original. Stable behavior targets open-source RabbitMQ 4.3; the worked client is Pika 1.3.2. This lesson contains three original figures, two interactive. The convention <domain>.<region>.<event> is design guidance, not a broker-mandated schema.
00 Failure first

When exact labels multiply into a private query language

A direct exchange is clear while the vocabulary is finite: created, paid, cancelled. Then regional operations wants all EU events, analytics wants every order event, and fraud wants every created event across regions. Enumerating every combination as a direct binding makes topology size grow with the product of dimensions. Every new region demands another binding rollout.

A topic exchange solves that binding explosion by matching patterns against a structured routing key. Publishers still emit a concrete key. Topology owners bind queues with patterns. The broker's guarantee remains mechanical—not semantic: it splits the key and pattern on dots, applies two wildcard rules, and routes to every destination whose pattern matches.

Production warning

RabbitMQ does not validate that order.eu.created really describes an order, region, or event. It does not migrate old patterns when a team changes segment order. The key grammar is your API; the exchange only executes it.

01 Matching engine

Segments, *, and # ▸

A topic key is a sequence of dot-separated segments. In a binding pattern, * consumes exactly one segment. The # wildcard consumes zero or more segments. Those two words—exactly and zero—explain almost every boundary case.

Consider three subscriptions: order.eu.*, order.*.created, and order.#. The key order.eu.created matches all three. The shorter order.created matches only order.#; neither star can invent the missing middle segment. The key order also matches order.#, because hash may consume zero segments.

Interview follow-up

Does order.*.created match order.created? No. Star must consume exactly one segment. Does order.# match order? Yes. Hash can consume zero.

02 Boundary cases

Depth is part of matching

Teams often test only the happy three-segment key and ship a hidden depth bug. A star is not “anything”; it is one segment between dots. Therefore order.eu.* matches order.eu.created but not order.eu.payment.failed. A hash tolerates variable depth, but its breadth can admit future keys that the consumer cannot actually process.

A binding with no wildcard behaves like exact direct-style matching. A lone # receives every routing key through that topic exchange. Both are valid, but they should be deliberate; topic is not automatically better merely because it can emulate direct and fanout.

03 Ownership

Publish concrete keys; bind with patterns ▸

The publisher describes one fact with a concrete key such as order.eu.created. It should not publish order.*.created; wildcard semantics belong to bindings. Subscribers express the set they can process, and the topology can evolve without asking the publisher to enumerate consumers.

Patterns may overlap. If one queue is bound with both order.# and order.*.created, a created order matches two edges but is enqueued in that destination queue once for that publication. RabbitMQ de-duplicates the reached destination; overlapping bindings are not a technique for intentionally creating duplicate queue copies.

04 Contract design

Design a routing-key taxonomy that can be explained

A useful key orders stable categorical dimensions from broad to narrow. For this course, <domain>.<region>.<event> makes order.eu.created readable and supports order.#, order.*.created, and *.eu.*. Another system may legitimately choose tenant, entity, version, or sensitivity dimensions instead. What matters is a documented grammar and a bounded vocabulary.

Only place data in the key when consumers genuinely route on it. Order IDs, timestamps, and free text create near-unbounded binding vocabularies, leak domain data into broker metadata and logs, and make permissions harder to reason about. Keep identity and rich attributes in message headers or body. Topic routing keys are also bounded to 255 bytes—bytes, not Unicode characters or words.

05 Evolution

Changing key shape is a topology and authorization migration

Changing order.eu.created to order.v2.eu.created breaks every fixed-depth star pattern. The safe path is explicit compatibility: inventory bindings and topic permissions, publish or accept both contracts for a bounded window, test a routing matrix for old and new forms, then remove the old paths deliberately. A hash can bridge variable suffix depth, but broadening it should be reviewed as a consumer-compatibility decision, not a shortcut.

Topic permissions can match publishing and binding routing keys. A grammar migration may therefore change who is authorized even when queue and exchange names stay constant. Include security tests alongside destination-set tests.

RabbitMQ 4.3 patch caveat

RabbitMQ 4.3.1 introduced the topic_binding_projection_v5 feature flag for a topic-routing fix; it takes effect after every node is upgraded and the flag is enabled. For a maintained 4.3 cluster, use the current signed 4.3.3 patch overlay rather than reasoning from 4.3.0 alone, and verify feature-flag state during the upgrade. This maintenance detail does not change the wildcard contract taught above.

06 Worked scenario

Execute the routing matrix, including de-duplication

The lab declares four ephemeral queues: EU events, created events, every order event, and an overlap queue with two matching bindings. It publishes normal, short, deep, and different-domain keys, then asserts destination membership.

Complete runnable labPython 3 · Pika 1.3.2

Test sets, not a guessed single destination

python · install pika==1.3.2 and run against localhost
import pika

connection = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
try:
    channel = connection.channel()
    channel.confirm_delivery()
    channel.exchange_declare(
        exchange="lab.orders", exchange_type="topic", auto_delete=True
    )

    queues = {
        name: channel.queue_declare(queue="", exclusive=True).method.queue
        for name in ("eu", "created", "all", "overlap")
    }
    channel.queue_bind(queues["eu"], "lab.orders", "order.eu.*")
    channel.queue_bind(queues["created"], "lab.orders", "order.*.created")
    channel.queue_bind(queues["all"], "lab.orders", "order.#")
    channel.queue_bind(queues["overlap"], "lab.orders", "order.#")
    channel.queue_bind(queues["overlap"], "lab.orders", "order.*.created")

    keys = [
        "order.eu.created",
        "order.created",
        "order.eu.payment.failed",
        "order",
        "billing.eu.created",
    ]
    for key in keys:
        channel.basic_publish(
            exchange="lab.orders",
            routing_key=key,
            body=key.encode("utf-8"),
        )

    def drain(queue_name):
        result = []
        while True:
            method, _properties, body = channel.basic_get(queue_name, auto_ack=True)
            if method is None:
                return result
            result.append(body.decode("utf-8"))

    received = {name: drain(queue) for name, queue in queues.items()}
    assert received["eu"] == ["order.eu.created"]
    assert received["created"] == ["order.eu.created"]
    assert received["all"] == keys[:4]
    assert received["overlap"] == keys[:4]
    assert received["overlap"].count("order.eu.created") == 1
    print(received)
finally:
    connection.close()

The final assertion is the subtle one: the overlap queue matches two patterns for order.eu.created, but it records one copy. The matrix should always describe a set of destination queues, not a count of matching binding edges.

Self-test

1. Why does order.*.created reject order.created?

The star must consume exactly one segment between order and created; that key has no middle segment.

2. Name three keys matched by order.#, including its shortest match.

order, order.eu, and order.eu.created. Hash consumes zero or more segments.

3. Should a publisher send order.*.created?

No. Publishers send a concrete fact such as order.eu.created. Wildcards are subscription patterns on bindings.

4. What happens when two matching bindings lead to the same queue?

The queue receives one copy of that publication; RabbitMQ de-duplicates the reached destination.

5. Why can adding one key segment be a breaking change?

Fixed-depth star patterns stop matching, consumers may reject the new grammar, and topic authorization patterns can change meaning.

6. Is the 255 limit measured in words, characters, or bytes?

Bytes. Multi-byte Unicode characters therefore consume more than one unit of the field limit.
