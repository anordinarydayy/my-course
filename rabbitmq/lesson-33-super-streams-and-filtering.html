Super Streams & Stream Filtering

A super stream scales a stream by partitioning it across several ordinary streams; stream filtering lets a consumer skip data it does not want. Both features are powerful and both are routinely oversold: a super stream is a topology, not an in-place split, and Bloom filtering is probabilistic, not a promise that only matching messages cross the wire.

Stable behavior targets open-source RabbitMQ 4.3 (latest signed patch overlay 4.3.3; public release/download/docs pages still showed 4.3.2 when accessed 2026-07-21). Native examples use the RabbitMQ Stream Java client 1.8.0 and the rabbitmq-streams CLI. This chapter has three original figures, two interactive.
00 Failure first

Two shortcuts that quietly break correctness

The first shortcut is thinking a super stream repartitions an existing stream in place — that you flip a switch and RabbitMQ transparently shards your log. It does not. A super stream is a logical name over several regular streams, described by an exchange, partition streams, and bindings. You choose the partition count up front, and you route each message to a partition; there is no magical redistribution of already-written data.

The second shortcut is reading “stream filtering” as “the broker sends only the messages I asked for.” The default and most broadly supported filter is a Bloom filter stored per chunk. Bloom filters have false positives and operate at chunk granularity, so a matching chunk is delivered in full and can contain records you did not want. Unless you pair the Bloom filter with an exact AMQP 1.0 filter expression, you must re-check on the client. Skipping that re-check is how “filtered” consumers end up processing the wrong records.

Both features are genuinely useful once framed correctly. This chapter builds the correct mental model: the exchange-and-bindings topology of a super stream, how routing decides a partition and why order is per-partition, how single active consumer coordinates one reader per partition, and the three distinct filtering stages with their exact protocol reach.

Framing invariant

A super stream is an exchange over regular stream partitions; ordering is per partition, offsets are per partition, and there is no total order. Filtering has three stages: a probabilistic per-chunk Bloom filter, exact AMQP 1.0 property/SQL expressions, and a client-side predicate. Only the middle stage removes the need for a client-side re-check.

01 Topology

A super stream is an exchange over partition streams ▸

Take an invoices super stream with three partitions. Under the hood there is an invoices exchange, three partition streams — invoices-0, invoices-1, invoices-2 (each a normal stream, which is also an AMQP queue) — and bindings that describe the routing rules from the exchange to the partitions. Client libraries read this topology to discover partitions and route messages; from the application's point of view the super stream looks like one large stream.

On the 4.3.3 patch overlay, RabbitMQ caps a super stream at 1,000 partitions by default. An operator can raise the ceiling with stream.max_super_stream_partitions in rabbitmq.conf, but that is a guardrail, not a recommended count — raising it does not remove the routing, skew, replica, and per-partition progress costs that partitioning introduces. The figure plays through a publish being routed to exactly one partition by its key, key affinity preserving order within a partition, and round-robin trading that affinity for spread.

02 Routing

Routing chooses a partition; order lives inside a partition

A native client routes each publish with one of three strategies. Hash routing derives an application key, hashes it, and selects one partition — the RabbitMQ Stream Java client uses 32-bit MurmurHash3 by default. Binding-key routing resolves a business key through the super-stream exchange's bindings, which is natural when partitions have meaning such as a region. Custom routing lets you select one, several, or no partitions, with the corresponding complexity.

A stable key-to-partition rule keeps every record for that key on one partition, which gives publish and consume order within that partition. There is no total order across partitions, because each partition advances independently and has its own offset sequence. Round-robin routing improves spread but deliberately abandons per-key ordering. Because offsets are partition-local, a super-stream consumer is composite — one internal consumer per partition — and there is no single global super-stream offset, so any manual checkpoint must retain the partition identity.

Do not partition by default

Partitioning is an explicit scale trade-off. It adds routing, skew, rebalancing, and per-partition progress concerns. Begin with a single stream and move to a super stream only when a single stream's throughput or storage limits have actually been reached — not because “sharded” sounds faster.

03 Coordination

Single active consumer: one reader per partition, per group ▸

Stream single active consumer (SAC) is a native Stream-protocol feature. Consumers that share a stream and the same name form a group; one member is active and receives messages while the others wait. A different name defines an independent group that can also have an active reader on the same stream. For a super stream, each application instance creates an internal consumer for every partition; with SAC enabled and the same group name, the broker and clients coordinate so that exactly one member is active for each partition. Several partitions can therefore be processed concurrently by different instances.

Failover promotes a waiting member; the activation carries the offset from which delivery should resume. Built-in tracking supplies a sensible default, while an external store or manual tracking requires correct activation/deactivation callbacks and per-partition offsets — and failover can still replay work after the last durable checkpoint, so idempotency remains necessary. Crucially, queue SAC and stream SAC are different mechanisms: the AMQP argument x-single-active-consumer=true applies to classic and quorum queues; it does not enable SAC on a stream, which requires a native Stream client. Without stream SAC, two composite consumers of the same super stream each read every partition, so both instances receive the same records — super streams do not by themselves create a Kafka-style shared consumer group.

04 Filtering

Three filtering stages that must not be collapsed

RabbitMQ 4.3 offers three filtering stages, and conflating them into one promise is the classic mistake. Each stage is optional; with no filter a consumer reads everything.

StageMechanismProtocol reachExactness
1 · BloomPublisher sets one string filter value per message; RabbitMQ stores a Bloom filter in each chunk header; the consumer supplies one or more values (OR).AMQP 1.0, AMQP 0-9-1, Stream protocol, STOMPProbabilistic and per chunk. A definite miss skips the chunk before reading; a possible hit sends the whole chunk. False positives and unrelated records in a matching chunk need stage 2 or a client re-check.
2 · AMQP filter expressionsAn AMQP property filter or an AMQP SQL filter expression (mutually exclusive; either combinable with stage 1).AMQP 1.0 stream consumers onlyExact per-message metadata evaluation server-side; only matching records are delivered.
3 · Client predicateA client-library or application predicate, including body inspection.Any capable clientExact and flexible, but the bytes have already crossed the network unless an earlier stage reduced them.

Property filter expressions arrived in RabbitMQ 4.1 and SQL filter expressions in 4.2, so both are stable in 4.3 — not Next-only features. Stable property filters cover the immutable properties and application-properties sections, including the documented prefix/suffix modifiers; stable SQL expressions inspect application properties, AMQP properties, and only the priority header field, and do not support delivery/message annotations, the footer, other header fields, composite indexing, several string/date functions, or EXISTS. RabbitMQ implements a subset of the OASIS AMQP Filter Expressions specification, which is itself a Committee Specification Draft 01 — not a final OASIS Standard.

The re-check is mandatory for Bloom-only

A Bloom filter by itself never justifies “only matching messages cross the network.” For AMQP 0-9-1, Stream-protocol, and STOMP clients, retain an explicit client-side post-filter. Only AMQP 1.0 can combine the Bloom filter with an exact property or SQL expression so both stages run server-side.

05 Boundaries

Cardinality, protocol reach, and the scale decision

Filter values should be low- to moderate-cardinality categories — a region, an event type, a tenant class. A unique value per record (say a customer ID on every message) makes the chunk Bloom filter far less useful: nearly every chunk matches, false-positive pressure rises, and the filter-size overhead grows. If you truly need high-cardinality matching, that is a job for an exact AMQP 1.0 SQL expression, or a larger x-stream-filter-size-bytes (16–255, default 16) accepting more storage, not for hoping the Bloom filter narrows it.

Keep the protocol boundaries crisp. Bloom filtering spans AMQP 1.0, AMQP 0-9-1, Stream protocol, and STOMP, but is probabilistic. Exact property and SQL expressions are AMQP-1.0-only and operate only on supported metadata; they cannot inspect the body. And partitioning remains a scale decision, not a default. 06 Build

Partition, coordinate with SAC, and filter with a re-check

This lab creates a three-partition super stream from the CLI, consumes it with a single-active-consumer group using the native Stream client, and filters a partition with a Bloom filter plus the mandatory client-side re-check. The CLI commands are the topology; the Java uses the RabbitMQ Stream Java client 1.8.0. Everything created is deleted at the end.

Complete runnable super-stream + filter buildrabbitmq-streams CLI · Stream Java client 1.8.0

Step 1 — create the partitioned topology

shell · run on a RabbitMQ 4.3 node with the stream plugin enabled
# A super stream is a topology (exchange + partition streams + bindings),
# created explicitly. It does NOT repartition an existing stream in place.
rabbitmq-streams add_super_stream invoices --partitions 3
# On the 4.3.3 overlay the default ceiling is 1000 partitions; raise it only
# deliberately via stream.max_super_stream_partitions in rabbitmq.conf.

# ... run the consumer below ...

# Cleanup: remove the whole super stream (exchange, partitions, bindings).
rabbitmq-streams delete_super_stream invoices

Step 2 — consume the super stream with single active consumer

java · RabbitMQ Stream Java client 1.8.0 (native Stream protocol, port 5552)
import com.rabbitmq.stream.Consumer;
import com.rabbitmq.stream.Environment;
import com.rabbitmq.stream.OffsetSpecification;

Environment environment = Environment.builder()
    .host("localhost").port(5552).build();

// One internal consumer per partition. With the SAME group name and SAC,
// exactly one consumer is active PER PARTITION across all instances.
Consumer consumer = environment.consumerBuilder()
    .superStream("invoices")
    .singleActiveConsumer()
    .name("invoice-processor")                 // group name, mandatory for SAC
    .offset(OffsetSpecification.first())
    .messageHandler((context, message) -> {
        // process the message, then checkpoint THIS partition's offset
        context.storeOffset();                 // per-partition; store(long) would fail
    })
    .build();

// ... process for a while, then release resources ...
consumer.close();
environment.close();

Step 3 — filter a partition with a Bloom filter and a client re-check

java · a partition is a regular stream, so per-stream filtering applies
import com.rabbitmq.stream.Consumer;
import com.rabbitmq.stream.Environment;

Environment environment = Environment.builder().build();

Consumer filtered = environment.consumerBuilder()
    .stream("invoices-0")                      // one partition = one regular stream
    .filter()
        .values("emea")                        // stage 1: server-side Bloom (per chunk)
        .postFilter(msg ->                     // stage 3: mandatory client-side re-check
            "emea".equals(msg.getApplicationProperties().get("region")))
        .builder()
    .messageHandler((context, message) -> {
        // Only records that pass BOTH the Bloom chunk match and the exact
        // client re-check reach here; Bloom alone can yield false positives.
    })
    .build();

filtered.close();
environment.close();

The postFilter is not decoration — it is the correction for the Bloom filter's chunk-level, probabilistic nature. If this consumer spoke AMQP 1.0 instead, it could replace the postFilter with an exact property or SQL expression and run both stages server-side; over the Stream protocol shown here, the client-side re-check stays.

Self-test

1. Does creating a super stream repartition an existing stream?

No. A super stream is a logical topology — an exchange, partition streams, and bindings — created explicitly. It does not redistribute data already written to some other stream in place.

2. What ordering guarantee does a super stream give?

Order within a partition. A stable key-to-partition rule keeps a key's records on one partition in publish/consume order; there is no total order across partitions, and offsets are per partition.

3. What does stream single active consumer coordinate?

One active consumer per partition within a group of consumers sharing the stream and the same name. Other members wait and take over on failover. It is not one consumer for the whole super stream.

4. Why doesn't x-single-active-consumer=true enable stream SAC?

That AMQP declaration argument applies to classic and quorum queues. Stream SAC is a native Stream-protocol feature and requires a native Stream client.

5. Why is a Bloom filter alone not enough to receive only matching messages?

It is probabilistic and evaluated per chunk. A matching chunk is delivered whole and can contain non-matching records, and false positives occur. AMQP 0-9-1, Stream, and STOMP consumers must re-check client-side.

6. Which filtering stage removes the client-side re-check, and for whom?

Stage 2, the exact AMQP property or SQL filter expression, but only for AMQP 1.0 stream consumers. It can be combined with the Bloom filter so both run server-side.
