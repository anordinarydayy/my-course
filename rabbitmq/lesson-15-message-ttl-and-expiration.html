Message TTL & Expiration

TTL prevents stale work from being newly delivered after its deadline. It does not promise immediate physical deletion, automatic dead-lettering, a fresh timer after requeue, or an exact scheduling service. Those distinctions determine whether expiry protects a business invariant or merely hides growing disk usage.

Original study chapter. The scenarios, timing traces, code, questions, and SVGs are original. Stable semantics target open-source RabbitMQ 4.3; runnable code uses Pika 1.3.2. This chapter contains three original figures, two interactive. Millisecond values are illustrative contracts, not latency guarantees.
00 Failure first

A deadline on a publication is not one global timer

A price quote is routed to a fast checkout queue and a slow audit queue. The team says “the message lives five seconds,” then expects both copies to disappear together. RabbitMQ instead evaluates residence time per queue copy. Each queue has its own enqueue time, queue policy, head position, dead-letter configuration, and removal opportunity.

Message TTL answers a delivery question: once a copy is expired, RabbitMQ will not newly deliver it. Physical removal and dead-lettering are separate operations and can happen later. Streams use segment retention rather than traditional message TTL; do not transfer queue expiry intuition into a retained log.

TTL invariant

For each queue copy, the effective deadline is the lower applicable message TTL. Expired copies are not newly delivered, but reclamation is generally head-driven and dead-lettering occurs only when a valid DLX is configured.

01 Effective deadline

Queue TTL and per-message expiration combine by taking the lower value ▸

A queue-level message TTL is configured as policy key message-ttl or declaration argument x-message-ttl. A publisher can set the AMQP 0-9-1 expiration property as a string containing milliseconds. Values are non-negative. If both forms apply, the shorter lifetime wins for that queue copy.

Suppose a publication carries expiration="5000". Checkout has a 2,000 ms policy, so its copy expires after 2 seconds. Audit has a 10,000 ms policy, so the publication’s 5-second value wins there. Routing one publication to two queues therefore creates two independently evaluated deadlines.

TTL zero has a precise edge meaning: the copy expires when it reaches a queue unless it can be delivered immediately. RabbitMQ does not send basic.return merely because a routed copy expires at zero. A configured DLX can receive it; without one, it is discarded.

02 Physical lifecycle

“Expired” and “removed from storage” are different moments ▸

RabbitMQ guarantees that an expired message is not newly delivered. It does not scan every queue position on every millisecond tick. Quorum queues dead-letter expired copies when they reach the head. Classic queues remove or dead-letter at the head and can also react when a relevant policy change notifies the queue.

This matters when TTL is applied retroactively. An expired copy can remain behind an unexpired head, consume resources, and appear in queue statistics until the head advances. A policy update is therefore not an instant disk-cleanup command. There is also a narrow delivery race if expiration happens after bytes have already been written to a consumer socket.

Production warning

Do not promise millisecond-precise deletion or use retroactive TTL as emergency free-space reclamation. Monitor ready depth, disk, and dead-letter destinations, and drain or recreate a pathological backlog under an explicit operational plan.

03 Outcome

Expiration does not imply dead-lettering, and requeue does not reset age

An expired copy is dead-lettered only when the source queue has a valid dead-letter exchange configuration and routing succeeds. Otherwise RabbitMQ discards it. “Expired messages usually go to a DLX” is unsafe wording because the DLX is optional topology with its own availability and capacity.

If a consumer explicitly requeues a delivery, or its channel closes and RabbitMQ requeues it, the original expiry time is preserved. TTL is residence age, not a fresh processing lease per attempt. A job with 200 ms remaining does not receive a new five-second budget because a worker failed.

Per-message TTL is supported by classic and quorum queue semantics, with the queue-type removal behavior above. Streams instead retain segments by age or bytes; they do not turn each reader’s replay into destructive TTL delivery.

Interview follow-up

Where does an expired message go? It is no longer newly deliverable. When RabbitMQ removes it, it is dead-lettered only if a valid DLX is configured; otherwise it is discarded. The removal itself can be head-driven.

04 Entity lifetime

Queue expiration is an inactivity lease, not message TTL

Queue expiration uses policy key expires or declaration argument x-expires, with a positive millisecond value. It deletes the queue after it has remained unused for at least that interval. “Unused” includes having no online consumer and no qualifying recent operation; declaration and basic.get can renew classic queue use. Deletion is eventual after the threshold, not an exact timer interrupt.

Quorum queues support queue expiration, but RabbitMQ’s feature matrix notes that redeclaration does not renew their lease. Streams do not support queue expiration. Type-specific behavior therefore belongs in lifecycle tests rather than in a generic “touch the queue” assumption.

RabbitMQ 4.3 denies non-durable, non-exclusive queues by default. For a shared resource that should eventually disappear, the current release guidance is a durable queue with queue TTL, rather than reviving that deprecated property combination. Exclusive queues remain the right temporary form when one connection owns them.

05 Operations

Prefer policies for mutable TTL; treat delay queues as a trade-off

Use a regular policy for queue-level message TTL and queue expiration when operators may tune them. Policies can change matching queues without an application redeploy. Hard-coded x-message-ttl and x-expires arguments are harder to revise and usually override a regular user policy, so they can defeat an emergency operational adjustment.

Per-message expiration remains a publisher property because its value describes that publication. Applying a queue TTL retroactively is valid, but the head-removal caveat means the old backlog may continue consuming resources. Roll out, observe, and validate actual dead-letter traffic.

Interviewer asks next

“Why can a five-minute message block a one-minute delay?” Because per-message expiration and physical removal are head-driven. A shorter-lived copy behind a longer-lived head may be expired but not yet dead-lettered. Separate delay buckets or use a mechanism whose ordering contract fits the requirement.

06 Worked scenario

Combine queue and per-message TTL, then observe conditional dead-lettering

The lab gives a classic work queue a two-second queue TTL and a DLX. The first publication has a shorter 200 ms per-message expiry; the second inherits two seconds. After 350 ms, requesting the next work item advances the head: RabbitMQ skips/dead-letters the expired first copy and returns the still-live second copy.

Complete TTL + DLX proofPython 3 · Pika 1.3.2

Prove lower-wins and head-driven outcome

python · install pika==1.3.2 and run against localhost
import time
import uuid

import pika

suffix = uuid.uuid4().hex[:10]
dlx = f"lab.ttl.dlx.{suffix}"

connection = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
channel = connection.channel()
try:
    channel.confirm_delivery()
    channel.exchange_declare(
        exchange=dlx, exchange_type="fanout", auto_delete=True
    )
    dead_q = channel.queue_declare(queue="", exclusive=True).method.queue
    work_q = channel.queue_declare(
        queue="",
        exclusive=True,
        arguments={
            "x-queue-type": "classic",
            "x-message-ttl": 2_000,
            "x-dead-letter-exchange": dlx,
        },
    ).method.queue
    channel.queue_bind(queue=dead_q, exchange=dlx)

    channel.basic_publish(
        exchange="",
        routing_key=work_q,
        body=b"stale-quote",
        properties=pika.BasicProperties(expiration="200"),
        mandatory=True,
    )
    channel.basic_publish(
        exchange="",
        routing_key=work_q,
        body=b"fresh-order",
        mandatory=True,
    )

    time.sleep(0.35)
    method, _properties, body = channel.basic_get(work_q, auto_ack=True)
    assert method is not None and body == b"fresh-order"

    deadline = time.monotonic() + 2.0
    expired_body = None
    while time.monotonic() < deadline and expired_body is None:
        method, _properties, expired_body = channel.basic_get(
            dead_q, auto_ack=True
        )
        if method is None:
            expired_body = None
            time.sleep(0.05)

    assert expired_body == b"stale-quote"
    print({"delivered": body.decode(), "dead_lettered": expired_body.decode()})
finally:
    connection.close()

The declaration arguments keep this disposable lab self-contained; production should normally apply queue TTL and DLX through policies. The expired copy did not generate basic.return because it was routed successfully. It reached the dead queue only because a valid DLX and binding existed.

Self-test

1. A message has expiration 5,000 ms and its queue policy says 2,000 ms. What is effective?

Two seconds. RabbitMQ applies the lower applicable per-message and per-queue TTL for that queue copy.

2. Can an expired message remain visible in queue resource use?

Yes. It is not newly deliverable, but physical removal is generally head-driven, so an expired copy can remain behind an unexpired head.

3. Does requeue restart message TTL?

No. Explicit requeue and channel-close requeue preserve the original expiry time.

4. Does TTL zero make RabbitMQ return the publish as unroutable?

No. It can expire at the queue unless immediately deliverable, but expiry does not trigger basic.return.

5. What does x-expires age?

The unused queue entity, not individual messages. Its value is a positive inactivity interval and deletion is eventual.

6. Why is TTL + DLX not an exact timer service?

Dead-lettering depends on valid topology and physical head-driven removal; mixed deadlines behind a longer-lived head can move later than their nominal expiry.
