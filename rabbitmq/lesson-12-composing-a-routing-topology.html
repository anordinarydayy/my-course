Composing a Routing Topology

A realistic event must reach selected business services and every independent audit sink. Topic plus fanout seems obvious—until that always-on audit route changes what “unroutable” means. This build converts requirements into a directed graph, tests destination sets, and exposes the alternate-exchange blind spot before production does.

Original study chapter. The topology, prose, diagrams, tests, and drills are original. Stable semantics target open-source RabbitMQ 4.3; runnable code uses Pika 1.3.2. This chapter contains three original figures, two interactive. Exchange-to-exchange and alternate exchanges are RabbitMQ features/extensions, not portability-neutral AMQP assumptions.
00 Requirements first

Turn stakeholder nouns into routing invariants

An order platform has two business subscribers: billing handles order.*.created, while fulfillment handles order.*.ready. Independently, a compliance archive and a security pipeline must each see every order publication. The naive choices both fail: one shared queue makes the four concerns compete, while four producer publishes couple application code to topology and can partially succeed.

The route contract is a set, not a single arrow. For each concrete key, write the expected destination queues. Business queues are selective. Audit queues are unconditional and independent. A topic ingress expresses the first rule; an exchange-to-exchange # edge to a fanout exchange expresses the second. To make queue de-duplication executable rather than assumed, the lab also gives compliance a redundant direct order.*.created binding from ingress; a created event reaches that same queue by two matching paths.

Design invariant

The publisher targets one ingress exchange once. Binding topology determines all queue destinations. Each reached queue gets one retained copy even if more than one graph path reaches it; the deliberate compliance overlap must still yield one copy.

01 Business branch

Start with selective service routes ▸

The ingress exchange is topic because services subscribe to stable slices of a dot-separated key. Billing binds order.*.created; fulfillment binds order.*.ready. Publishers emit concrete keys such as order.eu.created. Service ownership is now visible in bindings rather than hidden in producer conditionals.

This branch deliberately rejects unknown event shapes. order.eu.cancelled matches neither service queue. At this stage it is unroutable. That statement will change after the audit branch is attached—which is exactly why topology must be evaluated as one graph.

02 Cross-cutting branch

Add one # edge to a fanout audit exchange ▸

Bind the fanout exchange events.audit as a destination of the topic ingress using #. Hash admits every routing key, including a zero-segment suffix. Once admitted, the destination fanout ignores the key and reaches every bound audit queue.

Compliance and security need separate queues. If they shared one, they would compete, and one concern's outage or acknowledgements would affect the other. The fanout exchange itself is not an audit log; it stores nothing. The audit queues provide independent retention and delivery.

The lab adds one intentionally redundant edge: compliance.q also binds directly to the topic ingress with the valid pattern order.*.created. For order.eu.created, that direct path and the # → fanout path converge on compliance, but RabbitMQ enqueues one compliance copy. Other matrix rows reach compliance only through fanout.

Interview follow-up

“Why not attach two consumers to one audit queue?” Because consumers on one queue compete. Separate queues are required when compliance and security must each observe every publication and own independent backlog and retry behavior.

03 Verification

Test the topology as a routing matrix

Visual plausibility is not enough. For each representative key, assert the complete set of queue destinations. Include a normal key for each business branch, a business miss, an unrelated domain, the audit queues, and a deliberate overlap. A matrix makes hidden assumptions reviewable before any consumer runs.

For this graph, order.eu.created reaches billing, compliance, and security; compliance is reached directly and through fanout but appears once. order.eu.ready reaches fulfillment, compliance, and security. order.eu.cancelled and unrelated billing.eu.created reach compliance and security only. Thus both business branches are exercised, every publication is audited, and every row is routed at ingress.

04 Hidden consequence

The unconditional audit branch masks business-route misses

An alternate exchange runs only when no queue is reached through the primary exchange's combined route graph. After the # audit branch exists, every publication reaches compliance and security as long as those bindings and queues are healthy. Therefore order.eu.cancelled is routed—even though no business service matched.

Prefer an operator-managed policy for production AE configuration because it can change without redeploying declarers. A client-supplied alternate-exchange declaration argument overrides a policy when both specify one. For that client declaration RabbitMQ checks configure and read permission on the source exchange and write permission on the named alternate exchange.

The alternate need not exist when the primary exchange is declared; declaring it first is merely convenient. If an unroutable publication later needs a configured AE that is missing, RabbitMQ emits a warning rather than recording a successful route. An AE receives the original message and routing key and can have its own AE. The chain terminates when a queue is reached, when the current exchange has no configured AE, or before a cycle would revisit an exchange already traversed.

Adding an alternate exchange to events.in cannot detect “no service accepted this key.” It sees the successful audit destinations and does not run. Likewise, mandatory=true will not return the publication. A successful alternate route would also satisfy mandatory; only a publication that reaches no primary or alternate queue is returned.

Production warning

Do not use ingress unroutable counts as a proxy for business coverage once an unconditional audit, metrics, or archive branch exists. The routing invariant is “at least one queue anywhere in the graph,” not “at least one queue in the branch I care about.”

05 Architecture choice

Separate business-miss semantics when they matter

If a miss means “the publisher used an unsupported business event,” validate the event contract before publishing and reject unknown keys at the application boundary. If misses must be broker-observable, publish to a business-only routing boundary whose alternate exchange can see an empty service destination set, then handle audit as a separate, explicitly reliable operation. That second publication introduces partial-success risk and needs confirms, idempotency, or an outbox.

Another option is to treat audit as a consumer of the accepted business stream rather than an unconditional ingress branch, but then genuinely unsupported publications are not audited. There is no free topology that simultaneously makes an audit queue count as routed and makes the same queue invisible to the alternate-exchange decision.

Interviewer asks next

“Can an alternate exchange tell whether a billing queue matched if an audit queue did?” No. AE activation asks whether any queue was reached in the route graph. Branch-specific acceptance is an application/topology contract you must model separately.

06 Worked scenario

Build the graph, execute the matrix, and keep the alternate empty

The lab configures an alternate exchange on ingress, then attaches both business branches, the unconditional audit branch, and the deliberate direct compliance overlap. It publishes the created, ready, cancelled, and unrelated matrix rows. Assertions prove both selective services, one audit copy per event—including the two-path created case—and an empty alternate queue. That empty queue is the intended consequence of universal audit, not a broken test.

Complete runnable topology proofPython 3 · Pika 1.3.2

Declare in dependency order, publish once, assert sets

python · install pika==1.3.2 and run against localhost
import pika

connection = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
try:
    channel = connection.channel()
    channel.confirm_delivery()

    channel.exchange_declare(
        "lab.unrouted", exchange_type="fanout", auto_delete=True
    )
    channel.exchange_declare(
        "lab.audit", exchange_type="fanout", auto_delete=True
    )
    channel.exchange_declare(
        "lab.ingress",
        exchange_type="topic",
        auto_delete=True,
        arguments={"alternate-exchange": "lab.unrouted"},
    )

    names = ("billing", "fulfillment", "compliance", "security", "miss")
    queues = {
        name: channel.queue_declare(queue="", exclusive=True).method.queue
        for name in names
    }
    channel.queue_bind(
        queues["billing"], "lab.ingress", routing_key="order.*.created"
    )
    channel.queue_bind(
        queues["fulfillment"], "lab.ingress", routing_key="order.*.ready"
    )
    channel.queue_bind(
        queues["compliance"], "lab.ingress", routing_key="order.*.created"
    )
    channel.exchange_bind(
        destination="lab.audit", source="lab.ingress", routing_key="#"
    )
    channel.queue_bind(queues["compliance"], "lab.audit")
    channel.queue_bind(queues["security"], "lab.audit")
    channel.queue_bind(queues["miss"], "lab.unrouted")

    keys = [
        "order.eu.created",
        "order.eu.ready",
        "order.eu.cancelled",
        "billing.eu.created",
    ]
    for key in keys:
        channel.basic_publish(
            "lab.ingress",
            routing_key=key,
            body=key.encode("utf-8"),
            mandatory=True,
        )

    def drain(queue_name):
        result = []
        while True:
            method, _properties, body = channel.basic_get(queue_name, auto_ack=True)
            if method is None:
                return result
            result.append(body.decode("utf-8"))

    received = {name: drain(queue) for name, queue in queues.items()}
    assert received["billing"] == ["order.eu.created"]
    assert received["fulfillment"] == ["order.eu.ready"]
    assert received["compliance"] == keys
    assert received["security"] == keys
    assert all(received["compliance"].count(key) == 1 for key in keys)
    assert received["compliance"].count("order.eu.created") == 1
    assert received["miss"] == []
    print(received)
finally:
    connection.close()

Declaring lab.unrouted first is convenient for a deterministic lab, not a requirement that it exist when ingress is declared; it must be available if a later unroutable publish needs it. Pika's E2E call names destination first. Created proves two paths converge on one compliance copy, ready proves fulfillment, and cancelled plus unrelated prove universal audit. All four publishes satisfy mandatory through audit queues, so the alternate queue remains empty.

Self-test

1. Why does each independent audit sink need its own queue?

Consumers sharing one queue compete. Separate queues provide each sink every publication plus independent backlog, acknowledgements, and retry fate.

2. What roles do the topic and fanout exchanges each retain?

The topic source decides which keys enter each branch; the fanout destination sends every admitted publication to all its bound audit queues.

3. Which row proves overlap de-duplication, and what does cancelled reach?

order.eu.created reaches compliance directly and through fanout but produces one compliance copy. order.eu.cancelled reaches no business queue, but it reaches both compliance and security.

4. Why does the ingress alternate exchange not receive that cancelled event?

The audit branch reaches queues, so the combined primary route graph is not empty. Alternate routing is therefore not activated.

5. Will mandatory=true return a business miss that reaches audit?

No. Reaching any audit queue makes the publication routed for mandatory semantics.

6. How can a design detect “no business service matched” despite universal audit?

Validate the business contract before publish or use a separate business-only routing boundary and accept the reliability cost of a separate audit operation.
