07Concept · RabbitMQ

Virtual Hosts, Users & Multi-Tenancy

You almost never have just one app. You have payments, notifications, and analytics, plus a staging copy of each, plus three teams who all named a queue orders. A single flat broker lets their names collide and their messages mix; a broker each is wasteful. RabbitMQ splits the difference with the virtual host — a fully isolated logical broker living inside one physical broker — and layers users, permissions, and tags on top as the access-control story. This lesson builds the mental model of that boundary and shows exactly where it stops.

Original study notes. Written from scratch for engineers prepping backend and system-design interviews — and the real work behind them. Facts track RabbitMQ 4.x (mid-2026) and are treated as illustrative. Names like vhost, configure/write/read, and Khepri are used as plain identifiers; every sentence, diagram, and line of code is our own. 00 Orientation

One broker is not one namespace

Here is the tension every multi-tenant broker is an answer to. Standing up a RabbitMQ cluster — and keeping it highly available — is expensive to operate. So you're tempted to run one and put everything on it. But the moment three teams share a single flat broker, three problems arrive together. Their resource names collide: everyone wants a queue called orders, and the second team to declare it either fails or, worse, silently binds to the first team's queue. There's no access boundary: any connection that can read one queue can, by default, read them all. And there's no blast-radius control: a runaway app can open every connection or declare a million queues and starve the rest.

Spinning up a separate broker per app fixes all three but wastes hardware and multiplies the operational burden. The virtual host — usually shortened to vhost — resolves the tension: it partitions the single physical broker into independent logical brokers, so each app behaves as if it owns the whole thing. Crucially this is a logical, administrative boundary. A vhost is not a separate OS process, a separate port, or a separate node; creating one costs almost nothing and takes milliseconds. It is a namespace and a runtime scope drawn inside the broker you already run.

The one sentence to leave with

A vhost is a namespace boundary and a runtime boundary; a user is a broker-wide identity whose reach inside each vhost is defined by permissions and tags. Multi-tenancy in RabbitMQ is exactly that pairing: vhosts for isolation, users and permissions and tags for the access-control layer on top.

01 The boundary

What actually lives inside a vhost ▸

To reason about isolation you need to know precisely what a vhost contains and what it does not. Everything on the messaging path is vhost-scoped: exchanges, queues, bindings, and all the runtime objects that hang off them — connections, channels, consumers, and the messages flowing through. Two queues with the same name in two different vhosts share nothing: not messages, not bindings, not consumers, not even a byte of state. orders in /payments and orders in /analytics are two unrelated queues that never see each other.

What is broker-global and therefore not vhost-scoped is just as important: users, the metadata store, the cluster's nodes, the network listeners and ports, and the Erlang runtime itself. Those are shared by every vhost. The default vhost created at install is a single forward slash, / — you'll want your apps off it, but it's always there. Step through two identically-named queues to see that a name only has to be unique within a vhost, and that a connection is pinned to exactly one vhost for its whole life:

Namespace and runtime, in one boundary

A vhost isolates names (so orders can exist twice) and runtime (so the connections, channels, and consumers in one vhost are invisible to another). There is no cross-vhost routing, ever — an exchange in /payments cannot deliver to a queue in /analytics. If you need a message to travel between vhosts, you move it explicitly with a tool like the shovel or federation plugin; the core routing engine will never do it for you.

02 Identity

Users authenticate to the broker, not to a vhost

Here is the split that trips almost everyone up the first time. A user is a broker-wide credential — a username plus a password hash, or an x509 certificate or OAuth 2.0 identity. Authentication — the “who are you?” question — happens exactly once, at connection time, against the broker as a whole. You do not log in to a vhost; you log in to the broker and then select a vhost for that connection. So the rule to memorize is: authentication is global; authorization is per-vhost. One identity, many possible reaches.

Every fresh install ships one user, guest with password guest, and this is where the classic “why can't I connect?” gotcha lives. By default guest is restricted to loopback connections — it works from localhost and is refused from any remote host — a deliberate safety default so a freshly-exposed broker isn't wide open. You must never ship guest as a production credential, and you'll usually want your apps off the default / vhost entirely, each with its own dedicated user.

Why the two-word split matters

Because a user is global, one service account can be granted access to several vhosts, or none. Authenticating tells the broker you are svc-orders; it tells the broker nothing about what svc-orders may do. That second question — may this identity publish here, consume there, alter topology anywhere — is authorization, and it is answered entirely by per-vhost permissions, which is the next section.

03 Authorization

configure / write / read — regexes, per vhost ▸

For each (user, vhost) pair you grant exactly three permissions, and each one is a regular expression matched against resource names. configure covers altering topology — creating or deleting a queue or exchange. write covers publishing to an exchange (and binding a queue to it). read covers consuming from a queue, and is the permission checked on the exchange that acts as a binding's routing source. Two special values do most of the work in practice: the empty string "" matches nothing and so grants no access, while .* matches everything. A user with no permission entry at all for a vhost cannot even open a connection to it — the refusal happens during connection, not later on a declare.

There is a finer, separate layer called topic permissions that authorizes individual routing keys on a topic exchange — reach for it when name-level control isn't precise enough. But the canonical payoff of the three basic permissions is the least-privilege split: a pure publisher gets write (and read only if it consumes replies) with configure left empty, so it can send but never reshape the topology; a pure consumer gets read. Watch one user, svc-orders, pass through all three gates — authentication, then per-vhost permissions, then the management plane:

Read the diagram as three independent checks in sequence. The user cleared authentication once, yet /staging still refused the connection — because authorization is a per-vhost question with its own answer. And even inside a vhost the permission is per-name: declaring orders passed the configure regex ^orders$, while audit-log failed the same regex and was denied. Default-deny is the spirit throughout: no matching entry means no access.

Least privilege as a naming convention

Because permissions are regexes over names, a naming convention becomes a security boundary. Give a publisher write of ^pay\..* and it can only publish to exchanges whose names start with pay.; the convention and the authorization rule are the same string. Anchor your regexes — ^pay\..*, not the unanchored pay\..*, which would also match xpay.foo.

04 Management plane

Tags gate the management plane

Permissions govern the messaging path — the AMQP operations of declaring, publishing, and consuming. A completely separate axis, user tags, governs the management path — the HTTP Management API and the web UI. The two are orthogonal, and conflating them is one of the most common mistakes in interviews. The standard tags are management (log in to the UI and see your own permitted vhosts), monitoring (see all vhosts and cluster-wide metrics), policymaker (manage policies and runtime parameters in your permitted vhosts), and administrator (everything, including creating users and vhosts). There's also a rarely-used impersonator and support for custom tags.

The key consequence: a user can hold full messaging permissions and no tag at all. That user is a perfectly functional AMQP client — it publishes and consumes fine — and is completely invisible in the management UI. That is the normal, correct shape for a service account. It also demolishes the myth that you need the administrator tag to send or receive messages: administrators manage the broker; messaging is governed entirely by per-vhost permissions, so a well-designed client carries no tag.

Permissions — the messaging door

  • Govern the AMQP path: declare, publish, consume.
  • Scoped per (user, vhost), per-resource-name regex.
  • Values: three regexes configure/write/read (plus optional topic permissions).
  • A service account has full messaging perms in its own vhost.

Tags — the management door

  • Govern the HTTP API / UI path only.
  • A broker-wide capability level, not per-vhost.
  • Values: management, monitoring, policymaker, administrator.
  • A service account typically has no tag at all.
Interviewer asks next

“How do you give a monitoring tool read-only visibility into every vhost without letting it publish or consume?” Answer: give it the monitoring tag — which sees every vhost's metrics cluster-wide — and grant it no messaging permissions at all. Because tags and permissions are independent axes, it can observe the whole broker while being unable to touch a single message. That independence is the whole point.

05 Worked example

Blast radius: limits, defaults, and onboarding a tenant

Isolating names is tidy; isolating resources is what makes multi-tenancy safe. Two per-vhost knobs do that. max-connections and max-queues (set with rabbitmqctl set_vhost_limits, where -1 means unlimited) cap how much of the broker a single tenant can consume, so a noisy neighbor can't exhaust the cluster's connections or flood it with queues. A per-vhost default queue type — classic, quorum, or stream — decides what kind of queue the team gets when they declare one without specifying; set it to quorum and every queue is replicated and durable by default. You can also attach vhost metadata (a description and tags) and pre-seed limits in rabbitmq.conf for vhosts that get created dynamically. Now put every idea in this lesson together and onboard a team.

Worked examplerabbitmqctl / CLI · pika
Onboarding the payments team onto the shared broker

The platform team runs one 3-node cluster. payments needs its own isolated space, a service account that can only publish and consume its own resources (least privilege, never creating topology), a human lead who can manage policies and see the UI, sane resource caps so payments can't starve other tenants, and quorum queues by default. No app should ever touch guest or the / vhost.

Think it through

Isolation first

A vhost costs nothing and gives payments its own namespace and runtime. Create it before any user, with quorum as the default queue type so durability is the default, not an opt-in.

Authenticate globally, authorize locally

add_user mints an identity; it grants no power. set_permissions -p payments is the line that actually lets that identity do anything — and only in this vhost.

Least privilege via regex

The publisher gets write/read pinned to ^pay\..* and configure of ^$ (matches nothing) — so it can send and receive on its own names but can never alter topology. Ops pre-declares queues.

Tags are a different door

svc-payments gets no tag (invisible to the UI). alice gets management+policymaker, not administrator — she manages payments, not the broker.

Cap the blast radius

set_vhost_limits converts logical isolation into resource protection: at most 500 connections and 200 queues, so one tenant can't exhaust the cluster.

Provision it · rabbitmqctl (run on any node; changes replicate)

bash

# 1) Isolated vhost — its own namespace, quorum queues by default
rabbitmqctl add_vhost payments \
  --description "Payments team - prod" \
  --default-queue-type quorum \
  --tags "team-payments,prod"

# 2) Cap the blast radius: at most 500 connections, 200 queues (-1 = unlimited)
rabbitmqctl set_vhost_limits -p payments '{"max-connections": 500, "max-queues": 200}'

# 3) Service account — authenticates to the BROKER, scoped only to `payments`
rabbitmqctl add_user svc-payments 's3cr3t-rotate-me'
# no set_user_tags  →  this account cannot touch the management UI/API at all

# 4) Least privilege, as regexes over RESOURCE NAMES:
#    configure ^$   → may NOT create/delete topology (ops pre-declares it)
#    write / read   → only names starting with "pay." (its own objects)
rabbitmqctl set_permissions -p payments svc-payments \
  '^$' '^pay\..*' '^pay\..*'
#      configure    write         read

# 5) A human lead — manages policies + sees the UI, but is NOT a broker admin
rabbitmqctl add_user alice 'change-me'
rabbitmqctl set_user_tags alice management policymaker
rabbitmqctl set_permissions -p payments alice '.*' '.*' '.*'

# 6) Verify
rabbitmqctl list_permissions -p payments
rabbitmqctl list_vhost_limits -p payments

Same thing over the HTTP API · handy in CI

bash

# rabbitmqadmin v2 (RabbitMQ 4.x) — flag syntax, not the legacy key=value form
rabbitmqadmin declare vhost --name payments --default-queue-type quorum \
  --description "Payments team - prod"

rabbitmqadmin declare permission --vhost payments --user svc-payments \
  --configure '^$' --write '^pay\..*' --read '^pay\..*'

Client side · the vhost is chosen at CONNECT time

python

import pika

# The vhost is part of the connection parameters — not switchable later.
params = pika.ConnectionParameters(
    host="broker.internal",
    virtual_host="payments",                    # pinned for this connection's life
    credentials=pika.PlainCredentials("svc-payments", "s3cr3t-rotate-me"),
)
conn = pika.BlockingConnection(params)
ch = conn.channel()

# Works: name matches the write/read regex ^pay\..*
ch.basic_publish(exchange="pay.events", routing_key="charge.created", body=b"...")

# Fails at declare: configure is ^$ (empty) → ACCESS_REFUSED, channel closed by broker.
# ch.queue_declare(queue="pay.charges")   # raises ChannelClosedByBroker (403)
Narrate it to the interviewer

“I create a vhost per tenant, because it costs nothing and gives payments its own namespace and runtime. I set its default queue type to quorum so every queue the team declares is replicated and durable without them thinking about it. Then I mint a service user — it authenticates to the broker, but I scope it with per-vhost permissions: write and read regexes pinned to a pay. prefix, and configure empty so it can send and consume but never reshape topology. I give it no management tag, so it's a pure client, invisible in the UI. The human lead gets management+policymaker, not administrator, because she runs payments, not the broker. Finally I cap max-connections and max-queues so a noisy payments deploy can't starve other tenants — and I never let anything near guest or the / vhost.”

Edge cases to raise aloud: deleting a vhost is irreversible — it drops every queue, exchange, binding, and message in it, so it's a big hammer; zero permissions means no connection — the refusal happens at connect, not on the first declare; changing permissions doesn't retroactively close existing channels or consumers, so force-close connections if you need immediate revocation; topic exchanges need topic permissions if you want to authorize by routing key rather than by name.

06 Judgment

Choosing your tenancy boundary — and where it stops

In practice you draw the vhost boundary along one of three lines: by environment (/prod, /staging), by team or app, or by customer. All three are cheap and all three give you full name isolation and per-vhost access control. But you must know exactly what the boundary does not give you, because that's the interview trap. A vhost is not a network, CPU, or OS sandbox. Every vhost shares the same nodes, the same Erlang schedulers, the same memory, and the same disk. A quorum queue in /payments competes for the very same Raft and I/O budget as one in /analytics. Per-vhost limits cap counts; they do not partition hardware.

So when you need genuine physical isolation — hard resource guarantees, an independent failure domain, independent upgrade windows, or a compliance boundary — the answer is not more vhosts but separate clusters. The static map below is the reference to keep in your head: vhost columns on shared nodes, a metadata ribbon underneath, users fanning in by permission.

That ribbon is the last piece of the model. In RabbitMQ 4.x all vhost, user, and permission definitions live in the Khepri metadata store — a Raft-based store that replicates them to every node — so your topology of tenants exists identically across the cluster and survives a node loss. (Khepri has been fully supported since 4.0, and over the 4.x line it becomes the default and eventually the only metadata store — so on a current 4.x cluster it holds and replicates every vhost, user, and permission.) Here are the three isolation strengths side by side:

Shared vhost · naming only

  • Name safety: none — manual prefixes.
  • Access control: regexes within one vhost.
  • Resource isolation: none.
  • Cost: lowest. Use only for one trusted, tidy team.

Separate vhosts · one cluster

  • Name safety: full — unique per vhost.
  • Access control: per-vhost users, permissions, tags.
  • Resource isolation: logical only — limits cap counts, nodes shared.
  • Cost: very low. The default multi-tenant choice.

Separate clusters

  • Name safety: full; independent auth per cluster.
  • Resource isolation: physical — dedicated hardware.
  • Failure domain & upgrades: independent.
  • Cost: highest. Use for compliance / hard SLA / noisy-neighbor guarantees.
The blast-radius rule

Vhosts isolate names and access, not hardware. Set max-connections and max-queues to stop one tenant from exhausting the broker, treat the default queue type as your durability default, and reach for separate clusters — not more vhosts — the day you need a true physical or failure boundary. Everything above that line is logical, and logical isolation is shared substrate wearing many name tags.

★ Review

Summary & self-test

The whole lesson compresses to one idea: a vhost is a fully isolated logical broker inside one physical broker — its own exchanges, queues, bindings, and runtime — while a user is a broker-wide identity whose reach in each vhost is set by permissions and tags. You authenticate once to the broker, you're authorized per vhost, and the isolation stops at the hardware. Everything else is where you draw the boundary and how tightly you cap it.
