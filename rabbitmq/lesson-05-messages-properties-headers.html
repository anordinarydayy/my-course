05Concept · RabbitMQ

Messages: Properties, Headers & the Body

Most people picture a “message” as the payload they publish — and then get baffled when a message vanishes across a restart, a per-message TTL silently does nothing, or a user_id earns them a channel exception. Every one of those surprises is the same gap: not knowing which parts of a message the broker reads and acts on versus which parts it carries blindly from producer to consumer. This lesson draws that line sharply.

00 Orientation

The three compartments of a message ▸

Think of a RabbitMQ message as an envelope with three compartments, and read every field through one question: does the broker act on this, or just carry it?

  • The body is an opaque byte array. The broker never parses, validates, or looks inside it. JSON, Protobuf, a JPEG, or random bytes are all identical to RabbitMQ. Content is 100% an application contract, signalled out of band by a property like content_type — the bytes themselves mean nothing to the broker.
  • The well-known properties (basic.properties) are a fixed, spec-defined set of typed fields. A small subset drives broker behaviour (delivery_mode, expiration, priority, user_id); the rest are transport metadata the broker preserves untouched for the consumer.
  • The headers are an arbitrary, application-defined key/value table that lives inside the properties. Mostly pass-through — except a handful the broker reads (CC/BCC, headers-exchange matching) and a handful the broker writes (x-death).

The one sentence to leave with: the broker reads a tiny, well-defined set of fields to make routing and lifecycle decisions; everything else — including the entire body — is metadata it faithfully delivers but never interprets. The question to apply to every field

“Does the broker read this, or just carry it?” Ask it of the body (carry), of delivery_mode (read), of correlation_id (carry), of the CC header (read). Once that boundary is instinct, message design stops being guesswork and mysterious behaviours become predictable.

01 The vocabulary

The well-known properties: a fixed vocabulary

AMQP 0-9-1 defines a fixed set of basic.properties. These keys are reserved and typed — you don’t invent new ones here. Custom data belongs in headers (itself one of these properties). Split the set into two buckets and you’ve captured most of the lesson:

  • Metadata for the consumer — the broker moves these byte-for-byte and does nothing else: content_type, content_encoding, correlation_id, reply_to, message_id, timestamp, type, app_id, and headers.
  • Broker-acted-upon — the four the broker actually inspects to make a decision: delivery_mode, expiration, priority, user_id.

A useful first design instinct is knowing where a given piece of information should live at all. The same value can go in a property, a header, or the body — but the consequences differ sharply:

Well-known property

  • Keys defined by the spec, fixed and typed.
  • The broker may act on the read-set.
  • Use for TTL, persistence, priority, RPC ids, content type.
  • Misuse cost: wrong type = a silent no-op (e.g. expiration).

Header

  • Keys are yours, arbitrary and free-form.
  • Broker acts only on CC/BCC, headers-exchange matches, and x-*.
  • Use for trace / tenant / schema metadata and extra routing.
  • Misuse cost: colliding with x-*/CC = surprise behaviour.

Body

  • Bytes are yours, wholly arbitrary.
  • The broker acts on it never.
  • Use for the actual payload.
  • Misuse cost: encoding routing intent here = the broker ignores it.
Headers are a property, not a separate frame

A common mental slip is picturing headers as a distinct part of the wire frame. It isn’t — headers is one of the well-known properties, a nested table sitting inside basic.properties. And the key namespaces are reserved: property keys are fixed by the spec, and header keys starting with x- belong to the broker and its plugins, so don’t name your own keys that way.

02 The read-set

The four properties the broker acts on

This is the heart of the lesson. Exactly four standard properties change what the broker does with a message; learn these and the rest is transport metadata.

  • delivery_mode — 1 = transient, 2 = persistent. Value 2 asks the broker to write the message to disk on a durable classic queue. It is a request, not a guarantee (section 05 is dedicated to the catch).
  • expiration — a per-message TTL. When it elapses the broker drops the message, or dead-letters it if the queue has a dead-letter exchange. The notorious gotcha: it is a string of milliseconds. expiration="60000" is correct; the integer 60000 is a client-dependent trap — many clients (pika included) raise if you pass an int, and where a client lets it through, the value simply won’t take effect.
  • priority — honoured only where the queue supports it. A classic queue must be declared with x-max-priority (up to 255 levels, though ≤ ~10 is recommended); a quorum queue in 4.x provides two effective levels — normal and high, with any priority > 4 treated as high. Set on a queue with no priority support, it is simply ignored.
  • user_id — if present, the broker validates it equals the connection’s authenticated username and rejects the publish otherwise. This is enforcement, not decoration — describing it as pass-through is wrong.
The two classics: a string TTL and an enforced user_id

expiration must be a string of milliseconds — pass an integer and the outcome is client-dependent: many clients (pika included) raise, and where a client lets it through it violates the field’s type and simply doesn’t take effect. And a mismatched user_id doesn’t get quietly stripped: the broker raises a channel exception and closes the channel. Two failure modes — one client-dependent, one always a loud broker-side rejection — both from the read-set.

03 Pass-through

Metadata the broker carries but never reads

Everything outside that four-field read-set is a convention. The broker moves correlation_id, reply_to, content_type, content_encoding, message_id, timestamp, type, and app_id byte-for-byte from publisher to consumer and does nothing else with them. Their meaning is entirely an agreement between your producer and consumer.

The RPC pattern is the classic example: reply_to names a queue for the answer and correlation_id ties a reply back to its request — but the application, not the broker, reads those and publishes the reply. RabbitMQ won’t route a response for you; it just carried the two labels along.

The single most persistent myth here: setting content_type="application/json" does not make the broker parse or validate JSON. The body is always opaque bytes. content_type is a hint the consumer chooses to honour — validation is the application’s job, full stop.

The one special-cased reply_to

There is exactly one place the broker treats a pass-through field specially: the pseudo-queue amq.rabbitmq.reply-to. Set reply_to to that magic name and you get direct reply-to — a fast, queueless RPC return path the broker manages, with no real reply queue to declare or clean up. Any other reply_to value is pure metadata your code must act on.

04 Headers

Headers — and the few the broker reads

The headers table is a free-form field map for application metadata: trace ids, tenant, schema version, anything. By default it is pure pass-through — but three categories are broker-significant, and knowing them is the sharpest point of the lesson.

  • Routing headers. The CC and BCC headers add extra routing keys (“sender-selected distribution”): the broker routes an additional copy using each listed key. BCC is stripped before the message reaches any consumer, so the extra destination stays hidden. Separately, a headers exchange matches on header key/values using x-match: all | any | all-with-x | any-with-x instead of a routing key (the -with-x variants also match x--prefixed headers).
  • Broker-written headers. On dead-lettering, the broker injects and updates x-death (a running history of rejections/expiries) plus x-first-death-reason, x-first-death-queue, and x-first-death-exchange. You read these; you don’t set them.
  • Reserved x- conventions. The x- prefix is reserved by the broker and plugins. Your keys should avoid it.

05 Durability

delivery_mode is necessary, not sufficient ▸

Now the half-truth that trips almost everyone: “set delivery_mode=2 and my message is safe.” It isn’t, by itself. Persistence needs both a persistent message and a durable queue. A persistent message on a transient (non-durable) queue is still lost on restart, because the queue itself doesn’t survive. Step through a restart and watch which message lives:

And persistence is still not the same as a delivery guarantee. To know the broker actually accepted and durably stored a message, you need publisher confirms — a forward reference to the reliability phase. On quorum queues and streams everything is on disk by design, so delivery_mode is effectively moot there.

“Persistent message” (delivery_mode=2)

  • A request to write the message to disk.
  • A no-op on a non-durable queue.
  • Irrelevant on quorum queues / streams — always on disk.

“Durable delivery”

  • Persistent message + durable queue + publisher confirms.
  • Survives a broker restart and is acknowledged as stored.
  • Quorum queues give the durable-queue half by default.
Misconception to flag out loud

“delivery_mode=2 guarantees my message won’t be lost” is half-true: without a durable queue and publisher confirms it guarantees nothing. And a historical trap — reaching for “classic mirrored queues” as the durability answer. Those were removed in 4.0; the modern replicated-durability answer is quorum queues.

06 Worked example

Worked: an order event with an audit copy

Let’s exercise all three compartments in a single publish. It touches a broker-read property, a broker-read header, and pass-through metadata at once — exactly the shape an interviewer probes.

Worked exampleorder-service · Python / pika
Publish once, route twice, and identify the sender

An order-service publishes an order.created event that must: go to the orders queue, send a copy to an audit queue via the CC header, carry a 60-second per-message TTL as a string, be persistent, identify the publisher via user_id, and carry RPC-style reply_to/correlation_id — all in one publish.

Think it through

Serialize + signal

The broker sees body as bytes; the consumer only knows it’s JSON because we set content_type. Serialization and its advertisement are separate steps — the broker validates neither.

Persistence is two-part

delivery_mode=2 is a request; it’s honoured only because orders and audit are declared durable=True. Drop the durability and the “persistent” flag is a no-op.

TTL type discipline

expiration is a string of milliseconds. expiration=60000 (an int) is a client-dependent trap — pika raises, and clients that let it through never apply the TTL; "60000" is correct.

Extra fan-out for free

CC: ["audit"] tells the broker to also route using audit as a key — one publish, two queues, no exchange change. Use BCC if the copy’s destination must be hidden (the broker strips it before delivery).

user_id is enforced

Because the connection authenticated as order-service, user_id="order-service" passes validation. Any other value → the broker raises a channel exception and closes the channel.

The single publish

python

import pika, json, uuid

# Connection authenticated as user "order-service"
creds = pika.PlainCredentials("order-service", "secret")
conn  = pika.BlockingConnection(pika.ConnectionParameters("localhost", credentials=creds))
ch    = conn.channel()

# Durable queues, so delivery_mode=2 actually means something
ch.queue_declare(queue="orders", durable=True)
ch.queue_declare(queue="audit",  durable=True)

payload = {"order_id": 4711, "total": 99.90}

props = pika.BasicProperties(
    delivery_mode=2,                  # READS: persist to disk (on a durable queue)
    expiration="60000",              # READS: per-message TTL — MUST be a STRING of ms
    priority=5,                      # READS: only if the queue supports priority
    user_id="order-service",         # READS: must equal the authenticated user, or publish is rejected
    content_type="application/json", # PASS-THROUGH: a hint; broker does NOT parse the body
    content_encoding="utf-8",        # PASS-THROUGH
    correlation_id=str(uuid.uuid4()), # PASS-THROUGH: app-level RPC correlation
    reply_to="q.thumbs.reply",         # PASS-THROUGH: app names its own reply queue
    message_id=str(uuid.uuid4()),
    type="order.created",            # PASS-THROUGH
    app_id="order-service",          # PASS-THROUGH
    headers={
        "CC": ["audit"],            # READS: routes an extra copy using "audit" as a key
        "trace_id": "abc-123",     # PASS-THROUGH: your metadata
        "schema_version": 2,       # PASS-THROUGH
    },
)

# Default exchange routes by routing_key == queue name; CC adds "audit" as a second key
ch.basic_publish(
    exchange="",
    routing_key="orders",
    body=json.dumps(payload).encode("utf-8"),  # opaque bytes to the broker
    properties=props,
    mandatory=True,                          # bounce back via basic.return if unroutable
)
print("published")
conn.close()
Narrate it to the interviewer

“I publish it persistent on durable queues with a string TTL, use the CC header to fan a copy to audit, and set user_id so the broker can vouch for the sender. content_type, correlation_id, and reply_to are purely consumer-facing metadata — the broker acts on delivery_mode, expiration, priority, user_id, and CC, and carries the rest untouched. One publish, two queues, no exchange reconfiguration.”

Edge cases to raise aloud: expiration as an int → client-dependent (pika raises; where a client lets it through it just won’t take effect), must be a string; priority=5 with no priority support → ignored on a classic queue, coarsened to normal/high on a quorum queue (any priority > 4 = high); user_id mismatch → a channel exception, not a silent drop and different from an unroutable message; mandatory=True with a bad key returns the message via basic.return — register a return callback; routing in the body (e.g. a "cc" field in the JSON) does nothing — only the CC header is broker-read.

07 Limits & bridge

Body limits, and the richer AMQP 1.0 model

The opaque body isn’t unbounded. RabbitMQ 4.x defaults max_message_size to 16 MiB (16,777,216 bytes), with an absolute hard ceiling of 512 MiB. The practical guidance follows from the whole lesson: the broker moves bytes it never reads, so a giant payload just burns memory and network for no routing benefit. Keep messages small and put large blobs in object storage, then carry a pointer (a URL or key) in the message.

One bridge before we close. Everything above describes AMQP 0-9-1, this course’s primary model. Over native AMQP 1.0 — first-class in 4.x, not a plugin — the message model is richer: distinct header, delivery-annotations, message-annotations, properties, application-properties, and body sections. In 1.0 “persistent” is the durable boolean in the header section (the analog of delivery_mode=2). RabbitMQ maps transparently between 0-9-1 and 1.0 — and crucially, the read-vs-pass-through principle is identical: a small set of fields drives behaviour, and the body is always yours.

Same principle, more compartments

Don’t over-index on the 1.0 section names for interviews — the takeaway is that even a richer envelope keeps the same contract. A narrow, typed set of fields steers routing and lifecycle; annotations and application properties are metadata; the body stays an opaque payload the broker never parses.

★ Review

Summary & self-test

The whole lesson compresses to one idea: a message is an opaque body plus a fixed set of well-known properties plus arbitrary headers — and the broker reads only a tiny, well-defined slice of that (delivery_mode, expiration, priority, user_id, and the CC/BCC headers), faithfully carrying everything else — including the entire body — untouched to the consumer.
