35Core mechanism · Streams & multi-protocol

MQTT 5.0, STOMP & Protocol Interop

RabbitMQ speaks MQTT and STOMP through bundled plugins and can carry both over WebSocket. Producers and consumers on different protocols can meet on the same exchange or queue — but only after their addresses and bindings align, and only for the fields that conversion preserves. “Most of MQTT 5,” not all; and cross-protocol is a topology choice, not automatic equivalence.

Original study chapter. The prose, scenarios, diagrams, and code are original. Stable behavior targets open-source RabbitMQ 4.3 (latest signed patch overlay 4.3.3; public release/download/docs pages still showed 4.3.2 when accessed 2026-07-21). The runnable example uses the Eclipse Paho MQTT Python client 2.x speaking MQTT 5.0. This chapter has three original figures, two interactive.
00 Failure first

Three comfortable illusions about “multi-protocol”

The first illusion is that MQTT 5.0 support means full MQTT 5.0 conformance. RabbitMQ supports most MQTT 5 features, and the gaps matter: QoS 2 is unsupported, re-authentication via the AUTH packet is unsupported, shared subscriptions are unsupported, and retained messages carry node-local and wildcard caveats. A device fleet that assumes exactly-once QoS 2 or token renewal will fail on connect or on publish, not silently degrade.

The second illusion is that “STOMP and WebSocket” are two interchangeable messaging protocols. They are not peers. STOMP is a small text-framed messaging protocol with its own frames and acknowledgement modes; WebSocket is a bidirectional transport with a subprotocol mechanism. Web STOMP and Web MQTT are separate bridge plugins that carry a messaging protocol over a WebSocket, and a browser still needs a matching JavaScript client.

The third illusion is that publishing once lets any protocol consume identically. Cross-protocol delivery is real when addresses, bindings, permissions, and capabilities align, but conversion tables have empty cells: some properties are dropped or transformed, topic separators and wildcards differ, and MQTT session and retained semantics do not become queue semantics. This chapter maps each mechanism precisely and marks where meaning is preserved versus quietly lost.

Interop invariant

Interoperability is a topology-and-conversion property, not a shared feature set. Protocols meet on the same exchange, queue, or stream only when addresses, bindings, permissions, and capabilities align; and only the fields the conversion supports survive. MQTT QoS, AMQP settlement, and STOMP ack modes describe different scopes and do not merge into one end-to-end guarantee.

01 Scope

Most of MQTT 5.0 — with named omissions

The shipped MQTT plugin supports MQTT 3.1, 3.1.1, and 5.0. In 5.0 it supports most features: QoS 0 and QoS 1 publish and subscribe, TLS and OAuth 2.0, clean and non-clean sessions, message and session expiry, subscription identifiers and options, will messages including will delay, request/response (including interoperability with AMQP), topic aliases, user properties, retained messages with caveats, and MQTT over WebSocket via the Web MQTT plugin. The plugin listens on port 1883 by default, and 8883 for TLS; it must be enabled with rabbitmq-plugins enable rabbitmq_mqtt on every node.

The omissions are specific and worth memorizing. QoS 2 (exactly once) is unsupported: an MQTT 5.0 client that publishes at QoS 2 is disconnected with reason code 155 (“QoS not supported”), while older MQTT versions are downgraded to QoS 1. The MQTT 5.0 AUTH packet and re-authentication or token renewal are unsupported, so an expiring token disconnects the client. Shared subscriptions are unsupported. Overlapping subscriptions at different QoS levels can produce duplicate deliveries the application must tolerate. And retained-message stores are node-local and not replicated, wildcard subscriptions receive no retained messages, and a will that is both delayed and retained is not retained.

02 Mapping

MQTT maps onto a topic exchange and per-session queues ▸

The MQTT plugin builds on the AMQP 0-9-1 model. MQTT publishes are routed by a topic exchange — amq.topic by default, configurable via mqtt.exchange — and MQTT subscribers consume from queues bound to that exchange. The plugin creates a dedicated queue per subscriber: zero queues if the client only publishes, one queue if it subscribes at a single QoS level, and two queues if it subscribes at both QoS 0 and QoS 1. These queues follow the pattern mqtt-subscription-<client-id>qos[0|1]; MQTT clients never see them, because MQTT has no concept of queues.

Topic strings are translated: MQTT uses / as the level separator while AMQP 0-9-1 uses ., so MQTT cities/london becomes AMQP cities.london. MQTT's single-level wildcard + maps to AMQP *, and the multi-level wildcard # maps to #. The limitation is symmetrical and important: MQTT topics containing dots and AMQP routing keys containing slashes are ambiguous and should be avoided in an interoperating namespace. One more boundary: MQTT clients never consume a RabbitMQ stream directly, although an MQTT publish can route to a bound stream. 03 STOMP

STOMP is the messaging protocol; WebSocket is the transport

RabbitMQ's STOMP plugin supports STOMP 1.0 through 1.2. STOMP is deliberately a small text-framed protocol, and its specification makes destination strings and delivery semantics server-specific. RabbitMQ therefore maps STOMP destinations onto its own entities: /exchange, /queue, /amq/queue, /topic, and /temp-queue. These are RabbitMQ conventions, not portable STOMP syntax, and the plugin proxies internally over AMQP 0-9-1. The plugin also supports STOMP acknowledgement modes and RabbitMQ extensions for queue arguments, publisher persistence and receipts, stream offsets, and Bloom stream filtering — and, as in the streams lesson, stream filtering over STOMP remains probabilistic and needs a client-side exact check.

WebSocket is a different layer entirely. Web STOMP is a separate, minimal bridge that carries STOMP over an RFC 6455 WebSocket, by default at /ws on port 15674; Web MQTT similarly carries MQTT at /ws on port 15675. Both support wss when TLS is configured, and a browser still needs a matching STOMP or MQTT JavaScript client. So “STOMP and WebSocket” is not a choice between two messaging protocols: STOMP supplies the messaging frames and acknowledgements, and WebSocket supplies a browser-capable framed transport underneath.

Enable the right plugin

MQTT, STOMP, Web MQTT, and Web STOMP all ship with RabbitMQ but are plugins — they must be enabled per node. “Ships with RabbitMQ” is not “enabled by default.” AMQP 0-9-1 and native AMQP 1.0 are the core protocols that need no plugin.

04 Invariant

What cross-protocol interoperability actually is ▸

Here is the honest version of “one broker, many protocols.” A producer and consumer using different protocols can meet on the same exchange, queue, or stream when their addresses, bindings, permissions, and resource capabilities align. RabbitMQ stores AMQP 1.0, AMQP 0-9-1, and MQTT queue messages in the publishing protocol's format and converts when a different protocol consumes. Streams are the exception: they always store an AMQP 1.0-encoded message.

Making that meeting happen requires configuration. MQTT publishes use the configured topic exchange, so an AMQP or STOMP consumer receives them only from a queue bound to that exchange, and conversely an AMQP or STOMP producer reaches an MQTT subscriber only by publishing to that exchange with a compatible routing key. AMQP 1.0 producers and consumers must use RabbitMQ's address mappings and STOMP clients must use RabbitMQ's destination mappings. “Same queue” is a topology decision, never automatic protocol discovery. 05 Boundary

Where semantics are dropped, transformed, or simply different

Conversion is not lossless, and the details bite in production. Conversion tables have empty mappings: AMQP to and subject, some timestamp and group fields, and complex values may not carry across, and AMQP 0-9-1 array or table header values are not converted into AMQP application properties. MQTT's retain flag, topic alias, and subscription identifier have no general AMQP message-property equivalent; MQTT user-property keys can be deduplicated and values stringified, and AMQP compound property values cannot all become MQTT user properties. Values can change representation or time precision.

More fundamentally, MQTT QoS, AMQP settlement and outcomes, STOMP acknowledgement modes, publisher confirms, transactions, retained-message stores, queue durability, and stream retention describe different scopes. Routing one payload across protocols does not turn these into the same end-to-end guarantee. Wildcard and address syntaxes are not interchangeable, and header and property names and types are not universally preserved. The rule for any real integration: test the exact producer/consumer pair against RabbitMQ's conversion tables rather than assuming a generic “header map.”

06 Build

An MQTT 5.0 publish/subscribe round trip

This lab enables the MQTT plugin, then runs a small MQTT 5.0 client with Eclipse Paho. It subscribes at QoS 1, publishes only after the subscription is confirmed (so the round trip is deterministic), and prints what it received. The comments mark the interop facts: the publish routes through amq.topic, the / separators become . for AMQP consumers, and a QoS 2 publish would be rejected. It uses the Paho v2 callback API and the MQTT v5 protocol.

Complete runnable MQTT 5.0 round tripshell · Python 3 · Paho MQTT 2.x

Step 1 — enable the MQTT plugin

shell · run once per node; MQTT listens on 1883 (8883 for TLS)
# MQTT ships with RabbitMQ but is a plugin: it must be enabled per node.
rabbitmq-plugins enable rabbitmq_mqtt
# For MQTT over WebSocket in browsers, also: rabbitmq-plugins enable rabbitmq_web_mqtt

Step 2 — publish and subscribe over MQTT 5.0

python · pip install "paho-mqtt>=2,<3" and run against a RabbitMQ 4.3 node
import threading

import paho.mqtt.client as mqtt
from paho.mqtt.enums import CallbackAPIVersion

# MQTT publishes route through the topic exchange (amq.topic by default).
# MQTT "/" maps to AMQP ".", so an AMQP 0-9-1 consumer would bind the key
# "sensors.room-1.temperature" to receive this message.
TOPIC = "sensors/room-1/temperature"
received = []
done = threading.Event()


def on_connect(client, userdata, flags, reason_code, properties):
    # Subscribe from on_connect so the subscription is restored on reconnect.
    client.subscribe(TOPIC, qos=1)          # QoS 0 and 1 are supported; QoS 2 is not


def on_subscribe(client, userdata, mid, reason_code_list, properties):
    # Publish only after the SUBACK, so we deterministically receive our message.
    client.publish(TOPIC, payload=b"21.5", qos=1)   # QoS 1 = at least once


def on_message(client, userdata, message):
    received.append(message.payload)
    done.set()


client = mqtt.Client(
    CallbackAPIVersion.VERSION2, client_id="lab-sensor", protocol=mqtt.MQTTv5
)
client.on_connect = on_connect
client.on_subscribe = on_subscribe
client.on_message = on_message
client.username_pw_set("guest", "guest")
client.connect("localhost", 1883, keepalive=30)
client.loop_start()
try:
    assert done.wait(timeout=5)             # the publish/subscribe round trip completed
    assert received == [b"21.5"]
    # A QoS 2 publish here would disconnect this MQTT 5.0 client with reason code 155.
    print({"topic": TOPIC, "received": [payload.decode() for payload in received]})
finally:
    client.loop_stop()
    client.disconnect()

The round trip stays entirely within MQTT, which is why it is deterministic and self-contained. To make it cross-protocol you would bind a queue to amq.topic with routing key sensors.room-1.temperature and consume with an AMQP client — at which point the conversion caveats of the previous section apply, and any MQTT-only metadata such as the retain flag or topic alias may not survive.

Self-test

1. What happens when an MQTT 5.0 client publishes at QoS 2?

QoS 2 is unsupported, so RabbitMQ disconnects the MQTT 5.0 client with reason code 155 (“QoS not supported”). Older MQTT versions are downgraded to QoS 1 instead.

2. How does an MQTT topic become an AMQP routing key?

The / level separator becomes ., the + single-level wildcard becomes *, and # stays #. So MQTT cities/london is AMQP cities.london. Dots in MQTT topics and slashes in AMQP keys are ambiguous and should be avoided.

3. How many queues does the MQTT plugin create per session?

Zero if the client only publishes, one if it subscribes at a single QoS level, and two if it subscribes at both QoS 0 and QoS 1. The queues are an implementation detail MQTT clients never see.

4. Are STOMP and WebSocket alternatives to each other?

No. STOMP is a text-framed messaging protocol; WebSocket is a transport. Web STOMP and Web MQTT are separate plugins that carry the messaging protocol over a WebSocket, and a browser needs a matching JavaScript client.

5. When can a producer on one protocol be consumed on another?

When they meet on the same exchange, queue, or stream with aligned addresses, bindings, permissions, and capabilities. RabbitMQ stores in the publishing protocol's format and converts on read; streams always store AMQP 1.0.

6. Name fields that do not survive cross-protocol conversion.

MQTT retain flag, topic alias, and subscription identifier have no general AMQP equivalent; AMQP 0-9-1 array/table headers are not converted to AMQP application properties; and QoS, settlement, and ack modes are different scopes, not one guarantee.
