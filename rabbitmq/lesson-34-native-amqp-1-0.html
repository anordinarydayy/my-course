34Core mechanism · Streams & multi-protocol

Native AMQP 1.0 & the Multi-Protocol Broker

AMQP 1.0 and AMQP 0-9-1 share a name but not a wire protocol. Since RabbitMQ 4.0, AMQP 1.0 is a native, enabled-by-default core protocol — no proxy plugin — with its own connection, session, and link model, its own settlement outcomes, and a RabbitMQ-specific address format that maps the standard onto exchanges, queues, and bindings.

Stable behavior targets open-source RabbitMQ 4.3 (latest signed patch overlay 4.3.3; public release/download/docs pages still showed 4.3.2 when accessed 2026-07-21). The runnable example uses the RabbitMQ AMQP 1.0 Java client 1.2.0 (com.rabbitmq.client:amqp-client). This chapter has three original figures, two interactive.
00 Failure first

“AMQP 1.0 is just AMQP 0-9-1 version 2” — it is not

The names invite a false equivalence. AMQP 0-9-1 defines a broker model — exchanges, queues, bindings — and multiplexes channels over a connection. AMQP 1.0 is a different protocol: it standardizes peer-to-peer transport and messaging primitives without prescribing any broker topology at all. It is an ISO/IEC and OASIS standard whose connections carry sessions, whose sessions carry unidirectional links, and whose links move deliveries with credit and settlement. A team that assumes channels, exchange declarations over the wire, and 0-9-1 acknowledgements will be surprised on every one of those points.

The second false assumption is that “native” means “complete.” Native means RabbitMQ speaks AMQP 1.0 directly instead of proxying it through the old 3.13-era plugin. It does not mean RabbitMQ implements every optional AMQP 1.0 facility — link recovery, transactions, and several others are explicitly unsupported. Getting both of these right is the difference between an AMQP 1.0 integration that behaves and one that mysteriously stalls.

This chapter separates the standard from the RabbitMQ mapping: how 4.0 made AMQP 1.0 native, how the connection/session/link hierarchy and settlement outcomes work, how the v2 address format resolves onto RabbitMQ's exchanges and queues, what native explicitly does not include, and where “one broker, many protocols” is real versus wishful.

Protocol invariant

AMQP 1.0 is native and enabled by default since RabbitMQ 4.0 — no AMQP 1.0 protocol plugin. It negotiates on port 5672 by protocol header, requires SASL, and models delivery as links with credit and settlement outcomes. RabbitMQ supplies the missing broker mapping through its v2 address format; the AMQP 1.0 standard does not define exchanges or queues.

01 Status

Native and core since exactly 4.0

RabbitMQ has supported AMQP 1.0 natively as a core protocol since version 4.0. Both AMQP 1.0 and AMQP 0-9-1 are accepted out of the box on the normal AMQP listener, port 5672. After the TCP or TLS connection is established and before any frames are sent, the client sends a protocol header that selects which protocol it wants; RabbitMQ routes accordingly. For AMQP 1.0 connections RabbitMQ requires SASL, and it rejects a connection that does not use it.

“Native” is a precise architectural claim. Before 4.0, an optional plugin proxied AMQP 1.0 through AMQP 0-9-1, which reduced feature coverage and added conversion overhead. RabbitMQ 4.0 replaced that with direct core support that talks to exchanges and queues without an internal 0-9-1 hop. So on 4.3 there is no AMQP 1.0 protocol plugin to enable, and the pre-4.0 plugin model should not be used to describe current behavior. Equally, AMQP 0-9-1 was not removed or deprecated — its client ecosystem remains the larger one — so there is no migration narrative in which 4.x requires AMQP 1.0.

02 Model

Connection, session, link — with credit and settlement ▸

An AMQP 1.0 connection can carry one or more sessions; a session carries unidirectional links; each link joins a source terminus to a target terminus and transfers deliveries in one direction. Flow is credit-based: the receiver grants the sender a number of credits, and the sender may transfer that many deliveries. This is the fine-grained flow control that lets one AMQP 1.0 connection publish and consume efficiently and lets a consumer prioritize specific source queues.

Settlement replaces 0-9-1's acknowledgement frames with outcomes. When the client is the publisher and RabbitMQ the receiver, RabbitMQ settles each delivery: accepted (equivalent to basic.ack — all target queues accepted, and for quorum queues a majority has written to disk), rejected (equivalent to basic.nack, carrying the queue name and reason such as maxlen or unavailable), or released (the message could not be routed to any queue). 03 Addressing

The v2 address format maps onto exchanges and queues ▸

The AMQP 1.0 standard says an address determines where a message goes but leaves the meaning to each broker. RabbitMQ implements the 0-9-1 model, so its addresses name exchanges, queues, and routing keys. RabbitMQ 4.0 introduced the v2 address format (the old 3.x form is v1, deprecated since 4.0 and still permitted by default in 4.3 under the amqp_address_v1 feature flag, to be unsupported in a future release). The valid v2 target forms are /exchanges/:exchange/:routing-key, /exchanges/:exchange, /queues/:queue, and the AMQP null value for an anonymous terminus where each message sets its own to. The only valid v2 source form is /queues/:queue — you consume from queues, and you must declare topology first because v2 does not auto-declare.

Names and routing keys are percent-encoded per RFC 3986 where needed: to send to exchange amq.direct with routing key a/b, the target is /exchanges/amq.direct/a%2Fb. A queue target such as /queues/:queue still routes internally through the default exchange, so the user needs write permission to amq.default. 04 Invariant

What “native” explicitly does not include

Native support maps AMQP outcomes onto all three queue types, but RabbitMQ 4.3 documents important omissions, and treating any of them as supported causes real bugs. There is no link suspend, resume, or recovery; no resuming of unsettled deliveries and therefore no “exactly once” link recovery; no terminus-expiry policies; no aborted field on a transfer; no AMQP transactions; and no AMQP TLS protocol-header layer — RabbitMQ runs a pure TLS server, so TLS is established directly rather than negotiated through an AMQP security header.

Two subtler points round this out. The modified outcome (used to requeue or dead-letter while changing message annotations) is supported on quorum queues but not classic queues, and it makes no sense for a stream, whose log is immutable. And AMQP 1.0's bare message is immutable when stored and consumed as AMQP 1.0, preserving the properties and application-properties for hashes, checksums, or signatures — a genuine fidelity guarantee, but one that must not be generalized across protocol conversion, which is exactly the subject of the next section and the following lesson.

Do not promise what is unimplemented

If a design depends on AMQP transactions, link recovery, resuming unsettled deliveries, or “exactly once,” it depends on features RabbitMQ's native AMQP 1.0 does not provide. Build idempotency and at-least-once handling instead, and establish TLS directly rather than via an AMQP protocol header.

05 Trade-off

“One broker, many protocols” — true, with conditions

RabbitMQ genuinely serves AMQP 1.0, AMQP 0-9-1, and other protocols against the same exchanges and queues. But that statement is only valid when clients address the same resource and the conversion supports the fields in play. It does not imply identical features, headers, addressing, or delivery guarantees across protocols. An AMQP 1.0 producer and an AMQP 0-9-1 consumer meet on a queue only when the addresses, bindings, permissions, and capabilities line up; “same queue” is a topology choice, not automatic protocol discovery.

One product boundary belongs here explicitly. Open-source RabbitMQ exposes AMQP 1.0 on the normal listener, but AMQP 1.0 over WebSocket — the rabbitmq_web_amqp plugin — is a closed-source feature exclusive to commercial VMware Tanzu RabbitMQ. It is not part of the open-source distribution, so native/core AMQP 1.0 on port 5672 must not be extrapolated into open-source AMQP-1.0-over-WebSocket. (Web MQTT and Web STOMP, covered next lesson, are shipped open-source.) The static figure summarizes the AMQP 1.0 versus 0-9-1 contrast.

06 Build

Publish and consume with the native AMQP 1.0 client

This lab uses the RabbitMQ AMQP 1.0 Java client. It creates an environment and a connection (SASL PLAIN via the URI credentials), declares topology through the management API, publishes to an exchange target and inspects the ACCEPTED status, consumes from a queue source and settles with accept(), and deletes everything it created. The .exchange(...).key(...) and .queue(...) builder calls are translated by the library into v2 addresses.

Complete runnable AMQP 1.0 publish/consumeJava · RabbitMQ AMQP 1.0 client 1.2.0

Declare topology, publish to an exchange, consume from a queue

java · com.rabbitmq.client:amqp-client:1.2.0, against a RabbitMQ 4.3 node
import com.rabbitmq.client.amqp.Connection;
import com.rabbitmq.client.amqp.Consumer;
import com.rabbitmq.client.amqp.Environment;
import com.rabbitmq.client.amqp.Management;
import com.rabbitmq.client.amqp.Message;
import com.rabbitmq.client.amqp.Publisher;
import com.rabbitmq.client.amqp.impl.AmqpEnvironmentBuilder;
import java.nio.charset.StandardCharsets;

// AMQP 1.0 is native since RabbitMQ 4.0; it negotiates on port 5672 and
// requires SASL. The URI credentials select SASL PLAIN here.
Environment environment = new AmqpEnvironmentBuilder()
    .connectionSettings().uri("amqp://guest:guest@localhost:5672/%2f")
    .environmentBuilder().build();
Connection connection = environment.connectionBuilder().build();

String exchange = "lab.amqp.orders";
String queue = "lab.amqp.orders.emea";
Management management = connection.management();
try {
    // v2 addressing does not auto-declare: create topology explicitly.
    management.exchange().name(exchange).type(Management.ExchangeType.TOPIC).declare();
    management.queue().name(queue).quorum().queue().declare();
    management.binding().sourceExchange(exchange).destinationQueue(queue).key("emea").bind();

    // Publish to /exchanges/lab.amqp.orders/emea (the library builds the v2 address).
    Publisher publisher = connection.publisherBuilder().exchange(exchange).key("emea").build();
    Message message = publisher.message("invoice-1".getBytes(StandardCharsets.UTF_8)).messageId(1L);
    publisher.publish(message, context -> {
        // Settlement outcome from the broker: accepted == basic.ack equivalent.
        if (context.status() == Publisher.Status.ACCEPTED) {
            System.out.println("publish accepted");
        }
    });

    // Consume from /queues/lab.amqp.orders.emea and settle each delivery.
    Consumer consumer = connection.consumerBuilder().queue(queue)
        .messageHandler((context, msg) -> {
            byte[] body = msg.body();            // the AMQP 1.0 bare message
            context.accept();                    // accepted outcome: delete from the queue
        }).build();

    Thread.sleep(500);
    consumer.close();
    publisher.close();
} finally {
    management.queueDelete(queue);
    management.exchangeDelete(exchange);
    management.close();
    connection.close();
    environment.close();
}

The publish callback inspects Publisher.Status.ACCEPTED, the AMQP 1.0 accepted outcome that corresponds to an AMQP 0-9-1 basic.ack; a rejected outcome would carry the queue and reason, and a released outcome would signal an unroutable message. The consumer's accept() is settlement, not a 0-9-1 ack frame. Everything the lab created is torn down through the same management API in finally.

Self-test

1. Since which version is AMQP 1.0 native in RabbitMQ, and what does native mean?

Since 4.0. Native means RabbitMQ speaks AMQP 1.0 directly as a core protocol rather than proxying it through the pre-4.0 plugin; there is no AMQP 1.0 plugin to enable, and it is on by default on port 5672.

2. How does AMQP 1.0 multiplex and control flow compared with AMQP 0-9-1?

A connection carries sessions; sessions carry unidirectional links joining a source to a target. Flow is credit-based — the receiver grants credit — rather than 0-9-1's channels.

3. What replaces AMQP 0-9-1 acknowledgements in AMQP 1.0?

Settlement outcomes: accepted (like basic.ack), rejected (like basic.nack, with queue and reason), and released (unroutable). The modified outcome is supported on quorum queues only.

4. Why does an AMQP 1.0 client need RabbitMQ's v2 addresses?

Because the AMQP 1.0 standard does not define exchanges, queues, or bindings. RabbitMQ supplies that mapping with v2 addresses such as /exchanges/:exchange/:routing-key and /queues/:queue; topology must be declared explicitly.

5. Name three AMQP 1.0 features RabbitMQ 4.3 does not support.

Any three of: link suspend/resume/recovery, resuming unsettled deliveries / “exactly once”, terminus-expiry policies, the aborted transfer field, AMQP transactions, and the AMQP TLS protocol header.

6. Is AMQP 1.0 over WebSocket available in open-source RabbitMQ?

No. The rabbitmq_web_amqp plugin is closed-source and exclusive to commercial VMware Tanzu RabbitMQ. Open-source ships Web MQTT and Web STOMP, but not Web AMQP.
