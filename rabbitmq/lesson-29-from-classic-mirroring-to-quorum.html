From Classic Mirroring to Quorum

Classic queue mirroring was removed in RabbitMQ 4.0. If your reliability plan still says “set ha-mode and we’re replicated,” it targets a feature that no longer exists. This lesson replaces the mirroring mental model with the modern one: replicated safety comes from quorum queues or streams, queue type is chosen once at declaration, and moving from old to new is a planned migration — never an in-place flip.

Original study chapter. The scenarios, diagrams, code, and SVGs are written from scratch. Stable behavior targets open-source RabbitMQ 4.3, with the signed 4.3.3 maintenance release as the current patch overlay; runnable code uses Python 3 and Pika 1.3.2. This chapter contains three original figures, two interactive. Migration is a runbook with ordering and duplicate assumptions, not a lossless one-click conversion.
00 Failure first

“Set ha-mode and it’s replicated” targets a deleted feature

An operator inherits a 4.3 broker, wants a critical classic queue to survive a node failure, and reaches for the reflex learned years ago: apply an ha-mode: all policy. Nothing replicates. Puzzled, they try the other reflex — redeclare the queue as quorum — and the channel slams shut with 406 PRECONDITION_FAILED. Two habits, two dead ends, because both assume a world that RabbitMQ left behind at 4.0.

Here is that world, stated plainly. Classic queue mirroring — the whole ha-* policy family that kept synchronized copies of a classic queue — was deprecated in 2021 and removed in RabbitMQ 4.0. On a 4.3 broker a classic queue is explicitly non-replicated. When you need replicated data safety, you use a quorum queue or a stream. An ha-mode policy on a 4.3 classic queue does not mirror anything; there is no mirroring machinery left for it to switch on.

The second habit fails for a different, deeper reason: queue type is fixed when the queue is declared and cannot be changed later by policy or by redeclaration. So you cannot convert a classic queue into a quorum queue in place. Getting from the old world to the new one is a migration to a new entity, with a plan for moving data and cutting over — which is exactly what the rest of this lesson builds.

The core distinction

Mirroring is removed, and queue type is immutable. Replicated safety is a property you get by choosing a quorum queue or stream at declaration — not by adding a policy to a classic queue and not by redeclaring one.

01 Mechanism

Why a policy cannot make a classic queue replicated ▸

Two facts combine to close every “just change it” path. First, mirroring was removed in 4.0, so the ha-* keys no longer drive any replication behavior; they are obsolete policy data. Second, a classic queue in 4.3 is non-replicated by definition — its messages live on one node. Put together, a policy can still tune supported behaviors of a classic queue (TTL, limits, dead-lettering), but it has no lever that turns a single-node queue into a replicated one, because that lever was deleted.

The stepper below walks both reflexes to their dead ends and then to the real path. The ha-mode policy applies but replicates nothing; the redeclare-as-quorum attempt is a property mismatch that closes the channel and leaves the queue classic; and the correct move is to declare a brand-new quorum queue as the migration target. Keep an eye on the verdict box: the queue’s type never changes across the first five steps.

02 Invariant

Type is declaration-time; migrate intent, not syntax

The invariant to internalise is that queue type is part of the queue’s identity, set at declaration and immutable thereafter. Policies configure supported behavior; they never change type. That is why the redeclare fails and why there is no “convert” command — changing type would mean a different queue. Every migration is therefore a matter of standing up new, correctly-typed queues and moving to them.

Because you cannot mechanically translate an ha-mode value into a queue type, the useful exercise is to translate intent. What did the old policy want? “Mirror to every node” usually meant “survive a node failure” — which today is a three-member quorum queue. “Exactly N copies” maps to a quorum queue with an odd member count near N. A need to replay history or fan out a large log maps to a stream. And a genuinely disposable, single-node queue can stay a classic queue, which remains fully supported in its non-replicated role.

This intent-mapping step is where good migrations are won or lost. If you copy the old topology verbatim you carry forward obsolete keys and mis-sized guarantees. If you first write down what each queue actually needs to survive, the target types almost choose themselves — and you will find some queues do not need replication at all.

Interview follow-up

“How do you convert a mirrored classic queue to quorum?” Reject the framing: “You don’t convert it — type is immutable and mirroring was removed in 4.0. You map the old policy’s intent to a new quorum queue or stream, declare it explicitly, and migrate data with a blue-green plan.”

03 Boundary

The documented path is a blue-green migration ▸

For deployments coming from 3.13-era mirrored classic queues, the stable 4.3 guidance is a blue-green migration between two clusters rather than an upgrade-in-place. The documented sequence is deliberate: stand up the green cluster on 4.3; transform and import the definitions (dropping obsolete mirroring keys) and declare the correct quorum topology there; establish queue federation from blue to green so the backlog can flow; move consumers to green; drain the messages; move producers to green; and only then decommission blue.

The ordering is not arbitrary. Consumers move before producers so that the backlog on blue drains through federation while new work begins arriving on green, which keeps the cutover monotonic instead of sloshing messages back and forth. The stepper animates the whole arc so the phase boundaries — and which component moves when — are concrete.

04 Trade-off

Stripping ha-* keys removes data; it does not create quorum queues

Tooling helps with the definitions, but only with the part it actually does. The v2 rabbitmqadmin can transform an exported definitions file: it strips classic-mirroring policy keys (ha-mode and its related ha-* keys) and removes any policy left empty by that stripping. That is genuinely useful — it clears out obsolete configuration that would otherwise error or confuse on 4.3.

But be precise about what that transformation proves, because this is the step teams over-trust: removing mirroring keys removes obsolete data. It does not, by itself, make any imported queue a quorum queue. The green cluster’s queue declarations — or its default queue type — are what determine whether a queue is quorum, and you must design and verify that explicitly. A definitions file with the ha-* keys scrubbed can still describe a fleet of plain classic queues.

bash · transform definitions, then explicitly declare and verify quorum topology
# Export from blue, then transform: strip classic-mirroring policy keys
# (ha-mode and related ha-* keys) and drop policies left empty by that.
rabbitmqadmin definitions export --file blue-defs.json
# ...apply the mirroring-key-stripping transformation to blue-defs.json...

# IMPORTANT: stripping ha-* keys removes obsolete DATA — it does not make any
# queue quorum. Design green's declarations / default type, then verify:
rabbitmqadmin definitions import --file green-defs.json
rabbitmq-queues quorum_status orders.work   # prove the target really is quorum

So treat the transformation as hygiene, not as the migration. The migration is the deliberate choice of target types plus the data movement and cutover around them.

05 Trade-off

Ordering, duplicates, and one honest omission

Federation and Shovel can move a backlog from blue to green, but they come with assumptions you must state rather than paper over. Running federation and shovel concurrently, or otherwise moving the same stream of messages through two paths, can change the source ordering. So any migration claim must spell out its ordering guarantee, its duplicate handling, its producer-cutover moment, and its drain condition. “We federated the queues and it was clean” is not a runbook; a runbook says what happens to order and to duplicates and when producers switch.

Because the transfer can reorder and can redeliver, the safe posture is the same one quorum queues already demand: publisher confirms on the green side and idempotent consumers, so a duplicate during drain is harmless and an out-of-order arrival is tolerable. Promise availability and eventual completeness with dedupe — not an inherently lossless, order-preserving conversion.

Honest omission

You will often hear that mirroring was removed because of “split-brain, sync storms, and unbounded recovery.” The stable 4.3 sources establish the removal and its replacement, but they do not substantiate that specific causal trio as the official reason. This lesson therefore states the facts — deprecated in 2021, removed in 4.0, replaced by quorum queues and streams — and does not present that trio as sourced 4.3 fact.

06 Build

Prove the type is fixed, then create the real target

The script makes immutability undeniable. It declares a classic queue, then tries to redeclare the same name as quorum. The broker answers with 406 PRECONDITION_FAILED and closes the channel — the script catches it, asserts the code, reopens a channel, and declares a genuinely new quorum queue as the migration target. That is the whole lesson in code: you do not flip a type; you create a new entity.

Queue-type immutability checkpointPython 3 · Pika 1.3.2

A redeclare cannot change type; migration declares a new queue

python · install pika==1.3.2 and run against localhost
import uuid

import pika
from pika.exceptions import ChannelClosedByBroker

CLASSIC = f"lab.l29.classic.{uuid.uuid4().hex[:8]}"
QUORUM = f"lab.l29.quorum.{uuid.uuid4().hex[:8]}"

connection = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
channel = connection.channel()
try:
    # A classic queue in 4.3 is non-replicated; its TYPE is fixed at declaration.
    channel.queue_declare(
        queue=CLASSIC, durable=True, arguments={"x-queue-type": "classic"}
    )

    # "Just change the type" cannot work: redeclaring the same name as quorum is
    # a property mismatch, so the broker closes the channel with 406.
    type_is_immutable = False
    try:
        channel.queue_declare(
            queue=CLASSIC, durable=True, arguments={"x-queue-type": "quorum"}
        )
    except ChannelClosedByBroker as exc:
        type_is_immutable = exc.reply_code == 406  # PRECONDITION_FAILED
    assert type_is_immutable

    # The failed declare closed the channel; reopen to continue the migration.
    channel = connection.channel()

    # Migration = a NEW, correctly-typed entity (then move data and cut over).
    created = channel.queue_declare(
        queue=QUORUM, durable=True, arguments={"x-queue-type": "quorum"}
    )
    assert created.method.queue == QUORUM
    print({"type_is_immutable": type_is_immutable, "new_target": QUORUM})
finally:
    cleanup = connection.channel()
    cleanup.queue_delete(queue=CLASSIC)
    cleanup.queue_delete(queue=QUORUM)
    connection.close()

Run it and the assertion on 406 is the point: RabbitMQ refuses to pretend a classic queue became quorum. In production the new quorum queue is where federation drains the backlog before you move producers and retire the old one.

Self-test

1. What happened to classic queue mirroring, and what replaces it?

It was deprecated in 2021 and removed in RabbitMQ 4.0. On 4.3 a classic queue is non-replicated; replicated data safety comes from quorum queues or streams. An ha-* policy no longer enables any mirroring.

2. Can you change a classic queue into a quorum queue with a policy or a redeclare?

No. Queue type is set at declaration and is immutable. A policy configures behavior, not type, and redeclaring the same name with a different type fails with 406 PRECONDITION_FAILED.

3. What is the documented migration path from mirrored classic queues?

A blue-green migration: stand up the green 4.3 cluster, transform and import definitions with the correct quorum topology, establish queue federation, move consumers, drain messages, move producers, then decommission blue.

4. Does stripping ha-* keys from a definitions file make queues quorum?

No. It removes obsolete mirroring data and empties leftover policies. Whether a queue is quorum depends on the green cluster’s declarations or default queue type, which you must design and verify explicitly.

5. What must a migration runbook say about ordering and duplicates?

It must state the ordering guarantee, duplicate handling, the producer-cutover moment, and the drain condition. Concurrent transfer paths can reorder messages, so plan for reordering and duplicates rather than promising a lossless, order-preserving move.

6. Is “split-brain, sync storms, unbounded recovery” the official removal reason?

Not per the stable 4.3 sources. They establish the removal and its replacement but do not substantiate that specific causal trio, so it should not be presented as a sourced 4.3 fact.
