RabbitMQ vs Kafka vs Redis Streams vs SQS

The comparison interviewers love has no universal winner — no official source supports “Kafka is fastest,” “Redis is simplest,” or “SQS has zero operations.” What actually differs are workload contracts: what gets retained, who owns routing, what ordering scope is honest, and what redelivery a handler must tolerate. Compare those, not reputations.

Original study chapter. The scenarios, comparison matrix, and rubric are written from scratch. RabbitMQ behavior targets open-source 4.3 (signed 4.3.3 patch overlay); Kafka references target the official Apache Kafka 4.3 documentation; Redis references are version-qualified against current Redis 8.2–8.8 docs; AWS behavior comes from the official SQS/SNS developer guides. 00 Failure first

“Kafka is always faster, so use Kafka”

A candidate answers a system-design question with “Kafka is faster than RabbitMQ, so we should use Kafka here,” and the interviewer pushes back with one question: faster at what? No official documentation from either project supports a universal throughput or latency ranking — the honest answer depends on message size, fan-out shape, durability settings, and what “fast” is even measuring. The candidate who leads with a reputation-based ranking has already lost the thread of the actual question.

A second candidate does better and worse at once: “RabbitMQ only has destructive queues; Kafka alone has retained logs.” That was true once. It stopped being true when RabbitMQ shipped Streams — replicated, retained, append-only logs with replay by offset. The binary the candidate is reaching for is a real distinction between two different modes, but it no longer maps cleanly onto two different products.

The core distinction

Compare workload contracts — what's retained, who routes, what ordering scope is real, what redelivery model a handler must tolerate — not product reputations. Every one of these four systems can be the right answer for a workload matched to its actual contract.

01 Mechanism

Four primary abstractions ▸

RabbitMQ queues emphasize broker-side exchange routing, per-delivery consumer acknowledgements, push delivery, and destructive work-queue semantics — but RabbitMQ also has replicated retained Streams and partitioned super streams, so “RabbitMQ has only destructive queues” is obsolete. Apache Kafka 4.3 uses retained partitioned append logs with pull consumption and consumer offsets; conventional consumer groups assign each partition to one consumer at a time, but Kafka 4.3 also documents Share Groups, where consumers share partitions and acknowledge individual records under time-limited acquisition locks. Redis Streams are append-only logs stored as Redis keys, with consumer groups tracking pending work in a Pending Entries List; a stream key is not automatically partitioned across instances. Amazon SQS is a fully managed, polling queue where receiving a message starts a visibility timeout and successful processing requires an explicit delete.

03 Framework

The seven-point decision rubric

  1. Disposable job or retained history? Prefer queue semantics for independently acknowledged work; prefer a retained log when consumers must rewind or rebuild. RabbitMQ Streams mean this no longer maps 1:1 to product names.
  2. How much broker-side routing? RabbitMQ exchanges fit rich dynamic routing; Kafka and Redis put more selection into producer/app design; SNS supplies AWS-native fan-out and filtering.
  3. Ordering key and parallelism target? Scope order per RabbitMQ queue/consumer topology, Kafka partition, Redis processing topology, or SQS FIFO message group — never promise global order while adding unconstrained parallel retries.
  4. What redelivery contract can handlers tolerate? All four require idempotency for common failure paths — compare ack/requeue, offsets/Share Groups, PEL/claims, and visibility/delete.
  5. How long must data stay replayable? Compare RabbitMQ Streams retention, Kafka topic retention, Redis trimming, and SQS's bounded window.
  6. Who owns operations and portability? A managed service reduces broker-infrastructure work but never removes application-level operations.
  7. What ecosystem or integration is decisive? Evaluate actual connectors, client maturity, and team support — don't substitute a generic ranking for a required integration.
04 Nuance

Product-specific qualifications an interviewer will probe ▸

Kafka's broad default is at-least-once; its exactly-once mechanisms are scoped to transactions and Kafka Streams for coordinated Kafka-to-Kafka processing — external systems still need cooperation or idempotency. Kafka 4.3 Share Groups use individual acknowledgements and 30-second default acquisition locks, blurring the old queue-versus-log binary without turning every consumer group into a RabbitMQ queue.

Redis XREADGROUP with > reads never-before-delivered entries; XACK removes an entry from the pending list, and XAUTOCLAIM transfers idle pending entries but can redeliver, so handlers stay idempotent. Redis Streams participate in whatever persistence and replication the deployment configures — an RDB-only setup can lose data since the last snapshot, and durability is a deployment property, not a data-type property. SQS long polling can wait up to 20 seconds and reduces empty receives, but it is still polling, not broker push; FIFO deduplication suppresses repeated sends under the same deduplication identity for a five-minute window — it does not make an arbitrary external side effect exactly-once.

05 Build

Apply the rubric to a real scenario

Order events: 90-day analytics replay plus immediate fulfillmentapplied rubric

“Order events need 90-day replay for analytics, plus immediate processing for fulfillment”

1. Disposable or retained? Both — fulfillment is disposable per-order work; analytics needs 90 days of retained, replayable history. That single sentence already rules out a single-queue-only design.

2. Routing? Fulfillment benefits from RabbitMQ's routing (topic exchange by region/priority); analytics just needs the full retained stream, no selective routing required.

3. Ordering? Fulfillment needs no cross-order ordering — competing workers are fine. Analytics needs to preserve arrival order for replay, which favors a log-shaped store over a destructive queue.

4. Redelivery contract? Fulfillment workers must be idempotent regardless of mechanism. Analytics consumers reading from a retained log naturally tolerate re-reads, since retained offsets don't disappear when read.

5. Replay window? 90 days is well past what a destructive work queue is designed to hold, but squarely inside RabbitMQ Streams' retention model or a Kafka topic's configurable retention.

Answer: a topic exchange feeding a quorum queue for fulfillment (disposable, ordered-enough, idempotent workers), and a separate RabbitMQ Stream — or a Kafka topic if the org already runs Kafka for analytics — for the 90-day retained copy. One event, two independently scaled consumption models, chosen by contract rather than by product reputation.

Self-test

1. Is it accurate to say RabbitMQ can only do destructive queue delivery?

No. RabbitMQ Streams are replicated, retained, append-only logs with replay by offset — the destructive-queue-only framing predates Streams.

2. Does Kafka guarantee global ordering across all partitions of a topic?

No. Ordering is guaranteed within one topic-partition, not globally across the topic.

3. Is Kafka's exactly-once guarantee universal across any consumer?

No. It's scoped to transactions and Kafka Streams for coordinated Kafka-to-Kafka processing; external systems still need cooperation or idempotency.

4. Are Redis Streams inherently durable?

No. Durability follows the deployment's configured persistence (RDB/AOF) and replication/failover policy, not a property of the Streams data type itself.

5. Does SQS FIFO deduplication make external side effects exactly-once?

No. It suppresses duplicate sends under the same deduplication identity for a five-minute window — external processing still needs its own idempotency.

6. What is the first question in the seven-point rubric?

Whether the dominant unit is a disposable job or retained event history — it determines whether queue semantics or a retained log fits the workload.
