Build: Upgrades & Operating a Cluster

Upgrading RabbitMQ is not one operation — it's a supported version path, an irreversible feature-flag gate, a metadata migration that must happen before you reach 4.3, and a rolling node-by-node procedure that keeps the cluster available without ever promising zero downtime. Get the sequencing wrong and there is no supported way back.

Original study chapter. The scenarios, diagrams, and commands are written from scratch. Stable behavior targets open-source RabbitMQ 4.3, with the signed 4.3.3 maintenance release requiring Erlang/OTP 27.0 or newer as its runtime baseline. This chapter contains three original figures, two interactive.
00 Failure first

“We'll just upgrade straight to 4.3”

A team running RabbitMQ 4.0 schedules a maintenance window and tries to jump straight to 4.3. The upgrade fails to start cleanly, because the only supported in-place source series for 4.3 is 4.2.x — 4.0 and 4.1 deployments must pass through 4.2 first. There is no shortcut here, and no downgrade path once you've enabled flags trying to force it: RabbitMQ does not support downgrading, even between some adjacent patches.

A second team gets the version path right but the sequencing wrong: they believe Khepri migration is something you do once you're already on 4.3. It isn't. The migration to Khepri happens on 4.2, before you ever start the 4.3 upgrade — 4.3 has no Mnesia fallback at all, so by the time a node is running 4.3, the metadata store question needs to already be settled. This single sequencing correction is one of the most commonly missed details in real operations work.

The core distinction

The upgrade path, the feature-flag gate, the Khepri migration, and the rolling procedure are four separate steps that must happen in this order: reach the latest 4.2 patch, enable every stable 4.2-and-earlier flag, migrate to Khepri while still on 4.2, verify, then begin the rolling upgrade into 4.3.

01 Path

The supported path and the patch-level gates ▸

Every stable feature flag introduced in 4.2 and earlier must be enabled before a 4.3 node starts. Enabled flags cannot be disabled, and RabbitMQ does not support downgrade as a rollback strategy — enable_feature_flag all means all stable flags, not experimental ones. Patch-level runtime requirements matter too: signed 4.3.3 requires Erlang/OTP 27.0 or newer and will simply fail to start on an older Erlang release. At the time of writing, Erlang 27 was fully supported, Erlang 28 was supported only for brand-new clusters because of a known Khepri rolling-upgrade issue affecting 27→28, and Erlang 29 was unsupported — recheck the target patch's release notes immediately before approving any change.

A mixed 4.2/4.3 cluster exists only to perform the rolling upgrade itself and should last hours, not become a steady deployment mode. Use CLI tools that match the version of the node they're controlling.

02 Sequencing

Khepri migration happens on 4.2 — before you touch 4.3

Interview correction

“One-way Khepri migration in 4.3” is a phrase to avoid: 4.3 has no Mnesia at all, so there is nothing left to migrate from once you're there. The migration itself happens on 4.2, is operationally one-way once it succeeds, and must be complete and verified before you begin the 4.3 upgrade.

The 4.2 prerequisite: every node online and healthy, scheduled away from peak load, with reviewed backups of both definitions and messages already taken.

bash · run while the ENTIRE cluster is still on a supported 4.2.x patch
rabbitmqctl list_feature_flags name state stability
rabbitmqctl enable_feature_flag khepri_db
rabbitmqctl enable_feature_flag all
rabbitmqctl list_feature_flags name state stability

The explicit khepri_db command makes the migration gate visible on its own; the later all is idempotent for flags already enabled. During migration, records are copied while the cluster keeps serving traffic, then Mnesia is briefly made read-only to drain final updates — client operations can pause or time out during that window. If migration fails before completion, RabbitMQ documents an automatic return to Mnesia. Once it completes successfully, the flag cannot be disabled and the old Mnesia tables are cleaned up: the successful transition is operationally one-way, which is exactly why it must happen deliberately on 4.2, with backups in hand, rather than being discovered mid-upgrade.

03 Procedure

Rolling, one node at a time ▸

bash · one node at a time, verified before proceeding to the next
rabbitmq-diagnostics -q alarms
rabbitmqctl list_feature_flags name state stability
rabbitmq-diagnostics check_if_node_is_quorum_critical
rabbitmq-upgrade await_online_quorum_plus_one

# Optional controlled drain: closes client connections and transfers eligible leaders.
rabbitmq-upgrade drain

# Stop the node with the platform service manager; upgrade RabbitMQ and, if required,
# Erlang; start it; then verify before touching the next node.
rabbitmqctl cluster_status
rabbitmq-diagnostics -q alarms

# If a planned stop is cancelled before restart, undo maintenance mode explicitly.
rabbitmq-upgrade revive

await_online_quorum_plus_one may genuinely wait — do not bypass it just to hit a schedule. drain intentionally closes client connections, so applications must reconnect, reopen channels, and restore confirms, QoS, topology, and consumers on their own. A normal restart exits maintenance mode automatically; revive is only for an aborted stop, not a routine post-restart step. Verify node version, cluster membership, alarms, logs, and replica catch-up after every single node — never batch verification across multiple nodes to save time.

bash · after every node is on the target patch and healthy
rabbitmqctl enable_feature_flag all
rabbitmqctl list_feature_flags name state stability
rabbitmq-queues rebalance all
“No downtime” is conditional, not a guarantee

A healthy multi-node cluster can remain available during a supported rolling upgrade, but that is conditional on N−1 capacity, sufficient quorum, and client recovery — not an unconditional promise. A single-node broker simply stops. Clients attached to the node being restarted disconnect. Insufficient quorum, long synchronization, incompatible clients or plugins, or an application recovery defect can interrupt a workload even while the cluster still has running nodes.

04 Build

Definitions export/import: topology, not messages

Export, transform, and re-import cluster topologyshell + ini

Definitions cover users, vhosts, permissions, queues, exchanges, bindings, and policies

They do not include message bodies or queue/stream contents, and every definition file is sensitive — it can contain password hashes and URI-bearing Shovel or Federation parameters.

bash · core export/import; encrypt and access-control the artifact
umask 077
rabbitmqctl export_definitions /secure/path/rabbitmq-definitions.json
# Inspect and transform version-incompatible policies/parameters before import.
rabbitmqctl import_definitions /secure/path/rabbitmq-definitions.json
ini · rabbitmq.conf — boot-time seeding, once after cluster formation for large sets
definitions.import_backend = local_filesystem
definitions.local.path = /etc/rabbitmq/definitions/cluster.json
definitions.skip_if_unchanged = true

rabbitmqctl does not require the management plugin for these operations. Validate JSON and target-version compatibility, and test the import into a disposable cluster first. Import is not a desired-state prune: an object's absence from the file is not an instruction to delete a live object, and boot-time import does not overwrite existing broker contents. Plugin definitions are imported after plugins activate, so make sure required plugins are enabled first — an import that assumes a plugin's queue type before the plugin is running will simply fail.

05 Alternative

Blue-green: the alternative when in-place isn't the plan

Create the green cluster at the target version, import reviewed definitions, then connect blue and green with queue federation and/or explicit Shovels. Move consumers, drain and reconcile the backlog, pause and then switch publishers, verify confirms, duplicates, ordering, and queue emptiness — then decommission blue. Definition import alone performs only the topology step; concurrent federation and Shovel movement can reorder messages, and retries can duplicate, so “blue-green” is not by itself a seamless or zero-loss guarantee. Rollback also becomes a data-reconciliation problem the moment both clusters accept writes, which is why the publisher switch happens last and only after verification.

Self-test

1. Can you upgrade RabbitMQ 4.0 directly to 4.3 in place?

No. The only supported in-place source series for 4.3 is 4.2.x. A 4.0 deployment must reach 4.2 first through the supported sequence.

2. On which version does the Khepri metadata migration happen?

On 4.2 — before the 4.3 upgrade begins. 4.3 has no Mnesia fallback at all, so the migration must already be complete and verified by the time a node runs 4.3.

3. Can an enabled feature flag be disabled later?

No. Feature flags are irreversible once enabled, and RabbitMQ does not support downgrade as a rollback strategy.

4. What does rabbitmq-upgrade drain actually do?

It closes client connections on that node and transfers eligible leaders elsewhere, intentionally disconnecting clients so they must reconnect and restore their own state — it is optional but recommended before stopping a node.

5. Is "no downtime" an accurate description of a rolling upgrade?

Only conditionally. It depends on maintaining N-1 capacity, sufficient quorum, and correct client recovery — a single-node broker stops entirely, and even a healthy cluster can be interrupted by insufficient quorum or recovery defects.

6. Do exported definitions include message bodies?

No. Definitions cover topology — users, vhosts, permissions, queues, exchanges, bindings, and policies — never message bodies or queue/stream contents.
