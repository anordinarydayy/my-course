02Concept · RabbitMQ

Messaging Patterns: Work Queues, Pub/Sub & RPC

Newcomers picture a broker as “a queue you push into and pull out of.” That model shatters the first time you need more than one consumer, selective delivery, or a reply. The real question every messaging design answers isn’t “which queue?” but “what routing shape do I need?” This lesson shows that work queues, publish/subscribe, routing, and RPC are not four things to memorize — they are one machine with a different dial setting.

Original study notes. Written from scratch for engineers prepping backend and system-design interviews. Terms like exchange, binding, and routing key are used as plain identifiers; every sentence, diagram, and line of code here is our own, tracking RabbitMQ 4.x (mid-2026). 00 The frame

Four shapes, one machine

Essentially every messaging problem collapses onto three yes/no questions. Once you can ask them in order, the “patterns” stop being a catalogue and become a decision tree:

Cardinality

  • Handled by exactly one of N interchangeable workers?
  • → work queue (competing consumers).
  • Or by every interested party? → fan-out.

Selectivity

  • Do all consumers want everything? → fanout.
  • Or a filtered subset by key or pattern?
  • → direct / topic routing.

Directionality

  • Fire-and-forget — the sender moves on?
  • Or request/reply, where it waits for a correlated answer?
  • → RPC.

Now the one load-bearing insight that makes all of this cohere. Producers in RabbitMQ never publish to a queue. They publish to an exchange; the exchange plus its bindings decide which queues — zero, one, or many — receive a copy. All four patterns run the same machinery, publish → exchange → binding → queue → consumer, differing only in the exchange type and the binding rule. RabbitMQ ships a small toolkit of exchange types — default, direct, fanout, topic (and headers) — and each “shape” is just a choice of type plus binding.

The rule to memorize

The case that looks like “publishing straight to a queue” — the plain work queue — is really the default (nameless) exchange doing direct routing on the queue’s own name. There is no exception to the rule; the default exchange just hides it. Get this one sentence wrong and you will never be able to explain fan-out.

Common misconception

“Producers publish to queues.” They don’t — they publish to exchanges. The default exchange is a built-in direct exchange with an implicit binding of every queue to its own name, which makes point-to-point look direct. You can’t bind to it manually, and its behavior (route routing_key → same-named queue) is fixed.

01 Point-to-point

The work queue: competing consumers ▸

Start with the most useful shape. You have one queue, many identical workers, and each message must go to exactly one worker — this is horizontal scaling of a task. The producer publishes to the default exchange with routing_key = queue_name, and the broker load-balances deliveries across whichever consumers are currently attached. Add workers, go faster; the producer never changes.

Two settings decide whether this works or falls apart. First, prefetch (basic_qos) controls fair dispatch: without it, a busy worker still gets round-robined more messages while an idle one waits. Set prefetch_count=1 and the broker won’t hand a worker a new message until it acks the current one — so fast workers naturally pull more and slow ones pull less. Second, manual acks are what make redelivery safe: an un-acknowledged message from a crashed worker is requeued and given to someone else. Watch both in motion:

The colour tells the story: grey is queued, amber is in-flight/unacknowledged (delivered but the broker still holds its copy), and green is acked/done. Notice the crash in step 6 — Worker B dies mid-task, and because it never acked, the broker returns the message to the queue head with a redelivery mark rather than losing it. This is at-least-once delivery. The queue type here is a quorum queue (x-queue-type: quorum), the durable, Raft-replicated default in 4.x that survives a broker restart or node loss.

prefetch = fairness · ack = safety

Keep these two knobs separate in your head. basic_qos(prefetch_count=n) is a throughput/fairness knob — it caps how many un-acked messages a consumer may hold, so load follows capacity. The ack is a safety knob — ack only after the work succeeds, and a crash becomes a redelivery instead of a lost message. Myth to debunk: RabbitMQ does not automatically send work to the least-busy consumer; that only happens once you set prefetch.

02 Broadcast

Publish/subscribe: fan-out to everyone

Now flip the cardinality. Sometimes every consumer needs its own copy of the same message — cache invalidation, live dashboards, an audit trail, notification fan-out. Contrast this sharply with the work queue: the work queue gives one message one delivery; pub/sub gives one message N deliveries, one per subscriber.

The mechanism is a fanout exchange plus one queue per consumer, each queue bound to the exchange. A fanout exchange ignores the routing key entirely — it copies every message into every bound queue. The important structural detail: each subscriber typically declares its own server-named, exclusive, auto-delete queue (queue_declare(queue="", exclusive=True, auto_delete=True)), so subscribers can come and go without leaving debris behind. Those throwaway queues are classic transient queues, and that is correct — quorum queues cannot be exclusive, and you don’t want a replicated queue for a dashboard that vanishes on disconnect.

Fan-out duplicates

  • 3 consumers, 1 message → 3 deliveries (a copy each).
  • Adding a consumer adds another recipient.
  • Mental tag: “tell everyone.”

Work queue distributes

  • 3 consumers, 1 message → 1 delivery (one worker).
  • Adding a consumer adds another unit of capacity.
  • Mental tag: “get it done once.”
The interviewer’s next question

“You have a work queue and add a second consumer — does that double throughput or duplicate the work?” It distributes: each message still goes to exactly one worker, so you get more capacity, not redundancy. Follow-up: “Now every service needs its own copy — what changes?” You move from a shared queue to a fanout (or topic) exchange with one queue per subscriber. Fan-out never balances load — flag that aloud, because expecting it to is the single most common conceptual error in interviews.

03 Selective routing

Direct & topic exchanges ▸

Fan-out is often too much — a consumer wants some messages, not all of them. Two exchange types add a filter. A direct exchange matches the routing key exactly (bind error, bind warning, and only those keys arrive). A topic exchange matches dotted keys against wildcard patterns: * matches exactly one word, and # matches zero or more words. A common myth is that * means “anything” — it matches one word only.

Here is the unifying move: fanout is just the degenerate case of topic. A queue bound with # matches every key, so it receives everything — that is subscribe-to-all pub/sub. So routing is the general pattern, and pub/sub is a special case of it. One publish can land in 0, 1, or many queues depending on how the bindings overlap. Step the topic exchange through three different publishes:

Wildcards, precisely

* = exactly one dot-delimited word; # = zero or more words. So payments.# matches payments.error, payments.captured, and payments itself, but *.error matches payments.error yet not auth.failed.error (that’s two words before error). And # alone matches every key — which is exactly why fanout is the # special case of topic.

04 Request / reply

RPC over messaging

Sometimes the producer needs an answer back. The pattern layers a reply channel on top of the same publish machinery. The client sends a request carrying two message properties — reply_to (where to send the answer) and correlation_id (a unique token) — then blocks until a reply carrying the matching correlation_id arrives. RPC is really just two async sends stitched together by an id.

Why is correlation_id mandatory? Because one client channel may have many requests in flight at once, and replies can arrive out of order. Without the token, the client cannot tell which reply answers which request — it would hand request A’s caller request B’s result. The modern, cheap way to receive replies is direct reply-to: consume from the pseudo-queue amq.rabbitmq.reply-to with no manual ack, and the broker routes replies straight back to your channel without you ever declaring a real reply queue.

Trace the loop: the client publishes to the default exchange with routing_key = "rpc_queue", tagging the envelope with correlation_id and reply_to (step 1). The server consumes with prefetch=1, computes the result (step 2), and publishes the reply to the default exchange with routing_key = props.reply_to, copying the same correlation_id straight back (step 3). The broker routes that reply directly to the originating client’s channel through the amq.rabbitmq.reply-to pseudo-queue — no real queue is ever created (step 4). The client’s handler checks props.correlation_id == abc123, matches, and unblocks the waiting call() (step 5).

The edge you must design for

If the server dies before step 3, no reply ever comes — and a blocking call() would hang forever. RPC over a broker always needs a client-side timeout (and a plan for what a timeout means: retry, fail, or degrade). A broker gives you decoupling, not a free liveness guarantee on the far end.

05 Worked example

A durable work queue for thumbnails

Let’s take the canonical shape end-to-end. An upload service receives images and must generate thumbnails. Thumbnailing is CPU-bound and bursty, so we decouple it: the web tier publishes a task per image, and a pool of interchangeable workers competes for the tasks. We want (a) no task lost if a worker crashes mid-resize, (b) load to follow worker capacity, and (c) durability across a broker restart. This is the point-to-point work queue from section 01, made concrete.

Worked examplePython / pika · quorum queue
Thumbnailer: decouple the resize from the upload

Uploads must return fast, but generating thumbnails is slow and bursty. Distribute the work across a pool of identical workers so that no task is lost if a worker crashes mid-resize, load follows capacity, and nothing is dropped on a broker restart.

Think it through

Cardinality

Each image needs thumbnailing once, by any free worker → competing consumers, not fan-out → one queue, many workers.

Reaching the queue

Producers publish via the default exchange, whose built-in rule routes routing_key to the same-named queue. No exchange or binding to declare — that’s why it looks like “publishing to a queue.”

Fair dispatch

Set basic_qos(prefetch_count=1) so the broker won’t hand a worker a new task until it acks the current one — a fast worker naturally pulls more, a slow one less.

Crash safety

Keep manual acks and ack only after the thumbnail succeeds. A worker that dies mid-task leaves the message un-acked, so the broker requeues and redelivers it — at-least-once.

Restart safety

Declare a quorum queue (x-queue-type: quorum): durable and Raft-replicated across nodes, so messages survive a broker restart and node loss.

Producer · the web tier

python

import pika

conn = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
ch = conn.channel()

# Quorum queue: replicated + durable by default in RabbitMQ 4.x.
ch.queue_declare(queue="thumbnails", durable=True,
                 arguments={"x-queue-type": "quorum"})

def enqueue(image_id: str) -> None:
    ch.basic_publish(
        exchange="",                 # default (nameless) exchange
        routing_key="thumbnails",    # == queue name -> direct routing by name
        body=image_id.encode(),
        properties=pika.BasicProperties(
            delivery_mode=pika.DeliveryMode.Persistent))  # quorum treats all as persistent

for img in ("img-1001", "img-1002", "img-1003", "img-1004"):
    enqueue(img)
conn.close()

Consumer · run N copies

python

import pika, time

conn = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
ch = conn.channel()
ch.queue_declare(queue="thumbnails", durable=True,
                 arguments={"x-queue-type": "quorum"})

def on_task(ch, method, properties, body):
    image_id = body.decode()
    make_thumbnail(image_id)                       # the real (slow) work
    ch.basic_ack(delivery_tag=method.delivery_tag) # ack ONLY after success

ch.basic_qos(prefetch_count=1)     # fair dispatch: one un-acked task at a time
ch.basic_consume(queue="thumbnails", on_message_callback=on_task)  # manual ack (default)
ch.start_consuming()
Narrate it to the interviewer

“It’s a work queue on the default exchange — the producer publishes with routing_key="thumbnails", which the default exchange routes to the same-named queue, so there’s no binding to set up. I set prefetch=1 for fair dispatch, so load follows capacity instead of turn order, and I keep manual acks and ack only after the resize succeeds, so a worker that dies mid-task gets its message redelivered — at-least-once, nothing lost. I declare it as a quorum queue so the backlog survives a broker restart or a node failure. To scale, I just run more worker processes against the same queue.”

Edge cases to raise aloud: at-least-once, not exactly-once — a worker can crash after the resize but before the ack, so make handlers idempotent (key the output by image_id); poison messages — a task that always crashes the worker requeues forever, so cap it with a dead-letter exchange / delivery-count limit (quorum queues expose x-delivery-count); prefetch=1 caps throughput for short tasks — tune it up when work is quick; and publisher confirms if the producer must know the broker actually accepted the task.

Variation B · when the caller needs the answer (RPC)

Keep the same default-exchange plumbing, but add reply_to and correlation_id so the request becomes a synchronous call, using direct reply-to to avoid a per-call reply queue:

python

# client, per call:
corr = str(uuid.uuid4())
ch.basic_consume("amq.rabbitmq.reply-to", on_response, auto_ack=True)  # pseudo-queue, no ack
ch.basic_publish(exchange="", routing_key="rpc_queue",
                 properties=pika.BasicProperties(
                     reply_to="amq.rabbitmq.reply-to", correlation_id=corr),
                 body=str(n).encode())

# server, on request:
ch.basic_publish(exchange="", routing_key=props.reply_to,
                 properties=pika.BasicProperties(correlation_id=props.correlation_id),
                 body=str(result).encode())
Narrate the variation

“RPC is just two async sends stitched together by a correlation_id. The client publishes the request with reply_to = amq.rabbitmq.reply-to, the server copies the correlation_id back onto its reply, and direct reply-to gives me a return path without declaring or cleaning up a queue per call. I still need a client-side timeout in case the server never answers.”

06 Judgment

Choosing the primitive — and the queue type

Turn the three axes into a walkthrough. One-of-N or all-of-N? → work queue vs pub/sub. Everyone or a filtered subset? → fanout vs direct/topic. Do I need a reply? → RPC. That picks the routing shape, which is entirely a matter of exchange type + binding. Here are the four shapes side by side:

Work queue

  • Exchange: default / direct.
  • Who: one of N workers.
  • Binding: queue name.
  • Use: task distribution, scaling.

Pub / sub

  • Exchange: fanout.
  • Who: every bound queue.
  • Binding: bind queue, key ignored.
  • Use: cache bust, notify, audit.

Routing

  • Exchange: direct / topic.
  • Who: queues that match.
  • Binding: exact key / pattern.
  • Use: logs by severity, by domain.

RPC

  • Exchange: default (both ways).
  • Who: one server → one client.
  • Binding: queue name + reply_to.
  • Use: sync lookups, command+result.

Then a second, orthogonal choice: the queue type, which controls durability and HA — not routing. These are independent knobs. You pick the exchange for where messages go and the queue type for how safe they are:

Quorum

  • The default for durable work in 4.x.
  • Raft-replicated across nodes; always durable; all messages persistent.
  • Can’t be exclusive.

Classic transient

  • The throwaway per-subscriber pub/sub queue.
  • exclusive=True, auto_delete=True — vanishes on disconnect.
  • Correct for dashboards, not for durable work.

Streams

  • Append-only log with offset-based replay.
  • For large fan-out / high throughput.
  • Forward-reference — a later phase.
Outdated answer to avoid

If the interviewer says “make the work queue highly available,” do not say “mirror the queue” or “set an ha-mode policy.” Classic mirrored (HA) queues were removed in RabbitMQ 4.0. The current answer is quorum queues (Raft-replicated) for durable work, and streams for replayable, high-throughput fan-out. Name the removed feature only to say it’s gone.

07 Failure modes

What breaks in production

Every one of these traces back to the same spine: the exchange decides routing; the ack decides safety. Get one of those two wrong and here is what you see on-call:

  • Publishing “to a queue” and being surprised by fan-out. The mental model that skips the exchange works right up until a second service needs its own copy — then you can’t express it, because you never had an exchange to bind more queues to. Fix: always reason in exchange → binding → queue.
  • Forgetting basic_qos. Without prefetch, RabbitMQ round-robins messages regardless of load, so one worker sits on a pile while others idle. Fix: set prefetch_count and get capacity-following dispatch.
  • Using auto_ack. Auto-ack deletes the broker’s copy on delivery, so a crash mid-work loses the message. Fix: manual ack, only after the work succeeds.
  • A fresh reply queue per RPC call. Declaring and tearing down a real queue for every request leaks resources and adds latency. Fix: amq.rabbitmq.reply-to direct reply-to — a pseudo-queue you never declare.
  • Expecting fan-out to balance load. A fanout exchange duplicates a message to every bound queue; it never distributes. If you want distribution, that’s a shared queue with competing consumers. Confusing the two is the classic interview miss.
The spine to carry forward

Two questions settle almost every messaging design. Where should this message go? — answered by the exchange type and its bindings. What happens if a consumer dies holding it? — answered by the ack mode (and, for restarts, the queue type). Routing shape and durability are independent dials; keep them independent in your head and the four patterns fall out for free.

★ Review

Summary & self-test

The whole lesson compresses to one idea: a producer publishes to an exchange, and the exchange plus its bindings decide which queues get a copy — so work queue, pub/sub, routing, and RPC are one machine with four dial settings. Cardinality, selectivity, and directionality pick the shape; the queue type is a separate choice about safety.
