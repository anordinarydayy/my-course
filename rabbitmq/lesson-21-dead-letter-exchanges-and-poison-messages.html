Dead-Letter Exchanges & Poison Messages

A dead-letter exchange is where rejected, expired, over-length, and limit-exceeded messages get a second life — but it is an exchange, not a lossless queue, and “I configured a DLX” is not “my messages are safe.” This lesson pins down the four reasons, the x-death record, the honest transfer guarantees, and how RabbitMQ 4.3 changed retry.

Original study chapter. The scenarios, diagrams, code, and SVGs are written from scratch. Stable behavior targets open-source RabbitMQ 4.3, with the signed 4.3.3 maintenance release as the current patch overlay; runnable code uses Python 3 and Pika 1.3.2. This chapter contains three original figures, two interactive. Default dead-lettering is at-most-once; safer transfer is opt-in and conditional.
00 Failure first

A poison message has only bad endings until you give it a home

Some messages can never succeed: a malformed payload, a reference to a deleted account, a bug that throws on one specific record. Left alone, a poison message has two bad endings. If the consumer keeps rejecting it with requeue, it hot-loops forever and starves real work. If the consumer discards it, the evidence is gone and no one can investigate. Neither is acceptable for anything that matters.

The dead-letter exchange (DLX) is RabbitMQ’s answer: a normal exchange that a queue routes messages to when they meet a dead-letter condition, so failed messages leave the hot path and land somewhere you can inspect, alert on, and replay. It turns “a message that cannot be processed” from an operational emergency into a routing outcome.

But the mechanism is narrower and more literal than its reputation. A DLX is an exchange, so it retains nothing on its own—you must bind a queue behind it. The default transfer has no internal safety net, so a misconfiguration silently drops the very messages you were trying to save. And 4.3 added new machinery—native delayed retry and a quorum poison counter—that changes the old advice. This lesson separates what a DLX guarantees from what you must build around it.

The core distinction

A DLX is an exchange used for republishing dead letters. It is not a queue, not a retry engine, and not a guarantee of delivery. Everything useful—retention, alerting, replay—is topology and process you add around it.

01 Mechanism

Exactly four queue-side reasons dead-letter a message ▸

RabbitMQ 4.3 documents exactly four conditions under which a queue dead-letters a message. One: a consumer rejects it with basic.reject or basic.nack and requeue=false (or an AMQP 1.0 rejected outcome). Two: the message’s per-message TTL expires. Three: a queue-length or byte overflow drops the message under a drop-head-style policy. Four: a quorum queue exceeds its configured delivery limit. Those are the only queue-side triggers—memorise them, because interviewers ask for all four.

There is one exclusion that trips people up: expiration of the entire queue does not dead-letter its contents. A per-message TTL dead-letters the message; a queue-expiry (x-expires) simply deletes the whole queue, messages included, with no dead-lettering. The two look similar and behave oppositely, so keep them straight.

The stepper walks each reason routing a message to the DLX, then shows the queue-expiry exclusion, then the DLX republishing to its bound queue—because dead-lettering is a republish through an ordinary exchange, nothing more exotic.

02 Configuration

Configure the DLX by policy, and know what the republish rewrites

A DLX is wired to a source queue with two settings: dead-letter-exchange and an optional dead-letter-routing-key. Prefer policies over client x-arguments. A client argument overrides a regular policy value, but arguments are baked into the declaration and hard to change—altering them may require redeclaring the queue, which you often cannot do live. A policy can be updated without shipping code. The DLX must live in the same virtual host as the source queue, and declaring the arrangement checks read permission on the source queue and write permission on the DLX.

Dead-lettering is a republish, and a republish rewrites metadata. If no dead-letter-routing-key is set, the message keeps its original routing key; if one is set, it replaces the key. The republish drops any BCC header and removes the original expiration so the message does not immediately expire again at the destination—AMQP 0-9-1 records the former value as original-expiration. Understanding these rewrites is what lets you bind the dead-letter queue correctly instead of wondering why nothing arrives.

Configuration order

Declare and bind the dead-letter queue behind the DLX before messages start dying. If the DLX exists but no queue is bound, or the routing key does not match any binding, the default transfer discards the dead letter and you have built a silent hole.

03 Invariant

x-death is compressed history, not a retry counter

Every dead-lettering stamps an x-death header, and it is routinely misread. In AMQP 0-9-1 it is an array ordered most-recent-first and compressed by {queue, reason}: repeated deaths for the same queue and reason collapse into one entry whose count increments, rather than appending a new element each time. Each entry carries queue, reason, count, time, exchange, routing-keys, and optionally original-expiration. The four possible reasons are rejected, expired, maxlen, and delivery_limit. Alongside the array, x-first-death-* fields stay fixed at the first death while x-last-death-* fields update.

The practical rule follows directly: to count how many times a message died for a specific reason, read the count of the matching {queue, reason} entry—never the array length, and never assume every retry passed through a DLX. A message can be retried many times without dead-lettering at all, so x-death.count is a count of dead-letter events for one queue-and-reason, not a universal “attempts” number.

RabbitMQ’s cycle protection is likewise conditional. It detects a dead-letter cycle and drops the message—but only when there was no rejection anywhere in the cycle. So do not claim RabbitMQ makes every cyclic retry topology safe or bounded; a cycle that includes a rejection is not caught by this protection, and you must bound it yourself.

Interview follow-up

“How do you count retries with x-death?” The precise answer: “I read the count on the matching {queue, reason} entry, because the array is compressed by that pair and ordered most-recent-first. Length is not the retry count, and retries that never dead-letter are not there at all.”

04 Boundary

Default transfer is at-most-once; the safe transfer is opt-in ▸

Here is the fact that undermines most “we have a DLX so we’re safe” claims: the default dead-letter transfer is at-most-once. RabbitMQ republishes the dead letter without internal publisher confirms and removes it from the source immediately. If the DLX is missing, the message is silently dropped; if the target is unavailable or rejecting, the message can be lost. “Configured a DLX” is therefore not equivalent to “guaranteed parking.”

Quorum queues offer a safer transfer, but it is opt-in and conditional. Configure dead-letter-strategy=at-least-once, overflow=reject-publish, a DLX, and the documented feature prerequisite. The source quorum queue then retains the dead letter while an internal consumer republishes it with confirms, closing the transfer’s loss window. The trade-offs are real: it consumes more CPU, memory, and source capacity; an absent, unroutable, or unavailable target causes retries and can create duplicates at the target; and changing back to at-most-once—including indirectly by changing overflow—can delete pending dead letters. Target durability still matters: use a durable target queue and publish the original as persistent for the copy to survive a restart.

The current patch overlay matters here. The signed 4.3.3 maintenance release fixes a quorum at-least-once dead-lettering process that could become permanently stuck after repeated queue membership changes. That is a liveness and forward-progress fix; the release note does not state that messages were lost, so treat it as “apply 4.3.3 before relying on at-least-once dead lettering,” not as evidence of a loss bug.

05 Trade-off

Retry patterns, the 4.3 poison counter, and the parking lot

Poison handling on quorum queues is not generic queue behavior. Since RabbitMQ 4.0 a quorum queue has a default delivery limit of 20, and in 4.3 that limit is evaluated against delivery-count; a message over the limit is dropped, or dead-lettered when a DLX is configured. Classic queues gain no such built-in delivery-limit behavior. And as Lesson 18 established, in 4.3 an explicit basic.nack return does not advance delivery-count—so do not promise automatic parking after 20 nacks. The separate x-acquired-count counts assignments and does not prove the consumer actually saw the message.

RabbitMQ 4.3 also adds native quorum delayed retry: a bounded linear backoff of min(min_delay × delivery_count, max_delay), configured by delayed-retry-type (all, failed, or returned) plus min and max. It removes the client republish-then-ack gap that the old TTL+DLX workaround needed—but narrow the marketing language carefully: it does not eliminate loss or duplication in general, only that one retry pattern’s republish/ack window; returns that do not increment delivery-count stay at the minimum delay. The older TTL+DLX cycle still works for classic queues and explicit delay tiers, but it is no longer the only 4.3 quorum option and it is not “backoff for free.”

Finally, a parking lot is an application topology and an operating process, not a broker feature. You declare and bind the destination, monitor its depth and age, retain diagnostics and idempotency keys, and define replay or terminal-disposition procedures. A DLX does not classify poison messages, alert an operator, or make replay safe—those are things you build.

06 Build

Dead-letter a poison message into a parking queue

The script builds the smallest honest parking lot: a source quorum queue whose DLX fans out to a parking queue. It publishes a poison message, rejects it with requeue=false, and then reads it from the parking queue to inspect the x-death record. The asserts prove the reason is rejected, the count belongs to the matching {queue, reason} entry, and the message left the source—the default transfer removed it immediately.

Dead-letter routing checkpointPython 3 · Pika 1.3.2

Reject without requeue, then read x-death in the parking queue

python · install pika==1.3.2 and run against localhost
import time
import uuid

import pika

DLX = f"lab.dlx.{uuid.uuid4().hex[:8]}"
MAIN = f"lab.main.{uuid.uuid4().hex[:8]}"
PARK = f"lab.parking.{uuid.uuid4().hex[:8]}"


def as_text(value):
    return value.decode() if isinstance(value, bytes) else value


connection = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
channel = connection.channel()
try:
    channel.exchange_declare(exchange=DLX, exchange_type="fanout", durable=True)
    channel.queue_declare(queue=PARK, durable=True)      # bind a queue behind the DLX
    channel.queue_bind(queue=PARK, exchange=DLX)
    # In production the DLX is set by policy; a client argument keeps this lab self-contained.
    channel.queue_declare(
        queue=MAIN,
        durable=True,
        arguments={"x-queue-type": "quorum", "x-dead-letter-exchange": DLX},
    )
    channel.basic_publish(
        exchange="", routing_key=MAIN, body=b"poison",
        properties=pika.BasicProperties(delivery_mode=2, message_id="poison-1"),
    )

    # A non-retryable failure: reject without requeue dead-letters the message.
    method, _props, _body = channel.basic_get(queue=MAIN, auto_ack=False)
    assert method is not None
    channel.basic_reject(delivery_tag=method.delivery_tag, requeue=False)

    # The dead letter is republished through the DLX into the parking queue.
    dead = (None, None, None)
    for _ in range(50):
        dead = channel.basic_get(queue=PARK, auto_ack=True)
        if dead[0] is not None:
            break
        time.sleep(0.05)

    method2, props2, body2 = dead
    assert method2 is not None
    assert body2 == b"poison"
    deaths = props2.headers["x-death"]
    first = deaths[0]                                  # most-recent-first, per {queue, reason}
    assert as_text(first["reason"]) == "rejected"      # one of the four reasons
    assert as_text(first["queue"]) == MAIN
    assert first["count"] >= 1                         # count is per {queue, reason}, not array length
    main_depth = channel.queue_declare(queue=MAIN, passive=True).method.message_count
    assert main_depth == 0                             # removed from source under default transfer
    print({"reason": as_text(first["reason"]), "count": first["count"], "main_depth": main_depth})
finally:
    channel.queue_delete(queue=MAIN)
    channel.queue_delete(queue=PARK)
    channel.exchange_delete(exchange=DLX)
    connection.close()

This is the default at-most-once transfer—fine for a lab. For a source you cannot afford to leak, switch the quorum queue to dead-letter-strategy=at-least-once with overflow=reject-publish on 4.3.3, accept the extra cost, and keep the parking-queue replay idempotent.

Self-test

1. What are the four dead-letter reasons?

Reject or nack with requeue=false, per-message TTL expiry, queue-length or byte overflow dropping a message, and a quorum queue exceeding its delivery limit. Whole-queue expiry is not a dead-letter reason.

2. Why is “I configured a DLX” not the same as “my messages are safe”?

The default transfer is at-most-once: RabbitMQ republishes without internal confirms and removes the message from the source immediately. A missing or unavailable target drops it silently. A DLX is an exchange, and it retains nothing without a bound queue.

3. How should you read the count in x-death?

The array is compressed by {queue, reason} and ordered most-recent-first. Read the count on the matching entry; it counts dead-letter events for that queue and reason, not total attempts, and retries that never dead-letter are absent.

4. What does quorum at-least-once dead lettering require and cost?

It requires dead-letter-strategy=at-least-once, overflow=reject-publish, a DLX, and the feature prerequisite. The source retains the message and republishes with confirms, at extra CPU/memory cost, with possible duplicates at the target; switching back can delete pending dead letters. Apply the 4.3.3 fix.

5. In 4.3, does a delivery limit bound every retry loop?

No. The quorum delivery limit (default 20 since 4.0) is evaluated against delivery-count, and an explicit basic.nack return does not advance it. Use delayed retry and an explicit terminal policy instead of assuming automatic parking.

6. Is TTL+DLX still the recommended quorum retry pattern?

It remains valid for classic queues and explicit delay tiers, but on 4.3 quorum queues native delayed retry is the broker-native option. TTL+DLX adds extra republishes and head-of-queue expiry behavior, and it is not “backoff for free.”
