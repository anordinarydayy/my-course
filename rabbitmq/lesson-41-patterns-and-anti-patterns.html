Patterns & Anti-Patterns

Most RabbitMQ interview slogans are half-truths that harden into rules: “a queue per user is always wrong,” “RPC over a broker is always wrong,” “durable plus persistent means no loss.” Every one of them fails a workload test. This lesson replaces the slogans with the actual reusable shapes — and the specific way each one breaks when pushed past its honest limits.

Original study chapter. The scenarios, diagrams, and tables are written from scratch, synthesizing patterns from earlier phases of this course. Stable behavior targets open-source RabbitMQ 4.3, with the signed 4.3.3 maintenance release as the current patch overlay. This chapter contains three original figures, two interactive.
00 Failure first

A design review that rejects a valid design

A design review kills a queue-per-user proposal on sight: “that's a well-known anti-pattern.” Nobody asks how many users, how long each queue lives, or how often they churn. At a few thousand long-lived, low-churn tenants, a queue per user can be entirely reasonable; at ten million ephemeral users it clearly isn't — but the slogan short-circuited the actual analysis in both directions.

The opposite failure ships instead of blocking: a team builds RPC over reply_to with no timeout, no idempotency, and no cancellation, because “RabbitMQ supports RPC.” It does — but a server that publishes a response and then crashes before acknowledging the original request creates a duplicate execution the caller has no way to detect. The pattern wasn't wrong to reach for; it was incomplete.

The core distinction

Every pattern in this lesson is a shape with a workload test attached, not a rule to apply blindly. The anti-pattern register at the end exists to replace five common slogans with the specific question each one actually needs answered.

01 Recap

Competing workers: the shape, the acknowledgement boundary ▸

A work queue puts multiple consumers on the same queue. Each delivery goes to exactly one consumer — they compete rather than each receiving a copy — and manual acknowledgements let unacknowledged work be redelivered after a channel or connection failure. The detail that actually matters in production: a worker should acknowledge only after the externally meaningful work is durably committed, because a crash between the side effect and the acknowledgement produces a duplicate attempt that needs an idempotency key to land safely.

Prefetch limits unacknowledged in-flight deliveries, and prefetch_count=1 from RabbitMQ's own tutorial illustrates fairer dispatch for uneven jobs — it is not a universal optimum. Tune it from processing time, memory, downstream concurrency, and recovery cost; 0 means unlimited and can overload a consumer or the broker. Push consumers are the normal long-lived model; a single queue has a single-core hot path, so shard by a meaningful key or add queues only when measurement and real ordering/isolation needs justify it — not reflexively.

02 Recap

Pub/sub fan-out: pick the exchange from the access pattern

Exchanges route publications; queues buffer independently. A fanout exchange ignores routing keys entirely and sends a copy to every bound queue — but multiple consumers on one of those queues still compete, so independent subscribers each need their own independent queue. Use fanout only when every bound subscriber genuinely needs every publication; use direct for exact routing-key matches and topic for wildcard-based selective subscriptions. “Pub/sub” does not require fanout if subscribers actually need different subsets of the traffic.

Ephemeral, instance-scoped subscriptions can use exclusive server-named queues; durable, independently operated services generally need stable durable queues instead. RabbitMQ 4.3 disables transient non-exclusive queues by default because that particular combination is deprecated — don't present it as a normal middle-ground option. And an unroutable AMQP 0-9-1 publication is discarded by default unless the publisher sets mandatory=true or the exchange has an alternate exchange: publisher confirms and routing detection answer different questions, and an unroutable message can still be positively confirmed.

03 Trade-off

RPC over reply_to versus Direct Reply-To ▸

RPC is a constrained pattern, not a default architecture. It is appropriate only when the business interaction genuinely requires a response before the caller can proceed, and the team accepts network-style failure semantics. It becomes an anti-pattern the moment it disguises an asynchronous workflow, builds a long synchronous dependency chain, or omits deadlines, cancellation, idempotency, and observability — RabbitMQ's own tutorial explicitly warns that RPC can hide latency and failure and produce a brittle system.

Reply mechanismWhat it providesWhat it does not providePrefer it when
Durable or reusable callback queueA real queue that buffers replies per its durability/lifetime config; app controls acknowledgement and lifecycleExactly-once execution, automatic request cancellation, or atomicity with client stateReplies must survive a requester reconnect, need buffering, or require explicit queue semantics
Direct Reply-ToA broker pseudo-queue with no reply-queue metadata or actual queue process; reduces reply-queue declaration/churnDurable buffering or redelivery — replies are at most once and can be dropped if the requester is unavailableRequester is online, losing a response is acceptable because timeout/retry exists, and avoiding reply-queue overhead matters

Direct Reply-To is not “faster RPC” as a universal claim — it changes resource and delivery semantics. The requester consumes from the pseudo-queue on the same connection/channel context the protocol requires, and a lost reply must be handled as a plain timeout. Retrying a timed-out request needs an idempotent operation or server-side deduplication, because the original request may already have executed once.

04 Checklist

Bounded retry is an end-to-end policy, not a queue setting

Every retry design needs all eight of these, regardless of mechanism: an attempt budget counted by application metadata and/or broker death fields; error classification that treats permanent failures differently from transient ones; a delay policy that reserves immediate requeue for narrowly understood conditions; a deadline or maximum age so a stale message doesn't consume retries forever; a terminal path to an explicitly declared, monitored parking queue; idempotency because publisher retries, consumer crashes, dead-letter forwarding, and operator replay can all duplicate attempts; resource guardrails via explicit queue limits and overflow policy; and observability and replay control that records failure class, attempt history, age, and stable IDs.

The nack-versus-reject trap

An unbounded reject/nack with requeue=true can create an immediate redelivery loop consuming network and CPU. In RabbitMQ 4.3, a quorum queue's default delivery limit does not make every such loop safe: basic.reject/failed outcomes advance the failure-oriented delivery-count, but AMQP 0-9-1 basic.nack returns do not advance it. A loop built on plain nack-and-requeue can bypass the delivery limit entirely — bound it explicitly at the application level.

05 Register

The anti-pattern register: slogans replaced with tests

Simplistic ruleStable, defensible replacement
“A queue per user is always wrong.”Evaluate user cardinality, churn, idle lifetime, retention, queue-type/replica cost, and isolation. Valid at bounded scale; a database or retained stream is often better for very high cardinality or long replay.
“RPC over a broker is always wrong.”Use it for genuine bounded request/reply with timeout, cancellation, correlation, and idempotency. Prefer asynchronous workflows when the caller need not block.
“RabbitMQ is not a database, so it cannot retain/replay.”A destructive queue shouldn't be the system of record, but RabbitMQ Streams are replicated, retained, append-only logs with replay. Choose by lifecycle and query needs, not a slogan.
“Durable queue + persistent message means no loss.”Durability and persistence are separate settings. Add confirms, correct routing/return handling, a matching queue type, and application recovery — unconfirmed publishes remain a risk.
“More prefetch is always faster” or “prefetch must be 1.”Prefetch is a workload-specific in-flight bound. Measure processing variance, memory, downstream limits, fairness, and redelivery cost.

Self-test

1. Why should a worker acknowledge after the side effect, not before?

Acknowledging before the side effect risks losing work if the worker crashes after acking but before committing. Acknowledging after means a crash produces a safe duplicate redelivery instead — provided the side effect is guarded by an idempotency key.

2. Does a fanout exchange guarantee each subscriber gets its own copy of every message?

Only if each subscriber has its own bound queue. Multiple consumers sharing one bound queue still compete for deliveries the normal way — fanout controls exchange-to-queue copying, not queue-to-consumer delivery.

3. Is Direct Reply-To durable across a requester disconnect?

No. It is a pseudo-queue with no actual queue process or buffering — replies are at most once and can be dropped if the requester is unavailable when the reply arrives.

4. Does the quorum queue delivery limit stop every redelivery loop?

No. basic.reject and failed outcomes advance the failure-oriented delivery-count, but AMQP 0-9-1 basic.nack returns do not — an unbounded nack-and-requeue loop can bypass the limit.

5. Is "RabbitMQ cannot retain or replay data" still accurate in 4.3?

No. RabbitMQ Streams are replicated, retained, append-only logs with replay by offset. The destructive-queue-only framing predates Streams and Super Streams.

6. What is the one honest test behind every anti-pattern slogan in this lesson?

A workload-specific question — cardinality, churn, lifecycle, replication cost, isolation, or failure tolerance — rather than a categorical yes/no rule.
