RabbitMQ Streams: The Log-Based Queue

A stream is a persistent, replicated, append-only log. Consuming it does not remove a record, so many readers can replay the same history at their own pace. That single property — non-destructive reads — changes offsets, retention, tracking, and durability, and it is why a stream is a different data structure, not a faster queue.

The runnable example uses Python 3 with Pika 1.3.2 over AMQP 0-9-1; the native Stream protocol is referenced but attributed to dedicated stream clients. 00 Failure first

“It is just a faster queue” breaks two assumptions at once

Two teams reach for a stream and are surprised. The first treats it like a work queue: they expect that acknowledging a message removes it, and that a second consumer will therefore see a smaller backlog. It never shrinks, because stream reads are non-destructive. The second team expects the broker to remember, over an ordinary AMQP 0-9-1 connection, where each consumer left off — the way a Kafka consumer group commits offsets. The broker does store a start position when asked, but committed progress is a separate concern that core AMQP access does not manage for you.

Both surprises come from the same root. RabbitMQ Streams model an append-only log that can be read repeatedly until data expires. A read advances only that reader; it does not delete the record or move a shared pointer. So the questions you must answer before choosing a stream are different from queue questions: how far back must readers replay, how many independent readers exist, how large is the retained history, and who is responsible for remembering processing progress.

The course already placed streams next to classic and quorum queues in the queue-type lesson: classic and quorum are competing-consumer work queues with destructive acknowledgement, while a stream is a retained log with offsets. This chapter goes inside that log: how offsets and start specifications work, why a start offset is not a durable checkpoint, how retention deletes whole segments rather than exact records, and what the confirm boundary does and does not guarantee.

Stream invariant

A stream is an append-only, replicated log with non-destructive reads. Consuming advances a single reader's position; it never deletes records or moves a shared cursor. Choose a stream for replay, many independent readers, large retained backlogs, and high throughput — not for destructive work distribution.

01 Mechanism

An append-only log that many readers share ▸

Producers append messages to the tail of the log, and RabbitMQ assigns each appended message a monotonically increasing offset. On disk the stream is a sequence of fixed-size segment files; each segment holds chunks, and each chunk holds one to a few thousand messages depending on ingress rate. An index maps offsets and timestamps to positions so a reader can attach quickly at a chosen point.

Because reading does not consume, any number of consumers can attach at different offsets and move forward independently. A large fan-out no longer needs one dedicated queue per subscriber, and a reader can rewind to reprocess history. Streams are always durable and replicated with a leader and replicas, so read load can also be spread across replicas. 02 Offsets

Start specifications choose where to attach, with caveats

A consumer chooses where to begin with an offset specification. If none is given, it behaves like next. The supported values each carry a qualification that interviewers and production incidents both probe:

SpecificationMeaningQualification to state out loud
firstFirst record still available in the log.After retention this may no longer be offset 0.
lastStart at the last written chunk.A chunk can hold many messages; this is not “only the final message”.
next / omittedWait at the current tail for data appended later.An idle consumer sees nothing until a producer appends.
absolute offsetA numeric position to attach at.Out-of-range values clamp to the start or end; offsets are monotonic but need not be contiguous because storage holds non-message entries.
timestampA chunk found by broker arrival time.Not an application timestamp; chunk granularity can deliver records from shortly before the requested time. Over AMQP 0-9-1 the resolution is one second.
intervalA time window relative to now (units Y M D h m s).Do not assume every client API exposes every form identically.

These specifications only pick an attachment point in the retained log. They say nothing about which records a reader has already processed. That distinction — start position versus committed progress — is the subject of the next section and the single most common stream misconception.

03 Invariant

A start offset is not a durable checkpoint ▸

Selecting first or offset 5000 tells the broker where to begin dispatching to this subscription. It does not record how far the application has successfully processed. Committed progress is a separate mechanism. The native Stream protocol has explicit store_offset and query_offset commands, and the dedicated stream clients layer automatic or manual tracking on top of them; those stored offsets are persisted inside the stream itself as non-message data, which is why the log grows slightly per checkpoint and why offsets are not perfectly contiguous.

Broker-side offset tracking is currently a Stream-plugin (native protocol) feature. An AMQP 0-9-1 consumer can select a start position but has no broker checkpoint store; it must persist its own resume offset in an external store. And tracking of either kind is periodic, so a checkpoint can lag work already completed. After a restart the consumer resumes from the last stored offset and re-delivers everything since — duplicates. The rule that survives every design review: checkpoint only after your chosen processing boundary, and make handling idempotent.

04 Boundary

Retention deletes whole segments, not exact records

A stream would grow until the disk fills, so retention discards the oldest data by age, by total size, or both. Two parameters control it: max-age (units Y M D h m s, for example 7D) and max-length-bytes. They can be set as declaration arguments or as a policy, and for these retention settings the policy takes precedence over queue arguments.

The crucial qualification is granularity. Retention is evaluated per segment, not per record. RabbitMQ deletes a whole segment file once its data falls outside the limit, and it always leaves at least one segment in place as long as that segment holds at least one message. So the actual retained size can exceed the nominal max-length-bytes until a segment rolls over, and old data can survive slightly past max-age. Segment size — x-stream-max-segment-size-bytes, default 500 MB — therefore shapes when data actually disappears. That argument, like x-stream-filter-size-bytes, is applied only if present at declaration time; changing it by policy later does not reconfigure an existing stream.

Replay is bounded by retention

“Replay” means reattaching at an available earlier offset. It cannot reconstruct expired segments, does not override retention, and does not guarantee a timestamp lands exactly on the first record at or after that instant. If a workload must replay ninety days, retention must actually keep ninety days of segments — and that is a disk-sizing decision, not a default.

05 Trade-off

When a stream beats a queue — and the confirm caveat

Streams shine for four workloads that queues serve poorly: large fan-outs to many independent readers, replay or time-travel, high sustained throughput, and very large retained backlogs held with minimal in-memory overhead. These are workload-dependent benefits, not universal superiority. Queue semantics remain preferable for competing-consumer work distribution and for features streams deliberately do not implement — per-message TTL, priority, dead-lettering, temporary or exclusive queues, and destructive removal after acknowledgement. The dedicated Stream protocol is the recommended path to the complete feature set and the best throughput; AMQP clients can use a stream as a queue-shaped resource but do not get native super-stream orchestration, stream single-active-consumer, publish deduplication, or broker offset tracking.

“Persistent and replicated” still does not equal the strongest confirmed-write boundary. Stream publisher confirms are issued after replication to a quorum of stream replicas, but the implementation does not explicitly fsync each confirmed record; it relies on the operating system to flush the page cache. An uncontrolled shutdown of a node can therefore lose confirmed data on that node, which is normally re-replicated from the other members. When the requirement is RabbitMQ's strongest documented confirmed-write boundary for work, quorum queues — which confirm only after a quorum has both written and flushed to disk — are the relevant candidate, not streams.

06 Build

Prove non-destructive replay over AMQP 0-9-1

This lab uses an ordinary AMQP 0-9-1 client — Pika — because a stream remains a declarable AMQP queue. It shows what core AMQP access legitimately does with a stream: declare it, publish records, attach at an offset specification, set a prefetch and acknowledge (acks act as a credit mechanism that advances the reader, not a delete), and re-read from the beginning to prove the records are still there. It deliberately does not claim broker offset tracking, which requires the native Stream protocol; instead it notes where an external store would live.

Complete runnable stream replay probePython 3 · Pika 1.3.2 · AMQP 0-9-1

Reading twice returns the same records

python · install pika==1.3.2 and run against a RabbitMQ 4.3 node with streams enabled
import uuid

import pika

stream = f"lab.stream.orders.{uuid.uuid4().hex[:10]}"
connection = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
channel = connection.channel()


def read_from(offset_spec, limit):
    """Attach a fresh AMQP 0-9-1 consumer at an offset specification and read
    up to `limit` records without deleting them."""
    # Streams require a per-consumer QoS prefetch; global QoS is rejected.
    channel.basic_qos(prefetch_count=20)
    seen = []
    for method, _properties, body in channel.consume(
        stream,
        auto_ack=False,
        arguments={"x-stream-offset": offset_spec},
        inactivity_timeout=2,
    ):
        if method is None:
            break  # no more data arrived within the timeout window
        seen.append(body)
        # Ack advances THIS reader's credit; it does not remove the record.
        channel.basic_ack(method.delivery_tag)
        if len(seen) >= limit:
            break
    channel.cancel()
    return seen


try:
    channel.queue_declare(
        queue=stream,
        durable=True,
        exclusive=False,
        auto_delete=False,
        arguments={"x-queue-type": "stream", "x-max-age": "1h"},
    )
    published = [f"order-{i}".encode() for i in range(5)]
    for body in published:
        channel.basic_publish(exchange="", routing_key=stream, body=body)

    first_pass = read_from("first", limit=5)
    second_pass = read_from("first", limit=5)  # a second reader re-attaches at the start
    tail_wait = read_from("next", limit=1)      # "next" waits at the tail

    assert first_pass == published        # started at the first available record
    assert second_pass == published       # non-destructive: the records are still there
    assert tail_wait == []                # nothing was appended after we attached
    print({"published": len(published), "reread": len(second_pass), "tail_wait": tail_wait})
finally:
    # Broker offset tracking would need the native Stream protocol; an AMQP 0-9-1
    # consumer resuming later must persist its own offset in an external store.
    channel.queue_delete(queue=stream)
    connection.close()

The two assertions on first_pass and second_pass are the whole lesson in executable form: a second attach at first returns the identical five records, so consumption did not delete anything. The tail_wait assertion shows next parking at the tail. In production you would keep the stream (not delete it), attach at a stored offset to resume, and record that offset only after the processing boundary so restarts stay idempotent.

Self-test

1. Why does acknowledging a stream message not shrink the backlog for other consumers?

Stream reads are non-destructive. An acknowledgement advances the acknowledging consumer's credit/position; it does not delete the record, so other readers still see it until retention removes the segment.

2. What does the last offset specification actually start from?

The last written chunk, not the single final message. A chunk can contain many messages, so last can deliver a batch, not one record.

3. How is a start offset different from a committed checkpoint?

A start offset selects where a subscription begins reading. A checkpoint records how far processing has succeeded. The Stream protocol stores checkpoints via store_offset/query_offset; an AMQP 0-9-1 consumer must keep its own external store.

4. Why can a restarted consumer reprocess messages even with offset tracking?

Tracking is periodic, so the stored checkpoint can lag work already done. On restart the consumer resumes from that checkpoint and re-delivers everything since, producing duplicates unless handling is idempotent.

5. Why can a stream's on-disk size exceed max-length-bytes?

Retention is evaluated per segment, not per record. A segment is deleted only once its data is fully outside the limit, and at least one segment is always kept, so actual size can overshoot until a segment rolls over.

6. Are stream confirms as strong as quorum-queue confirms?

No. Stream confirms are issued after replication to a quorum of replicas but without an explicit fsync; quorum queues confirm only after a quorum has written and flushed to disk.
