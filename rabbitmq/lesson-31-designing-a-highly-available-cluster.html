Designing a Highly Available Cluster

High availability is not a product you switch on; it is a chain of decisions, each derived from a written requirement and each falsifiable by a drill. This capstone turns “make it HA” into node count, failure domains, queue members, client recovery, and a rolling-maintenance plan — then states the guarantee honestly, with all its conditions.

Original study chapter. The design, scenario, diagrams, code, and SVGs are written from scratch. Stable behavior targets open-source RabbitMQ 4.3, with the signed 4.3.3 maintenance release as the current patch overlay; runnable code uses Python 3 and Pika 1.3.2. This chapter contains three original figures, two interactive. The availability guarantee is conditional, never unconditional.
00 Requirements first

“Three nodes and a load balancer” is not an availability plan

The most common HA design is a sentence: “we run three nodes behind a load balancer, so we’re highly available.” It omits everything that decides whether that is true. Which failures must you survive — one node, one rack, one availability zone? Which queues hold data you cannot lose? What must a client do when its node vanishes mid-publish? What happens to a message you sent but never got a confirm for? And how will you prove the design under failure instead of hoping?

So start with a contract, not a topology. Write the availability requirement in one line — for example, “survive the loss of any one node or one failure domain without losing confirmed work, tolerating brief pauses.” Then derive each decision from it: node count and placement, queue type and member sizing, client connection and recovery, and the maintenance procedure. Every choice traces back to the requirement, and every choice has a drill that can falsify it.

This lesson walks that derivation end to end and finishes with the guarantee stated the way the documentation supports it: conditional. A load balancer, in particular, earns a precise role — it selects an endpoint, and that is all. It is not queue HA, and it does not recover a single byte of your client’s channel state.

The design invariant

Requirement first, then derive. Node count and failure domains give a Khepri majority; quorum members give per-queue safety; client recovery plus confirms and idempotency give correctness across reconnects; drills turn the design from a claim into evidence.

01 Derivation

From the requirement to nodes, members, clients, and drills ▸

The derivation is a chain, and the stepper animates it link by link. Surviving one failure means an odd node count whose majority tolerates one loss — three nodes, placed across independent failure domains so that a single rack or zone outage removes only one. That gives Khepri a majority of two out of three. The critical queues then become quorum queues with three members placed across those same nodes, so each queue also tolerates one loss, with observable and balanced leaders.

Clients come next: they need an endpoint list or a sufficiently available load balancer to find a node, plus explicit reconnect, channel and settings restoration, topology redeclaration, publisher confirms, and idempotency to stay correct across a failover. Finally, the design is only a hypothesis until failure drills and metrics confirm it — so the maintenance plan and the drills are part of the design, not an afterthought.

02 Decision

Node count, failure domains, and per-queue member sizing

Node count answers the metadata question. Three nodes across independent failure domains give Khepri a majority of two, so one node, rack, or zone can fail and topology operations still commit. Odd counts are the rule; a fourth node adds cost without buying more tolerance, and two nodes tolerate zero failures. Placement matters as much as count — three nodes in one rack survive a process crash but not the rack.

Member sizing answers the per-queue question, and it is a separate decision. Each critical queue is a quorum queue with three members placed across the three nodes, so it tolerates one member loss independently of Khepri. Keep the two numbers distinct: the broker node count is the metadata majority; each queue’s member count is that queue’s majority. Leaders should be balanced across nodes and observable, so that no single node carries every queue’s leader and so you can see when one does.

03 Decision

Clients must recover; a load balancer only chooses a door ▸

Clients connect to one node at a time and can connect to any healthy node; RabbitMQ routes queue operations to the relevant leader. The hard truth is what happens on failure: a node outage does not teleport an existing TCP connection to a survivor. The application must reconnect to another node, reopen its channels, restore channel settings including prefetch/QoS and confirm mode, redeclare topology, and recover its consumers. None of that is free, and none of it is done for you by the network.

This is where a Python-specific caveat matters. RabbitMQ’s 4.3 upgrade guide lists Java, .NET, and Bunny under automatic connection recovery, but lists Pika under connection-close callbacks. So do not assume Pika restores your topology automatically; drive an explicit, bounded reconnect-and-redeclare loop instead. And a load balancer, useful as it is, solves only endpoint selection — it does not provide queue quorum, does not recover channel state or topology, and does not resolve the ambiguity of a publish that was never confirmed.

04 Procedure

Rolling maintenance: one node at a time, proven at each step

Maintenance is where availability is either preserved or quietly lost, so the procedure is strict: stop, upgrade, start, and validate exactly one node at a time. Before each stop, verify cluster health, confirm there is capacity with the node absent, check that there are no alarms and no active replica synchronization, and confirm quorum safety. The check that encodes the last point is rabbitmq-diagnostics check_if_node_is_quorum_critical, which fails if stopping the target would remove an online majority from a quorum queue, stream, or internal component; rabbitmq-upgrade await_online_quorum_plus_one can gate an automated shutdown until enough nodes are online.

To take a node out gracefully, enter maintenance mode with rabbitmq-upgrade drain: it stops accepting new client traffic, closes existing client connections (so applications reconnect elsewhere), and attempts to transfer quorum-queue leaders off the node before shutdown. A restart exits maintenance mode automatically. Then wait — for the restarted node to rejoin and for replicas to catch up — before touching the next node. Only after every node runs the target version do you enable newly introduced stable feature flags, and you rebalance leaders if they have bunched.

bash · a rolling node maintenance, with the precheck and the proof at each step
# 1. Precheck: would stopping THIS node strand a majority? (fails if so)
rabbitmq-diagnostics check_if_node_is_quorum_critical
rabbitmq-upgrade await_online_quorum_plus_one        # optional shutdown gate

# 2. Drain: stop new traffic, close connections, move quorum leaders off.
rabbitmq-upgrade drain

# 3. Stop, upgrade, and start this one node. A restart exits maintenance mode.

# 4. Prove rejoin and catch-up BEFORE moving to the next node.
rabbitmqctl cluster_status
rabbitmq-queues quorum_status orders.work

# 5. After ALL nodes run the target version: enable new stable flags, rebalance.
rabbitmqctl enable_feature_flag all
rabbitmq-queues rebalance quorum
Sequencing warning

Never stop the next node until the previous one has rejoined and its replicas have caught up. Skipping the wait can momentarily drop a quorum below its majority — the one thing the whole design exists to prevent.

05 Falsification

State the guarantee with its conditions — then drill it

The tempting sentence is “a rolling restart never drops a committed message.” It is too broad. The defensible, documented claim is conditional: with enough capacity, a maintained Khepri majority, a maintained majority for every important quorum queue, publisher confirms, strict one-node-at-a-time sequencing, and working client recovery, the cluster can remain available and publisher-confirmed quorum-queue messages retain their documented safety. Every one of those conditions is load-bearing.

And even when they all hold, the honest edges remain: leader elections can still pause traffic briefly; the drain step disconnects clients, which must reconnect; a publish that was never confirmed stays ambiguous; and retransmission and requeue mean duplicates and redeliveries are possible. That is why idempotent consumers are not optional. The way you turn this from a story into a fact is to drill it — and to watch metrics that would reveal a broken assumption.

Interview follow-up

“Does your cluster guarantee zero message loss during upgrades?” Answer conditionally: “Confirmed messages on quorum queues stay safe while a majority is maintained and we upgrade one node at a time with client recovery. Unconfirmed publishes are ambiguous, elections cause brief pauses, and clients reconnect on drain — so consumers are idempotent and we drill the failures.”

06 Build

An explicit reconnect-redeclare-confirm loop, because Pika won’t do it for you

The script encodes the client half of the design exactly as the dossier prescribes for Python: an explicit, bounded reconnect loop that reopens a channel, restores confirm mode, redeclares topology, and publishes idempotently with a message_id. It does not rely on automatic recovery, because Pika is documented via connection-close callbacks rather than the guide’s automatic-recovery list. Against a healthy broker it succeeds on the first attempt; the structure is what would carry it through a node failure.

Client recovery checkpointPython 3 · Pika 1.3.2

Bounded reconnect, redeclare, confirm, and idempotent publish

python · install pika==1.3.2 and run against localhost
import time
import uuid

import pika
from pika.exceptions import AMQPError

QUEUE = f"lab.l31.orders.{uuid.uuid4().hex[:10]}"
ENDPOINTS = ["localhost"]        # a real client passes several nodes or a load balancer
MAX_ATTEMPTS = 5


def connect(endpoints):
    # Most clients accept multiple endpoints for initial connect and recovery;
    # a load balancer is an alternative. Neither restores channel state for you.
    return pika.BlockingConnection([pika.ConnectionParameters(host=h) for h in endpoints])


def declare_topology(channel):
    # Redeclare on every (re)connect and restore settings: a new node does not
    # remember your channel, its QoS, or its confirm mode.
    channel.queue_declare(
        queue=QUEUE, durable=True, arguments={"x-queue-type": "quorum"}
    )
    channel.confirm_delivery()


def send_with_recovery(endpoints, message_id, body):
    # Pika is documented via connection-close callbacks, not the guide's
    # automatic-recovery list, so we drive an EXPLICIT bounded reconnect loop.
    for attempt in range(1, MAX_ATTEMPTS + 1):
        try:
            connection = connect(endpoints)
            channel = connection.channel()
            try:
                declare_topology(channel)
                # message_id lets an idempotent consumer dedupe the duplicates a
                # retransmit after an ambiguous confirm will inevitably create.
                channel.basic_publish(
                    exchange="", routing_key=QUEUE, body=body,
                    properties=pika.BasicProperties(delivery_mode=2, message_id=message_id),
                    mandatory=True,
                )
                return attempt
            finally:
                connection.close()
        except AMQPError:
            if attempt == MAX_ATTEMPTS:
                raise
            time.sleep(min(2 ** attempt, 10))
    raise RuntimeError("exhausted reconnect attempts")


attempts = send_with_recovery(ENDPOINTS, "order-1", b"pay")
assert attempts == 1  # first try on a healthy broker; the loop survives failovers

verify = connect(ENDPOINTS)
channel = verify.channel()
try:
    ready = channel.queue_declare(queue=QUEUE, passive=True).method.message_count
    assert ready == 1  # the confirmed publish is on the quorum members
    print({"attempts": attempts, "ready": ready})
finally:
    channel.queue_delete(queue=QUEUE)
    verify.close()

The loop is the design in miniature: endpoints to find a node, redeclare because the new node is stateless about your channel, confirms to know the write reached a majority, and an idempotency key because reconnection means duplicates. Swap the single endpoint for three nodes or a load balancer and the same code rides through a one-node failure.

Self-test

1. Why is “three nodes and a load balancer” an incomplete HA plan?

It omits failure-domain placement, per-queue member sizing, client reconnect and topology recovery, publisher confirms, idempotency, and the maintenance procedure and drills. A load balancer only selects an endpoint; it does not provide queue HA or recover client state.

2. How many nodes and members, and why?

Three nodes across independent failure domains give Khepri a majority of two, tolerating one loss. Critical queues are quorum queues with three members placed across those nodes, so each queue independently tolerates one member loss. Counts are odd; broker nodes and queue members are separate numbers.

3. What must a client do when its node fails?

Reconnect to another node (from an endpoint list or via a load balancer), reopen channels, restore settings including QoS and confirm mode, redeclare topology, recover consumers, and retransmit unconfirmed publishes. In Python, drive this explicitly — Pika is documented via close callbacks, not automatic recovery.

4. What is the correct order for taking a node down during a rolling upgrade?

Run check_if_node_is_quorum_critical (and optionally await_online_quorum_plus_one), then rabbitmq-upgrade drain, then stop/upgrade/start. Wait for rejoin and replica catch-up before the next node; enable new stable flags and rebalance only after all nodes run the target version.

5. State the availability guarantee honestly.

Conditional: with capacity, a maintained Khepri majority and per-queue majority, confirms, one-node-at-a-time sequencing, and client recovery, the cluster stays available and confirmed quorum messages stay safe. Elections still pause traffic, drain disconnects clients, unconfirmed publishes are ambiguous, and duplicates/redeliveries are possible.

6. Why are failure drills part of the design?

Because the guarantee is a hypothesis until injected failures (node loss, leader loss, partition, drain) and metrics (confirms, depth, redeliveries, catch-up time) confirm it. Drills turn a claim into evidence and reveal a broken assumption before production does.
