Federation & Shovel: Linking Brokers

Federation and Shovel move messages between logically separate brokers over the WAN — but neither turns two clusters into one, and neither is synchronous replication. One is a policy-driven, demand-aware pull; the other is an explicit, unconditional consume-and-republish pump. Picking between them is picking how much control you want to give up.

Original study chapter. The scenarios, diagrams, and commands are written from scratch. Stable behavior targets open-source RabbitMQ 4.3, with the signed 4.3.3 maintenance release as the current patch overlay. This chapter contains three original figures, two interactive.
00 Failure first

“Federation replicates everything, like clustering”

A team wires up exchange federation between two regional clusters expecting every message published in region A to land in region B, the way a quorum queue replicates to every member. Nothing arrives. The federation link is healthy, the policy matches, and yet the downstream exchange stays quiet — because no queue in region B is bound with a routing key the upstream message actually satisfies, and exchange federation is routing-aware: it forwards only what can route downstream.

A second team assumes the opposite failure mode: they set ack-mode to no-ack for “better throughput” on a Shovel moving orders across a WAN link, then lose messages during a network blip with no trace of what vanished. Federation and Shovel are asynchronous client connections between separate brokers, not a replication protocol — every safety property you get is one you explicitly configured.

The core distinction

Federation is policy-driven and demand-aware: a downstream broker starts a link to an upstream and pulls only what its own topology can use. Shovel is an explicit, unconditional pump: it consumes from a configured source and republishes to a configured destination, full stop. Neither is clustering, and neither is exactly-once.

01 Decision

Choose by intent, not by a generic “multi-DC” label

The two mechanisms overlap enough to look interchangeable and differ enough that picking the wrong one creates real operational pain. The question to ask is not “which is for multi-datacenter” — both can be — but what shape of demand and control the situation needs.

Queue federation’s local-consumer precedence is the detail interviewers probe: an upstream queue with its own active consumers keeps its messages local, and federation only forwards the overflow to a downstream cluster that has none. A Shovel has no such courtesy — it moves what it is told to move, unconditionally, which is exactly why it is the right tool for a deliberate one-off migration.

02 Mechanism

The directional pull ▸

Federation terminology is directional, and getting the direction backward is the most common conceptual mistake. The downstream broker is the one you configure — it defines an upstream and starts a link that pulls from it. Nothing pushes into a downstream broker uninvited.

Exchange federation is routing-aware: it will not forward a message that cannot route to anything downstream. Queue federation is demand-aware in the opposite sense — it forwards toward downstream consumers only when the upstream queue’s own local consumers are absent. Neither is “Federation replicates every message and every queue,” and treating them as identical mechanisms with different names is the error that produces surprised silence in production.

03 Safety

The ack-mode safety spectrum ▸

Both Federation and Shovel let you choose how a message is acknowledged as it crosses the link, and that choice is the single biggest lever on loss versus duplication versus speed. None of the three options is exactly-once — say that up front so nobody walks away with a false sense of safety.

The default on-confirm waits for a downstream publisher confirm before the source considers the message handled, which protects against loss in the failure cases it covers — but an uncertain confirm followed by a reconnect can still redeliver, so the consumer at the far end must be idempotent regardless. on-publish and no-ack explicitly trade that safety for throughput and can lose messages outright during a disruption; treat them as a deliberate choice for data you can afford to lose, never a default.

04 Boundary

Hops and duplicate paths

Exchange federation’s default max-hops is one. Raising it lets a message traverse more of a federation graph without revisiting the same node twice, which sounds like a pure improvement — but a graph with multiple paths to the same eventual destination can still deliver the same message twice by two different routes, independent of any ack-mode setting. More hops is not a substitute for consumer idempotency; it changes reachability, not exactly-once delivery.

Neither is cluster replication

Federation and Shovel connect logically separate brokers or clusters over asynchronous client connections that tolerate WAN interruptions by reconnecting. They do not turn those brokers into one RabbitMQ cluster, and no combination of ack-mode or hop count makes either mechanism a synchronous, zero-data-loss replication channel.

05 Build

Link two clusters, then move one queue explicitly

The federation example below runs on the downstream cluster — the one that pulls. The Shovel example is a separate, explicit one-off move; running both against the same backlog can reorder messages, so treat them as alternatives for a given queue, not a combo.

Federation upstream + policy, then a dynamic Shovelshell

Federation — configure the downstream, then verify

bash · run on the downstream cluster; replace every placeholder
rabbitmq-plugins enable rabbitmq_federation

# Percent-encode the vhost; use a least-privilege upstream user with verified TLS.
rabbitmqctl set_parameter -p "$VHOST" federation-upstream upstream-a \
  '{"uri":"amqps://<upstream-host>/<encoded-vhost>","ack-mode":"on-confirm","reconnect-delay":5}'

rabbitmqctl set_policy -p "$VHOST" --apply-to exchanges \
  federate-orders '^orders$' \
  '{"federation-upstream":"upstream-a"}'

# federation_status is NODE-LOCAL — check every node eligible to host a link.
rabbitmqctl federation_status

Shovel — one explicit, unconditional queue move

bash · a dynamic shovel is the modern preferred type over a static one
rabbitmq-plugins enable rabbitmq_shovel

rabbitmqctl set_parameter -p "$VHOST" shovel blue-to-green-orders \
  '{"src-protocol":"amqp091","src-uri":"amqps://<source-host>/<encoded-vhost>","src-queue":"orders","dest-protocol":"amqp091","dest-uri":"amqps://<target-host>/<encoded-vhost>","dest-queue":"orders","ack-mode":"on-confirm","reconnect-delay":5}'

rabbitmqctl shovel_status --formatter=pretty_table

Both endpoints need their own least-privilege identity and verified TLS — never paste connection URIs with embedded credentials into shell history or into a definitions export without protecting the artifact. Predeclare the destination queue’s intended type; an accidental default classic queue is easy to end up with if you let the Shovel create it implicitly. Confirm routing, duplicate handling, message properties, and drain completion before deleting a migration Shovel — deleting it early can strand in-flight work.

↗ Practice

Configure → Diagnose → Design

ConfigureSet up exchange federation from a regional upstream, with an on-confirm ack-mode. State exactly what happens to a message that has no matching downstream binding, and why that is not a bug.
DiagnoseA queue federation link that was supposed to relieve an overloaded upstream queue never forwards anything. The upstream queue still has active local consumers. Explain the demand rule that produces this and what you would change.
DesignYou must migrate one queue's backlog from an old cluster to a new one during a maintenance window, and you also want ongoing routing-aware exchange flow afterward. Decide which mechanism does which job and why running both against the same queue simultaneously is risky.

Self-test

1. Which broker starts a federation link — upstream or downstream?

The downstream broker. It defines the upstream and starts a link that pulls messages; nothing is pushed into a downstream broker uninvited.

2. Why might a healthy federated exchange link forward nothing?

Exchange federation is routing-aware — it will not forward a message that cannot route to any binding downstream. A healthy link with no matching downstream binding legitimately delivers nothing.

3. When does queue federation move work to a downstream cluster?

Only when the upstream queue has no local consumers of its own. Local consumers take precedence; federation forwards the overflow, not a live copy of everything.

4. Is on-confirm ack-mode exactly-once?

No. It reduces loss by waiting for a downstream confirm before the source considers a message handled, but an uncertain confirm followed by a reconnect can still redeliver — consumers must remain idempotent.

5. What does raising exchange federation's max-hops actually change?

It lets a message traverse more of a federation graph without revisiting the same node, changing reachability. It does not prevent duplicate delivery when multiple graph paths reach the same destination.

6. Should you run a Shovel and queue federation against the same backlog at once?

Avoid it — both mechanisms moving the same backlog concurrently can reorder messages relative to each other. Choose one deliberate mechanism per queue for a given operation.
