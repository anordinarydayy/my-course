Security: TLS, AuthN & AuthZ

Four separate questions hide inside the word “security”: is the connection encrypted, do both sides trust each other's certificate, does RabbitMQ know who you are, and are you allowed to do what you're asking. Each layer can pass while the next one silently fails open — and the gap between them is exactly where a “secure” deployment still lets guest in.

Original study chapter. The scenarios, diagrams, and configuration are written from scratch. Stable behavior targets open-source RabbitMQ 4.3, with the signed 4.3.3 maintenance release as the current patch overlay. This chapter contains three original figures, two interactive.
00 Failure first

“We set verify_peer, so we have mTLS”

A team enables TLS, sets ssl_options.verify = verify_peer, and requires a client certificate. They call this mutual TLS and move on. But verify_peer on the server is only half of mutual TLS — it makes RabbitMQ validate the client's certificate chain. Nothing in that setting makes the client validate the server's certificate or hostname, and nothing in it maps the client's certificate to a RabbitMQ identity. The client that skipped server validation would have connected just as happily to an impostor broker.

The second half of the same mistake: even after true mTLS is working, a client presenting a perfectly valid certificate can still log in as guest over PLAIN, because requiring a certificate and authenticating with one are different mechanisms. Without the rabbitmq_auth_mechanism_ssl plugin, the EXTERNAL SASL mechanism, and a certificate-to-username rule, a valid client certificate proves nothing to RabbitMQ's authentication layer — it just proves the TLS handshake succeeded.

The core distinction

Encryption, peer trust, authentication, and authorization are four separate control points. Passing one says nothing about the next. A deployment is only as secure as its weakest configured layer, and the layers do not compose automatically just because they all mention “TLS” or “certificates.”

01 Framework

Four separate layers, in order ▸

Walk a connection through all four checkpoints in the order RabbitMQ actually evaluates them, and the “we have security” question becomes four much sharper questions.

Transport security — TLS encrypts the connection, and server certificate validation authenticates the server to the client. Mutual peer validation — true mTLS means both peers validate certificate chains; RabbitMQ's verify_peer is the server's half only, and the client must independently validate the server and its hostname. RabbitMQ authentication — a valid client certificate does not by itself map to a RabbitMQ user; that needs rabbitmq_auth_mechanism_ssl, the SASL EXTERNAL mechanism, a certificate-to-username rule, and a matching user in the selected backend. Authorization — successful authentication still requires vhost access and configure/write/read checks on named resources, and topic authorization is an additional routing-key check for topic exchanges, not a substitute for ordinary resource permissions.

02 Configuration

TLS listener and the client-certificate requirement

ini · rabbitmq.conf — paths are illustrative; readable only as needed by RabbitMQ
listeners.ssl.default = 5671
ssl_options.cacertfile = /etc/rabbitmq/tls/ca-bundle.pem
ssl_options.certfile   = /etc/rabbitmq/tls/server-cert.pem
ssl_options.keyfile    = /etc/rabbitmq/tls/server-key.pem
ssl_options.verify     = verify_peer
ssl_options.fail_if_no_peer_cert = true

# Disable plaintext only after every client and health check has migrated.
# listeners.tcp = none
bash · verify what is actually listening before rolling further
rabbitmq-diagnostics listeners

Stage the CA, server, and client certificates and file permissions on every node, and verify SAN/hostname matching and chain depth from every client runtime before rolling the configuration cluster-wide. fail_if_no_peer_cert = true rejects any client that doesn't present a certificate — test this deliberately rather than discovering it in production. Restricting to TLS 1.3 only can exclude older client runtimes; choose versions and ciphers from your target patch's supported Erlang/OpenSSL and client matrix. Disabling the plaintext listener prematurely can lock out applications and diagnostics tooling that haven't migrated yet.

Never use verify_none in production

ssl_options.verify = verify_none disables certificate validation entirely and is sometimes reached for as a quick fix during a certificate-chain debugging session. It should never survive past that debugging session — it removes the layer this entire lesson is about.

03 Mechanism

EXTERNAL: mapping a certificate to a username ▸

Requiring a certificate and authenticating with one are different mechanisms, and the gap between them is where the “we require client certs” team still finds guest/PLAIN logins succeeding.

bash · enable the mapping plugin
rabbitmq-plugins enable rabbitmq_auth_mechanism_ssl
ini · rabbitmq.conf — offer EXTERNAL; keep PLAIN only as a deliberate choice
# Prefer the full distinguished name unless the PKI guarantees globally unique CN/SAN values.
auth_mechanisms.1 = EXTERNAL
# Keep PLAIN only as an intentional migration/fallback decision over TLS.
auth_mechanisms.2 = PLAIN
ssl_cert_login_from = distinguished_name

The client must still opt into EXTERNAL — it isn't automatic just because the plugin is enabled — and a RabbitMQ user matching the extracted identity must already exist with permissions. Any password the client sends is simply ignored under EXTERNAL. Switching extraction from the full distinguished name to the common name can create collisions if your PKI doesn't guarantee CN uniqueness. Keeping PLAIN available broadens what's accepted; removing it before every client supports EXTERNAL causes an outage, so this is a staged migration, not a flag flip.

04 Trade-off

Authentication backends are alternatives, not stacked layers

RabbitMQ's authentication backends are chosen, not composed automatically — enabling a plugin changes nothing about policy until you also select it in auth_backends.

BackendWhat it providesProduction caveat
Internal (default)Users, password hashes, and permissions stored in RabbitMQ; managed by rabbitmqctl user/permission commandsBuilt-in guest identity is loopback-only by default — should never be enabled remotely in production
LDAPCan provide authentication, authorization, or authentication paired with internal authorizationDefault authorization query is permissive; production needs explicit vhost/resource/topic queries, verified TLS to LDAP, timeouts, and usually a cache backend
OAuth 2Validates a signed JWT and (by default) its audience, then translates token scopes into permissions and management tagsMessaging-backend token validation and management-UI OAuth login are separate configurations; never disable audience validation just to make a token work
bash · enabling a plugin is not the same as selecting it
rabbitmq-plugins enable rabbitmq_auth_backend_ldap
rabbitmq-plugins enable rabbitmq_auth_backend_oauth2
ini · choose and configure ONE deliberate policy — never paste all three as-is
auth_backends.1 = ldap
# auth_backends.1 = oauth2
# auth_backends.1 = internal

Selecting an external backend without its endpoints, TLS trust, authorization queries or scopes, and failure behavior fully configured can either deny every client or grant far more access than intended. Apply the same backend order consistently across every node in the cluster — a node that disagrees on backend order is a silent inconsistency waiting to be discovered during an incident.

05 Build

Least-privilege resource and topic permissions

Deny-by-default permissions for an existing topologyshell

Grant only what the application's declare/bind/publish/consume sequence needs

bash · resource permissions are regular expressions over queue/exchange names
# configure: '^$' denies ALL declarations — this app never creates topology itself.
# write: publish to the exchange, or bind to the queue.
# read: consume the queue, or read the exchange as part of a binding.
rabbitmqctl set_permissions -p /prod orders-app \
  '^$' '^(orders\.topic|orders\.queue)$' '^(orders\.topic|orders\.queue)$'

# Topic authorization is an ADDITIONAL check for routing keys on this topic exchange —
# it does not replace the resource permissions set above.
rabbitmqctl set_topic_permissions -p /prod orders-app orders.topic \
  '^tenant\.42\.publish\..*$' '^tenant\.42\.consume\..*$'
bash · read-only inspection — internal backend only
rabbitmqctl list_user_permissions orders-app
rabbitmqctl list_user_topic_permissions orders-app

Test the application's actual declare/bind/publish/consume sequence against this before deploying — the example deliberately denies configure operations, so an app that still tries to declare its own queue will fail loudly. Under the internal backend, defining no topic permissions means topic checks default to allow, so topic restriction is opt-in, not a safety net you get for free. These inspection commands only read internal-backend records; they cannot evaluate an external LDAP query or a JWT's effective scopes, so verifying an external backend needs a live authentication test, not a list_* command.

Self-test

1. Does setting ssl_options.verify = verify_peer give you mutual TLS?

No. That configures the server's validation of the client's certificate only. True mTLS also requires the client to independently validate the server's certificate and hostname.

2. Does a valid client certificate automatically authenticate a RabbitMQ user?

No. It requires the rabbitmq_auth_mechanism_ssl plugin, the client opting into the EXTERNAL SASL mechanism, a certificate-to-username extraction rule, and a matching user with permissions in the selected backend.

3. What happens to a client's password when it authenticates via EXTERNAL?

It is ignored. Identity comes entirely from the validated certificate; the password field is not checked.

4. Is enabling the LDAP authentication backend plugin enough to use it?

No. The plugin must be enabled AND selected in auth_backends, with its endpoints, TLS trust, and query behavior configured — otherwise no policy has actually changed.

5. Does topic authorization replace resource permissions on a topic exchange?

No. It is an additional check on routing keys; ordinary resource permissions (configure/write/read) still apply and are evaluated separately.

6. Under the internal backend, what happens if you define no topic permissions for a user?

Topic checks default to allow. Topic restriction is opt-in — omitting it is not a safety net.
