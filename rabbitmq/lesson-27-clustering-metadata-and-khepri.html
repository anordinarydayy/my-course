Clustering: Nodes, Metadata & Khepri

A RabbitMQ cluster is not one big queue in the sky. It is a set of equal broker peers that share metadata through a Raft-replicated store called Khepri, while message bodies stay wherever their queue type puts them. Getting that boundary right is the whole lesson — and the phrase “every node sees every queue” is the trap that gets it wrong.

Original study chapter. The scenarios, diagrams, code, and SVGs are written from scratch. Stable behavior targets open-source RabbitMQ 4.3, with the signed 4.3.3 maintenance release as the current patch overlay; runnable code uses Python 3 and Pika 1.3.2. This chapter contains three original figures, two interactive. In 4.3, Khepri is the only supported metadata store; Mnesia was removed.
00 Failure first

“Every node sees every queue” is true — and routinely misread

A team scales a single broker to three nodes expecting three copies of everything, then loses a node and is shocked that a pile of messages went with it. The confusion comes from a true sentence read the wrong way. In a RabbitMQ cluster every node does see every queue — you can list it, bind to it, and publish to it from any node. But “sees” means the queue’s definition is known cluster-wide, not that the queue’s contents live on every node.

That single distinction — definition versus content, metadata versus message bodies — explains almost every clustering surprise. A classic queue keeps its messages on exactly one node. A quorum queue keeps its messages on its configured member set. Neither scatters a copy onto all nodes just because all nodes can see the name. If you delete the wrong node, or split the network, what you lose depends entirely on where the content was, not on where the definition was visible.

So the mental model we build here has two layers. The bottom layer is the cluster of broker nodes and the metadata they agree on. The top layer is the per-queue and per-stream data, replicated (or not) by each resource’s own consensus group. Once those layers are separate in your head, the majority rules, the partition behavior, and the node operations all stop being mysterious.

The core distinction

Metadata (definitions of queues, exchanges, bindings, users, policies) is replicated to every node by Khepri. Message content is stored only where the queue type places it. Visibility of a name is not storage of its data.

01 Mechanism

Khepri replicates metadata; queue type decides where content lives ▸

The metadata store records the durable topology of the broker: users and their internal permissions, virtual hosts, exchanges, queue and stream definitions, bindings, runtime parameters, and policies. It deliberately does not store queue or stream message bodies. In RabbitMQ 4.3 that store is Khepri, a Raft-based, tree-structured database, and it keeps a replica on every connected cluster node. Because there is a replica everywhere, metadata consensus is scoped to the RabbitMQ cluster’s own node membership.

When a client declares a queue, that declaration is a metadata write. It travels to the Khepri leader, is appended to the Raft log, and is considered committed once a majority of nodes acknowledge it. After the commit, the definition is visible and reachable through any node — that is what “every node sees the queue” actually guarantees. The message bodies you then publish are a different thing entirely: they are content, and they are stored only on the queue’s member node or nodes.

The figure below plays the whole sequence: three equal peers each holding a Khepri replica, a declaration committed by majority, the definition becoming visible everywhere, and then the crucial contrast where the message bodies land on the members only. It ends on the reminder that connections, channels, and many metrics are node-local, not replicated metadata at all.

02 Mechanism

Equal broker peers, but many independent Raft leaders

At the broker level, cluster nodes are equal peers. There is no “primary RabbitMQ node” that owns the cluster; any healthy node can accept a connection and route work. But underneath, several separate Raft consensus groups run at once, and each has its own leader. Khepri is one Raft group. Every quorum queue is its own Raft group. Stream coordinators form their own groups too. A quorum queue’s leader is a leader of that queue’s group — it is not a special node that leads the cluster.

This matters because “leader” is scoped. Node A can be the Khepri leader, node B the leader of the orders quorum queue, and node C the leader of the events quorum queue, all at the same time. Losing node A costs you the Khepri leadership (a new one is elected) and any queue whose leader or content lived there — but it says nothing automatic about the other queues, whose groups elect and store independently.

Keeping the groups separate in your head also fixes the vocabulary. Modern RabbitMQ speaks of queue leaders and members, and of the queue-leader-locator. The old queue-master-locator and “master/mirror” words survive only as deprecated classic-queue compatibility names; they describe a mechanism that no longer exists in 4.x.

Interview follow-up

“Which node is the master?” Correct the premise: “There is no master node. Nodes are equal peers. Khepri, each quorum queue, and each stream coordinator are independent Raft groups, each with its own leader. Losing a node affects only the groups it led or stored.”

03 Invariant

Topology changes need a reachable Khepri majority ▸

Because Khepri is Raft, the rule for changing metadata is the Raft rule: an update, a delete, or a cluster-membership change must be accepted by an absolute majority of the group before it commits. If the leader cannot reach a majority, the operation blocks and can time out. The minority side simply cannot commit conflicting topology — that safety is intrinsic to consensus and, unlike the old Mnesia partition modes, it is not a knob you configure.

Be precise about the blast radius, though. It is wrong to say “the whole broker stops without a Khepri majority.” Existing, already-committed metadata can still be read from reachable nodes, and a quorum queue or stream has its own replica group that may still have its own majority. What cannot progress without the Khepri majority is the class of operations that require Khepri consensus: topology changes and certain strongly-consistent reads.

One more caveat that bites in practice: a committed write is accepted after a majority, not after every node has observed it. If a client declares a binding on one node and immediately publishes through a different node, it may briefly see stale routing state. The 4.3 everyday-operations guidance is explicit about this. Prefer static topology, sequence declare-then-use on the same node, or gate on an explicit readiness check rather than assuming instantaneous all-node visibility.

04 Boundary

Form clusters by peer discovery; clients still need their own endpoints

A production cluster should form itself with an automated peer-discovery mechanism — classic configuration, DNS, Kubernetes, AWS, Consul, or etcd. Manual rabbitmqctl join_cluster is documented as error-prone and is best kept for development, tests, or exceptional recovery. Since 4.1 you no longer stop and reset before joining; join_cluster performs the preparation. It remains destructive to the joining node’s pre-existing broker data, so never point it at a node you care about.

Two kinds of discovery are easy to conflate. Broker peer discovery forms the cluster out of blank nodes: a fresh node discovers peers and joins one cluster. But an existing member that restarts does not rediscover the cluster — it rejoins using its previously known peers. Application endpoint discovery is a separate concern entirely: clients still need a host list or a load balancer to find a node. Peer discovery never hands endpoints to your clients.

ini · rabbitmq.conf — automated peer discovery is preferred over manual join
# A blank node discovers peers and forms one cluster.
cluster_formation.peer_discovery_backend = dns
cluster_formation.dns.hostname = rabbitmq.internal.example
# An existing member that restarts rejoins using its known peers instead
# of rediscovering, so discovery races mainly affect first formation.

Finally, clustering assumes a LAN. Nodes exchange a great deal of low-latency traffic and are not meant to span a wide-area network. To link brokers across regions or data centres, use Federation or Shovel; those are asynchronous links between independent brokers, not an extension of one cluster’s consensus.

Production warning

join_cluster wipes the joining node’s data and identity. Automate formation for blank nodes, let restarted members rejoin on their own, and keep a real client endpoint list or load balancer — discovery does not do that for you.

05 Trade-off

Node operations, cookies, and one honest note about stale docs

Day-two operations are where the metadata/content split becomes muscle memory. Nodes authenticate to each other with a shared secret, the Erlang cookie, and are addressed by node name (rabbit@host); a cookie or name mismatch is the classic reason a node silently refuses to cluster. Stopping and starting a member is routine — on restart it rejoins from its known peers and catches its Raft groups up. A reset deletes local data and identity, which is exactly why joining is destructive.

Removing a node needs the most care. forget_cluster_node evicts a permanently gone node from the cluster, and in doing so it removes any quorum-queue and stream replicas that lived there. That can leave a queue with a temporarily even member count, so you must inspect membership and grow it back rather than assuming a replacement node automatically receives replicas. Adding a fresh RabbitMQ node does not move existing queue replicas onto it by itself.

bash · a cluster-mutating removal, with its precondition and proof
# Read-only first: see membership and reachability.
rabbitmqctl cluster_status

# Precondition: the target node is stopped and will NOT return.
# forget_cluster_node also drops quorum/stream replicas it hosted.
rabbitmqctl forget_cluster_node rabbit@old-node

# Prove the outcome, then repair replica counts if a queue is left even.
rabbitmqctl cluster_status
rabbitmq-queues quorum_status orders.work

Now the honest note the dossier insists on. Several 4.3 pages still carry pre-4.3 text: a metadata overview that mentions two backends, an enablement page that talks about starting on Mnesia, a feature-flags page describing khepri_db as optional. Those passages are stale carry-over. The tagged 4.3.0 release notes and the reworked partition guide are authoritative: in 4.3, Khepri is the only supported metadata store and Mnesia is gone. Do not teach Mnesia as selectable, or khepri_db as an operator choice, on a running 4.3 broker. The one place khepri_db still matters is the upgrade: a 4.2 cluster must enable all required feature flags, including khepri_db, before upgrading — a prerequisite, not evidence that 4.3 can run on Mnesia.

06 Build

Prove the definition is visible while the content stays with the members

The script makes the boundary executable. It declares a durable quorum queue on one connection, publishes a handful of persistent messages, then opens a second connection and re-declares the queue passively. A passive declare reads metadata only, so in a cluster it would succeed from any node that has seen the committed definition — that is the “every node sees the queue” guarantee. The asserts confirm the definition is visible and that the stored count equals what the members actually hold.

Metadata visibility checkpointPython 3 · Pika 1.3.2

Declare once, read the definition from a second connection

python · install pika==1.3.2 and run against localhost (or any cluster node)
import uuid

import pika

QUEUE = f"lab.l27.orders.{uuid.uuid4().hex[:10]}"
MESSAGE_COUNT = 5


def declare_orders(channel, name):
    # Immutable identity: a durable quorum queue. The DEFINITION is metadata,
    # so once the Khepri majority commits it, any node can see and route to it.
    channel.queue_declare(
        queue=name,
        durable=True,
        exclusive=False,
        auto_delete=False,
        arguments={"x-queue-type": "quorum"},
    )


publisher = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
channel = publisher.channel()
try:
    declare_orders(channel, QUEUE)

    # CONTENT: persistent messages are stored only on the quorum queue's
    # member nodes, never copied onto every node in the cluster.
    channel.confirm_delivery()
    for index in range(MESSAGE_COUNT):
        channel.basic_publish(
            exchange="",
            routing_key=QUEUE,
            body=f"order-{index}".encode(),
            properties=pika.BasicProperties(delivery_mode=2),
        )

    # A separate connection re-declares the queue PASSIVELY. A passive declare
    # reads metadata only, so in a cluster it succeeds from any node that has
    # already seen the committed definition.
    reader = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
    reader_channel = reader.channel()
    try:
        found = reader_channel.queue_declare(queue=QUEUE, passive=True)
        assert found.method.queue == QUEUE               # definition is visible metadata
        assert found.method.message_count == MESSAGE_COUNT  # members hold the content
        print({
            "definition_visible": True,
            "stored_messages": found.method.message_count,
        })
    finally:
        reader.close()
finally:
    channel.queue_delete(queue=QUEUE)
    publisher.close()

On a single dev node the assertions still hold, because the definition is local metadata and the content is on the one member. In a real cluster the passive declare would succeed against any node while the five bodies remain on the quorum members — which is precisely the point of the lesson.

Self-test

1. What does “every node sees every queue” actually guarantee?

That the queue’s definition is cluster-wide metadata, so you can list, bind, and publish from any node. It does not mean the queue’s message bodies are stored on every node — content lives only on the queue type’s member node(s).

2. In RabbitMQ 4.3, which metadata stores can an operator choose?

None to choose — Khepri is the only supported metadata store in 4.3 and Mnesia was removed. Khepri was the default for new 4.2 deployments; some 4.3 pages still carry stale two-backend text, which is carry-over, not current guidance.

3. Is there a “master node” that leads the cluster?

No. Nodes are equal broker peers. Khepri, every quorum queue, and every stream coordinator are independent Raft groups, each with its own leader. A queue leader is not a primary cluster node.

4. What happens to topology changes when the Khepri leader loses its majority?

They block and can time out; the minority cannot commit conflicting topology. Already-committed metadata can still be read from reachable nodes, and each quorum queue/stream has its own separate replica group.

5. Does broker peer discovery connect client applications?

No. Peer discovery forms the broker cluster from blank nodes; a restarted member rejoins via known peers. Clients still need their own endpoint list or a load balancer to reach a node.

6. Why is forget_cluster_node risky, and what must follow it?

It removes the node and any quorum-queue and stream replicas it hosted, potentially leaving an even member count. Afterward, inspect membership (quorum_status) and grow it back; a new node does not automatically receive replicas.
