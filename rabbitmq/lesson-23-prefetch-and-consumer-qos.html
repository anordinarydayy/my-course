23Consumers & throughput

Prefetch & Consumer QoS

Prefetch is the single dial that decides how much unacknowledged work a broker may push at one worker. Set too high it drowns a slow consumer and hoards a private backlog; set too low it can idle on round-trip latency. This lesson treats prefetch as a back-pressure and memory-safety control, then tunes it by measurement.

Original study chapter. The scenario, credit-window model, figures, code, and SVGs are original. Stable behavior targets open-source RabbitMQ 4.3 (latest signed patch overlay 4.3.3; public release and docs pages still showed 4.3.2 when researched); runnable code uses Python 3 and Pika 1.3.2. This chapter contains three original figures, two interactive. All rates are engineering estimates for teaching, never RabbitMQ guarantees.
00 Failure first

A worker that accepts everything eventually accepts too much

Picture a single worker subscribed to a busy queue with no quality-of-service configured and automatic acknowledgement switched on. The broker has nothing to hold it back, so it streams deliveries as fast as the socket drains. The client library buffers them in memory faster than the callback can process them. Latency for the oldest buffered message climbs, the process heap grows, and if that worker crashes every buffered, already-acknowledged message is gone. Nothing here is a RabbitMQ bug; it is the absence of a limit.

Now switch to manual acknowledgement but still request no prefetch limit. The unacknowledged messages are at least recoverable on failure, yet one worker can still pull a huge private slice of the queue into its own in-flight set while its neighbours sit idle. The queue looks drained from the broker’s side, but almost none of that work is actually complete. The missing control in both stories is consumer prefetch: a bound on how many deliveries a consumer may hold unacknowledged at once.

Prefetch invariant

With manual acknowledgement, prefetch is the maximum number of delivered-but-unacknowledged messages a consumer may hold. When that window is full the broker sends it nothing more until acknowledgements free space. Prefetch is therefore a safety limit and a fairness lever, not merely a speed setting.

01 Mechanism

basic.qos sets a window; RabbitMQ scopes it per consumer

A consumer asks for a window with basic.qos, supplying a prefetch_count. The AMQP 0-9-1 specification describes that count as something shared by a whole channel. RabbitMQ deliberately deviates: by default the count is non-global, applied separately to each consumer created afterward on that channel. Two consumers on one channel each with prefetch_count=10 can therefore hold up to ten unacknowledged deliveries each, not ten between them.

RabbitMQ also lets you set a second, channel-wide limit by requesting a global QoS. When both a per-consumer count and a channel-wide count exist, each consumer must stay under its own limit and all consumers together must stay under the channel limit. Enforcing that shared ceiling requires extra coordination between the channel and its queues, so it can be slower than the plain per-consumer window. Treat the shared limit as a deliberate choice, not a default.

Acknowledgement is what recycles credit. Every basic.ack (or a negative acknowledgement that removes the delivery) returns capacity to the window so the broker may push again. This makes delivery ack-paced: a healthy consumer that acknowledges promptly keeps its window turning over; a stalled consumer stops receiving new work automatically, without the broker having to detect that it is slow.

Interview framing

“In RabbitMQ, prefetch_count is per consumer by default, not per channel as the raw spec implies. That is the number to reason about when I size in-flight work. A channel-wide global limit exists too, but I only reach for it when I explicitly need to cap a whole channel’s in-flight set.”

02 Invariant

Watch the window fill and drain ▸

The window has one rule that never bends: outstanding unacknowledged deliveries for a consumer never exceed its effective prefetch. Delivery consumes credit; acknowledgement returns it. Step through a window of three below. Notice that the broker pauses deliveries the instant the window is full and resumes the moment an acknowledgement frees a slot — the consumer, not the broker’s guesswork, paces the flow.

The same window explains why a stuck message quietly throttles a worker. If a consumer holds three unacknowledged deliveries and blocks on the first, no acknowledgement arrives, no credit is freed, and it receives nothing further. The queue is not broken; the consumer has simply pinned its whole window. That is exactly why a small window plus prompt acknowledgement keeps work flowing to other consumers instead of stranding it in one.

03 Boundary

Zero is not infinity, and prefetch does not apply everywhere

Setting prefetch_count=0 requests no client-imposed limit. It does not promise unlimited delivery from every source. A source can still impose its own ceiling: a quorum queue caps a consumer’s prefetch at 2,000 to keep its Raft log from growing without bound, regardless of what the client asked for. So “zero” means “I set no limit,” not “the broker will hand me the entire queue.”

Prefetch is also queue-type sensitive. A channel-wide global QoS can be used with classic queues, but quorum queues and streams reject consumption on a channel that has global QoS enabled — their supported model is per-consumer prefetch only. Do not present a global, channel-wide limit as portable across every queue type; if you consume from quorum queues or streams, plan on per-consumer windows.

Finally, prefetch governs the push path only. It has no effect on basic.get, the polling API, even with manual acknowledgement — each poll fetches one message on request. And an automatic-acknowledgement consumer has no unacknowledged window at all, so there is nothing for prefetch to bound; the broker will push as fast as the connection allows. If you need back-pressure, you need manual acknowledgement and a push subscription.

Common trap

“I set prefetch=0 so the quorum queue will feed one greedy consumer everything.” It will not: the queue caps that consumer at 2,000. And “I lowered prefetch to protect my auto-ack consumer” does nothing — auto-ack has no window to protect. Match the control to the delivery mode and queue type.

04 Trade-off

Prefetch is tuned by measurement, not by a magic number ▸

A window of one minimises unacknowledged work, so almost nothing is redelivered on a crash — but it can substantially lower throughput, especially over a high-latency link, because the consumer waits a full delivery-and-acknowledge round trip between messages. Raising prefetch hides that round trip and lifts throughput until some other resource becomes the limit. Past that point extra prefetch buys nothing and costs more: higher client and broker memory exposure, and more work to redeliver if the consumer fails with a large window open.

RabbitMQ’s guidance offers 100–300 as a range that often performs well and notes diminishing returns above it, but it makes the choice explicitly workload-dependent. Treat 100–300 — and the example default_consumer_prefetch value of 250 — as starting candidates for a sweep, never as a correct value for every deployment. 05 Read the signals

The metrics that tell you the window is wrong

You do not tune prefetch by intuition; you read it off the broker and client together. A useful shortcut: for a single queue, total unacknowledged depth tends toward consumer_count × prefetch when consumers are keeping their windows full. If unacknowledged sits near that product while throughput is flat and memory and latency are rising as you raise prefetch, you have passed the point of diminishing returns and should stop raising it.

Conversely, if ready depth is climbing while consumer capacity (the metric formerly called consumer utilisation) sits well below 100%, the consumers are not the binding constraint: either there are too few of them, processing is slow, or the window is too small to hide delivery latency. The static map below pairs each symptom with the adjustment it actually justifies, so you change one thing deliberately rather than reflexively raising prefetch.

Consumer capacity is a helpful hint, but it is not a complete autoscaling signal on its own; pair it with application metrics such as end-to-end latency and downstream success rate. A window that looks perfect on a synthetic 12-byte auto-ack benchmark can behave very differently under real payloads, manual acknowledgement, and a durable quorum queue.

06 Build

Bound a consumer and prove the window holds

The runnable checkpoint declares a short-lived quorum queue, publishes a batch, sets an explicit per-consumer window with basic_qos(..., global_qos=False), and consumes with manual acknowledgement while tracking the maximum number of simultaneously in-flight deliveries. The assertion proves the invariant from section 02: the unacknowledged count never exceeds the configured prefetch. The lab resource is deleted in finally.

Bounded consumer checkpointPython 3 · Pika 1.3.2

Make the prefetch window observable

python · install pika==1.3.2 and run against localhost
import uuid

import pika

QUEUE = f"lab.qos.window.{uuid.uuid4().hex[:10]}"
PREFETCH = 3
TOTAL = 12


def main():
    params = pika.ConnectionParameters("localhost")
    connection = pika.BlockingConnection(params)
    channel = connection.channel()
    try:
        # Quorum queue: caps consumer prefetch at 2000 no matter what we request.
        channel.queue_declare(
            queue=QUEUE,
            durable=True,
            arguments={"x-queue-type": "quorum"},
        )
        channel.confirm_delivery()
        for index in range(TOTAL):
            channel.basic_publish(
                exchange="",
                routing_key=QUEUE,
                body=f"job-{index}".encode(),
                properties=pika.BasicProperties(delivery_mode=2),
            )

        # Non-global: the window is per consumer, RabbitMQ's default scope.
        channel.basic_qos(prefetch_count=PREFETCH, global_qos=False)

        in_flight = 0
        max_in_flight = 0
        handled = 0
        for method, _properties, _body in channel.consume(
            QUEUE, inactivity_timeout=5
        ):
            if method is None:
                break
            in_flight += 1
            max_in_flight = max(max_in_flight, in_flight)
            assert in_flight <= PREFETCH, "prefetch window was exceeded"
            channel.basic_ack(method.delivery_tag)  # frees exactly one credit
            in_flight -= 1
            handled += 1
            if handled >= TOTAL:
                break

        assert handled == TOTAL
        assert max_in_flight <= PREFETCH
        print({"queue": QUEUE, "prefetch": PREFETCH, "max_in_flight": max_in_flight})
    finally:
        channel.cancel()
        channel.queue_delete(queue=QUEUE)
        connection.close()


if __name__ == "__main__":
    main()

In production you would size PREFETCH from a sweep, not a constant, and you would run several consumers so the freed credit is offered to a neighbour rather than pulled back by the same worker. The assertion here is the point: whatever the number, the broker never lets a manual-ack consumer exceed its window.

Self-test

1. In RabbitMQ, is a default prefetch_count shared by the channel or applied per consumer?

Per consumer. RabbitMQ’s default QoS is non-global, so each consumer created afterward on the channel gets its own window; the spec’s channel-wide wording does not describe RabbitMQ’s default.

2. What does prefetch_count=0 actually request, and what still bounds it?

It requests no client-imposed limit. It is not infinite: a quorum queue caps a consumer’s prefetch at 2,000 to bound Raft-log growth, and other sources can impose their own ceilings.

3. Why does prefetch have no effect on a basic.get or auto-ack consumer?

basic.get fetches one message per poll on request, outside the push window. An auto-ack consumer has no unacknowledged window at all, so there is nothing for prefetch to bound.

4. Is a channel-wide global QoS portable across queue types?

No. It can be used with classic queues, but quorum queues and streams reject consumption on a channel with global QoS enabled. Their supported model is per-consumer prefetch.

5. Why can setting prefetch to 1 hurt throughput?

The consumer waits a full delivery-and-acknowledge round trip between messages. Over a high-latency link that idle time can substantially reduce throughput, even though it minimises unacknowledged work.

6. Is 250 (or 100–300) the correct prefetch to standardise on?

No. Those are starting candidates for a sweep. The right value is workload-dependent; raising prefetch past the throughput plateau only adds memory and redelivery exposure.
