Observability: Management UI, Prometheus & Grafana

The management UI and Prometheus are not competing dashboards — they are two different jobs. One is an operator console you look at; the other is a durable, per-node metrics feed you query and alert on. Confusing their roles is how teams end up either staring at a browser tab at 3 a.m. or drowning in unfiltered per-object cardinality they never asked for.

Original study chapter. The scenarios, diagrams, and code are written from scratch. Stable behavior targets open-source RabbitMQ 4.3, with the signed 4.3.3 maintenance release as the current patch overlay (public docs pages observed at 4.3.2 as of the 2026-07-21 access date). This chapter contains three original figures, two interactive.
00 Failure first

“The dashboard looked fine”

A team keeps the RabbitMQ management UI open in a browser tab as their monitoring strategy. Queue depth looks calm, so nobody worries — until a node goes unreachable during an incident and the UI, which fans a cluster-wide query out to every node, hangs waiting on the one node that cannot answer. The team has no history to look back at, because the management plugin’s statistics are a recent window, not a retained time series. They are debugging blind at the exact moment they need vision most.

The second failure is the opposite instinct: a team enables Prometheus, points Grafana at the official dashboards, and treats every default threshold as a verdict. A high unacknowledged-message count fires an alert — except with many consumers and a generous prefetch, a large unacked count is completely normal. The dashboard is not wrong; the assumption that its thresholds are a universal SLO is.

Both mistakes come from the same root: treating “observability” as one tool instead of a set of roles that need to be assigned deliberately. This lesson assigns them.

The core distinction

The management plugin is an operator interface for topology, users, and recent statistics — not a durable metrics store. Prometheus is the recommended production metrics path: it scrapes node-local data, and cluster-wide aggregation and retention happen outside the broker, which is exactly why it still works when a node does not.

01 Roles

Two tools, two jobs ▸

The management plugin gives you the browser UI, the HTTP API, topology and user controls, and a window of recent statistics. Its statistics collector runs on broker CPU and memory, and a cluster-wide query through it can sit waiting on a slow or unreachable peer — it is built for a human looking things up, not for unattended alerting.

rabbitmq_prometheus is RabbitMQ’s documented production metrics path. Each node serves its own node-local /metrics endpoint; Prometheus scrapes every node and performs cluster-wide aggregation itself, outside the broker. That separation is the whole point — retention and alerting are decoupled from the system being monitored, so a scrape still succeeds when one node is struggling.

bash · enable both roles; keep the metrics endpoint off the public network
rabbitmq-plugins enable rabbitmq_prometheus
rabbitmq-plugins enable rabbitmq_management

# RABBITMQ_METRICS_URL should point at an internal, ideally TLS, endpoint.
curl -fsS "${RABBITMQ_METRICS_URL}/metrics" | head

Prometheus listens on 15692 at /metrics by default; management commonly uses 15672. The metrics endpoint can be unauthenticated unless you configure it, so bind or firewall it to a monitoring network, or enable authentication and TLS — never leave it open on a public interface, and never put credentials in shell history.

ini · rabbitmq.conf — minimal endpoint configuration
prometheus.tcp.port = 15692
prometheus.authentication.enabled = true
management.tcp.port = 15672

If Prometheus becomes your exclusive metrics system, you can trim the management plugin’s own collection overhead without losing the UI or the HTTP API:

ini · optional — only once Prometheus is the system of record
management_agent.disable_metrics_collector = true

That hides charts and detailed statistics from the management UI and API; it does not disable the Prometheus plugin. Do not flip it just because Prometheus exists — validate that no operator workflow still depends on the UI’s own charts first.

02 Trade-off

Cardinality is a choice, not a default

RabbitMQ’s Prometheus plugin exposes several endpoints, and picking the wrong one is the most common way to overload a large cluster’s own monitoring. The base /metrics endpoint aggregates by metric name on a single node with no per-queue or per-connection label — cheap, and the right baseline scrape for every node. The per-object and detailed endpoints trade that cheapness for identity, and the cost scales with how many queues, connections, and channels exist.

EndpointSemanticsOperational useQualification
/metricsAggregated by metric name, one node, no per-object labelsLow-overhead baseline scrape from every nodeAggregation loses object identity; don’t re-sum a metric that is already cluster-wide
/metrics/per-objectEvery available object/metric pairShort-lived investigation on small environmentsPayload and serialization cost grows with object count; avoid routine scraping at high cardinality
/metrics/detailedOnly requested families, optional vhost and queue-regex filtersPreferred targeted per-object scrapeAn unfiltered or overbroad query is still expensive; quote the URL because & is a shell control character
/metrics/memory-breakdownIterates runtime processes and groups memory useInfrequent diagnosis onlyExpensive with tens of thousands of queues/connections; test before scraping on any schedule
bash · a targeted, filtered scrape instead of an unfiltered per-object dump
curl -fsS \
  "${RABBITMQ_METRICS_URL}/metrics/detailed?family=queue_coarse_metrics&family=queue_consumer_count"

Add vhost= and an anchored queue= regular expression wherever you can. Default aggregation is the safer baseline for a large cluster; per-object detail should be justified by a specific alert or drill-down, never enabled reflexively as if more data were automatically better.

03 Framework

A golden-signal lens for RabbitMQ metrics ▸

“Golden signals” is a course-level organizing lens, not a term RabbitMQ’s own documentation defines — say that plainly so nobody mistakes it for canonical vocabulary. It is simply a useful way to group the metrics RabbitMQ already exposes: traffic, saturation, errors, and latency.

SignalBroker / application evidenceInterpretation constraint
TrafficPublish, deliver/get, ack and confirm rates; bytes in/out; connection and channel opensCompare rates and their slopes — publish rate alone says nothing about routing success or consumer progress
Saturation / backlogmessages_ready, messages_unacked, consumer capacity; memory/disk headroom; alarms; CPU, disk I/O, inter-node linksQueue depth alone is not health. Growing ready messages with publish > ack is backlog; a large unacked count can just mean generous prefetch
Errors / availabilityUnroutable/dropped messages, redeliveries and nacks, auth failures, connection churn, unavailable queues, alarms and restartsA zero error counter can mean the metric was never collected — alert on rates over a meaningful window, not raw zero/nonzero
LatencyApplication end-to-end and processing latency, confirm latency, queue age if the app timestamps messagesRabbitMQ has no universal message-latency gauge. Queue depth is not latency — instrument publishers and consumers for the SLO you actually care about

RabbitMQ’s own alerting write-up gives concrete examples along these lines — no-quorum-majority, unroutable-message, connection-churn, predicted-disk, file-descriptor, socket, and restart alerts — but those are examples of the kind of thing to watch, not a complete alert policy you can paste in unmodified.

04 Tuning

Scrape interval and the rate() trap

RabbitMQ’s own guidance spans a 15–30 second Prometheus scrape interval, inside a broader 30–60 second production monitoring range. Five seconds is a development convenience, not a production default — teach it as such. Pick one interval, load-test it against your cluster size, and hold it steady.

The trap is in Grafana, not RabbitMQ: a rate() window shorter than a few scrape intervals turns one missed scrape into a visible cliff that looks like an incident. Set rate() ranges to at least four times your scrape interval so a single dropped scrape does not manufacture a false signal.

Dashboard thresholds are not universal

Team RabbitMQ’s Grafana dashboards are a starting point. Their thresholds and node-colour conventions assume a shape of workload — connection count, prefetch, queue types — that may not match yours. Review every threshold against your own deployment before you let it page anyone.

05 Build

Diagnose without Prometheus, then confirm with it

Before any dashboard exists, rabbitmq-diagnostics and rabbitmqctl give you a snapshot. These are not a substitute for scraping — they are what you run interactively during an incident, or to sanity-check what Prometheus is telling you.

Snapshot diagnosis before reaching for a dashboardshell

Correlate alarms, memory, and queue backlog by hand

shell · set VHOST first; these are point-in-time snapshots
# Cluster-wide alarm state — a fired alarm changes what "blocked" means below.
rabbitmq-diagnostics -q alarms

# Per-node memory breakdown in a readable unit.
rabbitmq-diagnostics -q memory_breakdown --unit MB

# Connection-level flow/blocking state — cheap, node-scoped.
rabbitmqctl list_connections name state

# Backlog signal: rising "ready" with flat "consumers" is the saturation
# read to act on; a nonzero "unacknowledged" alone is not evidence of trouble.
rabbitmqctl list_queues -p "$VHOST" \
  name messages_ready messages_unacknowledged consumers

Wide list_* commands can be costly against a very large cluster — use them for a focused check, not as a polling loop standing in for Prometheus. Once you have a hypothesis from this snapshot, confirm it with the same signal in Grafana over time, which is the only way to see whether it is a trend or a blip.

Self-test

1. Why can a management-UI query hang during an incident when Prometheus would not?

The management API fans a cluster-wide query out to every node and can wait on a slow or unreachable one. Prometheus scrapes each node's own /metrics endpoint independently and aggregates outside the broker, so one struggling node does not block the others.

2. Which endpoint should be the default scrape target on every node, and why?

/metrics — it aggregates by metric name with no per-object labels, so its cost does not grow with the number of queues or connections. Per-object and detailed endpoints trade that cheapness for identity and should be used deliberately, not routinely.

3. Is "golden signals" RabbitMQ's own terminology?

No — it is a course-level organizing lens for grouping metrics RabbitMQ already documents (traffic, saturation, errors, latency), not a term defined in RabbitMQ's own documentation.

4. Does RabbitMQ expose a universal end-to-end message-latency metric?

No. There is no broker-wide latency gauge; queue depth is not latency. Application-level SLOs need publishers and consumers to instrument their own timestamps.

5. Why should a Grafana rate() window be at least four scrape intervals wide?

A narrower window turns a single missed scrape into a visible cliff that looks like an incident. Widening it relative to the scrape interval absorbs one missed scrape without a false signal.

6. Is a large messages_unacknowledged count always a problem?

No. It can simply reflect a generous prefetch value across many consumers. Read it together with messages_ready trend and consumer capacity before treating it as an incident.
