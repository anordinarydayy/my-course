Queue Types: Classic vs Quorum vs Streams

A queue type is not a performance tier selected after deployment. It fixes the access pattern, replication boundary, lifetime rules, and failure modes of the data structure. Start with “work or replay?” and “which failures must be tolerated?”—then choose classic, quorum, or stream.

Original study chapter. The prose, scenarios, decision tables, code, and SVGs are original. Stable behavior targets open-source RabbitMQ 4.3; the worked client uses Pika 1.3.2. This chapter contains three original figures, two interactive. “Default” below distinguishes the product fallback from an engineering recommendation.
00 Failure first

Choosing by name hides the real data contract

A team sees “quorum” and assumes it is a safer drop-in upgrade for every queue. Another sees “stream” and assumes it is merely a faster queue. Both designs fail because the queue type changes semantics. A temporary reply inbox cannot be a quorum queue; a replaying analytics reader does not fit a destructive work queue; a classic queue cannot fail over its message contents to another node.

Ask two questions first. Read semantics: should one worker acknowledge and remove each item, or should independent readers revisit retained history? Failure domain: is losing the hosting node acceptable, or must a majority-replicated data structure continue after one member fails? Type then becomes a consequence of the contract rather than a fashionable default.

In the AMQP 0-9-1 work-queue model used here for classic and quorum queues, a delivery acknowledgement settles processing progress and lets RabbitMQ remove that delivery. A reader using the Stream protocol has a different state machine: consumer credit controls delivery flow, while offset tracking or checkpointing records where that reader should resume without deleting retained records. Credit is not a queue acknowledgement, and an offset checkpoint is not destructive consumption.

Selection invariant

Classic and quorum are competing-consumer work queues; stream is a retained append-only log. Classic has one content replica, while quorum and stream replicate. Publisher evidence, capacity planning, and current supported patches remain necessary, but downstream progress uses AMQP 0-9-1 delivery acknowledgements for work queues and Stream credit plus offset tracking for Stream-protocol readers.

01 Defaults

RabbitMQ’s fallback is classic; your requirement may say quorum ▸

If an AMQP 0-9-1 declaration omits x-queue-type, RabbitMQ applies the effective default queue type. In an uncustomized 4.3 installation, the built-in fallback is classic. An operator can set a node-wide default and a virtual-host default; the vhost value takes precedence. A changed default affects future declarations only because queue type is immutable.

That product default is separate from RabbitMQ’s design guidance: when a long-lived work queue needs replicated data and high availability, quorum is the normal candidate. “Quorum is the default for important work” is a recommendation, not a claim that an omitted argument creates a quorum queue. Applications whose intent must be environment-independent should declare the type explicitly.

Interview follow-up

What queue type does RabbitMQ 4.3 create by default? The effective default queue type; without operator or vhost override, its built-in fallback is classic. Quorum is the usual recommendation when replicated work-queue safety is required, not the unconfigured product default.

02 Single-replica work

Classic is supported, versatile, and deliberately non-replicated

A classic queue is a destructive work queue whose contents live on one node. It is the natural fit for exclusive server-named reply queues, temporary topology, high-churn queues, or work whose loss with the hosting node is an accepted trade-off. It supports familiar features such as priorities, TTL, length limits, policies, and exclusive lifetime.

Durable classic topology plus persistent messages can recover after that hosting node restarts if its durable storage survives. That is not replica failover and not protection from permanent loss of the node’s disk. Classic queue mirroring was removed in RabbitMQ 4.0; a 4.3 ha-mode policy cannot restore it.

Classic in 4.3 also does not mean “RAM queue.” CQv1 is removed, CQv2 is the storage implementation, and modern classic queues move message data to disk while retaining a working set in memory. Declarations using x-queue-version=1 or any old x-queue-mode fail; the former lazy-queue switch is not a current design choice.

Production warning

A durable classic queue is durable metadata around one content replica. If node-level data loss is outside the budget, select a replicated type instead of describing restart recovery as high availability.

03 Replicated work

Quorum trades flexibility and latency for a Raft majority boundary ▸

A quorum queue is always durable and replicates queue state and source messages. A new queue normally starts with up to three members, one per node, subject to cluster size and configuration. One member is leader; a majority must be available to make progress. Three members tolerate one unavailable member. Two members still need both for a majority, so “two replicas” does not buy one-node fault tolerance.

The source message is persisted regardless of AMQP 0-9-1 delivery_mode. In confirm mode, RabbitMQ acknowledges a quorum-queue publish after the quorum consensus boundary documented for safe acceptance. That boundary is stronger than merely writing bytes to one socket, but it is conditional: the publisher must wait for and handle confirms, a majority must remain, storage must be durable, and permanently losing a majority is outside the guarantee.

Quorum is best for long-lived correctness-critical work with manual acknowledgements. It cannot be exclusive or server-named temporary topology. RabbitMQ cautions against using it blindly for lowest latency, high queue churn, very large backlogs, broad fan-out, or applications that ignore confirms and acknowledgements. Streams or classic queues can be better.

04 Retained history

A stream keeps an append-only log for offsets and replay

Consuming a stream does not delete the message. Retention removes old segments according to age or byte rules, while independent readers attach at offsets or timestamps and replay at their own pace. This makes streams the primary candidate for many readers, replay, very large retained backlogs, and high-throughput log use—especially through the RabbitMQ Stream protocol.

Streams are always durable and replicated, and cannot be exclusive. Traditional queue TTL, priority, dead-letter exchange, destructive acknowledgement, and ready-length overflow semantics do not describe them. Their size and age controls are segment-based retention, so the retained amount is approximate at segment boundaries.

“Persistent and replicated” still does not make stream and quorum safety boundaries identical. Stream confirms wait for quorum replication, but the stream documentation says replicas do not explicitly fsync before confirming and rely on operating-system page-cache flushing. If the requirement is RabbitMQ’s strongest documented confirmed-write boundary for work, quorum—not stream—is the relevant candidate.

A queue replica’s hot path is also limited to one CPU core. A one-queue benchmark does not establish cluster throughput. Partition load across multiple queues or streams when the model needs parallelism, and benchmark payload sizes, confirms, acknowledgements, queue counts, storage, and injected failures.

Interviewer asks next

“Why not always choose quorum?” Because replication does not create replay, temporary lifetime, minimum latency, or unlimited backlog scale. Choose quorum when majority-backed destructive work is the invariant; choose a different data structure when the invariant differs.

06 Worked scenario

Declare all three types and make intent independent of defaults

This isolated lab explicitly declares one temporary classic queue, one durable quorum queue, and one durable stream. It proves the declaration constraints rather than pretending the three types are interchangeable consumers. The random names avoid collisions; the durable resources are deleted at the end.

Complete runnable declaration probePython 3 · Pika 1.3.2 · RabbitMQ 4.3

Put type intent in the declaration

python · install pika==1.3.2 and run against localhost
import uuid

import pika

suffix = uuid.uuid4().hex[:10]
quorum_name = f"lab.qtype.quorum.{suffix}"
stream_name = f"lab.qtype.stream.{suffix}"

connection = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
channel = connection.channel()
try:
    classic_name = channel.queue_declare(
        queue="",
        exclusive=True,
        auto_delete=True,
        arguments={"x-queue-type": "classic"},
    ).method.queue

    channel.queue_declare(
        queue=quorum_name,
        durable=True,
        exclusive=False,
        auto_delete=False,
        arguments={"x-queue-type": "quorum"},
    )
    channel.queue_declare(
        queue=stream_name,
        durable=True,
        exclusive=False,
        auto_delete=False,
        arguments={
            "x-queue-type": "stream",
            "x-max-length-bytes": 20_000_000,
        },
    )

    print(
        {
            "classic": classic_name,
            "quorum": quorum_name,
            "stream": stream_name,
        }
    )
finally:
    # The exclusive classic queue disappears with the connection.
    channel.queue_delete(queue=quorum_name)
    channel.queue_delete(queue=stream_name)
    connection.close()

The classic queue can be server-named and exclusive. Quorum and stream declarations are named, durable, and non-exclusive. The stream byte value is an illustrative lab retention argument—not a capacity recommendation. In production, prefer policies for supported mutable retention and guardrail settings; queue type itself remains declaration-time identity.

Self-test

1. What does RabbitMQ 4.3 create when x-queue-type is omitted?

It uses the effective default queue type. The built-in fallback is classic, but node and vhost configuration can override it, with the vhost value taking precedence.

2. Why is a durable classic queue not highly available message storage?

Its contents have one replica. Durable metadata and persistent messages support restart recovery when that node’s storage survives, not failover after permanent node-data loss.

3. How many unavailable members can a three-member quorum queue tolerate?

One. Two available members remain a majority; one available member cannot make progress.

4. Why can’t an exclusive server-named queue be quorum?

Quorum queues are durable, named, replicated entities and do not support exclusive or server-named temporary lifetime.

5. What semantic difference makes stream suitable for replay?

Consumption is non-destructive. Messages remain until segment retention removes them, and readers attach by offset or time.

6. Are quorum and stream confirms identical durability boundaries?

No. Both involve quorum replication, but stream replicas do not explicitly fsync before confirm; quorum documents the stronger confirmed-write boundary for queue work.
