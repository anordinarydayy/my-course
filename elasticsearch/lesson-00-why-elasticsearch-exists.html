00Concept · Core · Elasticsearch

Why Elasticsearch Exists

Your relational database handles transactions effortlessly — until users type two messy words into a search bar, expect ranked results and facet counts in thirty milliseconds, and a LIKE '%...%' query scans every row on disk. Elasticsearch exists for that moment. Built on Apache Lucene, it flips how data is indexed so search, analytics, and modern vector retrieval run in milliseconds — while asking you to respect what it is not.

Original study chapter. Written from scratch for backend, search, and platform interviews — and for the systems behind them. Behavior and examples target stable Elasticsearch 9.5 (built on Apache Lucene 10, tracking the 8.x → 9.x line as of late 2026); runnable code uses Python 3 and the official elasticsearch client (9.x). 00 The failure

The search wall: why SQL LIKE and B-trees break

Start with how search usually fails in production. An application keeps its product catalog or support tickets in PostgreSQL, adds a search box, and ships the obvious query: WHERE description LIKE '%timeout%'. On ten thousand rows in staging it returns in 4 milliseconds. Six months later, at fifty million rows, every keystroke locks CPU cores and stalls checkout traffic.

A standard database B-tree index cannot rescue that query. A B-tree sorts column values alphabetically from the first character left to right. If you ask for a prefix like LIKE 'time%', the engine jumps straight to the T range in O(log N). Put a wildcard at the front ('%timeout%'), and the prefix is unknown: the target word could appear at offset 0, offset 42, or offset 900. The B-tree has no entry point, so the planner falls back to a sequential scan — reading every row and checking every substring one by one.

And raw substring matching is only the first wall. Real search breaks a relational query on three more fronts at once:

  • Language mismatch — searching timeout misses "timeouts", "timed out", or a one-letter typo. Substring matching has no tokenization, stemming, synonyms, or fuzziness.
  • No notion of relevance — SQL LIKE is boolean: a row matches or it does not. A search user expects the document where "timeout" appears in the title three times to outrank one where it appears once in a footnote, weighted by how rare the word is across the corpus.
  • Faceted analytics at the same time — search pages do not just return ten hits; they compute live counts by category, brand, and price bucket across millions of matches, or combine keyword rules with semantic meaning.
Wait — can't Postgres full-text search do this?

Often, yes! PostgreSQL ships built-in tsvector / GIN indexes and pg_trgm trigram indexes, and if your dataset fits comfortably on one Postgres node and mainly needs basic text search joined cleanly against relational tables, keeping it in Postgres avoids a second datastore entirely. Elasticsearch earns its keep when search becomes a primary workload: multi-terabyte or multi-billion-document scale across shards, sub-second multi-level aggregations, tunable BM25 ranking combined with dense/sparse vectors (hybrid search), or high-ingest log and telemetry streams.

01 The mechanism

Flipping the index: document→words to word→documents ▸

Relational tables are organized around rows: given row ID 42, here is all the text inside it (a forward index). Finding which rows contain a word forces you to open rows and look inside them. Elasticsearch, via its underlying Apache Lucene engine, pays a modest cost at write time to invert that map completely.

When a JSON document arrives, Elasticsearch runs its text fields through an analyzer: breaking sentences into tokens, normalizing case, and optionally stemming words (so "timeouts" indexes under timeout). It records each unique token once in a sorted term dictionary and attaches a postings list — the sorted document IDs (plus frequencies and positions) containing that term. Looking up "timeout" no longer touches unrelated rows; the engine jumps directly to one dictionary entry, reads its postings list, and scores matches with BM25 (Okapi BM25).

The core invariant: front-load work at write time

Every search-engine trade-off starts right here. Elasticsearch does more work on write — running analyzers, building inverted postings lists, writing columnar doc values for sorting and aggregations, and optionally building HNSW vector graphs — so that reads stay proportional to the matching postings, not the size of the whole table. That extra write work and disk/memory footprint is the price you pay for sub-second search and analytics.

02 One engine, three jobs

Search, observability, security — the Search AI Platform

People meet Elasticsearch as the engine behind a product search bar, then are surprised to find the exact same engine running company-wide log analytics and security detection. That convergence is not marketing accident; all three workloads stress the exact same three primitives inside Lucene:

  • Search & GenAI — full-text inverted indexes, BM25 ranking, typo tolerance, exact keyword filters, and dense / sparse vector search (dense_vector over HNSW with quantization like Better Binary Quantization, plus sparse models like ELSER) to power hybrid retrieval and Retrieval-Augmented Generation (RAG).
  • Observability — ingesting massive append-only streams of application logs, metrics, and OpenTelemetry traces; filtering by service/status in milliseconds; and slicing billions of events by time histogram via columnar doc values and modern logsdb / Columnar Mode storage.
  • Security — SIEM, endpoint detection, and threat hunting across high-cardinality telemetry where an analyst correlates IP addresses, process hashes, and alert rules in real time using Query DSL, Event Query Language (EQL), or piped ES|QL.

That is why Elastic frames Elasticsearch 8.x and 9.x as a Search AI Platform: instead of wiring a separate keyword engine, a separate log store, and a separate vector database together with brittle glue code, one distributed engine handles lexical matching, structured aggregations, and semantic vector retrieval inside a single query plan.

What the interviewer probes next

“If embeddings capture meaning, why not replace Elasticsearch with a pure vector database?” Because real queries almost always carry hard constraints alongside semantics: exact product SKUs, error codes like ECONNRESET, tenant permissions, date ranges, and live facet counts. Pure vector similarity scores everything smoothly — even documents that violate an exact filter or miss a literal identifier. Combining lexical BM25, structured filters, and vectors in one pass (hybrid search) beats either alone.

03 The boundary

Why Elasticsearch is not your system of record ▸

Here is the trap that costs teams real data: someone builds a fast prototype storing orders or user accounts straight in Elasticsearch and skips the relational database. It works right up until concurrent updates collide, a bulk write fails halfway through, or a user saves a profile and refreshes the page 100 ms later only to see the old value.

Be precise about the boundary. For append-only telemetry like logs and metrics, Elasticsearch routinely is the primary store. For mutable, multi-entity business state (orders, balances, inventory), Elasticsearch is a derived search and analytics engine paired behind an authoritative system of record (like PostgreSQL). Four concrete mechanics enforce that line:

  • Single-document atomicity only — indexing or updating one JSON document is atomic, and Elasticsearch protects concurrent updates to that single document with optimistic concurrency control (_seq_no and _primary_term). There are no multi-document ACID transactions: a bulk call spanning ten documents can commit seven and reject three, with no rollback across them.
  • Near-real-time (NRT) visibility — newly indexed documents sit in an in-memory buffer (backed by a translog for durability) and become searchable only after a periodic refresh opens a new Lucene segment — by default every 1 second on indices actively receiving search requests. A write is not instantaneously visible to searches unless you explicitly ask to wait (?refresh=wait_for) or force a costly immediate refresh.
  • Denormalized documents, not relational joins — distributed search scales by embedding related attributes inside each JSON document rather than running arbitrary foreign-key joins across nodes at read time.
  • Reindex on schema evolution — changing how an existing field is analyzed or typed generally requires building a new index and reindexing from the authoritative source.

04 Judgment

Where Elasticsearch fits — and when to skip it

The mark of an experienced engineer is knowing when not to add another distributed cluster. Running Elasticsearch means owning shard counts, JVM memory + OS filesystem cache sizing, mappings, and an ingestion pipeline from your source of truth. Never pay that operational tax when a simpler tool already solves the problem.

Reach for Elasticsearch when

  • Users search natural language with typos, synonyms, multi-field boosts, and live facet counts.
  • You combine keyword precision + semantic vectors (hybrid search / RAG) with document-level security.
  • You ingest high-volume time-series logs, metrics, or traces and slice them with sub-second aggregations.

Skip Elasticsearch when

  • Queries only look up exact primary keys or prefixes like user_id = 42 or email LIKE 'ada%'.
  • You require multi-row ACID transactions, foreign-key constraints, and normalized joins.
  • A single Postgres table with tsvector or pg_trgm already answers your search SLA in <20 ms.
05 Worked example

First taste: inverted search & concurrency boundaries

Put the whole lesson in runnable code. The script below uses the official elasticsearch Python client (9.x line, targeting Elasticsearch 9.5) to create a small catalog index, insert JSON documents with refresh="wait_for", run a bool query that scores analyzed full-text matches (match) inside a non-scoring structured filter, and then trigger Optimistic Concurrency Control (ConflictError) to prove single-document safety without multi-document transactions.

Worked build Derived catalog index Elasticsearch 9.5 · elasticsearch==9.5.1
Search vs. SQL LIKE, NRT visibility, and single-doc OCC

Index three catalog items (where the user query is "mechanical keyboard", one title uses the plural "keyboards", and a strict budget requires price ≤ 150). Return ranked hits, then reject a stale concurrent update using _seq_no and _primary_term.

Think it through

1 · Mapping

Store sku as keyword (exact match, no tokenization) and title as text (analyzed into inverted-index tokens).

2 · NRT visibility

Pass refresh="wait_for" on the final index call so the write waits for the periodic refresh before searching, without forcing an expensive immediate segment flush on every write.

3 · Query vs filter

Put match in must (computes BM25 _score) and range in filter (exact yes/no gate, cache-eligible, no score distortion).

4 · Single-doc OCC

Pass if_seq_no and if_primary_term on an update; a concurrent edit bumps _seq_no and forces a safe 409 ConflictError.

The code

python 3 · pip install elasticsearch==9.5.1 · local node on http://localhost:9200

import uuid
from elasticsearch import Elasticsearch, ConflictError

# Local dev node (ES 8+/9+ defaults to HTTPS + auth in production setups)
client = Elasticsearch("http://localhost:9200")
INDEX = f"lab-catalog-{uuid.uuid4().hex[:8]}"

try:
    client.indices.create(
        index=INDEX,
        mappings={
            "properties": {
                "sku": {"type": "keyword"},     # exact ID: never split into words
                "title": {"type": "text"},      # analyzed into the inverted index
                "price": {"type": "float"},
            }
        },
    )

    docs = [
        ("1", {"sku": "KB-75", "title": "Compact mechanical keyboard 75%", "price": 129.0}),
        ("2", {"sku": "KB-PRO", "title": "Custom mechanical keyboards kit", "price": 240.0}),
        ("3", {"sku": "MS-10", "title": "Ergonomic wireless mouse", "price": 79.0}),
    ]
    for i, (doc_id, body) in enumerate(docs):
        wait = "wait_for" if i == len(docs) - 1 else "false"
        client.index(index=INDEX, id=doc_id, document=body, refresh=wait)

    # Query context scores text relevance; filter context gates price without scoring
    resp = client.search(
        index=INDEX,
        query={
            "bool": {
                "must": [{"match": {"title": "mechanical keyboard"}}],
                "filter": [{"range": {"price": {"lte": 150}}}],
            }
        },
    )
    hits = resp["hits"]["hits"]
    assert [h["_id"] for h in hits] == ["1"]  # doc 2 filtered by price; doc 3 misses text

    # Optimistic Concurrency Control: capture _seq_no & _primary_term, then race
    cur = client.get(index=INDEX, id="1")
    stale_seq, stale_term = cur["_seq_no"], cur["_primary_term"]

    # Winner updates price cleanly
    client.index(
        index=INDEX, id="1",
        document={**cur["_source"], "price": 119.0},
        if_seq_no=stale_seq, if_primary_term=stale_term,
    )

    # Stale writer using the old _seq_no is rejected with HTTP 409 ConflictError
    conflict_caught = False
    try:
        client.index(
            index=INDEX, id="1",
            document={**cur["_source"], "price": 99.0},
            if_seq_no=stale_seq, if_primary_term=stale_term,
        )
    except ConflictError:
        conflict_caught = True

    assert conflict_caught
    print({"matched_id": hits[0]["_id"], "score": round(hits[0]["_score"], 3), "occ_protected": conflict_caught})
finally:
    client.indices.delete(index=INDEX, ignore_unavailable=True)
Explain it aloud in an interview

“I keep Postgres as the system of record for catalog mutations and treat Elasticsearch as a derived search read model. Writes invert text at index time so queries like mechanical keyboard jump straight to postings lists instead of scanning rows with LIKE '%...%', while numeric constraints go in a non-scoring filter. Because Elasticsearch only gives single-document atomicity — protected here with _seq_no and _primary_term — and near-real-time 1-second refresh visibility, multi-entity commits still belong in the relational database and sync asynchronously via CDC or an outbox.”

Follow-ups to anticipate: why sku uses keyword instead of text (so hyphens aren't split), why refresh=true on every write hurts throughput (creates tiny segments constantly), and how you handle an out-of-order CDC retry (pass the upstream version or external versioning so stale events don't overwrite newer state).

Self-test

1. Why does a relational B-tree speed up LIKE 'err%' but fail on LIKE '%err%'?

A B-tree sorts strings strictly from the first character left-to-right. A trailing wildcard narrows a contiguous prefix range in O(log N), whereas a leading wildcard leaves the prefix unknown, forcing an O(N) sequential scan over every row’s string.

2. What fundamental trade-off does an inverted index make?

It moves CPU and storage work to write time (analyzing fields, maintaining sorted term dictionaries, postings lists, and doc values) so query time looks up terms directly and intersects postings lists in proportion to matches rather than total rows.

3. When is PostgreSQL full-text search enough without adding Elasticsearch?

When the corpus fits comfortably on your existing Postgres node, queries mainly need modest text matching joined against relational tables, and you do not yet need horizontal sharding, sub-second multi-level aggregations, or combined BM25 + vector hybrid retrieval.

4. Why do Search, Observability, and Security all run on the same Elasticsearch engine?

All three need fast arbitrary filtering (inverted index), fast grouping/time-bucket math (columnar doc values / Columnar Mode), and increasingly vector similarity + piped analytics (ES|QL) at multi-terabyte scale.

5. Name two concrete reasons Elasticsearch is not a drop-in relational system of record.

First, operations are atomic at the single-document level only — there are no multi-document ACID transactions or cross-document rollbacks. Second, newly indexed documents follow near-real-time visibility (~1 second default refresh_interval when searched) rather than immediate transactional read-your-own-writes.

6. Why is hybrid search often stronger than a pure vector database in production?

Embeddings capture semantic intent but blur exact tokens. Production queries frequently depend on literal product codes, error strings, tenant RBAC filters, date ranges, and faceted counts alongside semantic similarity — which hybrid retrieval executes together.
