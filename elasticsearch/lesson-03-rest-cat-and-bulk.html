03Concept · Phase 0 · Elasticsearch

Talking to the Cluster: REST, _cat & Bulk

Lessons 01 and 02 introduced port 9200, the coordinating node, and single-document CRUD. In real systems, nobody loads a million products one HTTP request at a time, and nobody reads a raw JSON cluster-state dump with their eyes during an incident. This chapter closes Phase Zero with the three interfaces you use every day: the REST conventions and query flags, the _cat tabular endpoints for operators, the _bulk NDJSON endpoint for throughput, and Kibana Dev Tools Console to drive them fast.

Original study chapter. Written from scratch for backend, search, and platform interviews — and for everyday cluster operations. Behavior and defaults target stable Elasticsearch 9.5 (Apache Lucene 10, tracking the 8.x → 9.x line; latest 9.5.6 patch); code examples show raw HTTP / Dev Tools Console syntax, curl, and Python 3 with elasticsearch==9.5.1 (elasticsearch.helpers). 00 The failure first

An HTTP 200 that silently dropped writes, and a monitor broken by whitespace

Start with two bugs that happen in almost every team’s first Elasticsearch integration.

First, an ingestion service tries to load 50,000 catalog items by running PUT /catalog/_doc/{id} in a loop. Every document pays a separate TCP/TLS round trip, JSON decode, and shard dispatch, taking minutes instead of seconds. The engineer switches to POST /_bulk, checks if resp.status_code == 200:, and marks the batch done. Weeks later, search is missing hundreds of products. Why? Because _bulk is not a transaction: it returns HTTP 200 OK even when half the documents in the batch failed with 400 mapper_parsing_exception or 429 es_rejected_execution_exception. Those errors sit inside items[] behind "errors": true, and code that checks only the outer status drops them silently.

Second, a cron alert runs curl /_cat/indices and splits columns with awk to track document counts, while another dashboard call pulls full multi-megabyte JSON responses over a thin link without trimming unused fields. A cluster upgrade shifts column layout or adds a column, breaking the parser — violating Elastic’s own rule that _cat is strictly for humans, while programs belong on typed JSON endpoints shaped with filter_path.

The build-up covers: REST conventions and common options (01), _cat vs. JSON (02), Kibana Dev Tools Console (03), _bulk NDJSON routing and partial failures (04), batch sizing and selective 429 retries (05), and an end-to-end build (06).

01 REST grammar

Targets, headers, and common options across every endpoint ▸

Every HTTP endpoint on port 9200 shares a small set of global conventions. Learn them once and they work identically on search, cluster inspection, and bulk writes.

  • Strict Content-Type and UTF-8 JSON — any request carrying a body must declare an explicit Content-Type header (typically application/json; application/x-ndjson for bulk and multi-search; YAML, CBOR, and SMILE are also supported). Text inside JSON must be UTF-8 encoded.
  • Multi-target paths and date math — data and search endpoints accept comma-separated names (orders-2025,orders-2026), wildcards with exclusions (logs-*,-logs-debug), or _all. Time-based indices also support date math expressions such as <logs-{now/d}> (which resolves dynamically to today’s UTC index name; URL-encode < as %3C and > as %3E in raw curl). Pair wildcards with ignore_unavailable=true, allow_no_indices=true, and expand_wildcards=open|closed|all|none so missing or closed indices do not fail a multi-index query.
  • X-Opaque-Id request tracing — attach an X-Opaque-Id: catalog-sync HTTP header to any request and Elasticsearch carries that tag into task management (_tasks), slow logs, and deprecation logs, letting you trace an expensive query straight back to the caller that sent it.
Common option What it changes When to use — and when to leave off
?filter_path=... Comma-separated dot paths (with *, **, and - exclusions) filtering what the coordinating node serializes back. Use in scripts and high-volume callers (e.g., filter_path=took,errors,items.*.error). Cuts wire payload dramatically, though shards still run the full query before trimming.
?pretty=true Indents and line-breaks the JSON response. Terminal debugging only. Adds bytes and serialization work; never send from application code.
?human=true Adds readable sizes and durations ("10kb", "1m") rather than raw bytes/ms only. Operator checks. Default is false on JSON APIs because computers want raw integer bytes and milliseconds.
?error_trace=true Includes the server-side Java stack trace inside 4xx/5xx error JSON. Local debugging only. Verbose and exposes internal stack details.
?refresh=false|wait_for|true Controls when writes become visible to search (false default, wait_for pauses for next periodic refresh, true forces immediate refresh). Keep false for bulk throughput; use wait_for only when the caller needs read-after-write visibility; reserve true for tests.
What the interviewer probes next

“Does ?filter_path=took,hits.total make the search execute faster on the shards?” Mostly no — the shards still score and return results to the coordinating node unless you also set "size": 0 or "_source": false in the query body. filter_path saves network bandwidth and client JSON parsing, not shard CPU.

02 Operator visibility

The _cat APIs: compact tables meant for human eyes, never code

JSON is great for programs and miserable to scan in an SSH session at 2 a.m. That is why Elasticsearch ships the _cat (Compact and Aligned Text) APIs. Send GET /_cat and the cluster prints every available endpoint. Unlike regular JSON APIs, _cat formats responses into fixed-width, whitespace-aligned terminal tables.

Endpoint What it answers immediately Operator call you actually run
GET /_cat/health One-line snapshot: timestamp, cluster name, green/yellow/red, nodes, active/unassigned shards. GET /_cat/health?v
GET /_cat/nodes Per-node CPU, load average, RAM, JVM heap%, roles, and * marking the elected master. GET /_cat/nodes?v&h=ip,heap.percent,ram.percent,cpu,node.role,master,name
GET /_cat/indices Health, status, primary/replica counts, live vs. deleted docs, and disk footprint per index. GET /_cat/indices?v&s=store.size:desc
GET /_cat/shards Exact node placement for every primary (p) and replica (r), plus why a shard is UNASSIGNED. GET /_cat/shards/catalog?v&h=index,shard,prirep,state,docs,store,node,unassigned.reason
GET /_cat/count Fast total document count across the cluster or a named index. GET /_cat/count/catalog?v
GET /_cat/thread_pool/write Active workers, queued requests, and cumulative rejected count on the write pool (critical during bulk tuning). GET /_cat/thread_pool/write?v&h=node_name,active,queue,rejected

Five shared query flags unlock almost all the power of _cat:

  • ?v (verbose) — prints the column header row. Without ?v, _cat prints bare data lines.
  • ?help — prints every supported column name, short alias, and description for that endpoint — no memorizing obscure headers.
  • ?h=col1,col2,... — selects only the columns you care about (supports wildcards such as h=node*,*store*).
  • ?s=col:desc — sorts rows by any column ascending or descending (for example, ?s=docs.deleted:desc to find segment bloat or ?s=store.size:desc to find the biggest indices).
  • ?bytes=mb / ?time=ms / ?format=json — normalizes unit scaling across rows, or emits JSON for one-off CLI piping into jq.

green  open   orders-v2     7aKp9x2...               3   1     420500         1820    142.8mb         71.4mb

Use /_cat/* when…

  • You are debugging live in a terminal or Kibana Console.
  • You want to spot which node holds an unassigned shard or which index has high docs.deleted in one glance.
  • You need interactive discovery via ?help and sorting via ?s=.

Use JSON APIs when…

  • A script, exporter, health check, or CI gate reads the answer (/_cluster/health, /_nodes/stats, /_count).
  • You need exact numeric bytes, milliseconds, or nested per-shard metrics without unit rounding.
  • You want predictable keys combined with ?filter_path=.
03 Interactive workbench

Kibana Dev Tools Console: fast iteration without shell escaping

Writing nested JSON queries and NDJSON bulk bodies straight in bash with curl -d '...' quickly turns into a war with single quotes, TLS flags, and missing trailing newlines. Kibana ships a built-in HTTP workbench at Dev Tools → Console (<kibana-url>/app/dev_tools#/console, plus a Persistent Console available from the footer on search and serverless views).

Console is not a separate query language — it is a thin Monaco-powered editor over the exact same Elasticsearch REST API (and Kibana APIs when prefixed with kbn:). What it adds is ergonomic speed:

  • Clean HTTP shorthand — write GET /_cat/shards?v or POST /catalog/_search followed directly by the JSON body, with no host, port, or Content-Type boilerplate.
  • Context-sensitive autocomplete & comments — suggests API paths, Query DSL clauses, and field names from your actual mappings, while allowing //, #, and /* ... */ comments inside your scratchpad (and keeping your last 500 executed requests in History).
  • One-click export to code — Console’s action menu can copy any request as curl, JavaScript, or Python once an experiment works.
The copy-paste trap between Console and curl

Console automatically handles two things that break when you move a working _bulk request into shell scripts: it sets the right Content-Type header, and it appends the mandatory trailing newline for you. When translating to curl, always pass -H "Content-Type: application/x-ndjson" and --data-binary (never plain -d, which strips line breaks and corrupts NDJSON!). Alongside Console in Dev Tools sit the Search Profiler, Grok Debugger, and Painless Lab for profiling queries and testing ingest rules.

04 Throughput & wire format

The Bulk API: NDJSON pairs, parallel routing, and why HTTP 200 can lie ▸

Why is looping 10,000 single-document PUT calls slow? Even when each document takes 2 ms inside Lucene, paying 10,000 HTTP round trips, TLS handshakes, and coordinator dispatches wastes almost the entire wall clock on transport overhead. The Bulk API (POST /_bulk or POST /<index>/_bulk) packs hundreds or thousands of index, create, update, and delete operations into one HTTP request.

Instead of one giant JSON array — which would force the coordinating node to deserialize every document body into memory before routing — _bulk uses Newline Delimited JSON (NDJSON) with Content-Type: application/x-ndjson:

  • One compact JSON object per line — never pretty-print inside a bulk payload; embedded newlines break line boundaries.
  • Two lines for writes, one line for deletes — index, create, and update take an action-metadata line followed immediately by a payload line ({"doc": ...} for update; plain fields for index/create). delete has no payload line; accidentally leaving an empty or body line after delete shifts every operation below it out of sync.
  • Mandatory trailing newline (\n) — the final line of the entire request body must end with \n (or \r\n), or the parser rejects the batch.
  • Data-stream rule carries over from L02 — you can mix index, create, update, and delete across multiple indices in one POST /_bulk call, except when targeting a data stream, which rejects everything except create.
  • Metadata options live inside the action header — per-item _index (optional if set in the URL), _id, routing, pipeline, if_seq_no/if_primary_term, and retry_on_conflict (for update) all belong in the action JSON line, not the URL query string.
The partial-failure invariant

_bulk is not atomic. Each action executes independently on its target shard: a bad field type or version conflict on item 2 never rolls back item 1 or item 3. Because the HTTP transport succeeded, the cluster returns 200 OK with "errors": true and the per-item statuses in items[] (in the exact order you sent them). Always inspect errors and scan items[] — never trust HTTP 200 alone.

What the interviewer probes next

“Why does Elasticsearch ask for NDJSON instead of a standard JSON array in _bulk?” Because the coordinating node needs to route documents to shards without allocating and JSON-parsing megabytes of document bodies on the coordinator heap. Line-by-line framing lets it inspect only the tiny action metadata lines, slice the raw source bytes straight through to the owning shard over port 9300, and parse each document once on the shard that actually stores it.

05 Sizing & backpressure

Tuning bulk throughput: the 5–15 MiB sweet spot and selective 429 retries ▸

If batching 500 documents beats sending 1, why not send 100,000 documents in a single request? Because Elasticsearch holds the raw bulk payload in JVM heap memory on the coordinating node while slicing and forwarding it. Send too little and network round trips throttle throughput; send too much concurrently and you trigger GC pauses, circuit breakers, or write thread-pool rejections.

  • Benchmark by doubling, don’t guess — Elastic’s indexing-speed guidance is empirical: benchmark against a single node and single shard starting around 100 documents, then double (200, 400, 800, …) until documents/sec plateaus. When two sizes tie, pick the smaller batch.
  • Watch payload bytes, not just document count — 500 tiny 200-byte log lines is 100 KB, while 500 50-KB product descriptions is 25 MB. In practice, batches of 5–15 MiB hit the throughput sweet spot; stay well under a few tens of megabytes per request. Remember that http.max_content_length (default 100 MB) is an upper safety guardrail, never a target batch size.
  • Auto-generated IDs skip existence checks — when using index or create without deduplication needs, letting Elasticsearch generate a 20-character _id skips checking every shard segment to see if that ID already exists.
  • Keep refresh=false during bulk loads — forcing refresh=true creates tiny Lucene segments on every batch and crushes write throughput.

Backpressure: 429 rejections and selective retry

When clients push bulk batches faster than shards can write them, either the node’s write thread pool queue fills up or indexing_pressure memory limits trip, producing 429 / es_rejected_execution_exception (either per item inside items[] or at the HTTP level). Note what not to do when that happens:

  • Never retry the whole batch blindly — re-sending items that already returned 201 wastes cluster CPU (or triggers 409 on create), and sending permanent 400 mapper_parsing_exception rows again will fail forever.
  • Retry only the 429 items with jittered exponential backoff — pause briefly (for example, 1–2 seconds doubling with random jitter), shrink concurrency if needed, and re-submit only the throttled subset.

Choosing the right Python Bulk API wrapper

Python API (elasticsearch 9.x) What it handles for you Best fit & watch-outs
client.bulk(operations=...) Thin wrapper over POST /_bulk. You chunk the payload and parse errors / items[] yourself. Custom batch protocols or mixed manual retry pipelines where you want raw server JSON back.
helpers.streaming_bulk(...) Generator consuming an action iterable in chunks (default chunk_size=500, max_chunk_bytes=104857600), yielding (ok, info) per item and retrying retry_on_status=(429,) up to max_retries with exponential backoff. Default choice for production ingestion. Streams memory cleanly; note it is lazy — nothing executes until you iterate over it!
helpers.bulk(...) Drains streaming_bulk into memory and returns (success_count, errors). Small scripts and tests where returning one summary tuple is nicer than streaming.
helpers.parallel_bulk(...) Uses a thread pool to run multiple streaming_bulk requests concurrently. High-bandwidth ETL into multi-node clusters; watch thread count so you don’t saturate write queues.

3 · Streaming Python script with selective error handling

python 3 · pip install elasticsearch==9.5.1 · elasticsearch.helpers.streaming_bulk

import uuid
from elasticsearch import Elasticsearch
from elasticsearch.helpers import streaming_bulk

client = Elasticsearch("http://localhost:9200")
# Tag every request with X-Opaque-Id so slow logs / _tasks point back to this job
scoped = client.options(headers={"X-Opaque-Id": "lesson-03-bulk-lab"})
INDEX = f"lab-bulk-{uuid.uuid4().hex[:8]}"


def generate_actions():
    yield {"_op_type": "create", "_index": INDEX, "_id": "kb-1",
           "_source": {"sku": "KB-1", "price": 99.0, "stock": 12}}
    yield {"_op_type": "index", "_index": INDEX, "_id": "kb-2",
           "_source": {"sku": "KB-2", "price": 149.0, "stock": 8}}
    yield {"_op_type": "index", "_index": INDEX, "_id": "bad-doc",
           "_source": {"sku": "BAD", "price": "not-a-float", "stock": 1}}
    yield {"_op_type": "update", "_index": INDEX, "_id": "kb-1",
           "retry_on_conflict": 2, "doc": {"stock": 10}}
    yield {"_op_type": "delete", "_index": INDEX, "_id": "kb-2"}


try:
    scoped.indices.create(
        index=INDEX,
        settings={"number_of_shards": 1, "number_of_replicas": 0},
        mappings={"properties": {
            "sku": {"type": "keyword"},
            "price": {"type": "float"},
            "stock": {"type": "integer"},
        }},
    )

    applied, dead_letter = 0, []
    # streaming_bulk is a generator: nothing runs until the loop pulls from it.
    # Retries ONLY 429 rejections automatically; permanent 400/409 errors surface to us.
    for ok, item in streaming_bulk(
        scoped,
        generate_actions(),
        chunk_size=500,
        raise_on_error=False,
        max_retries=3,
        retry_on_status=(429,),
        refresh="wait_for",
    ):
        op, info = next(iter(item.items()))
        if ok:
            applied += 1
        else:
            dead_letter.append((op, info.get("_id"), info.get("status"), info.get("error", {}).get("type")))

    # Use typed JSON APIs in Python code (never parse _cat text in applications!)
    count = scoped.count(index=INDEX, filter_path="count")["count"]
    assert applied == 4 and len(dead_letter) == 1 and count == 1
    print({"applied_ops": applied, "live_docs": count, "dead_letter": dead_letter})
finally:
    client.indices.delete(index=INDEX, ignore_unavailable=True)
Explain it aloud in an interview

“For operational checks I use _cat endpoints with ?v, ?h=, and ?s=, because they give humans compact tables in one screen — while keeping scripts strictly on typed JSON endpoints shaped with filter_path. For writes at scale I batch through _bulk using NDJSON: two lines per write, one line per delete, mandatory trailing newline. That lets the coordinating node parse only the tiny metadata lines and route sub-batches to shards in parallel. Because _bulk is not atomic and returns HTTP 200 even on partial failure, my client always scans items[], dead-letters permanent 400 or 409 errors, and retries only transient 429 queue rejections with jittered backoff — sizing batches empirically toward the 5–15 MiB plateau.”

Follow-ups to expect: why delete takes one line instead of two, why curl -d breaks bulk files while --data-binary works, why _cat/indices shows docs.deleted: 2 after kb-1 was updated and kb-2 was deleted, and what happens if you send an update inside a _bulk batch targeting a data stream (400 error: only create is allowed).

Self-test

1. Why should monitoring scripts never parse GET /_cat/indices text output?

_cat endpoints are built exclusively for human reading in terminals and Kibana Console. Their column order, spacing, and headers are not a stable programmatic contract. Scripts and alerting jobs should query typed JSON endpoints such as /_cluster/health, /_stats, or /_count (optionally trimmed with ?filter_path=).

2. Why does the Bulk API use NDJSON instead of a JSON array, and what happens if the trailing newline is missing?

NDJSON separates compact action-metadata lines from raw document payload lines so the coordinating node only parses the metadata lines to hash and route sub-batches to shards without buffering/deserializing huge document bodies on its heap. Every line — including the very last line — must end with \n (or \r\n), or Elasticsearch rejects the final operation.

3. Your POST /_bulk request returned HTTP 200 OK. Does that guarantee every document was indexed?

No. _bulk is not atomic. Valid operations succeed while malformed or rejected ones fail individually. Elasticsearch returns HTTP 200 OK with "errors": true and puts per-item statuses and error blocks inside the ordered items[] array.

4. How many lines does a delete action take in a _bulk request, and what happens if you include an empty body line?

A delete action takes one line only (no source payload line follows it). Including an extra line shifts every subsequent metadata/body pair out of alignment and breaks parsing for the rest of the batch.

5. A bulk batch hits 400 mapper_parsing_exception on two items and 429 es_rejected_execution_exception on ten items. What should the client retry?

Retry only the ten 429 items after randomized exponential backoff. Never resend items that succeeded (200/201), and never retry permanent 400 or 409 errors — route those to a dead-letter log or alert.

6. What happens if you run helpers.streaming_bulk(client, actions) in Python without iterating over it?

Nothing is sent to Elasticsearch. streaming_bulk returns a lazy generator that reads actions and dispatches chunks only as your loop pulls tuples from it (unlike helpers.bulk, which consumes the entire iterator internally).
