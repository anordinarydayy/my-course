01Concept · Phase 0 · Elasticsearch

The Mental Model: Cluster → Index → Shard → Segment

Lesson 00 showed why you leave SQL LIKE behind for an inverted index. The very next question is structural: what happens when your dataset grows beyond one disk, one CPU, or one file? Elasticsearch answers with a five-layer architecture — Cluster → Node → Index → Shard → Segment — holding JSON documents underneath and driven by a plain HTTP+JSON REST API on top. Hang this map on the wall once and every mapping rule, sizing guideline, and operational alert snaps into place.

Original study chapter. Written from scratch for backend, search, and platform interviews — and for running real clusters. Behavior and defaults target stable Elasticsearch 9.5 (built on Apache Lucene 10, tracking the 8.x → 9.x line; latest 9.5.6 maintenance patch as of late 2026); runnable code uses Python 3 and elasticsearch==9.5.1 alongside raw HTTP REST endpoints. Contains four original figures, two interactive (press Play, or step with Next). Deep dives on metadata/data streams, _cat/Bulk, segment merging, shard routing, and node roles follow in L02, L03, L05, L07, and L22–L24.
00 The problem first

Why you cannot put everything in one giant index file

Before memorizing five terms, ask what fails if you skip them. Suppose you launch a single search process backed by one monolithic Lucene index file on one server. On day one it flies. Within months, four distinct physical walls stop it cold:

  • Single-machine limits and Lucene’s hard doc cap — one server’s disk, RAM, and CPU saturate as traffic climbs. Underneath, a single Apache Lucene index also has a hard architectural ceiling of 2,147,483,519 documents (Integer.MAX_VALUE - 128, counting both live and unmerged deleted docs), and practical search and recovery latency degrades long before that (Elastic targets 10–50 GB and under 200 million documents per shard).
  • No survival across a host failure — one machine holding the only copy means a dead SSD or a host reboot takes every search query offline.
  • In-place mutation destroys inverted-index speed — an inverted index stores heavily compressed, sorted term dictionaries and postings lists. Rewriting one giant file in place whenever a single document changes would thrash disk I/O and stall readers.
  • Mixed workloads collide — stuffing product catalogs, nginx logs, and audit events into one undifferentiated pool mixes schemas, retention periods, and BM25 term frequencies.

Every layer of Elasticsearch’s mental model exists specifically to remove one of those walls: segments solve in-place mutation, shards solve size limits and parallel/redundant execution, indices separate logical datasets, nodes supply physical compute and storage, and the cluster coordinates the whole fleet as one addressable engine.

The misconception to drop right now

Most newcomers read “Cluster → Node → Index → Shard” as strict Russian nesting dolls — assuming a Node contains Indices, which contain Shards. That picture is wrong. An Index is a logical namespace, not a box inside one node. Physically, a cluster contains Nodes, and an index’s Shards are spread across multiple nodes. One node commonly hosts shards from many different indices, and one index commonly spans many nodes.

01 The five-box map

Cluster → Node → Index → Shard → Segment ▸

Keep the distinction between logical organization and physical placement sharp as you walk the five layers from top to bottom:

  • Cluster — one or more connected nodes sharing a cluster name and synchronized cluster metadata. Exposes one federated API across all data and coordinates failover automatically.
  • Node — a single running Elasticsearch JVM instance (one server or container). Stores assigned shards on disk, serves queries against them, and can act as a coordinating node to route incoming requests across the cluster.
  • Index — a logical collection of JSON documents sharing a schema (mapping) and configuration (settings). Think of it as the address your application targets by name or alias.
  • Shard — a physical horizontal partition of an index. Under the hood, every shard is a complete, self-contained Apache Lucene index. Every document hashes into one primary shard; replica shards are exact copies placed on different nodes for high availability and read throughput.
  • Segment — an immutable mini-inverted index living inside a shard. Writes accumulate into new segments instead of mutating old ones, and background merges combine small segments into larger ones.
02 Logical vs. physical

Index vs. Node, Primary vs. Replica, and why types are gone

The fastest way to avoid rookie cluster mistakes is to separate what your application names from how Elasticsearch places bytes on hardware. If you come from PostgreSQL or MySQL, an analogy helps for the first thirty seconds — and then immediately breaks in four places that interviewers love to test.

SQL / RDBMS concept Closest Elasticsearch match Where the analogy breaks
Cluster / Instance Cluster Many nodes cooperate as one peer-to-peer distributed engine, not one primary server plus read-only followers for the whole database.
Table Index An index is a logical namespace spread across nodes via shards — and unlike older ES versions, an index is not a database holding multiple “table types.”
Row JSON Document Documents can hold nested objects and arrays directly; there are no multi-table foreign-key ACID joins at query time.
Column Field A single text field commonly maintains multiple physical structures at once (inverted index, doc values, optionally vectors).
Schema Mapping Mappings can grow dynamically on new fields, but changing an existing field’s type requires building a new index and reindexing.
Partition / Table file Shard (Lucene index) Each shard is an entire independent search engine with its own inverted index, cache, segments, and hard ~2.14B document limit.

Mapping types are history (removed in 8.0.0)

Older blog posts and outdated interview answers compare an Elasticsearch index to a SQL database and a mapping type (like users or orders) to a SQL table. That design caused severe Lucene conflicts because two different types in the same index had to share identical underlying Lucene field definitions when field names collided. Elastic deprecated multi-type indices in 6.0, deprecated types further in 7.0, and completely removed mapping types in Elasticsearch 8.0.0. Today, one index holds one logical entity shape, and _doc in URLs like /orders/_doc/42 is simply the fixed typeless endpoint path.

Primary vs. Replica defaults — and the “yellow laptop” puzzle

Every regular index carries two core shard settings:

  • index.number_of_shards (defaults to 1 since 7.0; previously 5) — sets the count of primary shards. Every document routes to exactly one primary shard, and this setting is static at index creation (capped at 1024 shards per index by default). Changing primary shard count later requires reindexing into a new index (or using the Shrink/Split APIs under strict prerequisites; see L22).
  • index.number_of_replicas (defaults to 1) — sets how many replica copies exist for each primary shard. This setting is dynamic and can be scaled up or down live via PUT /<index>/_settings.

Crucially, Elasticsearch obeys one strict placement invariant: a replica shard is never allocated on the same node as its own primary shard. Putting primary and copy on the same machine wastes disk and protects against zero host failures. That single rule explains why a fresh single-node cluster immediately turns yellow as soon as you index your first document with default settings:

Green

  • Every primary and every replica shard is allocated and active.
  • Requires at least 1 + number_of_replicas data nodes for full redundancy.

Yellow

  • All primary shards are active (reads and writes work), but at least one replica is unassigned.
  • Classic cause: 1-node dev cluster with default number_of_replicas: 1.

Red

  • At least one primary shard is unassigned.
  • Part of the index is unavailable; searches return partial or error results depending on config.
What the interviewer probes next

“Suppose I create an index with number_of_shards: 3 and number_of_replicas: 2. How many shards exist in total, and how many nodes do I need for green health?” Answer cleanly: 3 primaries + 3 × 2 = 6 replicas = 9 shard copies total. Because a primary and its two replicas must sit on three distinct hosts, you need at least 3 data nodes for green cluster health.

03 Inside a shard

Segments: why Lucene never mutates an index file in place

Zoom all the way into one shard on disk. You do not find one monolithic file; you find an Apache Lucene index built out of immutable segments plus a commit point listing which segments currently belong to the shard. Each segment is itself a mini search engine containing its own term dictionary, postings lists, columnar doc values, and (when configured) HNSW vector graphs.

Why keep segments strictly read-only once written? Because immutability buys three things mutable B-tree pages struggle to deliver simultaneously:

  • Lock-free concurrent reads — search threads read finished segment files simultaneously with zero file locks or write-coordination stalls.
  • OS filesystem page cache stays hot — because an immutable segment file never changes bytes, the operating system caches it in free RAM aggressively without invalidating cached pages on every write.
  • Sequential I/O on write — new writes enter an in-memory buffer (backed by a transaction log for durability) and periodically open a fresh segment during a lightweight refresh (by default every 1 second on indices actively receiving searches).

If segments never change, how do UPDATE and DELETE work? When you delete or overwrite a document, Lucene sets a bit in a lightweight live-documents bitmap (.liv) marking the old document ID as deleted, and appends the updated version into a new segment. Queries filter out masked IDs automatically. Later, a background merge process picks compatible small segments, writes a consolidated segment containing only live documents, switches the commit point atomically, and deletes the obsolete segment files — keeping file descriptors and per-segment overhead bounded (detailed in L05 and L07).

04 At the bottom

The JSON document: your data plus its routing envelope

Follow the hierarchy down past segments and you reach the atomic unit of storage: a JSON document. Unlike rigid relational tuples, documents naturally carry nested objects and arrays (tags, metadata, embeddings). Whenever you index or fetch one, Elasticsearch pairs the JSON body you sent inside _source with system-managed metadata fields prefixed by an underscore.

Two of those metadata fields matter on day one because they connect directly back to the cluster map above: _index names the logical index holding the document, and _id uniquely identifies it within that index and serves as the default input to the hash function that picks its primary shard (_version, _seq_no, and _primary_term track single-document write ordering, explored in L02).

Regular Index (mutable entities)

  • Target directly when documents need updates or deletes by _id (product catalogs, user profiles, knowledge chunks).
  • One logical index backed by its fixed count of primary shards and dynamic replicas.

Data Stream (append-only telemetry)

  • Target for timestamped logs, metrics, and traces — covered deeply in L02 and L36.
  • One logical stream name automatically rolls over across hidden backing indices as time or shard size grows.
05 Driving the map

The HTTP + JSON REST API (and the coordinating node) ▸

Every layer you just drew has a direct HTTP+JSON address exposed on port 9200 (while nodes exchange cluster state, shard replication, and internal query traffic privately over a binary protocol on port 9300). Notice how cleanly the URL paths echo the hierarchy: cluster endpoints start with /_cluster or /_cat, index operations target /<index>, and document/search calls sit at /<index>/_doc and /<index>/_search.

Even better, every node is cluster-aware. Your client or load balancer can send an HTTP request to any node; that receiving node becomes the coordinating node for the request, looks up shard placement in its local cluster state, forwards writes or scatters searches to the actual shard owners over port 9300, and returns one combined JSON answer.

Layer Typical HTTP + JSON endpoint What you inspect or control
Cluster GET / · GET /_cluster/health Version & cluster name; green/yellow/red status, node count, active vs. unassigned shards.
Node GET /_cat/nodes?v · GET /_nodes/stats Human-readable node roles/heap/CPU (_cat), or JSON telemetry per node.
Index PUT /catalog · PUT /catalog/_settings Create index with static number_of_shards + mappings; dynamically resize number_of_replicas.
Shard & Segment GET /_cat/shards/catalog?v · GET /catalog/_segments Which node holds each primary/replica copy; live Lucene segments, doc counts, and deletions.
Document & Search POST /catalog/_doc · GET /catalog/_search Index or fetch a JSON document (L02); scatter-gather search across one copy of every shard (L13, L22).
Security note on 8.x & 9.x clusters

Since Elasticsearch 8.0, security (TLS on both 9200 HTTPS and 9300 transport, plus built-in authentication / API keys) is enabled automatically on newly bootstrapped clusters. Local single-node Docker tutorials often disable TLS or pass an auto-generated password/CA cert; in production, never leave port 9200 unauthenticated.

06 Worked example

Seeing Cluster → Index → Shard → Segment in real responses

Put the whole map against a real cluster. Below are the HTTP requests you can run in Kibana Dev Tools or curl, followed by a Python script using the official elasticsearch==9.5.1 client targeting Elasticsearch 9.5. It creates a 2-primary, 1-replica index, indexes a JSON document, inspects cluster health (catching why a 1-node local box reports yellow!), and opens /_segments to inspect the underlying Lucene 10 segments.

Inspecting all five layers via REST and Python

Create an index named catalog-map with 2 primary shards and 1 replica per primary (4 shards total). Index one JSON document with refresh="wait_for", then inspect _cluster/health and _segments to see the node IDs, primary/replica flags, and immutable Lucene segment counts.

2 · Equivalent Python script

python 3 · pip install elasticsearch==9.5.1 · local dev node on http://localhost:9200

import uuid
from elasticsearch import Elasticsearch

client = Elasticsearch("http://localhost:9200")
INDEX = f"lab-map-{uuid.uuid4().hex[:8]}"

try:
    # 1. Logical index: 2 primary shards (fixed) x 1 replica each (dynamic)
    client.indices.create(
        index=INDEX,
        settings={"number_of_shards": 2, "number_of_replicas": 1},
        mappings={"properties": {"sku": {"type": "keyword"}, "title": {"type": "text"}}},
    )

    # 2. Index one JSON document; wait for the NRT refresh to open a Lucene segment
    res = client.index(
        index=INDEX,
        id="kb-75",
        document={"sku": "KB-75", "title": "Compact mechanical keyboard"},
        refresh="wait_for",
    )
    # The response names the shard metadata stamps created by the primary shard
    assert res["_index"] == INDEX and res["_id"] == "kb-75"

    # 3. Cluster + shard placement check
    health = client.cluster.health(index=INDEX)
    # On 1 node: active_primary_shards=2, unassigned_shards=2 -> status="yellow"
    # On 2+ nodes: active_shards=4, unassigned_shards=0       -> status="green"
    expected = "yellow" if health["number_of_data_nodes"] == 1 else "green"
    assert health["status"] == expected

    # 4. Drill into shards -> Lucene segments inside the index
    seg_resp = client.indices.segments(index=INDEX)
    shards_map = seg_resp["indices"][INDEX]["shards"]
    assert set(shards_map.keys()) == {"0", "1"}

    summary = []
    for shard_id, copies in sorted(shards_map.items()):
        for copy in copies:
            segs = copy["segments"]
            summary.append({
                "shard": shard_id,
                "primary": copy["routing"]["primary"],
                "node": copy["routing"]["node"],
                "search_segments": copy["num_search_segments"],
                "lucene_versions": sorted({s["version"] for s in segs.values()}),
            })
    print({"health": health["status"], "nodes": health["number_of_nodes"], "shards": summary})
finally:
    client.indices.delete(index=INDEX, ignore_unavailable=True)
Explain it aloud in an interview

“When a client sends POST /catalog-map/_doc/kb-75 over HTTP port 9200, any node can accept it as the coordinating node. From the logical index name, it hashes _id to pick one of the index’s fixed primary shards — say shard 1 — and forwards the write over internal port 9300 to whichever data node hosts primary 1. That primary shard is an Apache Lucene index: it buffers the document, replicates it to its replica copy on another node, and opens a fresh immutable segment on the next 1-second refresh. Later reads can hit either the primary or replica shard.”

Follow-ups to expect: why _segments shows only one shard having 1 doc and the other having 0 (each document belongs to one primary shard), why number_of_shards is static while number_of_replicas is dynamic (changing primary count changes the shard routing hash space), and how L03 inspects this quickly via GET /_cat/shards?v.

Self-test

1. Why is “Cluster > Node > Index > Shard” misleading if read as physical containment?

Because an Index is a logical grouping, not something trapped inside one Node. Physically, a Cluster contains Nodes, and the Shards belonging to one Index are distributed across multiple Nodes (while one Node typically holds Shards from many different Indices).

2. What is the difference between an Elasticsearch shard and a Lucene segment?

A shard is a complete Apache Lucene index (owning routing, primary/replica status, and cluster allocation). Inside every shard sit multiple immutable segments, each holding its own mini inverted index, doc values, and commit-point membership.

3. Why does a brand-new single-node dev cluster turn yellow when you create an index with default settings?

New regular indices default to number_of_shards: 1 and number_of_replicas: 1. Elasticsearch never allocates a replica shard onto the same node as its primary shard, so the 1 primary starts (reads/writes succeed) while the 1 replica remains unassigned — reporting yellow.

4. Why are Lucene segments immutable, and how does deleting or updating a document work?

Immutability gives lock-free concurrent reads, sequential write I/O, and warm OS filesystem caching without page invalidation. On delete or update, Lucene marks the old document ID as deleted in a live-documents bitmap (.liv) and writes the new version to a fresh segment; background segment merging later drops the dead records physically.

5. Can you change number_of_shards or number_of_replicas on a live index?

number_of_replicas is dynamic and can be changed anytime via PUT /<index>/_settings. number_of_shards (primary shards) is static at index creation because changing it alters document-to-shard routing; changing it later requires reindexing (or using Shrink/Split APIs under specific rules).

6. What happened to mapping types, and what do ports 9200 vs. 9300 carry?

Mapping types were completely removed in Elasticsearch 8.0.0; one index holds one logical entity shape and _doc is a fixed typeless endpoint. Clients send HTTP+JSON REST requests to any coordinating node on port 9200, while nodes handle internal cluster state, replication, and forwarded shard operations over binary transport on port 9300.
