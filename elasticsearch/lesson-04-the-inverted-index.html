The Inverted Index

Phase Zero treated the inverted index as a black box that maps words to document IDs. Phase One opens the lid inside a single Lucene segment: how an off-heap term index locates a sorted term dictionary block, how delta-compressed postings lists and skip lists intersect millions of hits without scanning them, and how storing positions and offsets unlocks phrases and fast highlighting — along with the workloads where Elasticsearch skips the inverted index altogether.

00 The failure first

A broken phrase search, a slow highlight, and a sorted text trap

Start with three production surprises that happen whenever engineers treat “the inverted index” as a vague synonym for “search index.”

  • Disk savings that break phrase search — to shrink index storage, an engineer sets "index_options": "freqs" on an article body field. Regular keyword queries still work, until a user wraps a search in quotes (match_phrase). Every phrase query suddenly fails with HTTP 400: field was indexed without position data; cannot run PhraseQuery. The postings list dropped word positions, and you cannot fix it without reindexing.
  • Highlighting that re-analyzes megabytes per hit — another team renders search snippets across long legal contracts. Because default mappings stop at positions (not character offsets), the highlighter has to fetch raw _source and re-run the analyzer on every returned document — eating CPU on search nodes or tripping the 1,000,000-character index.highlight.max_analyzed_offset guardrail.
  • Assuming every field lives in an inverted index — a developer tries to sort or run a terms aggregation on a text field (which fails by default because the inverted index maps word → docs, not doc → values), or asks why a range query on product prices works fast even though scanning every distinct float in a term dictionary would crawl.

Each of those mysteries clears up once you look at what sits inside a Lucene segment: the term index and dictionary (01), postings compression and skip lists (02), the four cumulative rungs of index_options (03), and the boundary between inverted indexes, BKD trees, and doc values (04).

01 Term dict & postings

The book-index analogy made precise: FST → block dictionary → postings ▸

A textbook index at the back of a book lists sorted terms on the left and page numbers on the right. It fails as a literal implementation model at scale in two places: first, millions of distinct words would still be slow to scan on disk, and second, keeping the entire vocabulary in JVM heap memory would blow up garbage collection on large nodes.

Assuming the field’s analyzer has already normalized text into tokens (Lesson 06 opens that pipeline), Apache Lucene stores each field’s inverted index inside every immutable segment across three cooperating pieces:

  • Term Index (.tip, Finite State Transducer) — instead of holding every word in memory, Lucene builds an FST: a highly compact prefix-and-suffix-compressed trie mapping term prefixes to the byte offset of a block inside the on-disk dictionary. Since Elasticsearch 7.7, Lucene lazily maps .tip files off-heap via mmap into the OS page cache rather than pinning them on the JVM heap, dramatically cutting heap footprint per terabyte of data.
  • Term Dictionary (.tim, Block Tree) — stores every unique term in lexicographical order inside prefix-compressed blocks on disk, along with its document frequency (df) and a pointer to its postings list. Once the FST points to one block, Lucene seeks straight there and ignores every other word in the segment.
  • Postings Lists (.doc, .pos, .pay) — for each term, the sorted list of internal segment docIDs (0-based integers local to that segment, not your string _id) that contain the term, compressed with delta encoding and bit-packing. Storing [2, 5, 19, 24] as gaps [2, +3, +14, +5] packs small integers into a handful of bits so hot postings stay cached in OS RAM.
What the interviewer probes next

“Why is a leading wildcard like *timeout still slow on an inverted index?” Because both the FST and the sorted term dictionary organize terms left-to-right by prefix. A trailing wildcard (time*) walks the FST to prefix time and reads only that subtree; a leading wildcard (*timeout) gives the FST no starting prefix, forcing Lucene to enumerate terms across the entire segment dictionary. Expect a second probe: “What holds the FST in memory?” Since Elasticsearch 7.7, .tip is memory-mapped off-heap via the OS page cache, not pinned on the JVM heap.

02 Intersecting postings

Multi-term queries: skip lists, advance(), and Block-Max skipping ▸

Single-word lookups are the easy case. Real queries ask for all terms (gateway AND timeout) or any of several terms (gateway OR timeout OR retry) across millions of documents. Walking two million-entry arrays element by element would throw away half the advantage of an inverted index.

Lucene avoids linear scans because postings lists are always sorted by ascending internal docID and chunked into blocks with an auxiliary skip list:

  • Conjunctions (must / AND) leapfrog via advance(target) — Lucene inspects each term’s estimated cost (its document frequency) and lets the shortest postings list drive. If "gateway" matches 3 documents ([4, 48, 120]) while "timeout" matches 500,000, the iterator never decompresses the 43 documents between 4 and 48; it calls advance(48), jumps across skip-list blocks directly to the block containing 48, and decodes only that block.
  • Disjunctions (should / OR) skip low-scoring blocks with Block-Max impacts — when you ask for the top 10 scored hits, Lucene does not even score every matching document. Since Lucene 8 (and continuing in Lucene 10), postings skip metadata stores impacts: the precomputed maximum score contribution a term can add inside each block of documents. Using Block-Max WAND / Block-Max MAXSCORE, once the 10th-best score threshold (θ) exceeds a block’s upper-bound score, Lucene skips the entire block untouched — which is why Elasticsearch caps exact hit counting (track_total_hits) at 10,000 by default so skipping stays fast.
03 Positions & offsets

What positions and offsets buy you: phrases, proximity, and highlighting ▸

Notice how our first two diagrams only needed docIDs and frequencies. Why does Elasticsearch’s default text mapping store more? Because knowing that "compact" and "keyboard" both appear in document 1 cannot tell you whether the text reads “compact mechanical keyboard” or “keyboard cable — compact case”, and it cannot tell a search snippet highlighter which characters in the original string to wrap in <em> tags.

The mapping parameter index_options controls how much per-occurrence data Lucene writes into each term’s postings list. Each level is strictly cumulative — adding a capability without dropping earlier ones:

  • docs (default for keyword) — stores only docID. Answers binary membership (“does this exact term appear?”). No term-frequency scoring and no phrases.
  • freqs — stores docID + term frequency (tf). Unlocks BM25 term-frequency weighting so a document mentioning a word four times ranks above a single mention, while saving disk by omitting positions.
  • positions (default for text) — stores docID + tf + word positions (0, 1, 2, ...). Unlocks match_phrase, slop proximity queries, and span queries. Setting "index_phrases": true on a text field also indexes 2-word pairs (2-shingles) in a hidden subsidiary field so exact slop: 0 phrase queries avoid intersecting positions at query time, trading extra index space for phrase speed.
  • offsets — stores docID + tf + positions + UTF-16 start/end character offsets in the original string. Lets Elasticsearch’s default Unified Highlighter lift matching fragments straight from postings without re-running the analyzer over _source at query time.
SettingWhat is stored per occurrenceWhat breaks or slows down if omittedWhen to pick it
index_options: "docs" docID only. No frequency weighting (repeated terms score equal to 1); match_phrase throws a 400 error. Default on keyword; good for text tags/codes when you only check presence.
index_options: "freqs" docID + term frequency (tf). match_phrase and proximity queries throw indexed without position data. Large text fields where BM25 scoring matters and you never run phrase queries.
index_options: "positions" docID + tf + word position indices. Highlighting large fields falls back to re-analyzing _source at query time. Default for text. Balances size with phrase/proximity support.
index_options: "offsets" docID + tf + positions + char offsets. Slightly larger postings files than positions alone. Large highlighted fields using the default Unified Highlighter (far smaller than term vectors).
term_vector: "with_positions_offsets" Separate per-document forward term structure (_termvectors). Highest disk overhead (roughly doubles field index size). Legacy Fast Vector Highlighter (FVH) or massive (>1 MB) fields with complex multi-term highlights.
What the interviewer probes next

“We turned on highlighting on 200 KB documents and search CPU spiked — should we enable term_vector: "with_positions_offsets"?” Usually start with "index_options": "offsets" first! Elasticsearch’s default Unified Highlighter reads character offsets straight from the inverted index postings without re-analyzing _source, at a fraction of the disk cost of full term vectors. Reserve term_vector for the Fast Vector Highlighter or multi-megabyte documents with heavy wildcard/fuzzy highlighting.

04 The boundaries

What the inverted index is not for: BKD trees, doc values, and vectors

A common interview mistake is claiming Elasticsearch indexes every field in one giant inverted index. In modern Elasticsearch (8.x–9.x on Lucene 10), an inverted index is only one of four specialized per-segment data structures — because each access pattern hits a wall if forced onto the wrong one.

Inverted index excels when…

  • You search normalized words, phrases, or exact discrete strings (text, keyword).
  • You filter against a large set of exact IDs (terms lookup on a keyword field touches the dictionary in one sorted pass).
  • You index sparse learned embeddings like ELSER (which encode weighted tokens straight into Lucene postings!).

Reach for BKD trees or Doc Values when…

  • You query continuous ranges on numbers, dates, IPs, or coordinates — an inverted index would have to union thousands of distinct point terms, so Lucene uses BKD trees instead.
  • You sort hits or compute buckets/metrics — reading docID → value from columnar doc values (L05) beats inverting the whole term dictionary in reverse.
  • Design rule: map numeric-looking identifiers you never range-query (order_id, isbn, zip_code) as keyword, not long (or enable numeric index_terms if you need both range and term-heavy lookups).
The core invariant

An inverted index answers one question at segment speed: “Given a term (and optional position constraints), which sorted docIDs match?” Lookup time scales with the dictionary prefix and the length of the matching postings — never with total document count — while sorting, aggregations, and numeric ranges rely on doc values and BKD trees alongside it.

2 · Equivalent Python script

python 3 · pip install elasticsearch · local node on http://localhost:9200

import uuid
from elasticsearch import BadRequestError, Elasticsearch

client = Elasticsearch("http://localhost:9200")
INDEX = f"lab-inv-idx-{uuid.uuid4().hex[:8]}"

DOCS = [
    ("1", "KB-01", 99.0,  "compact keyboard layout"),
    ("2", "KB-02", 129.0, "compact mechanical keyboard"),
    ("3", "KB-03", 149.0, "keyboard compact travel"),
]


def phrase_ids(field, slop=0):
    resp = client.search(
        index=INDEX,
        query={"match_phrase": {field: {"query": "compact keyboard", "slop": slop}}},
        sort=[{"_id": "asc"}],
    )
    return [h["_id"] for h in resp["hits"]["hits"]]


try:
    client.indices.create(
        index=INDEX,
        settings={"number_of_shards": 1, "number_of_replicas": 0},
        mappings={
            "properties": {
                "sku": {"type": "keyword"},
                "price": {"type": "float"},
                "text_docs": {"type": "text", "index_options": "docs"},
                "text_freqs": {"type": "text", "index_options": "freqs"},
                "text_pos": {"type": "text"},
                "text_off": {
                    "type": "text",
                    "index_options": "offsets",
                    "term_vector": "with_positions_offsets",
                },
            }
        },
    )

    ops = []
    for doc_id, sku, price, text in DOCS:
        ops.append({"create": {"_id": doc_id}})
        ops.append({
            "sku": sku, "price": price,
            "text_docs": text, "text_freqs": text,
            "text_pos": text, "text_off": text,
        })
    client.bulk(index=INDEX, operations=ops, refresh="wait_for")

    # match_phrase requires positions; freqs throws 400 BadRequestError
    try:
        phrase_ids("text_freqs")
        raise AssertionError("expected PhraseQuery rejection")
    except BadRequestError as exc:
        assert "without position data" in str(exc)

    # positions enable exact adjacency (slop 0), gaps (slop 1), transpositions (slop 2)
    assert phrase_ids("text_pos", slop=0) == ["1"]
    assert phrase_ids("text_pos", slop=1) == ["1", "2"]
    assert phrase_ids("text_pos", slop=2) == ["1", "2", "3"]

    # _termvectors reveals exact position + character offset spans stored for doc 2
    tv = client.termvectors(
        index=INDEX, id="2", fields=["text_off"], positions=True, offsets=True
    )
    terms = tv["term_vectors"]["text_off"]["terms"]
    assert terms["compact"]["tokens"][0] == {"position": 0, "start_offset": 0, "end_offset": 7}
    assert terms["keyboard"]["tokens"][0] == {"position": 2, "start_offset": 19, "end_offset": 27}

    # Unified highlighter uses offsets; exact SKU uses keyword inverted index
    hl = client.search(
        index=INDEX,
        query={"bool": {
            "must": [{"match": {"text_off": "compact"}}],
            "filter": [{"term": {"sku": "KB-02"}}, {"range": {"price": {"lte": 140}}}],
        }},
        highlight={"fields": {"text_off": {"type": "unified"}}},
    )
    assert hl["hits"]["hits"][0]["highlight"]["text_off"][0] == "<em>compact</em> mechanical keyboard"
    print({"slop_0": ["1"], "slop_1": ["1", "2"], "slop_2": ["1", "2", "3"], "highlight": hl["hits"]["hits"][0]["highlight"]})
finally:
    client.indices.delete(index=INDEX, ignore_unavailable=True)
Explain it aloud in an interview

“Inside every Lucene segment, an inverted index splits each term-based field into three parts: an off-heap FST term index pointing to sorted blocks in an on-disk term dictionary, and delta-compressed postings lists with skip lists. For multi-term intersections, the shortest postings list drives advance() across skip blocks; for top-k disjunctions, Block-Max metadata skips low-scoring blocks altogether. Each posting can store docs, freqs, positions (default for text so phrase and slop queries work), or offsets (so the Unified Highlighter avoids re-analyzing _source). Meanwhile, numeric ranges go to BKD trees and sorting or aggregations go to columnar doc values.”

Follow-ups to expect: why *timeout leading wildcards still scan the dictionary, why transposed adjacent words take slop: 2 rather than 1, when index_phrases: true helps, and why a numeric ID like order_id should be mapped as keyword instead of long.

Self-test

1. Why does Lucene split the vocabulary into an FST term index (.tip) and an on-disk term dictionary (.tim), and where does the FST live?

Holding every unique term in RAM would exhaust JVM heap on large indices. Instead, the sorted term dictionary stays on disk in prefix-compressed blocks (.tim), while a compact Finite State Transducer (.tip) maps prefixes to disk block offsets. Since Elasticsearch 7.7, the FST is memory-mapped off-heap in the OS page cache rather than pinned on the JVM heap.

2. How does Elasticsearch intersect gateway AND timeout when one term appears in 400 documents and the other in 3 million?

Postings lists store sorted internal docIDs and skip-list blocks. Lucene lets the shorter postings list (gateway) drive advance(targetDocID) calls against the longer list (timeout), jumping across entire skip blocks without decompressing or checking millions of intermediate docIDs.

3. You mapped a text field with index_options: "freqs" to save space. What works and what breaks?

Standard match queries and BM25 term-frequency scoring work normally, because docIDs and tf are indexed. Phrase queries (match_phrase, match_phrase_prefix, proximity spans) fail with a 400 error stating the field was indexed without position data, and changing it requires reindexing.

4. How should you speed up highlighting on large text fields: index_options: "offsets" or term_vector: "with_positions_offsets"?

Start with index_options: "offsets". Elasticsearch’s default Unified Highlighter reads character offsets directly from the postings list without re-analyzing _source, using far less disk space than term vectors. Use term_vector: "with_positions_offsets" only for the Fast Vector Highlighter (FVH) or massive (>1 MB) fields with complex multi-term queries.

5. Why does match_phrase: "compact keyboard" match "keyboard compact" at slop: 2 rather than slop: 1?

In Lucene, slop counts total position moves needed to align terms in the query’s relative order. With keyboard at position 0 and compact at position 1, moving compact left to position 0 puts both on top of each other (1 move), and moving it one more step to position −1 places it before keyboard (2 moves total).

6. Do numeric fields like price or order_id use an inverted index by default? When should a numeric identifier be mapped as keyword?

No — numeric, date, IP, and geo fields default to BKD trees for fast range queries, not inverted indexes. If an identifier like order_id only ever serves exact term / terms filters and aggregations (never ranges), map it as keyword so exact lookups hit the inverted index in one sorted dictionary pass rather than traversing a BKD tree repeatedly.
