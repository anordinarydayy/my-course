02Concept · Core · Elasticsearch

Documents, Indices & Data Streams

Lesson 01 ended at the JSON document. This lesson opens it: the identity and version fields wrapped around your data, the difference between what Elasticsearch stores and what it searches, and how to create, read, update and delete a document without losing a concurrent write. Then it steps up one level to the two kinds of container, a regular index for things you update and a data stream for events you only append.

Original study chapter. Written from scratch for backend, search, and platform interviews. Behavior and defaults target stable Elasticsearch 9.5 (Apache Lucene 10; latest patch 9.5.6 as of late 2026). The build block was run end to end against a single-node 9.5.6; runnable code uses Python 3 and elasticsearch==9.5.1. Contains six original figures, four interactive (press Play, or step with Next). Bulk and _cat follow in L03, segments in L05, refresh and the translog in L07, synthetic _source in L08, mappings in L09, shard routing in L22, and templates with lifecycle policies in L36.
00 The failure first

A lost update, and a log index that cannot be pruned

Start with what goes wrong.

A price-sync job and an admin screen both load product kb-75 in the same second. The job changes price, the screen changes stock, and each sends back the whole document it read. Whichever request lands second replaces the other’s change, because it carries the old value of the field the other one edited. Nothing errors and nothing is logged. Elasticsearch has no row locks and no multi-document transactions (L00), so it needs a cheap way for a writer to say “apply this only if the document is still the one I read”. Section 04 builds that from two numbers on every document.

The second failure is slow. A service writes every request log into one index. After six months the retention rule says to keep thirty days. A delete_by_query on old timestamps flags each match as deleted but frees no disk, because the data sits inside immutable segments until merges rewrite them, and the index keeps growing while it runs. Deleting a whole index, by contrast, removes files and costs almost nothing. The cure is to give each slice of time its own index. A data stream automates exactly that (Sections 05 and 06).

The order is therefore: the document and its envelope (01), what is stored versus what is searched (02), the four verbs (03), the concurrency check (04), and then the containers (05 and 06).

01 The unit of storage

A document is your JSON plus an envelope Elasticsearch adds

Lesson 01 drew the envelope as one box. Here is each field in it. You send a JSON object, and Elasticsearch stores it as one document with metadata fields whose names start with an underscore. You choose some of them (_id, _routing), the cluster assigns others (_version, _seq_no, _primary_term), and one holds your own body unchanged (_source).

FieldWho sets itWhat it holdsWatch out for
_index The URL you wrote to The name of the index that stores the document. On a data stream, hits report the hidden backing index (.ds-…), not the stream name.
_id You, or Elasticsearch when you omit it The document’s identity inside one index and the default input to shard routing (L22). At most 512 bytes. Unique per index only. It cannot be sorted on, aggregated, or used in scripts; copy it into a normal field if you need that.
_source You (stored as sent) The JSON body you sent. Stored and returned, but not searched. See Section 02.
_version Elasticsearch A per-document counter: 1 on creation, plus 1 on every update or delete. Not a concurrency token for ordinary writes (Section 04).
_seq_no The primary shard The position of a write in that shard’s history. It grows by one per write operation. Per shard, not per index. Every shard, and every backing index, has its own _seq_no 0.
_primary_term The cluster A counter that rises each time the shard gets a new primary. It rises when a replica is promoted, and also when an unassigned primary starts again: a single-node restart on 9.5.6 took it from 1 to 2.
_routing You, optionally A custom value used instead of _id to pick the shard. Send the same value on get, update and delete, or the request looks on the wrong shard (L22).

A few more underscore fields appear in the reference and matter later. _ignored lists fields skipped at index time (for example by ignore_malformed), _meta carries application notes attached to a mapping, and _tier exposes the data tier a shard sits on (L25).

Two limits shape how you design a document. _id is capped at 512 bytes, and the HTTP request body is capped by http.max_content_length, which defaults to 100 MB; Elastic’s advice for anything larger is to split it into smaller documents. Long before either limit, size matters for another reason: Section 03 shows that every update rewrites the whole document, so a 200 KB document that changes often is expensive.

02 What gets stored

_source is the copy you get back, not what search runs on ▸

When a document arrives, Elasticsearch does two separate jobs with it. First it reads each field through the index mapping and feeds the structures that field needs: an inverted index for text and keyword values, doc values for sorting and aggregations (L04 and L05 take these apart). Second it saves the JSON body, as you sent it, in a stored field called _source. A search runs against the first set of structures to find matching document IDs. Only afterwards does the fetch step read _source to fill in the hits.

These consequences show up in interviews.

  • What you sent is what comes back. Send "price": "129.0" (a string) to a float field and the index holds the number 129.0, so a range query on price matches and sorting is numeric. A GET still returns "129.0" as a string, because the stored copy is never rewritten to match the mapping.
  • Update, reindex and highlighting read _source. Setting _source.enabled to false saves disk and disables the update and reindex APIs, highlighting, and rebuilding an index under a new mapping. It is not allowed on logsdb and time_series indices. If disk is the worry, Elastic’s advice is to raise the compression level first.
  • Trimming a response is free; trimming storage is not. _source_includes and _source_excludes on a GET, or _source filtering in a search, shrink what travels over the network. The includes and excludes options inside the mapping change what is stored, and they carry a similar reindex penalty to disabling _source.

A newer option, synthetic _source, rebuilds the body from doc values on read to save disk, at the price of reordered keys and reshaped arrays. L08 covers it together with logsdb.

What the interviewer probes next

“I index {"age": "42"} into an integer field. What does GET return, and does age ≥ 40 match?” GET returns the string "42", because _source is the original body, and the range query matches, because the index holds the integer 42. The usual follow-up is how to read the indexed value back. Ask for the field with the fields option of a search, which returns the value as the mapping parsed it ([42] on 9.5.6).

03 Create, read, update, delete

Four verbs, and what each one really does to the shard ▸

The REST paths read like SQL verbs, but the behavior underneath differs in ways that catch people out. The table is the reference, and the rules after it explain the surprises.

RequestID already existsID missingVersion fields
PUT /i/_doc/1 Replaces the whole document. 200 updated. Creates it. 201 created. _version and _seq_no both advance, even when the body is identical.
PUT /i/_create/1 409 version conflict. Creates it. 201. Advance only on success.
POST /i/_doc Not applicable: Elasticsearch generates a new ID. Creates it. 201. _version 1; _seq_no advances.
POST /i/_update/1 Merges doc and rewrites the document: 200 updated, or noop when nothing changes. 404 document missing, unless upsert or doc_as_upsert is set. Advance, except on noop.
DELETE /i/_doc/1 Flags it deleted. 200 deleted. 404 not_found. Both advance. On 9.5.6 the 404 response advanced them too.
GET /i/_doc/1 200 with _source. 404 with "found": false. Unchanged. The response reports the current values.
  • Index replaces, create refuses. PUT /idx/_doc/<id> writes the whole document whether or not the ID exists. PUT /idx/_create/<id> (the same as ?op_type=create) is put-if-absent and answers 409 when the ID is taken. POST /idx/_doc with no ID always creates, and Elasticsearch invents a 20-character ID such as T0ju9qEBeWuI3y05PbeH. Elastic’s indexing-speed guidance favors generated IDs, because an explicit ID forces the shard to check whether it already exists.
  • Get is real time, search is not. A GET by ID sees a write at once. A search sees it after the next refresh, about one second later by default (L07). With refresh switched off on 9.5.6, a GET found a fresh document while a search returned zero hits until POST /idx/_refresh. GET /idx/_source/<id> returns just the body, and HEAD tests existence without one.
  • Update is read, merge, rewrite. POST /idx/_update/<id> with a doc merges your fields into the stored _source. Objects merge key by key, while arrays and scalars are replaced whole, so sending "tags": ["mech"] turns ["mech", "usb"] into ["mech"]. The shard then indexes the entire merged result as a new document and flags the old one as deleted. Nothing changes inside a segment, because segments are immutable (L01). _update does the read and the write on the server, so it saves a round trip and shrinks the window for a conflict between them; retry_on_conflict makes the server retry if one still happens. It saves no storage work. A call that changes nothing returns noop and writes nothing (detect_noop, on by default). A script handles increments and list edits, and upsert or doc_as_upsert create the document when it is missing. Without them a missing ID answers 404 document_missing_exception.
  • Delete flags, it does not erase. DELETE /idx/_doc/<id> advances the counters and flags the document. The bytes stay in their segment until a merge rewrites it. Elasticsearch also remembers the delete for index.gc_deletes, 60 seconds by default, so that a late versioned write can still be refused (Section 04).

Because an update rewrites the whole document, its cost grows with the size of the document, not with the size of the change. Bumping a view counter 200 times a second on a 40 KB document re-analyzes and re-stores 40 KB each time and leaves a flagged copy behind for merges to clear. Keep fast-changing fields out of large documents, or batch them.

What the interviewer probes next

“Is _update a partial, in-place update?” No. The shard rebuilds the full document from the merged _source and writes it as a new one; only the request is partial. Expect “so what does repeating the same update cost?” next. With detect_noop it costs a read and nothing else. A plain PUT of an identical body costs a full rewrite and a new version, because the index API does not compare.

04 Concurrency

Two writers, one document: optimistic concurrency ▸

Distributed locks are expensive, so Elasticsearch lets writers collide and then detects the collision. The primary shard stamps every write operation with a sequence number (_seq_no), one higher than the previous operation on that shard, together with the shard’s current primary term (_primary_term). Each GET and each write response carries the pair for the document’s latest change. Send that pair back as if_seq_no and if_primary_term, and the write succeeds only while that change is still the latest one. Otherwise the answer is 409 version_conflict_engine_exception.

A 409 is information. It means someone else changed the document after you read it. The standard response is to re-read, re-apply your change to the fresh copy, and retry with the new pair, with a cap on attempts. If the change commutes, such as adding to a counter or appending a tag, a scripted _update with retry_on_conflict runs that loop on the server for you. For changes that depend on the whole document, keep the loop in the client.

The primary term exists because histories can diverge when a primary fails. A promoted replica may hand out a sequence number that the old primary had already used for a write the other copies never received. The term tells the two apart, and the newer term wins, so the pair, not the number alone, names one change. Both numbers are scoped to a shard: _seq_no 0 exists in every shard of every index, so compare a pair only against the same document. In a data stream each backing index counts separately. In a test on 9.5.6 the first document in the second backing index got _seq_no 0 although the first index had already used 0 and 1.

_version cannot do this job on ordinary writes: a request with ?version=5 returns a 400 telling you to use if_seq_no and if_primary_term. It keeps one concurrency role, external versioning, and the two mechanisms answer different questions:

if_seq_no + if_primary_term

  • The token comes from Elasticsearch. Read it from a GET, or from a search with seq_no_primary_term: true.
  • Question answered: has anyone changed this document since I read it?
  • Fits read-modify-write code: admin screens, workers that merge changes, corrections to old events.
  • On a 409: re-read, re-apply, retry with a cap.

version_type=external

  • The number comes from your system of record: a row version or an event sequence.
  • Question answered: is my copy newer than what is stored? Equal or older is refused with a 409 (external_gte also accepts equal and is meant for special cases).
  • Fits database-to-Elasticsearch sync through change data capture (CDC) or an outbox (L00): a late replay of an older event is refused instead of overwriting newer state.
  • A delete keeps its version for index.gc_deletes (60 seconds by default), so a replay just after a delete is still refused.
The invariant

Of two writers holding the same token, at most one write is accepted, because the first accepted write moves the document to a new sequence number. This protects one document. A change that spans two documents has no such check and no transaction, which is why L00 keeps the system of record outside Elasticsearch.

What the interviewer probes next

“Two services update the same product. How do you stop lost updates?” Read the document with its token, write with if_seq_no and if_primary_term, and treat the 409 as a signal to re-read and retry. Then come the follow-ups: is _seq_no unique across the index (no, it is per shard), why is the primary term needed as well (diverging histories after a failover), and how would you handle stock -= 1 (a scripted _update with retry_on_conflict, or keep the counter in the system of record).

Version note

Elasticsearch 9.4 added an experimental index setting, index.disable_sequence_numbers, that drops sequence numbers to save storage. On such an index if_seq_no and if_primary_term are rejected and single-document _update is unsupported. It is off by default, can only be set when the index is created, and nothing in this course depends on it.

05 The container problem

Why one ever-growing index cannot be pruned

Logs, metrics and business events have a property that a product catalog lacks: they are written once and discarded by age. A retention rule such as “keep 30 days” is a statement about slices of time. Put everything in one index and the only tool that matches the rule is a query, POST app-logs/_delete_by_query on @timestamp.

That call frees no disk. Each match is flagged as deleted, and the bytes stay inside immutable segments until merges rewrite those segments (L05, L07). Elasticsearch also keeps a little recent history so replicas can catch up, so the deleted-document counter can lag a merge by a short while. Meanwhile the delete competes with indexing for I/O, the flagged documents still sit in the segments that every search scans, and the index keeps growing.

Dropping an index has no per-document cost, because it removes the shard files. The design that matches the retention rule therefore gives each slice of time its own index and deletes the oldest index whole. Before Elasticsearch 7.9 teams built this by hand: a write alias pointing at today’s index, a scheduled rollover, and a naming habit such as app-logs-2026.11.18. The data stream packages those parts under one name.

Where delete_by_query still belongs

Removing one customer’s documents for a privacy request is a small, selective delete, and delete_by_query is the right tool. The failure is using it as the retention engine for a stream of events.

06 Indices vs data streams

Data streams: one name over hidden backing indices ▸

A data stream is a name you read from and write to that fronts a list of hidden backing indices. It adds rules to a plain index, and each rule exists so that retention can be automatic.

  • It needs a template and a timestamp. The stream name must match an index template that contains data_stream: {}, and every document must carry @timestamp (date or date_nanos; if the template does not map it, Elasticsearch maps it as date). A document without it is rejected with a 400 document_parsing_exception. The first write to a matching name creates the stream, or you create it with PUT _data_stream/<name>. Templates, priorities and component templates belong to L36. Avoid names that match the built-in logs-*-* or metrics-*-* patterns unless you mean to override those templates; L33 covers the type-dataset-namespace naming scheme.
  • Writes go to the newest backing index only. That index is the write index. Older backing indices accept no new documents, even when you address them by name. Reads such as search go to every backing index.
  • A rollover starts a new generation. It creates the next backing index and makes it the write index. Names look like .ds-app-events-2026.11.20-000003: the .ds- prefix, the stream name, the creation date, and a six-digit generation that starts at 000001. Index lifecycle management (ILM) or a data stream lifecycle triggers it on age or size (L36), or you call POST /<stream>/_rollover. A stream built from a bare template, like the one in the build below, reports managed_by: Unmanaged in GET _data_stream: nothing rolls it over or expires it until you attach a lifecycle. Treat the backing-index name as opaque. Elastic documents the pattern as an implementation detail, and shrink or restore can rename an index.
  • Writes are append-only. Only op_type=create is accepted. POST /stream/_doc and PUT /stream/_create/<id> work. PUT /stream/_doc/<id> is refused with a 400, _bulk takes only create actions, and _update and DELETE against the stream name are refused too.

To change an event after the fact you have three routes. _update_by_query and _delete_by_query accept the stream name. For a single document, search with "seq_no_primary_term": true to learn its backing index, _id, _seq_no and _primary_term, then send an ordinary write to that backing index with if_seq_no and if_primary_term. Or reindex into a new target. GET by ID needs a concrete index: against the stream name it fails with index_not_found_exception on 9.5.6, so look the document up with an ids query, or go to the backing index.

The ID gotcha

_id is unique per index, not per stream. After a rollover, PUT /stream/_create/1 succeeds even though event 1 already sits in generation 1, and a search then returns two documents with _id 1, one per backing index (run on 9.5.6). Elastic’s guidance matches this: a stream suits data written without an ID, or with an ID where the first write wins. If you overwrite by ID often and expect the last write to win, use an alias with a write index instead.

Choose the container by the write pattern.

Regular index

  • Entities updated by ID: catalog, users, knowledge chunks.
  • Every write verb works, and _id is unique in the index.
  • Retention by delete_by_query is the costly part, so keep it for small, selective deletes.

Data stream

  • Append-only, timestamped events: logs, metrics, traces.
  • create only. Corrections go through a backing index or by-query calls.
  • Retention drops whole backing indices. Needs a template and @timestamp.

Alias + write index

  • Time slices where you still overwrite by _id and want the last write to win.
  • You manage the alias, the is_write_index flag and the first index yourself, usually with an ILM rollover alias.
  • Elastic documents it as the fallback when the append-only rules do not fit.

A time series data stream (TSDS), used for metrics, is a variant that routes each document to the backing index whose time range covers its @timestamp, instead of always to the newest. The rules above describe the standard kind.

The invariant

All writes land in the newest backing index and are create-only, so every older backing index changes only through deliberate corrections. That is what makes it safe to delete a whole backing index when its time slice expires.

What the interviewer probes next

“Why not just use daily indices with an alias?” You can, and before 7.9 everyone did. A data stream removes the alias bookkeeping and refuses overwrites, which is a feature for logs and a limit for anything you correct by ID. Expect “what happens at rollover?” (a new backing index becomes the write index while clients keep the same name) and “how do you fix one bad event?” (the backing index with if_seq_no, or a by-query call).

07 Worked example

Build: a lost update prevented, a stream rolled over

The block below runs both halves of the lesson on one node. Replicas are set to 0 so a single node stays green and every _seq_no is easy to follow. Part 1 makes two writers collide on one document. Part 2 creates a data stream, rolls it over, and corrects an old event through its backing index. Run the requests in Kibana Dev Tools or with curl, or run the Python script, which asserts each claim above. Both were run against a single-node Elasticsearch 9.5.6.

Worked build Index + data stream Elasticsearch 9.5 · elasticsearch==9.5.1
Two writers on one document, then a stream and a rollover

Create an index with one shard and no replica. Write kb-75, show that _source keeps the string you sent, update it, repeat the update to get a noop, and let two writers race with the same token so that one gets a 409. Then create a data stream from a minimal template, show that PUT _doc/<id> is refused, roll the stream over, and correct an old event through its backing index.

Think it through

1 · Identity

Use _create so that a repeated ID is a 409 instead of a silent overwrite, and read _version, _seq_no and _primary_term from every response.

2 · Stored vs indexed

Send price as the string "129.0". A GET returns the string, while a range query still matches, because the index holds a number.

3 · The race

Both writers GET the document and keep the pair. A writes with it and wins. B sends the same pair and gets a 409, re-reads, re-applies its change on top of the fresh copy, and retries with the new pair.

4 · The container

A data stream needs a template with data_stream. The first write creates it, PUT _doc/<id> is refused, and a rollover adds generation 2, which becomes the write index.

5 · The correction

Search with seq_no_primary_term to find the old event’s backing index and token, then write to that backing index with if_seq_no and if_primary_term.

2 · Equivalent Python script

python 3 · pip install elasticsearch==9.5.1 · local dev node on http://localhost:9200

import uuid
from datetime import datetime, timezone

from elasticsearch import BadRequestError, ConflictError, Elasticsearch

client = Elasticsearch("http://localhost:9200")
RUN = uuid.uuid4().hex[:8]
INDEX = f"lab-docs-{RUN}"
STREAM = f"lab-events-{RUN}"
TEMPLATE = f"lab-events-tpl-{RUN}"
ID = "kb-75"


def raises(error, call, **kwargs):
    try:
        call(**kwargs)
    except error:
        return True
    return False


try:
    # Part 1: one regular index, one document, two competing writers
    client.indices.create(
        index=INDEX,
        settings={"number_of_shards": 1, "number_of_replicas": 0},
        mappings={"properties": {
            "sku": {"type": "keyword"}, "title": {"type": "text"},
            "price": {"type": "float"}, "stock": {"type": "integer"},
        }},
    )
    doc = {"sku": "KB-75", "title": "Compact mechanical keyboard",
           "price": "129.0", "stock": 40}
    made = client.create(index=INDEX, id=ID, document=doc, refresh="wait_for")
    assert (made["result"], made["_version"], made["_seq_no"]) == ("created", 1, 0)
    assert raises(ConflictError, client.create, index=INDEX, id=ID, document=doc)

    # _source keeps the string we sent; the index compared it as a number
    assert client.get(index=INDEX, id=ID)["_source"]["price"] == "129.0"
    found = client.search(index=INDEX, query={"range": {"price": {"lte": 150}}})
    assert [h["_id"] for h in found["hits"]["hits"]] == [ID]

    # a partial update rewrites the whole document; a repeat changes nothing
    updated = client.update(index=INDEX, id=ID, doc={"price": 119.0})
    assert (updated["result"], updated["_version"]) == ("updated", 2)
    repeat = client.update(index=INDEX, id=ID, doc={"price": 119.0})
    assert repeat["result"] == "noop"

    # both writers read the same version, then race to write it back
    seen = client.get(index=INDEX, id=ID)
    token = {"if_seq_no": seen["_seq_no"], "if_primary_term": seen["_primary_term"]}
    winner = {**seen["_source"], "price": 115.0}
    loser = {**seen["_source"], "stock": 35}
    client.index(index=INDEX, id=ID, document=winner, **token)
    stale = dict(index=INDEX, id=ID, document=loser, **token)
    assert raises(ConflictError, client.index, **stale)

    # the loser re-reads, re-applies its change on the fresh copy, and retries
    fresh = client.get(index=INDEX, id=ID)
    retry = {**fresh["_source"], "stock": 35}
    client.index(
        index=INDEX, id=ID, document=retry,
        if_seq_no=fresh["_seq_no"], if_primary_term=fresh["_primary_term"],
    )
    final = client.get(index=INDEX, id=ID)["_source"]
    # neither change was lost
    assert (final["price"], final["stock"]) == (115.0, 35)

    # four versions were written; the three superseded ones are only flagged
    client.indices.refresh(index=INDEX)
    stats = client.indices.stats(index=INDEX, metric="docs")
    docs = stats["_all"]["primaries"]["docs"]
    assert (docs["count"], docs["deleted"]) == (1, 3)

    # Part 2: a data stream needs a template that enables it
    client.indices.put_index_template(
        name=TEMPLATE, index_patterns=[STREAM], data_stream={}, priority=500,
        template={
            "settings": {"number_of_shards": 1, "number_of_replicas": 0},
            "mappings": {"properties": {
                "@timestamp": {"type": "date"},
                "level": {"type": "keyword"},
                "message": {"type": "text"},
            }},
        },
    )
    now = datetime.now(timezone.utc).isoformat()
    event = {"@timestamp": now, "level": "info", "message": "started"}
    # the first write creates the stream
    logged = client.index(index=STREAM, document=event)
    assert logged["_index"].startswith(f".ds-{STREAM}-")
    assert logged["_index"].endswith("-000001")
    refused = dict(index=STREAM, id="1", document=event)
    assert raises(BadRequestError, client.index, **refused)

    client.indices.rollover(alias=STREAM)
    stream = client.indices.get_data_stream(name=STREAM)["data_streams"][0]
    assert stream["generation"] == 2 and len(stream["indices"]) == 2
    newest = client.index(index=STREAM, document=event)
    assert newest["_index"] == stream["indices"][-1]["index_name"]

    # an old event is corrected through its own backing index, guarded by seq_no
    fixed = {**event, "level": "error"}
    corrected = client.index(
        index=logged["_index"], id=logged["_id"], document=fixed,
        if_seq_no=logged["_seq_no"], if_primary_term=logged["_primary_term"],
    )
    assert corrected["result"] == "updated"
    print({"final_doc": final, "write_index": newest["_index"]})
finally:
    quiet = client.options(ignore_status=404)
    quiet.indices.delete_data_stream(name=STREAM)
    quiet.indices.delete_index_template(name=TEMPLATE)
    quiet.indices.delete(index=INDEX)

The finally block deletes the stream before its template, because a template that a data stream uses cannot be deleted. The stream name is also the template’s only index pattern, so a leftover template from another run cannot collide with it.

Explain it aloud in an interview

“A document is a JSON body plus an envelope. The body is stored as _source exactly as sent, and the search structures are built from it separately, which is why a string price still matches a numeric range. An update rewrites the whole document into a new segment and flags the old one, so two writers who each send back a full copy overwrite each other. I prevent that by reading _seq_no and _primary_term with the document and sending them back as if_seq_no and if_primary_term. The stale writer gets a 409, re-reads, re-applies its change and retries. For events I use a data stream: one name over hidden backing indices, writes only to the newest, create only, and retention that deletes whole indices instead of documents.”

Follow-ups to expect: why docs.deleted is 3 while docs.count is 1 (four versions were written and three are flagged), why the second backing index starts again at _seq_no 0, why a GET by ID against the stream name returns 404, and how you would keep a fast-changing counter out of a large document.

Self-test

1. What is the difference between _version and _seq_no, and which one stops a lost update?

_version counts changes to one document: 1 on creation, plus 1 on every update or delete. _seq_no is a per-shard counter of write operations, assigned by the primary. A lost update is stopped by sending the document’s _seq_no and _primary_term back as if_seq_no and if_primary_term; a stale pair gets a 409. Ordinary writes refuse ?version= with a 400. _version matters with version_type=external, where your system of record supplies the number.

2. A GET returns price as the string "129.0" although the field is a float and a range query on it matches. Why?

_source is the original body, stored exactly as sent. The index structures are built separately from the mapping, which parsed the string into the number 129.0. Search runs on those structures, and the fetch step returns the untouched _source.

3. Is POST /idx/_update/1 an in-place partial update, and what does repeating it cost?

No. The shard reads the current _source, merges your doc, indexes the whole result as a new document in a new segment, and flags the old version as deleted. The cost grows with document size. A repeat that changes nothing returns noop and writes nothing, because detect_noop is on by default.

4. Why does delete_by_query not free disk right away, and what does a data stream do instead?

A delete only flags documents inside immutable segments, and space returns when merges rewrite those segments. A data stream splits data into time-sliced backing indices, so retention deletes the oldest backing index whole. That removes its files with no per-document work.

5. Why does PUT /my-stream/_doc/1 fail, and how do you write and later correct an event?

A data stream accepts only op_type=create, which keeps it append-only so that whole backing indices can be dropped later. Write with POST /my-stream/_doc or PUT /my-stream/_create/1. To correct an event, use _update_by_query or _delete_by_query on the stream, or search with seq_no_primary_term to find its backing index and token and write to that backing index with if_seq_no and if_primary_term.

6. After a rollover, PUT /my-stream/_create/1 succeeds although an event with _id 1 already exists. Is that a bug?

No. _id is unique per index, and each backing index is its own index, so the new write index has no document 1 and the stream ends up holding two. First-write-wins holds only inside one backing index. If you overwrite by ID and want the last write to win, use an alias with a write index instead.
