JSONB & Semi-structured Data

Sometimes the shape of your data varies row to row — product attributes, event payloads, external API blobs — and a rigid table of columns fights you. PostgreSQL's jsonb type lets a single column hold a whole document you can still query and index. This lesson teaches the operators, the GIN index that makes them fast, and the one design rule that keeps a document column from becoming a swamp: model what you filter and join; bag only the flexible tail.

00 The trade

A row of columns vs. one document

The relational model wants every row to have the same, declared columns. That is a feature: the schema is a contract, the planner knows the types, and constraints catch bad data. But some data genuinely doesn't fit a fixed shape. A products table where a T-shirt has size, a mug has oz, and a laptop has ram_gb would need dozens of mostly-NULL columns — a sparse, ever-growing schema. That's where a semi-structured column earns its place.

Postgres offers two JSON column types, and the choice is not close for most work:

json — text

  • Stores the exact input text, whitespace and duplicate keys included.
  • Re-parses on every read and every operator call.
  • Cannot be indexed with GIN for containment.
  • Only useful if you must preserve byte-for-byte fidelity.

jsonb — binary

  • Stored decomposed: keys sorted, duplicates dropped, numbers normalized.
  • Parsed once on write; fast to read and operate on.
  • Indexable with GIN — the whole point of this lesson.
  • The default choice; whitespace and key order are not preserved.

sql

CREATE TABLE events (
  id    bigint PRIMARY KEY,
  raw   json,    -- stored as exact text; re-parsed on every read
  data  jsonb    -- decomposed binary; sorted keys, deduped, indexable
);

So the real question is never "json or jsonb" (almost always jsonb) — it's column or document. Use a document when the fields are sparse, variable, or you don't query them individually (an audit payload you only ever read whole). Use real columns when you filter, join, sort, or constrain on a field — those are the operations a document column does slowly and a typed column does well. Most tables end up mixed: a spine of real columns plus a jsonb tail for the parts that vary.

The one-line rule

jsonb is for the fields you keep, not the fields you query. The moment a field becomes a filter, a join key, or a sort key, it wants to be a real column (or a promoted generated column). Reach for a document to absorb variety, not to avoid designing a schema.

01 The operators

Reaching into a document ▸

To use a document you have to pull pieces out of it, and Postgres gives you a small operator vocabulary. The trickiest split is arrow vs. double-arrow: -> keeps the result as jsonb, while ->> returns text. That one character decides whether you can cast and compare the value or whether you'll get a confusing type error. Step through each operator on a single document:

Here is the full operator toolkit in one query. Read the comments — they are the whole cheat sheet:

sql

SELECT
  data -> 'color'            AS color_json,   -- jsonb :  "red"
  data ->> 'color'           AS color_text,   -- text  :  red
  data #> '{specs,weight}'   AS w_json,       -- path  → jsonb
  data #>> '{specs,weight}'  AS w_text,       -- path  → text
  data @> '{"color":"red"}'  AS has_red,      -- contains?   → boolean
  data ? 'size'               AS has_size      -- key exists? → boolean
FROM products;

Two more you'll reach for constantly. ?| and ?& test whether any or all of a list of keys exist. And the SQL/JSON path language — jsonb_path_query to extract and the @@ operator to test a boolean path predicate — handles nesting and array wildcards cleanly:

sql

SELECT jsonb_path_query(data, '$.tags[*]') FROM products;   -- one row per tag
SELECT * FROM products WHERE data @@ '$.specs.weight > 100'; -- path predicate
-> vs ->> is the operator people get wrong

data -> 'weight' gives you a jsonb 200; comparing that to an integer fails or behaves oddly. You want (data ->> 'weight')::int — double-arrow to text, then cast to the type you actually mean. Rule of thumb: use -> only when you'll keep drilling deeper into JSON; use ->> at the leaf where you want a real scalar.

02 Making it fast

Indexing jsonb with GIN ▸

A WHERE data @> '{...}' filter on an unindexed jsonb column is a Seq Scan that re-examines every row. The fix is a GIN (Generalized Inverted iNdex): instead of one entry per row like a btree, GIN stores many entries per row — one per indexable piece of the document — and maps each back to the rows that contain it. That inverted structure is exactly what containment queries need. Watch the query flow through it:

There are two GIN operator classes for jsonb, and the choice is a real trade-off:

sql

-- default opclass (jsonb_ops): indexes keys AND values → serves @>, ?, ?|, ?&
CREATE INDEX idx_attrs      ON products USING GIN (attrs);

-- jsonb_path_ops: hashes key→value paths → smaller/faster; serves @> @? @@ but NOT key-existence ?
CREATE INDEX idx_attrs_path ON products USING GIN (attrs jsonb_path_ops);

Pick jsonb_path_ops when your only jsonb filter is containment (@>) — it produces a smaller index and fewer index entries to probe. Keep the default jsonb_ops if you also need key-existence tests (?, ?|, ?&), which jsonb_path_ops cannot serve. Either way, note two facts the diagram made concrete: the GIN match is lossy, so the plan always ends with a Recheck Cond on the heap; and GIN writes are expensive — one row insert can mean many index entries, which is why bulk loads often drop and rebuild the GIN, and why fastupdate batches new entries in a pending list.

Index the operator you actually run

A GIN index accelerates @>, ?, and friends — it does not help attrs ->> 'color' = 'red', because that is a function of the column, not a containment test. If ->>-style equality is your access pattern, you need a different index: an expression index on ((attrs ->> 'color')), or better, promote the field to a generated column (next section). Matching the index to the exact operator is the whole game.

03 The design rule

Model what you filter; bag what you don't

The failure mode with document columns is putting everything in the blob and then fighting the database to query it. The discipline is a split: promote the fields you filter, join, sort, or constrain into real columns; leave the sparse, rarely-queried tail in jsonb. Postgres gives you a clean tool for the promotion — a generated column — so you don't have to duplicate data or write triggers:

sql

CREATE TABLE products (
  id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sku    text NOT NULL UNIQUE,
  name   text NOT NULL,
  price  numeric(10,2) NOT NULL,
  attrs  jsonb NOT NULL DEFAULT '{}',
  -- promote a hot field into a real, indexable column
  color  text GENERATED ALWAYS AS (attrs ->> 'color') STORED,
  CONSTRAINT attrs_is_object CHECK (jsonb_typeof(attrs) = 'object')
);
CREATE INDEX ON products (color);                        -- btree: =, ranges, ORDER BY
CREATE INDEX ON products USING GIN (attrs jsonb_path_ops);  -- the flexible tail

Three things are working together there. The CHECK (jsonb_typeof(attrs) = 'object') stops someone storing a bare array or a JSON null where you expect an object — a document column still deserves constraints. The STORED generated column materializes color on write so a plain btree can serve color = 'red', ORDER BY color, and range scans — none of which GIN does well. (PG18 also adds VIRTUAL generated columns, computed on read; use STORED when you want to index the value.) And the GIN index still covers ad-hoc containment on the rest of attrs.

A related guardrail is CHECK (attrs ? 'sku')-style assertions to require keys you depend on, and remembering that SELECT * over a fat jsonb column ships the whole document every time — it defeats index-only scans and wastes bandwidth. Select the fields you need, not the blob.

Generated column, not a copy

A STORED generated column is derived by the database from attrs — you can't write it directly, and it can never drift out of sync the way an application-maintained duplicate column would. That is the safe way to "have your cake and eat it": one source of truth in jsonb, plus a typed, indexable projection of the hot field.

04 Worked problem

A product catalog with variable attributes ▸

Now put it together. You run a marketplace where every product type carries different attributes, and the catalog page must filter by them. Here is the schema and the data shape:

sql

CREATE TABLE products (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL,
  attrs jsonb NOT NULL DEFAULT '{}'
);
-- ~2,000,000 rows; roughly 4% of them are {"color":"red", ...}
-- shapes vary: {"color","size"}, {"color","oz"}, {"pages"}, ...

The task: return every red product, fast — and be ready when the product team asks to sort and page by color, too. Step through the catalog and the two ways to serve it:

The naive attempt — and why it's slow

The instinct from the operator section is to extract the field and compare it:

sql

SELECT id, name
FROM   products
WHERE  attrs ->> 'color' = 'red';   -- extracts text per row

It returns the right rows, but attrs ->> 'color' is a function of the column, not a containment predicate — a plain GIN index on attrs can't serve it, so the planner reads every row:

illustrative

Seq Scan on products  (cost=0.00..64500.00 rows=80000 width=25)
                      (actual time=0.02..612.4 rows=80000 loops=1)
  Filter: ((attrs ->> 'color'::text) = 'red'::text)
  Rows Removed by Filter: 1920000

Two million rows read, 1.92M thrown away by the Filter. On a busy catalog page, unacceptable.

The fix — containment plus a GIN index

Rewrite the predicate as containment so an index can serve it, and build the GIN. Since we only need @>, use the smaller jsonb_path_ops opclass:

sql

CREATE INDEX idx_products_attrs ON products USING GIN (attrs jsonb_path_ops);

SELECT id, name
FROM   products
WHERE  attrs @> '{"color":"red"}';   -- containment: the index can serve it

Now the planner probes the GIN, gathers candidate row pointers as a bitmap, fetches just those heap pages, and rechecks:

illustrative

Bitmap Heap Scan on products  (cost=44.0..2100.0 rows=80000 width=25)
                             (actual time=6.1..21.7 rows=80000 loops=1)
  Recheck Cond: (attrs @> '{"color": "red"}'::jsonb)
  Heap Blocks: exact=1580
  ->  Bitmap Index Scan on idx_products_attrs  (cost=0.00..24.0 rows=80000 width=0)
        Index Cond: (attrs @> '{"color": "red"}'::jsonb)

From ~612 ms of full scan to ~22 ms — because the Bitmap Index Scan jumps straight to the ~80k candidate rows instead of touching 2M. The Recheck Cond is expected: GIN is lossy, so the heap step re-verifies the JSON before returning each row.

When color becomes a first-class field

The product team now wants ORDER BY color and paging — operations a GIN can't do (it has no order). That's the signal to promote color:

sql

ALTER TABLE products
  ADD COLUMN color text GENERATED ALWAYS AS (attrs ->> 'color') STORED;
CREATE INDEX idx_products_color ON products (color);

SELECT id, name FROM products WHERE color = 'red' ORDER BY name;

The btree on color now serves equality, ranges, and ordering, and the query planner can even combine it for sorted paging. The attrs column keeps every other rare attribute; you promoted exactly the one field that graduated from "stored" to "queried."

Narrate it

"Attributes vary by product type, so I keep them in a jsonb column instead of dozens of sparse columns. To find red products I filter with containment — attrs @> '{\"color\":\"red\"}' — because a GIN index accelerates @>, giving a Bitmap Index Scan and a heap recheck instead of a Seq Scan; I choose jsonb_path_ops since containment is all I need. Once color also needs sorting and paging, I promote it to a STORED generated column with a btree, and leave the long tail in jsonb. Model what you query; bag what you don't."

05 Drills & traps

Practice, then the traps

Assume the catalog schema from above: products(id, name, attrs jsonb) with a GIN index on attrs. Try each drill before opening the solution.

Drill 1 — containment vs. existence

Write two queries: (a) products that have a size key at all, whatever its value; (b) products whose size is exactly "L".

Try it first, then read

SELECT * FROM products WHERE attrs ? 'size';  and  SELECT * FROM products WHERE attrs @> '{"size":"L"}';
Why: ? tests key presence only; @> tests a full key + value pair. (Note: ? needs the default jsonb_ops GIN — jsonb_path_ops won't index it.)

Drill 2 — the numeric-compare trap

Find products with oz greater than 10. First predict what the "obvious" version does wrong.

Try it first, then read

Wrong: WHERE attrs ->> 'oz' > '10' — that compares text, so '9' > '10' is true and '120' > '99' is false. Fix by casting: WHERE (attrs ->> 'oz')::int > 10, or use a path predicate: WHERE attrs @@ '$.oz > 10'.
Why: ->> always yields text; string comparison is lexicographic. Cast to a numeric type, or let the SQL/JSON path engine compare numbers for you.

Drill 3 — matching inside an array

Find products tagged "sale", where attrs looks like {"tags":["new","sale"]}.

Try it first, then read

SELECT * FROM products WHERE attrs @> '{"tags":["sale"]}';
Why: containment on an array asks "does this array contain these elements?" — so {"tags":["sale"]} matches any row whose tags array includes "sale". And the GIN index serves it, just like a scalar @>.

Drill 4 — choosing the opclass

Your catalog only ever filters with @> — never key-existence, never ?. Which GIN operator class do you build, and why? Write the index.

Try it first, then read

CREATE INDEX idx_attrs ON products USING GIN (attrs jsonb_path_ops);
Why: jsonb_path_ops indexes hashed key→value paths only — roughly 2–3× smaller and faster to probe than the default jsonb_ops — and it serves the containment/path operators (@>, @?, @@). You give up only key-existence (?/?|/?&), which you don't run.

The trap list — carry these

• ->> returns text — cast before any numeric or date comparison.
• @> is containment, ? is existence — different questions; don't swap them.
• GIN doesn't help ->> equality — you need an expression index or a generated column.
• jsonb_path_ops can't serve ? — pick the opclass by the operators you actually run.
• GIN writes are heavy — one row can mean many index entries; watch bulk-load and update cost.
• Deep nesting hides intent — if you constantly filter $.a.b.c, that field wants to be a column.
• SELECT * over fat jsonb — ships the whole blob and kills index-only scans; select fields.
• The recheck is normal — GIN is lossy, so a Bitmap Heap Scan always re-verifies the condition.

★ Review

Summary & self-test

One idea holds the lesson together: jsonb absorbs variety, and a GIN index makes containment on it fast — but any field you filter, sort, join, or constrain wants to graduate into a real (often generated) column. Use the document for the flexible tail, not as an excuse to skip schema design.

01jsonb, not jsonBinary, deduped, sorted, parsed once — and indexable. Reach for json only to preserve exact text.
02-> vs ->>Arrow keeps json; double-arrow returns text. Use ->> at the leaf, then cast for numbers or dates.
03@> is the workhorseContainment answers "does the doc contain this?" and is what GIN accelerates — filter with it, not ->>.
04? is existenceTests only whether a key is present. Different question from containment; needs the default jsonb_ops GIN.
05GIN, two opclassesjsonb_ops serves @>,?,?|,?&; jsonb_path_ops is smaller/faster but @> only.
06Bitmap + recheckA @> query plans as Bitmap Index Scan → Bitmap Heap Scan with a lossy Recheck Cond. Reads fast, writes cost.
07Promote hot fieldsA STORED generated column + btree gives equality, ranges, and ORDER BY that GIN can't.
08Model what you queryFiltered/joined/sorted fields → columns; sparse tail → jsonb. Constrain with CHECK; avoid SELECT *.

Cover the notes and answer aloud:
(1) Why jsonb over json in almost every case? Name two concrete differences.
(2) What does -> return vs ->>, and why does that decide whether > 10 works?
(3) Contrast @> and ? with an example of a query each one — and only one — can answer.
(4) Walk the plan for WHERE attrs @> '{"color":"red"}' with a GIN index. Why is there a Recheck Cond?
(5) When do you pick jsonb_path_ops over jsonb_ops, and what do you give up?
