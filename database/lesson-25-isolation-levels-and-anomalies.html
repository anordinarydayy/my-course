Isolation Levels & Anomalies

Run two transactions at once and the database can produce answers no serial order ever could — a value that changes mid-read, a total that quietly loses money, an invariant that both sides break at once. An isolation level is the contract that says which of those anomalies you might see, traded against how much concurrency you keep. This lesson names the anomalies, then shows the three levels PostgreSQL actually gives you — and how it quietly beats the SQL standard.

00 Orientation

Concurrency needs rules

A single transaction, running alone, is easy to reason about: statements happen in order, and the database moves from one valid state to the next. The trouble starts when many transactions run at the same time and the engine interleaves their reads and writes to keep the machine busy. That interleaving can produce a result that no serial order of those transactions could ever produce — and that is the precise definition of a concurrency bug. If some serial order (A-then-B, or B-then-A) would give the same answer, you're fine. When none does, you've hit an anomaly.

The obvious fix — run everything one at a time — throws away all your throughput. So databases offer a dial. An isolation level is a formal promise about which anomalies the engine guarantees you will never see, in exchange for how much concurrency it must give up to keep that promise. Weaker levels are cheaper and more parallel but let more anomalies through; stronger levels forbid more but cost more coordination (and, in Postgres, more retries).

The one-line definition to anchor

An isolation level is a contract about anomalies, not about speed. It never says “go faster”; it says “these specific bad interleavings cannot happen to you.” Choosing a level is choosing how much you'll pay — in concurrency and in retries — to be protected from a particular class of bug.

The SQL standard defines four isolation levels — Read Uncommitted, Read Committed, Repeatable Read, and Serializable — and defines them by which anomalies each one forbids. PostgreSQL implements only three distinct behaviors: it accepts READ UNCOMMITTED as a keyword but treats it exactly like Read Committed, because Postgres never shows uncommitted data to anyone. And where the standard merely sets a floor, Postgres is routinely stricter than required — most famously, its Repeatable Read forbids phantom reads, which the standard permits. So the standard is the map; Postgres's actual behavior is what you must know.

01 The vocabulary

The anomalies ▸

Before you can pick a level, you need names for the things a level protects you from. There are five that matter, roughly from “weakest to allow” to “hardest to catch”:

  • Dirty read — you read a row another transaction has written but not yet committed. If that writer rolls back, you acted on data that never existed. PostgreSQL never allows this — at any level, including Read Committed.
  • Non-repeatable read — you read a row, and when you read the same row again later in the same transaction, its value has changed because another transaction committed an update in between.
  • Phantom read — you run a range query (say WHERE age > 30) twice, and the second run returns a different set of rows because another transaction inserted or deleted rows that match.
  • Lost update — two transactions each read a value, compute a new one from it, and write it back; the second write clobbers the first, and one update silently vanishes.
  • Write skew — the sneaky one. Two transactions each read an overlapping set of rows, check a shared constraint that currently holds, and each writes to a different row. Individually every write is legal; together they break an invariant that no single-row conflict can catch.

The clearest one to watch is the non-repeatable read, because it needs only two transactions and one row. A reader sees 100; a writer commits 120; the reader asks again and the answer has moved:

Notice what did not happen: T1 never saw an uncommitted value. It only ever read committed data — first the committed 100, then the committed 120. That's why this is not a dirty read; it's a non-repeatable read, and it is perfectly legal at Read Committed. The distinction between “you saw someone's uncommitted work” (never in Postgres) and “committed data moved under you between two of your reads” (allowed at the default level) is the hinge the next two sections turn on.

Anomalies are about interleavings, not bugs in your code

Every anomaly above assumes each transaction, run alone, is correct. The problem is purely the interleaving the engine chose. That's why you can't fix them by writing more careful application logic in isolation — you fix them by choosing an isolation level (or taking explicit locks) that forbids the bad interleaving in the first place.

02 The three levels

Postgres’s three levels

Three levels, three contracts. You set one per transaction (or as a session/database default), and it governs every statement until COMMIT.

sql

-- pick a level for one transaction, two equivalent ways
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
  -- ... statements ...
COMMIT;

BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;   -- before the first query of the txn
  -- ...
COMMIT;

READ COMMITTED is the default. Every statement takes a fresh snapshot at the moment it starts, so it always sees data committed before it began — never a dirty read. But because each statement re-snapshots, two statements in the same transaction can disagree: non-repeatable reads and phantoms are both possible. It is cheap, highly concurrent, and correct for the great majority of short OLTP work.

REPEATABLE READ is Postgres's implementation of snapshot isolation: the transaction takes one snapshot at its first query and every statement sees that same frozen picture. No dirty reads, no non-repeatable reads, and — here Postgres is stronger than the SQL standard — no phantoms either. The catch is twofold: write skew is still possible, and if you update a row that another transaction has already updated and committed since your snapshot, Postgres cannot silently reconcile it, so it raises a serialization_failure (SQLSTATE 40001) and you must retry the whole transaction.

SERIALIZABLE adds Serializable Snapshot Isolation (SSI) on top of Repeatable Read. It tracks the read/write dependencies between concurrent transactions and, when it spots a dangerous structure among them (two consecutive read-write anti-dependencies — the fingerprint of a possible non-serializable cycle), it aborts one participant with the same 40001. It errs on the safe side, so it can occasionally abort a transaction that would in fact have been fine. The guarantee is complete: the outcome is always equivalent to running the transactions one at a time in some order, so every anomaly — including write skew — is gone. The price is again mandatory retries, and a little bookkeeping overhead.

Read Committed

  • Dirty read: never
  • Non-repeatable read: possible
  • Phantom: possible
  • Write skew: possible
  • Snapshot: fresh per statement

Repeatable Read

  • Dirty read: never
  • Non-repeatable read: never
  • Phantom: never (beats the standard)
  • Write skew: still possible
  • One snapshot; conflicts → 40001

Serializable

  • Dirty read: never
  • Non-repeatable read: never
  • Phantom: never
  • Write skew: never
  • True serial order; may abort with 40001
Read the table as a ladder

Each level forbids everything the weaker one does, plus more. Read Committed blocks only dirty reads; Repeatable Read adds non-repeatable reads and phantoms; Serializable adds write skew and every remaining cycle. The higher you climb, the fewer surprises — and the more often you must catch 40001 and retry. There is no free rung.

03 Same script, two levels

Read Committed vs Repeatable Read ▸

The difference between the two everyday levels is easiest to feel by running the identical operations at each and watching where they diverge. Session A reads a row, Session B commits a new value in between, and A reads again. The only thing that changes is the isolation level A chose:

sql

-- Session A at READ COMMITTED (the default)
BEGIN;
SELECT balance FROM accounts WHERE id = 1;   -- 100
        -- ... Session B: UPDATE accounts SET balance = 120 WHERE id = 1; COMMIT; ...
SELECT balance FROM accounts WHERE id = 1;   -- 120  ← fresh snapshot, changed!
COMMIT;

-- Session A at REPEATABLE READ
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;   -- 100
        -- ... same concurrent UPDATE to 120 commits here ...
SELECT balance FROM accounts WHERE id = 1;   -- 100  ← one frozen snapshot, unchanged
COMMIT;

The mechanism behind the split is a single design choice: when is the snapshot taken? Read Committed re-snapshots at the start of every statement, so A's second SELECT sees whatever is committed by then — the value moved. Repeatable Read snapshots once, at the transaction's first query, and every later statement reuses it — so B's commit is simply invisible to A until A commits and starts fresh. Neither is “more correct”; they answer different questions. Read Committed asks “what is true right now?”; Repeatable Read asks “what was true when I started?”

Reach for Repeatable Read when a report must be self-consistent

Any transaction that runs several queries and needs them to agree — a balance sheet that sums three tables, a page that reads a parent then its children — wants Repeatable Read, so all of it reflects one instant. Under Read Committed those queries can straddle other people's commits and quietly contradict each other. That's the practical reason to climb a rung: not paranoia, but a stable picture.

04 The sneaky anomaly

Write skew & Serializable ▸

Repeatable Read stops non-repeatable reads and phantoms, so it's tempting to treat it as “safe enough.” But one anomaly slips right through it, and it's the one interviewers love because snapshot isolation looks bulletproof until you see it fail. The classic example: an on-call schedule with the invariant “at least one doctor must always be on call.” Two doctors, Alice and Bob, are both on. Each independently decides to go off, and each checks the rule first — “only go off if another doctor is still on.”

sql

-- schema
CREATE TABLE on_call (
  doctor   text PRIMARY KEY,
  on_call  boolean NOT NULL
);
INSERT INTO on_call VALUES ('alice', true), ('bob', true);

-- Session A (Alice)                    Session B (Bob) -- both at REPEATABLE READ
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;   -- (B runs the same BEGIN)
-- go off only if someone ELSE is still on call:
SELECT count(*) FROM on_call
  WHERE on_call AND doctor <> 'alice';   -- A sees 1 (bob)  → allowed
                                        -- B sees 1 (alice) → allowed
UPDATE on_call SET on_call = false WHERE doctor = 'alice';
                                        -- B: UPDATE ... WHERE doctor = 'bob';
COMMIT;                                 -- B: COMMIT;
-- Result at REPEATABLE READ: 0 doctors on call — invariant BROKEN (write skew)

Why does Repeatable Read let this through? Because its only conflict check is on rows written by two transactions — and here Alice and Bob write different rows. Each read its own frozen snapshot (in which the other was still on call), each write is individually legal, and no first-updater-wins rule fires. Snapshot isolation guarantees a consistent read view, not a consistent outcome across the two writes. The invariant spans two rows, so a per-row check can never see the danger.

To do it with locks by hand at Repeatable Read, you'd have to materialize the conflict — e.g. SELECT ... FOR UPDATE a shared summary row both transactions must lock, forcing them to serialize. Serializable does that reasoning for you. SSI watches the read/write dependencies: A read a set that B then modified, and B read a set that A then modified — a cycle that no serial order (Alice-first or Bob-first) could produce. So it aborts one with 40001:

retry loop (pseudocode)

for attempt in 1..N:
    BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
    -- the same read + write as before
    COMMIT;                 -- may raise SQLSTATE 40001 (serialization_failure)
    # success  -> break
    # on 40001 -> ROLLBACK and loop again; the retry sees the winner's commit

On B's retry, Alice has already committed herself off, so B's re-read now shows no other doctor on call — the rule refuses, Bob stays on, and the invariant holds. That's the shape of every Serializable app: the level guarantees correctness, but only if you actually catch 40001 and retry. A Serializable transaction with no retry loop is a latent bug.

Write skew is the reason Serializable exists

If all you ever had were single-row conflicts, Repeatable Read (with first-updater-wins) would be enough. Write skew — two txns, two rows, one broken cross-row invariant — is precisely the gap snapshot isolation can't close and SSI can. When an interviewer asks “why isn't Repeatable Read good enough?”, the one-word answer is write skew; the doctors are the canonical demo.

05 Choosing a level

Reason about it

Put the machinery aside and reason like an engineer picking a default. You have four moves, in rough order of how often you'll reach for them:

  • READ COMMITTED for most OLTP. Short transactions that touch a few rows and don't depend on a stable multi-statement view are correct and cheapest here. It's the default for a reason; don't climb unless a specific anomaly threatens you.
  • REPEATABLE READ for multi-statement reports. When one transaction runs several reads that must agree — a statement, an export, a “read parent then children” page — freeze a single snapshot so nothing shifts underneath. Cheap protection against non-repeatable reads and phantoms.
  • SERIALIZABLE for cross-row invariants. When correctness depends on a rule that spans rows (at least one doctor on call, no double-booked seat, a balance across accounts) and you'd rather not hand-craft locks, let SSI find the dangerous cycles. You pay in retries, not in reasoning.
  • Or stay at Read Committed and take explicit locks. SELECT ... FOR UPDATE serializes access to the exact rows you're about to change, defeating lost updates without raising the whole transaction's level. That's the subject of the next lesson — often the most surgical tool.

Whichever of the upper two you choose, one rule is non-negotiable: every transaction running at Repeatable Read or Serializable must be wrapped in a retry loop. Both levels can abort a perfectly good transaction with serialization_failure (40001) purely because of what other transactions did — that's not an error in your logic, it's the level telling you “re-run me and I'll get it right.” Treat 40001 like an optimistic-lock miss: roll back, and try the whole thing again. Apps that forget this appear to work in testing and then throw mysterious errors under load.

A quick decision rule

Ask two questions. Do my statements need to agree with each other? If yes, climb to Repeatable Read. Does correctness depend on a rule spanning more than one row that I'm not locking by hand? If yes, climb to Serializable and add the retry loop. If neither, stay at Read Committed. Then, and only then, reach for explicit locks to plug a specific single-row race.

Where this shows up next. Every level here is built on snapshots, and a snapshot is a fact about which transactions had committed at a point in time — the next lesson (L26, MVCC) opens up how Postgres actually builds those snapshots from the hidden xmin/xmax version columns, which is why readers never block writers. The explicit-locking tools this section gestured at — FOR UPDATE, SKIP LOCKED, deadlocks — are L27. And the dead row-versions all this snapshotting leaves behind are what VACUUM (L29) exists to reclaim. Isolation is the contract; MVCC and locking are how it's kept.

★ Review

Summary & self-test

One idea holds the lesson together: an isolation level is a contract naming which concurrency anomalies you are guaranteed not to see — and PostgreSQL keeps that contract with snapshots, quietly forbidding more than the SQL standard requires (never a dirty read; no phantoms even at Repeatable Read) while asking you to retry on 40001 for the two upper levels. Pick the weakest level that forbids the anomaly that would actually hurt you.
