Partitioning

A table can outgrow its own good behavior: a billion-row events log makes every scan crawl and turns "delete last year's data" into an hours-long, lock-holding, bloat-generating DELETE. Declarative partitioning splits one logical table into physical child tables by a key, so Postgres can route writes to the right child, prune reads down to a slice, and drop a whole month of data in a single instant metadata operation. This lesson is about doing that correctly — and about the sharp edges that make partitioning a foot-gun when the key isn't in your WHERE clause.

00 Orientation

One table on the surface, many tables underneath

Declarative partitioning lets you define a single logical table that Postgres physically stores as a set of partitions — separate child tables — chosen by a partition key. You still write INSERT INTO events and SELECT FROM events; the parent table has no storage of its own and does nothing but route each row to the child whose bounds contain the key, and, at query time, help the planner skip the children that can't match. It's called declarative because you declare the scheme with PARTITION BY and Postgres does the routing — as opposed to the old inheritance-plus-trigger approach you should never build by hand today.

There are three strategies, and picking the right one is most of the design work:

  • RANGE — each partition owns a contiguous, half-open range of the key. The classic case is time: one partition per month of created_at. Ideal for time-series and anything you retire by age.
  • LIST — each partition owns an explicit set of discrete values, e.g. one partition per region or per tenant_id group.
  • HASH — Postgres hashes the key and assigns rows by remainder, spreading rows evenly across a fixed number of partitions when there's no natural range or list.

When it pays. Partitioning earns its complexity at scale — think roughly tens of millions of rows or hundreds of gigabytes and up, especially time-series data with a retention policy. The two headline wins are cheap data lifecycle (dropping or archiving an old partition is an O(1) metadata operation, not a giant DELETE) and partition pruning (a query with the key in its filter touches only the relevant partitions). A secondary win: maintenance like VACUUM, index builds, and freezing runs per-partition, so it stays parallel and bounded.

What it costs. Every unique constraint (including the primary key) must include the partition key; indexes are created per-partition; the planner does more work with more partitions; and pruning only helps when the key appears in the query. Most importantly, partitioning is not a faster index — a well-indexed 5-million-row table beats a badly-partitioned one every time.

Partitioning is not sharding

Both split a table, but partitioning keeps every partition on one Postgres server (it's about data lifecycle and pruning), while sharding spreads partitions across many servers to scale write throughput and total size beyond one machine (Phase 8, Citus). Partition first for manageability on a single node; shard only when one node genuinely can't hold the data or the write rate. They compose — Citus distributes tables that are themselves partitioned by time.

Correct first, then fast

Reach for partitioning to solve a data-management problem (retention, archival, unbounded growth) or to prune enormous scans — not to speed up an OLTP point lookup, which a good index already does. Below ~10M rows, the honest answer in an interview is "I'd index it and revisit partitioning when growth or retention forces it." Premature partitioning adds real operational weight for no benefit.

01 Routing

RANGE partitioning: a row finds its home ▸

Start with the most common scheme, PARTITION BY RANGE. You declare a parent table and then attach one child per range of the key. Each child's bounds are written FROM (lo) TO (hi) and the interval is half-open: lo is included, hi is excluded. That half-open rule is what lets consecutive months abut perfectly — [Feb 1, Mar 1) and [Mar 1, Apr 1) — with no overlap and no gap, so 2026-03-01 00:00:00 belongs unambiguously to March.

sql

CREATE TABLE events (
    id          bigint       GENERATED ALWAYS AS IDENTITY,
    user_id     bigint       NOT NULL,
    created_at  timestamptz  NOT NULL
) PARTITION BY RANGE (created_at);           -- parent: no storage, just a router

CREATE TABLE events_2026_02 PARTITION OF events
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');   -- [Feb 1, Mar 1)

Now every INSERT INTO events is examined by the parent and dispatched to the child that contains its created_at. Step through the routing:

Two details matter in practice. First, a row whose key matches no partition's range is rejected with an error — unless you create a DEFAULT partition to catch strays (handy, but a default partition can't be pruned and complicates adding future ranges). Second, this is why you must create next month's partition before rows for it arrive; a forgotten future partition is a classic 2 a.m. insert failure, which is exactly why teams automate creation with pg_partman or a scheduled job.

Half-open ranges are a feature

Writing bounds as FROM ('2026-02-01') TO ('2026-03-01') — not TO ('2026-02-28') — means the upper bound of one partition is the exact lower bound of the next. Contiguous, gapless, overlap-free. Trying to be "inclusive" on the high end is how you create a one-microsecond gap that silently rejects a midnight-boundary insert.

02 Pruning

Partition pruning: read a slice, skip the rest ▸

Routing is the write-side win; partition pruning is the read-side win, and it's the whole reason partitioning speeds up queries. When your WHERE clause constrains the partition key, the planner compares that constraint against each partition's declared bounds and eliminates the partitions that provably can't contain a matching row. It never opens them. The plan is an Append node over the surviving partitions — and when exactly one survives, Postgres elides the single-child Append and you see just that partition's scan.

The catch is the precondition, and it's the single most-tested fact about partitioning: pruning only happens when the partition key appears in the query, comparable to a constant or parameter. Filter on created_at and you prune; filter only on user_id and the planner has nothing to eliminate on, so it scans every partition. Watch both cases:

Postgres prunes at two moments. Plan-time pruning happens when the bounds are constants the planner can see — the eliminated partitions never even appear in EXPLAIN. Run-time pruning handles values not known until execution — a bound from a parameter ($1) or from the other side of a join — and shows up in EXPLAIN ANALYZE as Subplans Removed: N under the Append. Both are good; the point is that some comparison to the key must exist.

The mistake that disables pruning

Wrapping the partition key in a function breaks pruning, because the planner can no longer relate the expression to the raw partition bounds. WHERE date_trunc('month', created_at) = '2026-02-01' scans every partition; the prunable form is WHERE created_at >= '2026-02-01' AND created_at < '2026-03-01'. Same idea with an implicit cast or created_at::date = .... Always leave the partition column bare on one side of the comparison.

03 The rest of the toolkit

LIST, HASH, and the operational realities

RANGE is the workhorse, but the other two schemes fit real problems. LIST partitions by a set of discrete values — a natural fit for a categorical column like region or a small set of tenants:

sql

CREATE TABLE orders (region text, ...) PARTITION BY LIST (region);
CREATE TABLE orders_eu PARTITION OF orders FOR VALUES IN ('de', 'fr', 'es');
CREATE TABLE orders_us PARTITION OF orders FOR VALUES IN ('us');

HASH partitions by a hash of the key modulo a fixed count. Use it when there's no meaningful range or list but you still want to spread a hot table's rows (and its lock/IO contention) evenly — for example splitting a huge user_id table into 8 balanced parts:

sql

CREATE TABLE sessions (user_id bigint, ...) PARTITION BY HASH (user_id);
CREATE TABLE sessions_0 PARTITION OF sessions FOR VALUES WITH (MODULUS 8, REMAINDER 0);
-- ... repeat REMAINDER 1..7. Note: an equality on user_id still prunes to one partition.

RANGE

  • Contiguous key ranges (time, id ranges).
  • Best for time-series + retention.
  • Prunes on >, <, BETWEEN, =.
  • Archive by dropping the oldest range.

LIST

  • Explicit sets of discrete values.
  • Best for region / category / tenant.
  • Prunes on equality & IN.
  • Isolate or drop one category cleanly.

HASH

  • Even spread by MODULUS/REMAINDER.
  • Best for no natural range, hot tables.
  • Prunes only on equality of the key.
  • No cheap "drop old" — ranges aren't meaningful.

ATTACH / DETACH: the archival superpower

The reason time-partitioning is so loved is data lifecycle. To load a prepared table as a new partition, ALTER TABLE events ATTACH PARTITION ...; to retire one, ALTER TABLE events DETACH PARTITION ... pops it out into a standalone table (add CONCURRENTLY, PG14+, to avoid a heavy lock), which you can then archive to cold storage or DROP TABLE. DETACH is a near-instant metadata pop; ATTACH is too if the incoming table already carries a matching CHECK constraint on the bound (otherwise Postgres scans it once to prove every row fits). Either way it beats a DELETE that must scan matching rows, write to the WAL, bloat the table, and leave cleanup for VACUUM.

The constraints you can't skip

  • Indexes are per-partition (local). Postgres has no single global index across partitions. Creating an index on the parent is a convenience that creates a matching local index on every child; each partition physically owns its own index.
  • The partition key must be part of every unique constraint and the primary key. Because uniqueness is enforced per-partition (there's no global index), Postgres can only guarantee uniqueness if the key that decides the partition is in the constraint — so PRIMARY KEY (id) is rejected on a table partitioned by created_at; you need PRIMARY KEY (id, created_at). A corollary: you cannot enforce global uniqueness on a column that excludes the partition key.
  • Too many partitions hurt. The planner examines partitions during planning; thousands of them inflate planning time and catalog size. Prefer monthly over daily unless volume demands it, and keep the count in the low hundreds. pg_partman automates rolling creation and retention so you don't hand-manage the window.
Foreign keys and partitioned tables

A partitioned table can have outgoing foreign keys, and since PG12 it can also be referenced by them. But a foreign key still can't reference a non-key column's uniqueness that you can't declare — so others usually reference the composite key. When you model, decide the partition key first; it ripples into every PK, unique constraint, and FK on the table.

04 Worked problem

Partition an events table by month ▸

Let's build the canonical case end to end and watch what each step buys us.

1 · The schema (before)

An analytics service records user events. The table already exists as an ordinary heap and is heading for a billion rows, with a policy to keep only the last 12 months.

sql

CREATE TABLE events (
    id          bigint       GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id     bigint       NOT NULL,
    kind        text         NOT NULL,
    payload     jsonb        NOT NULL DEFAULT '{}',
    created_at  timestamptz  NOT NULL DEFAULT now()
);
CREATE INDEX ON events (created_at);

2 · The task

Two things must be fast and cheap: (a) "give me the events in a given month," and (b) the monthly retention job that removes data older than a year. Right now both are getting worse as the table grows.

3 · The naive approach, and why it hurts

Retention on the monolith is a big delete, run every month:

sql

DELETE FROM events WHERE created_at < '2026-01-01';   -- tens of millions of rows

This is exactly the operation partitioning exists to avoid. The DELETE must find and mark every matching row, write a WAL record for each, and touch every index. The dead rows don't vanish — they become bloat that only VACUUM reclaims later, and until it does, the table and its indexes stay swollen, slowing every other query. On a hot table the delete competes for locks and IO with live traffic and can run for a very long time. And the month-range read still scans one enormous index shared by all of history.

4 · The fix: range-partition by month

Redefine events as partitioned, put the partition key in the primary key, and create one child per month. (In production you'd migrate by creating the new partitioned table, backfilling in chunks, and swapping — but here is the target shape.)

sql

CREATE TABLE events (
    id          bigint       GENERATED ALWAYS AS IDENTITY,
    user_id     bigint       NOT NULL,
    kind        text         NOT NULL,
    payload     jsonb        NOT NULL DEFAULT '{}',
    created_at  timestamptz  NOT NULL,
    PRIMARY KEY (id, created_at)         -- partition key MUST be in the PK
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_01 PARTITION OF events
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE events_2026_02 PARTITION OF events
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
CREATE TABLE events_2026_03 PARTITION OF events
    FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');

CREATE INDEX ON events (created_at);   -- creates a LOCAL index on every partition

5 · Why it's better (read the plan)

A month-scoped query now prunes to one partition and index-scans just that child. With plain = or a bare range on created_at, plan-time pruning drops the other partitions before execution even starts:

sql

EXPLAIN ANALYZE
SELECT * FROM events
WHERE created_at >= '2026-02-10' AND created_at < '2026-02-20';

query plan · illustrative

Index Scan using events_2026_02_created_at_idx on events_2026_02 events
  (cost=0.29..40.66 rows=410 width=72) (actual time=0.022..0.151 rows=402 loops=1)
  Index Cond: ((created_at >= '2026-02-10'::timestamptz)
           AND (created_at < '2026-02-20'::timestamptz))
Planning Time: 0.42 ms
Execution Time: 0.24 ms

Jan and Mar were pruned at plan time and never appear. Note there is no Append: when pruning leaves exactly one partition, Postgres drops the single-child Append wrapper and you see a bare Index Scan straight on events_2026_02 (an Append shows up only when two or more partitions survive). Compare that to the monolith, whose plan would index-scan one index holding all of history's rows. And retention becomes a metadata drop instead of a delete:

sql

-- old way: DELETE FROM events WHERE created_at < '2026-02-01';  (scans, WAL, bloat, VACUUM)
ALTER TABLE events DETACH PARTITION events_2026_01;   -- pop it out, instant
DROP TABLE events_2026_01;                            -- reclaim the whole month at once

6 · Narrate it

"I range-partitioned events by month on created_at, so the partition key had to join the primary key as (id, created_at). Reads that name a month prune to one partition and index-scan it, so query cost tracks a single month, not all of history. Retention stops being a giant DELETE that bloats the table — I DETACH and DROP the oldest partition in one metadata operation. I create next month's partition ahead of time (via pg_partman) so inserts never hit a missing range, and I keep the partition count reasonable — monthly, not daily — to avoid planning overhead."

The one line that ties it together

Partitioning turned two O(rows) problems — a month read over a global index and a month delete — into two O(1)-ish ones: prune to one partition, and drop a whole partition. That trade only appears when the partition key is in the query and in the constraints.

05 Graded drills

Drills & traps

Predict each answer before you open the reveal. They climb from "will it even create" to "should you partition at all."

Drill 1 — the constraint that won't create

You try to partition an existing table by created_at but keep its old primary key:

sql

CREATE TABLE events (
    id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    created_at timestamptz NOT NULL
) PARTITION BY RANGE (created_at);
-- ERROR:  unique constraint on partitioned table must include all partitioning columns

Why does it fail, and what's the minimal fix?

Try it first, then read

Postgres enforces uniqueness per-partition (there's no global index), so it can only guarantee a unique value if the partition key is part of the key — otherwise two partitions could each hold id = 5. Fix: make the key composite so it includes the partition column: PRIMARY KEY (id, created_at). Why: the partition key must be in every unique/PK constraint on a partitioned table.

Drill 2 — the query that scans everything

The table has 36 monthly partitions. This dashboard query is mysteriously slow:

sql

SELECT * FROM events
WHERE user_id = 42
ORDER BY created_at DESC LIMIT 20;

Why is it slow across 36 partitions, and how do you make it prune?

Try it first, then read

There's no created_at predicate, so nothing prunes — the planner must scan all 36 partitions (each via its own index on user_id, if one exists) and merge them, a fan-out that gets linearly worse every month. Two fixes, best together: (1) add a bounded time filter the dashboard almost always wants anyway, e.g. AND created_at >= now() - interval '90 days', so pruning cuts it to ~3 partitions; and (2) add a per-partition index on (user_id, created_at DESC) so each surviving partition serves the top-N cheaply. Why: pruning needs the partition key in WHERE; without it, partition count is a tax on every query.

Drill 3 — global uniqueness you can't have

Each event carries an external_id that must be unique across the entire table (it's an idempotency key from an upstream system). You want UNIQUE (external_id) on the month-partitioned events. Can Postgres enforce it?

Try it first, then read

No. A unique constraint on a partitioned table must include the partition key, so UNIQUE (external_id) alone is rejected, and UNIQUE (external_id, created_at) only enforces uniqueness within the same created_at — not global. Options: (a) accept the weaker composite guarantee; (b) enforce global uniqueness in a separate non-partitioned lookup/dedup table that the write path checks with ON CONFLICT DO NOTHING; or (c) don't partition this table if global uniqueness is the hard requirement. Why: without a global index, Postgres cannot guarantee uniqueness over a column that excludes the partition key.

Drill 4 — too much of a good thing

To "future-proof," a teammate created daily partitions for ten years — about 3,650 of them. Now planning is slow and even simple inserts feel sluggish. Diagnose and prescribe.

Try it first, then read

Too many partitions. The planner considers partitions during planning and the catalog carries every child and its indexes, so thousands of partitions inflate planning time, memory, and lock acquisition — often swamping any pruning benefit. Prescribe: partition monthly (≈120 partitions for ten years, not 3,650), and don't pre-create a decade at once — use pg_partman to roll new partitions forward and drop old ones on a retention window. Keep the live count in the tens-to-low-hundreds. Why: partition count is itself a cost; the right granularity balances pruning gains against planning overhead.

Traps to keep on a sticky note

• Partition key must be in every PK/UNIQUE — or CREATE is rejected.
• No partition key in WHERE ⇒ no pruning — the query scans every partition.
• A function on the key kills pruning — date_trunc(created_at) or created_at::date; keep the column bare.
• No global uniqueness across partitions unless the key includes the partition column.
• Indexes are local — creating on the parent cascades, but there is no single global index.
• Too many partitions add planning overhead; too few give no benefit — aim tens-to-low-hundreds.
• It's not a faster index — below ~10M rows, a plain indexed table usually wins.
• Forgotten future partition ⇒ inserts fail (no DEFAULT) or silently bloat one DEFAULT partition. Automate creation.

★ Review

Summary & self-test

One idea to carry: partitioning splits one logical table into physical children by a key so Postgres can route writes, prune reads to a slice, and drop old data in one metadata operation — but every benefit is unlocked by having the partition key in your constraints and in your WHERE clause. It's a data-management and large-scan tool, not a replacement for an index.
