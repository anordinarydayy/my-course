MVCC: How Postgres Does Concurrency

Isolation levels (Lesson 25) told you what Postgres guarantees; MVCC is how it delivers them. Rather than lock a row so only one session may touch it, Postgres keeps many versions of each row and lets every transaction read the version valid for its own snapshot. The payoff is the one line worth memorizing: readers never block writers, and writers never block readers. The bill comes due as dead tuples and VACUUM — which is the next lesson.

00 The core move

Don't overwrite — version

Here is the obvious way to keep two sessions from clobbering the same row: lock it — let one session hold the row while it works, and make everyone else wait their turn. It is simple, and it is what older databases leaned on heavily. It also serializes your whole workload behind whoever holds the lock: a long-running report holding rows for a read can stall every writer that wants to touch them, and a slow writer can stall every reader. Concurrency dies at the busiest rows.

Postgres makes a different move. It never overwrites a live row in place. When you change a row, Postgres writes a new version of it and leaves the old version sitting in the table, and every transaction reads whichever version is valid for the moment it started. This is Multi-Version Concurrency Control (MVCC): many versions of a row coexisting, each transaction seeing exactly one of them.

That single design choice is why a half-hour analytics query can scan a table while thousands of writes land on it — the report keeps reading the versions that existed when it began, and the writers keep minting new versions beside them. Nobody waits. The rest of this lesson is just the mechanics of that idea: how a version is stamped (s1), how a snapshot decides which version you see (s2), what it costs (s3), and the payoff spelled out (s4).

The reframe

Stop picturing a row as a cell you overwrite and start picturing it as an append-only history of versions. An UPDATE doesn't change a value — it adds a newer version and marks the older one as superseded. Reads and writes then stop fighting over one cell, because they are looking at different versions. That is the whole trick, and everything else is bookkeeping.

01 The stamps

xmin / xmax — row versions ▸

Every row you see is really a tuple (a physical row version) in the heap, and every tuple carries two hidden system columns that do all the work: xmin — the transaction id (xid) that created this version — and xmax — the xid that deleted or superseded it (empty while the version is still current). A third hidden column, ctid, is the tuple's physical location (page, offset). The rules are short:

  • INSERT writes one tuple and stamps its xmin with the inserting xid; xmax is empty.
  • DELETE doesn't erase the tuple — it stamps the tuple's xmax with the deleting xid, marking it superseded.
  • UPDATE is a delete + insert: it inserts a brand-new tuple (new ctid, new xmin) and stamps the old tuple's xmax. The old version stays behind as a dead tuple.

You can watch this happen by asking for the hidden columns directly:

sql

-- xmin/xmax are hidden system columns — you must name them explicitly
SELECT ctid, xmin, xmax, id, balance FROM accounts WHERE id = 7;

-- this UPDATE does NOT overwrite the row in place:
UPDATE accounts SET balance = 150 WHERE id = 7;
-- → a NEW tuple (new ctid, xmin = this xid) is inserted, and
--   the OLD tuple's xmax is stamped with this same xid

This is why an update is more expensive than it looks — it always creates a new tuple — and why heavy update traffic generates dead tuples that someone (VACUUM) has to clean up later.

Update = delete + insert

There is no such thing as an "in-place" update of a live row in Postgres. Every UPDATE inserts a fresh version and expires the old one by stamping its xmax. That is the price of readers-don't-block-writers, and it is exactly why the two topics that book-end this phase — locking (when you deliberately do block) and VACUUM (cleaning the corpses) — exist at all.

02 Visibility

Snapshots decide what you see ▸

Stamping versions is only half the machine. The other half is the snapshot: the record, taken at a well-defined moment, of which transactions had already committed then (plus the list of xids still in flight). A snapshot is what turns a pile of coexisting versions into a single coherent view of the data. The visibility rule is one sentence worth memorizing:

The visibility rule

A row version is visible to a snapshot iff its xmin is committed and in the snapshot and its xmax is not (either empty, or belonging to a transaction the snapshot doesn't count as committed). Born-and-committed before you looked, not-yet-deleted as far as you can tell — then you see it.

Two transactions that started at different moments therefore hold different snapshots, and so they can read different versions of the very same row at the very same instant — each one correct for when it began. When you set REPEATABLE READ (Lesson 25), you are simply telling Postgres to take one snapshot at the transaction's first query and keep it for the whole transaction, so every read is consistent:

sql

BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 7;   -- snapshot fixed here → $100
-- ... meanwhile another session commits balance = 150 ...
SELECT balance FROM accounts WHERE id = 7;   -- STILL $100: one snapshot for the whole txn
COMMIT;

Notice what did not happen: T1 never had to wait for the writer, and the writer never had to wait for T1. They coexist because they are literally reading different tuples. This is also the precise mechanism behind Postgres never showing a dirty read, even at the default READ COMMITTED — a version whose xmin belongs to an uncommitted transaction fails the visibility rule, so you simply cannot see another session's in-progress work.

READ COMMITTED vs REPEATABLE READ, in one line

Both use snapshots; they differ in how often a fresh one is taken. READ COMMITTED (the default) takes a new snapshot at the start of every statement — so a later query in the same transaction can see rows a concurrent commit added (a non-repeatable read). REPEATABLE READ takes one snapshot for the whole transaction. MVCC is the shared engine; the isolation level is just the snapshot policy on top of it.

03 The cost

The bill: dead tuples & bloat

Keeping old versions around is not free. A version that is no longer visible to any live snapshot — its xmax is committed and older than the oldest running transaction — is a dead tuple. It still occupies space in the table's pages, still gets skipped over by scans, and still has index entries pointing at it. Accumulated dead tuples are bloat: a table (and its indexes) grow larger and slower than the live data alone would justify.

Dead tuples are reclaimed by VACUUM (Lesson 29), which marks their space reusable within the table so future inserts and updates can fill it. You can see the pressure building in the catalog:

sql

-- how much dead space has accumulated on this table?
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables WHERE relname = 'accounts';

But VACUUM can only remove a dead tuple if no snapshot could still need it — and that is where the most important operational lesson of MVCC lives. A long-running transaction holds a snapshot, and that snapshot pins the xmin horizon: the oldest xid any live transaction might still care about. VACUUM cannot clean up anything newer than that horizon, because somebody could still be looking. So one forgotten transaction left open — an idle BEGIN, a stuck report, a leaked connection — freezes the horizon and lets dead tuples pile up table-wide, even on tables that transaction never touched.

sql

-- which backend is holding back the xmin horizon (blocking cleanup)?
SELECT pid, age(backend_xmin) AS xmin_age, state, query
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC;

One optimization softens the update cost: a HOT update (Heap-Only Tuple). When an UPDATE changes no indexed column and the new version fits on the same page as the old one, Postgres chains the new tuple to the old on that page and skips updating the indexes entirely — the index still points at the old tuple, which forwards to the new one. HOT updates dramatically cut index bloat for update-heavy tables, which is one reason not to slap an index on a column you update constantly.

The one habit that prevents most MVCC pain

Keep transactions short. Don't BEGIN and then go do slow application work, call an external API, or wait on user input. A transaction that stays open for minutes pins the xmin horizon, starves VACUUM, and turns steady update traffic into runaway bloat. "One giant transaction" and "an idle transaction left open" are the two most common causes of a Postgres table that mysteriously keeps growing.

04 The payoff

Readers don't block writers ▸

Now the reward for all that bookkeeping. Picture a long analytics report scanning the accounts table for many seconds, while ordinary traffic keeps updating individual accounts. In a strict lock-based database this is a standoff: the report holds read locks that the writers must wait behind, or the writers hold locks that stall the report. Under MVCC there is no standoff at all — the reader reads its snapshot's versions, the writer mints new ones, and neither notices the other:

sql

-- Session R (a long report) — takes a snapshot and reads for a while
BEGIN;
SELECT sum(balance) FROM accounts;    -- scans millions of rows...

-- Session W (another connection, running at the same time) — does NOT wait
UPDATE accounts SET balance = balance + 50 WHERE id = 7;
-- W writes a new row version and commits; R keeps reading its own snapshot

The symmetry is exact and worth stating both ways: readers never block writers (the report never delays the update) and writers never block readers (the update never delays the report). What MVCC does not free is two writers to the same row — the second UPDATE of account #7 still waits for the first to commit or roll back, because Postgres cannot let both create a successor to the same version at once. That case — deliberate, row-level blocking — is exactly what row locks (Lesson 27) are for.

The boundary of the guarantee

"Never block" applies to reads vs writes, not to write vs write on the same row. Two transactions updating different rows never contend; two updating the same row serialize, one waiting on the other. If you find yourself needing readers to block (to reserve a row before updating it), that is a lock you ask for on purpose — SELECT ... FOR UPDATE — which is the whole subject of the next lesson.

05 Reason about it

Reason about it

Put the trade-off on one line: MVCC buys enormous read/write concurrency by paying in space and cleanup. Reads and writes stop fighting, dirty reads become impossible, and long reports run beside busy writers — but every update leaves a corpse, every version costs a visibility check, and someone (VACUUM) must haul the corpses away. Whether that trade is a bargain or a trap comes down to one variable almost entirely in your control: how long your transactions live.

Trace the chain of consequences from a single long transaction and you have the whole operational story of this phase:

  • A long transaction holds an old snapshot → that snapshot pins the xmin horizon.
  • A pinned horizon means VACUUM can't reclaim dead tuples newer than it → bloat grows table-wide.
  • The same held-back horizon blocks freezing of old rows → it nudges you toward transaction-ID wraparound risk (Lesson 30).
  • Meanwhile every scan wades through more dead tuples and more visibility checks → queries get slower.

So the practical wisdom is blunt: keep transactions short, and treat "one giant transaction" and "an idle open transaction" as anti-patterns. Open late, commit early, never hold a transaction across slow application work or user think-time. Almost every horror story about a Postgres table that ballooned to ten times its live size, or a database that stopped accepting writes, traces back to a transaction that stayed open far too long.

Where this shows up next

MVCC is the hinge of this whole phase. Isolation (L25) is snapshots as a policy — REPEATABLE READ is "one snapshot for the transaction," and serialization failures happen when snapshot-based isolation can't safely commit a write. Locking (L27) is the other side of the coin: when readers-don't-block-writers isn't what you want and you deliberately do block, with SELECT ... FOR UPDATE. And VACUUM (L29) is the bill arriving — the background machinery that makes MVCC's dead tuples sustainable. Carry one sentence forward: Postgres versions rows and reads by snapshot; that is why it barely locks, and why it must vacuum.

★ Review

Summary & self-test

The whole lesson compresses to one idea: Postgres never overwrites a live row — it keeps versions stamped with xmin/xmax, and each transaction reads the version its snapshot says is valid. That is why readers never block writers and writers never block readers — and why the price is dead tuples that VACUUM must reclaim.
