Index Types in Postgres

The B-tree is the default, and for most work it is exactly right — equality, ranges, sorting. But Postgres ships a whole toolbox of specialized index types for data a B-tree handles badly: arrays, JSONB, full-text, geometry, and enormous append-only tables. This lesson teaches you to recognize each query shape and reach for the index built for it — and, just as importantly, when the default is the wrong choice.

Original study notes. Written from scratch, PostgreSQL-based and current to PG 17/18. Contains three interactive diagrams (press Play or step with Next). This is a practice lesson: it ends in a worked SQL problem where you choose the index for three real queries, then a set of graded drills with solutions and a list of traps to avoid.
00 Orientation

One size doesn’t fit all

By now you know the deal an index offers: a separate, ordered structure that lets Postgres find rows without scanning the whole heap. But “ordered structure” described the B-tree specifically, and a B-tree is only one shape of index. It is the default, and for the bread-and-butter of an OLTP app — look up a row by id, filter a date range, sort a page of results — it is the correct default. You will type CREATE INDEX without a USING clause the vast majority of the time and be right.

The trouble is that a B-tree indexes one comparable key per row. Ask it to index a column that holds many values per row (an array of tags, a JSONB document, the words of a paragraph), or a value with no meaningful total order (a polygon, a geographic point, an IP subnet), or a table so vast that even a slim B-tree would cost gigabytes — and the default stops being the right answer. For each of those, Postgres gives you a purpose-built access method:

B-tree

  • The default. Ordered.
  • =, <, >, BETWEEN, ORDER BY, prefix LIKE 'a%'.

Hash

  • Equality only.
  • Compact for very large keys. WAL-logged since PG 10.

GIN

  • Inverted: many keys per row.
  • Arrays @>, JSONB, full-text, pg_trgm.

GiST

  • Balanced tree for overlap / nearest.
  • Ranges, geometry (PostGIS), KNN.

BRIN

  • Block-range min/max summaries. Tiny.
  • Huge, physically-ordered tables.

SP-GiST

  • Space-partitioned, non-balanced.
  • Quadtrees, tries, text prefixes.

The whole skill is a mapping: from the shape of your query and the type of your column, to the access method that serves it. Miss it and you either get no index used at all, or an index that technically works but is the wrong tool — a giant B-tree where a kilobyte-sized BRIN would do. The rest of this lesson walks the toolbox pair by pair, then makes you choose.

The one line to remember

Postgres exposes these as access methods (SELECT amname FROM pg_am;) and you pick one with CREATE INDEX … USING <method> (…). Omit USING and you get a B-tree. Everything specialized is a deliberate choice you make because the default can’t serve the query.

01 The two ordered-vs-not

B-tree & Hash ▸

Start with the two simplest types, because the contrast between them explains half of everything that follows. Both index a single scalar column. The difference is one word: a B-tree keeps its keys in sorted order; a hash index does not. From that one property everything each can (and can’t) do falls out.

Because a B-tree is ordered, it serves the widest set of predicates of any index type: equality (=), inequalities (<, >), BETWEEN, ORDER BY (the leaves are already sorted, so no separate Sort is needed), and even a prefix match like LIKE 'abc%' (a prefix is a range: everything from 'abc' up to 'abd').

sql

-- B-tree (the default): equality, ranges, and sorting
CREATE INDEX idx_users_created ON users (created_at);

SELECT * FROM users WHERE created_at BETWEEN '2026-01-01' AND '2026-02-01';
SELECT * FROM users WHERE email LIKE 'ana%';   -- prefix → range, usable
SELECT * FROM users ORDER BY created_at DESC LIMIT 20;

A hash index throws the key through a hash function and stores it in the resulting bucket. That makes equality lookups compact and quick — and for a very large key (say a long token, or a big text value) the hash is often smaller on disk than a B-tree, which must store the whole key in every internal page. But hashing deliberately destroys order: two keys that are “next to each other” land in unrelated buckets. So a hash index can answer = and nothing else — no range, no ORDER BY, no prefix.

sql

-- Hash: equality only. Crash-safe / WAL-logged since PG 10.
CREATE INDEX idx_sessions_token ON sessions USING hash (token);

SELECT * FROM sessions WHERE token = 'a1b2c3d4e5';   -- can use the hash index
-- WHERE token > 'x'  or  ORDER BY token  → the hash index is useless

So why does hash still exist, given B-tree already does equality? Two niche wins: on huge keys the hash can be materially smaller, and its equality lookup is a flat jump rather than a few tree hops. In practice the default B-tree is almost always fine even for equality, so hash indexes are rare — but knowing the trade-off is exactly the kind of thing an interviewer probes. The headline: reach for hash only when you do nothing but = on a large key, and never when a range or sort might appear.

Historical footnote worth knowing

Before PostgreSQL 10, hash indexes were not WAL-logged — they weren’t crash-safe and weren’t replicated, so the docs actively discouraged them. That warning is now obsolete: since PG 10 hash indexes are fully WAL-logged and safe. If you read old advice saying “never use hash indexes,” it predates this fix — the real reason to skip them today is just that B-tree usually matches or beats them.

02 Many-values & overlap

GIN & GiST ▸

The next pair is where Postgres pulls away from other databases. Both handle data a B-tree simply can’t model, but they solve different problems.

GIN (Generalized Inverted iNdex) is an inverted index: it’s built for columns where one row contains many indexable values. Instead of “row → key,” it stores “key → the list of rows that contain it” (a posting list). That is exactly the structure a search engine uses. It powers array containment (@>), JSONB queries, PostgreSQL full-text search (tsvector / @@), and trigram matching (pg_trgm).

sql

-- GIN for array containment
CREATE INDEX idx_posts_tags ON posts USING gin (tags);
SELECT * FROM posts WHERE tags @> ARRAY['sql'];

-- GIN for JSONB containment (jsonb_path_ops: smaller, tuned for @>)
CREATE INDEX idx_events_data ON events USING gin (data jsonb_path_ops);
SELECT * FROM events WHERE data @> '{"type":"click"}';

-- GIN for full-text search
CREATE INDEX idx_docs_fts ON docs USING gin (to_tsvector('english', body));
SELECT * FROM docs
WHERE to_tsvector('english', body) @@ to_tsquery('english', 'index & scan');

The price of that read power is write cost. Inserting one row means updating every token’s posting list — a row with ten tags touches ten places in the index. To soften that, GIN keeps a pending list (the fastupdate option): new entries are buffered and merged in bulk later. Great for read-heavy tables; something to watch on write-heavy ones.

GiST (Generalized Search Tree) is a different animal: a balanced tree, like a B-tree, but where each internal node stores a bounding predicate (“everything below me fits inside this box / this range”) instead of a single sort key. That makes it the tool for questions of overlap and nearness rather than ordering: does this range overlap that one (&&), does this box contain that point, and — crucially — K-nearest-neighbour searches (ORDER BY column <-> target), which GiST can answer directly. It is the backbone of PostGIS geometry and of range-type exclusion constraints.

sql

-- GiST for range overlap (e.g. no double-booking a room)
CREATE INDEX idx_res_during ON reservations USING gist (during);   -- during tsrange
SELECT * FROM reservations WHERE during && tsrange('2026-07-01', '2026-07-05');

-- GiST for K-nearest-neighbour: 5 closest places to a point
CREATE INDEX idx_places_geom ON places USING gist (geom);
SELECT * FROM places ORDER BY geom <-> ST_Point(0, 0) LIMIT 5;
GIN vs GiST, in one breath

GIN = many discrete keys per row (tags, JSONB paths, words, trigrams) — faster to read, slower to write. GiST = continuous / spatial “does it overlap or how near” (ranges, geometry, KNN) — more balanced read/write, and the go-to index for nearest-neighbour search (SP-GiST also supports KNN for point types). If the question is “does this row contain value X,” think GIN; if it’s “does this shape overlap / what’s closest,” think GiST. (JSONB is L31, full-text is L32 — both come back to GIN.)

03 Tiny & space-partitioned

BRIN & SP-GiST

The last pair are the specialists you reach for rarely but that win enormously when they fit. BRIN (Block Range INdex) is the one worth real attention, because it inverts the usual index trade-off. A B-tree stores an entry per row; a BRIN stores a tiny summary per range of pages — typically the min and max value of the indexed column across each 128-page block (1 MB by default). For a table of hundreds of millions of rows, the entire BRIN can be a few kilobytes, versus gigabytes for a B-tree.

The catch is what makes it work: physical correlation. A range scan with BRIN reads the per-block min/max, skips any block whose range can’t contain matching rows, and reads only the survivors from the heap. That only pays off if rows are stored roughly in order of the indexed column — which is exactly the case for append-only, time-ordered tables: an event log where created_at only ever increases as rows are inserted. If the column is scattered randomly across the heap, every block’s min/max spans the whole domain, nothing can be skipped, and BRIN degenerates into a full scan.

sql

-- BRIN: a kilobyte-scale summary index for a huge, time-ordered log
CREATE INDEX idx_events_created_brin ON events USING brin (created_at);

-- Tune the granularity: fewer pages per range = finer summaries, bigger index
CREATE INDEX idx_events_created_brin ON events
  USING brin (created_at) WITH (pages_per_range = 32);

SELECT count(*) FROM events
WHERE created_at >= now() - interval '1 day';

When does BRIN beat B-tree? When all of these hold: the table is enormous, the queries are range scans (not point lookups — BRIN is lossy and still rechecks the heap), the column has high physical correlation, and you care about space or write overhead (a BRIN barely slows inserts). Lose the correlation — e.g. after heavy updates shuffle the heap — and you must restore order with CLUSTER or rely on natural append order. Note that CLUSTER is a one-time reorganization; Postgres does not keep the table clustered as new rows arrive.

SP-GiST (Space-Partitioned GiST) rounds out the set. Where GiST is balanced, SP-GiST builds unbalanced, space-partitioning trees — quadtrees, k-d trees, radix tries — which fit data that naturally divides into non-overlapping regions: points in a plane, IP addresses / subnets, and text with shared prefixes. You’ll meet it far less often than the others, but it’s the right structure when your data is a hierarchy of disjoint partitions.

sql

-- SP-GiST: partition IP addresses by their prefix structure
CREATE INDEX idx_hosts_ip ON hosts USING spgist (ip inet_ops);
SELECT * FROM hosts WHERE ip <<= '10.0.0.0/8';   -- contained in subnet
BRIN’s deal, spelled out

BRIN trades precision for size. It never says “the row is here” — only “matching rows, if any, are somewhere in these blocks,” then rechecks. On the right table (huge, ordered, range-queried) that’s a spectacular win: a tiny index, negligible write cost, and range scans that skip most of the heap. On the wrong table (random order, point lookups) it’s worse than useless. Correlation is not optional — it is the whole premise.

04 Worked problem

Pick the index for each query ▸

Here is the skill under load. Same application, three columns, three query shapes — and three different right answers. We’ll set up the schema, look at each query’s naive plan, choose the index, and read the plan it enables. Watch the diagram route each query to its type, then work the SQL underneath it.

sql · schema

CREATE TABLE posts (
  id         bigint PRIMARY KEY,
  author_id  uuid   NOT NULL,
  tags       text[] NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- append-only, ~500M rows, inserted strictly in time order
CREATE TABLE events (
  id         bigint GENERATED ALWAYS AS IDENTITY,
  user_id    uuid   NOT NULL,
  kind       text   NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

Case A — array containment → GIN

Task: find every post tagged sql: WHERE tags @> ARRAY['sql']. With no index, the planner has no choice but to read all million rows and test each array:

illustrative · before

Seq Scan on posts  (cost=0.00..24500.00 rows=1180 width=64)
  Filter: (tags @> '{sql}'::text[])
  Rows Removed by Filter: 998820

Nearly a million rows read and discarded. A B-tree on tags can’t help — it would index each array as one opaque key, useless for “contains sql.” The right tool is GIN:

sql · fix

CREATE INDEX idx_posts_tags ON posts USING gin (tags);

illustrative · after

Bitmap Heap Scan on posts  (cost=32.10..3180.40 rows=1180 width=64)
  Recheck Cond: (tags @> '{sql}'::text[])
  ->  Bitmap Index Scan on idx_posts_tags  (cost=0.00..31.80 rows=1180 width=0)
        Index Cond: (tags @> '{sql}'::text[])

The GIN index produces a bitmap of matching rows (Bitmap Index Scan), the heap reads only those pages (Bitmap Heap Scan), and the estimated cost drops by nearly 8×. Reading bottom-up: probe the inverted index for sql, build a bitmap, fetch only the matching heap pages.

Case B — a range on a giant log → BRIN

Task: count events from the last day on the 500-million-row, time-ordered events table: WHERE created_at >= now() - interval '1 day'. A B-tree on created_at would serve this — but on 500M rows that index is several gigabytes and slows every insert. Because rows arrive in created_at order, a BRIN summarizes the whole table in kilobytes:

sql · fix

CREATE INDEX idx_events_created_brin ON events USING brin (created_at);

illustrative · after (PG 18: BUFFERS on by default)

Aggregate  (cost=182450.0..182450.1 rows=1 width=8) (actual time=421.7..421.7 rows=1 loops=1)
  Buffers: shared hit=210 read=23140
  ->  Bitmap Heap Scan on events  (cost=64.0..181900.0 rows=220000 width=0)
        Recheck Cond: (created_at >= now() - '1 day'::interval)
        Rows Removed by Index Recheck: 4100
        ->  Bitmap Index Scan on idx_events_created_brin  (cost=0.0..9.0 rows=... width=0)
              Index Cond: (created_at >= now() - '1 day'::interval)

The Bitmap Index Scan on the BRIN costs almost nothing because the index is tiny; it flags the block ranges whose min/max could hold recent rows, and the heap scan reads only those blocks. The Rows Removed by Index Recheck line is BRIN being lossy — it hands back whole blocks, and the recheck drops the few non-matching rows within them. On a random-order table this plan would collapse into reading everything; correlation is what makes it fast.

Case C — selective equality → B-tree (default)

Task: fetch one user’s recent events: WHERE user_id = :uuid. This is textbook B-tree work — a highly selective equality on a scalar column that also feeds joins and ORDER BY created_at. No exotic type needed; the default is exactly right:

sql · fix

CREATE INDEX idx_events_user ON events (user_id, created_at DESC);

illustrative · after

Index Scan using idx_events_user on events  (cost=0.57..8.79 rows=7 width=48)
  Index Cond: (user_id = '3f9a...'::uuid)

An Index Scan straight to the seven matching rows, already ordered by created_at DESC because the composite index put the sort column second — so a “latest events for this user” page needs no Sort node at all. GIN can’t do this (it’s for many-values-per-row), BRIN can’t (it’s lossy and range-only) — equality on a selective scalar is the B-tree’s home turf.

Narrate it — the reasoning you’d say out loud

“Three columns, three shapes. tags holds many values per row and the test is containment, so I invert it with GIN. created_at is a range query over a 500-million-row, append-ordered log where a B-tree would be gigabytes — so a kilobyte-scale BRIN on the correlated column, accepting the lossy recheck. user_id is a selective equality that also sorts and joins, so the default B-tree, composite with created_at DESC to serve the ordering for free.” That sentence — column type, query shape, why this method — is the whole answer an interviewer wants.

05 Graded drills

Graded drills & the traps

Four drills, increasing in subtlety. Read each challenge, decide the index (and its operator class) before you open the solution — the operator class is where most people slip.

Drill 1 — JSONB containment

An events table has a data jsonb column. The hot query is WHERE data @> '{"plan":"pro"}', run constantly; you never use the key-exists operators (?, ?|). Index it for the smallest, fastest structure.

Try it first, then read

sql

CREATE INDEX idx_events_data ON events USING gin (data jsonb_path_ops);
SELECT * FROM events WHERE data @> '{"plan":"pro"}';

Why: the default jsonb_ops class supports @> and key-exists (?), but is larger. jsonb_path_ops indexes only value-paths — smaller and faster for @> — at the cost of not supporting ?. Since you only do containment, it’s the better fit.

Drill 2 — case-insensitive infix search

Users type a fragment into a search box and you run WHERE name ILIKE '%ana%'. A plain B-tree is useless here (the leading % means it isn’t a prefix). Make this fast.

Try it first, then read

sql

CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_users_name_trgm ON users USING gin (name gin_trgm_ops);
SELECT * FROM users WHERE name ILIKE '%ana%';

Why: pg_trgm breaks each value into 3-character trigrams and indexes those, so an infix or leading-wildcard match becomes a lookup of the query’s trigrams — something no B-tree can do. Use gin_trgm_ops for fast reads; gist_trgm_ops is an option when writes dominate.

Drill 3 — a range on a log table

An 800-million-row logs(ts, level, msg) table is append-only (rows always arrive in ts order). The only queries are recent-window scans like WHERE ts >= now() - interval '2 hours'. You want the smallest index that serves them without slowing inserts.

Try it first, then read

sql

CREATE INDEX idx_logs_ts_brin ON logs USING brin (ts) WITH (pages_per_range = 64);

Why: enormous + physically ordered + range query = BRIN’s sweet spot — a few kilobytes, negligible insert cost, and block-range skipping for the recent window. Tuning pages_per_range down sharpens the summaries for tighter time windows. This only holds because inserts preserve ts order; if that ever breaks, the BRIN stops skipping and you’d need CLUSTER.

Drill 4 — the low-cardinality boolean trap

You index users(is_active) with a plain B-tree so that WHERE is_active is fast — but the planner keeps choosing a Seq Scan anyway. Why, and what should you build instead?

Try it first, then read

sql

-- Nearly useless: a boolean has ~2 distinct values; is_active = true
-- matches ~half the table, so a Seq Scan is cheaper than index + heap fetches.
CREATE INDEX idx_users_active ON users (is_active);

-- Better: a PARTIAL index over just the rows you actually query,
-- carrying a useful sort column as the key.
CREATE INDEX idx_users_active_recent ON users (created_at DESC) WHERE is_active;

Why: an index only helps when it lets you skip most of the table. A predicate matching half the rows doesn’t — the random heap fetches cost more than a sequential scan. The fix isn’t a different type, it’s a smarter B-tree: a partial index that only covers the hot subset (and here also serves the ordering). If instead is_active = true were rare (say 1%), even a plain B-tree would be worth it — selectivity, not the boolean type, is the real driver.

The traps that bite in review

  • GIN write amplification. One insert updates every token’s posting list. On write-heavy tables tune fastupdate / gin_pending_list_limit — or reconsider whether you need the index at all.
  • BRIN with no correlation. If rows aren’t physically ordered by the indexed column, every block’s min/max spans the domain, nothing is skipped, and BRIN reads the whole heap. It needs natural append order or a CLUSTER — and CLUSTER is not maintained automatically.
  • Hash can’t range, sort, or prefix. Equality only. The moment a <, >, ORDER BY, or LIKE 'a%' appears, a hash index is dead weight — use B-tree.
  • Wrong operator class. gin (data) vs gin (data jsonb_path_ops); gin_trgm_ops for LIKE/ILIKE; inet_ops for SP-GiST. The wrong opclass means the index is silently unused — always confirm with EXPLAIN.
★ Review

Summary & self-test

One idea carries the lesson: the index type is dictated by the shape of the query and the type of the column, not by habit. B-tree is the correct default for scalar equality, ranges, and sorting — but arrays, JSONB, text, geometry, and giant ordered tables each have a purpose-built access method that the default cannot match.

02Hash = equality onlyNo range, sort, or prefix. Niche win on very large keys; WAL-safe since PG 10.
03GIN invertsMany keys per row → posting lists. Arrays @>, JSONB, full-text, trigrams. Fast reads, heavier writes.
04GiST = overlap & nearBalanced tree of bounding predicates. Ranges, geometry, and the primary KNN index (SP-GiST also does KNN for points).
05BRIN is tinyPer-block min/max summaries. Kilobytes for a huge table — but only with high physical correlation.
06SP-GiST partitions spaceUnbalanced quadtrees / tries / radix. Points, IP subnets, shared text prefixes.

08Selectivity trumps typeA low-cardinality column wants a partial index, not a plain B-tree. An index only helps if it skips most rows.
