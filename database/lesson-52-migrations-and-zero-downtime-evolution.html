Migrations & Zero-Downtime Evolution

Your schema is never finished. The hard part isn't writing the new ALTER — it's applying it to a table that thousands of live queries are hitting right now, without stalling any of them. This lesson turns the danger into a repeatable recipe: the expand/contract pattern, the handful of Postgres tricks that keep every step lock-light, and a full worked migration you could run against production traffic.

Original study notes. Written for engineers shipping schema changes on a busy PostgreSQL (PG 17/18) database. Contains three interactive diagrams (press Play or step with Next). This is a practice lesson — it ends in a worked SQL problem and a set of graded drills, so keep a psql window handy and try each one before reading the fix.
00 Orientation

Changing a schema while it is in use

In a tutorial you run ALTER TABLE against an empty table and it returns instantly. In production the same statement runs against a table with a hundred million rows, being read and written by every request in flight — and now the question isn't "does it work?" but "what lock does it take, and for how long?" Get that wrong and a one-line migration becomes a customer-visible outage.

We first met this danger back in Phase 4 (indexing) and in the operations phase: a naive DDL statement can grab an ACCESS EXCLUSIVE lock — the strongest lock Postgres has — and hold it for the entire duration of a table rewrite. While that lock is held, every other query on the table, even a plain SELECT, has to wait. On a busy table that wait cascades: connections pile up, the pool exhausts, and the app falls over.

The good news is that safe schema evolution is a solved problem, and the solution is a single pattern with a memorable name: expand / contract (also called "parallel change"). Instead of one big, locking, irreversible statement, you break the change into a ladder of small steps, each of which is fast, holds no long lock, and can be verified or rolled back on its own. This lesson is about learning that ladder well enough to reach for it by reflex.

The one question to ask every migration

Before you run any DDL against a live table, ask: "Which lock does this take, and does it rewrite or scan the whole table while holding it?" If the answer is "a strong lock for a long time," you don't run that statement — you decompose it into steps that don't. Everything below is how.

01 The failure mode

The locking danger ▸

Not all DDL is dangerous — that's the crucial nuance. Some ALTERs are metadata-only: they change the catalog and return in microseconds, holding ACCESS EXCLUSIVE for only that instant. Since PG 11, ADD COLUMN with a non-volatile constant default is one of these — Postgres stores the default as a "missing value" in the catalog instead of writing it into every row.

Others force a full table rewrite or a full table scan while holding the strong lock. ALTER COLUMN ... TYPE, or ADD COLUMN ... DEFAULT gen_random_uuid() (a volatile default — a different value per row), must touch every row. On a large table that's minutes of held ACCESS EXCLUSIVE, and during those minutes the table is effectively frozen. Watch what that does to live traffic:

The lock queue is what makes this so vicious. In Postgres, lock requests are (roughly) ordered: once the migration's ACCESS EXCLUSIVE request is waiting behind current readers, every query that arrives after it also waits — even short SELECTs that would happily coexist with each other. So a slow migration doesn't just block itself; it forms a wall that stops all traffic. The two mistakes here — using a form that rewrites, and holding the lock with no timeout — are exactly what the rest of the lesson removes.

Metadata-only vs rewrite — the dividing line

Instant (metadata-only): ADD COLUMN nullable or with a constant default, DROP COLUMN, renaming, adding a CHECK ... NOT VALID. Rewrites or scans the whole table (dangerous): ALTER COLUMN ... TYPE, a volatile default, SET NOT NULL the naive way, adding a PRIMARY KEY or UNIQUE without a pre-built index. When in doubt, test on a copy and read the lock level in pg_locks.

02 The pattern

Expand / contract (parallel change) ▸

The core insight: you can't safely make a big, atomic, in-place change to a live table — so don't. Instead, add the new shape alongside the old one, migrate over to it gradually while both exist, and only then remove the old shape. Old and new coexist for a while; that's the "parallel" in parallel change. Every rung of the ladder is individually safe, deployable, and reversible.

Notice the shape of the deploys. Rungs 1 and 2 are pure database work (add the column, backfill it). Rung 3 is an application deploy — the code starts writing the new column too, so from that moment on no new row falls behind. Rung 4 is another app deploy that flips reads over. Only rung 5 removes the old thing, and by then nothing depends on it. Because each rung is compatible with the code both before and after it, a rollback is never a schema emergency — you just deploy the previous app version.

Why the ordering is non-negotiable

You must be able to drop the new column right up until reads are switched (rung 4), and you must keep writing the old column until you're sure you'll never need to roll back. That's why dual-write (rung 3) comes before switching reads (rung 4), and why contract (rung 5) is last and separate. Collapse two rungs into one deploy and you lose the safe rollback point between them.

03 The toolkit

The safe toolkit

Expand/contract is the strategy; these are the specific Postgres tools that keep each rung lock-light. Learn them as a checklist — most real migrations are just a few of these composed together.

Add columns the instant way

A nullable column, or a column with a constant default, is metadata-only since PG 11. A volatile default (one that produces a different value per row) forces a rewrite — so never do that on a live table.

sql

-- instant: metadata only
ALTER TABLE orders ADD COLUMN note text;
ALTER TABLE orders ADD COLUMN qty int DEFAULT 1 NOT NULL;   -- constant default, PG11+

-- DANGER: volatile default → full table rewrite under ACCESS EXCLUSIVE
ALTER TABLE orders ADD COLUMN token uuid DEFAULT gen_random_uuid();

Build indexes without locking writes

A plain CREATE INDEX takes a SHARE lock that blocks writes for the whole build. CONCURRENTLY builds the index in the background without blocking reads or writes — at the cost of two table scans and not being allowed inside a transaction block. If it fails partway, it leaves an INVALID index you must drop and retry.

sql

CREATE INDEX CONCURRENTLY idx_orders_user ON orders (user_id);

-- if a previous attempt failed, clean up the invalid index first:
DROP INDEX CONCURRENTLY IF EXISTS idx_orders_user;

Add NOT NULL and constraints without a blocking scan

Adding NOT NULL directly, or adding a CHECK/foreign key, normally scans the whole table under a strong lock. The trick is to split "record the rule" from "verify the data": add the constraint NOT VALID (instant — it only enforces new rows), then VALIDATE it in a second step that takes only SHARE UPDATE EXCLUSIVE and does not block reads or writes.

sql

ALTER TABLE orders ADD CONSTRAINT orders_total_pos
  CHECK (total >= 0) NOT VALID;          -- instant, brief lock
ALTER TABLE orders VALIDATE CONSTRAINT orders_total_pos;   -- scans, but doesn't block DML

Backfill in chunks, never in one transaction

One giant UPDATE holds row locks on millions of rows, bloats the table with dead tuples, and runs for so long it blocks VACUUM and stalls replication. Instead, loop over small batches, committing each — this keeps transactions short and lets autovacuum keep up.

sql

-- run repeatedly (from the app or a script) until 0 rows are updated
UPDATE orders
SET    status = 'legacy'
WHERE  id IN (
  SELECT id FROM orders WHERE status IS NULL LIMIT 5000
  FOR UPDATE SKIP LOCKED
);

Cap how long you'll wait for a lock

Always set lock_timeout before DDL. Without it, if your ALTER can't get its lock immediately it waits — and forms the very queue we saw in Figure 1. With a short timeout it fails fast instead, and you simply retry; a failed migration is far better than a stalled one.

sql

SET lock_timeout = '2s';      -- fail fast rather than block traffic
SET statement_timeout = '0';  -- but let the (unlocked) work itself run
ALTER TABLE orders ADD COLUMN note text;
Two more habits

Avoid long transactions around migrations — an idle-in-transaction session holds locks and blocks autovacuum. And for tables already bloated by heavy churn, pg_repack rebuilds them without the long ACCESS EXCLUSIVE that VACUUM FULL would take. Every tool here has the same goal: never hold a strong lock for longer than an instant.

04 Worked problem

Add a NOT NULL column with zero downtime ▸

Time to put it together on a realistic task, end to end.

1 · The schema

sql

CREATE TABLE orders (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL,
  total   numeric(12,2) NOT NULL
);  -- ~120 million live rows, heavy read + write traffic

2 · The task

Product wants a status column on orders, and it must be NOT NULL (every order has a status). Existing rows should default to 'legacy'; the app will start setting a real status going forward. Do it without an outage.

3 · The naive attempt — and why it fails

sql

-- DON'T: one statement, one long ACCESS EXCLUSIVE lock
ALTER TABLE orders
  ADD COLUMN status text NOT NULL DEFAULT 'legacy';

You might think the constant default makes this instant — and the column add is. But NOT NULL combined with a default on an existing 120M-row table still forces Postgres to be certain no row violates the constraint, and older/edge cases (or later changing the default) drag you toward a full rewrite while holding ACCESS EXCLUSIVE. Worse, teams often reach for a volatile default or a follow-up ALTER COLUMN ... TYPE, guaranteeing a rewrite. Minutes of held lock on this table means the queue-and-outage from Figure 1. Even in the versions where the fast path would apply, betting your uptime on that subtlety is the wrong instinct — decompose it and the danger disappears entirely.

4 · The fix — expand/contract, step by step

sql

-- ① EXPAND: nullable column, instant metadata change
SET lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN status text;

-- ② APP DEPLOY (before any enforcement!): ship the version that writes `status`
--    on every INSERT/UPDATE. New rows are now non-null; only the old backlog is NULL.

-- (optional) a partial index makes each backfill batch an index scan
CREATE INDEX CONCURRENTLY idx_orders_status_null
  ON orders (id) WHERE status IS NULL;

-- ③ BACKFILL the old rows in batches: loop until 0 rows updated
UPDATE orders SET status = 'legacy'
WHERE id IN (SELECT id FROM orders WHERE status IS NULL LIMIT 5000);

-- ④ record the NOT NULL rule without scanning (safe now: app + backfill both fill status)
ALTER TABLE orders
  ADD CONSTRAINT orders_status_nn CHECK (status IS NOT NULL) NOT VALID;

-- ⑤ verify existing rows — SHARE UPDATE EXCLUSIVE, no DML blocked
ALTER TABLE orders VALIDATE CONSTRAINT orders_status_nn;

-- ⑥ promote to a real NOT NULL — fast, reuses the validated CHECK (PG12+)
ALTER TABLE orders ALTER COLUMN status SET NOT NULL;
ALTER TABLE orders DROP CONSTRAINT orders_status_nn;
DROP INDEX CONCURRENTLY IF EXISTS idx_orders_status_null;

5 · Why it's better

No step holds ACCESS EXCLUSIVE for more than an instant. The column add is metadata-only; the backfill is a stream of short transactions; the NOT VALID constraint records the rule without scanning; VALIDATE scans under a weak lock that never blocks reads or writes; and the final SET NOT NULL is near-instant because, since PG 12, the planner sees an already-validated CHECK (status IS NOT NULL) and skips the full-table scan it would otherwise need. The partial index turns each backfill batch into an index scan instead of a repeated sequential scan of ever-fewer matching rows:

explain — illustrative

Update on orders  (cost=0.57..842.10 rows=0 width=0) (actual time=41.2..41.2 rows=0)
  ->  Index Scan using idx_orders_status_null on orders
        (cost=0.57..817.10 rows=5000 width=14) (actual rows=5000 loops=1)
Planning Time: 0.19 ms
Execution Time: 44.6 ms

An Index Scan on the partial index touches only the 5,000 rows in this batch — no Seq Scan over 120M rows per iteration. Each batch commits in tens of milliseconds and never contends with live traffic.

6 · Narrate it

"I never add a NOT NULL column to a big live table in one statement. I expand with a nullable column, backfill it in small committed batches (indexed so each batch stays cheap), then split the constraint: add it NOT VALID so it guards new rows instantly, and VALIDATE it under a lock that doesn't block DML. After the app deploy guarantees no more NULLs, SET NOT NULL is instant because Postgres trusts the validated check. Every step is fast, and I can stop or roll back between any two."

05 Graded drills

Drills & traps

Each drill is a migration someone actually shipped. Diagnose the danger and rewrite it safely before opening the solution.

Drill 1 — the volatile default (easy)

A teammate wants to add a per-row request token to a busy 80M-row table and runs this in a migration. What happens, and what's the safe version?

sql

ALTER TABLE events ADD COLUMN token uuid
  NOT NULL DEFAULT gen_random_uuid();
Try it first, then read

Solution. gen_random_uuid() is volatile — a distinct value per row — so this can't use the fast-default path; it rewrites all 80M rows under ACCESS EXCLUSIVE and freezes the table for minutes. Do it as expand/contract: add the column nullable, backfill tokens in batches, then add NOT NULL via CHECK ... NOT VALID → VALIDATE → SET NOT NULL.
Why: a volatile default forces a full rewrite; a nullable add is metadata-only.

Drill 2 — the blocking index (easy–medium)

To speed up a lookup, this ran during peak traffic and writes to the table stalled for 90 seconds. Fix it, and name the one operational gotcha of your fix.

sql

CREATE INDEX idx_events_user ON events (user_id);
Try it first, then read

Solution. A plain CREATE INDEX holds a SHARE lock that blocks all writes for the whole build. Use CREATE INDEX CONCURRENTLY idx_events_user ON events (user_id);. Gotcha: it can't run inside a transaction block (so it can't be wrapped with other statements in one migration), it scans the table twice (slower), and if it fails it leaves an INVALID index you must DROP INDEX CONCURRENTLY and retry.
Why: CONCURRENTLY trades speed and transactionality for not locking writes.

Drill 3 — the un-chunked backfill (medium)

This backfill "worked in staging" but on production it ran for 20 minutes, bloated the table, and lagged the replica. Rewrite it.

sql

UPDATE events SET region = lower(region_raw);   -- all 80M rows, one txn
Try it first, then read

Solution. One statement = one long transaction holding row locks on 80M rows, creating 80M dead tuples at once and pinning WAL / blocking VACUUM — which is what lags the replica. Batch it and commit each batch:

sql

-- repeat until 0 rows; each iteration is its own committed txn
UPDATE events SET region = lower(region_raw)
WHERE id IN (
  SELECT id FROM events
  WHERE region IS DISTINCT FROM lower(region_raw) LIMIT 10000
);

Why: short transactions let autovacuum reclaim dead tuples between batches and keep replication caught up.

Drill 4 — the missing lock_timeout (medium–hard)

This instant metadata change ran on a quiet-looking table, yet it took the whole app down for two minutes. The DDL itself was cheap. What happened, and how do you prevent it?

sql

ALTER TABLE orders ADD COLUMN note text;   -- metadata only… right?
Try it first, then read

Solution. The ALTER is instant, but to start it must acquire ACCESS EXCLUSIVE — and a long-running query (or an idle-in-transaction session) was already holding a weaker lock on orders. The ALTER waited for that lock, and while it waited every new query queued behind it (lock-queue ordering). Prevent it by always setting a short lock_timeout so the migration fails fast and retries instead of forming the queue:

sql

SET lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN note text;   -- fails fast if it can't get the lock

Why: the risk isn't the DDL's duration — it's how long it waits for its lock while blocking everyone behind it.

The traps, collected

  • Volatile default (gen_random_uuid(), random()) on ADD COLUMN → full table rewrite. Constant defaults are fine.
  • Plain CREATE INDEX on a live table blocks writes for the whole build → use CONCURRENTLY.
  • Naive SET NOT NULL / ADD CHECK / ADD FOREIGN KEY scans the table under a strong lock → use NOT VALID then VALIDATE.
  • One big backfill = one long transaction → bloat, dead tuples, replica lag → chunk and commit.
  • No lock_timeout → a waiting migration forms a lock queue and takes everything down.
  • Collapsing expand/contract rungs into one deploy destroys your safe rollback points.
  • ORM auto-generated migrations emit the naive form by default — review the raw SQL before shipping.
★ Review

Summary & self-test

One idea holds the whole lesson together: you cannot safely make a big, atomic, in-place change to a live table — so you replace it with a ladder of small, lock-light, reversible steps. Expand/contract is that ladder, and the toolkit (instant adds, CONCURRENTLY, NOT VALID+VALIDATE, chunked backfills, lock_timeout) is how each rung stays cheap.
