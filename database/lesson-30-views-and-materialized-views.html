Views & Materialized Views

Two features share the word “view” and could not be more different. A plain VIEW is a named query — it stores no data, and the planner inlines it into whatever query uses it, so it is never faster than the SQL it stands for. A MATERIALIZED VIEW stores a query's result on disk, turning an expensive aggregate into a cheap table read — at the price of going stale until you REFRESH it. This lesson pins down which tool solves which problem, then builds the exact one a slow dashboard needs.

Written from scratch, grounded in PostgreSQL 17/18 behaviour (view inlining, updatable views with WITH CHECK OPTION, REFRESH MATERIALIZED VIEW CONCURRENTLY, and scheduled refresh via pg_cron). 00 Orientation

Two things called “view”

Start with the one distinction the whole lesson turns on. A view is a stored query definition — a saved SELECT you can query as if it were a table. Nothing about its data is stored; every time you read the view, Postgres runs the underlying query. A materialized view is the opposite trade: it runs the query once, stores the resulting rows in a real on-disk relation, and hands you those pre-computed rows on every read until you explicitly rebuild them.

sql

-- a VIEW: just a named query. No rows are stored.
CREATE VIEW active_users AS
    SELECT id, email, country
    FROM users
    WHERE deleted_at IS NULL;

-- a MATERIALIZED VIEW: the result is computed once and STORED on disk.
CREATE MATERIALIZED VIEW daily_sales AS
    SELECT date_trunc('day', created_at) AS day,
           sum(total)                    AS revenue
    FROM orders
    GROUP BY 1;

From that one difference, everything else follows — and so does the single most common misconception in this whole topic:

The performance myth

A plain view is not a cache and does not make anything faster. Because the planner inlines it, SELECT ... FROM my_view runs the exact same plan as pasting the view's query by hand. If your goal is speed, a view does nothing; you want a materialized view (which stores the result) — and only when you can tolerate some staleness. Reach for a plain view for abstraction, reuse, and security, never for performance.

VIEW — a saved query

  • Stores no data; re-runs on every read.
  • Always fresh — it sees live base rows.
  • Same speed as the raw SQL (it's inlined).
  • For abstraction & security: expose a column/row subset.

MATERIALIZED VIEW — a stored result

  • Stores the computed rows on disk.
  • Goes stale — frozen at the last REFRESH.
  • Reads are a cheap scan of a small table.
  • For expensive aggregates you can serve slightly old.
01 Plain views

A plain view is inlined ▸

To believe the performance myth you have to see why it's true. When you query a view, Postgres does not run the view and then filter its output as a black box. It splices the view's definition straight into your query — a process called inlining (technically, subquery pull-up) — and then plans the combined query as a single whole. Your WHERE clause gets pushed down into the view's tables; indexes get chosen across the merged query. Step through it:

You can prove it with EXPLAIN. Query the view by primary key and the plan mentions the base table's index, not the view — the view has evaporated:

sql

CREATE VIEW active_users AS
    SELECT id, email, country FROM users WHERE deleted_at IS NULL;

EXPLAIN SELECT email FROM active_users WHERE id = 42;

EXPLAIN · illustrative

Index Scan using users_pkey on users  (cost=0.42..8.44 rows=1 width=32)
  Index Cond: (id = 42)
  Filter: (deleted_at IS NULL)

Notice what the planner did: it merged your WHERE id = 42 with the view's WHERE deleted_at IS NULL and ran a single index scan on users_pkey. That is the whole argument for “a view is not faster” — the plan is identical to what you'd get without the view. What a view does buy you is worth having, though: a stable, reusable name for a gnarly query, and a way to expose only a slice of a table.

Views for security, and writing through them

Because a view can drop columns and filter rows, it is a classic access-control tool: grant a role SELECT on active_users and it can never see password_hash or soft-deleted rows. A simple view — one table, no GROUP BY, DISTINCT, aggregates, or window functions — is even updatable: you can INSERT/UPDATE/DELETE through it. Add WITH CHECK OPTION to stop a write from creating a row that would fall outside the view:

sql

CREATE VIEW active_users AS
    SELECT id, email, country, deleted_at FROM users WHERE deleted_at IS NULL
    WITH CHECK OPTION;

UPDATE active_users SET country = 'US' WHERE id = 42;   -- OK: still visible
UPDATE active_users SET deleted_at = now() WHERE id = 42; -- ERROR: new row violates check option for view "active_users"
Updatable views have limits

The moment a view aggregates, joins in a way Postgres can't map back, uses DISTINCT/GROUP BY/UNION/window functions, or otherwise stops being a simple 1:1 projection of one table, it becomes read-only — Postgres can't tell which base rows a write should touch. If you truly need to write through such a view, you attach an INSTEAD OF trigger (Phase 6, L33) and code the mapping yourself. For most uses, keep views simple and read-only.

02 Materialized views

Materialized views & staleness ▸

Now the other tool. A materialized view runs its query once and stores the answer. Reads no longer touch the base tables at all — they scan a small precomputed relation, which is exactly what you want for an aggregate that costs seconds to compute but is read on every page load. The catch is the flip side of storing a result: the stored rows are a snapshot, frozen at the last refresh. New base-table writes are invisible to it until you rebuild it. Watch a matview drift out of sync and then get refreshed:

The two refresh modes you saw at the end are the operational heart of matviews. The plain form rebuilds the relation and swaps it in behind an exclusive lock — correct, but reads freeze until it finishes. The concurrent form rebuilds a copy and diffs it into place without blocking readers, at the cost of doing more work:

sql

-- rebuild the stored rows (recomputes the whole query):
REFRESH MATERIALIZED VIEW daily_sales;
--   ^ takes ACCESS EXCLUSIVE — every reader blocks until it finishes.

-- online refresh — readers keep serving, but it's slower and needs a UNIQUE index:
CREATE UNIQUE INDEX daily_sales_day_uq ON daily_sales (day);
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales;
Why CONCURRENTLY needs a UNIQUE index

REFRESH ... CONCURRENTLY works by computing the new rows and applying only the differences to the existing matview. To match old rows against new ones it needs a way to identify each row — that's what the unique index provides. Without one, Postgres raises cannot refresh materialized view "daily_sales" concurrently and refuses. The index must be unique across all rows (a single-column key like day, or a unique combination). It also makes your reads faster — two wins from one index.

One more thing that trips people up: a fresh matview has no indexes of its own beyond what you add. It is a real table on disk — a read that filters or sorts it will Seq Scan the whole matview unless you index it, exactly like any other table.

03 Keeping it fresh

Refresh strategies & the staleness budget

A matview only helps if you have a deliberate answer to one question: how stale is too stale? That number — your staleness budget — drives every refresh decision. If a revenue dashboard may lag reality by fifteen minutes, refreshing every fifteen minutes is perfect and cheap. If it must be within seconds, a matview is probably the wrong tool. Choose the budget first, then pick a mechanism to meet it.

Scheduled refresh (the workhorse)

The common pattern is a cron job that runs REFRESH ... CONCURRENTLY on a cadence matching the budget. Inside Postgres, the pg_cron extension does this without any external scheduler:

sql

CREATE EXTENSION IF NOT EXISTS pg_cron;

-- every 15 minutes: an online, non-blocking rebuild
SELECT cron.schedule(
    'refresh-daily-sales',
    '*/15 * * * *',
    $$REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales$$);

The refresh interval is your staleness window: reads can be up to one interval old. Tighten it and refresh cost rises (each concurrent refresh recomputes the whole query and diffs it in); loosen it and data lags more. That's the dial.

The other options, and their trade-offs

  • Concurrent vs blocking. Prefer CONCURRENTLY for anything user-facing so refreshes don't freeze reads. If the matview backs an offline report and nobody reads it mid-refresh, a plain (faster) REFRESH during a quiet window is fine.
  • Event-driven refresh. Instead of a fixed clock, kick a refresh after a batch of relevant writes (from application code, or an AFTER trigger that enqueues a job). Fresher after bursts, idle when nothing changes — but beware refreshing too often under heavy write traffic, since each refresh is a full recompute.
  • Incremental maintenance. The big limitation of REFRESH is that it recomputes everything, even if one row changed. Postgres has no built-in incremental matviews yet; the pg_ivm extension adds them (it maintains the result with triggers as base rows change), and hand-rolled trigger-maintained summary tables are the classic DIY version. These trade write-time cost and complexity for always-fresh, cheap reads.
Decision order

Ask in this sequence: (1) Is the read actually slow and repeated? If not, don't materialize anything. (2) What staleness can the feature tolerate? That's your budget. (3) Can a scheduled REFRESH ... CONCURRENTLY meet the budget within acceptable refresh cost? Usually yes — start there. (4) Only if you need near-real-time freshness on an expensive aggregate do you reach for pg_ivm or trigger-maintained summaries.

04 Worked problem

Worked: a slow dashboard rollup

Let's turn a real, slow dashboard query into a fast one and watch the plan collapse. This is the pattern to internalise: confirm the query is expensive and repeated, confirm you can tolerate staleness, then materialize the aggregate and index it.

1 · The schema and the task

sql

CREATE TABLE orders (
    id          bigint        PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    customer_id bigint        NOT NULL,
    status      text          NOT NULL,
    total       numeric(10,2) NOT NULL,
    created_at  timestamptz   NOT NULL DEFAULT now()
);   -- ~10M rows, years of history

An analytics dashboard loads on every visit and shows revenue per day for the last 30 days. The obvious query aggregates straight off the base table:

sql

SELECT date_trunc('day', created_at) AS day, sum(total) AS revenue
FROM orders
WHERE created_at >= now() - interval '30 days'
GROUP BY 1
ORDER BY 1;

2 · Attempt one — run the aggregate every load

EXPLAIN ANALYZE · illustrative

Sort  (cost=245311.6..245311.7 rows=30 width=16) (actual time=612.5..612.5 rows=30 loops=1)
  Sort Key: (date_trunc('day', created_at))
  ->  HashAggregate  (cost=245300.1..245310.8 rows=30 width=16) (actual time=612.1..612.4 rows=30 loops=1)
        Group Key: date_trunc('day', created_at)
        ->  Seq Scan on orders  (cost=0.00..241130.0 rows=834020 width=14) (actual time=0.03..430.9 rows=832145 loops=1)
              Filter: (created_at >= (now() - '30 days'::interval))
              Rows Removed by Filter: 9167855
Execution Time: 612.9 ms

Read it bottom-up. The Seq Scan reads all 10M rows and the Filter throws away 9.1M of them; the surviving 832,145 rows feed a HashAggregate that collapses them into 30 daily totals, which a Sort orders. The whole thing takes ~613 ms — and it runs on every single page load. Even an index on created_at only trims the scan; you'd still aggregate hundreds of thousands of rows each time to produce the same 30 numbers.

3 · A plain view changes nothing

The tempting non-fix: wrap that query in a VIEW and expect it to “cache.” It won't — the planner inlines it, so reading the view reproduces the 613 ms plan byte-for-byte:

sql

CREATE VIEW daily_sales_v AS /* the same aggregate */ …;
EXPLAIN SELECT * FROM daily_sales_v;  -- identical HashAggregate over 832k rows

The 30 output numbers barely change minute to minute, yet we recompute them from 800k+ rows constantly. That is precisely the shape a materialized view is for: an expensive aggregate whose result we can serve a little stale.

4 · The fix — materialize, index, refresh on a schedule

sql

-- store the whole per-day rollup once (all history, one row per day):
CREATE MATERIALIZED VIEW daily_sales AS
    SELECT date_trunc('day', created_at) AS day,
           sum(total)                    AS revenue,
           count(*)                      AS orders
    FROM orders
    GROUP BY 1;

-- unique index: enables REFRESH ... CONCURRENTLY *and* fast range reads
CREATE UNIQUE INDEX daily_sales_day_uq ON daily_sales (day);

-- keep it within a 15-minute staleness budget, without blocking readers:
SELECT cron.schedule('refresh-daily-sales', '*/15 * * * *',
    $$REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales$$);

The dashboard now reads the tiny precomputed table instead of the giant base table:

sql

SELECT day, revenue
FROM daily_sales
WHERE day >= now() - interval '30 days'
ORDER BY day;

EXPLAIN ANALYZE · illustrative

Index Scan using daily_sales_day_uq on daily_sales  (cost=0.28..12.8 rows=30 width=16) (actual time=0.012..0.028 rows=30 loops=1)
  Index Cond: (day >= (now() - '30 days'::interval))
Execution Time: 0.05 ms

From 613 ms to 0.05 ms — roughly a 12,000× speedup — because we replaced “scan 10M rows and aggregate 800k of them” with “Index Scan ~30 precomputed rows.” The unique index on day pulls double duty: it lets REFRESH ... CONCURRENTLY run online, and it turns the 30-day read into a clean index range scan. The price is honest and bounded: the numbers can be up to 15 minutes old. 5 · Narrate the design

Three decisions, each answering a specific pressure in the plan:

  • Materialize the aggregate because it is expensive (800k rows aggregated) and read constantly, while its output (30 numbers) changes slowly — the exact profile a stored result rewards.
  • Add the unique index on day for two reasons at once: it is the identity REFRESH ... CONCURRENTLY requires, and it turns the dashboard's 30-day filter into an index range scan.
  • Refresh concurrently on a 15-minute cron so the stated staleness budget is met without ever freezing a reader — the schedule interval literally is the freshness guarantee.
The materialize checklist

Slow + repeated read → is a plain view enough? (No, if you need speed.) → can I tolerate staleness? (Set the budget.) → CREATE MATERIALIZED VIEW → add a UNIQUE index (for concurrent refresh and fast reads) → schedule REFRESH ... CONCURRENTLY to the budget → prove the read is now an Index Scan with EXPLAIN. Skip any step and you get a stale, locking, or still-slow surprise in production.

05 Practice

Graded drills & traps

Four drills, increasing in difficulty. Reason each one out — write the SQL or name the cause — before opening the solution.

Drill 1 — “the numbers are behind”

Support reports the revenue dashboard is showing figures a few minutes old, and a stakeholder wants it “live.” It's backed by the daily_sales matview refreshed every 15 minutes. What's the lever, and what's the trade-off?

Try it first, then read

A matview is a snapshot; it only changes on REFRESH. Tighten the cadence to shrink the staleness window:

sql

SELECT cron.unschedule('refresh-daily-sales');
SELECT cron.schedule('refresh-daily-sales', '* * * * *',  -- every minute
    $$REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales$$);

Why: the interval is the freshness guarantee, but each refresh is a full recompute, so tighter = more load. For truly live numbers, don't use a matview — query the base table, or use incremental maintenance (pg_ivm/triggers). Pick the staleness budget deliberately.

Drill 2 — the dashboard freezes on the quarter-hour

Every 15 minutes, all dashboard reads hang for a couple of seconds, exactly when a scheduled job runs. The job is REFRESH MATERIALIZED VIEW daily_sales. Diagnose and fix.

Try it first, then read

A plain REFRESH takes an ACCESS EXCLUSIVE lock and rebuilds in place, so every reader blocks until it finishes. Switch to the online form:

sql

CREATE UNIQUE INDEX IF NOT EXISTS daily_sales_day_uq ON daily_sales (day);
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales;

Why: CONCURRENTLY builds a copy and diffs it in without an exclusive lock, so reads keep serving. It is slower and needs the unique index — a worthwhile trade for a user-facing dashboard.

Drill 3 — CONCURRENTLY refuses to run

You add the concurrent refresh and it errors: cannot refresh materialized view "daily_sales" concurrently. The matview is SELECT customer_id, region, sum(total) ... GROUP BY customer_id, region. What's wrong, and how do you fix it?

Try it first, then read

CONCURRENTLY needs a UNIQUE index that identifies every row, and none exists. No single column is unique here — but the grouping keys together are. Index the full key:

sql

CREATE UNIQUE INDEX daily_sales_cust_region_uq
    ON daily_sales (customer_id, region);

Why: a matview grouped by (customer_id, region) has exactly one row per pair, so that combination is a valid unique key. Match the unique index to the grouping columns that make each row distinct.

Drill 4 — the “caching view” and a failed write

A teammate wrapped the slow rollup in a plain VIEW named daily_sales_v “to cache it,” and reads are still slow. They also try INSERT INTO daily_sales_v ... and it errors. Explain both, and state when a view helps versus when you need a matview.

Try it first, then read

A view stores nothing: the planner inlines it and re-runs the full aggregate on every read, so there's no caching and the plan is identical to the raw query — a view is never a performance tool. And you can't INSERT through it because a view with GROUP BY/aggregates is not updatable — Postgres can't map an inserted summary row back to base rows.

Fix & rule: use a plain view for abstraction, reuse, and security (a stable name, a column/row subset). Use a materialized view when the query is expensive, read often, and you can accept staleness — then index it and schedule REFRESH ... CONCURRENTLY.

Traps to avoid

1. A plain view is not a cache. It re-runs its query every read (inlined). For speed you need a materialized view, not a view.
2. Matviews go stale silently. A snapshot frozen at the last REFRESH; nothing auto-updates it. Own the staleness budget and schedule the refresh.
3. Plain REFRESH blocks reads. It takes ACCESS EXCLUSIVE. Use CONCURRENTLY for anything user-facing, or refresh off-peak.
4. CONCURRENTLY needs a UNIQUE index and still fully recomputes (it isn't incremental) — it just swaps in without blocking.
5. Unindexed matviews Seq Scan. A matview is a real table; add indexes (starting with the unique one) or reads scan the whole thing.
6. Updatable-view limits. Aggregates, DISTINCT, GROUP BY, UNION, and window functions make a view read-only; use an INSTEAD OF trigger only if you must write through it.
