The Dual-Write Problem & the Transactional Outbox

Almost every service eventually has to do two things at once: save a row in Postgres and tell the outside world about it — publish an event, invalidate a cache, notify a search index. The moment those are two separate systems with no shared transaction, a single badly-timed crash can leave them permanently out of sync. This practice lesson names that failure precisely, then builds the standard cure — the transactional outbox — as real PostgreSQL you can run: one transaction, one extra table, and a relay that can never lose your event.

46 Motivation

Two systems, one crash

Picture the most ordinary handler in a web service: a customer places an order. Your code does two things. First it saves the order to Postgres. Then it publishes an event — order_placed — to a message broker like Kafka or RabbitMQ, so the email service can send a confirmation, the search index can list the item, and analytics can count the sale. This is a dual write: one logical action that must land in two independent systems.

Here is the whole problem in one sentence: a Postgres transaction protects only what happens inside Postgres. It cannot reach across into the broker. The broker has its own commit, its own durability, its own failure modes. There is no BEGIN that wraps "the order row and the Kafka message" into a single all-or-nothing unit. So the two writes are separate events in time — and any gap between them is a window in which the process can die, the network can drop, or the broker can be unreachable.

Whatever order you choose, one ordering's crash betrays you:

Commit first, then publish

  • Order is durably saved in Postgres.
  • Process crashes before the publish call.
  • The event is lost forever — no email, no search entry.
  • No error is raised; the order simply looks placed but silent downstream.

Publish first, then commit

  • Event is already on the broker.
  • Transaction rolls back (constraint fails, crash, deadlock).
  • Downstream acts on a ghost order that never existed.
  • You emailed a confirmation for a purchase that isn't in the database.

Neither ordering is safe, and no amount of "just add a retry" closes the hole — a retry only helps if the process survives long enough to run it, and the crash is precisely the case where it doesn't. This is the dual-write problem, and it shows up any time one action must update two stores: database + queue, database + cache, database + search, or two databases. Naming it is half the battle; the other half is a pattern that removes the second system from the critical path entirely.

Why not one big distributed transaction?

The tempting answer is "make Postgres and the broker commit together" — a two-phase commit (PREPARE TRANSACTION). It is a trap we dismantle in a later lesson: the coordinator becomes a single point of failure, and a crash mid-protocol leaves participants blocked, holding locks and pinning resources. The pattern that actually ships is far more boring, and that is its virtue.

The cruelest part is how quiet the failure is. Nothing throws. The API returned 201 Created; the order really is in the database; the customer's card may even be charged. Only the downstream world never heard about it — and you find out hours later when a support ticket asks where the confirmation email went, or when the analytics numbers don't reconcile. There is no stack trace pointing at the bug because, from each system's local point of view, nothing went wrong.

And notice why retries can't save you here. A publish that fails with an exception can be retried — but the crash happens between the successful commit and the publish call, killing the very code that would have done the retrying. The window is small, but "small times millions of requests" is a steady drip of lost events. At scale, rare is just a synonym for constant.

The gap is fundamental, not a bug you can code around

You cannot shrink the window to zero by writing more careful code, because the window is the space between two independent commits. As long as the event's fate lives in a second system that Postgres can't include in its transaction, some crash lands in the gap. The fix is not to protect the gap — it is to make it disappear by writing to only one system.

46 The pattern

The transactional outbox ▸

The insight is almost too simple: stop writing to two systems. Instead of "insert the order, then publish the event," you insert the order and a description of the event into the same Postgres transaction. That description goes into an ordinary table called the outbox. Because both inserts share one transaction, they are atomic — the order and its pending event commit together, or neither does. The event is now exactly as durable as the order itself.

A separate relay then reads the outbox and publishes to the broker, marking each row as sent. The broker is no longer in your request's critical path — it's downstream of a table you fully control. Follow the reshaped flow:

Trace what changed. The dangerous gap from Figure 1 — between the DB commit and the broker publish — is gone, because there is no longer a broker publish inside the request. There is one write, to one system, in one transaction. If the process crashes anywhere before COMMIT, both the order and the outbox row roll back together: no order, no orphan event, consistent. If it crashes anywhere after COMMIT, both are safely on disk and the relay will get to them: the order exists and the event is guaranteed to publish eventually. There is no interleaving that produces an order without its event, or an event without its order.

One source of truth, then fan out

The outbox turns a distributed-consistency problem into a local one. Postgres becomes the single source of truth for "what happened," and the outbox is a durable, ordered log of "what needs to be told to the outside world." Everything downstream — brokers, caches, search indexes — becomes a consumer of that log rather than a second thing you write to synchronously. You'll see this exact shape again when we sync a cache or a search index without dual-writing.

46 The relay

Getting events out of the outbox

The transaction side is now airtight. The remaining job — move rows from the outbox to the broker — is a comfortable, well-understood problem, because it happens after a durable commit and can be retried freely. There are two standard ways to run the relay.

Polling publisher

  • A worker loops: SELECT unsent rows → publish → mark sent.
  • Runs anywhere; no extra infrastructure.
  • Use FOR UPDATE SKIP LOCKED so several relay workers never grab the same row (recap L28).
  • Trade-off: polling adds a little latency and steady query load.

Log tailing (CDC)

  • Debezium (or raw logical decoding, L45) tails the WAL for outbox inserts.
  • Near-real-time, no polling query at all.
  • Streams changes straight to Kafka via a connector.
  • Trade-off: more moving parts to run and monitor.

Whichever you pick, three properties define whether your relay is correct in production.

Delivery is at-least-once, never exactly-once. Suppose the relay publishes an event to the broker, then crashes before it can mark the outbox row sent. On restart it sees the row still unsent and publishes again. The broker now holds the event twice. This is unavoidable — there is the same kind of gap between "publish succeeded" and "row marked sent" that we just eliminated on the write side. Exactly-once delivery is a myth; the real guarantee is at-least-once delivery plus an idempotent consumer that treats a duplicate as a no-op (the subject of L47).

Ordering costs care. Reading the outbox ORDER BY id preserves the order rows were inserted, so a single relay worker publishes events in the order they happened. But the instant you run several relay workers with SKIP LOCKED, two of them can publish out of order relative to each other. If consumers need per-entity order (an order's placed before its cancelled), you must route all events for one aggregate to the same worker or the same broker partition — a drill below.

Sent rows must be cleaned up. The outbox grows forever if you never prune it. Left alone, the table and its indexes bloat, and even a filtered scan slows. The fix is a partial index that indexes only unsent rows (so the relay's poll stays tiny no matter how many millions of sent rows accumulate) plus a periodic delete or partition-drop of old sent rows.

The outbox is the anti-dual-write, everywhere

This same pattern is how you keep a Redis cache or an Elasticsearch index in sync without dual-writing to them: write the change to Postgres and an outbox row atomically, then let a relay (polling or CDC) apply it to the derived store idempotently. Cache, search, warehouse, another service — they all become consumers of one ordered, durable log instead of a second synchronous write you can lose.

46 Worked build

A worked order outbox, end to end ▸

Now assemble the whole thing for an order service. First, watch the healthy lifecycle you are building toward — and its at-least-once tail, where a duplicate is absorbed by an idempotent consumer:

1 · The schema

Two tables: the domain orders, and a generic outbox that can carry events for any aggregate. A partial index on unsent rows keeps the relay's poll cheap forever.

sql

CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint      NOT NULL,
  total_cents int         NOT NULL,
  status      text        NOT NULL DEFAULT 'placed',
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE outbox (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  aggregate    text        NOT NULL,   -- 'order'
  aggregate_id bigint      NOT NULL,   -- the order id
  event_type   text        NOT NULL,   -- 'order_placed'
  payload      jsonb       NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now(),
  sent_at      timestamptz              -- NULL until the relay publishes it
);

-- keep the relay's poll tiny: index ONLY the rows still to send
CREATE INDEX outbox_unsent_idx ON outbox (id)
  WHERE sent_at IS NULL;

3 · The naive dual write, and why it is wrong

sql

-- WRONG: two systems, no shared transaction.
BEGIN;
  INSERT INTO orders (customer_id, total_cents) VALUES ($1, $2);
COMMIT;                              -- Postgres now durably holds the order
-- ...then, in application code, AFTER the commit:
--   broker.publish('order_placed', ...);
-- A crash between COMMIT and publish loses the event forever (Figure 1).

The commit and the publish are two separate durable events with a gap between them, and that gap is unclosable while the broker is a second system outside the transaction.

4 · The fix: one atomic write, then the relay

Insert the order and its outbox row in a single statement using a CTE, so the two inserts share one implicit transaction and commit atomically. The order's generated id flows straight into the event payload:

sql

-- RIGHT: order + event in ONE transaction — atomic
WITH new_order AS (
  INSERT INTO orders (customer_id, total_cents)
  VALUES ($1, $2)
  RETURNING id, customer_id, total_cents
)
INSERT INTO outbox (aggregate, aggregate_id, event_type, payload)
SELECT 'order', id, 'order_placed',
       jsonb_build_object('order_id', id,
                          'customer_id', customer_id,
                          'total_cents', total_cents)
FROM   new_order;

Now the relay. It claims a batch of unsent rows with FOR UPDATE SKIP LOCKED so parallel relay workers never grab the same rows, publishes each to the broker, then stamps sent_at — all inside one short transaction, so a failed publish releases the lock and leaves the rows unsent for a later retry:

sql

-- RELAY, one transaction: claim → publish → mark sent
BEGIN;

-- claim: lock a batch of unsent events in insert order
SELECT id, aggregate_id, event_type, payload
FROM   outbox
WHERE  sent_at IS NULL
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT  100;

-- ...publish each returned event to the broker (application code)...

-- mark the published rows sent, then COMMIT to release the locks
UPDATE outbox SET sent_at = now() WHERE id = ANY($1);

COMMIT;

5 · Why it is better — and what the planner does

Correctness first: there is now only ever one write in the request, to Postgres, in one transaction — the dual-write window is gone. Performance second: the partial index means the relay's claim never scans the ever-growing table. An illustrative EXPLAIN of the claim shows a LockRows node (that is FOR UPDATE SKIP LOCKED) over an index scan of just the unsent rows:

text · illustrative

Limit  (cost=0.29..12.45 rows=100 width=57)
  ->  LockRows  (cost=0.29..40.11 rows=320 width=57)
        ->  Index Scan using outbox_unsent_idx on outbox
              (cost=0.29..36.91 rows=320 width=57)

The line that matters is Index Scan using outbox_unsent_idx — not Seq Scan on outbox. Because the partial index holds only unsent rows, its size is bounded by your backlog, not by lifetime volume, so the poll stays a handful of index entries even at ten million published rows. If you ever see a sequential scan here, the partial index is missing or unused and the relay's cost is quietly growing with the whole table.

Narrate it in an interview

"There's only ever one write: the order row and an outbox row go into Postgres in a single transaction, so they're atomic — a crash leaves both or neither, and the event can't be lost. A relay claims unsent outbox rows with FOR UPDATE SKIP LOCKED, publishes them, and stamps sent_at. Delivery is at-least-once, so the consumer dedupes on an idempotency key. A partial index on unsent rows keeps the poll an index scan forever." That is the whole design in four sentences — and the duplicate-handling half is exactly the inbox/idempotency pattern of the next lesson.

46 Drills

Graded drills & traps

Attempt each drill on paper before opening its answer. They all build on the schema and relay from section 04.

Drill 1 — Keep the poll fast as the outbox grows

Months in, the outbox holds twenty million sent rows and a few thousand unsent ones. The relay's SELECT ... WHERE sent_at IS NULL has gotten slow. What one object fixes it, and why?

Try it first, then read

A partial index on just the unsent rows — it never contains the twenty million sent rows, so it stays tiny and delivers them already ordered by id:

CREATE INDEX outbox_unsent_idx ON outbox (id)
  WHERE sent_at IS NULL;

Why: the index size tracks your backlog, not lifetime volume, so the claim is an index scan over a handful of entries regardless of how many events have shipped.

Drill 2 — Reclaim space without blocking the relay

Even with the partial index, the table keeps growing with dead sent rows. Reclaim space without a giant table-locking delete.

Try it first, then read

Delete old sent rows in bounded batches (safe to run on a schedule), or make outbox range-partitioned by created_at and DROP whole old partitions (recap L34):

DELETE FROM outbox
WHERE  id IN (
  SELECT id FROM outbox
  WHERE  sent_at IS NOT NULL
    AND  sent_at < now() - interval '7 days'
  LIMIT 10000
);

Why: batched deletes keep each transaction short and avoid one huge lock; partition drops are near-instant and dodge VACUUM entirely.

Drill 3 — Preserve per-order event ordering

An order emits order_placed then order_cancelled. With several relay workers pulling via SKIP LOCKED, worker B could publish the cancel before worker A publishes the placement. How do you guarantee per-order order?

Try it first, then read

Ordering is only ever guaranteed per key, and only if one worker handles that key at a time. Route all of an aggregate's events to the same worker by sharding on aggregate_id, and publish with the broker key set to aggregate_id so the broker preserves per-key order:

  -- each of N relay workers owns one hash bucket:
  WHERE  sent_at IS NULL
    AND  (hashtextextended(aggregate_id::text, 0) % 4 + 4) % 4 = $worker_id  -- +4)%4 keeps it 0..3 (hash can be negative)
  ORDER BY id
  FOR UPDATE SKIP LOCKED

Why: same aggregate → same worker → published in id order; a per-key broker partition keeps that order end to end. Global total order across all orders is neither needed nor worth the serialization.

Drill 4 — Don't hold a row lock across the network publish

The section-04 relay holds FOR UPDATE during the broker publish, so a slow broker stalls the relay and bloats the table. Restructure so the DB lock is not held during the network call.

Try it first, then read

Split it into a short claim transaction and a separate mark, with publishing outside any transaction — exactly the crashed-worker reclaim shape from L28. Add a claimed_at column; a sweeper resets stale claims:

-- 1) claim & commit immediately (lock released at once)
UPDATE outbox SET claimed_at = now()
WHERE  id IN (
  SELECT id FROM outbox
  WHERE  sent_at IS NULL
    AND  (claimed_at IS NULL OR claimed_at < now() - interval '1 minute')
  ORDER BY id
  FOR UPDATE SKIP LOCKED
  LIMIT  100
)
RETURNING id, aggregate_id, event_type, payload;

-- 2) publish each event OUTSIDE any transaction (no lock held)
-- 3) mark sent
UPDATE outbox SET sent_at = now() WHERE id = ANY($1);

Why: the lock lasts only for the quick claim, not the slow publish. It is still at-least-once (a crash after publish, before mark, re-sends) — so consumers stay idempotent.

The five traps that break real outboxes

(1) Assuming exactly-once. The outbox is at-least-once — a relay can re-publish after a crash. Ship non-idempotent consumers and you get double charges. Always dedupe on an idempotency key (L47).
(2) Publishing inside the domain transaction "to be safe." That is the dual write again. The whole point is that the only write is to Postgres; the broker is touched only by the relay, afterward.
(3) Marking sent before publishing. If the publish then fails, the event is lost — you have re-introduced the exact bug. Mark sent_at only after a successful publish.
(4) No partial index or no cleanup. The outbox bloats, the poll degrades, and VACUUM struggles. Index unsent rows; prune or partition sent ones.
(5) Reaching for two-phase commit instead. PREPARE TRANSACTION across DB and broker gives a coordinator SPOF and blocked prepared transactions pinning locks and WAL. The boring outbox is the correct answer (L49).

★ Review

Summary & self-test

The whole lesson compresses to one line: you cannot atomically write Postgres and a broker, so don't — write the domain row and an outbox row in one transaction (atomic), and let a relay publish the outbox afterward at-least-once, with idempotent consumers absorbing the inevitable duplicates. One write, one source of truth, and the dual-write window disappears.
