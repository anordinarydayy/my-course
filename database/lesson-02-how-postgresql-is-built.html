00 Orientation

Client/server, one process per connection

PostgreSQL is a client/server system. The server is not one program you talk to directly — it's a small family of cooperating processes, and the head of that family is the postmaster: a supervisor that boots the database, opens a listening socket (TCP 5432 by default), and waits. When a client wants in — psql, your app's driver, a migration tool — it opens a connection, and the postmaster does something that shapes everything else: it forks a brand-new operating-system process, a backend, dedicated to that one connection for its entire life.

Read that twice, because the word is process, not thread. Every connection gets its own OS process with its own address space. That single design decision has consequences you will feel for the rest of the course:

What processes buy you

  • Isolation. One backend can't corrupt another's memory; a bug or crash in one session is contained.
  • Robustness. If a backend dies badly, the postmaster notices, resets shared state, and keeps serving.
  • Simplicity. Much of the engine can be written as straight-line, single-threaded code per connection.

What they cost you

  • Weight. A process is far heavier than a thread — memory and setup cost per connection.
  • A ceiling. max_connections is finite; thousands of idle connections waste real resources.
  • The fix later: a connection pooler in front (PgBouncer, or PG 17's built-in improvements) that multiplexes many clients onto few backends — Phase 7.

Whatever the client, it speaks one language on the wire: the PostgreSQL frontend/backend protocol. Your ORM, JDBC, libpq, and psql all frame their queries and results the same way. That uniformity is why any driver can talk to any Postgres, and why a pooler can sit transparently in the middle. You can even watch the backends: one row per live connection shows up in pg_stat_activity.

sql

-- one row per backend; client sessions AND the background processes
SELECT pid, backend_type, state, left(query, 30) AS q
FROM   pg_stat_activity
ORDER BY backend_type;
The one-line summary

Postgres is process-per-connection: a supervisor (the postmaster) forks a dedicated backend for each client. That gives you isolation and crash-resilience for free, but makes a raw connection expensive — which is the entire reason connection pooling exists. Every performance and scaling conversation later starts from this fact.

01 The layout

The process & memory map ▸

So the server is many processes. Where do they keep their data, and how do they cooperate without stepping on each other? The answer is a deliberate split between shared memory that every process attaches to, and private memory that belongs to one backend alone. Add a set of always-on background processes doing the housekeeping, and the files on disk, and you have the whole machine. Step through the map:

Two regions deserve a name you'll reuse constantly. shared_buffers is Postgres's own cache of 8 KB data pages, living in shared memory so every backend reads and writes the same cached pages — that's how thousands of sessions see a consistent, hot cache instead of each re-reading disk. work_mem, by contrast, is per-operation, per-backend private scratch space for sorts and hash joins; set it too high and a busy server can multiply it by hundreds of backends and run out of RAM. The background processes are the quiet crew: the checkpointer and background writer push dirty pages to disk, the WAL writer flushes the log, and autovacuum cleans up dead row versions (Phase 5).

Shared vs private — the split that explains the config

Almost every memory setting you'll ever tune falls on one side of this line. shared_buffers is set once for the whole server (commonly ~25% of RAM). work_mem is multiplied by concurrency — every sort in every backend can grab its own. Confusing the two is the classic way to accidentally configure a server into swapping. Keep the map in your head and the settings sort themselves.

02 On disk

How a table is stored

Zoom into one table. On disk it is a heap: an unordered collection of pages (also called blocks), each exactly 8 KB. A big table is just many such pages, split across files of up to 1 GB each. "Unordered" is literal — the heap makes no promise about row order; it's a pile, and finding a particular row without help means reading the whole pile (a sequential scan). That's precisely the problem indexes exist to solve, in Phase 4.

Inside a page is a small layout worth knowing: a header, then an array of item pointers growing down from the top, and the actual tuples (row versions) growing up from the bottom, meeting in the middle as free space. Every tuple has a physical address, its ctid — a pair (page number, item number). An index doesn't store rows; it stores keys pointing at ctids.

sql

SHOW block_size;            -- 8192: the page size, compiled in

-- ctid is the physical location: (page, item)
SELECT ctid, id, balance FROM accounts WHERE id = 1;
--  ctid  | id | balance
-- (0,1)  |  1 |     100

Two more facts round out the storage picture. First, TOAST: a single tuple must fit in a page, so any value too big (roughly > 2 KB — a long text, a jsonb blob) is compressed and, if still large, pushed out of line into a companion TOAST table, leaving a small pointer behind. It's automatic; you mostly notice it as "why is my wide row cheap to scan when I don't select the big column."

Second — and this is the one to file away — an UPDATE does not overwrite a row in place. Postgres writes a new tuple version elsewhere and marks the old one as expired (watch the ctid change after an update). The old version lingers until vacuum reclaims it. That sounds wasteful, but it's the mechanism behind MVCC — how readers never block writers and each transaction sees a consistent snapshot. We only foreshadow it here; Phase 5 makes it the main event.

Why UPDATE writing a new version matters

Keep this pinned: in Postgres, an update is really an insert-plus-expire. It explains three things you'll meet later — why heavily-updated tables accumulate bloat and need vacuum, why an update can be as expensive as an insert, and how the same row can have several live versions so different transactions each see the right one. The physical model here is the seed of the whole concurrency story.

03 Reading

The read path & the buffer cache ▸

The executor never touches the disk directly. When it needs the page holding a row, it asks the buffer manager for that page, and the buffer manager either has it cached in shared_buffers or fetches it. The difference between those two outcomes — a hit versus a miss — is the single biggest lever on how fast a read feels. Trace one page request:

This is why the same query can feel instant or sluggish for reasons that have nothing to do with the SQL. On a warm cache the pages are already in shared_buffers and everything is hits; on a cold cache the first run pays miss after miss. It's also why shared_buffers sizing matters, and why a page can be dirty — modified in the cache but not yet written back. When the pool fills, the buffer manager evicts a page to make room; if the victim is dirty, its changes must be written out first (which is exactly the write path in the next section). You can see hits and misses per query with BUFFERS:

sql

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM accounts WHERE id = 1;
--  Buffers: shared hit=3            <- all cached (fast)
--  Buffers: shared read=3          <- had to hit disk (a miss)
Two caches, stacked

There isn't one cache — there are two. shared_buffers is Postgres's own; beneath it sits the operating system's page cache. A miss in shared_buffers often still finds the page in the OS cache, so a "disk read" is frequently a memory read in disguise. This layering is why cold-vs-warm timings differ so wildly, and why PG 18's new asynchronous I/O (more in Phase 7's neighborhood) speeds up exactly the miss-heavy paths like large sequential and bitmap scans.

04 Writing

The write path & the WAL ▸

Reads were half the story; writes are where durability is earned. Here's the puzzle Postgres has to solve: a COMMIT must survive a crash immediately, yet writing the actual data page to its scattered location on disk on every commit would be brutally slow (random I/O). The resolution is the Write-Ahead Log (WAL), and its rule is in the name: log the intent before you touch the data. Step through an UPDATE:

The keystone is step 4. At COMMIT, the only thing that must reach disk is the WAL — a compact, sequential append. The data page it describes can stay dirty in RAM for a while longer; if the server crashes one millisecond after commit, recovery replays the WAL and reconstructs the change. So durability comes from the log, not from the data page being written. And because WAL writes are sequential — appending to the end of a file — they're dramatically cheaper than the random writes you'd pay to update scattered data pages on every commit. One fsync to a log, instead of many seeks.

The dirty pages are reconciled later. The checkpointer periodically writes all dirty pages out to their data files and records a checkpoint — a known-good point past which the older WAL is no longer needed for crash recovery. The background writer trickles some dirty pages out between checkpoints to keep clean buffers available for eviction. This is the same durability guarantee (the "D" in ACID from Lesson 00) — now you can see the machinery that delivers it, and it's the foundation replication is built on: ship that WAL stream to another server and it can replay your every change (Phase 8).

WAL-first is why crashes are safe and commits are fast

The write-ahead rule pulls double duty. Safety: the intent is always on disk before the data page, so any crash is recoverable by replay. Speed: a commit pays one sequential log flush, not a storm of random page writes. The tunables you'll meet in Phase 7 — synchronous_commit, wal_level, checkpoint pacing — are all dials on this mechanism. Lesson 03 goes deeper on exactly what durability promises and what you can trade away for throughput.

05 The through-line

The moving parts you’ll meet again

Let's run the whole machine once, end to end, and pin each part to the phase where it becomes the subject. A client connects; the postmaster forks a backend that will serve it for the session. You send SQL; the backend parses it, the planner chooses a plan, and the executor runs it. To read, the executor asks the buffer manager for pages — hits from shared_buffers, misses from disk (under which the OS cache waits). To write, it dirties a page and logs a WAL record; at COMMIT the WAL is fsync'd for durability, and the checkpointer writes the dirty page back later. Meanwhile autovacuum cleans up the old row versions that UPDATEs and DELETEs leave behind. That paragraph is the course.

Now the map from parts to phases — this is the payoff of learning the machine before the features:

  • The planner → Phase 4. Because you state what, it chooses how; reading and steering its decisions with EXPLAIN is the heart of performance work. The heap and ctids you saw here are exactly what indexes point into.
  • Tuple versions & vacuum → Phase 5. The "an UPDATE writes a new version" fact from §02 is MVCC. Isolation levels, snapshots, and bloat all grow from that one seed.
  • WAL & durability → Lesson 03 & Phase 7. The write path here becomes a full treatment of what "committed" guarantees and which durability knobs trade safety for speed.
  • Shipping the WAL → Phase 8. Replication is just streaming the WAL to a second server and replaying it. The log you met as a durability trick is also the backbone of high availability.
  • Heavyweight connections → Phase 7. Process-per-connection is why pooling exists; now you know precisely what a backend costs.

One modern note to carry forward: PostgreSQL 18 (GA September 2025) introduced an asynchronous I/O subsystem that lets a backend issue many read requests before the data comes back, rather than blocking on each one. On the read path you just traced, that turns a long line of serial misses into overlapping fetches — up to roughly 3× faster on large sequential and bitmap-heap scans. It's a change to the exact box in FIG. 2 where a miss goes to disk. You don't need the details yet; you need to recognize where in the machine it plugs in, which you now can.

Where this shows up next

Every later lesson is a zoom-in on one region of this map. When Phase 4 says "the index scan avoided reading the heap," you'll picture the buffer manager and pages. When Phase 5 says "the reader saw an older snapshot," you'll picture tuple versions. When Phase 8 says "the replica is 200ms behind," you'll picture the WAL stream. Hold the whole machine in your head — supervisor, backends, shared and private memory, the log, the disk — and the rest of the course stops being a list of features and becomes a tour of a system you already understand.

★ Review

Summary & self-test

The whole lesson compresses to one picture: Postgres is a supervisor that forks one process per connection; those processes share a page cache and a write-ahead log, keep private scratch memory, and lean on background workers to move dirty pages and old row versions to disk — reads come from the buffer cache, and every write is logged before the data page it changes ever lands. Everything the course does later is a zoom-in on one of those parts.
