Database Interview Drills

The last lesson is a workshop, not a topic. An interview rarely asks you to recite a definition — it hands you a scenario ("this query got slow," "two writes collided," "how would you scale it?") and listens to how you think. This lesson rehearses that: three drills that turn whole phases of the course into a single line of reasoning, a bank of crisp model answers, and the one meta-skill that ties it all together — reasoning out loud.

Original study notes. A capstone for the whole course, aimed at the interview room and the on-call channel. Examples target PostgreSQL (PG 17/18), but the reasoning is universal. 00 The meta-skill

How to reason out loud

Here is the thing almost no one tells you before a database interview: the content is a small part of the score. By this point in the course you know the content — the relational model, indexes, ACID, MVCC, replication, sharding. What a strong interviewer is actually measuring is your process: whether you clarify before you answer, whether you name the trade-off instead of declaring a winner, and whether you'd measure before you tune. Those habits are portable to every scenario, which is exactly why they're tested.

Four moves turn a wandering answer into a confident one. Run them, in order, on almost any prompt:

  • State your assumptions. "I'll assume this is an OLTP app, a few million rows, reads-heavy, single Postgres primary — stop me if that's off." One sentence and you've shown you know the answer depends on scale and shape, and you've de-risked the rest of your reasoning.
  • Name the trade-off, don't pick a winner. Almost every database question is a dial, not a switch. "An index makes this read fast but slows every write and costs disk." "Higher isolation is more correct but aborts more." The moment you frame it as a cost, you sound senior; the moment you say "always do X," you sound junior.
  • Correct first, then fast. Reach for integrity before performance. A sound schema with the right constraints prevents whole classes of bug that no tuning can fix — bad data is far more expensive than a slow query. Say it explicitly; interviewers listen for it.
  • Measure, don't guess. When something is slow, the honest answer is "I'd run EXPLAIN (ANALYZE, BUFFERS) and read the plan before changing anything." Guessing at database performance is how people spend a day adding an index the planner then ignores.

The rest of this lesson is these four moves applied. Section 1 is measure made concrete (the slow-query reasoning tree). Section 2 is name the trade-off under concurrency. Section 3 is a bank of answers you can already give in one paragraph each. Section 4 is correct-first-then-fast stretched across the whole scaling story. None of it is new material — it's the course, re-compiled into the shape an interview asks for.

The one-line posture

Treat every database question the way you'd treat a data-structure question: learn what problem it solves, what it costs, and when not to use it. An index, an isolation level, a read replica, a shard — each is a tool with a price. Answer with the price attached and you will almost never be wrong, because you'll have named the condition under which your answer flips.

01 Drill one · performance

Why is this query slow? ▸

This is the single most common database interview question, and the single most common on-call page. The wrong answer is a guess ("add an index?"). The right answer is a reasoning tree you walk out loud, and it compresses the whole of Phase 4 into one flow: read the plan → find the hot node → ask why it's hot → apply the one fix → confirm the plan changed. Step through the tree:

Make it concrete. A lookup on an un-indexed column of a million-row table produces a plan whose hottest line is a full scan:

EXPLAIN (ANALYZE, BUFFERS) — illustrative

Seq Scan on orders  (cost=0.00..18334.00 rows=1 width=68) (actual time=0.02..238.41 rows=1 loops=1)
  Filter: (email = 'ana@x.io')
  Rows Removed by Filter: 999999
  Buffers: shared read=8334
Planning Time: 0.09 ms
Execution Time: 238.55 ms

The tell is right there: Seq Scan reading 8,334 pages and Rows Removed by Filter: 999999 to return a single row — the planner had no index, so it read the whole table. Because the filter is selective (one row out of a million), the fix is a B-tree index on email. Add it and re-run:

sql

CREATE INDEX orders_email_idx ON orders (email);
ANALYZE orders;  -- refresh stats so the planner trusts the new option

EXPLAIN (ANALYZE) — illustrative, after the index

Index Scan using orders_email_idx on orders  (cost=0.42..8.44 rows=1 width=68) (actual time=0.031..0.033 rows=1 loops=1)
  Index Cond: (email = 'ana@x.io')
Execution Time: 0.061 ms

Same query, plan flipped from Seq Scan to Index Scan, 238 ms → 0.06 ms. But — and this is the senior move — an index isn't always the answer. The tree has three other branches. If the plan's estimate is wildly off the actual rows (say it guessed 5 and got 500,000), the problem is stale statistics, and the fix is ANALYZE, not an index. If the filter is WHERE lower(email) = ... or WHERE created_at::date = ..., a plain index can't be used because the predicate isn't sargable — you need an expression index or a rewrite. And if the "slow query" is actually the same query run 500 times in a loop, no index helps: that's the N+1 pattern, and the fix is to fetch in one set-based query.

Say this in the room

"I'd start with EXPLAIN (ANALYZE, BUFFERS) and find the node burning the most actual time. If it's a sequential scan on a big table with a selective filter, I'd add an index and confirm the plan flips to an index scan. But I'd first check whether the row estimates are way off — that's stale stats, not a missing index — and whether the predicate is even sargable. And I'd rule out N+1 before touching indexes at all." That answer wins because it measures first and names the branches instead of guessing one.

02 Drill two · concurrency

The concurrency drill ▸

The second classic: "two requests hit the same row at the same time — what goes wrong, and how do you fix it?" This is Phase 5 in one drill. The trap answer is "use a transaction" — but a transaction alone, at Postgres's default Read Committed, does not stop the bug about to happen. Watch two orders each buy the last units of a product with a naive read-modify-write:

The name matters, because the name selects the fix. This is a lost update: two transactions read the same value, each computes from its own stale copy, and the second write clobbers the first — one sale silently vanished. Read Committed permits it because each statement sees a fresh snapshot but nothing stops the interleave. You have three real fixes, and naming their trade-offs is the whole answer:

sql

-- Fix A: pessimistic lock. FOR UPDATE locks the row; B blocks until A commits,
-- then re-reads the fresh 9. Simple, but holds a lock for the transaction's life.
BEGIN;
SELECT stock FROM products WHERE id = 42 FOR UPDATE;
UPDATE products SET stock = stock - 1 WHERE id = 42;
COMMIT;

-- Fix B: make the write atomic — no read-modify-write in app code at all.
-- The database computes from the current value under its own row lock.
UPDATE products SET stock = stock - 1 WHERE id = 42 AND stock > 0;

-- Fix C: optimistic — run at SERIALIZABLE and retry on 40001 serialization_failure.
-- Best when conflicts are rare; you must code the retry loop.

Fix B is usually the best answer for a pure counter — it's one statement, no explicit lock management, and it can't lose the update because the read and the write happen together under Postgres's row-level write lock. FOR UPDATE (Fix A) is right when you must read, decide in application code, then write. And SERIALIZABLE (Fix C) is the general tool for the subtler cousin — write skew, where two transactions each read a set, each check a condition that's still true, and both write, breaking an invariant no single row could catch (two doctors both cancelling their on-call shift because each sees the other still on). Row locks don't catch write skew because there's no single contended row; Serializable does, at the cost of aborts you must retry.

Lost update vs write skew — the two you must distinguish

Lost update = same row, concurrent read-modify-write, second clobbers first → fix with an atomic UPDATE or FOR UPDATE. Write skew = different rows, a cross-row invariant, each txn's read stays valid → fix with SERIALIZABLE + retry (or a materialized lock). Naming which one you're facing is 80% of the answer; the interviewer is checking whether you know that "just use a transaction" isn't a fix on its own.

03 The bank

The question bank

These recur in nearly every database interview. The goal is not a memorized script but a tight paragraph for each — one that leads with the trade-off. Read each answer as a template you can compress or expand to fit.

When would you add an index, and what does it cost?

A B-tree index is a sorted side-structure that turns a table scan into a targeted lookup; add one when a query filters, joins, or sorts on a column with reasonable selectivity and the table is large enough that a scan hurts. The cost: every INSERT/UPDATE/DELETE must maintain the index, and it consumes disk and cache. Column order in a composite index matters (leftmost-prefix rule), and adding the selected columns via INCLUDE can enable an index-only scan. Don't index tiny tables or very low-cardinality columns (a boolean rarely helps), and always confirm with EXPLAIN that the planner actually chose it — an index the planner ignores is pure write-tax.

Normalization vs denormalization — which and when?

Normalize first (aim for 3NF): store each fact once so updates can't create contradictions. It's the correct default for OLTP and keeps writes cheap and integrity easy. Denormalize — duplicate a column, precompute an aggregate, keep a materialized view — only when a measured read pattern stays too slow after indexing. You're trading write complexity and the risk of the copies drifting out of sync for read speed. The framing that lands: "normalize for correctness, denormalize for a specific, proven read path — and own the sync cost you just took on."

Explain ACID and the isolation levels.

ACID = Atomicity (all-or-nothing), Consistency (constraints always hold), Isolation (concurrent transactions don't corrupt each other), Durability (a commit survives a crash). Isolation is a dial: Read Committed (Postgres default) blocks dirty reads but allows non-repeatable reads, phantoms, and lost updates; Repeatable Read (snapshot isolation in Postgres) blocks those but still allows write skew; Serializable (SSI) behaves as if transactions ran one at a time but can abort with a 40001 serialization failure, so the app must retry. Higher isolation buys more correctness and pays in more aborts and contention — a real cost, not a free switch.

How does MVCC work, and why does VACUUM exist?

Multi-Version Concurrency Control lets readers see a consistent snapshot without blocking writers: an UPDATE writes a new row version and marks the old one dead, and each transaction sees whichever versions were valid for its snapshot. The consequence is dead tuples accumulating as bloat; VACUUM (autovacuum, automatically) reclaims that space, updates the visibility map to enable index-only scans, and freezes old transaction IDs to prevent wraparound. The classic failure: a long-running or idle-in-transaction session holds back the xmin horizon so vacuum can't clean anything newer — bloat and slowdowns follow.

What is replica lag, and how do you handle read-after-write?

Asynchronous streaming replication is eventually consistent: a standby replays the primary's WAL a little behind, so a read sent to a replica immediately after a write can return stale data — the user updates their profile and sees the old value. Three handles: route reads-that-follow-a-write to the primary; or capture the write's LSN and wait until the replica's replay LSN catches up before reading; or accept a bounded staleness where it's harmless. Synchronous replication (synchronous_commit = remote_apply) removes the lag entirely at the cost of higher commit latency — the PACELC trade in one setting.

How does failover work, and what is split-brain?

On primary failure a cluster manager (Patroni) backed by a consensus store (etcd/Consul, Raft) promotes a standby that wins the leader key; a quorum of N/2+1 across an odd node count guarantees only one winner. Split-brain is the disaster it prevents: two nodes both accepting writes after a network partition, diverging into data you can't reconcile. Beyond quorum you need fencing/STONITH — a watchdog that kills or isolates the old primary before the new one takes over. Clients reroute through a proxy or VIP. The invariant to state plainly: at most one primary, ever.

How do you keep a cache or event stream in sync with the database?

You cannot atomically write to Postgres and to a queue or cache — a crash between the two loses or duplicates the event (the dual-write problem). The fix is the transactional outbox: write the domain row and an outbox row in the same transaction, then a relay (polling, or CDC tailing the WAL) publishes and marks them sent — at-least-once delivery. Since exactly-once delivery is a myth, make consumers idempotent: dedup on an idempotency key recorded in the same transaction as the effect (an inbox table + ON CONFLICT DO NOTHING), and prefer naturally idempotent effects (upsert/set, not blind increment). Caches are derived copies — design for eventual consistency, invalidation races, and TTL as a safety net.

When and how would you shard?

Shard only when a single primary genuinely can't hold the data volume or write throughput — and shard late, after scaling up, adding read replicas, and caching. You split rows across nodes by a shard key (hash or range). A query with the key hits one shard and is fast; a query without it, or a cross-shard join, fans out to every shard and merges — scatter-gather, slow and expensive. A good key has high cardinality, even distribution, and matches the access pattern (tenant_id for multi-tenant), and you colocate related rows so joins stay local. Citus turns Postgres into a distributed cluster if you must; multi-region active-active adds conflict resolution on top.

"Design a schema for X."

Use a method, out loud, so the interviewer follows your reasoning: entities → relationships → keys → constraints → indexes-for-queries. List the nouns as tables; classify each relationship (1:1, 1:N, or M:N → a junction table); pick keys (surrogate bigint/uuid vs a natural key); add constraints — NOT NULL, UNIQUE, FOREIGN KEY, CHECK — so that bad states are unrepresentable; only then add indexes for the queries you'll actually run. Close with correct-first-then-fast: "I'd model for integrity, ask about the read/write mix and scale, and denormalize only where a measured need shows up." Narrate your assumptions as you go — that is the answer.

Notice the shape of every answer

Each paragraph does the same three things: states what the tool is, names the cost, and gives the condition under which the choice flips. That shape — tool, cost, when-not-to — is what makes an answer sound like judgment rather than recall. If you internalize only one thing from this bank, internalize the shape, not the sentences.

04 Drill three · scaling

Scaling with a database ▸

The system-design finale: "your app is growing — how do you scale the database?" The senior answer is a ladder you climb one rung at a time, cheapest and least invasive first, and — crucially — you say why each rung and what it costs. This ladder is the arc of the whole course. Climb it:

The discipline is in not skipping rungs. A weak answer jumps straight to "shard it" or "add a NoSQL database"; a strong one exhausts the cheap wins first, because each higher rung buys capacity by giving up a guarantee. A single, well-indexed Postgres primary on modern hardware serves an enormous amount of traffic — most systems never need to leave rung 2. Read replicas (rung 3) scale reads but introduce replica lag, so you must handle read-after-write. A cache or search index (rung 4) offloads hot paths but is a derived copy you now have to keep in sync — cache-aside + TTL, or CDC/outbox, never a naive dual-write. Sharding (rung 5) is the only rung that scales writes past one node, and it's last because it costs you cheap cross-shard joins, cheap transactions, and operational simplicity all at once.

Say this in the room

"I'd start with one primary and a correct schema, then profile and add indexes — that's the cheapest lever and usually enough. If reads outgrow one node I'd add read replicas and handle the lag for read-after-write. For hot keys or search I'd add a cache or a search index as derived copies, kept in sync via CDC to avoid dual-writes. I'd only shard when writes genuinely exceed a single primary — it's last because it gives up cross-shard joins and simple transactions." That answer scales your credibility, because it treats capacity as something you buy with trade-offs, not a magic word.

05 Reason about it

Putting it together — and the course close

Let's run the meta-skill on a real prompt, the way you would live: "Users say the app got slow right after a marketing campaign drove a traffic spike. Walk me through how you'd investigate." Notice how the four moves carry the whole answer without a single memorized fact.

Assumptions first. "I'll assume this is our OLTP Postgres primary, the spike is mostly reads with some writes, and 'slow' means p95 latency climbed — tell me if it's errors instead." One sentence and you've scoped the problem and shown you know slowness has shapes.

Measure, don't guess. "I'd look at pg_stat_statements for the queries whose total time jumped, and pg_stat_activity for anything stuck — especially idle in transaction, which pins vacuum and locks. If one query dominates, I'd EXPLAIN (ANALYZE, BUFFERS) it." That's Drill 1, and it's the difference between diagnosing and flailing.

Name the trade-off at each branch. "If it's a sequential scan the traffic just made expensive, an index fixes it — at some write cost. If lock waits spiked, it's a concurrency problem: I'd look for a hot row and consider an atomic update or a lock, which is Drill 2. If the box is simply saturated on reads, the fix is a read replica — and then I owe you a read-after-write story for the lag." Each branch names its price.

Correct first, then fast. "Before any of that I'd confirm we're not returning wrong data under load — a slow-but-correct system is a tuning problem; a fast-but-wrong one is an outage. Once correctness is safe, I climb the cheapest rung of the scaling ladder that the evidence points to." And there is the whole course, delivered as a way of thinking rather than a list of facts.

Where this shows up next

Everywhere — that's the point of a capstone. The reasoning tree, the concurrency drill, and the scaling ladder aren't three tricks; they're the same four moves (assume, measure, name the trade-off, correct-then-fast) applied to performance, concurrency, and scale. The next place they show up is your next real system and your next real interview. You have the map now; the rest is reps.

The course close. You began at Lesson 00 with a single idea — a database is a correctness machine with a query language — and you've now walked every promise it makes: structure through the relational model and schema design; retrieval through SQL, joins, and the planner; safety through transactions, isolation, and MVCC; durability through the WAL, replication, and backup; and scale through indexing, caching, and sharding. What ties them together isn't syntax. It's a posture: learn what each tool solves, what it costs, and when not to use it — then measure before you change anything, and keep it correct before you make it fast. Carry that, and you'll reason well about databases you've never seen, in rooms you haven't walked into yet. That was always the goal.

Cover the notes and answer aloud — each spans a phase of the course:
(1) A query that returned instantly last week now takes 4 seconds. Name the four branches you'd check before adding an index, and how EXPLAIN (ANALYZE) tells you which one it is. (Phase 4)
