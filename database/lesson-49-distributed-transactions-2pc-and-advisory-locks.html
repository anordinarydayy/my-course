Distributed Transactions, 2PC & Advisory Locks

Sometimes one local transaction isn't enough — you truly need a change to land atomically across two databases or two systems. PostgreSQL offers a real distributed-commit primitive, PREPARE TRANSACTION (two-phase commit), and it is almost always a trap: it turns the coordinator into a single point of failure and can leave participants blocked, holding locks, forever. This lesson explains 2PC honestly, shows the failure mode, and hands you the two pragmatic tools that win in practice — sagas and advisory locks.

Original study notes. Written from scratch for engineers preparing for systems-design interviews and real on-call. Examples target PostgreSQL (PG 17/18), but the trade-offs — atomicity across systems, blocking commit protocols, compensation-based consistency — are universal. 00 The temptation

When you genuinely need atomicity across systems

Almost everything you write should fit inside one local transaction in one database — that's the happy path, and PostgreSQL's ACID guarantees make it airtight. But real systems eventually reach for something a single transaction can't span. You want to debit an account in database A and credit an account in database B, both or neither. You want to write a row and publish an event to a queue as one atomic act. You want to update Postgres and invalidate a Redis key together. The instinct is: "I need a transaction that covers both."

That instinct runs straight into the dual-write problem we met earlier (Lessons 46–47): you cannot atomically commit to two independent systems, because there is always a window — after you commit the first and before you commit the second — where a crash leaves them inconsistent. There is no free lunch here; the question is only which compromise you choose.

Two-phase commit

  • A coordinator forces all participants to agree.
  • Real atomicity — on paper.
  • Blocking; coordinator is a SPOF.

Sagas

  • A chain of local transactions.
  • Failures trigger compensating actions.
  • Eventual consistency, no distributed lock.

Advisory locks

  • An app-level, cross-session mutex.
  • Leader election, single-runner jobs.
  • Coordination, not atomic commit.

The honest summary up front: 2PC exists and is usually the wrong answer; sagas and advisory locks are the tools you actually reach for. The rest of this lesson earns that claim — first by showing exactly how 2PC works, then exactly how it fails, then what to use instead.

The one-sentence frame

A distributed transaction trades a small window of inconsistency for a blocking dependency between machines. Whenever you can absorb the inconsistency with idempotency and compensation instead, you should — because a blocked, in-doubt transaction is far harder to recover from than a duplicate event.

01 The protocol

Two-phase commit, step by step ▸

Two-phase commit (2PC) is the classic protocol for making several participants commit atomically. A coordinator (transaction manager) drives it in exactly two phases, as the name says. In PostgreSQL, phase one is PREPARE TRANSACTION and phase two is COMMIT PREPARED (or ROLLBACK PREPARED). The prepared transaction is written durably to disk and survives a server restart — that durability is the whole point, and also the whole danger.

sql

-- run against EACH participant database, driven by the coordinator
-- phase 1: do the work, then promise you can commit
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
PREPARE TRANSACTION 'txn-42';   -- votes YES; locks are STILL held

-- phase 2: only after ALL participants prepared successfully
COMMIT PREPARED 'txn-42';        -- or ROLLBACK PREPARED 'txn-42'

The rule is simple and strict: the coordinator sends PREPARE to everyone; if every participant votes YES (i.e. successfully prepared), the coordinator sends COMMIT PREPARED to everyone; if any participant cannot prepare, the coordinator sends ROLLBACK PREPARED to all. Atomicity across systems, achieved. Step through the well-behaved run:

Notice the crucial detail hiding in step 2: once a participant has prepared, it has made an irrevocable promise. It has written its changes durably and it keeps its locks held until the coordinator tells it commit or rollback. A prepared transaction is a loaded gun with the safety off — perfectly fine as long as the coordinator returns promptly with a decision. The next section is what happens when it doesn't.

PREPARE is a promise, not a commit

After PREPARE TRANSACTION the work is durable but not yet visible, and the participant has surrendered its autonomy: it can no longer decide to abort on its own. It must wait for the coordinator. That surrender of local control is what makes the whole protocol correct — and what makes it dangerous.

02 The failure mode

Why 2PC is a trap ▸

The happy path is seductive. The trouble is the window between the two phases. A participant has prepared — it is holding locks and waiting — and then the coordinator crashes before it can send the decision. The participant is now stuck in a state Postgres calls an in-doubt (orphaned) prepared transaction: it promised to obey, so it may not unilaterally commit or roll back, but there is no coordinator left to tell it what to do. Watch it happen:

The consequences compound. A prepared transaction holds its row locks and pins resources the way any open transaction does: it holds back VACUUM, so dead tuples can't be cleaned up and the table (and the transaction-id horizon) bloats. Its locks block any other transaction that needs the same rows. And it will sit there — through restarts, because it's durable — until a human notices and resolves it. You find these orphans in a catalog view:

sql

-- orphaned prepared transactions: the outage you didn't know you had
SELECT gid, prepared, owner, database
FROM   pg_prepared_xacts
ORDER BY prepared;                 -- old ones = trouble

-- the only cure is a manual decision:
ROLLBACK PREPARED 'txn-42';        -- or COMMIT PREPARED, if you can prove that's correct

And there is a guard rail that bites the unwary: prepared transactions are disabled by default. The parameter max_prepared_transactions is 0 out of the box, so PREPARE TRANSACTION errors until an administrator raises it — a deliberate signal from the Postgres developers that you should not turn this on without knowing exactly what you're doing. If you do enable it, you now own the job of monitoring pg_prepared_xacts forever.

The three-word summary of 2PC's flaw

Blocking on failure. A protocol is only as available as its least-available required participant plus its coordinator. 2PC multiplies single points of failure and, on a coordinator crash, converts a transient outage into pinned locks and a blocked VACUUM that a human must clear. It is technically atomic and operationally hazardous — a last resort, only with a real, battle-tested transaction manager (e.g. an XA-aware one) behind it.

03 The alternatives

Sagas & advisory locks ▸

If 2PC is the wrong answer to "atomicity across systems," what's the right one? Two tools, for two different jobs. For a multi-step business flow that spans services, use a saga. For coordination — making sure only one process does a thing — use an advisory lock.

Sagas: local transactions plus compensation

A saga replaces one big distributed transaction with a sequence of local transactions, each of which commits on its own. If a later step fails, you don't roll back the earlier ones — you can't, they've already committed — instead you run compensating actions that semantically undo them, in reverse order. Charged the card but couldn't reserve stock? Issue a refund. It's eventual consistency, achieved with no distributed lock and no coordinator holding everyone hostage:

Two design rules make sagas safe. First, every step and every compensation should be idempotent (Lesson 47): a retried refund must not refund twice, so key it and use ON CONFLICT DO NOTHING or an inbox table. Second, some actions can't be compensated (you can't un-send an email) — put those last, so everything reversible has already succeeded before you cross the point of no return.

Advisory locks: a distributed mutex in the database

The other tool solves a different problem: not "commit atomically" but "make sure only one worker does this." A PostgreSQL advisory lock is an application-defined, cross-session lock keyed by an integer you choose. Postgres doesn't attach any meaning to it — it just guarantees that at most one session holds a given key at a time. That's exactly a distributed mutex, and it's the simplest way to do leader election or a single-runner cron:

sql

-- SESSION-level: held until unlock or the session ends. Great for leader election.
SELECT pg_try_advisory_lock(42);   -- true = I'm the leader; false = someone else is
-- ... do the singleton work ...
SELECT pg_advisory_unlock(42);

-- TRANSACTION-level: auto-released at COMMIT/ROLLBACK. No leak if you crash mid-work.
BEGIN;
SELECT pg_advisory_xact_lock(42);  -- blocks until acquired; freed automatically
-- ... exactly-one-runner section ...
COMMIT;                            -- lock released here, guaranteed

Prefer pg_try_advisory_lock (non-blocking — returns immediately) so a would-be second leader steps aside instead of piling up. And prefer the transaction-scoped variant when you can: a session-level lock is held until you explicitly unlock or the session ends, so an app that forgets to unlock — or that returns the connection to a pool still holding it — leaks it, whereas an xact lock is always released by COMMIT or ROLLBACK. (A true process death still frees either kind, since Postgres tears the backend down.) Advisory locks are advisory — they enforce nothing about the data itself, only cooperation between sessions that agree to check the same key.

Two tools, two jobs — don't confuse them

A saga answers "how do I keep several systems consistent across a multi-step flow?" — the answer is compensation, not locking. An advisory lock answers "how do I make sure only one of my instances runs this?" — the answer is a shared mutex, not a transaction across systems. Neither is a distributed commit; both avoid the blocking trap that 2PC walks into.

04 Fit

When each one actually fits

Now the practical calibration — where each tool earns its place, and where it doesn't.

Two-phase commit — rarely, and only with a manager

Reach for 2PC only when you have a genuine, short, hard requirement for cross-system atomicity and a real, dedicated transaction manager (an XA coordinator, or a framework that owns recovery) sitting behind it — never a hand-rolled coordinator in your app. Keep the prepared window as short as possible; monitor pg_prepared_xacts and alert on any prepared transaction older than a few seconds. Classic legitimate cases are narrow: a bank moving money between two ledger databases that both support XA, under a proven middleware. If you're describing your own service as "the coordinator," stop — that's the smell of the trap.

Advisory locks — the everyday coordination workhorse

These fit a surprising number of real needs, and they're cheap:

  • Leader election — N app instances boot, each tries pg_try_advisory_lock(id); the one that wins runs the singleton loop, the rest idle and retry.
  • Single-runner cron / scheduled job — wrap the job body in pg_try_advisory_xact_lock so a duplicate trigger (two pods firing at once) becomes a harmless no-op.
  • A named mutex around a non-transactional resource — serialize a risky migration step, or gate access to an external API that must be called by one worker at a time.
  • Throttling a hot code path — a keyed lock so only one session recomputes an expensive cached artifact while others skip.

Sagas — multi-step business flows across services

Whenever a user action fans out into several services — order → payment → inventory → shipping — model it as a saga with a compensation for each reversible step. Combine it with the transactional outbox (Lesson 46) so each local step publishes its next event atomically, and with idempotent consumers (Lesson 47) so retries are safe. That trio — outbox + idempotency + saga — is how production systems get "distributed transaction" behavior without a distributed transaction.

The general rule

Prefer one local transaction — then outbox + idempotency — then a saga — and only then, as a genuine last resort, 2PC. Reach for advisory locks whenever the problem is really "only one runner," not "atomic across systems." Nine times out of ten the elegant distributed transaction you're imagining is better served by making a downstream effect idempotent and letting it retry.

05 Reason about it

The decision hierarchy — and where this shows up next

Let's walk one concrete scenario down the ladder, because the ladder is the lesson. Suppose a "place order" action must: create the order, charge the card (an external payment service), and reserve inventory (a separate service). You want all-or-nothing. How do you build it?

  • Rung 1 — can it be one local transaction? If all three effects lived in one Postgres database, you'd wrap them in BEGIN … COMMIT and be done. They don't — the payment and inventory are other systems — so a single transaction can't span them. Move down only because you're forced to.
  • Rung 2 — outbox + idempotency for the cross-system edges. Create the order and, in the same transaction, write outbox rows ("charge requested", "reserve requested"). A relay publishes them; the payment and inventory consumers are idempotent, so redelivery is safe. Now each hop is atomic-with-the-DB and at-least-once.
  • Rung 3 — a saga for the multi-step flow. String those hops into a saga: order → charge → reserve. If reserve fails, run compensations — refund the charge, cancel the order — in reverse. Consistency without a distributed lock. This is the answer for almost every real "distributed transaction" you'll ever design.
  • Rung 4 — 2PC, only if you truly must. If some regulatory or ledger requirement genuinely forbids any intermediate visible state and you have a real XA manager, then and only then reach for PREPARE TRANSACTION — eyes open to the coordinator SPOF, the blocking, and the pg_prepared_xacts monitoring you now own.
  • Sideways — advisory locks for coordination. Orthogonal to all of the above: if the real problem is "only one worker should process this saga at a time," or "elect one leader to run the relay," reach for pg_try_advisory_lock. That's coordination, not commit.

The through-line of this whole final phase is that distributed systems don't give you atomicity for free — they give you the tools to simulate it well enough. Idempotency turns "at-least-once" into "effectively once." Outboxes turn "dual write" into "one atomic write plus a relay." Sagas turn "roll back everything" into "compensate what committed." Advisory locks turn "who's in charge?" into a single database round-trip. Master those four, and the shiny distributed transaction almost never earns its keep.

Where this shows up next

This closes the loop opened by the dual-write problem and the transactional outbox (Lesson 46) and idempotent consumers (Lesson 47). In a systems-design interview, "how do you keep these two datastores consistent?" is a direct invitation to walk this exact ladder aloud — naming 2PC, explaining why you're not using it, and reaching for outbox + idempotency + saga instead. That reasoning, not the syntax, is what's being graded.

★ Review

Summary & self-test

The whole lesson compresses to one idea: you cannot get free atomicity across independent systems, so prefer to simulate it — one local transaction if you can, then outbox + idempotency, then a saga with compensation — and treat two-phase commit as a blocking, coordinator-dependent last resort, while advisory locks handle plain coordination.
