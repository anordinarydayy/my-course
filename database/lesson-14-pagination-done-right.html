Pagination Done Right

Everyone reaches for LIMIT ... OFFSET ... the first time they page a list, and it works beautifully on page 1. The trap is what happens at depth: OFFSET must produce and throw away every row you skip, so the same query that returns in 8 milliseconds on page 1 can take 8 seconds on page 10,000. Keyset (seek) pagination replaces "skip m rows" with "seek past the last row I saw," and stays constant-time at any depth. This lesson makes the cost visible, then drills the pattern you should reach for by default.

00 The setup

Two ways to page a big list

A list too large to send in one response gets delivered in pages. There are exactly two mental models for "give me the next chunk," and choosing the wrong one is one of the most common quiet performance bugs in web backends.

  • Page numbers — LIMIT / OFFSET. "Give me 20 rows, skipping the first 200,000." The client thinks in page indices; the server translates page k into OFFSET (k−1)×20. Trivial to write, and it supports jump to page N.
  • A cursor — keyset / seek. "Give me 20 rows that come after the last row I already have." The client sends back a small token — the sort key of the last row it saw — and the server seeks straight past it. A bit more code, no page numbers, but constant time at any depth.

Keep one concrete scenario in mind for the whole lesson: an infinite-scroll feed, newest posts first, 20 per page. A user has been thumbing the screen for a while and is now on page 5,000. With page numbers, the server is about to ask Postgres to skip 100,000 rows to hand back 20. With a cursor, it will hand over the same 20 rows for essentially the same cost as page 1. That gap — and why it exists — is the entire lesson.

The one-line summary, up front

OFFSET m is O(m): the database still has to generate the skipped rows in order before discarding them. Keyset is O(page size): it seeks to a boundary in an index and reads only what it returns. For anything that scrolls, prefer keyset; keep OFFSET for small page-number UIs where jumping to an arbitrary page matters more than depth.

01 The cost of skipping

Why OFFSET gets slower ▸

The critical thing to internalize is what OFFSET m LIMIT n actually does. It does not tell the storage engine "jump straight to row m." SQL has no notion of "the m-th row" until the rows are ordered and produced. So the executor must produce the first m + n rows in the requested order, discard the first m, and return the last n. Producing and throwing away those m rows is real, measurable work.

This is true even with a perfect index on the sort column. An index makes the rows come out pre-sorted, so Postgres skips the sort step — but it still has to walk the first m + n index entries (and, for a plain index scan, visit their heap rows) before LIMIT can take effect. The index turns "sort 10 million rows" into "walk m + n of them," which is a huge win — but m + n still grows with page depth.

Put numbers on it. On a 10-million-row feed table, indexed on (created_at DESC, id DESC), 20 rows per page:

  • Page 1 — OFFSET 0 — walk 20 entries — ~8 ms.
  • Page 1,000 — OFFSET 20,000 — walk 20,020 — ~900 ms.
  • Page 10,000 — OFFSET 200,000 — walk 200,020 — ~8 s.

Notice the returned page never changes size — it is always 20 rows. What grows is the discarded prefix. Step through it and watch the kept slice stay tiny while the thrown-away work runs away:

Convenience with a hidden linear tax

OFFSET feels free because it's one keyword and it can jump to any page number. But every deep jump pays an O(m) tax you never see in the SQL text. If your list scrolls rather than paginates by number, you are paying that tax on every fetch — and it compounds exactly where engagement is highest (deep in a long feed).

02 The seek pattern

Keyset (seek) pagination

Keyset pagination replaces "skip m rows" with a far cheaper instruction: "start after the last row I already have." Instead of a page number, the client hands back a cursor — the sort key of the last row on the previous page. The next query then asks for everything that sorts after that boundary:

sql

SELECT id, author_id, created_at, body
FROM   posts
WHERE  (created_at, id) < ($1, $2)   -- ($1,$2) = last row of the previous page
ORDER BY created_at DESC, id DESC
LIMIT  20;

Two pieces do the work. First, the row-value comparison (created_at, id) < ($1, $2). Postgres compares tuples lexicographically, exactly the way a dictionary orders words, so that single expression expands to:

sql

created_at < $1
OR (created_at = $1 AND id < $2)

Read that as "either the post is strictly older, or it's the same instant but a lower id." That is precisely "everything that comes after the boundary row in created_at DESC, id DESC order" — no more, no less. Write the expanded form by hand and it's easy to get the boundary condition subtly wrong (a stray <= duplicates a row; splitting it as created_at < $1 AND id < $2 is simply wrong — it drops legitimate rows). The tuple form is the one to memorize.

Second, the matching index. With CREATE INDEX ON posts (created_at DESC, id DESC), that WHERE/ORDER BY pair maps directly onto the index's own order. Postgres pushes the row comparison into the index as a starting condition, descends the B-tree straight to the boundary, and reads forward exactly LIMIT entries. Cost is O(page size) — independent of how deep you are. Page 1 and page 10,000 do the same amount of work.

The tiebreaker is mandatory, not decoration

The id in the sort key is not optional polish — it's what makes paging correct. created_at alone is not unique: many posts can share a millisecond. If you page on created_at only, a page boundary that lands in the middle of a group of ties will either skip rows (with <) or show them twice (with <=) as the user scrolls. Appending a unique column (the primary key) gives every row a total order, so the boundary is a single, unambiguous point. Rule: the last column of any keyset sort must be unique.

The price you pay for constant-time depth is that keyset has no page numbers. You can go to the next page (you hold its cursor) and, by keeping a stack of cursors, to the previous one — but you cannot say "jump to page 738," because you don't have page 737's last row to seek from. That's the right trade for feeds and infinite scroll, and the wrong trade for an admin table that shows "page 12 of 40." Match the tool to the UI.

03 Same index, two walks

OFFSET vs keyset on the index ▸

Here's the clarifying picture: both strategies walk the very same sorted index in the very same direction. The only difference is where they start and how much they touch. OFFSET always starts at the top of the index and discards its way down to your page. Keyset seeks straight to the boundary key and reads only the page. Watch the same request — "the three posts after 5007" — served both ways on one index:

The shapes tell the story. OFFSET's touched region starts at the top and its discarded part grows every page. Keyset's touched region is always just the page, wherever the boundary happens to be. At page 3 the difference is 9 vs 3; at page 10,000 it's 200,020 vs 20. Same index, same order, wildly different cost — because one counts from the top and the other seeks.

Why an index alone doesn't save OFFSET

People sometimes think "just add an index and OFFSET is fine." The index is already there in this picture — it's what lets Postgres avoid a sort and a full-table scan. But OFFSET's semantics force it to walk past the skipped entries regardless. The index removes the sort; only keyset removes the walk.

04 Worked problem

Worked: a feed endpoint ▸

Let's build the thing end to end — schema, the naive query, why it's slow, the correct query, the index, the plans, and how you'd say it out loud in an interview.

1 · The schema

sql

CREATE TABLE posts (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  author_id   bigint      NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  body        text        NOT NULL
);

-- the feed index: matches ORDER BY created_at DESC, id DESC exactly
CREATE INDEX posts_feed_idx ON posts (created_at DESC, id DESC);

Ten million rows. created_at is NOT NULL on purpose (a nullable sort column is a keyset trap we'll name later), and id is the unique tiebreaker.

2 · The task

Serve an infinite-scroll feed, newest first, 20 posts per page, that stays fast at any scroll depth.

3 · First attempt (OFFSET) — and why it's slow

The obvious version translates "page 10,000" into an offset:

sql

SELECT id, author_id, created_at, body
FROM   posts
ORDER BY created_at DESC, id DESC
OFFSET 200000 LIMIT 20;   -- page 10,000

It returns the right rows, but it makes Postgres produce 200,020 rows in sorted order and discard the first 200,000. The plan shows the tell — the scan under Limit reports far more rows than the 20 you asked for:

explain · illustrative

Limit  (cost=89440.43..89449.37 rows=20 width=88)
       (actual time=804.6..804.7 rows=20 loops=1)
  ->  Index Scan using posts_feed_idx on posts
       (cost=0.43..4472500.00 rows=10000000 width=88)
       (actual time=0.05..782.3 rows=200020 loops=1)
 Planning Time: 0.15 ms
 Execution Time: 804.8 ms

Read it bottom-up: the Index Scan feeds rows already sorted (good — no Sort node), but actual ... rows=200020 means it had to emit 200,020 entries before Limit could keep the last 20. Almost all of the ~800 ms is spent walking — and heap-fetching — the discarded prefix. Deeper page, bigger prefix, slower query. Linear in depth.

4 · The correct query (keyset)

Carry a cursor — the last row's (created_at, id) — and seek past it:

sql

SELECT id, author_id, created_at, body
FROM   posts
WHERE  (created_at, id) < ($1, $2)   -- cursor from the previous page
ORDER BY created_at DESC, id DESC
LIMIT  20;

5 · The index that helps + the improved plan

No new index — posts_feed_idx on (created_at DESC, id DESC) already matches. The difference is that Postgres now uses it as a seek, pushing the row comparison into the scan as an Index Cond:

explain · illustrative

Limit  (cost=0.43..0.68 rows=20 width=88)
       (actual time=0.03..0.10 rows=20 loops=1)
  ->  Index Scan using posts_feed_idx on posts
       (cost=0.43..1240.55 rows=98450 width=88)
       Index Cond: (ROW(created_at, id) < ROW($1, $2))
       (actual time=0.02..0.07 rows=20 loops=1)
 Planning Time: 0.12 ms
 Execution Time: 0.13 ms

The Index Cond line is the whole point: the row-value comparison became the starting position of the scan, so the scan opens at the boundary and stops after 20 (actual ... rows=20, not 200020). The planner's rows=98450 is just its estimate for the whole matching range; Limit plus the actual rows=20 show it never reads that far. ~0.1 ms — and it stays ~0.1 ms on page 10,000. That's the ~800 ms → ~0.1 ms win, from the same data and the same index.

6 · The cursor the API returns

The client never sees SQL. The endpoint returns the page plus an opaque next_cursor encoding the last row's sort key — typically base64 of created_at and id:

http

GET /feed                     → 20 posts + next_cursor
GET /feed?cursor=MjAyNi0wN...  → decode → ($1,$2) = (created_at, id)
                                → next 20 + a fresh next_cursor

Encoding it (rather than exposing raw values) keeps the contract opaque, lets you version or sign it, and stops clients from hand-crafting boundaries. Watch one request flow through the engine:

Narrate it (how you'd answer aloud)

"OFFSET pagination is O(m) in the page depth — Postgres still has to produce and discard every skipped row, so page 10,000 walks 200,000 entries and takes hundreds of milliseconds to seconds. For a feed I use keyset pagination: I carry the last row's sort key as a cursor and query WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20, backed by an index on (created_at DESC, id DESC). The row-value comparison expands lexicographically and Postgres pushes it into the index as an Index Cond, so it seeks straight to the boundary and reads only 20 rows — constant time at any depth. The id tiebreaker is required so rows sharing a timestamp aren't skipped or duplicated across pages. The trade-off is no random page jumps, which is fine for infinite scroll."

05 Drills & traps

Graded drills + traps

Reason each out before opening the callout. Assume the posts schema and posts_feed_idx from the worked problem unless told otherwise.

Drill 1 — the next page

Write the WHERE and ORDER BY for the page after a row whose cursor is ($1, $2) = (last_created_at, last_id), newest first, 20 per page, with id as tiebreaker.

Try it first, then read

sql

WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 20;

Why: the tuple comparison and the ORDER BY must use the same column order and direction as the index, so Postgres can seek instead of scan-and-discard.

Drill 2 — the very first page

There's no cursor yet (the user just opened the feed). Write page 1.

Try it first, then read

sql

SELECT id, author_id, created_at, body
FROM   posts
ORDER BY created_at DESC, id DESC
LIMIT  20;

Why: the first page is just the keyset query with the WHERE omitted — no boundary to seek past yet. Take the last row of this result to build the cursor for page 2. (Don't special-case it with OFFSET 0; keep one code path.)

Drill 3 — a leaderboard by score

Page a leaderboard highest score first, 20 per page. Scores are not unique. Give the query and the index.

Try it first, then read

sql

CREATE INDEX lb_idx ON scores (score DESC, id DESC);

SELECT id, player, score
FROM   scores
WHERE  (score, id) < ($1, $2)
ORDER BY score DESC, id DESC
LIMIT  20;

Why: same pattern, different sort column. Because score ties are common, the unique id tiebreaker is doing real work here — without it, players tied on a boundary score would flicker in and out across pages.

Drill 4 — how many pages are there?

The UI wants a "page X of N" total. Why is SELECT count(*) FROM posts a bad idea on a 10M-row feed, and what can you do instead?

Try it first, then read

count(*) has to visit every row (a full sequential or index-only scan) — O(N) — just to render a number, and you'd pay it on every page load. For an infinite feed you usually don't need a total at all. If you must show an approximate one, read the planner's estimate in O(1):

sql

SELECT reltuples::bigint AS approx_rows
FROM   pg_class
WHERE  relname = 'posts';

Why: pg_class.reltuples is the row-count estimate Postgres keeps for the planner, refreshed by ANALYZE/autovacuum. It's approximate but instant — perfect for a fuzzy "~10M posts" label, useless for exact accounting.

Traps to avoid

• OFFSET for deep pages. Fine for "page 3 of 20"; a linear-cost trap for anything that scrolls far.
• Missing / non-unique tiebreaker. Paging on a non-unique key alone skips rows (with <) or duplicates them (with <=) at page boundaries. Always end the sort with a unique column.
• Non-deterministic ORDER BY. No total order → the same row can appear on two pages or none. Ties must be broken; "sorted enough" isn't.
• A nullable sort column. With created_at DESC, NULLs sort first by default (NULLS FIRST), and a row-value comparison returns UNKNOWN when the NULL sits at the deciding position (a leading created_at does) — so keyset silently drops NULL-dated rows. Keep the sort column NOT NULL, or handle the NULL block as a separate, explicit range.
• Expanding the tuple wrong. created_at < $1 AND id < $2 is not the same as (created_at, id) < ($1, $2) — it wrongly drops rows. Use the row-value form (or the exact OR expansion).
• Expecting random page jumps. Keyset can't leap to "page 738." Use OFFSET (or a numbered index) for page-number UIs; keyset for feeds.

Modern note (PG 18)

PostgreSQL 18 (GA Sept 2025) added B-tree skip scans, which help some multicolumn-index cases — when a query omits an equality on a leading index column — by letting the planner "skip" between distinct prefix values instead of scanning the whole index. That's a real win for certain filters, but it does not change the pagination story: skip scan still can't make OFFSET constant-time. For feeds, keyset remains the right pattern.

★ Review

Summary & self-test

One idea to carry out: OFFSET m makes the database produce and throw away m rows, so it's O(m) in page depth; keyset pagination seeks to the last row's sort key and reads only the page, so it's O(page size) at any depth. Give every keyset sort a unique tiebreaker and a matching index, and deep pages stop hurting.
