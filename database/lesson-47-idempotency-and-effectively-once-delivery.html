Idempotency & Effectively-Once Delivery

Every serious message system delivers at least once, which means it sometimes delivers twice. You cannot stop the duplicate from arriving — but you can make the second arrival do nothing. That trick is idempotency, and paired with a small inbox table and one atomic INSERT … ON CONFLICT it turns unreliable at-least-once delivery into the strongest guarantee you can actually build: effectively-once.

Original study notes. Written from scratch for engineers preparing for systems interviews and real distributed work. Examples use PostgreSQL (PG 17/18), but the idea — at-least-once delivery plus an idempotent consumer — is universal across queues, streams, and webhooks. 00 The honest guarantee

Exactly-once delivery is a myth

Start with the claim that trips up most people: exactly-once delivery — every message reaching the consumer once and only once — is impossible across a network. Not hard, not expensive: impossible. The reason is the Two Generals problem. A producer sends a message; the consumer must send back an acknowledgement (ACK); but that ACK can be lost just as easily as the message. Neither side can ever be certain the other received the last packet, so any protocol must pick which risk to take.

That fork gives you exactly two honest delivery guarantees, and you choose one:

At-most-once

  • Send it, don't retry. If it's lost, it's gone.
  • No duplicates, ever — but you drop work.
  • Fine for a throwaway metric ping; wrong for a payment.

At-least-once

  • Retry until you get an ACK. Nothing is lost.
  • The price: a message may arrive 2+ times.
  • What almost every durable broker uses by default.

Anything that must not lose work chooses at-least-once and pays for it in duplicates. So the real engineering question is never "how do I stop duplicates arriving?" It is "how do I make processing a duplicate harmless?" The answer is to make the consumer idempotent: an operation is idempotent when applying it twice has the same effect as applying it once. Combine the two ideas and you get the guarantee you can actually deliver:

The equation to memorize

at-least-once delivery + an idempotent consumer = effectively-once. Also called exactly-once processing. Notice the distinction that resolves the whole confusion: delivery (how many times the message shows up) is unfixable, but processing (how many times the effect lands) is entirely under your control. A broker that markets "exactly-once" is either restricting itself to a closed transactional world, or it is doing idempotent processing under the hood and hoping you don't ask.

The rest of this lesson makes that concrete. First we watch a duplicate get born (s1). Then we build the dedup mechanism — an idempotency key plus an inbox table (s2), grade the kinds of effects by how easy they are to make idempotent (s3), and finish with a worked, runnable idempotent consumer and a set of drills (s4–s5).

01 How a duplicate is born

Why duplicates happen ▸

A duplicate is not a broker bug you can file a ticket against — it is a direct consequence of at-least-once. Here is the canonical window. A consumer pulls a message, does the real work (writes rows, charges a card), and then must ACK the broker so it stops tracking that message. If the consumer crashes after the work but before the ACK — or the ACK is lost, or processing ran past the broker's visibility timeout — the broker never hears "done." Faithful to its at-least-once promise, it redelivers. The work now runs a second time. Step through it:

The critical frame is step 4: the effect had already committed when the process died. From the broker's side, an un-ACKed message is indistinguishable from a message that never got processed at all — so it must assume the worst and resend. That single ambiguity is the whole story. It shows up in more places than a hard crash:

  • Crash after effect, before ACK — the case above; the effect is durable but the ACK never left.
  • Lost or delayed ACK — the work and the ACK both happened, but the ACK packet died on the wire; the broker resends anyway.
  • Visibility-timeout expiry — processing took longer than the broker's timeout, so it handed the same message to another worker while the first was still running.
  • Consumer-group rebalance / redeploy — a partition reassigns mid-batch and uncommitted offsets replay from the last checkpoint.
  • At-least-once publish, too — the producer side has the same window. An outbox relay (Lesson 46) that publishes and then crashes before marking the row sent will re-publish on restart.
Duplicates are a property, not a defect

You will not "fix" this in configuration. Every knob that reduces duplicates (longer timeouts, synchronous ACKs) trades throughput or edges you toward losing messages instead. The durable, correct move is to accept that the message can arrive more than once and to build the consumer so the extra arrivals are harmless. That is what the next three sections construct.

02 The dedup mechanism

Idempotency keys and the inbox ▸

To make a duplicate harmless, you first need to recognize it. Give every message a stable, unique idempotency key — an id that is the same on the original and on every redelivery of that same logical event. Then keep an inbox (also called a dedup table or processed-messages ledger): a table whose PRIMARY KEY is that idempotency key. The rule is simple — a message is a duplicate exactly when its key is already in the inbox.

sql

CREATE TABLE inbox (
  event_id      uuid PRIMARY KEY,        -- the idempotency key
  processed_at  timestamptz NOT NULL DEFAULT now()
);

The elegant part is that you never write a "does this key exist?" check yourself — you let the PRIMARY KEY do it, atomically, with INSERT … ON CONFLICT DO NOTHING RETURNING. If the insert creates a row, RETURNING hands it back and you know this is the first time — so you apply the effect. If the key was already there, the conflict makes the insert a no-op, RETURNING is empty, and you skip. Watch the dedup decide new vs duplicate:

Two design points decide whether this actually works. First, the key must be stable across retries: the same logical event must carry the same event_id on delivery #1 and delivery #7. Good sources are a UUID the producer stamps once when the event is created (the outbox row's own id from Lesson 46 is ideal), or a natural business key like (order_id, 'order.created'). A UUID freshly generated on each publish attempt is fatal — every duplicate looks brand-new and dedup never fires. Second, and the subject of s4: recording the key and applying the effect must be one atomic transaction. Split them and you reopen the very crash window we're trying to close.

Why RETURNING is the whole trick

ON CONFLICT DO NOTHING alone silently swallows the duplicate but tells you nothing. Adding RETURNING converts the conflict into a signal you can branch on: a row came back → new → run the effect; no row → duplicate → skip. One statement does the check, the record, and the verdict — with no read-then-write race, because the PRIMARY KEY arbiter resolves concurrency inside the insert itself.

03 A ladder of difficulty

Levels of idempotency

Not every effect needs an inbox. Before you reach for the dedup table, ask whether the effect is already idempotent — because the cheapest idempotency is the kind you get for free from how you wrote the write.

Level 0 — naturally idempotent effects

Some operations converge to a state rather than accumulate a change, so re-running them lands exactly where they were. These need no dedup at all:

Idempotent (converge to a state)

  • SET status = 'shipped' — assign, don't add.
  • UPSERT to a target row (Lesson 17): INSERT … ON CONFLICT DO UPDATE.
  • DELETE WHERE id = … — second run deletes nothing.
  • Setting a flag, storing a computed value, writing a known key.

Not idempotent (accumulate a change)

  • balance = balance + 10 — each run adds again.
  • INSERT a new row with no unique key — makes a copy.
  • Append to a list / push to an array.
  • Send an email, fire a webhook, ship a package.

The design lever is real: whenever you can, model the effect as "make the world look like this" instead of "change the world by this much." An UPSERT that sets a row to a computed target is idempotent by construction; the same information expressed as an increment is not. Reach for this reframing first — it can delete the dedup table from your design entirely.

Level 1 — the inbox / dedup table

When the effect is inherently non-idempotent (an increment you can't rewrite, or an external side effect), wrap it with the inbox keyed by the idempotency key. The ON CONFLICT … RETURNING gate from s2 makes the whole handler idempotent even though the inner effect isn't. This is the general-purpose tool; s4 builds it end to end.

Housekeeping — the inbox grows forever

Every processed message leaves a row, so the inbox grows without bound unless you prune it. But there is a hard rule: only delete rows older than the broker's maximum redelivery horizon — its retention window, or the longest a message can sit before a final redelivery. Prune with a scheduled job, or (better at scale) partition the inbox by day and DROP whole old partitions (Lesson 34):

sql

-- safe ONLY if the broker cannot redeliver anything older than 7 days
DELETE FROM inbox
WHERE processed_at < now() - INTERVAL '7 days';

Prune faster than that window and a genuinely late duplicate finds an empty inbox and gets applied twice — you'd trade unbounded growth for silent double-processing, a bad trade.

Why this beats a distributed transaction

A tempting alternative is "just wrap the broker and the database in one distributed transaction" — two-phase commit (2PC) across the queue and Postgres. Resist it. 2PC couples the availability of both systems, blocks holding locks if the coordinator dies between prepare and commit, and most brokers don't speak it well. The inbox needs no distributed coordinator: it is one local transaction inside the database you already trust, and it fails gracefully — a duplicate is a cheap zero-row no-op, never a resource pinned by an orphaned prepared transaction. This is the same lesson as the transactional outbox (Lesson 46): prefer one local transaction plus idempotency over cross-system atomicity.

The outbox and the inbox are two ends of one rope

The outbox (producer side, Lesson 46) guarantees the event is published at least once. The inbox (consumer side, this lesson) guarantees the event is applied at most once. At-least-once and at-most-once, composed, give you exactly-once end to end — without a single distributed transaction anywhere in the path.

04 Worked problem

Building an idempotent consumer ▸

Now assemble the pieces into a runnable consumer and see exactly where the naive versions leak.

1 — The schema

sql

-- the effect we must apply exactly once
CREATE TABLE wallet (
  user_id  bigint PRIMARY KEY,
  balance  numeric NOT NULL DEFAULT 0
);

-- the dedup ledger; event_id is the stable idempotency key
CREATE TABLE inbox (
  event_id      uuid PRIMARY KEY,
  processed_at  timestamptz NOT NULL DEFAULT now()
);

2 — The task

You consume wallet.credit events from a queue delivered at-least-once. Each event carries a stable event_id (uuid) and an amount. Apply each credit to the user's wallet exactly once, even when the broker delivers the same event several times.

3 — The naive attempts, and why they leak

Naive A — just apply it. Trust the queue and increment:

sql

-- WRONG: increment is not idempotent
UPDATE wallet SET balance = balance + :amount WHERE user_id = :uid;

A redelivery credits the account again — the exact $10 → $20 bug from FIG 1. An increment is inherently non-idempotent, so a bare UPDATE can never be safe under at-least-once delivery.

Naive B — check, then act. Look up the id, and if it's new, apply and record:

sql

-- WRONG: a race and a crash window hide in the gaps
SELECT 1 FROM inbox WHERE event_id = :eid;          -- app sees "not found"
UPDATE wallet SET balance = balance + :amount
  WHERE user_id = :uid;                             -- apply the effect
INSERT INTO inbox (event_id) VALUES (:eid);         -- record it (maybe a 2nd txn)

Two independent failures live here. (a) A time-of-check/time-of-use race: two concurrent redeliveries of :eid both run the SELECT, both see "not found," and both credit the wallet before either inserts. The PRIMARY KEY will reject the second INSERT — but only after the money was credited twice. (b) A crash window: if the UPDATE commits and the process dies before the INSERT (worse if they're separate transactions), the redelivery finds no inbox row and credits again. Check-then-act cannot be made safe by ordering; the check and the act must be one indivisible step.

4 — The fix: one atomic, race-safe statement

Fuse the dedup and the effect into a single data-modifying CTE. The INSERT … ON CONFLICT DO NOTHING RETURNING both records the key and reports whether it was new; the UPDATE reads that result via FROM claimed, so it fires only when a row was actually inserted:

sql

BEGIN;

WITH claimed AS (
  INSERT INTO inbox (event_id)
  VALUES (:eid)
  ON CONFLICT (event_id) DO NOTHING
  RETURNING event_id
)
UPDATE wallet w
SET balance = w.balance + :amount
FROM claimed
WHERE w.user_id = :uid;

COMMIT;

Trace both cases. First delivery: claimed yields one row, the UPDATE joins that one row to the wallet, and the balance rises once — the inbox record and the credit commit together, atomically. Redelivery: the insert conflicts on the PRIMARY KEY, claimed is empty, so UPDATE … FROM claimed joins the wallet against zero rows and touches nothing — a clean no-op. 5 — Why it's better (read the plan)

Correctness first: the effect is gated on the insert within the same statement's snapshot, so there is no read-then-write gap for a concurrent redelivery to slip through, and no crash window between recording and applying — they are the same transaction. Performance is a bonus: both cases are two index touches, no scans.

explain (analyze) — first delivery, illustrative

Update on wallet w  (cost=0.30..8.35 rows=0 width=0) (actual rows=0 loops=1)
  CTE claimed
    ->  Insert on inbox  (cost=0.00..0.01 rows=1 width=24) (actual rows=1 loops=1)
          Conflict Resolution: NOTHING
          Conflict Arbiter Indexes: inbox_pkey
          ->  Result  (cost=0.00..0.01 rows=1 width=24) (actual rows=1 loops=1)
  ->  Nested Loop  (cost=0.29..8.33 rows=1 width=42) (actual rows=1 loops=1)
        ->  CTE Scan on claimed  (cost=0.00..0.02 rows=1 width=32) (actual rows=1 loops=1)
        ->  Index Scan using wallet_pkey on wallet w  (actual rows=1 loops=1)
              Index Cond: (user_id = 42)
Planning Time: 0.11 ms
Execution Time: 0.09 ms

Read it top-down: the Insert on inbox uses inbox_pkey as its Conflict Arbiter — that PK is what catches a duplicate. On the first delivery its CTE Scan yields one row, the Nested Loop pairs it with the wallet found by Index Scan using wallet_pkey, and the Update credits one row. On a redelivery the same plan runs, but the insert's actual rows=0, so CTE Scan on claimed returns 0 rows, the Nested Loop produces 0, and Update on wallet reports actual rows=0 — the identical two index structures are probed, no heap is scanned, and nothing changes. Idempotency here costs one extra index probe, not a table scan.

6 — Narrate it

Say it out loud as a chain of guarantees: "The producer wrote the domain row and its outbox event in one transaction, so the event is published at least once (Lesson 46). A relay — or a worker that claimed the job with SELECT … FOR UPDATE SKIP LOCKED (Lesson 28) — delivers it, possibly twice. My consumer closes the loop: one transaction inserts the event_id into the inbox with ON CONFLICT DO NOTHING and applies the credit only if the insert was new. The inbox makes the effect land at most once. At-least-once publish plus at-most-once apply equals exactly-once, with no distributed transaction — just two local ones and a primary key doing the arbitration."

05 Practice

Drills & traps

Work each drill before opening its solution. Assume the wallet and inbox schema from s4, and at-least-once delivery throughout.

Drill 1 — spot the non-idempotent effect

Two events arrive: profile.activate (set the user's status to active) and loyalty.award (add 5 points to their balance). Which is naturally idempotent, which is not, and rewrite the unsafe one so a redelivery is harmless without an inbox if you can — otherwise say why the inbox is required.

Try it first, then read

profile.activate is idempotent: UPDATE users SET status = 'active' WHERE id = :uid converges to a state — run it ten times, the status is still active. loyalty.award (points = points + 5) is not: each replay adds 5 again. You cannot rewrite a pure increment into an idempotent single row-set, because the target value depends on how much was already there — so this one needs the inbox (gate the +5 on a new event_id). Why: "converge to a state" is idempotent for free; "accumulate a delta" needs a dedup key.

Drill 2 — the inbox in a separate transaction

A teammate applies the credit in one transaction and records the event_id in a second, "to keep the inbox write out of the hot path." Name the two distinct ways this loses correctness under at-least-once delivery.

Try it first, then read

(1) Crash window: if the credit's transaction commits and the process dies before the inbox transaction commits, the redelivery sees no inbox row and credits again — a double-apply. (2) Concurrency race: two redeliveries can both apply the credit before either records the id, because the dedup isn't visible until its own later commit. Both vanish only when the inbox insert and the effect are in the same transaction, so they commit or roll back as one. Why: atomicity is the whole point — splitting the record from the effect re-opens the exact gap idempotency exists to close.

Drill 3 — the key you can't dedup on

Deliveries are still doubling even though you added the inbox. You discover the producer calls gen_random_uuid() to build the event_id on every publish attempt, including retries. Explain why dedup silently fails, name the fix, and then bound the inbox's growth safely.

Try it first, then read

A per-attempt UUID means the original and its redelivery carry different keys, so the ON CONFLICT never triggers — every copy looks brand-new and gets applied. The fix is a stable idempotency key generated once at the source and reused on every retry: the outbox row's own id, or a natural key like (order_id, 'order.created'). For growth, prune the inbox but never inside the redelivery window: DELETE FROM inbox WHERE processed_at < now() - INTERVAL '30 days' on a schedule, or partition by day and DROP old partitions. Why: dedup can only work if duplicates share a key, and pruning faster than the broker can redeliver re-exposes late duplicates.

Drill 4 — "the vendor promises exactly-once"

An architect wants to delete all inbox logic because the new broker advertises "exactly-once delivery." What do you tell them, and under what narrow condition is a system's "exactly-once" claim actually meaningful?

Try it first, then read

Exactly-once delivery across a network to a consumer with an external side effect is impossible (Two Generals: the consumer can always crash after the effect and before the ACK). What vendors call "exactly-once" is either (a) exactly-once processing confined to a closed transactional world — e.g. read-process-write entirely inside the broker's own store with transactional offsets — which still relies on idempotent/transactional writes under the hood, or (b) marketing. The moment your effect touches an outside system (charge a card, send mail, write another database), you are back to at-least-once and you keep the inbox. Why: you can move where the idempotency lives, never remove the need for it.

Traps to carry into the interview

• Non-idempotent effect, no dedup (increment, append, blind insert, external call) → a redelivery corrupts state.
• Inbox recorded in a separate transaction from the effect → crash window plus race re-apply.
• Check-then-act (SELECT then INSERT) instead of atomic ON CONFLICT → TOCTOU race under concurrency.
• Unstable / missing idempotency key (fresh UUID per attempt) → duplicates don't share a key, so dedup can't fire.
• Idempotency key not the PRIMARY KEY/UNIQUE → the ON CONFLICT arbiter has nothing to catch on.
• Never pruning the inbox → unbounded growth; but pruning inside the redelivery window → late duplicates leak through.
• Believing "exactly-once delivery" exists → dropping idempotency and getting double-charged in production.

★ Review

Summary & self-test

One idea holds the lesson together: you cannot stop a message arriving twice, so you make the second arrival do nothing. Give each event a stable idempotency key, record processed keys in an inbox with a PRIMARY KEY, and apply the effect in the same transaction gated by INSERT … ON CONFLICT DO NOTHING RETURNING. At-least-once delivery plus that idempotent consumer is effectively-once.

01Exactly-once is a mythAcross a network you get at-most-once or at-least-once. Durable systems pick at-least-once and pay in duplicates.
02Delivery vs processingYou can't control how many times a message is delivered, but you fully control how many times its effect lands.
03The equationat-least-once delivery + idempotent consumer = effectively-once. That's the honest, buildable guarantee.
04Duplicates are structuralCrash-before-ACK, lost ACK, visibility timeout, rebalance: an un-ACKed message must be resent. Not a config bug.
05Idempotency key + inboxA stable per-event id as the PRIMARY KEY of a dedup table turns a redelivery into a zero-row no-op.
06ON CONFLICT … RETURNINGRow back → new → apply; no row → duplicate → skip. One atomic statement, no read-then-write race.
07Same transaction, alwaysRecord the key and apply the effect together, or the crash window and the race come straight back.
08Converge, don't accumulateSET/UPSERT are idempotent for free; increments and external calls need the inbox. Prune it, but only past the redelivery window.
