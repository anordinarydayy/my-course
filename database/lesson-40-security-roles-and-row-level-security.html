Security, Roles & Row-Level Security

Security in Postgres is two layers: who may connect and act (roles, privileges, authentication) and which rows they may see (Row-Level Security). Get the first wrong and the app runs as superuser with the keys to the kingdom; get the second wrong and one tenant reads another tenant's data. This lesson wires both correctly — least-privilege roles, a policy that auto-scopes every query, and the sharp edges (owner bypass, missing WITH CHECK, un-indexed policies) that turn a "secure" schema into a leak.

00 The threat model

Roles, privileges, and the principle of least privilege

In Postgres there are no separate "users" and "groups" — there is one concept, the role. A role with LOGIN is what you'd call a user; a role with NOLOGIN is what you'd call a group. Roles can be members of other roles, and (with INHERIT) a member automatically gains the privileges of every role it belongs to. That single mechanism gives you everything: model a job as a group role, grant privileges to the job, and hand people or services a login role that is a member of it.

A privilege is permission to do one thing to one object: SELECT / INSERT / UPDATE / DELETE on a table, USAGE on a schema or sequence, EXECUTE on a function, CONNECT on a database. You hand them out with GRANT and take them back with REVOKE. The governing rule is the principle of least privilege: every role gets exactly the privileges its job needs and not one more — and the application's role is emphatically not a superuser. A superuser bypasses all permission checks (and, as you'll see, Row-Level Security too), so an app running as superuser turns any SQL-injection bug into a full-cluster compromise.

sql

-- NOLOGIN roles model *jobs*; LOGIN roles are people/services
CREATE ROLE app_write NOLOGIN;            -- a bundle of privileges
CREATE ROLE app_ro    NOLOGIN;

GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA app TO app_write;
GRANT SELECT                 ON ALL TABLES IN SCHEMA app TO app_ro;

-- the app's login role: NOT a superuser, inherits the app_write job
CREATE ROLE app_svc LOGIN PASSWORD 'set-via-secret-manager'
  NOSUPERUSER NOCREATEDB NOCREATEROLE IN ROLE app_write;
The mental model

Think in three planes. Authentication answers "are you who you claim?" (password, certificate, token — the pg_hba.conf gate). Authorization answers "may this role do this to this object?" (GRANT/REVOKE). Row-Level Security answers "which rows of this object may this role touch?" (policies). This lesson climbs those three planes in order.

01 Authorization

Role hierarchy and object privileges ▸

Privileges attach to objects, and roles inherit them through membership. That indirection is the whole point: you grant once, to a job, and every login role that holds the job picks it up — and revoking the job removes it everywhere at once. Watch a privilege check resolve from a login role, up through its group, to a grant on a table, and see what happens when a privilege was never granted:

Beyond whole-table grants, Postgres supports column-level privileges (GRANT SELECT (id, email) ON customers TO support), so a support role can read two columns without seeing the rest. Two housekeeping tools matter in practice. First, USAGE on the schema is required in addition to table privileges — a common "permission denied for schema" gotcha. Second, GRANT ... ON ALL TABLES only affects tables that exist right now; for tables created later you need ALTER DEFAULT PRIVILEGES.

sql

GRANT USAGE ON SCHEMA app TO app_ro;              -- reach the schema first
GRANT SELECT (id, email) ON customers TO support;  -- column-level grant
REVOKE ALL ON SCHEMA public FROM PUBLIC;         -- close the open default

-- future tables in app also become readable by app_ro automatically
ALTER DEFAULT PRIVILEGES IN SCHEMA app
  GRANT SELECT ON TABLES TO app_ro;
Grant to the job, never to the person

Grant privileges to group roles (app_write, reporting, support) and make login roles members. When someone leaves or a service is retired, you drop or re-point one login role — you never chase a scatter of individual grants. This is also what makes an access audit tractable: read the group's grants, not fifty people's.

02 Row-level control

Row-Level Security: the query filters itself ▸

Table privileges are all-or-nothing per table: if you can SELECT orders, you can select every row of orders. Row-Level Security (RLS) adds a finer gate — a per-row predicate that Postgres silently ANDs into every query against the table. Turn it on with ENABLE ROW LEVEL SECURITY, then attach a POLICY whose USING expression decides which rows are visible. A classic multi-tenant policy keys off a per-connection setting:

sql

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant')::bigint);

The instant that policy exists, a plain SELECT * FROM orders — with no WHERE at all — returns only the rows whose tenant_id matches the session's app.tenant value. The filtering is invisible to the application; it cannot be forgotten in one code path and remembered in another, because it isn't in the application at all. Step through what the table "looks like" as RLS comes online and the tenant setting changes:

Two subtleties the diagram hints at. First, once RLS is enabled but no policy yet grants a row, the default is deny — a non-owner role sees zero rows and no error. That fail-closed default is a feature, not a bug: forget the policy and you leak nothing, rather than everything. Second, a USING clause governs which rows are visible (reads, and the rows an UPDATE/DELETE may touch); for writes there is a WITH CHECK clause — but on a FOR ALL policy it defaults to the USING expression, so writes are already tenant-scoped. You add an explicit WITH CHECK only when the write rule must differ from the read rule — a distinction the worked problem and the drills return to.

The predicate is ANDed, not substituted

RLS does not replace your WHERE; it adds to it. SELECT * FROM orders WHERE status = 'open' under the policy runs as if you'd written WHERE status = 'open' AND tenant_id = current_setting('app.tenant')::bigint. That is exactly why you must index the policy column — the extra predicate rides along on every single query, so it had better be cheap.

03 The front door

Authentication and hardening the perimeter

Roles and RLS decide what a connected session may do — but the connection has to be authenticated first, and that gate is pg_hba.conf (Host-Based Authentication). Postgres reads it top to bottom and uses the first matching line for a given connection type, database, user, and client address. The method column is where security is won or lost.

pg_hba.conf

# TYPE     DATABASE  USER      ADDRESS         METHOD
hostssl    app       app_svc   10.0.0.0/24     scram-sha-256   # TLS + hashed pw
hostssl    app       reporter  10.0.0.0/24     cert            # client certificate
host       all       all       0.0.0.0/0       reject          # deny everything else
  • SCRAM-SHA-256. The modern password method — set password_encryption = scram-sha-256 so stored verifiers are salted and challenge-response, never the plaintext or an unsalted md5. Never use trust outside a throwaway local sandbox; trust means "no password at all."
  • TLS. Use hostssl (not bare host) so credentials and data are encrypted in transit; set ssl = on and provide a server cert. cert auth goes further and authenticates the client by its certificate.
  • The superuser danger. The app's role must be NOSUPERUSER. A superuser bypasses every privilege check and every RLS policy, so any injection or logic bug becomes total. Keep superuser for a human DBA on a locked-down path only.
  • SECURITY DEFINER functions. A function marked SECURITY DEFINER runs with the owner's privileges, letting a low-privileged caller perform a narrow, audited action. It is powerful and dangerous: always pin search_path so a caller can't shadow objects, and keep the body tight.
  • Secrets. Passwords belong in a secrets manager / injected env, never in source, connection strings in the repo, or logs. Rotate them; scope them to the app_svc role, not superuser.
  • PG 18: OAuth 2.0. PG 18 adds an oauth authentication method in pg_hba.conf, delegating token validation to your identity provider — so database logins can ride your existing SSO / bearer-token infrastructure instead of long-lived passwords.

sql

-- runs as the function's OWNER; pin search_path so it can't be hijacked
CREATE FUNCTION redeem_coupon(code text) RETURNS boolean
  LANGUAGE plpgsql
  SECURITY DEFINER
  SET search_path = app, pg_temp          -- non-negotiable
  AS $$ BEGIN /* narrow, audited privileged action */ END $$;
Defense in depth

No single control is sufficient. TLS without SCRAM leaks passwords to a compromised network path insider; SCRAM without least privilege means one stolen credential owns everything; least privilege without RLS means one tenant reads another's rows. Layer them: authenticate at the door (pg_hba.conf + SCRAM/TLS), authorize by role (least privilege, no superuser app), and filter rows in the database (RLS). The worked problem next assembles the RLS layer end to end.

04 Worked problem

Watertight multi-tenant isolation with RLS ▸

A single Postgres database serves many tenants; rows share tables and carry a tenant_id. The requirement: a session for tenant A must never read or write tenant B's rows — enforced in the database, not trusted to application code — and it must stay fast at scale.

1 · The schema

sql

CREATE TABLE tenants (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL
);

CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id   bigint NOT NULL REFERENCES tenants(id),
  status      text   NOT NULL DEFAULT 'open',
  item        text   NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

2 · The task

Guarantee that SELECT, INSERT, UPDATE, and DELETE from the app role only ever see and touch the current tenant's rows — and that the guarantee holds even for the migration job and even if a developer forgets a WHERE tenant_id = ....

3 · The naive attempt (and why it leaks)

The tempting answer is "just always filter in the app": every query carries WHERE tenant_id = $current. It works until it doesn't — a single query in a single code path forgets the clause (a new report, a debug endpoint, an ORM-generated findAll) and that one omission returns every tenant's rows. Correctness that depends on never making a mistake is not correctness.

A better instinct is RLS — but a half-applied RLS is its own trap. Enable the policy but skip FORCE, and the table owner (your migration/admin connection) silently bypasses it. Skip the index, and every query pays a sequential scan for the added predicate:

explain · illustrative — RLS on, but no index on tenant_id

Seq Scan on orders  (cost=0.00..2891.00 rows=6 width=40)
  Filter: ((tenant_id = (current_setting('app.tenant'::text))::bigint)
           AND (status = 'open'::text))
  Rows Removed by Filter: 99994

Postgres reads all 100,000 rows and throws away 99,994 — the policy is correct but catastrophically slow, because the predicate it injects has nothing to seek on.

4 · The fix

sql

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE  ROW LEVEL SECURITY;   -- the owner obeys the policy too

-- one policy for reads and writes: USING gates visibility, WITH CHECK gates inserts/updates
CREATE POLICY tenant_rw ON orders
  USING       (tenant_id = current_setting('app.tenant', true)::bigint)
  WITH CHECK  (tenant_id = current_setting('app.tenant', true)::bigint);

-- index the policy column (+ a common filter) so the injected predicate seeks
CREATE INDEX orders_tenant_status_idx ON orders (tenant_id, status);

Then every connection sets its tenant once, right after checkout — and under a transaction-pooled connection it must be a transaction-local setting so it can't leak to the next tenant's transaction on the same physical connection:

sql

-- session-wide (direct connection or session-mode pooler):
SET app.tenant = '42';

-- transaction-scoped (safe under a transaction-mode pooler): resets at COMMIT
SELECT set_config('app.tenant', '42', true);   -- third arg true = LOCAL

5 · Why it is better

Now the guarantee lives in the database. USING makes cross-tenant rows invisible; WITH CHECK rejects an INSERT/UPDATE that would write another tenant's id; FORCE subjects even the owner to the policy; and the index makes the injected predicate a cheap seek. With current_setting(..., true) a missing setting yields NULL, so the predicate is NULL and no rows match — fail-closed, never fail-open. The same query that scanned the whole table now runs:

explain · illustrative — RLS on, indexed

Index Scan using orders_tenant_status_idx on orders
      (cost=0.42..18.74 rows=6 width=40)
  Index Cond: ((tenant_id = (current_setting('app.tenant'::text, true))::bigint)
               AND (status = 'open'::text))

The policy predicate is folded straight into the Index Cond — Postgres jumps to this tenant's slice of the index instead of reading the table. Correctness and speed, from the same three ideas. Step through the enforcement, including the owner-bypass leak that FORCE closes:

6 · Narrate it

"I isolate tenants in the database so no application mistake can cross the boundary. Each row carries tenant_id; I ENABLE and FORCE RLS on the table so the policy binds even the owner, and I write one policy with both USING (which rows are visible) and WITH CHECK (which rows may be written), keyed on a per-connection app.tenant GUC read with current_setting(..., true) so a missing value fails closed. The app sets that GUC transaction-locally right after connection checkout, which is pooler-safe. I index (tenant_id, status) so the predicate RLS injects becomes an index seek, not a full scan — the EXPLAIN shows it folded into the Index Cond. The one role I never let the app use is superuser, because superusers bypass RLS entirely."

05 Graded drills

Drills & traps

Attempt each before opening the solution. They rise in difficulty and target the exact places RLS setups leak in production.

Drill 1 · The migration still sees everything

You enabled RLS and wrote a correct tenant_isolation policy. The app role is isolated perfectly — but your nightly migration job, which connects as the owner of orders, still reads every tenant's rows. Why, and what is the one-line fix?

Try it first, then read

By default, the table owner bypasses RLS (so an owner can always inspect/repair data). Your migration runs as owner, so policies simply don't apply to it. Fix:

sql

ALTER TABLE orders FORCE ROW LEVEL SECURITY;

Why: FORCE makes the policy apply to the owner too. (A superuser still bypasses RLS regardless — so never run the app, or migrations, as superuser.)

Drill 2 · The app suddenly sees zero rows

You ran ALTER TABLE orders ENABLE ROW LEVEL SECURITY in a hotfix and deployed. No errors — but now every SELECT from the app returns an empty set, on data that clearly exists. What happened, and what did you forget?

Try it first, then read

Enabling RLS with no policy means the default: deny all. With no permissive policy to admit a row, every row is filtered out for non-owner roles — silently, no error. You forgot to create the policy:

sql

CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant', true)::bigint);

Why: RLS is fail-closed by design — the safe failure is "see nothing," not "see everything," which is exactly what you want from a security feature.

Drill 3 · Do writes need their own clause?

Your FOR ALL policy (Drill 2) has only a USING clause. A malicious client, in tenant 1's session, runs INSERT INTO orders (tenant_id, item) VALUES (99, 'x') to plant a row under tenant 99. Does it land? And when would a USING-only policy fail to guard writes?

Try it first, then read

It is rejected — ERROR: new row violates row-level security policy. For a FOR ALL policy, when you omit WITH CHECK Postgres reuses the USING expression as the write check, so a new row must also satisfy tenant_id = current_setting('app.tenant') and the forged 99 is blocked. You only need an explicit WITH CHECK when the write rule must differ from the read rule (e.g. "read the whole org, but only insert rows assigned to me"). Two hardening moves are still worth it — state the check explicitly for clarity, and, belt-and-suspenders, stop trusting the client's tenant_id at all:

sql

ALTER POLICY tenant_isolation ON orders
  WITH CHECK (tenant_id = current_setting('app.tenant', true)::bigint);

-- even better: don't let the app write tenant_id at all
ALTER TABLE orders ALTER COLUMN tenant_id
  SET DEFAULT current_setting('app.tenant')::bigint;
REVOKE INSERT (tenant_id) ON orders FROM app_write;

Why: a FOR ALL policy's USING already doubles as its WITH CHECK when the latter is omitted, so writes are tenant-scoped out of the box; an explicit WITH CHECK is for asymmetric read/write rules. Defaulting tenant_id from the session and revoking the column removes the chance to forge it entirely.

Drill 4 · Cross-tenant bleed under a pooler

Everything passes in tests on a direct connection. In production, behind PgBouncer in transaction mode, tenant A's request occasionally returns tenant B's rows. RLS is enabled, forced, indexed, and the policy is correct. What is leaking, and how do you fix it without abandoning the pooler?

Try it first, then read

You set the tenant with plain SET app.tenant = ..., which is session-scoped. In transaction-mode pooling, one physical connection is handed to many clients across transactions — so A's setting survives onto B's transaction. Make the setting transaction-local so it resets at commit:

sql

-- run at the start of every transaction, not once per session
SELECT set_config('app.tenant', '42', true);   -- true = LOCAL, cleared at COMMIT
-- equivalently:  SET LOCAL app.tenant = '42';   (inside a BEGIN…COMMIT)

Why: a LOCAL setting is scoped to the current transaction and reset when it ends, so no residue crosses onto the next client's transaction on the shared connection.

Traps to carry into the interview

• Owner bypass — ENABLE alone lets the owner (migrations!) see all rows; add FORCE.
• Superuser app — a superuser bypasses RLS and all grants; the app role must be NOSUPERUSER, always.
• Un-indexed policy — the injected predicate rides every query; no index on the policy column means a seq scan every time.
• USING vs WITH CHECK — USING gates reads/visibility; WITH CHECK gates writes and defaults to USING on a FOR ALL policy. Write an explicit one only for asymmetric read/write rules.
• SET vs SET LOCAL — session settings leak across transaction-pooled connections; use LOCAL/set_config(...,true).
• current_setting without the missing-ok flag — current_setting('app.tenant') errors if unset; use the two-arg form current_setting('app.tenant', true) so it returns NULL and fails closed.
• Default-deny vs default-allow — RLS is fail-closed; a forgotten policy leaks nothing. Missing app-side filtering is fail-open; a forgotten WHERE leaks everything. Prefer the database gate.
• Permissive policies OR together — multiple permissive policies are combined with OR, so a too-broad one widens access; use RESTRICTIVE policies (AND-ed) to tighten.

★ Review

Summary & self-test

One idea holds the lesson together: put the security boundary in the database, not in the application — least-privilege roles decide who acts, and Row-Level Security decides which rows they touch, so no forgotten WHERE and no rogue code path can cross a tenant line. The rest is knowing the sharp edges: FORCE, WITH CHECK, an index on the policy column, transaction-local settings, and never running the app as superuser.
