Full-Text Search

LIKE '%term%' is where naive search goes to die: it reads every row, ignores word endings, and cannot tell a strong match from a weak one. PostgreSQL ships a real search engine inside the database — tsvector and tsquery — that normalizes language into meaning-bearing lexemes, matches with the @@ operator, ranks by relevance, and is backed by a GIN index. This lesson builds a working article search from scratch and drills the traps that make FTS silently slow or silently wrong.

00 The problem

Why LIKE can’t really search

Every app eventually needs to search text: articles, product descriptions, support tickets, comments. The tempting first move is WHERE body ILIKE '%term%'. It works on a demo and falls apart in production, and it is worth being precise about why, because each failure is exactly what full-text search fixes.

sql

-- substring search: cannot use a b-tree, and misses word variants
SELECT id, title
FROM articles
WHERE body ILIKE '%running%';   -- scans every row; won't match "ran" or "runs"

Three things are broken here. First, it can’t use an index. A b-tree can serve a prefix like 'run%', but a leading wildcard '%run%' forces a Seq Scan over the whole table. Second, there is no language. The search is a raw byte-substring test: '%run%' also matches “brunch” and “grunt,” yet misses “runs” and “running” unless you contort the pattern. Third, there is no ranking. LIKE is a boolean — a row matches or it doesn’t — so you cannot put the best results first.

Full-text search replaces the byte match with a linguistic match. It normalizes text into a tsvector — a sorted set of lexemes (stemmed root words) with positions — and normalizes the query into a tsquery. The @@ operator asks “does this vector satisfy this query?” on meaning, not spelling, and a GIN index makes that match fast.

ILIKE '%term%'

  • Substring bytes — no stemming, no stop words.
  • Leading wildcard → Seq Scan, no b-tree help.
  • Boolean only — no relevance ranking.
  • Matches inside words; fine for a tiny table, wrong at scale.

tsvector @@ tsquery

  • Lexemes: “running”, “runs”, “ran”→ a common root.
  • Backed by a GIN inverted index — no full scan.
  • ts_rank scores matches so the best rise first.
  • Understands AND/OR/phrase and drops noise stop words.
The one-line reframe

Stop thinking “does this string contain that string” and start thinking “does this document match this search intent.” The entire machinery below — to_tsvector, @@, GIN, ts_rank — exists to answer that second question quickly and in ranked order.

01 Normalization

How text becomes a tsvector ▸

PostgreSQL never searches your raw text directly. It first runs the text through a text search configuration (here, 'english') that does three jobs: it tokenizes the text into words and records each word’s position; it drops stop words (extremely common words like “the,” “are,” “of” that carry no search signal); and it stems each remaining word to a root lexeme with a dictionary. The result is a tsvector: the sorted set of distinct lexemes, each tagged with the positions where it occurred.

sql

SELECT to_tsvector('english', 'The quick brown foxes are jumping');
-- 'brown':3 'fox':4 'jump':6 'quick':2

Notice what happened: “the” (position 1) and “are” (position 5) vanished as stop words, “foxes” became fox and “jumping” became jump, and the surviving lexemes were sorted alphabetically while keeping their original positions. Step through the pipeline:

The positions are not decoration. They let a tsquery ask for phrases (“quick” immediately followed by “fox”) and let ts_rank reward documents where the terms sit close together. The crucial habit to internalize: both sides must use the same configuration. If the document was built with 'english' but you query with 'simple' (which does no stemming), “running” stays “running” and never matches the stored run — a silent zero-results bug we return to in the drills.

Lexeme, not word

A tsvector stores lexemes, not words. “run,” “runs,” “running” all normalize to run, so a search for any of them finds all of them — the single biggest reason FTS beats LIKE. (Stemming is algorithmic, not a thesaurus: irregular forms like “ran” stem to ran, and synonyms need a separate dictionary.)

02 Matching & indexing

Matching with @@, fast with GIN ▸

A match is a single operator: tsvector @@ tsquery returns true when the document’s lexemes satisfy the query. Because both sides are normalized the same way, meaning lines up even when spelling doesn’t:

sql

SELECT to_tsvector('english', 'The foxes are running')
     @@ websearch_to_tsquery('english', 'run fox');   -- → true ('run' & 'fox' both present)

You never hand-write a tsquery from user input — you parse it with one of four functions, each with a different tolerance for messy text:

  • to_tsquery('english','run & fox') — strict: you write the boolean operators (& and, | or, ! not, <-> phrase). Errors on stray punctuation.
  • plainto_tsquery('english','run fox') — ANDs the words together; ignores operators.
  • phraseto_tsquery('english','quick fox') — requires the words adjacent, in order (uses <->).
  • websearch_to_tsquery('english','"quick fox" -brown') — Google-style syntax (quotes for phrases, - to exclude, or). The right default for a user-facing search box because it never throws on bad input.

Matching on @@ is correct but, done alone, it recomputes or scans for every row. The fix is to store the vector in a column and index it with GIN. A GIN (Generalized Inverted Index) is an inverted index: for each lexeme it keeps the sorted list of rows that contain it — exactly the structure a search engine needs. Modern Postgres makes the column maintenance automatic with a GENERATED column, and you order the output by ts_rank for relevance. Watch the query flow through the machinery:

One subtlety that trips people: the GENERATED column below calls the two-argument to_tsvector('english', …) with the config as a constant literal. That form is IMMUTABLE, which is exactly what a generated column and an expression index require. What you must avoid is the single-argument to_tsvector(…): it is only STABLE, because it reads the default_text_search_config setting at run time — so its result could change if that setting changes, and Postgres rejects it in an index or generated column. Always pass the configuration explicitly as a literal.

sql

-- store the vector as a maintained column, then index it
ALTER TABLE articles
  ADD COLUMN search tsvector
  GENERATED ALWAYS AS (to_tsvector('english', title || ' ' || coalesce(body, ''))) STORED;

CREATE INDEX articles_search_gin ON articles USING GIN (search);
03 Reach & limits

Fuzzy search, and where FTS stops

Full-text search matches lexemes, so it is superb at word variants and terrible at typos. Search “postgers” and FTS returns nothing — the misspelling stems to a lexeme that appears in no document. For typo tolerance and substring/“contains” matching you reach for a different tool: the pg_trgm extension, which compares strings by their trigrams (overlapping 3-character slices) and measures similarity.

sql

CREATE EXTENSION IF NOT EXISTS pg_trgm;
-- a trigram GIN index also accelerates ILIKE '%x%' and similarity
CREATE INDEX articles_title_trgm ON articles USING GIN (title gin_trgm_ops);

SELECT title, similarity(title, 'postgers') AS sim
FROM articles
WHERE title % 'postgers'          -- % = above the similarity threshold; catches the typo
ORDER BY title <-> 'postgers'     -- <-> = trigram distance (1 - similarity)
LIMIT 5;

Think of them as complementary layers: FTS for linguistic word/phrase matching with ranking, pg_trgm for typos, autocomplete, and “contains” queries. Real search boxes often use both — FTS as the primary matcher, trigram similarity as a fallback when FTS returns too few rows.

Use FTS when…

  • Searching natural-language documents.
  • You want stemming and stop words.
  • You need relevance ranking.
  • Phrase and boolean queries matter.

Use pg_trgm when…

  • Users make typos (“postgers”).
  • You need substring / “contains”.
  • Fuzzy autocomplete on names/SKUs.
  • Accelerating ILIKE '%x%'.

Reach for a search engine when…

  • Facets, synonyms, per-field boosts at scale.
  • Huge corpora, custom analyzers, typo + rank together.
  • Search is the core product, not a feature.
  • → a dedicated engine (Elasticsearch, the sister course).
Don’t jump to Elasticsearch too early

Postgres FTS comfortably powers site search into the millions of documents, and it keeps search transactionally consistent with your data — no separate system to sync, no dual-write problem. Reach for a dedicated engine when you truly outgrow it (advanced relevance tuning, faceting, very large corpora), not by reflex. Adding Elasticsearch means owning replication, invalidation, and eventual consistency between two stores.

04 Worked problem

Build a ranked search over an articles table ▸

The schema. A blog with a growing table of articles; we want a search box over titles and bodies.

sql

CREATE TABLE articles (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title         text NOT NULL,
  body          text NOT NULL,
  published_at  timestamptz NOT NULL DEFAULT now()
);

The task. Given a user’s search text (e.g. postgres index), return the most relevant articles, best first, and keep it fast at millions of rows.

1 — The naive attempt (and why it’s wrong)

sql

SELECT id, title
FROM articles
WHERE title ILIKE '%postgres index%' OR body ILIKE '%postgres index%';

This is broken three ways at once. It can’t use an index (leading wildcards → Seq Scan on every row). It demands the two words be adjacent and in order, so an article titled “Index tuning in Postgres” never matches. And it returns rows in whatever order the scan produced them — no relevance. On a big table it is both slow and low quality.

2 — The fix: a generated tsvector + GIN, ranked

Materialize the search vector as a maintained column, weight the title above the body so title hits rank higher, and index it with GIN. Then match with websearch_to_tsquery and order by ts_rank.

sql

-- setweight labels lexemes A..D; ts_rank weighs A (title) heaviest
ALTER TABLE articles
  ADD COLUMN search tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
    setweight(to_tsvector('english', coalesce(body,  '')), 'B')
  ) STORED;

CREATE INDEX articles_search_gin ON articles USING GIN (search);

-- the query the app runs
SELECT a.id, a.title,
       ts_rank(a.search, q) AS rank
FROM articles a,
     websearch_to_tsquery('english', 'postgres index') AS q
WHERE a.search @@ q
ORDER BY rank DESC
LIMIT 10;

The comma join puts the parsed query in a one-row q so it is computed once and reused in both the WHERE and the ORDER BY. Follow how a match is found and ranked:

3 — Why it’s better (read the plan)

Ask Postgres how it runs the query. The GIN index turns the match into a bitmap lookup instead of a full scan:

explain (illustrative)

Limit  (cost=48.12..48.14 rows=10 width=48) (actual time=0.412..0.416 rows=8 loops=1)
  ->  Sort  (cost=48.12..48.16 rows=16 width=48) (actual rows=8 loops=1)
        Sort Key: (ts_rank(a.search, q.q)) DESC
        Sort Method: quicksort  Memory: 25kB
        ->  Nested Loop  (cost=12.30..47.88 rows=16 width=48) (actual rows=8 loops=1)
              ->  Function Scan on websearch_to_tsquery q  (cost=0.00..0.01 rows=1 width=32)
              ->  Bitmap Heap Scan on articles a  (cost=12.30..47.55 rows=16 width=48) (actual rows=8 loops=1)
                    Recheck Cond: (a.search @@ q.q)
                    Heap Blocks: exact=8
                    ->  Bitmap Index Scan on articles_search_gin  (cost=0.00..12.29 rows=16 width=0) (actual rows=8 loops=1)
                          Index Cond: (a.search @@ q.q)

Read it bottom-up. The Bitmap Index Scan on articles_search_gin walks the GIN posting lists for postgr and index and builds a bitmap of candidate rows — the table itself is never fully scanned. The Bitmap Heap Scan fetches just those pages and its Recheck Cond confirms @@ on each. The parsed query rides in via a one-row Function Scan under a Nested Loop, and a small Sort orders the survivors by ts_rank before Limit takes the top 10. Compare that to the naive version’s Seq Scan reading every row.

4 — Narrate it

“I don’t search text with LIKE; I search a normalized tsvector. I materialize title and body into a GENERATED tsvector column — title weighted A, body B so titles rank higher — and index it with a GIN inverted index. User text goes through websearch_to_tsquery so a search box never errors. The @@ match uses the GIN index (a Bitmap Index Scan, not a Seq Scan), and I ORDER BY ts_rank ... LIMIT so the most relevant rows come first. It stays transactionally consistent with the data because the vector is generated from the same row.”

05 Drills

Graded drills & the traps

Work each one against the articles table from the worked problem. Write your answer before opening the solution.

Drill 1 — the Seq Scan that shouldn’t be (easy)

Your query WHERE search @@ websearch_to_tsquery('english','fox') is fast in dev but EXPLAIN on the 5-million-row production table shows Seq Scan on articles. What is missing, and which index type fixes it (and why not a b-tree)?

Try it first, then read

There is no GIN index on the search column, so @@ falls back to scanning and testing every row. A b-tree can’t help: it indexes whole ordered values, not the individual lexemes inside a vector. Create an inverted index:

sql

CREATE INDEX articles_search_gin ON articles USING GIN (search);

Why: GIN stores lexeme→row posting lists, so @@ becomes a Bitmap Index Scan. (GiST also supports @@ but is lossy and slower for this; GIN is the default choice for static-ish text.)

Drill 2 — the search that returns nothing (medium)

The search column was generated with to_tsvector('english', …). A teammate’s query WHERE search @@ to_tsquery('simple','running') returns zero rows even though many articles say “running.” Explain and fix.

Try it first, then read

Configuration mismatch. The document stored the lexeme run (the english stemmer folded “running”→run). But 'simple' does no stemming, so the query lexeme is running — which appears in no vector. Both sides must use the same config:

sql

WHERE search @@ websearch_to_tsquery('english', 'running')   -- 'run' matches 'run'

Why: stemming has to match on both sides or the lexemes never line up — a silent zero-results bug.

Drill 3 — rank it and highlight it (medium–hard)

Results come back in arbitrary order and the product team wants (a) best matches first and (b) a short highlighted snippet showing why each matched. Extend the query.

Try it first, then read

Order by ts_rank (or ts_rank_cd, which rewards term proximity) and build the snippet with ts_headline:

sql

WITH q AS (SELECT websearch_to_tsquery('english', 'postgres index') AS query),
top AS (
  SELECT a.id, a.title, a.body, ts_rank(a.search, q.query) AS rank
  FROM articles a, q
  WHERE a.search @@ q.query
  ORDER BY rank DESC
  LIMIT 10)
SELECT top.id, top.title, top.rank,
       ts_headline('english', top.body, q.query) AS snippet
FROM top, q
ORDER BY top.rank DESC;

Why & trap: ts_headline re-parses the original body text (not the vector), so it is expensive. In a flat query Postgres would run it for every matched row before the LIMIT; wrapping the match-rank-limit in the top CTE and calling ts_headline only in the outer query is what confines it to the 10 rows you actually return.

Drill 4 — the typo FTS can’t catch (hard)

A user searches postgers (a typo) and gets zero results, even though many articles are about Postgres. Why can’t FTS help, and what will?

Try it first, then read

FTS matches lexemes; “postgers” stems to a lexeme no document contains, so no amount of FTS tuning finds it. Typo tolerance is pg_trgm’s job — trigram similarity:

sql

CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX articles_title_trgm ON articles USING GIN (title gin_trgm_ops);

SELECT title, similarity(title, 'postgers') AS sim
FROM articles
WHERE title % 'postgers'
ORDER BY sim DESC LIMIT 5;

Why: trigrams (“pos”, “ost”, “stg”…) overlap heavily between “postgers” and “postgres,” so similarity is high. FTS and trigram are complementary layers, not competitors.

The traps, collected

  • No GIN index on the tsvector → every @@ is a Seq Scan. The most common FTS mistake.
  • Config mismatch between index and query (english vs simple) → stemming differs → silent zero results.
  • Non-immutable to_tsvector (config as a column, not a literal) → the GENERATED column / expression index is rejected. Pin the config to a literal.
  • No ranking → results come back in arbitrary heap order; add ORDER BY ts_rank ... DESC.
  • ts_headline over the whole table → it re-parses raw text; apply it only to the already-LIMITed page.
  • Expecting FTS to fix typos → that is pg_trgm’s job; FTS handles word variants, not misspellings.
  • SELECT * drags the fat tsvector column back to the app for nothing; select only the columns you show.

Where this shows up next: the same “derive an index structure and keep it consistent with the source” pattern reappears when we sync Postgres to an external search engine via CDC in Phase 8 — and it is the whole reason the sister Elasticsearch course exists.

★ Review

Summary & self-test

One idea to carry: full-text search replaces a byte-substring test with a linguistic match — normalize both the document and the query into lexemes, match with @@, back it with a GIN inverted index, and rank with ts_rank. LIKE asks “does this string contain that string”; FTS asks “does this document match this intent,” quickly and in ranked order.
