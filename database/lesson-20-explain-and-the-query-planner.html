EXPLAIN & the Query Planner

This is the single most-used debugging skill in the whole course. When a query is slow, you don’t guess — you ask Postgres to show its work with EXPLAIN, read the plan tree it chose, and compare what it expected to what actually happened. By the end you’ll read a plan bottom-up, name every node, spot the tell-tale gap between estimated and actual rows, and turn a full-table scan into an index scan on purpose.

Original study notes. Written from scratch for engineers preparing for interviews and real production systems. Examples are PostgreSQL (PG 17/18); the plan output shown is illustrative but uses real node types and numbers you can reproduce on your own tables. 00 The tool

The planner shows its work

Every SQL statement you write is a request, not a recipe. You said what rows you want; the planner decides how to get them — which index (if any), which join algorithm, in which order. EXPLAIN is the window into that decision. Put it in front of any query and Postgres prints the plan it would run, annotated with cost and row estimates — without executing anything:

sql

EXPLAIN
SELECT * FROM orders WHERE customer_id = 42;

That estimate-only form is fast and safe, but it is a prediction. To learn the truth, add ANALYZE: Postgres actually runs the query and records actual time, rows, and loop counts alongside its guesses. Add BUFFERS to see how many 8 KB pages it touched in cache versus on disk:

sql

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 42;
ANALYZE runs it — wrap writes in a transaction

EXPLAIN ANALYZE executes the statement for real. On a SELECT that’s harmless; on an UPDATE/DELETE/INSERT it actually modifies your data. To profile a mutating statement safely, run it inside a transaction and roll back:

sql

BEGIN;
EXPLAIN (ANALYZE, BUFFERS)
UPDATE orders SET status = 'shipped' WHERE id = 42;
ROLLBACK;   -- the plan ran & timed for real; ROLLBACK undoes the write

The output looks like an indented list, but it is really a tree. Each indented line is a node — a scan, a join, a sort — and its children are the nodes indented one level deeper beneath it. The crucial reading rule, which trips up everyone at first: a plan executes bottom-up. The most-indented leaves run first and hand their rows to their parents; the top line is the last thing that happens, the node whose rows are returned to you. Read it like a call tree evaluated inside-out, not like a program run top-to-bottom.

Two questions this lesson answers

Nearly every “why is this slow?” reduces to two reads of the plan. (1) What scan/join did it choose, and was there a cheaper option it missed? — usually a Seq Scan where an Index Scan belonged. (2) Did reality match the estimate? — a big gap between estimated and actual rows means the planner was working from bad statistics and likely picked the wrong plan downstream. Master those two and you’ve mastered the tool.

01 Reading it

Reading the plan tree ▸

Let’s read a real plan. Suppose we want the ten biggest line-items across all orders, joining order_items to products to compute a value, sorted, top ten. Here is the EXPLAIN ANALYZE output — don’t panic at the width, we’ll walk it from the leaves up:

illustrative

Limit  (cost=6812.34..6812.36 rows=10 width=28) (actual time=48.11..48.13 rows=10 loops=1)
  ->  Sort  (cost=6812.34..6937.34 rows=50000 width=28) (actual time=48.10..48.11 rows=10 loops=1)
        Sort Key: ((oi.qty * p.price)) DESC
        Sort Method: top-N heapsort  Memory: 27kB
        ->  Hash Join  (cost=27.00..4200.00 rows=50000 width=28) (actual time=0.42..38.90 rows=50000 loops=1)
              Hash Cond: (oi.product_id = p.id)
              ->  Seq Scan on order_items oi  (cost=0.00..1834.00 rows=50000 width=12) (actual time=0.01..12.30 rows=50000 loops=1)
              ->  Hash  (cost=17.00..17.00 rows=800 width=20) (actual time=0.39..0.39 rows=800 loops=1)
                    ->  Seq Scan on products p  (cost=0.00..17.00 rows=800 width=20) (actual time=0.01..0.18 rows=800 loops=1)
Planning Time: 0.204 ms
Execution Time: 48.203 ms

Every node carries the same two annotations. The first parenthesis is the estimate: cost=startup..total (abstract units, not milliseconds), rows= how many the planner expects, width= average bytes per row. With ANALYZE, the second parenthesis is the truth: actual time=first_row..last_row (ms), rows= how many really came out, and loops= how many times this node executed. Step through how rows flow upward:

Two reading habits fall out of that. First, the top-N heapsort line and the Limit cooperating: notice the Sort’s actual rows=10, not 50,000 — because a LIMIT above a Sort lets Postgres keep only the top ten in a small heap instead of fully sorting. Second, look at where the time is: the Hash Join’s actual time reaches 38.9 ms and the Sort finishes at 48.1 ms, so most of the wall-clock is the join scanning 50,000 rows. The plan didn’t just tell you the shape — it told you the bottleneck.

The four numbers to read on every node

cost (relative, for comparing plans — never a time), rows (estimate) versus actual rows (truth), and loops. A node’s actual time is per loop — the real work is time × loops. We’ll lean on the estimate-vs-actual comparison in the next section; it is the master diagnostic.

02 The vocabulary

The nodes you’ll see

A plan is built from a small alphabet of node types. You don’t need to memorize their internals to debug — you need to know, at a glance, what each one signals. Here is the working set, grouped by job. One line each:

Scans (get rows)

  • Seq Scan — reads every page. Right for tiny tables or when most rows match; a red flag on a big table with a selective filter.
  • Index Scan — walk the index, then fetch each matching heap row (random I/O). Good for a few rows.
  • Index Only Scan — all needed columns are in the index and the page is all-visible, so it skips the heap entirely.
  • Bitmap Index + Bitmap Heap Scan — many matches: build a bitmap of row locations, then read pages in physical order.

Joins (combine)

  • Nested Loop — for each outer row, probe the inner side. Great when the outer side is tiny; watch loops.
  • Hash Join — hash the small side, probe with the big side. Equality joins only; the usual choice for large sets.
  • Merge Join — both inputs arrive sorted, then zip together. Good when the data is already ordered.

Shaping & more

  • Sort / Incremental Sort — order rows; the incremental form reuses an already-sorted prefix.
  • HashAggregate / GroupAggregate — GROUP BY via a hash table, or via already-sorted groups.
  • WindowAgg — computes window functions over ordered partitions.
  • Limit — stop once N rows are produced. Gather — collect rows from parallel worker processes.

A few pairings are worth internalizing because they show intent. Bitmap scans appear when a filter matches too many rows for a plain Index Scan (random fetches) but too few for a Seq Scan — the planner compromises. A Nested Loop over an Index Scan inner side is the classic “lookup per outer row” shape, and it’s excellent right up until the outer side turns out to be huge (that’s the disaster in the next section). And a Sort feeding a Merge Join or a GroupAggregate is often the node you can delete by adding the right index — the data was already ordered, you just didn’t give Postgres a way to know.

Parallelism reads a little differently

When you see Gather near the top with Parallel Seq Scan below it, the work was split across worker processes. Under ANALYZE, the child node’s rows are per worker; multiply by loops (and remember the leader helps too) to reconcile the totals. Don’t read a Parallel Seq Scan’s per-worker row count as the whole-table count.

03 The master tell

Estimate vs actual — the tell ▸

Here is the one diagnostic that finds more bad plans than all the others combined: on every node, compare the planner’s rows= estimate with the actual rows= truth. When they’re close, the plan is standing on solid ground. When they diverge by 10×, 100×, or 1000×, the planner made its choices believing a number that turned out to be wildly wrong — and a bad estimate at the bottom of the tree cascades into a bad join at the top. Watch it unfold:

The fix is the lesson’s deepest idea: you don’t fix the plan, you fix the inputs the planner reasons from. Postgres has no query hints. When estimates are off, the cause is almost always stale or missing statistics — so you run ANALYZE to refresh them, raise default_statistics_target (or the per-column target) on a skewed column, or add CREATE STATISTICS for correlated columns the planner wrongly assumes are independent. Correct the numbers and the planner re-derives a good plan on its own.

Two more tells on the same node

Rows Removed by Filter: a large value means the node read a pile of rows only to throw them away — the filter isn’t being served by the index (or there’s no useful index at all). Buffers (shown by default under ANALYZE in PostgreSQL 18): shared hit= is pages found in cache, shared read= is pages fetched from disk. A ballooning read= is your query pounding storage — often the same root cause as the estimate gap.

04 Worked problem

Worked: diagnose a slow query ▸

Time to do it end to end. Here is the table and the query; we’ll read the slow plan, name the smoking gun, apply the fix, and re-read the improved plan.

1 · The schema

sql

CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint      NOT NULL,
  status      text        NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
-- ~200,000 rows loaded; only the PRIMARY KEY on id has an index so far.

2 · The task

Fetch one customer’s open orders — a bread-and-butter application query:

sql

SELECT id, created_at
FROM   orders
WHERE  customer_id = 42
  AND  status = 'open';   -- exactly 4 rows match, out of 200,000

3 · The naive plan — and why it’s slow

There is no index on customer_id or status, so the planner has exactly one option. Run EXPLAIN (ANALYZE, BUFFERS):

illustrative

Seq Scan on orders  (cost=0.00..5000.00 rows=4 width=16) (actual time=0.28..41.03 rows=4 loops=1)
  Filter: ((customer_id = 42) AND (status = 'open'))
  Rows Removed by Filter: 199996
  Buffers: shared read=2000
Planning Time: 0.12 ms
Execution Time: 41.06 ms

Read it: a single Seq Scan node. Its estimate (rows=4) is actually correct — this is not a statistics problem, it’s a missing-index problem. The tell is Rows Removed by Filter: 199996: to find 4 matching rows, Postgres read and discarded almost every row in the table. Buffers: shared read=2000 confirms it touched all ~2,000 pages, from disk. The work is O(table) when it should be O(matches).

4 · The fix

Both predicates are equalities, so a plain composite B-tree is exactly right. Put the two equality columns in the index:

sql

CREATE INDEX orders_cust_status_idx
  ON orders (customer_id, status);

5 · The improved plan

Re-run the exact same EXPLAIN (ANALYZE, BUFFERS):

illustrative

Index Scan using orders_cust_status_idx on orders  (cost=0.42..8.52 rows=4 width=16) (actual time=0.03..0.04 rows=4 loops=1)
  Index Cond: ((customer_id = 42) AND (status = 'open'))
  Buffers: shared hit=4
Planning Time: 0.21 ms
Execution Time: 0.06 ms

Now the node is an Index Scan. The predicates moved from Filter to Index Cond — the crucial difference: the index navigates straight to matching rows instead of reading everything and filtering. Rows Removed by Filter is gone (nothing to remove), and Buffers dropped to shared hit=4 — four pages, all from cache. Step through the before/after:

6 · Narrate it

Say it out loud, because this is exactly the sentence an interviewer wants: “The slow plan was a Seq Scan with a Filter, and ‘Rows Removed by Filter: 199,996’ told me it was reading the whole 200,000-row table to return 4 rows — a missing-index problem, not a stats problem, since the row estimate was already correct. I added a composite B-tree on the two equality columns, (customer_id, status). The new plan is an Index Scan whose Index Cond does the selection, so Rows Removed by Filter disappears and Buffers falls from 2,000 disk reads to 4 cache hits — about a 1,000× drop in pages touched, and roughly 41 ms to 0.06 ms.” Notice what made the diagnosis fast: you didn’t guess — you read two lines of the plan.

05 Drills & traps

Graded drills + traps

Reason each one out before opening the callout. Assume the orders table from the worked problem unless a drill says otherwise.

Drill 1 — the Seq Scan that shouldn’t be

You see this on a 5-million-row table. What is wrong, and what’s the fix?

illustrative

Seq Scan on events  (cost=0.00..96000.00 rows=38 width=40) (actual time=0.05..612.4 rows=38 loops=1)
  Filter: (user_id = 991234)
  Rows Removed by Filter: 4999962
  Buffers: shared read=42000
Try it first, then read

The estimate is right (rows=38 matches actual), so it is a missing-index problem, not a stats one. The proof is Rows Removed by Filter: 4,999,962 — it read almost all 5M rows to find 38. Fix:

sql

CREATE INDEX events_user_idx ON events (user_id);

Why: a highly selective equality on an unindexed column forces a full scan; a B-tree turns it into an Index Scan that visits only the ~38 matching rows.

Drill 2 — fingerprint a stats problem

This one is not a missing index. What broke, and what’s the fix?

illustrative

Nested Loop  (cost=0.71..48.20 rows=1 width=64) (actual time=0.9..2210.5 rows=61000 loops=1)
  ->  Index Scan on orders o  (cost=0.42..40.1 rows=1 width=16) (actual time=0.3..38.7 rows=61000 loops=1)
        Index Cond: (status = 'open')
  ->  Index Scan on customers c  (cost=0.29..8.1 rows=1 width=48) (actual time=0.03..0.03 rows=1 loops=61000)
Try it first, then read

The outer scan is estimated rows=1 but actually returns 61,000 — a 61,000× error. Believing “1”, the planner chose a Nested Loop, whose inner Index Scan then runs loops=61000 times. The fingerprint is estimate ≈ 1 vs actual huge on the driving node. Fix the stats, not the plan:

sql

ANALYZE orders;
-- if 'open' is common & skewed, raise its stats target (grows the MCV list):
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;

Why: with a correct estimate (~61,000), the planner switches to a Hash Join and stops running the inner side 61,000 times.

Drill 3 — find the truly expensive node

In Drill 2’s plan, which node actually costs the 2.2 seconds — the outer scan (38.7 ms) or the inner one (0.03 ms)?

Try it first, then read

The inner Index Scan — because its actual time is per loop. Multiply by loops: 0.03 ms × 61,000 ≈ 1,830 ms, the bulk of the runtime. The outer scan’s 38.7 ms runs once. Why: a node’s displayed time is one execution; the real cost of a Nested Loop’s inner side is time × loops. Reading loops is the difference between blaming the wrong node and finding the real one.

Drill 4 — read the Buffers line

Same query, two runs. Run A: Buffers: shared hit=4200. Run B (right after): Buffers: shared hit=4200 read=0. Then someone restarts Postgres and Run C shows Buffers: shared read=4200. What changed, and is the query itself slower?

Try it first, then read

hit = pages served from the shared-buffer cache (fast, RAM); read = pages fetched from disk/OS. The query touched the same 4,200 pages every time — it is doing the same amount of logical work. Run C is slower only because the cache was cold after the restart, so those pages came from disk. Why: hit+read (total pages) measures the query’s work; the hit-vs-read split measures cache warmth, not query quality. To make it durably faster you reduce total pages (a better index), not just warm the cache.

Traps to avoid

• Reading top-down. The top line runs last. Start at the deepest leaves and work up, or you’ll blame the wrong node.
• Treating cost as milliseconds. cost is in abstract planner units for comparing plans. Real time is only in actual time under ANALYZE.
• Ignoring loops. actual time and rows are per loop. Always multiply by loops before deciding a node is cheap.
• Running ANALYZE on a mutating query without a transaction. EXPLAIN ANALYZE executes it — an UPDATE/DELETE/INSERT really runs. Wrap it in BEGIN … ROLLBACK.
• Confusing a missing index with bad stats. Estimate = actual but slow → add an index. Estimate wildly ≠ actual → fix statistics. They need opposite fixes.
• Chasing the biggest cost instead of the biggest gap. The node that’s slow is often the one whose estimate was most wrong, not the one with the largest printed number.

★ Review

Summary & self-test

The whole lesson compresses to one habit: when a query is slow, read its plan — bottom-up, node by node — and ask two questions: did it pick the right scan/join, and did reality match the estimate? The answer points at the fix (an index, or better statistics), and you never had to guess.

Self-test before you move on

Cover the notes and answer aloud:
(1) What’s the difference between EXPLAIN and EXPLAIN ANALYZE, and why must you wrap an UPDATE in a transaction to profile it?
(2) In which order does a plan execute, and which line returns rows to the client?
(3) On one node you see rows=5 but actual rows=50000. What does that gap tell you, and what’s the fix — index or statistics?
(4) A Nested Loop’s inner Index Scan shows actual time=0.03 loops=61000. How much time did it really cost, and why is loops the key?
(5) You see Rows Removed by Filter: 199996 on a Seq Scan whose estimate was correct. Missing index or bad stats? What do you do?
(6) In PG18’s Buffers line, what do shared hit and shared read mean, and which one tells you the query is doing too much work (vs just running cold)?
