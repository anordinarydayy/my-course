Tables, Types & Constraints

A table definition is not a suggestion — it is a contract. Every column names a fact, gives it a type, and can attach rules the database enforces on every single write. Get that contract right and the DBMS rejects bad data at the door, so your application never has to trust itself. This lesson shows how the type system plus constraints become your first, cheapest line of defense — and why pushing invariants down into the schema beats scattering checks across every caller.

Original study notes. Written from scratch, and PostgreSQL-based (targeting PG 17/18). The examples are Postgres, but "make illegal states unrepresentable in the schema" is universal. 00 The contract

The table as a contract

Every CREATE TABLE is a promise about the shape of your data. Read one carefully and it tells you exactly what a valid row looks like — column by column, plus a few rules that span the whole row:

sql

CREATE TABLE account (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       text NOT NULL UNIQUE,
    status      text NOT NULL DEFAULT 'active'
                  CHECK (status IN ('active','suspended','closed')),
    balance     numeric(12,2) NOT NULL DEFAULT 0
                  CHECK (balance >= 0),
    created_at  timestamptz NOT NULL DEFAULT now()
);

Three things are happening at once. Each line is a column: a name and a type that fixes what values can even be written there. Attached to a column are its per-column constraints (NOT NULL, UNIQUE, CHECK, DEFAULT). And a constraint that spans several columns — a composite key, or a rule relating two columns — becomes a table-level constraint written on its own line. Types and constraints are the two halves of the contract: the type says what kind of thing, the constraint says which values are legal.

The design principle behind all of it has a name worth memorizing: make illegal states unrepresentable. If a status can only ever be one of three words, the schema should make a fourth word impossible to store — not merely discouraged. If a balance can never be negative, the row that tries should be rejected, not logged and cleaned up later. Every rule you can express in the schema is a rule no application code has to remember, re-implement, or get wrong.

Push invariants down, not up

An invariant enforced in the database holds for every writer — your API, a batch job, a one-off psql session, next year's microservice you haven't written yet. The same invariant enforced only in one service's code holds for exactly that code path, until someone opens a second door. Correctness that lives in the schema is correctness you can't accidentally bypass. So the rule of thumb is: if the database can enforce it, let it.

01 Types

Choosing the right type

The type is the cheapest constraint of all — it's checked before anything else and it costs you nothing at write time. Picking the right one is mostly about avoiding a handful of classic mistakes. Here are the families you'll reach for, and the traps beside each:

Whole numbers

  • integer holds ±2.1 billion — fine for most counts.
  • bigint for ids and anything that might grow; identity keys default to it.
  • Don't store a phone number or ZIP as an integer — those are text.

Money & exact

  • numeric(p,s) is exact decimal — the only right choice for money.
  • Never float/double for amounts: they're binary approximations.
  • Skip the money type too — it's locale-bound and inflexible.

Text, time & ids

  • Prefer text + a CHECK over varchar(n).
  • Always timestamptz, never timestamp.
  • boolean for yes/no; uuid for external ids.

The money one is not a style preference — it's arithmetic. Binary floating point can't represent most decimal fractions exactly, so the classic demonstration bites the moment you add two "round" numbers:

sql

SELECT 0.1::float8 + 0.2::float8;    -- 0.30000000000000004  ✗
SELECT 0.1::numeric + 0.2::numeric;  -- 0.3                 ✓

-- store money as exact decimal, not an approximation
amount   numeric(12,2) NOT NULL CHECK (amount >= 0)

A few more rulings that save real bugs. On text: prefer text and enforce length with a CHECK rather than varchar(50) — Postgres stores them identically, but changing a varchar(n) limit later is a heavier operation than adjusting a check, and text keeps you from guessing a number you'll regret. On time: always use timestamptz. Despite the name it does not store a timezone — it stores an absolute instant in UTC and converts on the way in and out, so two servers in two timezones agree on "when." Plain timestamp stores wall-clock digits with no anchor, and someday two of them will be an hour apart and nobody will know which is right.

For identifiers, uuid is the go-to when an id must be generated by clients or be unguessable. Random v4 UUIDs scatter across the index and hurt insert locality; the newer uuidv7() (available in PG 18) embeds a timestamp prefix so new rows cluster at the end of the index — the locality of a serial with the global-uniqueness of a UUID. Finally, when a column is a small fixed set of words (a status, a role), you have two good options: a Postgres enum type, or a plain lookup table referenced by a foreign key. The trade-off — enums are compact but awkward to reorder; lookup tables carry metadata and evolve freely — is a whole discussion we save for L08. For now, a CHECK (status IN (...)) covers most cases with zero ceremony.

Pick this, not that

numeric for money, not float.  timestamptz, not timestamp.  text+CHECK, not varchar(n).  bigint identity, not a 4-byte integer you'll overflow.  uuidv7(), not random v4 when you care about index locality. Each "not" is a bug someone has shipped to production.

02 Guardrails

Constraints as guardrails ▸

If the type says what kind of value, constraints say which of those values are actually legal — and they are enforced on every INSERT and every UPDATE, declaratively, whether the write comes from your app or a stray script. The six you'll use constantly:

  • NOT NULL — the column must hold a value; nothing is not allowed.
  • CHECK (expr) — an arbitrary boolean rule the row must satisfy, e.g. price > 0.
  • UNIQUE — no two rows may share this value (backed by a unique index).
  • DEFAULT — a value to use when the writer supplies none (not a rejection — a fill-in).
  • PRIMARY KEY — the row's identity: NOT NULL + UNIQUE, one per table.
  • FOREIGN KEY — this value must match an existing row in another table (referential integrity).

Picture a write as a row that has to walk a gauntlet of gates on its way into storage. A good row clears every gate. A bad row is stopped at the exact gate whose rule it breaks — and it never touches the table. Step through it:

Two things to notice. First, the row is rejected before it is stored — there is no half-written, later-to-be-cleaned-up state; the whole write fails atomically and the table is untouched. Second, the database returns a precise error naming the violated constraint, which is exactly what your application catches and turns into a friendly message. You didn't write any of that checking logic. You declared the rules once, and the engine enforces them forever.

Declarative, not procedural

You never wrote "if email is null, reject." You wrote NOT NULL and the engine figured out the rest — including running the check on writes you'll add years from now. That's the payoff of a declarative contract: the rule and its enforcement are the same line of code, and it can't drift out of sync with an if statement buried in a service.

03 Generated

Let the database fill it in ▸

Some columns you should never send from the application at all — because the database can produce them more reliably than you can. There are three ways to let it fill in a column, and knowing which is which is the difference between clean inserts and subtle drift:

  • GENERATED ALWAYS AS IDENTITY — the modern replacement for SERIAL. The database hands out the next number for the primary key. (Prefer it over SERIAL: it's SQL-standard and blocks accidental manual overrides. Note it's NOT NULL but not unique on its own — you still declare PRIMARY KEY.)
  • GENERATED ALWAYS AS (expr) STORED — a computed column derived from other columns in the same row, recomputed on every write. PG 18 adds a VIRTUAL variant that computes on read instead of storing.
  • DEFAULT — a value used only when you omit the column: DEFAULT now() for timestamps, DEFAULT gen_random_uuid() or DEFAULT uuidv7() for ids.

sql

CREATE TABLE app_user (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       text NOT NULL UNIQUE,
    first_name  text NOT NULL,
    last_name   text NOT NULL,
    full_name   text GENERATED ALWAYS AS (first_name || ' ' || last_name) STORED,
    signup_id   uuid NOT NULL DEFAULT gen_random_uuid(),
    created_at  timestamptz NOT NULL DEFAULT now()
);

The division of labor is the whole point. You send only the facts you actually know — the human's email and name. The database owns everything it can derive or guarantee: the surrogate identity, the creation timestamp, the concatenated full_name. Because GENERATED ALWAYS means always, you literally cannot insert a wrong full_name — there's no code path that lets full_name disagree with the first and last name it's built from. That's another illegal state made unrepresentable.

Why generated beats app-side computation

Computing full_name in the application works — until a second service, a data migration, or a manual fix writes the row a different way and the derived value drifts. A generated column can't drift: it is recomputed by the engine from the same source, on every write, from every writer. The same argument is why DEFAULT now() beats passing a client timestamp: the database's clock is the single source of truth.

04 Schema vs app

Why the schema beats an app check ▸

Here is the argument that convinces the skeptic. "I don't need a UNIQUE constraint — I check for the email in my code before inserting." That check is a SELECT followed by an INSERT, and between those two statements lies a gap that another session can slip through. Two users register the same email at the same instant; both SELECT and see nothing; both INSERT; now you have a duplicate your code swore was impossible. That's a race condition, and it is invisible in testing and inevitable in production. Watch it happen:

The lesson generalizes: constraints don't race; app checks do. A UNIQUE constraint isn't a SELECT you run before writing — the uniqueness test happens inside the insert, under a lock the second writer can't sneak past. There is no gap to exploit. One line of DDL replaces a fragile, race-prone dance of application code, and it protects every writer at once. When two things must not both happen, that "must not" belongs in the schema.

Two practical extensions. First, CHECK vs trigger: a CHECK validates one row against a fixed boolean expression and is declarative and cheap — reach for it first. Only when a rule must consult other rows or tables (which a plain CHECK can't) do you fall back to a trigger, accepting the extra complexity. Second, adding a constraint to a live table without a long lock: validating millions of existing rows can block writes, so Postgres lets you add the constraint NOT VALID (it applies to new writes immediately, skipping the back-scan) and then VALIDATE it separately with a gentler lock:

sql

-- 1. enforce on new writes now, skip the expensive full-table scan
ALTER TABLE orders
  ADD CONSTRAINT orders_amount_pos CHECK (amount > 0) NOT VALID;

-- 2. later, verify the existing rows under a lighter lock
ALTER TABLE orders VALIDATE CONSTRAINT orders_amount_pos;
The one-line takeaway

Any invariant you can state as a constraint is enforced atomically, inside the write, for every session — which is precisely what an application-level check-then-act can never promise. If correctness matters, spell it in the schema; if it merely needs to be convenient, then and only then consider doing it in code.

05 Design

Design it: a users + orders schema

Let's put the whole lesson to work by narrating a small design, choice by choice. The domain is the most ordinary thing there is — users and their orders — but every line is a deliberate decision about type and constraint:

sql

CREATE TABLE users (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       text NOT NULL,
    created_at  timestamptz NOT NULL DEFAULT now()
);
-- case-insensitive uniqueness: Ana@X.com and ana@x.com are the same person
CREATE UNIQUE INDEX users_email_lower ON users (lower(email));

CREATE TABLE orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id     bigint NOT NULL REFERENCES users(id),
    amount      numeric(12,2) NOT NULL CHECK (amount > 0),
    status      text NOT NULL DEFAULT 'pending'
                  CHECK (status IN ('pending','paid','shipped','cancelled')),
    created_at  timestamptz NOT NULL DEFAULT now()
);
-- Postgres does NOT auto-index FK columns — add it yourself
CREATE INDEX orders_user_id ON orders (user_id);

Read it as a chain of justified choices. The identity primary key gives each row a stable, meaningless surrogate id — meaningless on purpose, so it never has to change when a real-world attribute does. amount is numeric(12,2) because it's money and money is exact, and it carries a CHECK (amount > 0) because a zero or negative order is nonsense that should be impossible, not merely unusual. Both created_at columns are timestamptz DEFAULT now(): absolute instants in UTC, stamped by the database's own clock so no client can lie about when.

The status column shows the cheap way to constrain a small set of words — CHECK (status IN (...)) — with a DEFAULT 'pending' so a fresh order starts in the right state without the caller thinking about it. (If the set grew or needed metadata like a display label, this is where you'd graduate to an enum or a lookup table — the L08 discussion.) Email uniqueness is deliberately case-insensitive: a plain UNIQUE would treat Ana@X.com and ana@x.com as two people, so we build the constraint on lower(email) instead. And the relationship — orders.user_id REFERENCES users(id) — makes an orphaned order (one pointing at no real user) impossible; the database refuses it. The final line matters more than it looks: Postgres does not automatically index foreign-key columns, so we add orders_user_id ourselves — without it, "find this user's orders" and cascading delete checks both scan the whole table.

Where this shows up next

Every choice here opens a later door. Keys — surrogate vs natural, composite, and what a primary key really guarantees — get their deep dive in L05. Normalization — why users and orders are separate tables rather than one wide one — is L06. And the fact that NOT NULL is doing quiet, load-bearing work here (because NULL breaks intuition in ways that bite) is the subject of NULL logic in Phase 2. You've now built the contract; the rest of Phase 1 makes it airtight.

★ Review

Summary & self-test

The whole lesson compresses to one idea: a table definition is a contract, and the type system plus constraints are your cheapest, most reliable line of defense — push each invariant down into the schema so the database rejects bad data at the door, for every writer, on every write.
