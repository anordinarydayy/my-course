Sharding & Distributed Postgres

When a single primary can no longer hold your data or absorb your write rate, you shard: split rows across many nodes by a chosen shard key. The mechanics are easy; the judgement is not. The two decisions that make or break a sharded system are which key you shard on and how much you pay when a query can't use it — and both are the whole subject of this lesson.

00 Orientation

When one node runs out of room

You have already scaled Postgres the sane ways: a bigger instance, tuned indexes, read replicas for read-heavy traffic. Those buy you a long runway. But two walls eventually appear that vertical scaling and replicas cannot climb. The first is data size — the working set no longer fits, indexes bloat, vacuum falls behind, backups take a day. The second is write throughput — every replica still funnels all writes through the one primary, so replicas do nothing for a write ceiling. When you hit either wall, the only way forward is to spread the rows across multiple machines. That is sharding.

The idea is simple to state: choose a column — the shard key (also called the distribution or partition key) — and use a deterministic function of it (a hash, or a range) to decide which node each row lives on. Every row has exactly one home. A query that carries the shard key can be routed to the one node that owns the matching rows; a query that doesn't must be broadcast to all nodes and its partial answers stitched together.

Shard late, and only when you must

Sharding is the most expensive scaling decision you can make: it complicates every query, every join, every transaction, every backup, and every schema change. Exhaust the cheaper options first — scale up the box, add the right indexes, offload reads to replicas, archive cold data with partitioning. Reach for sharding only when a single primary genuinely cannot hold the data or the write rate. Sharding too early is a classic self-inflicted wound — you pay all the complexity for none of the need.

Note the relationship to two things you already know. Partitioning (Phase 6) splits one table across many child tables inside one server; sharding splits data across many servers. And replication (earlier this phase) copies the same rows to more nodes for availability and read scaling; sharding puts different rows on different nodes for capacity. Real systems combine them: each shard is itself a replicated primary-plus-standbys.

01 The mechanism

Sharding by key ▸

Picture a multi-tenant SaaS: every row belongs to some tenant_id. If you shard on tenant_id with a hash function, each tenant's rows deterministically land on one shard, and the number of shards can be far larger than the number of physical nodes (Citus keeps 32 shards per table by default, spread across the workers, so you can rebalance without re-hashing). The payoff is that any query filtering on tenant_id becomes a single-shard query — routed to exactly one node, where it runs like ordinary local Postgres.

The crucial property is that the shard key is baked into the physical layout. It is not just another indexed column — it decides which machine the row is on. That is why a well-chosen key feels magical (one hop, full local speed, perfect horizontal scaling) and a badly chosen one is a permanent tax: changing the shard key of a live distributed table means moving essentially every row.

Hash vs range sharding

Hash sharding (hash the key, then map the hash to a shard — Citus gives each shard a slice of the 32-bit hash space rather than a literal modulo) spreads rows evenly and kills hotspots, but destroys locality — adjacent keys scatter, so range scans fan out. Range sharding (key 1–1000 → shard A, 1001–2000 → shard B) keeps ranges local and makes archiving easy, but invites hotspots: if the key is monotonic (a timestamp, a serial id) every new write piles onto the last shard. Multi-tenant systems almost always hash on tenant_id; time-series systems often range on time. Pick for your access pattern, not by default.

02 The tax

The cost of crossing shards ▸

The single-shard query is the dream. The nightmare is its opposite: a query that cannot be routed. If the WHERE clause has no shard key — say you filter by status = 'paid' — the router has no way to know which shard holds the answer, so it must send the query to every shard, wait for all of them, and merge the results at the coordinator. This is scatter-gather (also called fan-out). It is not always bad — an analytics query wants to touch every shard in parallel — but on a hot OLTP path it multiplies your latency and load by the shard count and turns a distributed system back into a single, slow one.

The second source of cross-shard pain is joins. If two tables are sharded on different keys, joining them means one side's rows must be shuffled across the network to meet the other's. The cure is colocation: shard related tables on the same key so matching rows always live on the same node, and every join runs locally. Watch both the fan-out and the fix:

So the entire art of designing a sharded schema reduces to one goal: make your hot queries single-shard. Choose the key that appears in almost every query's WHERE, colocate the tables that get joined, and push the unavoidable fan-out queries (reports, admin dashboards) onto a schedule or a replica where their latency doesn't hurt anyone. Every cross-shard query on the critical path is a design smell worth a second look.

Three flavours of distributed query

Single-shard (keyed): routed to one node, runs at local speed — aim for this. Colocated multi-shard: touches several shards but each does independent local work with no cross-node shuffle — parallel and fine. Repartition / broadcast: rows must move between nodes to complete a join — the slow path, avoid on hot code. Knowing which one a query becomes, before you ship it, is the skill.

03 The tooling

Citus, and how to choose the key

Vanilla Postgres does not shard across machines by itself. Citus — an open-source extension, now maintained by Microsoft and installable with CREATE EXTENSION citus — turns a cluster of Postgres nodes into one distributed database. You keep writing ordinary SQL against a coordinator node; Citus stores the metadata (which shard lives on which worker), rewrites your query into per-shard tasks, ships them to the workers, and merges the results. It offers three table types you must learn to reach for:

  • Distributed tables — sharded across the workers by a distribution column. This is where your big, tenant-scoped data goes: SELECT create_distributed_table('orders', 'tenant_id').
  • Reference tables — small, shared lookup tables replicated in full to every worker, so any join to them stays local: SELECT create_reference_table('products'). Perfect for currencies, countries, plans, feature flags.
  • Local tables — ordinary tables that live only on the coordinator, for things that never need to scale (a small config table, migration bookkeeping).

Everything then hinges on the distribution column. A good shard key has three properties, and a bad key fails at least one of them:

High cardinality

  • Many distinct values, so rows spread across all shards.
  • A boolean or a status column is a disaster — two or three buckets.
  • tenant_id, user_id: thousands+ of values.

Even distribution

  • No single value dominates — avoid skew and hotspots.
  • One giant tenant on one shard = that shard melts while others idle.
  • Watch for the “whale” customer; consider isolating it.

Matches the access pattern

  • The key is in nearly every query's WHERE.
  • That's what makes hot queries single-shard.
  • Multi-tenant → tenant_id is almost always right.

A few operational truths round it out. Citus keeps a fixed number of shards (32 per table by default) independent of the worker count, so adding a worker means rebalancing — moving whole shards to the new node with SELECT rebalance_table_shards(), which runs online but costs real I/O and takes time. The distribution column must be part of every primary key and unique constraint on a distributed table (Postgres can only enforce uniqueness within a shard). And a transaction that writes to rows on more than one shard is committed with two-phase commit under the hood — correct, but slower and subject to the same coordinator-failure risks you met with distributed transactions; keep writes single-shard when you can.

Multi-region is a different, harder problem

Sharding within one region scales capacity. Spanning regions for latency or disaster tolerance adds conflict resolution: if two regions accept writes to the same logical row, which wins? Active-active designs lean on last-write-wins (simple, silently loses data) or CRDTs (conflict-free replicated data types that merge deterministically). Most teams avoid true active-active and instead keep one write region with the others read-only. Treat multi-region active-active as a last resort, not a starting point.

04 Worked problem

Shard a multi-tenant app with Citus ▸

Let's do it end to end. A B2B SaaS has outgrown one primary: hundreds of thousands of tenants, and the orders table is billions of rows. We'll distribute it on tenant_id, keep a shared catalog as a reference table, then write the hot per-tenant query correctly and see what a careless version costs.

1 · The schema

sql

-- small shared catalog: replicated in full to every worker
CREATE TABLE products (
    product_id  bigint PRIMARY KEY,
    sku         text NOT NULL,
    name        text NOT NULL
);
SELECT create_reference_table('products');

-- big tenant-scoped tables: sharded by tenant_id
CREATE TABLE customers (
    tenant_id   bigint NOT NULL,
    customer_id bigint NOT NULL,
    email       text NOT NULL,
    PRIMARY KEY (tenant_id, customer_id)   -- shard key must be in the PK
);
SELECT create_distributed_table('customers', 'tenant_id');

CREATE TABLE orders (
    tenant_id   bigint NOT NULL,
    order_id    bigint NOT NULL,
    customer_id bigint NOT NULL,
    product_id  bigint NOT NULL,
    total_cents bigint NOT NULL,
    placed_at   timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, order_id)
);
-- colocate_with keeps a tenant's orders on the SAME shard as its customers
SELECT create_distributed_table('orders', 'tenant_id',
                                colocate_with => 'customers');

2 · The task

For a tenant's dashboard: list that tenant's orders in the last 30 days, each with the customer's email and the product's name. This runs on every page load — it must be single-shard.

3 · The naive attempt (and why it hurts)

sql

-- NAIVE: no tenant_id filter; join on customer_id alone
SELECT o.order_id, c.email, p.name, o.total_cents
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
JOIN products  p ON p.product_id  = o.product_id
WHERE o.placed_at >= now() - interval '30 days';

Two things are wrong. There is no tenant_id in the WHERE, so Citus cannot prune to one shard — the query fans out to all 32. Worse, the customers join is on customer_id only, not the distribution column, so Citus cannot prove the matching customer sits on the same shard as the order; it must repartition — shuffle customers rows across the network to complete the join. You have turned a one-node lookup into a cluster-wide scatter with a shuffle on top.

4 · The fix

sql

-- FIXED: tenant_id prunes to one shard; join includes the colocation key
SELECT o.order_id, c.email, p.name, o.total_cents
FROM orders o
JOIN customers c
  ON c.tenant_id   = o.tenant_id       -- colocation key in the join
 AND c.customer_id = o.customer_id
JOIN products p ON p.product_id = o.product_id   -- reference table: local copy
WHERE o.tenant_id = 42
  AND o.placed_at >= now() - interval '30 days';

Now tenant_id = 42 lets the router hash once and target a single shard. The join carries c.tenant_id = o.tenant_id, so Citus knows the customer is colocated — the join runs locally. And products is a reference table, so its rows are already on that worker. The whole query executes on one node as plain local Postgres.

The tell is Task Count: 1: Citus routed the entire query to one shard (note the shard suffixes — orders_102042, products_102170 — real per-shard tables on worker-1). The naive version would instead show Task Count: 32 and, for the un-colocated join, a repartition or broadcast step. Same rows, same result — one node versus the whole cluster.

6 · Narrate it

“Because it's multi-tenant, I distribute customers and orders on tenant_id and colocate them, so one tenant's data lives on one shard. The shared catalog is a reference table, replicated everywhere, so joins to it are always local. The dashboard query filters on tenant_id = 42, which prunes to a single shard, and I include tenant_id in the join condition so Citus keeps the join colocated. EXPLAIN shows Task Count: 1 — it's a single-shard query running at local Postgres speed, so it scales horizontally: more tenants just means more shards, and each dashboard load still touches exactly one node.”

05 Drills

Graded drills & the trap list

Work each before reading the answer. They climb from “spot the bad key” to “design under skew.”

Drill 1 · The wrong shard key

A teammate distributes orders on order_id (its own primary key) with create_distributed_table('orders', 'order_id'), reasoning that it's unique and high-cardinality. Every tenant dashboard query then gets slow. Why — and what should the key have been?

Try it first, then read

order_id is high-cardinality and even, but it fails the third rule: it's not in the access pattern. Dashboard queries filter by tenant_id, not order_id, so with orders scattered by order_id hash, a single tenant's orders spread across all shards — every dashboard read becomes a scatter-gather. The key should be tenant_id, so a tenant's orders colocate on one shard. Why: the best shard key is the column in your hottest queries' WHERE, not the most-unique column.

Drill 2 · The query that forgot the key

Tables are correctly distributed on tenant_id. Support runs SELECT * FROM customers WHERE email = 'x@y.com' to find an account and complains it's slow. The fix isn't a new index. What is it, and what's the deeper lesson?

Try it first, then read

Even with an index on email, the query has no tenant_id, so Citus fans it out to all shards and each does an index lookup — N shard round-trips for one row. Add the shard key: WHERE tenant_id = 42 AND email = 'x@y.com' makes it single-shard. If support genuinely doesn't know the tenant, keep a small reference (or coordinator-local) lookup table mapping email → tenant_id, resolve it first, then do the keyed query. Why: in a sharded world, “which shard?” must be answerable from the query itself — an index can't save a keyless fan-out.

Drill 3 · Rebalancing and the whale

You add a third worker to relieve load, but one tenant (a huge customer) is 40% of all rows and pins one shard at 100% CPU while the new worker sits idle. Rebalancing shards evenly doesn't help. What's happening, and what are your options?

Try it first, then read

This is data skew: hash sharding distributes shards evenly, but if one tenant_id dominates, its single shard is a hotspot no rebalance can split (all its rows share one hash bucket). Options: (1) isolate the whale — Citus isolate_tenant_to_new_shard() moves that one tenant onto its own shard/node; (2) use a composite/finer key so a big tenant's rows spread (e.g. distribute on a (tenant_id) but partition the shard by time within it); (3) give the whale its own dedicated cluster. Why: even distribution is a property of your data, not just your hash — a single dominant key value is unshardable by that key alone.

Drill 4 · The cross-tenant analytic

Product wants “top 10 products by revenue across all tenants,” refreshed hourly. Written naively it's SELECT product_id, SUM(total_cents) FROM orders GROUP BY product_id ORDER BY 2 DESC LIMIT 10. Is fan-out wrong here? How do you serve it without hurting the dashboards?

Try it first, then read

Fan-out is correct and even good here — it's an analytic that legitimately touches all shards, and Citus parallelizes it: each worker computes a partial SUM (GroupAggregate/HashAggregate per shard) and the coordinator merges them (Task Count: 32). The problem is only where it runs. Don't let it compete with OLTP: run it on a schedule into a materialized result (or a rollup table), or point it at a read replica of the coordinator. Why: scatter-gather isn't inherently bad — it's bad on the hot path. Move unavoidable fan-out off the critical path rather than trying to eliminate it.

The trap list — memorize these

● Bad shard key: low cardinality, skewed, or not in your queries → hotspots or universal fan-out.
● Cross-shard joins: un-colocated tables force a network repartition → colocate on the same key.
● Queries missing the key: no shard key in WHERE → scatter-gather; an index can't fix it.
● Rebalancing cost: adding nodes moves whole shards (real I/O); skew can't be rebalanced away.
● Distributed transactions: multi-shard writes use 2PC under the hood — slower, coordinator-dependent; keep writes single-shard.
● Sharding too early: the biggest trap — scale up, index, and add replicas first; shard only when one node truly can't cope.

★ Review

Summary & self-test

The whole lesson compresses to one idea: sharding buys capacity by splitting rows across nodes on a shard key — and every design decision is about keeping your hot queries on one shard. Choose the key that lives in your queries' WHERE, colocate the tables you join, push fan-out off the hot path, and shard only when you genuinely must.
