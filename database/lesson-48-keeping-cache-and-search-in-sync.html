Keeping Cache & Search in Sync with the DB of Record

Postgres is your system of record; Redis and Elasticsearch are derived copies of it. The moment you keep two copies of the same fact, they can disagree — and every "the search results are stale" or "I edited it but the cache still shows the old value" bug is that disagreement leaking to users. This lesson turns the drift problem you met at row scale into a systems-scale discipline: understand the invalidation race, pick a sync strategy on purpose, and drive derived stores from an ordered, idempotent change feed.

Original study notes. Written from scratch for engineers who want database depth that pays off in interviews and in real systems. Examples use PostgreSQL (PG 17/18) alongside Redis and Elasticsearch, but the ideas — a single source of truth, eventual consistency, idempotency, ordering — are universal. 00 Orientation

One source of truth, two derived copies

By this phase you accept a hierarchy that a lot of production incidents are caused by forgetting: there is exactly one system of record, and everything else is a cache of it. Postgres holds the authoritative rows. Redis holds a fast copy of some of them so you don't hit the database for every read. Elasticsearch holds a reshaped copy — tokenized, denormalized, scored — so you can search in ways SQL is bad at. Both are derived: if you deleted them entirely and rebuilt from Postgres, nothing would be lost.

That framing carries a rule with real teeth: writes go to the record, never to a derived store first. A cache you write to directly is no longer a cache — it's a second source of truth you now have to reconcile. The whole job of this lesson is keeping the derived copies faithfully following the record, cheaply, and admitting up front that they will lag.

Postgres — record

  • The authoritative rows; ACID.
  • Every write commits here first.
  • If it's not here, it isn't true.

Redis — cache

  • A fast, partial copy of hot rows.
  • Read-mostly; disposable.
  • Correctness = knowing when to drop a key.

Elasticsearch — search

  • A reshaped copy for full-text/facets.
  • Denormalized documents, eventually in step.
  • Correctness = ordered, idempotent updates.

The hard part is not writing to two systems — it's the gap between them. That gap is the same drift problem you saw between a row and its computed value, only now the two copies live in different processes, on different machines, updated by different code paths. Everything below is about shrinking, bounding, and self-healing that gap.

The one rule to carry through

Design for eventual consistency, not perfect consistency. A derived store will be briefly stale; the engineering question is never "can I make it never stale?" (you can't, cheaply) but "how do I bound the staleness, guarantee it converges, and make sure a duplicate or out-of-order update can't make it diverge?"

01 The classic bug

The cache-aside invalidation race ▸

The default caching pattern is cache-aside (a.k.a. lazy caching): on a read, look in the cache; on a miss, read the database and populate the cache; on a write, update the database and invalidate (delete) the cache key so the next read reloads. It's simple and it's everywhere — and it has a famous race that produces a value that stays wrong indefinitely, not just briefly.

The trap is the order of two interleaved operations: a slow reader that read the old value but hasn't populated the cache yet, and a writer that updates the row and deletes the (empty) key. When the slow reader finally writes, it repopulates the cache with the value it read before the write. Step through the exact interleaving:

Notice why deleting the key on write is not enough on its own: the delete happened while the key was empty, and the stale write landed after it. The reader's SET has no way to know the value it holds is older than what's now in the database. Two things fix this cleanly, and you'll use both: a TTL so the poison self-heals within seconds (a safety net, not a strategy), and — the real fix — making the populate conditional on a version, so a write can only ever install a newer value, never an older one. Once the update carries a version, arrival order stops mattering; the same idea reappears verbatim for search in the worked problem.

Invalidate, don't update — and still bound it

On a write, prefer to DEL the key (invalidate) over SET-ing the new value. A DEL that loses the race just causes a cache miss and a fresh reload; a SET that loses the race installs stale data. But even DEL-on-write can't stop the read-repopulate race above — that's what the TTL and the version guard are for. "Always give cache entries a TTL" is the cheapest bug-limiter you will ever add.

02 Strategies

Three ways to keep a copy in step ▸

There are three broad strategies for keeping a derived store in sync, and they trade freshness against complexity. Know all three by name; real systems layer them.

Cache-aside + TTL

  • Lazy: populate on miss, invalidate on write.
  • Simplest; the default. Has the race above.
  • TTL bounds staleness and self-heals drift.

Write-through

  • The write path updates DB then cache together.
  • Fresher reads; but it's a dual-write.
  • A crash between the two steps drifts.

CDC-driven sync

  • DB commit → change feed → update copies.
  • No dual-write; ordered, replayable.
  • Most robust; more moving parts.

The third one deserves the spotlight, because it dissolves the two problems the others fight. Instead of the application trying to write two systems atomically (which it cannot do — that's the dual-write problem from the outbox lesson), the change is captured from the committed WAL — by logical decoding, or by a transactional outbox row written in the same transaction as the data. A relay reads that single, ordered stream and pushes it to the cache and the search index. Watch the shape:

The elegance is that the DB commit is the only atomic action. Everything downstream is a faithful projection of committed facts, replayed in order. If a consumer crashes, it resumes from its last position and re-applies — which is safe precisely because each update is idempotent. You get no lost events (the change is durably in the WAL/outbox), no dual-write, and a natural place to add a second consumer later (analytics, another cache) without touching the write path.

When each strategy is the right call

Reach for cache-aside + TTL first — for a read cache it's usually enough, and the TTL forgives a lot. Use write-through only when a few seconds of staleness is unacceptable and you can tolerate the dual-write risk (or wrap it in the outbox). Graduate to CDC-driven sync when you have multiple derived stores, need ordering/replay, or the search index is big enough that rebuilding it from a change feed is your operational lifeline.

03 Hazards

Six hazards to design for up front

Whichever strategy you pick, the same handful of hazards will find you. Name them now so they're checklist items, not 2 a.m. surprises.

  • TTL is a safety net, not a plan. A short TTL guarantees any drift self-heals within its window, so a missed invalidation is a bounded bug instead of a permanent one. But TTL alone means every key is stale up to its lifetime and reloads cost a DB hit; it complements correct invalidation, it doesn't replace it.
  • Versioned keys beat blind overwrites. Attach a monotonically increasing version (a row version column, an updated_at, or the WAL LSN) to every cached/indexed value, and only install an update if its version is newer. This is what makes updates commutative under reordering — the antidote to the race in FIG. 1.
  • The expiry stampede (thundering herd). When a hot key expires, every concurrent reader misses at once and stampedes the database with identical rebuild queries — sometimes enough to fall over. Defenses: request coalescing (single-flight — one rebuild, everyone else waits), jittered TTLs so keys don't expire in lockstep, early/probabilistic refresh before expiry, and stale-while-revalidate (serve the old value while one worker refreshes).
  • Out-of-order updates. Two updates to the same row can be applied to a derived store in the wrong order (retries, parallel consumers, network reordering), leaving the older value winning. Order by version and reject anything not newer — never trust arrival order.
  • Delete propagation. The easiest change to forget. If a row is deleted but its cache key or search document lingers, users see ghosts — deleted products still searchable, revoked access still cached. Deletes must flow through the same feed as upserts, and a delete's version must guard against a late upsert resurrecting the row (a tombstone).
  • Design for eventual consistency. Accept a bounded lag and make it non-scary: show "updating…" states, avoid read-your-own-write from a lagging copy for the writer (route their immediate re-read to Postgres), and make every consumer idempotent so at-least-once delivery and replays converge instead of corrupt.
The through-line

Five of these six hazards are solved by the same two properties: a version on every change (fixes reordering, blind overwrites, and stale-delete resurrection) and an idempotent apply (fixes duplicates and replays). TTL and stampede protection handle the read side. Build those in from the start and you rarely have to reason about a specific interleaving again.

04 Worked problem

Keeping a search index in sync via CDC ▸

Let's build the robust path end to end: a products table in Postgres, mirrored into an Elasticsearch index for search, kept in sync by a transactional outbox and an idempotent consumer that handles duplicates, reordering, and deletes.

1 · The schema

sql · postgres

CREATE TABLE products (
  id          bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  name        text NOT NULL,
  price_cents integer NOT NULL,
  version     bigint NOT NULL DEFAULT 1,   -- bumped on every UPDATE
  updated_at  timestamptz NOT NULL DEFAULT now()
);

-- the transactional outbox: one row per change, written in the SAME txn
CREATE TABLE outbox (
  id       bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  doc_id   bigint NOT NULL,          -- product id
  op       text   NOT NULL,          -- 'upsert' | 'delete'
  version  bigint NOT NULL,          -- the row's version at change time
  payload  jsonb,                     -- the document body (NULL for delete)
  sent_at  timestamptz                -- NULL until the relay ships it
);
-- a partial index so the relay scans ONLY unsent rows, in order
CREATE INDEX outbox_unsent ON outbox (id) WHERE sent_at IS NULL;

2 · The task

Every change to products must reach Elasticsearch exactly in effect — inserts and updates as document upserts, deletes as document deletes — such that no committed change is lost, duplicates are harmless, and an out-of-order delivery never installs an older value. The search index may lag by a moment; it may never diverge.

3 · The naive attempt, and why it's broken

app pseudocode · dual-write (do not do this)

BEGIN;
  UPDATE products SET name = 'Widget Pro', version = version + 1 WHERE id = 42;
COMMIT;
// ...then, in application code, right after the commit:
es.index("products", 42, { name: "Widget Pro", ... });   // <-- second write

This is the dual-write problem wearing a search-shaped hat. The database commit and the es.index() call are two separate writes to two systems with no shared transaction. If the process crashes, the network blips, or Elasticsearch is briefly down between them, Postgres has the new name and the index has the old one — permanent divergence with no record that a sync is owed. Worse, under concurrent updates the two es.index() calls can execute in the opposite order from the two commits, so the index ends up with the older name. There is no ordering guarantee and no durability of the intent to sync.

4 · The fix: outbox in the same transaction, idempotent versioned consumer

First, make the intent to sync part of the transaction with a trigger, so a committed change and its outbox row are one atomic fact:

sql · postgres

CREATE FUNCTION products_to_outbox() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF TG_OP = 'DELETE' THEN
    INSERT INTO outbox (doc_id, op, version, payload)
    VALUES (OLD.id, 'delete', OLD.version, NULL);
    RETURN OLD;
  ELSE
    INSERT INTO outbox (doc_id, op, version, payload)
    VALUES (NEW.id, 'upsert', NEW.version,
            jsonb_build_object('id', NEW.id, 'name', NEW.name,
                               'price_cents', NEW.price_cents));
    RETURN NEW;
  END IF;
END $$;

CREATE TRIGGER products_outbox
  AFTER INSERT OR UPDATE OR DELETE ON products
  FOR EACH ROW EXECUTE FUNCTION products_to_outbox();

Next, a relay drains the outbox in id order, claiming a batch with FOR UPDATE SKIP LOCKED so multiple relay workers never grab the same rows:

sql · the relay's claim query

SELECT id, doc_id, op, version, payload
FROM outbox
WHERE sent_at IS NULL
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;
-- ...ship each row to Elasticsearch, then:
UPDATE outbox SET sent_at = now() WHERE id = ANY($1);

Finally, the idempotent, versioned apply to Elasticsearch. The trick is to let Elasticsearch enforce ordering with external versioning: it will refuse to overwrite a document with an equal-or-lower version, so duplicates and out-of-order deliveries become automatic no-ops.

http · elasticsearch external versioning

# upsert product 42 at version 5 — rejected (409) if the stored version is >= 5
PUT /products/_doc/42?version=5&version_type=external
{ "id": 42, "name": "Widget Pro", "price_cents": 1999 }

# delete carries a version too, so a late upsert (v4) cannot resurrect the row
DELETE /products/_doc/42?version=6&version_type=external

5 · Why it's better

The dual-write is gone: the only atomic action is the Postgres commit, and the outbox row rides inside it, so the intent to sync is as durable as the data itself. The relay is at-least-once and crash-safe — it can re-ship a batch after a crash because external versioning makes a re-apply a no-op. Ordering is enforced at the destination by version, not by hoping deliveries arrive in order. The claim query is cheap because it rides the partial index — only unsent rows exist in it:

explain (illustrative) · the relay claim query

Limit  (cost=0.29..12.4 rows=100 width=140) (actual time=0.031..0.208 rows=100 loops=1)
  ->  LockRows  (cost=0.29..248.5 rows=2000 width=140) (actual rows=100 loops=1)
        ->  Index Scan using outbox_unsent on outbox
              (cost=0.29..228.5 rows=2000 width=140) (actual time=0.021..0.09 rows=100 loops=1)
Planning Time: 0.14 ms
Execution Time: 0.31 ms

Read that plan: the Index Scan using outbox_unsent walks the partial index in id order and stops after the LIMIT — it never touches the millions of already-sent rows, because they aren't in that index at all. The LockRows node above it is FOR UPDATE SKIP LOCKED claiming those rows so a second relay worker skips them. Sub-millisecond, regardless of table size.

6 · Narrate it

"Postgres is the record; Elasticsearch is a derived copy. To keep them in step without a dual-write, a trigger writes an outbox row in the same transaction as every product change, stamped with the row's version. A relay drains that outbox in order using SKIP LOCKED, and applies each change to Elasticsearch with an external version. Because the version guards every write, a duplicate redelivery is a no-op, a late out-of-order event is rejected, and a delete can't be undone by a straggling old upsert. The index lags by milliseconds and always converges — and if it's ever corrupted, I replay the feed to rebuild it."

05 Drills

Graded drills & the trap list

Attempt each before opening the solution. They climb from the cache race up to production read-side failure modes.

Drill 1 · Bound the read-repopulate race

Your service uses plain cache-aside: read-through on miss, and on write it deletes the key. Users occasionally report a stale value that "sticks" for hours until they edit the record again. What two changes make this bug bounded and then eliminated — without adopting full CDC?

Try it first, then read

(1) Give every cached entry a TTL (say 30–60s): this turns "stale forever" into "stale for at most the TTL," because the poisoned key self-expires and reloads fresh. (2) Make the populate version-aware: store {version, value} and, when populating on a miss, only overwrite if your version is newer (a Lua SET that compares, or embed the version in a compare-and-set). Now a slow reader holding v1 cannot clobber a freshly written v2.
Why: TTL bounds the damage; the version guard removes the race entirely because arrival order stops mattering.

Drill 2 · Kill the dual-write to the cache

A teammate proposes write-through: after committing to Postgres, the request handler also does redis.set(key, newValue) so reads are instantly fresh. Name the failure mode and give the minimal safer design that keeps most of the freshness.

Try it first, then read

The failure is a dual-write: the DB commit and the Redis set aren't atomic, so a crash or error between them (or two concurrent writers landing their sets out of order) leaves the cache holding a value that disagrees with Postgres, with nothing tracking that a fix is owed. Minimal safer design: invalidate instead of set — redis.del(key) after commit and let the next read reload from the record; a lost del just costs a miss, and add a TTL as backstop. If you truly need push-freshness, drive the set from the outbox/CDC feed (versioned), not the request handler.
Why: a delete-that-fails degrades to a harmless miss; a set-that-fails installs stale data.

Drill 3 · Two updates, wrong order

Two rapid edits to product 42 emit updates v5 then v6, but your parallel consumers apply v6 first, then v5 — so search shows the older name. The transport is at-least-once and you can't guarantee ordered delivery. How do you make the index correct anyway?

Try it first, then read

Stop trusting arrival order; enforce it at the destination with a version. Carry the row's version (or WAL LSN) on every event and apply last-write-wins by version, not by arrival: in Elasticsearch use version_type=external so v5 arriving after v6 is rejected with a 409 version_conflict; in a SQL-side projection, UPDATE ... WHERE incoming_version > stored_version. Optionally serialize a single key's events to one consumer (partition by doc_id) to reduce conflicts, but the version guard is what makes it correct.
Why: a monotonic version makes updates commutative — any delivery order converges to the newest value.

Drill 4 · The hot key expires at 3 a.m.

A single cache key holds an expensive aggregate every request needs. It has a 60s TTL. When it expires, latency spikes and the database CPU pegs for a second. Diagnose it and give three mitigations.

Try it first, then read

This is the cache stampede / thundering herd: on expiry, thousands of concurrent requests all miss simultaneously and run the same expensive rebuild against the DB at once. Mitigations: (1) request coalescing / single-flight — the first miss takes a lock and rebuilds; everyone else waits for that one result. (2) Stale-while-revalidate — serve the just-expired value while one background worker refreshes, so no request blocks on the rebuild. (3) Probabilistic early expiration (XFetch) and jittered TTLs — refresh slightly before expiry and spread expiries out so keys never all die at the same instant.
Why: the problem is N simultaneous rebuilds; every fix collapses it to one.

Traps to keep on a card:

  • Forgetting deletes. Upserts get synced, deletes get missed — ghost documents and stale cache entries. Deletes must ride the same feed, versioned.
  • No TTL anywhere. Any missed invalidation becomes permanent drift. A TTL is the cheapest self-heal you can buy.
  • Dual-writing to a derived store. The app can't atomically write Postgres and Redis/ES; a crash between them diverges silently. Use invalidate-on-write or an outbox.
  • SET on write instead of DEL. A losing SET installs stale data; a losing DEL only causes a miss. Prefer invalidation.
  • Trusting arrival order. Without a version, out-of-order or replayed events let an older value win. Version everything.
  • Synchronized TTLs on hot keys. Lockstep expiry plus no coalescing equals a stampede. Jitter and single-flight.
  • Treating the cache/replica as a backup. A derived copy replicates mistakes too; it is not a recovery point.
★ Review

Summary & self-test

One idea holds the lesson together: keep a single system of record, treat Redis and Elasticsearch as derived copies that will lag, and make every update to them ordered by version and idempotent so at-least-once, out-of-order, and replayed changes all converge instead of diverge. Cache-aside plus TTL bounds the read side; a transactional outbox plus a versioned consumer removes the dual-write on the write side.
