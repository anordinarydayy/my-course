Window Functions

A window function computes across a set of related rows — a running total, a rank, the previous month's value — and hands the answer back without collapsing those rows the way GROUP BY does. The engine is the OVER clause: it defines the window each row can see. This practice lesson drills the three moves that trip people up: partitioning and ordering the window, choosing the right function family, and — the deep part — getting the frame right so a running total doesn't silently double-count its ties.

00 The core idea

Aggregate without collapsing the rows

You already know GROUP BY: it folds many rows into one per group and lets you attach an aggregate — sum, count, avg. The price is that the individual rows disappear. Ask "what fraction of my department's payroll is my salary?" and GROUP BY fights you: it can give the department total, but not next to each person's row, because the people are gone.

A window function solves exactly this. It computes an aggregate (or a rank, or a neighbour's value) over a window of related rows, and then writes the answer onto every row — no collapsing. The only new syntax is the OVER (...) clause hanging off the function. Compare the two directly:

sql

-- GROUP BY: one row per dept, the individual rows are gone
SELECT dept, sum(salary) AS payroll
FROM   employees
GROUP BY dept;

-- WINDOW: every employee kept, dept payroll added as a column
SELECT name, dept, salary,
       sum(salary) OVER (PARTITION BY dept) AS dept_payroll
FROM   employees;

Read the second query slowly. sum(salary) is the same aggregate as before, but OVER (PARTITION BY dept) tells Postgres: don't collapse — for each row, sum the salaries of every row that shares this row's dept, and put the result here. The result has one line per employee, each carrying its department's total alongside. Now salary / dept_payroll is a column you can select. That single capability — a per-group number sitting next to per-row detail — is why window functions show up in almost every non-trivial reporting query.

The one-line mental model

GROUP BY reduces rows; a window function annotates them. If your answer needs both the detail rows and a computation across their neighbours — rank, running total, share-of-total, previous value — you want a window function, not a GROUP BY plus a self-join.

01 Defining the window

PARTITION BY & ORDER BY ▸

Two optional clauses inside OVER (...) shape the window. PARTITION BY splits the rows into independent groups — each partition is its own little world, and the function restarts at every partition boundary. It is the window analogue of GROUP BY, except the rows are not collapsed. ORDER BY (inside the OVER, distinct from the query's final ORDER BY) sequences the rows within each partition — which is mandatory the moment you rank or run a total, because "the first row" and "the rows so far" only mean something once the rows are ordered.

Two things to burn in. First, the numbering restarts at each partition — Eng gets its own 1, 2, 3 with no memory of Sales. Second, the table still has five rows out for five rows in: the window added a column, it did not fold anything. Drop the PARTITION BY and the whole table becomes one window; drop the ORDER BY and any ranking function has no defined sequence to count along (Postgres will run it, but the order — and therefore the numbers — is arbitrary).

Two ORDER BYs, don't confuse them

The ORDER BY inside OVER (...) orders rows within the window for the function's benefit. The ORDER BY at the end of the query orders the final output. They are independent — you often need both, and they can differ. A ranking that looks scrambled on screen is usually a windowed sort that was never mirrored by a final ORDER BY.

02 The toolbox

The three function families

Every window function falls into one of three families. Knowing which family you need is half the battle; the syntax is nearly identical across them.

Ranking

  • row_number() — unique 1..n.
  • rank() — ties share, then a gap.
  • dense_rank() — ties share, no gap.
  • ntile(k) — split into k buckets.

Offset

  • lag(x) / lead(x) — previous / next row's value.
  • first_value(x) / last_value(x).
  • nth_value(x, n).
  • Reach across rows without a self-join.

Aggregates-as-windows

  • sum / avg / count / min / max OVER.
  • Any aggregate, but not collapsing.
  • Running totals, moving averages.
  • Share-of-total, cumulative counts.

The ranking family is where the classic interview trap lives, so spell it out. Take four salaries — 90, 80, 80, 70 — ordered descending, and put all four ranking functions side by side:

sql

SELECT name, salary,
       row_number() OVER w AS rn,
       rank()       OVER w AS rk,
       dense_rank() OVER w AS dr,
       ntile(2)     OVER w AS half
FROM   employees
WINDOW w AS (ORDER BY salary DESC);

The results diverge exactly on the two tied 80s:

  • row_number → 1, 2, 3, 4 — always unique; the two 80s get 2 and 3 in some arbitrary but stable order (add a tiebreak column to ORDER BY to make it deterministic).
  • rank → 1, 2, 2, 4 — the ties both get 2, then rank skips to 4 (a gap the size of the tie).
  • dense_rank → 1, 2, 2, 3 — ties both get 2, then no gap: the next value is 3.
  • ntile(2) → 1, 1, 2, 2 — four rows split into two equal buckets.

Notice the WINDOW w AS (...) clause: when several functions share the same window, name it once and reference it by alias. It is pure de-duplication — the query means the same thing as repeating OVER (ORDER BY salary DESC) four times — but it reads better and guarantees the windows really are identical (which, as you'll see in the worked problem, lets the planner compute them all in a single pass).

Pick the ranking by the tie rule

"Top 3 rows, ties broken arbitrarily" → row_number. "The three highest distinct scores, keeping every tie" → dense_rank <= 3 (it numbers distinct score levels). Note rank <= 3 is a third thing: it keeps everyone down to the third position but then leaves a gap after a tie, so with scores 100, 100, 90, 80 it yields ranks 1, 1, 3, 4 and drops the 80 — whereas dense_rank gives 1, 1, 2, 3 and keeps it. Choosing row_number when the rule is "keep all ties" is the subtle, common bug — it silently drops a legitimately-tied row.

03 The depth

Frames: ROWS vs RANGE vs GROUPS ▸

Here is the part most people get wrong. When a window function has an ORDER BY, it doesn't necessarily see the whole partition — it sees a frame: a sliding slice of the partition relative to the current row. And there is a default frame you didn't ask for:

sql

-- these two are IDENTICAL — the frame is implicit in the first
sum(amt) OVER (ORDER BY day)
sum(amt) OVER (ORDER BY day RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)

Three frame modes decide what "the rows up to the current row" means:

  • ROWS — a physical count of rows. "3 preceding" means literally the three rows above this one.
  • RANGE — value peers. All rows whose ORDER BY value ties the current row's are treated as one; the frame extends over the whole peer group. This is the default.
  • GROUPS — like RANGE but you count in units of peer groups ("2 groups preceding"), not values.

The default RANGE ... CURRENT ROW is a trap for running totals: at a tie, "current row" secretly means all tied peers, so every tied row gets the running total that includes the whole tie at once. Step through it with a deliberate tie on day = 2:

The two tied rows are the whole story. With the default RANGE, both day-2 rows report 60 — because their peer group (10 + 20 + 30) is summed as a unit and both rows sit at its end. With ROWS UNBOUNDED PRECEDING, the first day-2 row reports 30 and the second 60: a genuine row-by-row cumulative sum. If you ever see a running total that "jumps" and repeats a value across ties, you are looking at the default-RANGE bug.

The running-total rule

For a true row-by-row cumulative sum, always write the frame explicitly: sum(x) OVER (ORDER BY k ROWS UNBOUNDED PRECEDING). Reserve the default RANGE for when tied rows genuinely should share one cumulative value. And remember last_value(): under the default frame it returns the current row's value, not the partition's last — it needs ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING to see the whole partition.

04 Worked problem

Top 3 earners per department, with a running payroll ▸

Time to put it together on a realistic task. Here is the schema:

sql

CREATE TABLE employees (
  id     int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  dept   text NOT NULL,
  name   text NOT NULL,
  salary numeric NOT NULL
);

Task. Within each department, rank employees by salary (highest first), keep only the top 3, and show a running payroll total that accumulates down those top earners.

The wrong first attempt

The instinct is to compute the rank and filter it in one WHERE:

sql

SELECT dept, name, salary,
       row_number() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn
FROM   employees
WHERE  rn <= 3;          -- ERROR: column "rn" does not exist

This fails, and the error is the lesson. Window functions are evaluated after WHERE, GROUP BY, and HAVING — near the very end of the logical pipeline, just before the final ORDER BY/LIMIT. So at the moment WHERE runs, rn hasn't been computed and the alias isn't in scope. You cannot filter a window result in the same query level where you created it. You must compute it in one level and filter in an outer one.

The correct query

Wrap the windowed computation in a CTE (or subquery), then filter in the outer query. Compute both windows — the rank and the running total — in the same step, using the identical window so Postgres sorts once:

sql

WITH ranked AS (
  SELECT dept, name, salary,
         row_number() OVER w AS rn,
         sum(salary)  OVER (PARTITION BY dept ORDER BY salary DESC
                            ROWS UNBOUNDED PRECEDING) AS running_payroll
  FROM   employees
  WINDOW w AS (PARTITION BY dept ORDER BY salary DESC)
)
SELECT dept, name, salary, rn, running_payroll
FROM   ranked
WHERE  rn <= 3
ORDER BY dept, rn;

Two details worth defending. The row_number() uses the named window w; the sum() spells out the same partition/order but adds ROWS UNBOUNDED PRECEDING for a true cumulative total (per the frame rule from §03 — the default RANGE would lump salary ties together). Both share the partition and order, so a single sort feeds both. Watch it resolve on one department:

The plan, and the index that helps

Because both windows share PARTITION BY dept ORDER BY salary DESC, the executor needs the input sorted that way exactly once. The two functions use different frames (row_number takes the default, the cumulative sum uses ROWS UNBOUNDED PRECEDING), so Postgres stacks a WindowAgg node per distinct frame — both fed by that single sort. With no supporting index it must sort first:

illustrative

Subquery Scan on ranked  (cost=128.4..183.4 rows=333 width=72)
  Filter: (ranked.rn <= 3)
  Rows Removed by Filter: 667
  ->  WindowAgg  (cost=128.4..158.4 rows=1000 width=72) (actual time=1.9..3.6 rows=1000)
        ->  WindowAgg  (cost=128.4..153.4 rows=1000 width=64) (actual time=1.9..3.4 rows=1000)
              ->  Sort  (cost=128.4..130.9 rows=1000 width=40)
                    Sort Key: employees.dept, employees.salary DESC
                    Sort Method: quicksort  Memory: 103kB
                    ->  Seq Scan on employees  (cost=0.00..18.0 rows=1000 width=40)

The whole table is read, sorted, and windowed before the rn <= 3 filter throws most of it away — the Rows Removed by Filter: 667 line makes that waste visible. A composite index in the window's exact order removes the Sort: the executor can walk the index and feed WindowAgg pre-ordered.

sql

CREATE INDEX employees_dept_salary_idx
  ON employees (dept, salary DESC);

illustrative

Subquery Scan on ranked  (cost=0.28..100.3 rows=333 width=72)
  Filter: (ranked.rn <= 3)
  Rows Removed by Filter: 667
  ->  WindowAgg  (cost=0.28..75.3 rows=1000 width=72) (actual time=0.03..1.8 rows=1000)
        ->  WindowAgg  (cost=0.28..70.3 rows=1000 width=64) (actual time=0.03..1.6 rows=1000)
              ->  Index Scan using employees_dept_salary_idx on employees
                    (cost=0.28..45.3 rows=1000 width=40) (actual time=0.02..0.7 rows=1000)

The Sort node is gone; the Index Scan delivers rows already in (dept, salary DESC) order, and startup cost drops from ~128 to ~0.28 because the executor can begin emitting immediately instead of waiting for a full sort to finish.

Narrate it

"For each department, sort employees by salary descending. row_number() numbers them 1..n and a cumulative sum() — framed ROWS UNBOUNDED PRECEDING so ties don't lump — runs the payroll down them. Both windows share one sort. I compute those in a CTE because a window result can't be filtered in WHERE, then the outer query keeps rn <= 3. An index on (dept, salary DESC) matches the window order, so the plan is stacked WindowAgg nodes over an Index Scan with no separate Sort."

05 Practice

Graded drills & the traps

Attempt each before opening the solution. Assume the employees schema above, plus a monthly(month date, revenue numeric) table and a payments(id int, paid_at timestamptz, amt numeric) table where noted.

Drill 1 — the three ranks on ties (warm-up)

Output every employee with three columns — rn, rk, dr — ranking by salary descending, so a reader can see how each ranking function treats ties.

Try it first, then read

sql

SELECT name, salary,
       row_number() OVER w AS rn,
       rank()       OVER w AS rk,
       dense_rank() OVER w AS dr
FROM   employees
WINDOW w AS (ORDER BY salary DESC)
ORDER BY salary DESC;

Why: one named window feeds all three; row_number is unique, rank leaves gaps after ties, dense_rank does not.

Drill 2 — month-over-month change (offset)

From monthly(month, revenue), show each month's revenue and how much it changed versus the previous month.

Try it first, then read

sql

SELECT month, revenue,
       revenue - lag(revenue) OVER (ORDER BY month) AS mom_change
FROM   monthly
ORDER BY month;

Why: lag(revenue) reaches back one row in the ordered window; the first month's mom_change is NULL (no prior row). Use lag(revenue, 1, 0) if you want 0 instead of NULL.

Drill 3 — a correct running total (frame)

From payments(id, paid_at, amt), produce a true row-by-row cumulative total ordered by paid_at — and make it survive same-timestamp ties.

Try it first, then read

sql

SELECT id, paid_at, amt,
       sum(amt) OVER (ORDER BY paid_at, id
                     ROWS UNBOUNDED PRECEDING) AS running_total
FROM   payments
ORDER BY paid_at, id;

Why: ROWS UNBOUNDED PRECEDING forces a physical row-by-row sum (no default-RANGE lumping), and adding id to the order makes the sequence deterministic when two payments share a timestamp.

Drill 4 — top-N per group (windowed CTE)

Given sales(category text, product text, revenue numeric), return the top 2 products by revenue in each category.

Try it first, then read

sql

WITH ranked AS (
  SELECT category, product, revenue,
         row_number() OVER (PARTITION BY category
                            ORDER BY revenue DESC) AS rn
  FROM   sales
)
SELECT category, product, revenue
FROM   ranked
WHERE  rn <= 2
ORDER BY category, rn;

Why: the window can't be filtered in WHERE, so rank in a CTE and filter outside. If you need every product tied for 2nd to stay, swap row_number for rank. (For a strict single-latest-per-group with no ties, DISTINCT ON (category) ... ORDER BY category, revenue DESC is the terser idiom — see Lesson 18.)

The traps, collected

Four failure modes that account for most window-function bugs:

  • Filtering a window in WHERE. Windows run after WHERE/GROUP BY, so WHERE rn <= 3 errors (unknown column). Wrap in a CTE/subquery and filter in the outer level.
  • The default-RANGE running total. sum(x) OVER (ORDER BY k) lumps tied peers and repeats their total. Write ROWS UNBOUNDED PRECEDING for a real cumulative sum.
  • last_value with the default frame. It only sees up to the current row, so it returns the current row's value. Add ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING to reach the partition's true last row.
  • A ranking window with no ORDER BY. row_number() OVER (PARTITION BY dept) has no defined sequence — the numbers are arbitrary and can change between runs. Ranking always needs an ORDER BY inside OVER.
★ Review

Summary & self-test

One idea holds the lesson together: a window function computes over a set of related rows and writes the result onto every row without collapsing them — you shape that set with PARTITION BY and ORDER BY, and its exact extent with the frame. Get the frame right and the running total is correct; get the pipeline order right and you know why the filter lives in an outer query.
