VACUUM, Bloat & Wraparound

MVCC (Lesson 26) buys you a beautiful property — readers never block writers — but it charges rent. Every UPDATE and DELETE leaves an old row version behind as a dead tuple, and someone has to clean up. That someone is VACUUM. This lesson is the maintenance side of the concurrency you already learned: what dead tuples cost, how autovacuum reclaims them, how a single long transaction turns that garbage into runaway bloat, and the one failure you must never reach — transaction-ID wraparound.

Original study notes. Written for engineers who want database depth that pays off in interviews and on call. Examples use PostgreSQL (facts current to PG 17/18). Contains three interactive diagrams (press Play or step through with Next). This is a concept lesson — no SQL drill; it builds the mental model of the maintenance MVCC demands, and closes Phase 5.
00 The trade you signed

MVCC leaves garbage — on purpose

Back in Lesson 26 you learned Postgres's trick for concurrency: it never overwrites a row in place. Instead, every row version carries two hidden system columns — xmin (the transaction that created this version) and xmax (the transaction that deleted or superseded it). An INSERT sets xmin. A DELETE sets xmax. And an UPDATE is really a delete-plus-insert: it stamps xmax on the old version and writes a brand-new version beside it. The old version is left lying there.

That leftover is a dead tuple: a row version that no current or future snapshot can ever see again. It is invisible to queries — but it is not gone. It still occupies its slot on the page, and every sequential scan still has to read past it. This is the deal MVCC struck on your behalf:

The bargain

Because writers create new versions instead of overwriting old ones, a reader can keep reading its own consistent snapshot while a writer changes the same row — readers never block writers, writers never block readers. The price is that the old versions pile up as dead tuples. MVCC doesn't make the garbage disappear; it just defers cleanup to a background janitor so your foreground queries stay fast and non-blocking.

So a healthy Postgres table is always generating dead tuples as it runs — that is normal and expected. The question is never "how do I avoid dead tuples?" (you can't, short of never updating anything) but "is the janitor keeping up with them?" When it keeps up, you never think about this. When it falls behind, dead tuples accumulate faster than they are reclaimed, and you get the two failure modes this lesson is about: bloat (wasted space and slow scans) and, in the worst case, transaction-ID wraparound (a shutdown-your-writes emergency). The janitor is VACUUM, and everything else follows from understanding exactly what it does.

Where the dead ones come from

An UPDATE that changes even one column writes a whole new tuple and marks the old one dead — this is why a table you only ever UPDATE (never INSERT/DELETE) still bloats. A DELETE marks its row dead but leaves it on the page until vacuum comes. Even a rolled-back INSERT leaves a dead tuple. HOT updates (Lesson 26) soften the blow when no indexed column changed, but they don't eliminate dead tuples — they just avoid churning the indexes.

01 The janitor's job

What VACUUM actually does ▸

The single most common misconception about VACUUM is that it "shrinks the table" or "gives space back to the disk." It does not — and understanding what it does instead is the key to this whole lesson. A plain VACUUM works page by page: it finds the dead tuples, removes their index entries, and marks their line pointers as reusable. The space stays inside the table file; new rows will simply be written into those freed slots. Watch one heap page get vacuumed:

Notice what changed and what didn't. The dead tuples' space became reusable, but the file is exactly as big as before — Postgres reclaims space for the table's own future rows, not for the operating system. In steady state that is fine: a table that churns rows reaches an equilibrium size and reuses its own freed space forever. Vacuum also did two more valuable things on that page: it updated the visibility map (the per-page all-visible bit that powers index-only scans, Lesson 19) and the free space map, and it froze old rows — a mechanism we return to in s4. Run a vacuum by hand like this:

sql

VACUUM (VERBOSE, ANALYZE) orders;   -- reclaim dead tuples + refresh planner stats
-- Different, heavy tool — rarely what you want:
VACUUM FULL orders;                 -- rewrites the whole table, ACCESS EXCLUSIVE lock

That second command is a different beast. VACUUM FULL is the built-in that returns bloated space to the OS in bulk (plain VACUUM only hands back completely-empty pages at the very end of the table, never the dead space scattered through its interior) — and it does so by rewriting the entire table into a fresh file under an ACCESS EXCLUSIVE lock, which blocks every read and write on the table for the whole rewrite. On a live, hot table that is an outage. Reach for it only in a maintenance window on a table that bloated badly once and won't again; for ongoing health, plain (auto)vacuum is the tool.

The one-line summary of VACUUM

Plain VACUUM = "make dead space reusable within the table, update the visibility/free-space maps, freeze old rows" — cheap, concurrent, runs constantly. VACUUM FULL = "rewrite the table to give space back to the OS" — expensive, takes an exclusive lock, never on a live table. Confusing the two is the classic junior mistake: someone sees bloat, runs VACUUM FULL on production at noon, and takes the app down.

02 The automatic janitor

Autovacuum, and the modern engine

You almost never run VACUUM by hand. A background process called autovacuum watches every table and runs VACUUM + ANALYZE for you when a table has changed enough to be worth it. "Enough" is a simple, tunable formula: autovacuum fires a table when its dead-tuple count crosses

threshold

-- autovacuum triggers a table when:
n_dead_tup > autovacuum_vacuum_threshold
           + autovacuum_vacuum_scale_factor * reltuples

The scale factor is the important knob. It defaults to 0.2 — 20% of the table must be dead before autovacuum bothers. That's a sensible default for a small table, but on a 500-million-row table, 20% is 100 million dead tuples: an ocean of bloat before cleanup even starts. So the number-one autovacuum tuning move is to make big or hot tables far more eager:

sql

-- make autovacuum aggressive on a large, write-heavy table
ALTER TABLE events SET (
  autovacuum_vacuum_scale_factor = 0.02,   -- 2% dead, not 20%
  autovacuum_vacuum_threshold    = 1000
);

The other thing worth knowing is that autovacuum got dramatically better in the exact versions this course targets — this is a favorite "do you keep up?" interview angle:

PG 17 — TIDStore

  • Replaced the old fixed dead-tuple array with TIDStore, an adaptive radix tree.
  • Removed the old 1 GB maintenance_work_mem cap on how many dead tuples one pass could track.
  • So vacuum no longer makes repeated index passes on huge tables — one pass, far less I/O.

PG 18 — faster & smarter

  • Async-I/O heap scans during vacuum — reads overlap instead of stalling.
  • On-the-fly autovacuum worker tuning without a restart.
  • autovacuum_vacuum_max_threshold — a hard dead-tuple cap so huge tables vacuum sooner, regardless of scale factor.
  • Eager freezing of all-visible pages — heads off wraparound (s4).

The operational rule that falls out of all this is blunt: never turn autovacuum off. Every so often an engineer disables it to "stop the load spikes," the dead tuples stop being reclaimed, and a week later the table is triple its size and creeping toward wraparound. If autovacuum is causing pain, the fix is to make it run more often in smaller bites (raise autovacuum_max_workers, lower the per-table scale factor, tune the cost-delay), never to switch off the one process keeping the table alive. You can always watch what it's doing:

sql

SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
03 When the janitor can't win

Bloat: the slow leak ▸

Bloat is what happens when dead tuples accumulate faster than vacuum removes them. There are two ways to get there. The first is brute force: a write rate so high that autovacuum simply can't keep pace (the s2 tuning is the answer). The second is subtler, more common, and the one that catches people — a single long-running transaction. Here is the crucial rule that ties it to MVCC: vacuum may only remove a dead tuple if it is dead to every possible snapshot — that is, older than the xmin horizon, the oldest snapshot any active transaction still holds. One old transaction that stays open pins that horizon in the past, and nothing newer than it can be cleaned — even in tables that transaction never touched. Watch it happen:

Read the shape of that story: dead tuples climb the whole time A is open, autovacuum runs but is powerless to remove anything younger than A's pinned horizon, and the pile only drains after A finally commits (or is killed) and the horizon lurches forward. This is why "idle in transaction" is a phrase that makes DBAs wince — an app that opens a transaction, does one query, then sits waiting on a slow external API call while never committing, can bloat an entire database. And notice the sting in the tail: even after the cleanup, the file stayed its bloated size (only VACUUM FULL would shrink it). Diagnose it by finding the oldest transaction and the most-bloated tables together:

sql

-- who is holding the horizon open?
SELECT pid, state, now() - xact_start AS txn_age, query
FROM pg_stat_activity
WHERE state IS NOT NULL AND state <> 'idle'
ORDER BY xact_start;      -- oldest transaction first

-- and how bloated is each table? (dead as a share of live)
SELECT relname, n_live_tup, n_dead_tup,
       round(n_dead_tup * 100.0
         / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
Bloat is a symptom, the horizon is the cause

When you see rising bloat, resist the urge to VACUUM FULL the symptom away. Look first for the cause: a transaction that's been open for hours (kill it, and fix the app so it commits promptly), or a write rate the scale factor is too lazy for (tune s2). Set idle_in_transaction_session_timeout so a forgotten transaction can't hold the horizon forever. Fix the source and the bloat stops growing; only then, if a table is already huge, consider a one-time rewrite in a maintenance window.

04 The emergency

Transaction-ID wraparound — the one you must never hit ▸

This is the failure that takes databases offline, and it comes straight out of the same xmin/xmax machinery. Transaction IDs are only 32-bit, so they run out after about 4 billion and wrap around back to the start. Visibility is decided by comparing xids — "is this row's xmin in the past relative to my snapshot?" — and in a wrapping counter, "past" is only the most recent ~2 billion values. So a row that stays untouched while 2 billion newer transactions go by would suddenly have an xmin that looks like it's in the future, and the row would silently vanish from every query. The defense is freezing: marking an old row as permanently visible so its original xmin no longer matters. Watch the counter climb — and what stops it:

The good news is that this is almost entirely automatic and almost never hit — Postgres runs an anti-wraparound autovacuum that is deliberately aggressive and, unlike a normal vacuum, non-cancelable (it will not politely step aside for your DDL). It freezes old rows long before the counter is anywhere near dangerous. You only reach the cliff if something has been actively sabotaging freezing for a long time — and it's the same two culprits as bloat: autovacuum disabled, or a long-running transaction holding the horizon so old rows can't be frozen. If freezing still can't catch up, Postgres does the only safe thing: it stops accepting writes and goes read-only, rather than let a wrapped xid corrupt your data. Recovery means letting vacuum finish. Monitor the age so you never get close:

sql

-- how close is each database to wraparound? higher age = more urgent
SELECT datname, age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY xid_age DESC;   -- alert well before 2 billion
The whole risk in one sentence

Wraparound is not really a separate problem — it is bloat's evil twin, caused by the same two things (autovacuum off, or a long transaction pinning the horizon) but with a far worse ending: not a slow table, but a database that refuses writes. Keep autovacuum on and keep transactions short, and you will never meet it. PG18's eager freezing of all-visible pages pushes the danger even further away.

05 Make it stick

Reason about it: the operational discipline

Step back and notice how tightly this whole lesson coils around two root causes. Bloat and wraparound look like different problems — one is wasted space, the other is a database-halting emergency — but trace each to its source and you find the same two hands on the wheel: autovacuum not running enough, and transactions staying open too long. Fix those two things and you have solved 90% of Postgres maintenance before it happens. Let's reason through the discipline.

First, never disable autovacuum, and tune it to your write rate. The default 20% scale factor is fine for a small table and negligent for a large hot one. If a table is churning millions of rows, tell autovacuum to wake at 2% dead, not 20% — smaller, more frequent passes that never let dead tuples ocean up. If autovacuum is causing load spikes, the answer is more workers and gentler cost-delay, never the off switch. On PG 17/18 the engine does far more of this well on its own (TIDStore's single index pass, PG18's max-threshold and eager freezing), but the scale-factor tuning is still yours to own.

Second — and this is the one that pays off everywhere — keep transactions short. A long transaction is the single most destructive thing you can do to a Postgres instance, because it pins the xmin horizon and thereby blocks both dead-tuple cleanup (bloat) and freezing (wraparound) across the whole database, even in tables it never reads. The classic villain is "idle in transaction": code that runs BEGIN, does a little work, then holds the transaction open across a slow HTTP call or a user's think-time. Set idle_in_transaction_session_timeout as a guardrail, and design so transactions do their work and commit.

sql

-- the guardrail: don't let a forgotten transaction pin the horizon
SET idle_in_transaction_session_timeout = '30s';

-- NEVER do this on a real system:
ALTER TABLE orders SET (autovacuum_enabled = false);  -- bloat + wraparound await

Third, monitor two numbers and you'll sleep well: the dead-tuple percentage per table (the pg_stat_user_tables query from s3 — a table trending past ~20% dead that isn't shrinking means autovacuum is losing) and the datfrozenxid age per database (the pg_database query from s4 — alert long before 2 billion). Two dashboards, and the two failure modes of this lesson announce themselves weeks before they bite.

Where this shows up next

You've now closed the loop on MVCC: Lesson 26 explained why the dead tuples exist (versioning is what lets readers and writers not block each other), and this lesson explained how they're cleaned up and what happens when cleanup falls behind. The visibility map that vacuum maintains is exactly what makes index-only scans (Lesson 19) fast — vacuum is a performance feature, not just hygiene. And the monitoring instinct here — watch dead-tuple % and xid age, alert early — is the opening move of Phase 7, Operations & Reliability, where autovacuum tuning, the WAL, and health metrics become a first-class discipline. ★ Review

Summary & self-test

The whole lesson compresses to one idea: MVCC keeps concurrency non-blocking by leaving old row versions behind as dead tuples, and VACUUM is the janitor that reclaims them — a janitor that only two things can defeat, a lazy autovacuum and a long-running transaction, which is why bloat and wraparound share the exact same cure.
