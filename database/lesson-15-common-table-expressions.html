Common Table Expressions

A WITH clause gives a subquery a name, so a query you once had to read inside-out becomes a pipeline you read top-to-bottom. WITH RECURSIVE goes further and lets a query call itself — the one clean way to walk a tree, a graph, or a generated sequence in pure SQL. And the 2019 change that made a CTE stop being an optimization fence is one of the most reliable Postgres interview gotchas there is. This lesson drills all three.

Original study notes. Written for engineers who want SQL depth that pays off in interviews and in production. Everything runs on PostgreSQL 17/18 and every query is meant to be copy-paste runnable. 00 The idea

WITH: give a subquery a name

A Common Table Expression (CTE) is a named, temporary result set that exists only for the single statement it is attached to. You write it with the WITH keyword, hand it a name, and then SELECT from that name in the main query as if it were a table. That is the whole mechanism — and its payoff is readability. A nested subquery forces you to read from the innermost parentheses outward; a CTE lets you read the same logic as a top-down list of named steps.

Watch the identical query written both ways. First the nested form, which you parse inside-out:

sql

-- read this from the inside out
SELECT region, avg_spend
FROM (
  SELECT region, avg(total) AS avg_spend
  FROM orders
  GROUP BY region
) r
WHERE avg_spend > 100;

Now the same thing with a CTE — read it straight down:

sql

WITH by_region AS (
  SELECT region, avg(total) AS avg_spend
  FROM orders
  GROUP BY region
)
SELECT region, avg_spend
FROM by_region
WHERE avg_spend > 100;

Same result, same performance in modern Postgres (more on that in section 02) — but the second version names its intermediate step, and names are how humans manage complexity. You can also chain several CTEs, comma-separated, and each may reference any CTE defined before it:

sql

WITH a AS (SELECT ...),          -- step 1
     b AS (SELECT ... FROM a),  -- step 2 reads step 1
     c AS (SELECT ... FROM b)   -- step 3 reads step 2
SELECT * FROM c;                       -- main query reads the last

Three rules to keep straight from the start. A CTE is query-scoped: it vanishes the instant the statement finishes — it is not a temp table you can reuse later. References only go backward: a cannot see b (the one exception is a recursive CTE, which is allowed to reference itself). And a CTE is not restricted to SELECT — you can also put INSERT, UPDATE, or DELETE ... RETURNING inside WITH to build multi-step data pipelines in a single statement.

The mental model

Think of WITH as a “let” binding for SQL: WITH name AS (query) is let name = query in …. You are naming a value so the rest of the expression can refer to it by name instead of by copy-pasting its definition. Everything else in this lesson is what you can do once your steps have names — including having a step refer to itself.

01 Composition

Composing a report as a chain of named steps ▸

Where CTEs earn their keep is a report that is really a pipeline: filter the raw rows, aggregate them, rank the aggregates, then pick the top few. Written as one nested query it is a wall of parentheses; written as a chain of CTEs it reads like the four sentences you'd use to describe it. Here is “the top 3 customers by spend over the last 30 days”:

sql

WITH recent AS (                         -- 1. filter
  SELECT * FROM orders
  WHERE created_at >= now() - interval '30 days'
),
per_cust AS (                            -- 2. aggregate
  SELECT customer_id, sum(total) AS spend
  FROM recent
  GROUP BY customer_id
),
ranked AS (                              -- 3. rank
  SELECT customer_id, spend,
         rank() OVER (ORDER BY spend DESC) AS rnk
  FROM per_cust
)
SELECT customer_id, spend                -- 4. pick
FROM ranked
WHERE rnk <= 3
ORDER BY spend DESC;

Step through the pipeline and notice how each named step narrows the data for the next — a million raw rows become three at the end:

The ranked step is doing more than tidying up: it exists because you cannot filter on a window function in WHERE. Window functions run after WHERE and GROUP BY, so WHERE rank() OVER (...) <= 3 is rejected outright — ERROR: window functions are not allowed in WHERE — because the rank simply doesn't exist yet when WHERE runs. Computing the rank in its own CTE and filtering it in the outer query is the idiomatic fix, and it's a pattern you'll reach for constantly.

Why the extra CTE isn't wasteful

You might worry that four named steps means four full passes over the data. In modern Postgres it usually doesn't: because these CTEs are singly-referenced and side-effect-free, the planner inlines them and builds one fused plan — the same plan it would build from the equivalent nested query. You get the readability for free. The next section is exactly about when that inlining happens and when it doesn't.

02 The gotcha

CTE vs subquery, and the PG12 inlining change

Here is the fact that trips people in interviews, because the answer changed. For years the rule was: a CTE is an optimization fence. Before PostgreSQL 12, whatever you put in a WITH clause was always materialized — computed in full into a temporary work area first, then read back. The planner could not push an outer WHERE into the CTE, could not reorder it, could not use an index inside it based on how you filtered outside it. Developers even exploited this as a hint, wrapping a subquery in a pointless CTE to force materialization.

Since PostgreSQL 12 the default flipped. A CTE that is (1) not recursive, (2) side-effect-free (no INSERT/UPDATE/DELETE, no volatile functions), and (3) referenced exactly once is inlined by default — it plans just like a subquery, with filters pushed in and joins reordered freely. You now control it explicitly:

AS MATERIALIZED

  • Forces the old behavior: compute once, into a worktable.
  • Shows up as a CTE Scan node in the plan.
  • Use it to compute an expensive thing once, or to pin a plan you like.

AS NOT MATERIALIZED

  • Forces inlining even when Postgres would otherwise materialize.
  • Plans exactly as if you'd written a subquery.
  • Use it to un-fence a CTE the planner is being conservative about.

See it in a plan. Imagine events has 50 million rows and an index on user_id. This CTE is singly-referenced, so it inlines and the outer filter is pushed all the way to the index:

sql

WITH big AS (
  SELECT * FROM events
)
SELECT * FROM big WHERE user_id = 42;

illustrative

Index Scan using events_user_id_idx on events  (cost=0.44..38.60 rows=9 width=72)
  Index Cond: (user_id = 42)

Nine rows, a millisecond. Now force the pre-12 behavior with a single keyword and watch it fall apart — Postgres must build the entire 50-million-row CTE before it can even look at your filter:

sql

WITH big AS MATERIALIZED (
  SELECT * FROM events
)
SELECT * FROM big WHERE user_id = 42;

illustrative

CTE Scan on big  (cost=0.00..1500000.00 rows=250000 width=72) (actual rows=9)
  Filter: (user_id = 42)
  Rows Removed by Filter: 49999991
  CTE big
    ->  Seq Scan on events  (cost=0.00..1000000.00 rows=50000000 width=72)

The CTE Scan node and the “Rows Removed by Filter: 49,999,991” line are the smoking gun: the whole table was materialized, then filtered. So when should you deliberately reach for MATERIALIZED? Three good reasons: a CTE that is expensive and referenced many times (compute once, reuse the worktable); a CTE whose result you want to pin against a planner that keeps re-deriving a worse plan; or a CTE that must run exactly once for correctness (a data-modifying CTE, or one wrapping a side-effecting or volatile function). Note the flip side of the default: recursive CTEs, and CTEs referenced more than once, are still materialized automatically — you don't have to ask.

The interview answer, memorized

“Is a CTE an optimization fence in PostgreSQL?” → “Not since version 12. A non-recursive, side-effect-free CTE referenced exactly once is inlined by default and plans like a subquery. It's only a fence if it's recursive, referenced multiple times, has side effects, or I explicitly write MATERIALIZED.” Saying that one sentence cleanly signals you know current Postgres, not a decade-old blog post.

03 Recursion

WITH RECURSIVE: a query that calls itself ▸

SQL has no loops — and yet trees, graphs, hierarchies, and generated sequences all need something loop-shaped. WITH RECURSIVE is that something. Its shape is fixed and worth memorizing: a base term (the starting rows) UNION ALL a recursive term that references the CTE by name.

sql

WITH RECURSIVE t(n) AS (
  SELECT 1                 -- base term: the anchor row
  UNION ALL
  SELECT n + 1 FROM t      -- recursive term: references t
  WHERE n < 5              -- termination guard
)
SELECT n FROM t;              -- → 1, 2, 3, 4, 5

The execution model is a precise little loop, and understanding it is the difference between writing recursive CTEs confidently and fearing them. The engine keeps a working table. It runs the base term once, and its rows become both the first output and the initial working table. Then it repeats: run the recursive term with the CTE name bound to the current working table, emit whatever comes back, and make those rows the new working table. It stops the instant an iteration produces zero rows. Step through it:

Two knobs control safety and shape. UNION ALL keeps every row the recursion emits; plain UNION de-duplicates each pass, which both trims duplicates and gives you a crude cycle guard — if a graph loops back to a row you've already produced, UNION discards it and the loop can die out. A pure tree can't cycle, so UNION ALL is fine there; a graph with back-edges needs real cycle protection, which we build in the worked problem next.

The two ways a recursive CTE goes wrong

Both failure modes are “it never stops.” Either there's no termination guard — nothing shrinks the frontier, like forgetting the WHERE n < 5 above — or the data has a cycle and each pass keeps finding “new” rows. The engine won't save you; it will happily run until it exhausts memory or disk. Every recursive CTE you write needs an answer to “what makes the recursive term eventually return zero rows?”

04 Worked problem

Worked: every descendant of a category ▸

This is the canonical recursive-CTE interview question, and it's worth doing end to end. Start with the schema — a classic adjacency-list tree, where each row points at its parent:

sql

CREATE TABLE categories (
  id        int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name      text NOT NULL,
  parent_id int REFERENCES categories(id)   -- NULL at the roots
);
CREATE INDEX ON categories(parent_id);

The task, in one sentence: given a category :root, return every category in its subtree — all descendants, to any depth.

The naive attempt, and why it's wrong

The instinct without recursion is to self-join a fixed number of times:

sql

-- WRONG: hard-codes the depth
SELECT c2.*
FROM categories c1
JOIN categories c2 ON c2.parent_id = c1.id
WHERE c1.parent_id = :root OR c1.id = :root;

Each JOIN reaches exactly one level deeper, so N joins reach exactly N levels. A real category tree is arbitrarily deep, so any fixed query silently misses everything below its last join — and you can't add “enough” joins because you don't know the depth. This is precisely the problem recursion exists to solve: repeat the “find my children” step until there are no more children.

The correct query

sql

WITH RECURSIVE subtree AS (
  SELECT id, name, parent_id
  FROM categories
  WHERE id = :root                       -- base: the root itself
  UNION ALL
  SELECT c.id, c.name, c.parent_id
  FROM categories c
  JOIN subtree s ON c.parent_id = s.id   -- recurse: children of found rows
)
SELECT * FROM subtree;

Follow the recursion levels expanding — the base grabs the root, then each pass grabs the children of the rows found in the previous pass, until a pass finds none:

The plan, and the index that makes it fast

The CREATE INDEX ON categories(parent_id) is the whole performance story. Without it, every single iteration re-scans the entire table to find children; with it, each iteration is a cheap index lookup keyed by the ids currently in the working table. That's exactly what the plan shows:

illustrative

CTE Scan on subtree  (cost=8.72..9.34 rows=31 width=40) (actual rows=6 loops=1)
  CTE subtree
    ->  Recursive Union  (cost=0.28..8.72 rows=31 width=40) (actual rows=6)
          ->  Index Scan using categories_pkey on categories  (cost=0.28..8.30 rows=1 width=40)
                Index Cond: (id = 42)
          ->  Nested Loop  (cost=0.28..0.80 rows=3 width=40) (actual rows=2 loops=3)
                ->  WorkTable Scan on subtree s  (cost=0.00..0.20 rows=10 width=4)
                ->  Index Scan using categories_parent_id_idx on categories c  (cost=0.28..0.56 rows=2 width=40)
                      Index Cond: (parent_id = s.id)
Planning Time: 0.14 ms
Execution Time: 0.09 ms

Read it top-down: the Recursive Union is the loop. Its first child, the base term, is an Index Scan on the primary key for id = 42. Its second child, the recursive term, is a Nested Loop joining a WorkTable Scan (the rows found last iteration) against an Index Scan on categories_parent_id_idx — so each known row's children are fetched by index, not by scanning the table. The loops=3 on the nested loop tells you the recursion ran three passes before drying up.

Adding depth and a cycle guard

Two production upgrades. Carry a depth counter and a path array; the path both records ancestry and lets you refuse to revisit a node — the safe way to survive a mis-entered cycle in what should be a tree:

sql

WITH RECURSIVE subtree AS (
  SELECT id, name, parent_id,
         1 AS depth,
         ARRAY[id] AS path
  FROM categories
  WHERE id = :root
  UNION ALL
  SELECT c.id, c.name, c.parent_id,
         s.depth + 1,
         s.path || c.id
  FROM categories c
  JOIN subtree s ON c.parent_id = s.id
  WHERE NOT c.id = ANY(s.path)          -- don't revisit a node
)
SELECT id, name, depth, path FROM subtree ORDER BY path;

Since PostgreSQL 14 you can let the engine track cycles for you with the CYCLE clause instead of hand-rolling the path check — it auto-adds a boolean marker column and a path column:

sql

WITH RECURSIVE subtree AS (
  SELECT id, name, parent_id FROM categories WHERE id = :root
  UNION ALL
  SELECT c.id, c.name, c.parent_id
  FROM categories c JOIN subtree s ON c.parent_id = s.id
) CYCLE id SET is_cycle USING path
SELECT id, name FROM subtree WHERE NOT is_cycle;

Narrate it

If an interviewer asks you to talk through this: “It's an adjacency-list tree, so I walk it with a recursive CTE. The base term selects the root by primary key. The recursive term joins the table to the working set on child.parent_id = found.id, which descends exactly one level per iteration; UNION ALL accumulates them and the recursion stops when a level has no children. The index on parent_id turns each iteration into an index lookup, so the plan is a Recursive Union over a WorkTable Scan joined to an index scan. If the data might contain cycles rather than being a strict tree, I carry a path array and add WHERE NOT id = ANY(path), or use the CYCLE clause on PG14+.” That answer hits the model, the plan, and the failure mode — everything the question is probing.

05 Drills & traps

Graded drills, then the traps

Attempt each before opening its solution. They rise in difficulty from “readability” to “bend the planner to your will.”

Drill 1 — a three-step chained report

From sales(id, product_id, sold_at, amount) and products(id, category), produce each category's revenue and its share of total revenue, using a chain of CTEs so the logic reads top-down.

Try it first, then read

sql

WITH per_cat AS (                    -- 1. revenue per category
  SELECT p.category, sum(s.amount) AS revenue
  FROM sales s
  JOIN products p ON p.id = s.product_id
  GROUP BY p.category
),
grand AS (                             -- 2. the grand total
  SELECT sum(revenue) AS total FROM per_cat
)
SELECT c.category, c.revenue,        -- 3. combine into a share
       round(100.0 * c.revenue / g.total, 1) AS pct
FROM per_cat c CROSS JOIN grand g
ORDER BY c.revenue DESC;

Why: grand is referenced once so it inlines to a scalar; the CROSS JOIN to a one-row CTE is the clean way to divide every category by the same total.

Drill 2 — generate a series recursively

Produce the first day of every month in 2026 (Jan through Dec) with a recursive CTE — no generate_series.

Try it first, then read

sql

WITH RECURSIVE months(m) AS (
  SELECT date '2026-01-01'
  UNION ALL
  SELECT (m + interval '1 month')::date
  FROM months
  WHERE m < date '2026-12-01'
)
SELECT m FROM months;

Why: the base fixes the column type to date, so the recursive term casts m + interval back to date to match; the WHERE m < '2026-12-01' is the termination guard. In real code you'd write generate_series('2026-01-01'::date, '2026-12-01', '1 month') — but knowing the recursive form proves you understand the mechanism.

Drill 3 — a tree with depth and a breadcrumb path

From the categories table, list every category with its depth and a human breadcrumb like Electronics > Laptops > Gaming, ordered so children sit under their parents.

Try it first, then read

sql

WITH RECURSIVE tree AS (
  SELECT id, name, parent_id,
         1 AS depth,
         name AS path
  FROM categories
  WHERE parent_id IS NULL                 -- start at every root
  UNION ALL
  SELECT c.id, c.name, c.parent_id,
         t.depth + 1,
         t.path || ' > ' || c.name
  FROM categories c
  JOIN tree t ON c.parent_id = t.id
)
SELECT depth, path FROM tree ORDER BY path;

Why: the base starts at roots (parent_id IS NULL); each level concatenates the child's name onto the parent's path, and ORDER BY path gives a stable, indented-looking pre-order listing.

Drill 4 — force MATERIALIZED to stop recomputation

A CTE computes an expensive per-row score with a slow function. Because it's referenced only once, Postgres inlines it — and can end up evaluating slow_score() more times than you intend (once to join, again in the outer filter). Make it compute exactly once.

Try it first, then read

sql

WITH scored AS MATERIALIZED (        -- compute once, into a worktable
  SELECT id, slow_score(id) AS score
  FROM candidates
  WHERE active
)
SELECT s.id, s.score
FROM scored s
JOIN other o ON o.cand_id = s.id
WHERE s.score > 0.9;

Why: MATERIALIZED pins scored as a single CTE Scan, so slow_score() runs once per candidate instead of being re-derived wherever the planner inlines it. This is the modern, legitimate use of the keyword — a deliberate choice, not a reflex.

Traps to sidestep

  • Assuming “CTE = fence.” False since PostgreSQL 12 for a non-recursive, side-effect-free, singly-referenced CTE — it inlines. Don't wrap a subquery in a CTE expecting to force materialization; write MATERIALIZED if you actually mean it.
  • Infinite recursion. No termination guard, or a cyclic graph, and the query runs until it exhausts resources. Always give the recursive term a reason to eventually return zero rows: a bound, UNION instead of UNION ALL, a path-array check, or the CYCLE clause.
  • Forward-referencing a CTE. A CTE can only see CTEs defined before it (a recursive CTE seeing itself is the sole exception). If a needs b, define b first.
  • A huge MATERIALIZED CTE that kills a good plan. Forcing materialization blocks filter push-down and index use inside the CTE — occasionally you turn a fast index scan into a full materialize-then-filter, exactly the 50-million-row disaster from section 02. Reach for MATERIALIZED deliberately, then re-check the plan.
★ Review

Summary & self-test

One idea holds the lesson together: a CTE names a step. Naming steps makes a complex query readable top-down; letting a step name itself (WITH RECURSIVE) is how SQL walks trees and sequences; and since PostgreSQL 12 a plain CTE plans like a subquery unless you say otherwise.

01WITH names a subqueryA query-scoped, temporary result you SELECT from by name — turning inside-out nesting into a top-down pipeline.
02Chain, backward-onlyComma-separate multiple CTEs; each may reference those defined before it. No forward references (except a recursive CTE to itself).
03Not a fence since PG12A non-recursive, side-effect-free, singly-referenced CTE inlines by default and plans like a subquery.
04MATERIALIZED / NOTForce compute-once (a CTE Scan) or force inlining. Recursive and multiply-referenced CTEs materialize automatically.
05Windows need their own CTEYou can't filter a window result in WHERE; compute rank() in a CTE and filter it in the outer query.
06RECURSIVE = base ∪ selfBase term UNION ALL a recursive term referencing the CTE; iterate the working table until a pass returns zero rows.
07Guard the recursionTerminate with a bound, UNION dedup, a path-array check, or the PG14 CYCLE clause — or it runs forever.
08Index the recurse keyIndexing categories(parent_id) turns each iteration into an index lookup — a Recursive Union over a WorkTable Scan + Index Scan.
