Schema Design Workshop

The interview question that separates people is not "write a query" — it is "design the schema for this system." Here you turn a vague product ("build ticketing") into tables that stay correct and answer the real queries fast. You will practice one repeatable method — requirements, entities, relationships, keys, constraints, then the index plan — and narrate it the way a senior engineer does at the whiteboard.

Original study notes. Written from scratch, tested against PostgreSQL PG 17/18. This is a practice lesson: it ends in a worked SQL problem — a complete event-ticketing schema with its indexes and one deliberate denormalization — and a set of graded drills. Contains three interactive diagrams (press Play or step with Next): the design method, the entity build-up, and the finished schema. The rule that runs through all of it: make it correct first, then make it fast.
00 Orientation

Model the way the interview asks

By this point in the course you know the pieces in isolation: keys and normalization (Phase 1), joins and window functions (Phases 2–3), indexes and the planner (Phase 4), isolation and MVCC (Phase 5), JSONB and partitioning (Phase 6), replication and operations (Phases 7–8). A design question asks you to assemble them under time pressure, out loud, from a one-line prompt. That is a different skill from any single query, and it is the most common senior-level database screen there is.

The failure mode is jumping straight to CREATE TABLE. Strong candidates slow down for sixty seconds and follow a method, because the method is what makes the answer defensible. Here is the whole pipeline you will run every time:

  • Requirements — what does the system do, and which queries must be fast? Nouns become tables; verbs become the access patterns you index for.
  • Entities & attributes — the real-world things (user, event, booking) and the typed columns that describe them.
  • Relationships — how entities connect: one-to-many (an event has many bookings) and many-to-many (a user attends many events; an event has many attendees), the latter resolved by a junction table.
  • Keys — a primary key names each row; foreign keys wire the relationships together by value.
  • Constraints — NOT NULL, UNIQUE, CHECK, and FK actions that make bad states impossible, not merely unlikely.
  • Indexes for the queries — only now, and only driven by the access patterns from step one.

Notice the order is deliberate: structure and correctness come before performance. A missing constraint is a bug the database will happily let your application write forever; a missing index is a slowdown you can add in one line later. We spend the first five steps making the data correct, and the last step making the important reads fast.

What this lesson delivers

Three interactive diagrams walk the method, build up an entity-relationship (ER) sketch, and reveal a finished schema. Then a fully worked event-ticketing problem gives you the actual CREATE TABLEs, the two or three queries that matter, the indexes they need, and one denormalization with its justification. Finally, graded drills make you model a feed, a chat, and a marketplace from scratch.

01 The method

The design method, as a pipeline ▸

Treat the six steps as a pipeline where each stage feeds the next: the requirements decide the entities, the entities expose the relationships, the relationships demand keys, the keys and business rules become constraints, and the access patterns from step one — carried all the way down — decide the indexes. Run the packet through it once:

The single most valuable habit this diagram encodes is starting from the queries, not the tables. Before you draw a box, write the two or three sentences the product owner cares about: "show a user their upcoming bookings," "show which seats are taken for an event," "count how many tickets an event has sold." Those sentences are simultaneously your entity list, your relationship list, and your index list — you just have to read them three different ways.

Say it out loud

In the interview, narrate each stage as you go: "Requirements first — the hot queries are a user's bookings and an event's remaining seats. Entities: users, events, bookings. Relationship: users-to-events is many-to-many, so bookings is a junction. Keys: surrogate id on each, FKs on the junction. Constraints: one seat per event, one booking per user per event. Then the indexes." That monologue is the answer; the SQL just writes it down.

02 Worked design, part 1

Draw the entities and the ER shape ▸

Pick a concrete system so the method has something to bite on: an event-ticketing app. A user buys tickets to events; an event sells many tickets to many users. That last sentence is the whole modeling problem — it is a many-to-many relationship, and relational databases cannot store M:N directly. You resolve it the same way every time: introduce a junction table (also called an associative or bridge table) that holds one row per pairing, with a foreign key to each side. Watch the three entities and their links assemble (recap of the keys from Phase 1):

The move that trips people up is realizing you cannot put a "list of events" inside a user row, nor a "list of users" inside an event row — a relational column holds one value, not a list. The junction table bookings is the answer: it decomposes one M:N into two clean 1:M relationships (one user has many bookings; one event has many bookings). Every attribute of the pairing itself — the seat, the price paid, when it was booked — lives naturally on the junction row, which is exactly where it belongs.

M:N always becomes a junction table

Whenever a sentence has "many … many" in it — students take many courses, posts have many tags, orders contain many products — you need a third table with a foreign key to each side. A composite UNIQUE(a_id, b_id) on the junction stops duplicate pairings, and any data that describes the combination hangs off that middle table. Memorize this pattern; you will use it in almost every design question.

03 The trade-offs

The decisions you must narrate

A design answer is graded less on the tables and more on the trade-offs you name. Five choices come up in almost every question. You will not always pick the same side — the point is to show you know the axis exists and can justify your position for this system.

Normalize vs denormalize

Normalization (Phases 1–2) stores each fact once, so there is exactly one place to update it and no chance of two copies disagreeing. It is the correct default: start fully normalized. Denormalization — deliberately keeping a redundant copy, like a cached tickets_sold counter on events instead of COUNT(*)-ing bookings every page load — buys read speed at the cost of having to keep the copy in sync. Do it only when a measured read is too slow, and only with a plan (a trigger, or an update in the same transaction) to keep the copy honest. Premature denormalization is a classic anti-pattern: it invites data drift to solve a performance problem you do not yet have.

Surrogate vs natural keys

A surrogate key is a meaningless, system-generated id (bigint GENERATED ALWAYS AS IDENTITY); a natural key is a real-world identifier (an email, an ISBN, a country code). Prefer a surrogate primary key: it never changes, it is small and fast to index and join on, and it does not leak business meaning. Keep the natural key too — but enforce it as a UNIQUE constraint, not as the primary key, so that when the "unique" business value turns out not to be (people change emails, ISBNs get reused) you are not re-keying half your database.

The index plan

Indexes (Phase 4) are decided by the access patterns, not sprinkled on hopefully. Index the columns you filter, join, and sort on — especially every foreign key you query through, because Postgres does not auto-create an index on the referencing side of an FK, and an unindexed FK means slow lookups and slow cascaded deletes. But indexes are not free: each one slows every write and consumes disk, so a table drowning in unused indexes is its own anti-pattern. Add the ones your queries prove they need; drop the ones pg_stat_user_indexes shows are never scanned.

Partitioning at scale

Declarative partitioning (Phase 6) splits one huge table into per-range/list/hash child tables. It earns its keep at roughly ten million rows and up, especially for time-series data: partition bookings by created_at and old months can be detached and archived in one metadata operation, while queries that filter on the partition key are pruned to just the relevant children. It is a scale tool, not a starting point — too many partitions add planning overhead, and the partition key must be part of every primary key and unique constraint, which constrains the design. Mention it as "how this evolves," not as day-one structure.

Multi-tenancy

If the system serves many customers (Phase 8), decide how tenants are isolated. The common pattern is a shared schema with a tenant_id column on every table, enforced by Row-Level Security so each query is auto-filtered to the current tenant and one customer can never read another's rows. Index that tenant_id column, and make it the leading column of composite indexes, because every query carries it.

The meta-rule under all five

Correct first, then fast. Every trade-off above is really the same question — how much correctness am I willing to trade for how much speed, and have I earned that trade with a measurement? Reach for the fast-but-riskier option (denormalize, drop a constraint, add a cache) only after a normalized, constrained design proves too slow with real numbers. In an interview, stating this principle unprompted signals seniority more than any single table does.

04 Worked problem

The full worked schema ▸

Now assemble the whole thing. Here is the finished event-ticketing schema, the queries it must serve, the indexes those queries need, and the one denormalization we can justify. Read it as an interview answer: each clause is a decision you can defend.

1 · The schema

sql

CREATE EXTENSION IF NOT EXISTS citext;   -- case-insensitive text type (not built-in)

-- one identity per person; email is a natural key kept as UNIQUE, not PK
CREATE TABLE users (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       citext      NOT NULL UNIQUE,
  full_name   text        NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

-- tickets_sold is a DENORMALIZED counter (justified below)
CREATE TABLE events (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name         text        NOT NULL,
  venue        text        NOT NULL,
  starts_at    timestamptz NOT NULL,
  capacity     integer     NOT NULL CHECK (capacity > 0),
  tickets_sold integer     NOT NULL DEFAULT 0 CHECK (tickets_sold >= 0),
  CHECK (tickets_sold <= capacity)          -- never oversell
);

-- the junction: one row per (user, event) pairing
CREATE TABLE bookings (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint      NOT NULL REFERENCES users(id),
  event_id   bigint      NOT NULL REFERENCES events(id) ON DELETE CASCADE,
  seat       text        NOT NULL,
  status     text        NOT NULL DEFAULT 'confirmed'
                CHECK (status IN ('confirmed', 'cancelled')),
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (event_id, seat),        -- one physical seat sold once
  UNIQUE (user_id, event_id)      -- one booking per user per event
);

Every line is a decision: surrogate bigint identity PKs; citext + UNIQUE for a case-insensitive email that is a natural key but not the PK; timestamptz (never naive timestamp) for anything time-related; NOT NULL on every column that has no meaningful "unknown"; two CHECKs that make overselling and negative counts impossible; and two UNIQUEs that encode the real business rules directly in the schema so no application bug can violate them.

2 · The queries that matter

The product cares about two hot reads. First, a user's bookings, newest first — the account page:

sql

SELECT b.id, e.name, e.starts_at, b.seat, b.status
FROM bookings b
JOIN events e ON e.id = b.event_id
WHERE b.user_id = 42
ORDER BY b.created_at DESC;

Second, "how many tickets has this event sold?" for the event page — and this is the one that motivates a design decision, so hold it for the denormalization step.

3 · The naive attempt, and why it is slow

Ship the schema with no extra indexes and run the account-page query on a bookings table of a million rows. The planner has no index on user_id, so it reads the entire table and throws away everything that is not user 42:

EXPLAIN ANALYZE · illustrative

Sort  (cost=24680.12..24680.15 rows=12 width=48)
        (actual time=118.4..118.4 rows=12 loops=1)
  Sort Key: b.created_at DESC
  ->  Hash Join  (cost=... rows=12 width=48)
        ->  Seq Scan on bookings b  (cost=0.00..24500.00 rows=12)
              Filter: (user_id = 42)
              Rows Removed by Filter: 999988
Planning Time: 0.2 ms
Execution Time: 118.7 ms

The tell is Seq Scan on bookings with Rows Removed by Filter: 999988 — the database touched a million rows to return twelve. The same query for the event page, computing sold counts with SELECT count(*) FROM bookings WHERE event_id = ... on every request, scans thousands of rows per event view. Both are the correct answer computed the expensive way.

4 · The fix: index for the access pattern

Give the planner the index the query is begging for — the filter column first, then the sort column, so one index both finds the rows and returns them pre-ordered:

sql

-- covers WHERE user_id = ? ORDER BY created_at DESC in one shot
CREATE INDEX bookings_user_created_idx
  ON bookings (user_id, created_at DESC);

-- the FK to events is queried through, so index it too;
-- (event_id, seat) UNIQUE already indexes event_id on its left edge)

Re-run the account-page query and the plan changes shape entirely:

EXPLAIN ANALYZE · illustrative

Nested Loop  (cost=0.85..96.20 rows=12 width=48)
        (actual time=0.04..0.11 rows=12 loops=1)
  ->  Index Scan using bookings_user_created_idx on bookings b
        (cost=0.42..8.61 rows=12 width=24)
        Index Cond: (user_id = 42)
  ->  Index Scan using events_pkey on events e
        Index Cond: (id = b.event_id)
Planning Time: 0.3 ms
Execution Time: 0.15 ms

Seq Scan is gone; the plan is an Index Scan whose Index Cond: (user_id = 42) jumps straight to the twelve rows, already in created_at DESC order (no separate Sort node), then a Nested Loop looks up each event by primary key. Execution drops from ~119 ms to a fraction of a millisecond. Same SQL, same data — a different plan, because we handed the planner a better option.

5 · The one justified denormalization

The event page needs a sold count on every view. Even indexed, count(*) over all of an event's bookings is O(rows sold) and runs constantly on the busiest pages. This is the moment denormalization earns its place: store tickets_sold directly on events and keep it correct with a trigger, so the read becomes a single-row lookup and the CHECK (tickets_sold <= capacity) also gives you an atomic oversell guard.

sql

CREATE FUNCTION sync_tickets_sold() RETURNS trigger AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    UPDATE events SET tickets_sold = tickets_sold + 1
      WHERE id = NEW.event_id;
  ELSIF TG_OP = 'DELETE' THEN
    UPDATE events SET tickets_sold = tickets_sold - 1
      WHERE id = OLD.event_id;
  END IF;
  RETURN NULL;
END; $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_tickets_sold
  AFTER INSERT OR DELETE ON bookings
  FOR EACH ROW EXECUTE FUNCTION sync_tickets_sold();

Why this is a good trade and not premature: the count is read far more than it is written, the source of truth (the bookings rows) still exists so the cache can always be rebuilt, and the update runs in the same transaction as the booking, so the two can never disagree. That is the discipline — denormalize a proven-hot read, keep the source of truth, and make the copy transactionally consistent.

6 · How it evolves

At ten million bookings, partition bookings by RANGE (created_at) so old seasons detach and archive cheaply and date-filtered queries prune to a few children (its PK/uniques would then need to include created_at). If the app becomes multi-tenant per organizer, add a tenant_id column and Row-Level Security. If reporting load grows, send analytics to a read replica or a warehouse rather than burdening the OLTP primary. All of that is Phase 6–8 work — and the next lesson (L52) takes this exact schema through a zero-downtime migration to add a feature.

Narrate it as one answer: "Three tables. Surrogate bigint identity keys everywhere; email is a unique natural key, not the PK. bookings is the junction resolving the user-to-event many-to-many, with two UNIQUEs encoding the real rules — one seat sold once, one booking per user per event — and a CHECK that makes overselling impossible. The hot query is a user's bookings newest-first, so a composite index on (user_id, created_at DESC) serves the filter and the sort together; the FK to events is indexed by the unique constraint's left edge. The event page reads a sold count constantly, so I denormalize tickets_sold onto events, kept correct by a trigger in the same transaction, with the booking rows still the source of truth. At scale, partition bookings by month; for multi-tenancy, add tenant_id with RLS." That is a complete, defensible answer.

05 Drills & traps

Model these yourself

Each prompt below is the kind of one-liner an interviewer drops on the table. Do the full method — requirements, entities, relationships, keys, constraints, index plan — and sketch the tables before you open the reveal. Difficulty climbs from drill 1 to drill 3.

Drill 1 · A social feed

Model a Twitter-style feed: users write posts, users follow other users, and users like posts. What tables, keys, and the one relationship shape that traps beginners?

Try it first, then read

users(id PK, handle UNIQUE, ...), posts(id PK, author_id FK→users, body, created_at). Two junctions: follows(follower_id FK→users, followee_id FK→users, PRIMARY KEY(follower_id, followee_id), CHECK(follower_id <> followee_id)) — a self-referential M:N — and likes(user_id FK, post_id FK, PRIMARY KEY(user_id, post_id)) so a like is idempotent. Indexes: posts(author_id, created_at DESC) for a profile timeline; follows(follower_id) to fan out a home feed. Why: "follow" is a many-to-many from users to users, which surprises people — both foreign keys point at the same table, and the CHECK stops self-follows.

Drill 2 · A chat app

Model group chat: users belong to conversations, conversations hold messages. Support both 1:1 and group conversations with the same structure.

Try it first, then read

conversations(id PK, created_at), a membership junction conversation_members(conversation_id FK, user_id FK, PRIMARY KEY(conversation_id, user_id), joined_at), and messages(id PK, conversation_id FK→conversations, sender_id FK→users, body, created_at). A 1:1 chat is just a conversation with two members — no special case. Index: messages(conversation_id, created_at DESC) is the single most important one; it powers "load the latest messages in this conversation" and paginates cleanly with keyset pagination on created_at. Why: putting membership in its own table (not a user_id array on conversations) keeps it queryable, constrainable, and indexable in both directions.

Drill 3 · A marketplace

Model an e-commerce marketplace: sellers list products, buyers place orders, and an order contains many products at the price and quantity at purchase time. What must you not do with money and with the line-item price?

Try it first, then read

sellers, products(id PK, seller_id FK, name, price_cents, ...), orders(id PK, buyer_id FK, status, placed_at), and the crucial junction order_items(order_id FK, product_id FK, quantity CHECK(quantity > 0), unit_price_cents, PRIMARY KEY(order_id, product_id)). Two traps: (1) store money as numeric or integer cents, never float — binary floats cannot represent 0.10 exactly and will lose pennies; (2) copy the price onto order_items.unit_price_cents at purchase time rather than joining live to products.price — the product's price changes tomorrow, but the order must forever show what the buyer actually paid. That is a legitimate, required denormalization: a historical snapshot, not a cache. Index the FKs: order_items(product_id) for "who bought this product," orders(buyer_id, placed_at DESC) for order history.

The anti-patterns to name and avoid

  • EAV (entity-attribute-value) — a generic (entity, attribute, value) table to store "anything." It defeats types, constraints, and the planner; every read becomes a self-join pile-up. If you need flexible attributes, use a jsonb column on a real table and promote hot fields to real columns.
  • The God table — one wide table with 80 nullable columns bolting several entities together. Split it along its natural entities; nullable columns that are "only for type X rows" are the smell.
  • No constraints — treating the database as a dumb store and validating only in the app. The app has bugs and races; the database is the last line of defense. Encode the rule as NOT NULL / UNIQUE / CHECK / FK so bad data is impossible, not just discouraged.
  • Premature denormalization — caching a count or copying a field before you have measured a slow read. You have signed up for sync bugs to solve a problem you do not have.
  • Unindexed foreign keys — Postgres does not auto-index the referencing side. The FK lookups and the cascaded deletes both do sequential scans until you add the index yourself.
★ Review

Summary & self-test

The one idea: a schema is designed, not typed — run the method (requirements → entities → relationships → keys → constraints → indexes-for-the-queries), make it correct with constraints first, then make the proven-hot reads fast with the right index, and be able to defend every clause out loud.
