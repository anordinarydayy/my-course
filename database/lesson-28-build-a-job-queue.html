Build a Job Queue

"Do I really need a message broker for background jobs?" is a classic interview question, and the surprising answer is often no — PostgreSQL already ships the two ingredients a correct queue needs: row locks and transactions. In this practice lesson you build a concurrent worker queue directly in the database, starting from the naive version that hands the same job to two workers and fixing it with one clause, FOR UPDATE SKIP LOCKED. By the end you will have a complete schema, an atomic claim query, retries with backoff, and a stuck-job reclaimer — the exact pattern behind tools like que, graphile-worker, and River.

Original study notes. Written from scratch for engineers who want database depth that pays off in interviews and in real systems. All SQL is valid PostgreSQL and current as of PG 17/18. 28 Motivation

A queue inside your database

A job queue is one table of work to be done later: send this email, resize that image, retry this webhook. Some worker processes poll the table, each grabs a job, does the work, and marks it finished. The whole design question is coordination — how do many workers share one table without stepping on each other?

You could reach for a dedicated broker, but doing it in Postgres buys you something a broker cannot: your jobs live in the same database as your data, so enqueuing a job is transactional with the change that caused it. Create an order and enqueue its confirmation email in one transaction — either both commit or neither does. There is no window where the order exists but the email job was lost, and no window where the job fired for an order that rolled back. And there is no extra service to run, monitor, or secure.

Whatever the mechanism, a real queue owes you four guarantees:

  • Exactly-one delivery per attempt. Each job is handled by one worker at a time — never two at once.
  • No double-processing. Two workers polling simultaneously must not both claim the same row.
  • Retries. A job that throws should be tried again — with a cap, so a poison job cannot loop forever.
  • Ordering. Older jobs (or higher-priority ones) should generally go first.
When a broker wins instead

This pattern is excellent from small scale up through a healthy chunk of production traffic — thousands of jobs per second is very achievable. But at genuinely high throughput, or when you need fan-out to many consumer groups, features like dead-letter routing, or cross-service delivery, a purpose-built broker (the subject of the RabbitMQ course) earns its keep. Reach for the database queue first; graduate to a broker when you have measured a reason to.

28 The race

The naive queue and its race ▸

The obvious first attempt reads the oldest pending row, then flips it to running in a second statement:

sql

-- Worker: step 1, find a job
SELECT id FROM jobs
WHERE  status = 'pending'
ORDER BY created_at
LIMIT  1;

-- Worker: step 2, claim it (separate statement, using the id from step 1)
UPDATE jobs SET status = 'running' WHERE id = $1;

With one worker this is fine. With two, it is broken. Nothing stops both workers from running the SELECT in the same instant, before either has run its UPDATE. Both see the row as pending, both take its id, both flip it to running, and both do the work. That is a lost update / double-processing bug — the confirmation email goes out twice, the charge is applied twice. Step through exactly how the two workers collide:

The instinct is to add FOR UPDATE to the SELECT, taking a row lock. That fixes correctness — the second worker now blocks until the first commits, so it never processes the same row. But it fixes it the wrong way: plain FOR UPDATE makes the second worker wait for the locked row, and it is still waiting for that exact row when the first worker releases it. Your pool of workers collapses into a single-file line, all queuing for whichever row is at the front. Correct, but serial — you have thrown away all your concurrency.

The shape of the fix

What you actually want is for the second worker to say: "that row is taken? Skip it and give me the next free one." Not "block on it." That single change — skip locked rows instead of waiting on them — is the whole trick, and Postgres has a clause for exactly it.

28 The fix

FOR UPDATE SKIP LOCKED ▸

Add SKIP LOCKED to a locking SELECT and Postgres changes the rule: instead of waiting for a row another transaction has locked, it silently steps over it and returns the next row that is free to lock. Each worker locks the oldest unlocked pending row:

sql

SELECT id FROM jobs
WHERE  status = 'pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT  1;

Now two workers running at the same instant do not collide. Worker 1 locks job #1; Worker 2 reaches #1, sees it locked, skips it, and locks job #2 instead. Both hold different rows, both proceed — no blocking, no double-processing. Watch it play out:

Three properties make this the standard answer. It is non-blocking: no worker ever waits on another, so throughput scales with your worker count. It is correct: the row lock guarantees only one worker holds a given row, so nothing is double-claimed. And it degrades gracefully: add more workers than there are ready jobs and the extras simply get empty results and poll again — they never pile up on a lock.

SKIP LOCKED is deliberately "wrong" for reads

SKIP LOCKED returns an inconsistent snapshot on purpose — it silently omits rows it could not lock. That is exactly what you want for a queue (any free job will do) and exactly what you must never use for a report or a count, where skipping rows would drop data. Reach for it only when "give me any available rows, I don't care which" is truly the intent.

28 The pattern

The full claim pattern

Two statements — a SELECT then an UPDATE — leave a gap where a worker could crash after selecting but before claiming. Collapse them into one atomic statement: an UPDATE whose target row is chosen by the SKIP LOCKED subquery, returning the claimed row so the worker knows what to do:

sql

UPDATE jobs
SET    status = 'running',
       locked_at = now(),
       attempts = attempts + 1
WHERE  id = (
  SELECT id FROM jobs
  WHERE  status = 'pending' AND run_after <= now()
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED
  LIMIT  1
)
RETURNING *;

That one statement is the claim. The inner SELECT picks the oldest ready-and-unlocked job and locks it; the outer UPDATE flips it to running, stamps locked_at, and bumps the attempt counter; RETURNING * hands the whole row back to the worker. If the queue is empty, zero rows come back and the worker sleeps a moment before polling again. Around that claim, a worker's life is a small loop:

  • Claim one job with the statement above.
  • Process it — do the actual work, outside a long transaction (more on why in the traps).
  • Mark done on success (status = 'done'), or on failure decide between a retry and giving up.

Retries with backoff. The attempts counter (already incremented at claim time) is your retry budget. On failure, if the job still has attempts left, set it back to pending but push run_after into the future so it is not retried instantly. The formula below is a simple linear backoff (10s, 20s, 30s…); many systems prefer exponential — run_after = now() + base * power(2, attempts). Once attempts crosses a cap, park it as failed so a poison job cannot loop forever.

Reclaiming stuck jobs. A worker can crash mid-job, leaving a row stranded in running forever. That is what locked_at is for: a periodic sweeper flips any running row whose locked_at is older than a timeout back to pending, so another worker can pick it up. This is your at-least-once safety net.

Keeping the scan tiny. As jobs complete, done rows pile up — but the claim only ever cares about pending ones. A partial index indexes exactly those:

sql

CREATE INDEX jobs_pending_idx ON jobs (created_at)
  WHERE status = 'pending';

Because the index only contains pending rows, it stays small no matter how many millions of finished jobs sit in the table, and it delivers them already sorted by created_at — so the claim is an index scan over a handful of entries, not a scan of the whole table.

Why RETURNING closes the gap

Folding select-and-claim into one UPDATE ... RETURNING means the row is chosen, locked, and marked running in a single atomic step. There is no instant where a job is "selected but not yet claimed," so a worker crash can never leak a half-claimed job. The claim is all-or-nothing — Atomicity doing exactly its job.

28 Worked build

The complete build ▸

Now assemble the whole thing. Read the task, try to write each piece yourself, then check against the worked answer. First, see the healthy lifecycle you are building toward — two workers, two different jobs, each running claim → process → done exactly once:

1 · The schema

Six columns carry everything a worker needs: an identity key, the work itself as jsonb, a status, a retry counter, a "not before" timestamp for delays and backoff, and a lock timestamp for reclaiming crashes.

sql

CREATE TABLE jobs (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  payload    jsonb        NOT NULL,
  status     text         NOT NULL DEFAULT 'pending',
  attempts   int          NOT NULL DEFAULT 0,
  run_after  timestamptz  NOT NULL DEFAULT now(),
  locked_at  timestamptz,
  CHECK (status IN ('pending', 'running', 'done', 'failed'))
);

CREATE INDEX jobs_pending_idx ON jobs (created_at)
  WHERE status = 'pending';

noteThe partial index above orders on created_at, so add a created_at timestamptz NOT NULL DEFAULT now() column too — shown separately here only to keep the six "moving parts" columns in focus.

2 · The task

You have the table. Write: (a) the wrong naive claim and say why it fails; (b) the correct atomic claim; (c) the worker's success and failure updates, with capped retries and backoff; (d) the stuck-job reclaimer. Try each before reading on.

3 · The naive claim, and why it is wrong

sql

-- WRONG: a plain SELECT takes no lock, so two workers
-- can both read the same row as pending and both claim it.
SELECT id FROM jobs
WHERE  status = 'pending'
ORDER BY created_at
LIMIT  1;
-- ...then a separate UPDATE ... SET status='running' WHERE id=$1;
-- Between the SELECT and the UPDATE, another worker slips in. Double-processing.

4 · The correct claim + worker loop

The atomic claim from section 03 does the hard part. Then the worker either marks the job done, or — on failure — retries with backoff until the cap, and only then gives up:

sql

-- CLAIM: atomic select-and-lock-and-mark-running
UPDATE jobs
SET    status = 'running', locked_at = now(), attempts = attempts + 1
WHERE  id = (
  SELECT id FROM jobs
  WHERE  status = 'pending' AND run_after <= now()
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED
  LIMIT  1
)
RETURNING *;

-- SUCCESS: worker finished the payload cleanly
UPDATE jobs SET status = 'done', locked_at = NULL WHERE id = $1;

-- FAILURE: retry with linear backoff, or give up after 5 tries
UPDATE jobs
SET    status = CASE WHEN attempts >= 5 THEN 'failed' ELSE 'pending' END,
       run_after = now() + (interval '10 seconds' * attempts),
       locked_at = NULL
WHERE  id = $1;

Note that attempts was already incremented by the claim, so the failure update reads the true count. The backoff interval '10 seconds' * attempts spreads retries out — 10s, 20s, 30s — instead of hammering a failing dependency.

5 · The stuck-job reclaimer

Run this on a schedule (say every minute) from a sweeper. Anything left running past the timeout is presumed dead and returned to the pool:

sql

UPDATE jobs
SET    status = 'pending', locked_at = NULL
WHERE  status = 'running'
  AND  locked_at < now() - interval '5 minutes';

6 · What the planner does with the claim

The point of the partial index is that the claim never scans the growing table. An illustrative EXPLAIN of the whole claim shows the InitPlan (the subquery) doing an index scan on jobs_pending_idx wrapped in a LockRows node (that is where FOR UPDATE SKIP LOCKED lives), and the outer Update finding its one target row by primary key:

text

Update on jobs  (cost=0.43..8.47 rows=0 ...)
  InitPlan 1 (returns $1)
    ->  Limit  (cost=0.43..0.48 rows=1 ...)
          ->  LockRows  (cost=0.43..8.46 rows=1 ...)
                ->  Index Scan using jobs_pending_idx on jobs jobs_1
                      Filter: (run_after <= now())
  ->  Index Scan using jobs_pkey on jobs
        Index Cond: (id = $1)

An Index Scan using jobs_pending_idx — not a Seq Scan on jobs — is the line that tells you the queue will stay fast at ten million completed rows. If you ever see a sequential scan here, your partial index is missing or unused, and the claim's cost is growing with the whole table.

Narrate it in an interview

"One table; workers claim with a single UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING *, so the pick, the lock, and the status flip are atomic. SKIP LOCKED keeps workers concurrent instead of serialized; a partial index on pending rows keeps the scan tiny; attempts plus run_after give capped retries with backoff; and a locked_at timeout reclaims crashed workers." That is the whole design in four sentences. The same idempotent-claim idea returns in Phase 8, where an inbox table dedupes incoming events the same way — claim-once, process-once.

28 Drills

Graded drills & traps

Attempt each drill on paper before opening its answer. They all build on the claim from section 04.

Drill 1 — Claim a batch of N jobs

A worker that claims one job at a time makes one round-trip per job. Rewrite the claim to grab up to 10 jobs in a single statement.

Try it first, then read

Swap the id = (...) equality for id IN (...) and lift the LIMIT to 10 — the subquery still uses FOR UPDATE SKIP LOCKED, so the batch is a set of distinct, unlocked rows:

UPDATE jobs SET status = 'running', locked_at = now(), attempts = attempts + 1
WHERE  id IN (
  SELECT id FROM jobs
  WHERE  status = 'pending' AND run_after <= now()
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED
  LIMIT  10
)
RETURNING *;

Drill 2 — Schedule a job for later

Enqueue a job that must not run until one hour from now. Change nothing in the claim.

Try it first, then read

The claim already filters on run_after <= now(), so delay is just an insert with a future run_after — no worker will touch it until the clock catches up:

INSERT INTO jobs (payload, run_after)
VALUES ('{"kind":"reminder"}', now() + interval '1 hour');

Drill 3 — Reclaim jobs stuck past a timeout

Write the sweep that returns jobs stranded in running for more than 2 minutes back to the pool.

Try it first, then read

Compare locked_at to now() minus the timeout interval:

UPDATE jobs SET status = 'pending', locked_at = NULL
WHERE  status = 'running'
  AND  locked_at < now() - interval '2 minutes';

Drill 4 — Turn it into a priority queue

Add a priority int NOT NULL DEFAULT 0 column and make high-priority jobs jump the line while ties still run oldest-first.

Try it first, then read

Change only the ORDER BY in the claim's subquery — highest priority first, oldest-created as the tiebreaker (and a partial index on (priority DESC, created_at) WHERE status = 'pending' to keep it fast):

  -- inside the claim's inner SELECT:
  ORDER BY priority DESC, created_at
The four traps that break real queues

(1) Omitting SKIP LOCKED. Plain FOR UPDATE is correct but serializes every worker onto the front-of-line row — your concurrency silently vanishes.
(2) No partial index. Without WHERE status = 'pending', the index (or scan) grows with every completed job, and claim latency creeps up as the table ages.
(3) Processing inside one long transaction. If you claim, do minutes of work, then commit — all in one transaction — you hold the row lock the whole time and bloat the table with dead tuples. Claim in a short transaction; process outside it; mark done in another short one.
(4) No retry cap. Infinite retries turn one poison job into an endless loop that burns a worker forever. Always cap attempts and park exhausted jobs as failed.

28 Review

Summary & self-test

The whole lesson compresses to one line: a correct database job queue is a single table plus one atomic claim — UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING * — surrounded by capped retries, backoff via run_after, a locked_at timeout for crashes, and a partial index on the pending rows. Everything else is a variation on that claim.

01Queue = one tableJobs live beside your data, so enqueuing is transactional with the change that caused it. No broker, no lost-email window.
02The naive raceSELECT-then-UPDATE lets two workers claim the same row and double-process it — a lost update.
03SKIP LOCKED is the fixLocked rows are skipped, not waited on, so workers claim different jobs concurrently — no blocking, no duplicates.
04Plain FOR UPDATE serializesCorrect but wrong: without SKIP LOCKED every worker queues on the front row and concurrency collapses.
05Atomic claimOne UPDATE ... RETURNING picks, locks, and marks running in a single step — no half-claimed gap on a crash.
06Retries + backoffAn attempts counter caps tries; pushing run_after forward spaces retries out so a failing dependency isn't hammered.
07Reclaim the stucklocked_at plus a timeout sweep returns crashed jobs to pending — the at-least-once safety net.
08Partial indexIndex only pending rows so the scan stays tiny as done rows pile into the millions.
