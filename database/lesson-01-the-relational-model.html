01Concept · Databases & SQL

The Relational Model

Lesson 00 showed you tables, primary keys, and foreign keys at a glance. Now we go one level down, to the thing those pictures are pictures of: the relational model, a formal, mathematical model of data that Edgar Codd defined in 1970. The formality is not academic decoration. It is exactly what buys you optimization, integrity, and composability — the three superpowers that let a database rewrite your query, refuse bad data, and let every operation feed the next.

00 The claim

What “relational” actually means

The word relational fools almost everyone at first. It sounds like it refers to tables relating to one another through foreign keys — the lines we drew in Lesson 00. It doesn’t. It refers to a precise object from set theory called a relation, introduced by Edgar F. Codd in his 1970 paper “A Relational Model of Data for Large Shared Data Banks.” A relation is a set of tuples drawn from typed domains. Every table you will ever write is one concrete instance of that idea, and understanding the idea is what separates people who use SQL from people who can reason about it.

Break the definition into its three words. A domain is a type — the set of all legal values, such as “all integers,” “all text strings,” or “all valid dates.” An attribute is a named slot backed by a domain, such as price over the domain numeric. A tuple is one value for each attribute — one complete row. A relation gathers those tuples into a set: unordered, and with no duplicates. That single sentence is the entire foundation of the trillion-dollar relational-database industry.

The model vs. its implementation

A relation is an abstract object. The table you see — rows on a screen, 8 KB pages in a heap file on disk, a B-tree index beside it — is one physical realization of that relation, not the relation itself. Codd’s decisive move was to split the logical model (what the data means) from the physical model (how it is stored). You query the logical picture; PostgreSQL is free to store, index, cache, and reorganise the physical one however it likes. That separation has a name we’ll keep returning to: data independence.

Why go to all this trouble to be formal? Because when your data is a set and your operations are defined mathematically on sets, the engine can treat your query as algebra. It can prove that two very different execution strategies return the exact same set, and then choose the cheaper one. It can rewrite WHERE a AND b into WHERE b AND a to evaluate the cheaper test first, push a filter down below a join, or turn a subquery into a join — all while guaranteeing the answer is unchanged. None of that is safe if a query is a procedure (a fixed list of steps); it is only safe because a query is a declaration over sets. Formality is what makes the optimizer possible. Keep that link in mind — it is the payoff for everything in this lesson.

01 Vocabulary

Anatomy of a relation ▸

Let’s make the four words concrete on one relation, products. Step the diagram and watch each term light up on the same table — a relation is the whole set; a tuple is one row; an attribute is a named typed column; a single value is drawn from that attribute’s domain. Two size measures matter enough to have names: the degree is the number of attributes (columns), and the cardinality is the number of tuples (rows).

In SQL, you declare a relation with CREATE TABLE, and every column carries its domain (its type). This is the products relation above, written as PostgreSQL:

sql

CREATE TABLE products (
  product_id  int            GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name        text           NOT NULL,
  price       numeric(10,2) NOT NULL,   -- money: exact, never float
  category    text           NOT NULL
);

Now the part that trips people up. In the pure model, a relation is a genuine mathematical set, which means it has no row order and no duplicate rows. Two tuples with identical values are the same tuple; asking “which row is first?” is meaningless. PostgreSQL, being a real system that stores rows in physical pages, relaxes both: a table can physically contain two identical rows, and rows sit somewhere on disk in some order. But you must never rely on that — a query with no ORDER BY may return rows in any order, and that order can change after an update or a VACUUM. Treat your tables as sets and add a key so duplicates can’t happen; that is how you keep the model’s guarantees on a physical engine.

Model vs. Postgres, item one

Model: no order, no duplicates. PostgreSQL: physical order exists and duplicates are possible unless a key forbids them. The lesson is not “Postgres is wrong” — it is that the model is the contract and the engine is the implementation. When you design as if the set rules hold (every relation has a key, order is never assumed), you get the model’s clean reasoning and the engine’s speed.

02 Identity

Keys — naming a row

If a relation is a set with no order, there is no “third row” to point at. So how do you ever refer to one specific tuple? By value — you name it with data it already contains. That is what a key is: a set of attributes whose values pick out exactly one tuple. Keys come in a small hierarchy, and getting the vocabulary straight now saves confusion for the rest of the course.

Superkey

  • Any set of columns whose values are unique across all rows.
  • Can be “too big” — may include columns not needed for uniqueness.
  • e.g. {product_id, name} is a superkey (but wasteful).

Candidate key

  • A minimal superkey — remove any column and uniqueness breaks.
  • A relation can have several.
  • e.g. {product_id}, and maybe {sku} too.

Primary key

  • The one candidate key you elect as the row’s official name.
  • Implies UNIQUE and NOT NULL.
  • Other candidates become UNIQUE constraints.

Read that left to right and it’s a funnel: every candidate key is a superkey (minimal ones); the primary key is the single candidate you promote to be the tuple’s official identity. Everything else that is also unique — a second candidate key like an email or a SKU — you declare with a UNIQUE constraint so the database enforces it too.

sql

CREATE TABLE products (
  product_id  int  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- surrogate key
  sku         text NOT NULL UNIQUE,                            -- a second candidate key (natural)
  name        text NOT NULL
);

Why must every relation have a key at all? Without one, two tuples could be byte-for-byte identical, and then no query, no foreign key, no update could target one without the other — you literally cannot name a row. A key is what makes rows individually addressable, and it is the anchor every relationship in your schema hangs off. Declaring a primary key is not a formality; it is the difference between a relation and a bag of indistinguishable rows.

One more rule that follows straight from the definition: a primary key can never contain NULL. NULL means “unknown,” and in SQL two unknowns are not considered equal (NULL = NULL is not true), so a null key value could neither guarantee uniqueness nor reliably identify a row. PostgreSQL enforces this for you: a PRIMARY KEY column is automatically NOT NULL. Note that GENERATED ALWAYS AS IDENTITY gives you a NOT NULL auto-incrementing number, but identity alone does not make a column unique — you still pair it with PRIMARY KEY (or UNIQUE) to get the guarantee.

Surrogate vs. natural — a one-line preview

A natural key is real-world data that happens to be unique (an ISBN, an email, a SKU). A surrogate key is a meaningless id the database mints for identity alone (an IDENTITY integer, or a uuidv7() in PG 18). Each has real trade-offs — stability, join size, exposure — and choosing between them is its own decision. We give it a full treatment in Lesson 05; for now, just know both are candidate keys, and one of them becomes the primary.

03 Relationships

Linking by value & referential integrity ▸

Here is the idea the whole model is named for, even if the name misleads. To say “this book was written by that author,” a relation does not hold a memory address of another row. It stores a value — a copy of the other relation’s key. That stored value is a foreign key. Step through two relations, authors and books, and watch the link form and then be enforced:

Three things in that sequence are worth naming out loud. First, the link is a value, not a pointer. books.author_id just holds the number 1; nothing is wired together in memory. Second, because it is a value, the join runs in either direction — “Le Guin’s books” and “this book’s author” are the same match seen from two sides, computed fresh at query time. Third, and most important, the database can check the value: referential integrity means the engine refuses to store a books row whose author_id points at no real author. You declare all of that in one line:

sql

CREATE TABLE books (
  id         int  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  author_id  int  NOT NULL REFERENCES authors (id),   -- the foreign key
  title      text NOT NULL
);

-- The database now enforces the reference:
INSERT INTO books (author_id, title) VALUES (99, 'Ghost');
-- ERROR: insert or update on table "books" violates foreign key constraint
--        Key (author_id)=(99) is not present in table "authors".

Contrast this with a linked structure in application memory, where a node holds a pointer to another node. That pointer is only valid inside one process, for the life of that process; it can dangle, and you cannot join two independent objects that were never wired together. A relational link is the opposite: it is just data, so it survives restarts, works across tables that were designed years apart, joins in any direction, and — because it is a value the engine understands — can be validated. Linking by value is the quiet decision that makes the whole model flexible and safe.

Model vs. Postgres, item two

Referential integrity is enforced, but the matching still costs work — and PostgreSQL does not automatically index a foreign-key column. It indexes the primary key it points to, not the author_id that points back. Leaving books.author_id unindexed makes “find all books by this author” a full scan, and makes deletes on authors slow. The fix is one line — CREATE INDEX ON books (author_id); — and we return to exactly why in Phase 4.

04 The algebra

Set-based thinking: relational operations ▸

Codd did not just define what data is; he defined a small set of operations on relations — the relational algebra. You don’t need the Greek to use SQL, but three operations carry most of the intuition, and each maps to a piece of a SELECT you already know:

  • Restrict / select (σ, the WHERE clause) — keep only the rows that pass a test. Fewer rows come out.
  • Project (π, the SELECT column list) — keep only the columns you asked for. Fewer columns come out.
  • Join (⋈) — combine two relations on matching values into one wider relation.

Now the property that makes all of this powerful: closure. Every relational operation takes relation(s) as input and produces a relation as output — never a number, never a list, never some other kind of thing. Output is the same kind as input, so operations compose: the result of a join can be restricted, the result of that restriction can be projected, and the whole chain is still a relation. Watch a single query run as that pipeline:

That whole pipeline is what the following four lines of SQL describe — and note you wrote them as one declaration of the result you want, not as the ordered steps of the figure:

sql

SELECT b.title, a.name          -- π  project: keep two columns
FROM books b
JOIN authors a ON a.id = b.author_id   -- ⋈  join: match on the value
WHERE b.price < 20;              -- σ  restrict: drop rows that fail

Two payoffs fall straight out of closure, and they are the reasons SQL feels the way it does. First, SQL is composable: because a query returns a relation, a query can appear anywhere a relation can — inside a FROM, a subquery, a WITH (CTE), or a view. You build big questions by nesting small, verified pieces. Second, SQL is declarative: since the operations are algebra with known equivalences, you state what relation you want and the planner is free to choose how — join first then filter, or filter first then join, whichever it estimates is cheaper. The figure’s top-to-bottom order is a mental model, not an execution order; PostgreSQL will reorder it freely as long as the resulting set is identical. That freedom is precisely the “formality buys optimization” claim from Section 00, now cashed in.

Think in sets, and closure does the rest

When you catch yourself planning a loop — “for each author, go fetch their books” — stop and describe the set instead: “authors joined to books, restricted, projected.” One relational expression replaces a nest of loops, and because every step is a relation, you can grow it without ever leaving the algebra. Set-based thinking is not a style preference; it is what lets the engine optimise on your behalf.

05 Reason about it

Why the model won

Step back and ask the historian’s question: the 1970s had perfectly good navigational databases — hierarchical and network models where you followed pointers by hand, hop by hop. They were fast. So why did the relational model, initially slower and dismissed by many as too abstract, take over the world? Reason through the three forces, because each one is a property we just built.

First, data independence. Because you query the logical relation and never the physical layout, the storage can change — new indexes, a different page layout, partitioning, a whole engine rewrite — without touching a single query. Applications written against 1990s SQL still run today. Navigational code, wired to a physical path, broke whenever the storage moved. Decoupling what from how is what let databases and applications evolve independently, and it is the single biggest reason the model endured.

Second, closure and composability. Every operation returns a relation, so queries nest without limit and a small language expresses enormous questions. You are never handed a special-case result you have to re-wrap; the output of one query is a legal input to the next. That is why SQL scaled from “get one row” to analytics over billions of rows using the same handful of operations.

Third, declarative optimization. Because the algebra has provable equivalences, the engine can rewrite your query and pick a plan — and it keeps getting smarter underneath your unchanged SQL. The same query you shipped last year runs faster this year because PostgreSQL’s planner and executor improved (PG 18, for instance, added an asynchronous I/O subsystem that can make large reads markedly faster, and B-tree skip scans). You inherit those gains for free — a dividend you only get because you described intent, not steps.

Now the honest part: the model bends in practice, and knowing where it bends is a mark of maturity, not heresy. Strict first-normal-form purity says every value is atomic — yet PostgreSQL gives you array columns and JSONB for semi-structured data, and sometimes you deliberately store a denormalized copy (a cached count, a duplicated name) to avoid a join on a hot path. None of these are “cheating.” They are deliberate trade-offs: you give up a slice of the model’s clean guarantees (a JSONB blob the engine can’t constrain as tightly; a denormalized copy you must now keep in sync) to buy something concrete (flexibility, or speed). The rule is simple — bend the model on purpose, with your eyes open, not by accident. The default is normalized relations with real keys and constraints; you depart from it only when a specific need justifies the cost.

Where this shows up next

★ Review

Summary & self-test

The whole lesson compresses to one idea: a relation is a formal object — a set of typed tuples, named by a key, linked to other relations by value, and transformed by operations that always return relations — and it is that formality, not the tabular look, that buys you integrity, composability, and an optimizer.
