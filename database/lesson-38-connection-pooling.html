Connection Pooling

A PostgreSQL connection is not a cheap socket — it is a whole operating-system process with its own memory. Open a few thousand of them and the database doesn't get faster, it falls over. This lesson builds the fix from first principles: why connections cost so much, how a pooler multiplexes many clients onto a few backends, the modes it can run in, the sharp edge of transaction pooling, and how to actually size and configure one for a real service.

00 The cost

Why a Postgres connection is heavy

Most databases you might have met treat a connection as a lightweight thread. PostgreSQL does not. Its architecture is process-per-connection: when a client connects, the postmaster fork()s a brand-new operating-system process — a backend — that lives for the entire life of that connection and does nothing but serve that one client. That design choice buys robustness (a crashing backend can't corrupt its neighbours) but it makes every connection expensive in three separate ways.

  • Setup cost. Each new connection pays for a process fork, authentication (SCRAM, and a TLS handshake if enabled), and backend initialization before it can run a single query. Opening a connection just to run one fast statement can cost more than the statement.
  • Standing memory. Every backend carries private memory — catalog caches, a relcache, prepared-statement state — commonly on the order of several megabytes even while idle, plus up to work_mem per sort or hash node while it runs a query. A thousand idle backends is gigabytes of RAM doing nothing.
  • Scheduling & contention. A machine with 4 or 8 CPU cores can only truly run 4 or 8 things at once. Point a thousand active backends at it and the kernel spends its time context-switching between processes and they fight over shared structures (lightweight locks, the buffer mapping) instead of doing work.

This is why max_connections exists and why the sane values are small — a few hundred, not tens of thousands. It is also why a naive web app is dangerous: forty application pods, each with its own local pool of twenty-five connections, quietly aims a thousand connections at a four-core database. Traffic spikes, every pod grabs more connections, and the database greets you with FATAL: sorry, too many connections — or worse, accepts them all and melts under the scheduling storm.

The one-line reframe

A Postgres connection is a process, not a socket. So the goal is not "let every client hold a connection" — it is "let a small, warm set of backends do the work, and share them." That sharing layer is a connection pooler, and everything in this lesson is about running one correctly.

01 The middle layer

The pooler in the middle ▸

A connection pooler is a small proxy that sits between your application and PostgreSQL. To the app it looks exactly like a Postgres server, so clients connect to it cheaply and in large numbers. Behind it, the pooler keeps only a small, fixed set of real backend connections open to the actual database, and it hands those few backends out to whichever client needs work done. Thousands of client connections in the front; a couple of dozen server connections out the back.

The three you'll meet in the wild: PgBouncer — the classic, a single tiny C process, by far the most deployed; Supavisor — Supabase's Elixir pooler, built for many tenants and huge client counts; and PgCat — a Rust pooler that adds load-balancing and sharding. They differ in features, but the core trick is identical. Step through it:

The economics are the whole point. Client connections to the pooler are cheap — no Postgres process is created for them — so you can have thousands. Server connections are the scarce, expensive resource, so you keep them few and busy. The pooler's job is to make sure a real backend is never sitting idle when a client has work, and never multiplied past what the database can actually run.

Where the pooler lives

Run it as a sidecar next to the database, as its own tier behind a load balancer, or as a managed service (RDS Proxy, Cloud SQL, Supabase all ship one). What matters is that it is shared across all your app processes — that is exactly what an in-process, per-pod pool can never be, and why we return to that distinction in the worked problem.

02 The modes

Session, transaction, or statement ▸

The multiplexing in the last figure only pays off if the pooler can reclaim a backend and give it to someone else. When it is allowed to do that is the pooling mode, and it is the single most important setting you will choose.

Session

  • A server is pinned to a client for the whole session (until it disconnects).
  • Behaves exactly like a raw connection — every feature works.
  • Almost no multiplexing: N clients need ≈ N servers.
  • Use only when you truly need session state.

Transaction

  • A server is assigned per transaction, returned at COMMIT/ROLLBACK.
  • Between transactions the backend is free for anyone.
  • Massive multiplexing — the common, default-in-practice mode.
  • The catch: no state survives a transaction (§03).

Statement

  • A server is released after every single statement.
  • The most aggressive reuse of all.
  • Multi-statement transactions are impossible — it forbids them.
  • Niche: fully autocommit, stateless workloads.

Transaction mode is where nearly every production system lives, because a web request typically is one short transaction: begin, run a few statements, commit, done. In the gap before the next request, the backend goes back to the pool. Watch a single backend serve two different clients over time:

That reuse is the entire reason 500 clients can live behind 20 backends. It also draws the boundary of the guarantee: a backend belongs to a client only for the duration of one transaction. The moment that transaction ends, anything the client set up on that particular backend is fair game to disappear — which is the sharp edge we handle next.

Rule of thumb

Reach for transaction mode by default and design your app to be transaction-scoped. Fall back to session mode only for the specific connections that genuinely need session features (a worker doing LISTEN/NOTIFY, say), and pay the multiplexing cost knowingly. Statement mode is a rarity you will almost never choose.

03 The sharp edge

The transaction-mode catch: session state doesn't survive

Here is the rule that causes more pooling bugs than anything else, and it follows directly from the last figure: in transaction mode, nothing that lives at the session level survives across transactions, because the very next transaction may run on a different backend. Anything you set up assuming "this is my connection for a while" is a landmine. The usual casualties:

  • Server-side prepared statements. The classic. Your driver runs PREPARE on one backend, then a later EXECUTE lands on a different backend that never saw it — prepared statement "S_1" does not exist, or on reuse ...already exists. Modern PgBouncer (≥ 1.21, 2023) can track and rewrite protocol-level prepared statements across backends if you set max_prepared_statements; otherwise you must disable server-side prepared statements in the driver.
  • SET (session GUCs). A plain SET search_path = app or SET timezone = ... lives on one backend and is gone next transaction. Use SET LOCAL (transaction-scoped, safe) inside the same transaction, put the setting in the connection string's options, or bake it into ALTER ROLE ... SET / ALTER DATABASE ... SET defaults.
  • Session advisory locks. pg_advisory_lock() is held until the session ends or you explicitly unlock — but "the session" is now a shared backend. Use the transaction-scoped variants: pg_advisory_xact_lock(), released automatically at commit.
  • LISTEN / NOTIFY. LISTEN registers interest for the life of the session; on a pooled backend it will not reliably receive notifications. Give listeners a dedicated session-mode connection.
  • Temp tables, WITH HOLD cursors, session GUCs (SET), LISTEN/NOTIFY. All are session-scoped state; under a transaction-mode pool the next transaction may land on a different backend that never saw them, so they vanish or error.

None of this makes transaction mode wrong — it makes it a contract. The contract is: keep everything you need inside a single transaction, or push it out of the session entirely (into the connect string, role defaults, or a dedicated session-mode connection). Almost every "it worked locally but breaks behind PgBouncer" story is a violation of exactly this rule.

The other half of running a pool well is sizing, and it is delightfully counter-intuitive: bigger is not better. Because a backend only makes progress when it is on a CPU core, the useful concurrency is bounded by cores, not by hope. A well-worn starting point:

Sizing heuristic

pool_size ≈ cores × 2–3 (some tune toward cores × 2 + effective_spindle_count for spinning disks). The multiplier over 1× is there to keep cores busy while some connections wait on I/O. Past that, extra connections don't add throughput — they add context-switching and lock contention and make everything slower. A small pool with a short wait queue beats a huge pool almost every time.

04 Worked problem

Size and configure a pool for a real service ▸

Time to put it together on a concrete, common incident.

The task

A REST API runs on 40 pods, each with an in-process pool (HikariCP) of 25 connections, pointed straight at a 4-vCPU PostgreSQL with max_connections = 200. Under load it throws FATAL: sorry, too many connections, DB CPU pins at 100%, and latency is awful. Right-size and re-plumb the connections so the service is stable.

1 · The setup

topology · before

# the database
4 vCPU cores  ·  max_connections = 200

# the app tier — each pod has its own local pool
40 pods × HikariCP maximumPoolSize = 25  =  up to 1000 client connections
                                              (aimed straight at Postgres)

2 · The naive attempt — and why it fails

The tempting one-liner is to make the error message go away by raising the ceiling:

sql

ALTER SYSTEM SET max_connections = 1000;   -- then restart Postgres

This "works" only in the sense that the FATAL stops. It makes the real problem worse. Now up to 1000 backends can exist, each holding several MB of standing memory (gigabytes total, competing with the shared buffer cache), and up to 1000 processes contend for 4 cores. The machine drowns in context switches and lightweight-lock contention; throughput drops as concurrency climbs. You didn't fix the overload — you removed the safety valve that was warning you about it.

3 · The fix

Put a pooler in front in transaction mode, size the server pool to the database's cores, and let it absorb the thousand client connections. Point the app at the pooler and shrink the per-pod pools so they stop hoarding.

pgbouncer.ini

[databases]
appdb = host=10.0.0.5 port=5432 dbname=appdb

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type   = scram-sha-256
pool_mode   = transaction        # the workhorse mode
max_client_conn      = 2000       # cheap front-side connections
default_pool_size    = 10         # ~ 4 cores × 2.5, the scarce resource
reserve_pool_size    = 5          # small burst headroom
reserve_pool_timeout = 3
max_prepared_statements = 200     # let PgBouncer 1.21+ carry prepared stmts

app side · each pod

# point at PgBouncer, not Postgres, and stop hoarding:
jdbc:postgresql://pgbouncer:6432/appdb
HikariCP.maximumPoolSize = 5      # 40 pods × 5 = 200 client conns → PgBouncer

The math now lines up: at most 40 × 5 = 200 client connections reach PgBouncer (well under max_client_conn), and PgBouncer maintains just 10 real backends to a database whose max_connections can drop back to a safe ~50.

4 · Why it's better

Measure the backends directly — the honest evidence here isn't an EXPLAIN plan (pooling isn't a query-planning problem), it's the backend count in pg_stat_activity:

sql

SELECT state, count(*)
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state;

illustrative · before (direct connections)

       state         | count
---------------------+-------
 active              |     4      -- only 4 can really run at once (4 cores)
 idle                |   960      -- ~1 GB of backends doing nothing
 idle in transaction |    36      -- and these are pinning rows/locks

illustrative · after (behind PgBouncer, transaction mode)

   state    | count
------------+-------
 active     |     4
 idle       |     6      -- 10 backends total, warm and reused

The four cores still run four queries at a time either way — that ceiling is physical. What changed is everything around it: memory reclaimed, context-switching gone, the connection storm collapsed onto a warm pool of ten. Excess concurrency now waits a few milliseconds in PgBouncer's queue instead of thrashing the CPU, so tail latency drops and the FATAL disappears for good.

5 · Narrate it

If you had to explain this in an interview: "Postgres is process-per-connection, so a thousand direct connections meant a thousand heavy backends fighting over four cores — the overload wasn't a limit to raise, it was a signal. I put PgBouncer in transaction mode in front, sized the server pool to about the DB's core count — ten — and shrank the per-pod app pools so 40 pods times 5 is only 200 client connections. The pooler multiplexes those onto ten warm backends; excess load queues for milliseconds instead of thrashing the CPU. Because we're in transaction mode I set max_prepared_statements so the ORM's prepared statements still work, and I audited for session-scoped things — SET, advisory locks, LISTEN — that transaction pooling would have quietly broken."

05 Graded drills

Drills & traps

Four drills, hardest last. Try each before opening the solution.

Drill 1 · The vanishing search_path

Your app runs SET search_path = app, public once right after connecting, then relies on it for every query. After you move to PgBouncer transaction mode, queries intermittently fail with relation "..." does not exist. Why, and what's the fix?

Try it first, then read

SET is session state. It ran on whatever backend served the first transaction; the next transaction lands on a different, pooled backend that never saw it, so search_path is back to default. Fix: stop relying on a runtime SET — bake it into the role with ALTER ROLE app_user SET search_path = app, public; (or a database default, or the connect-string options=-c search_path=app,public). Why: those apply on every backend automatically, so no session-scoped state is assumed.

Drill 2 · The "just make the pool bigger" reflex

To cut latency on the same 4-core DB, a teammate raises default_pool_size from 10 to 300. Under load, latency gets worse and CPU sits at 100%. Explain what happened.

Try it first, then read

300 backends oversubscribe 4 cores. Only ~4 can truly run at once; the other ~296 don't add throughput — they add context-switching, CPU-cache thrash, and contention on shared locks, so total work done per second falls. Fix: put it back to roughly cores × 2–3 (~10) and let excess transactions queue in the pooler. Why: a bounded number of workers with a short queue maximizes throughput; concurrency beyond the cores is negative-return.

Drill 3 · Pool exhaustion with an idle database

Under load, clients get timeout waiting for pool (or HikariCP Connection is not available) — yet DB CPU is low and few queries are running. What's the most likely cause, and how do you confirm and fix it?

Try it first, then read

Transactions are being held open while doing non-DB work — a slow external HTTP call, or app logic, inside a transaction — so backends sit idle in transaction and are never returned to the pool. The pool drains even though the DB is barely working. Confirm: SELECT state, count(*) FROM pg_stat_activity GROUP BY state; shows a pile of idle in transaction. Fix: keep transactions short — never do network I/O inside one — and set idle_in_transaction_session_timeout as a backstop. Why: raising the pool size only postpones the same exhaustion; the leak is duration, not count.

Drill 4 · Prepared statements, and app-pool vs external pooler

Two parts. (a) After switching your ORM to PgBouncer transaction mode you get prepared statement "S_3" already exists. Give two independent fixes. (b) You already had HikariCP in every pod — so why add an external pooler at all?

Try it first, then read

(a) Either (i) upgrade PgBouncer to ≥ 1.21 and set max_prepared_statements > 0 so it tracks and re-prepares statements per backend, or (ii) disable server-side prepared statements in the driver (JDBC prepareThreshold=0; asyncpg statement_cache_size=0). (b) An in-process pool only multiplexes within one pod — 40 pods × 25 still equals 1000 connections at the DB, because the pods can't share each other's connections. An external pooler multiplexes across all pods, so it's the only thing that caps total backends. Why: use both — a small app pool per pod pointing at a shared external pooler.

Traps to keep in your pocket

▸ Adding a pooler but leaving app pools huge — they multiply, so shrink the per-pod pool too.
▸ Believing a bigger pool means more throughput — past ~cores×2–3 it's the opposite.
▸ Running LISTEN/NOTIFY, session advisory locks, temp tables, or WITH HOLD cursors over transaction mode.
▸ Forgetting server-side prepared statements need max_prepared_statements (or must be disabled) in transaction mode.
▸ Long / idle-in-transaction transactions silently draining the pool while the DB looks idle.
▸ Not watching pool saturation — PgBouncer's SHOW POOLS (cl_waiting, maxwait) tells you before users do.

★ Review

Summary & self-test

The whole lesson compresses to one idea: a Postgres connection is a heavy OS process, so you don't give one to every client — you put a pooler in front, run it in transaction mode, and size the small server pool to the database's cores while a short queue absorbs the spikes. Everything else is the fine print of not breaking session state.
