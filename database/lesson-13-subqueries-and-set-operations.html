Subqueries & Set Operations

A query can hold another query inside it — a single value, a whole derived table, a list to test membership against, or a check that reruns for every outer row. And two queries can be combined as sets: stacked, intersected, or subtracted. Master these two ideas and a huge class of "customers who did X but not Y" questions collapses into a few readable lines — the exact shape interviewers love.

Original study notes. Written for engineers who want database depth that shows up in interviews and in production. Examples run on PostgreSQL (PG 17/18) and are ANSI-correct. 00 The taxonomy

A query inside a query

A subquery is a SELECT nested inside another statement. The word covers four distinct shapes, and the whole trick to using them well is knowing which shape you have — because each returns a different thing and is legal in a different place. Learn the four names now and the rest of the lesson is just applying them.

1 · Scalar subquery — exactly one value

A subquery wrapped so it yields a single row, single column. Because it is just a value, it can go almost anywhere an expression can: in the SELECT list, in a WHERE comparison, in an ORDER BY. If it ever returns more than one row at runtime, Postgres raises an error — more than one row returned by a subquery used as an expression.

sql

SELECT o.id,
       (SELECT c.name FROM customers c WHERE c.id = o.customer_id) AS customer
FROM orders o;

2 · Derived table — a subquery in FROM

A subquery placed in the FROM clause behaves like a temporary, unnamed table — you must give it an alias. Everything the outer query sees is whatever columns the inner one projected. Use it to compute an intermediate result set and then filter or join against it.

sql

SELECT dept, avg_sal
FROM (SELECT department AS dept, avg(salary) AS avg_sal
      FROM employees
      GROUP BY department) t
WHERE avg_sal > 50000;

3 · IN-list subquery — a column of values

A subquery returning one column, many rows, used to test set membership with IN (or = ANY). It answers "is this value among that set?"

sql

SELECT * FROM orders
WHERE customer_id IN (SELECT id FROM customers WHERE country = 'VN');

4 · Correlated subquery — references the outer row

The one that trips people up: the inner query mentions a column from the outer query (c.id below). It cannot be run once on its own — conceptually it reruns for each outer row, using that row's value. Almost always you pair it with EXISTS to ask "does at least one matching row exist for this outer row?"

sql

SELECT c.name FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);   -- c.id is the correlation
The one question to always ask

Before you write a subquery, decide what it returns: one value (scalar), one column (IN-list), a table (derived), or a per-row check (correlated). That single decision tells you where it is legal, whether it can error at runtime, and how the planner will likely execute it. Everything downstream follows from it.

01 The mental model

How a correlated subquery executes ▸

The mental model for a correlated subquery is a loop: take each row of the outer query, plug its value into the inner query, run the inner query, and let its result decide whether the outer row survives. The inner query is parameterised by the outer row — that is exactly what "correlated" means. Step through it for a "customers who have placed at least one order" query:

That per-row loop is the model, not a promise about the plan. If Postgres ran a fresh inner query for every one of a million outer rows, correlated subqueries would be hopelessly slow. So the planner does something smarter: it recognises the EXISTS pattern and rewrites it into a semi-join — a single join that stops at the first match per outer row and never duplicates the outer row. You get the semantics of "run the inner query per row" with the performance of one well-planned join. Reason with the loop; trust the planner to collapse it.

Semi-join, not a real join

A plain JOIN to orders would produce one output row per matching order — a customer with three orders shows up three times. A semi-join (what EXISTS and IN compile to) outputs the outer row at most once and stops probing as soon as one match is found. That "at most once, stop early" behaviour is precisely why EXISTS is the right tool for existence questions — and why you don't need a DISTINCT to clean up after it.

02 The three tests

IN vs EXISTS vs scalar =

Three operators test a value against a subquery, and interviewers love to ask how they differ. Here is the honest answer: for positive membership, IN and EXISTS usually plan to the same semi-join in Postgres, so choose whichever reads clearest. The real, correctness-level difference lives in the negative forms and in the arity each one demands.

IN (subquery)

  • Tests membership in a set of values (one column, many rows).
  • Reads naturally: "id is one of these."
  • Plans as a semi-join for the positive case.
  • Danger lives in NOT IN + NULL.

EXISTS

  • Tests whether at least one row exists — a boolean.
  • Ideal for correlated existence checks.
  • Stops at the first match; the select-list is irrelevant (SELECT 1).
  • NOT EXISTS is NULL-safe.

scalar =

  • Compares to a subquery that returns exactly one value.
  • "balance = (the account's limit)".
  • Returns > 1 row → runtime error.
  • Returns 0 rows → NULL, so the row is dropped.

The one place the choice becomes a bug rather than a style preference is negation — and it is the single most common subquery trap, worth recapping from the NULL lesson. NOT IN against a subquery that can produce a NULL silently returns no rows at all. Why: x NOT IN (a, b, NULL) expands to x <> a AND x <> b AND x <> NULL, and that last comparison is UNKNOWN, which poisons the whole AND to never-TRUE. The fix is to use NOT EXISTS, which evaluates a genuine per-row existence check and is completely NULL-safe.

sql

-- FRAGILE: if any customer_id in the subquery is NULL, this returns ZERO rows
SELECT * FROM orders o
WHERE o.customer_id NOT IN (SELECT customer_id FROM banned);

-- SAFE: NOT EXISTS is unaffected by NULLs in the inner set
SELECT * FROM orders o
WHERE NOT EXISTS (SELECT 1 FROM banned b WHERE b.customer_id = o.customer_id);
Default rule

Reach for EXISTS / NOT EXISTS as your default for existence and non-existence tests. It is correlated-friendly, short-circuits at the first match, and — crucially — NOT EXISTS never gets ambushed by a NULL the way NOT IN does. Save scalar = for when you can guarantee the subquery yields exactly one row (a unique key lookup, an aggregate with no GROUP BY).

03 Combining result sets

Set operations: UNION / INTERSECT / EXCEPT ▸

Subqueries nest one query inside another; set operators stack two queries side by side and combine their rows as mathematical sets. There is one hard precondition: the two inputs must be union-compatible — the same number of columns, in the same order, with compatible types. Column names don't have to match (the first query's names win); the shapes do. Given that, three operators combine them:

  • UNION — all rows from both, with duplicates removed. UNION ALL keeps duplicates and skips the dedup step, so it is faster — prefer it whenever you know the inputs are disjoint or duplicates are fine.
  • INTERSECT — only rows that appear in both inputs (also distinct by default).
  • EXCEPT — rows in the first input that are not in the second (distinct by default). Order matters: A EXCEPT B is not B EXCEPT A.

Watch which rows survive each operator over two small inputs — set A = {1, 2, 3} and set B = {2, 3, 4}:

Two subtleties earn their keep in interviews. First, UNION pays for its distinctness — Postgres must sort or hash the combined rows to eliminate duplicates, which is real CPU and memory. If you already know the branches can't overlap (say, "active users" and "archived users"), writing UNION instead of UNION ALL just buys you a needless sort. Second, all three operators use the whole row to decide equality, and they treat two NULLs as equal for this purpose — a deliberate departure from the usual NULL = NULL is UNKNOWN rule you learned earlier.

ORDER BY / LIMIT bind to the whole set

You can only put one ORDER BY (and LIMIT) at the very end of a set operation — it sorts the combined result, not either branch. If you need to sort inside a branch (e.g. to LIMIT it), wrap that branch in a derived table with its own ORDER BY/LIMIT, then union the wrapped subqueries.

04 Worked problem

Customers who bought A but not B ▸

This is the canonical "set difference" interview question, and it is the perfect place to see subqueries and set operators solve the same problem two ways. Here is the schema — one narrow table where each row is a single line-item purchase:

sql

CREATE TABLE orders (
  id           bigint PRIMARY KEY,
  customer_id  bigint NOT NULL,
  product_id   text   NOT NULL
);

The task, in one sentence: list every customer who has bought product 'A' but has never bought product 'B'.

The wrong-first attempt

The instinct is to self-join orders to itself and say "bought A, and also bought something that isn't B":

sql

-- WRONG: this is not the question you were asked
SELECT DISTINCT a.customer_id
FROM orders a
JOIN orders b ON b.customer_id = a.customer_id
WHERE a.product_id = 'A' AND b.product_id <> 'B';

The bug is conceptual, not syntactic. b.product_id <> 'B' asks "does this customer have some order that isn't B?" — which is the opposite of "does this customer have no B order." A customer who bought A, B, and C still matches, because the C row satisfies <> 'B'. You cannot express "for all the customer's orders, none is B" with a single row-level <> — a join finds a row, but this question is about the absence of a row. That's a job for a set difference or an anti-join.

Correct — Approach 1: EXCEPT

Two clean sets, subtracted. EXCEPT even dedups for free, so the result is distinct customer ids:

sql

SELECT customer_id FROM orders WHERE product_id = 'A'
EXCEPT
SELECT customer_id FROM orders WHERE product_id = 'B';

explain · illustrative

HashSetOp Except  (rows=380)
  ->  Append
        ->  Subquery Scan on "*SELECT* 1"
              ->  Seq Scan on orders   (Filter: product_id = 'A')
        ->  Subquery Scan on "*SELECT* 2"
              ->  Seq Scan on orders   (Filter: product_id = 'B')

Read the plan top-down: Postgres scans out the A-buyers and the B-buyers, appends the two streams, then a HashSetOp builds a hash table and keeps A-rows with no B-match. It's tidy and reads like the maths, but note both branches are full Seq Scans — it materialises both whole sets before subtracting.

Correct — Approach 2: NOT EXISTS (anti-join)

The same answer as an existence check: keep A-buyers for whom no B-order exists. This form composes with extra predicates and takes better advantage of an index:

sql

SELECT DISTINCT a.customer_id
FROM orders a
WHERE a.product_id = 'A'
  AND NOT EXISTS (SELECT 1 FROM orders b
                  WHERE b.customer_id = a.customer_id
                    AND b.product_id = 'B');

Now give the planner the index it wants — a composite on (product_id, customer_id). The leading product_id lets it jump straight to the A-rows, and the trailing customer_id lets the anti-join probe be an index-only lookup:

sql

CREATE INDEX orders_prod_cust ON orders (product_id, customer_id);

explain · illustrative

HashAggregate  (rows=380)                 -- the DISTINCT
  Group Key: a.customer_id
  ->  Nested Loop Anti Join  (rows=400)
        ->  Index Only Scan using orders_prod_cust on orders a
              Index Cond: (product_id = 'A')
        ->  Index Only Scan using orders_prod_cust on orders b
              Index Cond: (product_id = 'B' AND customer_id = a.customer_id)

The star node is the Nested Loop Anti Join: for each A-buyer, it probes the index for a B-order with the same customer_id, and — being an anti join — keeps the outer row only when that probe finds nothing, stopping at the first hit otherwise. Because both scans can be Index Only, it can skip the heap entirely when those pages are marked all-visible (freshly vacuumed); otherwise it falls back to a heap check per candidate. When the A-set is selective and the index exists, this typically beats the double full-scan of EXCEPT; when both sets are large and roughly the same size, the hashed set-op is perfectly competitive. Both are correct — pick by data shape and readability.

Narrate it

Here is how I'd say it aloud in the room: "This is a set-difference question — customers in bought A minus customers in bought B. The trap is the self-join with <> 'B', which finds customers with a non-B order rather than customers with no B order, so it wrongly keeps anyone who bought both. I'd write it as EXCEPT for clarity, or as NOT EXISTS if I want it to ride a (product_id, customer_id) index as an anti-join and stay composable with more filters. Both dedup the customer id automatically — EXCEPT by definition, NOT EXISTS because I add DISTINCT. And I'd avoid NOT IN here in case customer_id can be null in the inner set."

05 Practice

Graded drills & traps

Try each on paper (or in psql) before opening the answer. They climb from a plain scalar subquery to the semantic gap between INTERSECT and a join — exactly the ladder an interviewer walks you up.

Drill 1 — scalar subquery

For each order, show its id and how many orders that customer has placed in total.

Try it first, then read

sql

SELECT o.id, o.customer_id,
       (SELECT count(*) FROM orders o2
        WHERE o2.customer_id = o.customer_id) AS customer_orders
FROM orders o;

Why: a correlated scalar subquery returns exactly one value (a count with no GROUP BY always yields one row), so it drops neatly into the select list. A window function — count(*) OVER (PARTITION BY customer_id) — is the usual faster rewrite.

Drill 2 — EXISTS

List the customers who have at least one refunded order. Assume orders(customer_id, status), where refunds carry status = 'refunded'.

Try it first, then read

sql

SELECT c.id, c.name
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o
              WHERE o.customer_id = c.id
                AND o.status = 'refunded');

Why: EXISTS stops at the first refunded order per customer and returns each customer once — no DISTINCT needed, and no fan-out even if a customer has many refunds.

Drill 3 — UNION ALL vs UNION

Merge two email sources — newsletter_signups(email) and trial_users(email) — into one list. When should you write UNION ALL, and when UNION?

Try it first, then read

sql

-- one contact list, duplicates collapsed (a person may be in both)
SELECT email FROM newsletter_signups
UNION
SELECT email FROM trial_users;

-- raw event feed, keep every occurrence (and it's cheaper)
SELECT email FROM newsletter_signups
UNION ALL
SELECT email FROM trial_users;

Why: UNION adds a sort/hash to remove duplicates — use it only when you truly need distinct results. If the sources are disjoint, or duplicates are acceptable, UNION ALL skips that cost.

Drill 4 — INTERSECT vs an inner join

Find the customer ids that appear in both promo_a(customer_id) and promo_b(customer_id). Why isn't a plain inner join always equivalent to INTERSECT?

Try it first, then read

sql

-- INTERSECT: distinct common values, guaranteed
SELECT customer_id FROM promo_a
INTERSECT
SELECT customer_id FROM promo_b;

-- JOIN: one row per matching PAIR — duplicates on either side fan out
SELECT DISTINCT a.customer_id
FROM promo_a a
JOIN promo_b b USING (customer_id);

Why: INTERSECT is set-valued — it dedups automatically. A join emits a row for every matching pair, so if a customer_id appears twice in promo_a and three times in promo_b you get six rows. Add DISTINCT to collapse those duplicates — though the two still differ on a NULL key, since INTERSECT treats two NULLs as equal (grouping semantics) while the join's = does not.

Traps to keep in your head

• NOT IN + NULL. One NULL in the inner set makes NOT IN return zero rows. Default to NOT EXISTS.
• Accidental UNION. Writing UNION when you meant UNION ALL silently adds a dedup sort — a real cost on large inputs, and it hides genuine duplicates.
• Scalar subquery returning > 1 row. A scalar subquery used in SELECT/WHERE that matches multiple rows fails at runtime — not at plan time. Guarantee uniqueness (a key, or an aggregate).
• Unindexed correlation column. A correlated subquery whose inner filter (e.g. o.customer_id = c.id) has no index degrades toward re-scanning the inner table per outer row — quadratic. Index the correlated column.

★ Review

Summary & self-test

One idea holds the lesson together: a subquery is defined by what it returns — one value, one column, a table, or a per-row check — and set operators combine two whole queries as sets, deduping unless you say otherwise. Get those two classifications right and "did X but not Y", "in both", and "in either" stop being puzzles.
