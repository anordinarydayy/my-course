LATERAL, DISTINCT ON & Grouping Sets

Three Postgres power tools, each of which collapses an awkward, many-line pattern into one clean query. LATERAL is a join whose right side can see the left row — the idiomatic top-N-per-group. DISTINCT ON keeps the first row per key — the idiomatic latest-per-group. GROUPING SETS / ROLLUP / CUBE compute many aggregation levels in a single pass. Learn these and a whole class of "how do I even write that?" questions become one-liners.

00 Orientation

Three power tools

Everything so far in the SQL phase — joins, aggregation, subqueries, CTEs, window functions — is the load-bearing structure. This lesson adds three finishing tools. Each one exists because some very common request is genuinely clumsy to express with the basics, and each turns that request into a short, readable query. They are the moves that make experienced SQL people say "wait, you can do that in one query?" — which is exactly why this is a Stretch lesson: none of it is mandatory to get data out, but all of it separates a report you dread from a report you enjoy.

LATERAL

  • A subquery in FROM that may reference the row to its left.
  • Kills: top-N per group, joining to unnest()/generate_series().
  • Runs the right side once per left row — a correlated join.

DISTINCT ON

  • Keeps the first row per key as ordered.
  • Kills: latest / first per group (newest login, current price).
  • Terser than a row_number() = 1 window; same result.

GROUPING SETS

  • Many grouping levels in one pass; ROLLUP / CUBE are shorthands.
  • Kills: reports needing detail + subtotals + total.
  • GROUPING() labels the rolled-up rows.

The through-line: each tool trades a pile of UNION ALLs, self-joins, or application-side loops for a single set-based expression the planner can optimise. Work through the three interactive diagrams below, then the worked problem stitches two of them into one realistic report.

How to read this lesson

Don't just skim the queries — for each tool, fix in your head the one sentence that says what it keeps or produces. LATERAL: "the right side sees the left row." DISTINCT ON: "first row per key, in order." Grouping sets: "several GROUP BYs at once." Those three sentences are what you'll actually reach for in an interview.

01 Correlated joins

LATERAL: a join that sees the left row ▸

A normal subquery in the FROM clause is uncorrelated: it is computed once, on its own, and cannot mention any other table in the same FROM. Try to reference an outer column and Postgres refuses — invalid reference to FROM-clause entry. LATERAL lifts that restriction: a LATERAL subquery (or set-returning function) in FROM may reference columns of the FROM items written before it. It is, in effect, a correlated join — the right side is re-evaluated for each row of the left side.

That single ability solves the two patterns that are otherwise painful in plain SQL. First, top-N per group: "each customer joined to their three most recent orders." Second, joining to a set-returning function that needs a column value, like generate_series(s.starts_at, s.ends_at, …). Step through how the right side runs once per left row:

Here is the canonical top-3-per-customer, side by side with the plain (uncorrelated) subquery that cannot do it:

Plain subquery in FROM — can't correlate

sql · error

SELECT c.id, o.id
FROM customers c,
     (SELECT id FROM orders
      WHERE customer_id = c.id  -- ✗
      ORDER BY created_at DESC
      LIMIT 3) o;
-- ERROR: invalid reference to
-- FROM-clause entry for table "c"

LATERAL — the right side sees c

sql

SELECT c.id, o.id
FROM customers c
CROSS JOIN LATERAL (
  SELECT id FROM orders
  WHERE customer_id = c.id  -- ✓
  ORDER BY created_at DESC
  LIMIT 3
) o;

Two practical notes. CROSS JOIN LATERAL drops any customer with zero matching orders (the subquery returns nothing, so the join produces no row); if you need every customer to survive, use LEFT JOIN LATERAL (…) o ON true, which pads the missing side with NULLs. And when the right side is a set-returning function — generate_series, unnest, jsonb_array_elements — the LATERAL keyword is implied, so FROM t, unnest(t.arr) already correlates. Writing LATERAL explicitly just makes the intent obvious.

LATERAL vs a plain subquery

The one distinction to keep straight: a plain FROM subquery is computed once, independently; a LATERAL subquery is computed once per left row and may use that row's columns. That "per left row" execution is what makes top-N-per-group possible — and also what you must keep an eye on for performance: it is a loop, so the inner query wants an index (here, orders(customer_id, created_at DESC)) to stay fast.

02 First-per-group

DISTINCT ON: first row per group ▸

A staggeringly common request: "the latest row per group" — the newest login per user, the current price per product, the most recent order per customer. Postgres has a purpose-built, terse answer: DISTINCT ON (key). It keeps the first row of each distinct key, where "first" is decided by the query's ORDER BY. The rule that trips everyone up once: the ORDER BY must begin with the same expressions as DISTINCT ON; anything after those is the tiebreak that decides which row survives within a key.

So "latest login per user" is: partition by user_id (that's the DISTINCT ON), and within each user pick the newest by ordering logged_in_at DESC (that's the tiebreak). Watch Postgres walk the sorted stream and keep the first row of each user:

In code, the whole thing is three lines:

sql

SELECT DISTINCT ON (user_id)
       user_id, logged_in_at, ip
FROM logins
ORDER BY user_id, logged_in_at DESC;   -- ORDER BY MUST start with user_id

The equivalent with a window function is longer but generalises: row_number() partitioned by the key, then keep rank 1. Because a window result can't be filtered in WHERE (windows run after WHERE), you must wrap it in a subquery or CTE:

sql

SELECT user_id, logged_in_at, ip
FROM (
  SELECT user_id, logged_in_at, ip,
         row_number() OVER (PARTITION BY user_id
                            ORDER BY logged_in_at DESC) AS rn
  FROM logins
) t
WHERE rn = 1;

Reach for DISTINCT ON when

  • You want exactly one row per key (the first/latest).
  • You value terseness; it's one clause, no wrapper.
  • An index on (key, tiebreak) lets it avoid a sort.

Reach for row_number() when

  • You want top-N (N>1) per group, not just the first.
  • You need the rank number itself, or ties kept (rank).
  • You're already computing other window columns.
The one rule that bites

The ORDER BY must lead with the DISTINCT ON expressions or Postgres raises "SELECT DISTINCT ON expressions must match initial ORDER BY expressions." And if you leave off the tiebreak entirely (ORDER BY user_id only), the query is legal but which row survives each group is arbitrary — the classic nondeterministic-latest bug. Always spell out the tiebreak (logged_in_at DESC) so "first" means something.

03 Many levels, one pass

Grouping sets, ROLLUP, CUBE ▸

A report almost never wants only the finest grain. "Revenue by region and product" is nice, but the reader also wants the subtotal per region and the grand total. Written naively, that's three separate GROUP BY queries stitched with UNION ALL, scanning the table three times. Grouping sets let you ask for several grouping levels in one query and one pass:

  • GROUPING SETS ((a,b),(a),()) — lists the levels explicitly: by (a,b), by (a), and the grand total.
  • ROLLUP(a,b) — the hierarchical shorthand: (a,b), then (a), then (). Subtotals rolling up to a grand total.
  • CUBE(a,b) — every combination: (a,b), (a), (b), () — that's 2n sets.

On the subtotal and total rows, the columns that were rolled up come back as NULL. To tell a real NULL from a "this column was aggregated away" marker, use GROUPING(col), which returns 1 exactly on the rows where col was rolled up. Step through a ROLLUP(region, product):

The three forms are just shorthands over the same machinery. These are equivalent for two columns:

sql

-- ROLLUP is shorthand for a nested list of grouping sets:
GROUP BY ROLLUP (region, product)
GROUP BY GROUPING SETS ((region, product), (region), ());

-- CUBE adds the "(product) alone" and repeats the total:
GROUP BY CUBE (region, product)
GROUP BY GROUPING SETS ((region, product), (region), (product), ());
CUBE grows fast — count before you type

CUBE(a,b,c,d) is 24 = 16 grouping sets in one query; add a fifth column and it's 32. Each set is a full aggregation level, so a wide CUBE can quietly do far more work than you intended. When you only want subtotals up a natural hierarchy (region → product), reach for ROLLUP; save CUBE for when you genuinely need every cross-combination, and list explicit GROUPING SETS when you want just a few.

04 Worked problem

Worked: a regional report with subtotals, and the latest order per customer

Two realistic asks in one small schema — the first exercises ROLLUP + GROUPING(), the second puts DISTINCT ON and LATERAL head to head. Here is the schema:

sql

CREATE TABLE customers (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL
);

CREATE TABLE sales (
  id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  region   text NOT NULL,
  product  text NOT NULL,
  amount   numeric(10,2) NOT NULL
);

CREATE TABLE orders (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id  bigint NOT NULL REFERENCES customers(id),
  created_at   timestamptz NOT NULL
);

Part A — regional report: detail, subtotals, grand total

Task: produce revenue per (region, product), a subtotal per region, and a grand total — in one pass — with each subtotal/total row clearly labelled.

Naive first attempt. Reach for three queries glued with UNION ALL:

sql · works but clumsy

SELECT region, product, sum(amount) FROM sales GROUP BY region, product
UNION ALL
SELECT region, NULL, sum(amount) FROM sales GROUP BY region
UNION ALL
SELECT NULL, NULL, sum(amount) FROM sales;

Why it's poor: it scans sales three times, repeats the aggregate three ways, and — worst — its NULLs are indistinguishable from real NULLs in the data, so a consumer can't reliably tell a subtotal row apart. The single-pass version fixes all three:

sql

SELECT
  CASE WHEN grouping(region)  = 1 THEN 'ALL REGIONS' ELSE region  END AS region,
  CASE WHEN grouping(product) = 1 THEN 'all products' ELSE product END AS product,
  sum(amount)                 AS revenue,
  grouping(region, product)  AS gflag
FROM sales
GROUP BY ROLLUP (region, product)
ORDER BY grouping(region), region, grouping(product), product;

With the three demo rows (North/Widget 100, North/Gadget 60, South/Widget 90), the result is:

illustrative · result

   region    |   product    | revenue | gflag
-------------+--------------+---------+-------
 North       | Gadget       |   60.00 |     0   -- detail
 North       | Widget       |  100.00 |     0   -- detail
 North       | all products |  160.00 |     1   -- region subtotal
 South       | Widget       |   90.00 |     0   -- detail
 South       | all products |   90.00 |     1   -- region subtotal
 ALL REGIONS | all products |  250.00 |     3   -- grand total

Read gflag as a bitmask over (region, product): 0 = both present (detail), 1 = product rolled up (region subtotal), 3 = both rolled up (grand total). That single integer, or the two CASEd labels, is how the report marks its subtotal rows unambiguously. The plan reads:

illustrative · EXPLAIN ANALYZE

GroupAggregate  (cost=1.31..1.66 rows=7 width=68) (actual time=0.052..0.061 rows=6 loops=1)
  Group Key: region, product
  Group Key: region
  Group Key: ()
  ->  Sort  (cost=1.31..1.32 rows=3 width=40) (actual time=0.030..0.033 rows=3 loops=1)
        Sort Key: region, product
        Sort Method: quicksort  Memory: 25kB
        ->  Seq Scan on sales  (cost=0.00..1.03 rows=3 width=40) (actual rows=3 loops=1)
Planning Time: 0.20 ms
Execution Time: 0.10 ms

Read it bottom-up: one Seq Scan, one Sort by (region, product), and then a single GroupAggregate that emits all three Group Key levels from that one sorted stream — the three-scan UNION ALL collapsed into one pass. (When Postgres decides some grouping sets are cheaper to hash than to sort, the same query shows a MixedAggregate node with a mix of Hash Key and Group Key lines — same result, different mechanics.)

Part B — the latest order per customer, two ways

Task: return, for each customer, their single most recent order.

Naive first attempt — the correlated-max filter:

sql · slow and non-unique

SELECT o.customer_id, o.id, o.created_at
FROM orders o
WHERE o.created_at = (
  SELECT max(o2.created_at) FROM orders o2
  WHERE o2.customer_id = o.customer_id
);

Two problems. It runs a correlated aggregate subquery — conceptually once per row — and, crucially, if a customer has two orders at the exact same max timestamp it returns both: there is no single "latest." DISTINCT ON fixes both — one row per customer, guaranteed, with a deterministic tiebreak:

sql · the clean way

SELECT DISTINCT ON (customer_id)
       customer_id, id, created_at
FROM orders
ORDER BY customer_id, created_at DESC, id DESC;   -- id DESC breaks timestamp ties

The LATERAL top-1 is the same idea driven from the customers side — clearer when you also want customer columns, or want to keep customers with no orders (swap to LEFT JOIN LATERAL … ON true):

sql · the LATERAL equivalent

SELECT c.id AS customer_id, c.name, o.id, o.created_at
FROM customers c
CROSS JOIN LATERAL (
  SELECT id, created_at
  FROM orders
  WHERE customer_id = c.id
  ORDER BY created_at DESC, id DESC
  LIMIT 1
) o;

Both want the same index — the composite that makes "newest per customer" a single ordered walk:

sql

CREATE INDEX orders_cust_created_idx
  ON orders (customer_id, created_at DESC, id DESC);

With that index, the DISTINCT ON avoids sorting entirely — it reads the index in order and a Unique node keeps the first row per customer_id:

illustrative · EXPLAIN ANALYZE

Unique  (cost=0.29..66.3 rows=200 width=24) (actual time=0.024..0.310 rows=200 loops=1)
  ->  Index Scan using orders_cust_created_idx on orders
          (cost=0.29..58.8 rows=3000 width=24) (actual time=0.022..0.230 rows=3000 loops=1)
Planning Time: 0.15 ms
Execution Time: 0.34 ms

No Sort node — the index already delivers rows in (customer_id, created_at DESC) order, so Unique just skips to the next customer after taking the first row. The LATERAL version instead shows a Nested Loop whose inner side is a Limit over an Index Scan with Index Cond: (customer_id = c.id) — a per-customer index probe, one row deep.

Narrate it

Part A takes a report that would be three table scans and a pile of indistinguishable NULLs and turns it into one sorted pass through GroupAggregate, with GROUPING() flags that let the reader label every subtotal and the grand total unambiguously. Part B replaces a correlated-max filter — slow, and silently non-unique on ties — with either DISTINCT ON (terser, index-driven, no sort) or LATERAL top-1 (clearer when you want customer columns or zero-order customers). Same data, a fraction of the work, and in both cases the right index turns the operation into a single ordered walk instead of a repeated scan.

05 Graded drills

Graded drills & traps

Attempt each in your head (or a scratch database) before opening the solution. They climb from a direct application to a compound one.

Drill 1 — top-3 orders per customer (LATERAL)

Return each customer's name alongside up to their three most recent orders — and keep customers who have no orders.

Try it first, then read

sql

SELECT c.id, c.name, o.id AS order_id, o.created_at
FROM customers c
LEFT JOIN LATERAL (
  SELECT id, created_at
  FROM orders
  WHERE customer_id = c.id
  ORDER BY created_at DESC, id DESC
  LIMIT 3
) o ON true
ORDER BY c.id, o.created_at DESC;

Why: the LATERAL subquery re-runs per customer with LIMIT 3 — top-N-per-group. LEFT JOIN … ON true keeps order-less customers (their o.* come back NULL).

Drill 2 — latest login per user (DISTINCT ON)

From logins(user_id, logged_in_at, ip), return one row per user: their most recent login.

Try it first, then read

sql

SELECT DISTINCT ON (user_id)
       user_id, logged_in_at, ip
FROM logins
ORDER BY user_id, logged_in_at DESC;

Why: in a stream sorted by (user_id, logged_in_at DESC), the first row of each user_id is the newest. The ORDER BY leads with the DISTINCT ON key, as required.

Drill 3 — a ROLLUP report reading the GROUPING flags

From sales(region, product, amount), give revenue by region and product with per-region subtotals and a grand total, exposing the two GROUPING() flags so a caller can classify each row.

Try it first, then read

sql

SELECT region, product,
       sum(amount)        AS revenue,
       grouping(region)  AS g_region,
       grouping(product) AS g_product
FROM sales
GROUP BY ROLLUP (region, product)
ORDER BY grouping(region), region, grouping(product), product;

Why: g_product = 1 marks a region subtotal (product rolled up); g_region = 1 AND g_product = 1 marks the grand total. Ordering by the grouping() values first pushes subtotals below their details and the total to the very bottom.

Drill 4 — LATERAL with a set-returning function

Given subscriptions(id, starts_at date, ends_at date), expand each subscription into one row per calendar month it is active.

Try it first, then read

sql

SELECT s.id, gs.month::date
FROM subscriptions s
CROSS JOIN LATERAL generate_series(
  date_trunc('month', s.starts_at),
  date_trunc('month', s.ends_at),
  interval '1 month'
) AS gs(month)
ORDER BY s.id, gs.month;

Why: generate_series needs each row's starts_at/ends_at as its bounds — a correlated reference only LATERAL allows. (For set-returning functions the LATERAL is technically implicit, but writing it states the intent.)

Traps to internalise

• DISTINCT ON with the wrong ORDER BY. The ORDER BY must begin with the DISTINCT ON expressions or Postgres errors outright; and if you omit the tiebreak, which row survives each key is arbitrary (nondeterministic "latest").
• Forgetting LATERAL is correlated. A plain FROM subquery can't see sibling tables — WHERE customer_id = c.id raises "invalid reference to FROM-clause entry" unless the subquery is LATERAL.
• CUBE column-count explosion. CUBE generates 2n grouping sets; four columns is already 16 aggregation levels. Use ROLLUP or explicit GROUPING SETS unless you truly need every combination.
• Misreading subtotal rows. On a rolled-up row the grouped column shows NULL; if the column can also contain real NULLs, only GROUPING(col) = 1 — never col IS NULL — reliably identifies subtotal/total rows.

★ Review

Summary & self-test

One idea ties the three tools together: each replaces an awkward multi-statement or application-side pattern with a single set-based expression the planner can run in one pass. LATERAL correlates a join to the left row; DISTINCT ON keeps the first row per key; grouping sets compute many levels at once. Learn the one-sentence job of each and you'll recognise its problem on sight.

01LATERAL sees the left rowA FROM subquery that may reference earlier FROM items; runs once per left row — a correlated join.
02Top-N per groupThe canonical LATERAL use: join each group to its ORDER BY … LIMIT N. Use LEFT JOIN LATERAL … ON true to keep empty groups.
03DISTINCT ON = first per keyKeeps the first row of each key as ordered — the terse latest-per-group. The ORDER BY must lead with the key.
04DISTINCT ON vs row_number()Same result; DISTINCT ON is shorter, row_number()=1 generalises to top-N and exposes the rank.
05Grouping sets in one passGROUPING SETS/ROLLUP/CUBE give detail + subtotals + total from a single scan instead of stacked UNION ALLs.
06GROUPING() labels rowsReturns 1 where a column was rolled up — the only safe way to distinguish a subtotal row from a real NULL.
07Right index, one walkAn index on (key, tiebreak DESC) lets DISTINCT ON and LATERAL top-1 avoid sorting — a single ordered scan.
08Watch the costLATERAL is a loop (index the inner query); CUBE is 2n sets. Power tools still have a bill.
