Monitoring & Observability

A running database is a black box until you learn to read its instruments. Postgres keeps a live account of its own health — a family of pg_stat_* views — and reading them is the difference between "the database is slow, restart it" and "one idle transaction is holding a lock; here's the pid." This lesson turns those instruments into a diagnostic routine you can run under pressure.

Original study notes. Written for engineers who get paged. The examples use PostgreSQL (PG 17/18), but the discipline — measure the system's own signals before you touch it — is universal. Contains three interactive diagrams (press Play or step with Next). This is a practice lesson: it ends in a worked SQL problem — a real "why is it slow?" page — and a set of graded drills.
00 Orientation

Seeing inside a running database

You cannot fix what you cannot see, and you cannot see a database by watching CPU and memory graphs from the outside. A blocked query burns zero CPU while it waits; a table quietly bloating to twice its size looks fine on every host metric right up until every scan is slow. The signals that matter live inside Postgres, and it exposes them through views you can query with plain SQL. Learning those views is the whole skill of operating a database.

Almost every incident you will ever diagnose is one of six signals. Learn where each one lives and you have a map:

  • Slow queries — which statements actually consume the server's time. Lives in pg_stat_statements.
  • Locks & blocking — one held lock can freeze a hundred sessions behind it. Lives in pg_locks + pg_blocking_pids().
  • Bloat & vacuum health — dead tuples pile up and slow every read. Lives in pg_stat_user_tables.
  • Replication lag — how far behind a read replica has fallen. Lives in pg_stat_replication.
  • Cache hit ratio — how often reads are served from RAM instead of disk. Lives in pg_statio_user_tables.
  • Connections & idle-in-transaction — too many connections, or one that never commits. Lives in pg_stat_activity.

Two of those, pg_stat_statements and the live snapshot in pg_stat_activity, resolve the large majority of pages by themselves. We build up to a routine that walks all six in order.

The instruments ship in the box

You do not need Datadog or an agent to start. Postgres computes these statistics itself; every view here is one SELECT away in psql. External tools — pganalyze, Prometheus + postgres_exporter, your cloud console — mostly scrape, store, and graph the same numbers over time, which is what turns a single snapshot into a trend you can alert on. Master the built-in views first; add history second.

01 The tuning view

pg_stat_statements: tune the worst first ▸

The single most valuable view for performance work is pg_stat_statements. It is an extension that normalizes every query — replacing literals with $1, $2, … so WHERE id = 42 and WHERE id = 99 collapse into one row — and then accumulates per-shape counters: calls, total_exec_time, mean_exec_time, min/max/stddev, rows, and shared-buffer hits and reads. Instead of guessing which query is expensive, you ask.

It is not on by default — it needs a preloaded library (a restart) and the extension created once:

sql

-- postgresql.conf (needs a restart to take effect):
--   shared_preload_libraries = 'pg_stat_statements'
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

Then the one query you will run more than any other — "where is the server actually spending its time?":

sql

SELECT queryid,
       calls,
       round(total_exec_time)      AS total_ms,
       round(mean_exec_time, 2)    AS mean_ms,
       rows,
       left(query, 60)             AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

Order by total_exec_time, not by "which query feels slow." The point is to spend your effort where the server spends its seconds. Step through how to read the result:

The result teaches a formula worth burning in: total = calls × mean. A query can top the list two very different ways. The monthly report is slow per call (5 seconds each) — the fix is a better plan: an index, or a MATERIALIZED VIEW. The orders lookup is fast per call (0.20 ms) but runs 2.1 million times — the fix is fewer or cheaper calls: kill an N+1, add a caching layer, or give it a hotter index. Both are real, and both are invisible if you only chase the query that "feels" slow.

Cumulative counters need a baseline

total_exec_time grows forever — it is a running total since the last statistics reset or server restart. "610 s" only means something next to over what window? After a deploy, run SELECT pg_stat_statements_reset(); to zero the counters, then read them fresh — now you are measuring the new code, not the last month. A number without "compared to when" is noise; we return to this in the traps.

02 Right now

The live views: what's happening this instant ▸

pg_stat_statements is aggregated history. The other half of monitoring is the live snapshot — what the server is doing right now — and that comes from a small set of views you should be able to recall from memory. Each is a window onto one of the six signals.

Start with pg_stat_activity — one row per backend (connection). The three states to know cold are active (running a query), idle (connected, waiting on the client), and idle in transaction (inside a transaction but running nothing — the dangerous one, because it still holds its snapshot and any locks it took):

sql

SELECT pid, usename, state,
       wait_event_type, wait_event,
       now() - xact_start AS xact_age,
       left(query, 50) AS query
FROM pg_stat_activity
WHERE state IS DISTINCT FROM 'idle'
ORDER BY xact_start;

When a query hangs, it is usually waiting on a lock. You do not have to decode pg_locks by hand — pg_blocking_pids() names the culprit directly:

sql

SELECT pid,
       pg_blocking_pids(pid) AS blocked_by,
       wait_event,
       left(query, 50) AS query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

pg_stat_user_tables is your window on bloat and vacuum health. High n_dead_tup relative to live rows, or a stale last_autovacuum, means dead rows are dragging on every scan:

sql

SELECT relname,
       n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup
             / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;

On a primary, pg_stat_replication has one row per connected standby, and it is where replica lag is measured — in bytes (the LSN gap) and in time (replay_lag):

sql

SELECT application_name, state, sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes,
       replay_lag
FROM pg_stat_replication;

Finally, pg_stat_io (new in PG16) breaks reads, writes, and cache hits down by backend type and I/O context — normal, vacuum, bulkread — so you can see where your I/O comes from, not just how much.

Memorize the map, not the columns

Under interview or incident pressure you will not recall every column, but you must recall which view answers which question: "who is stuck?" → pg_stat_activity; "who blocks them?" → pg_blocking_pids; "what's bloated?" → pg_stat_user_tables; "how far behind is the replica?" → pg_stat_replication. The exact SQL you can always look up; the map is what makes you fast.

03 From numbers to alerts

The signals and their thresholds

A raw counter is not an alert. The operating skill is turning each signal into a threshold — a line that, when crossed, means something. Here are the ones worth wiring up, and the judgment behind each.

Cache hit ratio. The fraction of block reads served from shared_buffers instead of the OS/disk. For an OLTP workload, healthy is above ~99%:

sql

SELECT round(100.0 * sum(heap_blks_hit)
             / nullif(sum(heap_blks_hit + heap_blks_read), 0), 2) AS cache_hit_pct
FROM pg_statio_user_tables;

Treat it as a coarse trend, not a latency metric — it is cumulative, and a "read" may still be served from the OS page cache in RAM (more on this in the drills).

  • Long-running & idle-in-transaction. Alert on any transaction whose xact_start age exceeds a few minutes. Enforce it, don't just watch: set idle_in_transaction_session_timeout and statement_timeout so a stuck session self-terminates instead of holding locks and pinning vacuum.
  • Replication lag. Alert on the LSN byte gap and on replay_lag. The right threshold depends on need: a replica you read-after-write from must be near-zero; a reporting replica can lag minutes.
  • Autovacuum health. Watch dead_pct climbing and last_autovacuum going stale — especially a table autovacuum never reaches, which usually means a long-running transaction is holding back the xmin horizon.
  • Connection saturation. Compare active connections to max_connections, but the real fix for "too many connections" is a pooler (PgBouncer), not a bigger limit. Watch the active / idle / idle in transaction split, not just the count.

auto_explain closes the gap for the slow query you did not catch live: it logs the plan (optionally with timings) of any statement over a duration you choose, so the next slow execution captures its own plan for you:

sql

-- log the plan of any statement slower than 500 ms
LOAD 'auto_explain';
SET auto_explain.log_min_duration = '500ms';
SET auto_explain.log_analyze = on;

Above the built-in views sit the external tools: pganalyze, Prometheus with postgres_exporter, and cloud dashboards (RDS Performance Insights, Cloud SQL Insights). They do not invent new signals — they scrape these same views on an interval, store the history, draw the graphs, and fire the alerts. History is what lets you say "this started at 14:00," which is often the whole diagnosis.

Alert on symptoms, not on every counter

The counters are for diagnosis; alerts should fire on symptoms your users feel — request latency, error rate, replica lag past your read-after-write budget, disk filling. Alerting on every raw metric ("cache hit dropped to 98.7%!") trains you to ignore the pager. Few, meaningful alerts → many detailed dashboards you consult after one fires.

04 Worked problem

Diagnose “the database is slow” ▸

Here is the page you will actually get. Nothing about it names a query, a lock, or a table — just "it's slow." The job is to turn that into a specific cause and a specific fix, using only Postgres's own views.

1 · The setup

sql

-- e-commerce OLTP, PG 18. pg_stat_statements is enabled.
CREATE TABLE orders (
  id           bigserial PRIMARY KEY,
  user_id      bigint NOT NULL,
  email        text,
  status       text,
  total_cents  int,
  created_at   timestamptz DEFAULT now()
);   -- ~20M rows; indexed on (id), (user_id) -- NOT on email

2 · The task

At 14:00 the pager fires: API p95 latency jumped from 40 ms to 900 ms. The host CPU graph looks normal; memory is fine. A 13:50 deploy went out ten minutes earlier. Find the cause and fix it without restarting the database — a restart clears the evidence and the symptom will just come back.

3 · The naive attempt — and why it fails

The reflex is to reach for the two biggest levers: restart Postgres (or the app), and add CPU/RAM. Both are wrong here, for instructive reasons.

  • Restarting drops every connection, so the symptom vanishes for a few minutes — and you have learned nothing, destroyed the live evidence in pg_stat_activity, and guaranteed a recurrence at the next busy moment.
  • Adding hardware targets the one instrument that was already normal. A query blocked on a lock, or one doing a sequential scan and waiting on I/O, does not show up as high CPU — a blocked backend burns zero CPU while it waits. You would be paying for capacity that the bottleneck can't use.

The deeper error is method: acting before measuring. The database is telling you exactly what's wrong; you just have to read it.

4 · The fix — walk the checklist

Run the live views top-down, cheapest checks first. Step through the exact routine:

Running the checklist surfaces two findings. pg_stat_activity shows a reporting session idle in transaction for 22 minutes, and a cluster of checkout sessions sitting active but waiting on a Lock — pg_blocking_pids() confirms they are all blocked by that one pid. Separately, pg_stat_statements (reset after the deploy) shows a new #1 by total_exec_time: SELECT ... FROM orders WHERE email = $1, averaging 884 ms, that did not exist before 13:50. Its plan explains why:

explain — illustrative

Seq Scan on orders  (cost=0.00..438521.00 rows=1 width=62)
                    (actual time=402.1..883.9 rows=1 loops=1)
  Filter: (email = 'ana@example.com')
  Rows Removed by Filter: 19999999
Planning Time: 0.14 ms
Execution Time: 884.0 ms

5 · Why the fix is better

Two targeted actions, each aimed at a measured cause. First, end the idle-in-transaction session (SELECT pg_terminate_backend(pid);) and set idle_in_transaction_session_timeout so it can't recur — the checkout queue drains the instant the lock releases. Second, give the new query the index it's begging for, without locking the table:

sql

CREATE INDEX CONCURRENTLY orders_email_idx ON orders (email);

The same query re-planned:

explain — illustrative

Index Scan using orders_email_idx on orders
  (cost=0.44..8.46 rows=1 width=62)
  (actual time=0.03..0.04 rows=1 loops=1)
  Index Cond: (email = 'ana@example.com')
Execution Time: 0.06 ms

884 ms → 0.06 ms per lookup, and the lock storm gone. Neither fix was a guess: one came from pg_stat_activity + pg_blocking_pids, the other from pg_stat_statements + a plan. That is the entire value of monitoring — it converts "the database is slow" into two lines of SQL.

6 · Narrate it

"P95 doubled right after a deploy, but CPU was flat — so I suspected a lock or a bad plan, not load. pg_stat_activity showed a reporting transaction stuck idle-in-transaction for 22 minutes with checkout sessions queued behind its lock; pg_blocking_pids named it, and I terminated it. pg_stat_statements (reset after the deploy) surfaced a new top query scanning orders by email with no index — the plan showed a Seq Scan removing 20 million rows. I added the index CONCURRENTLY and set an idle-in-transaction timeout so it can't recur. Latency was back to 40 ms within a minute, and I never restarted the database."

05 Your turn

Graded drills & the traps

Four drills, increasing in difficulty. Write the SQL (or the reasoning) before you open each solution.

Drill 1 — catch the silent lock-holder

List every backend that has been idle in transaction for more than 5 minutes, most-stuck first — the single most common cause of mysterious locks and bloat.

Try it first, then read

SELECT pid, usename, now() - state_change AS idle_for, left(query,40) AS last_query FROM pg_stat_activity WHERE state = 'idle in transaction' AND now() - state_change > interval '5 minutes' ORDER BY state_change;
Why: for a backend in this state, state_change is when it entered "idle in transaction," so its age is exactly how long it has been pinning its snapshot and holding any locks — the thing to terminate.

Drill 2 — is the cache healthy?

Write the buffer cache hit-ratio query. You're told it reads 99.4%. Is the database healthy? Name at least one way this number can lie.

Try it first, then read

SELECT round(100.0 * sum(heap_blks_hit) / nullif(sum(heap_blks_hit + heap_blks_read),0), 2) FROM pg_statio_user_tables; — 99.4% is fine for OLTP (aim >99%). But it can lie three ways: (1) it's cumulative since the last stats reset, so a great lifetime ratio can hide a bad last hour; (2) a "read" only means the block wasn't in shared_buffers — the OS page cache may still serve it from RAM, so a low ratio isn't necessarily disk I/O; (3) a giant sequential scan can post a high hit ratio and still be slow. Why: it's a coarse trend, not a latency metric.

Drill 3 — the query that's slow but "looks fine"

After the 13:50 deploy, checkout feels slow — but in pg_stat_statements its mean_exec_time looks normal. Where do you look, and what do you run first?

Try it first, then read

An average is not a distribution, and the history is stale. (1) Weeks of fast pre-deploy calls are dragging the mean down — run SELECT pg_stat_statements_reset(); and watch fresh numbers. (2) The mean smooths outliers; check max_exec_time and stddev_exec_time, or enable auto_explain to capture the actual slow executions and their plans (a plan flip after new statistics never shows up in the mean). (3) Catch one live: query pg_stat_activity during a slow checkout and read its wait_event. Why: reset to get a baseline, then look at the tail and the plan — not the average.

Drill 4 — when is a replica safe to read?

On the primary, report each replica's lag in bytes and in seconds, and decide when a replica is safe to serve a read-after-write. What's the gotcha with the "seconds" number?

Try it first, then read

SELECT application_name, pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes, replay_lag FROM pg_stat_replication;
A replica is safe for read-after-write only when its replay_lsn has reached the LSN of your write: capture pg_current_wal_lsn() on the primary at write time and compare it to the replica's pg_last_wal_replay_lsn(). Gotcha: replay_lag is time-based and reads NULL when the standby is fully caught up or simply idle (no traffic to time) — so "NULL lag" can mean perfectly current or no recent activity. Why: trust the byte/LSN comparison for correctness; use seconds only for human dashboards.

The traps

  • Idle in transaction is the silent killer. It holds locks and pins the xmin horizon, so autovacuum can't clean dead rows → bloat. Set idle_in_transaction_session_timeout and don't let application code hold a transaction open across a slow external call.
  • Watching the wrong instrument. CPU and RAM graphs can look perfect while one lock freezes everything. Measure the database's own signals, not just the host's.
  • No baseline. Cumulative counters (pg_stat_statements, pg_statio_*) are meaningless without "compared to when." Reset after a deploy and compare fresh.
  • pg_stat_statements not enabled. It needs shared_preload_libraries + a restart + CREATE EXTENSION. Turn it on before the incident — during one is too late to see the history.
  • Alert fatigue. Too many noisy alerts train you to ignore the pager. Alert on symptoms (latency, errors, replica lag) with sane thresholds; keep the raw counters for the dashboards you open afterward.
★ Review

Summary & self-test

The whole lesson compresses to one habit: a database reports its own health through the pg_stat_* views — read them before you touch the engine, and "it's slow" becomes a specific pid, query, or table you can fix. Guessing adds indexes the planner ignores and restarts that hide the cause; measuring hands you the answer.
