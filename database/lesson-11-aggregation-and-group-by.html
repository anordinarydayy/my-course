Aggregation & GROUP BY

Every report, dashboard, and "how many / how much" question is the same move under the hood: take a pile of rows and collapse it into summaries. This lesson is the aggregate toolkit — count, sum, avg, min, max, GROUP BY, and HAVING — plus the handful of NULL-and-grouping mistakes that trip up almost everyone in an interview and in production. We build the mental model, then earn it on a real query and a set of graded drills.

Original study notes. Written from scratch for engineers who want SQL depth that pays off in interviews and in real systems. PostgreSQL-based (PG 17/18); the ideas are ANSI-standard and portable. 00 Orientation

From many rows to one number

Most of the SQL you have written so far preserves rows: a SELECT with a WHERE filters the set but each surviving row still comes out on its own. An aggregate function does the opposite — it collapses a whole set of rows into a single scalar value. Feed sum(amount) a thousand rows and you get back one number. That collapse is the entire idea; everything else in this lesson is about which rows get collapsed together.

Postgres ships the five you will reach for constantly, plus a few more:

  • count(...) — how many rows (we spend a whole section on its three forms).
  • sum(...) — the total of a numeric column.
  • avg(...) — the mean (watch the type: integer input still needs care — more below).
  • min(...) / max(...) — the smallest / largest value; they also work on text and dates.
  • Handy extras: bool_and / bool_or, string_agg, array_agg, and the statistical set (stddev, percentile_cont).

Run one with no GROUP BY and it treats the entire result set as a single group, returning exactly one row:

sql

SELECT count(*), sum(price), avg(price)   -- one row out, no matter how many rows in
FROM products;

Add GROUP BY category and you change the granularity of "a group": instead of one bucket holding every row, Postgres makes one bucket per distinct category and runs the aggregates inside each bucket. You get one row per group — the shape of every "sales by region", "signups by day", "errors by service" query ever written.

The one sentence to memorize

An aggregate collapses a set of rows to one value; GROUP BY decides which rows share a set. No GROUP BY means "the whole table is one set" → one row out. With GROUP BY key, each distinct key is its own set → one row per key. Hold that and the rest is bookkeeping.

01 The core mechanic

GROUP BY partitions, aggregates collapse ▸

The clearest way to hold GROUP BY in your head is as a two-step move. First it partitions the input rows into groups by the grouping key — no data is lost yet, the rows are just sorted into buckets. Then, for each bucket, every aggregate in your SELECT collapses that bucket's rows down to one value, and the bucket emits a single summary row.

Two details worth locking in. First, the number of output rows equals the number of distinct grouping keys, not the number of input rows — that is exactly why aggregation is a "collapse". Second, once you have grouped, the only things you may put in the SELECT are the grouping columns themselves and aggregates over the rest; a raw column like amount no longer has a single value per group, so Postgres will refuse it. That rule is the subject of the next section.

Grouping does not sort

A subtle habit-breaker: GROUP BY guarantees grouping, not ordering. The result above happened to come out A-then-B, but Postgres may return groups in any order — especially when it picks a HashAggregate plan. If you want the rows in a particular order, say so with an explicit ORDER BY. Never rely on grouping to sort for you.

02 Rules & traps

The rules and the traps

Aggregation has a small rulebook, and every rule maps to a classic bug. Learn them together.

Rule 1 — every non-aggregated column must be grouped

Postgres enforces the standard: any column in the SELECT that is not wrapped in an aggregate must appear in the GROUP BY. The reason is arithmetic honesty — if a group holds many amount values, which one would a bare amount return? There is no answer, so the query is rejected:

sql

SELECT category, amount, sum(amount)   -- ✗ ERROR: column "amount" must appear in GROUP BY
FROM orders
GROUP BY category;                        -- ...or be used in an aggregate function

Fix it by deciding what you actually meant: group by amount too, or aggregate it (max(amount), sum(amount)). (A narrow exception exists: if you group by a table's primary key, Postgres lets you select that table's other columns "for free", since the key already pins one row per group. Rely on it rarely — being explicit reads better.)

Rule 2 — WHERE filters rows, HAVING filters groups

This is the single most-tested distinction in the topic, and it falls straight out of the logical order of operations Postgres follows for a SELECT:

  • FROM / JOIN → assemble the raw rows
  • WHERE → filter individual rows (no aggregates allowed — groups don't exist yet)
  • GROUP BY → partition the survivors into groups
  • aggregates evaluated → each group gets its count, sum, …
  • HAVING → filter whole groups by their aggregate value
  • SELECT → project the final columns / expressions
  • ORDER BY → sort → LIMIT / OFFSET → page

So WHERE runs before grouping and cannot see an aggregate; HAVING runs after and is the only place a count(*) or sum(...) predicate belongs. Push every plain-row condition into WHERE (it shrinks the input before the expensive grouping), and reserve HAVING for conditions on the aggregate:

sql

SELECT category, sum(amount) AS revenue
FROM orders
WHERE created_at >= '2026-01-01'   -- row filter, before grouping — cheap
GROUP BY category
HAVING sum(amount) > 1000;        -- group filter, after aggregation

Rule 3 — aggregates skip NULLs (and the empty-group trap)

Every standard aggregate — sum, avg, min, max, count(col) — silently ignores NULL inputs (count(*) counts rows, so it doesn't; a few collection aggregates like array_agg are exceptions, keeping NULLs). That is usually what you want (the average of {10, NULL, 20} is 15, not "unknown"), but it creates a famous surprise: when a group ends up with no non-null values — or a filter leaves no rows at all — count returns 0 but sum, avg, min, and max return NULL, not 0.

The trap

  • sum of no rows → NULL
  • Your dashboard shows a blank instead of $0.
  • Arithmetic on it (revenue * 1.1) stays NULL and spreads.

The fix

  • Wrap the outside: coalesce(sum(amount), 0).
  • Now an empty set reports 0, and downstream math behaves.
  • Use it any time a "total" must render as a number.

Rule 4 — integer division truncates

Averaging by hand as sum / count is a landmine when the operands are integers: 7 / 2 in SQL is 3, not 3.5, because integer ÷ integer yields an integer. Postgres's avg() already returns numeric for integer input, so prefer it; but the moment you compute a ratio yourself, cast one side to numeric:

sql

-- ✗ truncates: both operands are integer
SELECT sum(qty) / count(*) FROM order_items;
-- ✓ real average: promote to numeric first
SELECT sum(qty)::numeric / count(*) FROM order_items;
Four rules, four bugs

Non-grouped column → a rejected query. WHERE/HAVING mix-up → an error or a wrong filter. Forgotten coalesce → a NULL where a 0 belonged. Bare integer division → a silently wrong average. None of these throw a stack trace in production — the last two just return quietly wrong numbers, which is worse. Internalize the four and you have dodged the whole topic's error surface.

03 The three counts

count(*) vs count(col) vs count(DISTINCT col) ▸

"How many?" has three different SQL answers, and the gap between them is exactly where NULLs and duplicates live. Getting the wrong one is one of the most common quietly-wrong queries in a codebase, so pin the three down precisely:

  • count(*) — counts rows. It never inspects a value, so NULLs and duplicates all count. This is the fast one and the right default for "how many rows".
  • count(col) — counts rows where col is not NULL. Same as count(*) only when the column has no NULLs.
  • count(DISTINCT col) — counts distinct non-NULL values. Duplicates collapse to one; NULLs are still ignored.

One more trap the picture makes obvious: people sometimes write count(status = 'paid') hoping for "how many paid?". It does not do that — status = 'paid' is a boolean expression, and count of it just counts the rows where the expression is not NULL (i.e. almost all of them). The right tools for "count a condition" are count(*) FILTER (WHERE status = 'paid') or the old sum(CASE WHEN … THEN 1 ELSE 0 END) — both shown in the drills.

Reach for the cheap one by default

count(*) is the right answer to "how many rows" and it is the fastest — the planner never has to test a value or de-duplicate. Only step up to count(col) when NULLs must be excluded, and to count(DISTINCT col) when you truly need unique values (which also costs a sort or hash). Choosing the strongest count "just in case" is a common, needless slowdown.

04 Worked problem

Worked: top 5 categories by revenue ▸

Time to put it together on an interview-shaped question. First the pipeline in one picture, then the full write-up: schema, a tempting wrong first attempt, the correct query, the index and its plan, and how to say the answer out loud.

1 · The schema

sql

CREATE TABLE products (
  id        int PRIMARY KEY,
  category  text NOT NULL,
  price     numeric(10,2) NOT NULL
);
CREATE TABLE order_items (
  id          int PRIMARY KEY,
  product_id  int NOT NULL REFERENCES products(id),
  qty         int NOT NULL
);

2 · The task

For each product category, compute total revenue as sum(price × qty), keep only categories with more than 10 order line items, and return the top 5 categories by revenue, highest first.

3 · The tempting wrong first attempt

The instinct is to filter the "more than 10" condition in WHERE, the same place we filter everything else:

sql

SELECT p.category, sum(p.price * oi.qty) AS revenue
FROM products p
JOIN order_items oi ON oi.product_id = p.id
WHERE count(*) > 10            -- ✗ ERROR: aggregate functions are not allowed in WHERE
GROUP BY p.category
ORDER BY revenue DESC
LIMIT 5;

Postgres rejects it outright. Recall the order of operations: WHERE runs before GROUP BY, so at that moment there are no groups and no count(*) to test — the aggregate simply does not exist yet. A predicate on a group's aggregate is what HAVING is for.

4 · The correct query

sql

SELECT p.category, sum(p.price * oi.qty) AS revenue
FROM products p
JOIN order_items oi ON oi.product_id = p.id
GROUP BY p.category
HAVING count(*) > 10           -- group predicate: keep busy categories
ORDER BY revenue DESC
LIMIT 5;

Every clause earns its place: the JOIN pairs each line item with its product's category and price; GROUP BY p.category partitions; sum(p.price * oi.qty) collapses each partition to a revenue; HAVING count(*) > 10 drops categories with 10 or fewer line items; ORDER BY revenue DESC ranks; LIMIT 5 takes the podium.

5 · The index and the plan

First, the index this schema is missing: Postgres does not auto-index foreign-key columns, so add one on the join key.

sql

CREATE INDEX ON order_items (product_id);

Here is an illustrative plan for the correct query on a modest data set (200 products, ~5,000 line items). The plan-node names are real Postgres:

explain (illustrative)

-- EXPLAIN (ANALYZE) of the correct query
Limit  (cost=412.6..412.6 rows=5) (actual rows=5)
  ->  Sort  (cost=412.6..412.6 rows=12)  (actual rows=7)
        Sort Key: (sum((p.price * oi.qty))) DESC
        ->  HashAggregate  (cost=..380 rows=12)  (actual rows=7)
              Group Key: p.category
              Filter: (count(*) > 10)
              Rows Removed by Filter: 5
              ->  Hash Join  (cost=..320 rows=5000)  (actual rows=5000)
                    Hash Cond: (oi.product_id = p.id)
                    ->  Seq Scan on order_items oi  (rows=5000)
                    ->  Hash
                          ->  Seq Scan on products p  (rows=200)
Execution Time: 8.4 ms

Read it bottom-up. The two Seq Scans feed a Hash Join (Postgres builds a hash table on the small products side and probes it with all 5,000 line items). HashAggregate is where GROUP BY lives, and — key point — HAVING count(*) > 10 shows up as its Filter, with Rows Removed by Filter: 5 telling you five thin categories were dropped after grouping. Finally a tiny Sort over the 7 survivors and a Limit.

Notice what the new index did not do: this plan still reads every row. That is the honest lesson — a full-table aggregate has to read the whole table; no index removes work you genuinely need. An index pays off the moment you can filter rows before grouping. Add a real row predicate and the same query changes shape entirely:

sql

SELECT p.category, sum(p.price * oi.qty) AS revenue
FROM products p
JOIN order_items oi ON oi.product_id = p.id
WHERE p.price > 100              -- row filter FIRST: only pricey products
GROUP BY p.category
HAVING count(*) > 10
ORDER BY revenue DESC
LIMIT 5;

explain (illustrative)

-- now only ~45 products qualify, so the index earns its keep
Limit
  ->  Sort  (Sort Key: revenue DESC)
        ->  HashAggregate  (Group Key: p.category, Filter: count(*) > 10)
              ->  Nested Loop  (actual rows=900)
                    ->  Seq Scan on products p  (Filter: price > 100, rows=45)
                    ->  Index Scan using order_items_product_id_idx on order_items oi
                          Index Cond: (product_id = p.id)

Now the planner filters products to 45 rows, then for each does an Index Scan on order_items via our new index — a Nested Loop touching ~900 rows instead of 5,000. That is the payoff of filtering early: fewer rows ever reach the aggregate.

Last tool worth knowing here — the FILTER clause lets you compute conditional aggregates side by side in one pass, e.g. total revenue and bulk-only revenue together:

sql

SELECT p.category,
       sum(p.price * oi.qty)                             AS revenue,
       sum(p.price * oi.qty) FILTER (WHERE oi.qty >= 2) AS bulk_revenue
FROM products p
JOIN order_items oi ON oi.product_id = p.id
GROUP BY p.category;

6 · Narrate it (say this out loud)

The interview answer, spoken

"I join line items to products so each row carries its category and price, then GROUP BY category and sum price × qty for revenue. The 'more than 10 orders' rule is a condition on the group's row count, so it goes in HAVING count(*) > 10, not WHERE — WHERE can't see aggregates because it runs before grouping. Then ORDER BY revenue DESC LIMIT 5. In the plan it's a hash join into a HashAggregate; the HAVING is the aggregate's filter. Since I aggregate the whole table there's nothing to index away — but if the question added a row filter, I'd index order_items(product_id) so the join becomes index scans over far fewer rows."

05 Drills

Graded drills & traps

Four drills, hardest last. Write your answer before opening each solution. Assume an orders(id, created_at timestamptz, status text, total numeric) table where noted.

Drill 1 — orders per calendar day

Count how many orders were placed on each day, oldest day first.

Try it first, then read

sql

SELECT date_trunc('day', created_at) AS day, count(*) AS orders
FROM orders
GROUP BY day               -- Postgres lets you group by the output alias
ORDER BY day;

Why: date_trunc('day', ...) buckets every timestamp to midnight, so all of a day's orders share one group key. Group by the same expression (or, as a Postgres extension, by its output alias day).

Drill 2 — average order value, NULL- and integer-safe

Report the mean order total three ways: skipping missing totals, treating missing totals as 0, and the grand total rendered as a number even when there are no rows.

Try it first, then read

sql

SELECT avg(total)                    AS avg_ignoring_nulls,   -- NULL totals skipped
       avg(coalesce(total, 0))     AS avg_nulls_as_zero,    -- NULL counted as 0
       coalesce(sum(total), 0)     AS revenue               -- empty set → 0, not NULL
FROM orders;

Why: the two averages answer different questions — decide whether a missing total means zero. If total were an integer column, an explicit ratio would need a cast: sum(total)::numeric / count(*) to dodge integer division.

Drill 3 — conditional counts in one pass

In a single scan, return the total number of orders and the number that are 'paid'.

Try it first, then read

sql

SELECT count(*)                                        AS all_orders,
       count(*) FILTER (WHERE status = 'paid')    AS paid,
       sum(CASE WHEN status = 'paid' THEN 1 ELSE 0 END) AS paid_old_way
FROM orders;

Why: FILTER is the modern, readable idiom; the CASE-sum is the pre-9.4 equivalent. Do not write count(status = 'paid') — that counts every row where the boolean is non-NULL, which is nearly all of them.

Drill 4 — the join-then-aggregate double count, fixed

You add a product_tags(product_id, tag) table and join it to compute category revenue. Revenue suddenly balloons. Explain and fix (this is the fan-out from Lesson 10).

Try it first, then read

sql

-- ✗ WRONG: each order_items row is duplicated once per matching tag,
--   so sum(price*qty) is multiplied by the tag count — inflated revenue.
SELECT p.category, sum(p.price * oi.qty) AS revenue
FROM products p
JOIN order_items oi ON oi.product_id = p.id
JOIN product_tags  t  ON t.product_id  = p.id   -- fan-out!
GROUP BY p.category;

-- ✓ RIGHT: aggregate on the correct grain, then attach anything else separately.
WITH cat_rev AS (
  SELECT p.category, sum(p.price * oi.qty) AS revenue
  FROM products p
  JOIN order_items oi ON oi.product_id = p.id
  GROUP BY p.category
)
SELECT * FROM cat_rev ORDER BY revenue DESC;

Why: never sum a value across a join that multiplies its grain. Pre-aggregate each table to its own grain (in a CTE or subquery), then combine the summaries. If you truly need one query, sum(DISTINCT ...) is not a fix — it drops legitimately equal amounts.

Traps to keep on a sticky note

1. Counting NULLs. count(col) skips NULLs; count(*) doesn't — pick on purpose.
2. HAVING vs WHERE. Row conditions → WHERE; aggregate conditions → HAVING. An aggregate in WHERE is an error.
3. Non-grouped column. Every non-aggregated SELECT column must be in GROUP BY, or Postgres rejects the query.
4. Integer-division averages. int / int truncates — cast to numeric for a real ratio.
5. Fan-out double counts. A join that multiplies rows inflates sum/count; pre-aggregate to the right grain first.

★ Review

Summary & self-test

The whole lesson compresses to one idea: an aggregate collapses a set of rows to a single value, GROUP BY chooses which rows share a set, WHERE filters rows before that and HAVING filters groups after — and NULLs, duplicates, and integer types quietly change the answer if you let them.

02Partition then collapseGROUP BY buckets rows by key, then each aggregate reduces a bucket to one summary row.

04Group every bare columnAny non-aggregated SELECT column must be in GROUP BY — Postgres enforces it.
05Three countscount(*) = rows; count(col) = non-NULL; count(DISTINCT col) = distinct non-NULL.
06Aggregates skip NULLsEmpty group → count is 0 but sum/avg are NULL. Wrap totals in coalesce(…, 0).
