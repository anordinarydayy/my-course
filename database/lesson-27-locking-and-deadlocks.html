Locking & Deadlocks

Most of the time PostgreSQL lets you forget locks exist — its MVCC design keeps readers and writers out of each other's way. But when two transactions fight over the same row, or you must protect an invariant like a balance or a stock count, you reach for locks deliberately — and the moment a transaction holds two of them, deadlock becomes possible. This practice lesson is about taking locks on purpose, reading how they block, and writing code that never deadlocks.

27 When to block

When you do need to block

Start with the good news, because it is most of the news: under MVCC (multi-version concurrency control), Postgres gives every transaction its own snapshot of the data. Readers never block writers and writers never block readers — an UPDATE writes a new row version while old readers keep seeing the old one. For the overwhelming majority of your queries, you never take a lock by hand, and you should lean on that default rather than reaching for locks out of nervousness.

But MVCC has one hard limit it cannot wish away: two transactions that write the same row must serialize. Whoever writes second has to wait for the first to commit or roll back — otherwise one update would silently overwrite the other, a lost update. Postgres enforces this automatically, with a row lock taken by every UPDATE and DELETE. You don't ask for it; it's simply there whenever two writers collide on a row.

There is a second, sharper reason to lock on purpose: invariants that span your read and your write. If your logic is "read the stock, check it is above zero, then decrement," that check is only meaningful if nobody changes the row between your read and your write. MVCC alone will happily let another transaction slip in there. To close the gap you must hold a lock on the row while you decide — the classic read-modify-write pattern, and exactly what SELECT … FOR UPDATE is for.

Postgres offers two granularities of lock, and it helps to keep them straight from the start:

Row locks

  • Protect individual rows, not the table.
  • Taken by UPDATE/DELETE and by SELECT … FOR UPDATE/FOR SHARE.
  • Fine-grained: different rows lock independently, so concurrency stays high.
  • Your everyday tool for same-row contention and read-modify-write.

Table locks

  • Protect a whole table.
  • Taken automatically by everything — a weak one for SELECT, the strongest for ALTER/DROP.
  • Coarse: the strong modes exclude every other query on the table.
  • You rarely take them by hand, but DDL does — where migrations bite.
Lock last, not first

The instinct from other systems is "lock the data before you touch it." In Postgres that instinct is usually wrong: MVCC already isolates snapshots, so a manual lock is a deliberate choice you make only for same-row write contention or a read-modify-write invariant. Every lock you hold is concurrency you gave up — so take the weakest lock that does the job, hold it for the shortest window, and let MVCC do the rest.

27 Row locks

Row locks: FOR UPDATE and friends ▸

The workhorse is SELECT … FOR UPDATE. It reads the matching rows and takes an exclusive lock on each one, as if to announce "I am about to update these." Any other transaction that tries to UPDATE, DELETE, or SELECT … FOR UPDATE those same rows will wait until you commit or roll back. It does not error, it does not read a stale value — it queues.

A plain UPDATE or DELETE already takes a row lock for you — technically FOR NO KEY UPDATE, a hair weaker than FOR UPDATE (it still lets the FOR KEY SHARE that foreign-key checks use pass through). The practical effect is identical: a second writer to the same row waits. The four row-lock strengths, weakest to strongest:

  • FOR KEY SHARE — weakest; taken by foreign-key checks. Blocks only changes to the row's key.
  • FOR SHARE — a shared read lock; many transactions can hold it at once, but it blocks writers. Use it when you need a row to stay put while you read related data.
  • FOR NO KEY UPDATE — what a plain UPDATE takes; exclusive against other writers.
  • FOR UPDATE — the strongest row lock; fully exclusive. Reach for it when you will modify the row after reading it.

Watch two sessions contend for the exclusive lock on one row. The point is that the second one waits — it is not rejected, and it never sees the value the first is busy changing:

Here is the read-modify-write done right — a stock decrement that cannot lose an update, because the row is locked from the read through the write:

sql

BEGIN;
-- lock row 7 AND read its current stock in one shot
SELECT stock FROM products WHERE id = 7 FOR UPDATE;
-- app decides: stock is 3, so selling one is fine
UPDATE products SET stock = stock - 1 WHERE id = 7;
COMMIT;   -- commit releases the lock
The lock lives only inside the transaction

FOR UPDATE only helps if it wraps the read and the write in one transaction. If you SELECT … FOR UPDATE, COMMIT, and then UPDATE in a fresh transaction, you have thrown the lock away before using it — the gap reopens. A row lock is held until the transaction that took it commits or rolls back, and not one statement longer.

27 Table locks

Table-level locks, and failing fast

Every statement also takes a table-level lock, usually one so weak you never notice it. They exist to keep DDL from yanking a table out from under a running query. There are eight modes; you mostly care about the two ends of the ladder and one rule that connects them.

  • ACCESS SHARE — taken by a plain SELECT. The weakest mode; it conflicts only with ACCESS EXCLUSIVE. Many readers hold it at once.
  • ROW SHARE / ROW EXCLUSIVE — taken by SELECT … FOR UPDATE and by INSERT/UPDATE/DELETE. Ordinary writes; they don't block one another at the table level (row locks sort out the row-by-row conflicts).
  • SHARE / SHARE ROW EXCLUSIVE — taken by a non-concurrent CREATE INDEX and some ALTERs.
  • ACCESS EXCLUSIVE — the strongest. Taken by most ALTER TABLE, by DROP TABLE, TRUNCATE, and VACUUM FULL. It conflicts with everything, including a plain SELECT.

The rule to remember: readers share, DDL excludes. Any number of ACCESS SHARE locks coexist happily, so concurrent reads never block each other. But an ACCESS EXCLUSIVE lock must wait for every current query on the table to finish, and while it waits it blocks every new query behind it.

That is why an innocent-looking ALTER TABLE on a busy table can freeze your whole app. It queues behind the running queries to get its ACCESS EXCLUSIVE lock, and while it sits in that queue, every fresh query queues behind it. A five-millisecond schema change can cause a five-minute stall. Doing DDL safely on a live table is its own craft — Phase 9, L52 — but the core defense is to not let a lock wait be unbounded.

Two tools let you fail fast instead of waiting forever:

  • NOWAIT — SELECT … FOR UPDATE NOWAIT errors immediately (SQLSTATE 55P03) if the row is already locked, rather than blocking. Good when a wait would be pointless.
  • lock_timeout — SET lock_timeout = '2s' caps how long any lock acquisition may block before it errors. A safety valve, especially around migrations, so a stuck lock fails fast instead of piling connections up behind it.

sql

-- error out at once if row 7 is already locked
SELECT * FROM products WHERE id = 7 FOR UPDATE NOWAIT;

-- or: wait at most 2 seconds for any lock, then fail
SET lock_timeout = '2s';
ALTER TABLE products ADD COLUMN note text;
NOWAIT vs lock_timeout

NOWAIT means "never wait at all — fail the instant the lock is taken." lock_timeout means "wait, but no longer than N." For migrations the standard guardrail is a short lock_timeout plus a retry: the ALTER either grabs its lock quickly or bows out cleanly, so it can never be the thing holding an ACCESS EXCLUSIVE lock while a hundred queries pile up behind it.

27 Deadlocks

How a deadlock forms ▸

A deadlock is not a Postgres bug — it is a shape your transactions make. It needs exactly two ingredients: two transactions, each holding a lock the other one wants, arranged in a cycle. The classic recipe:

  • T1 locks row A, then asks for row B.
  • T2 locks row B, then asks for row A.
  • Neither can proceed and neither will release. That mutual wait is the cycle.

Postgres does not hang. Each waiting transaction, after blocking for deadlock_timeout (1 second by default), triggers the deadlock detector, which builds the wait-for graph and looks for a cycle. Find one and it breaks the cycle by aborting a single transaction — the victim — which fails with SQLSTATE 40P01 (deadlock detected). The other transaction's wait ends and it proceeds as if nothing had happened.

Two consequences for you. First, a deadlock is a normal, recoverable error: catch 40P01 and retry the victim's transaction from the top — it usually succeeds on the second try, because the contention has cleared. Second, better than retrying is not deadlocking: since the cycle needs two transactions grabbing the same locks in opposite orders, you prevent every deadlock of this kind by always grabbing locks in a consistent order. That single discipline is the heart of the worked problem next.

deadlock_timeout is a detection delay, not a fix

It is tempting to "solve" deadlocks by raising deadlock_timeout. Don't — it only makes real deadlocks take longer to surface, so your transactions sit blocked for longer before the victim is chosen. Leave it near the default; the detector runs rarely and cheaply. The real fix is to design the cyclic ordering out of your code so the detector has nothing to find.

27 Worked problem

A deadlock-free balance transfer ▸

Time to put it together. The bank transfer is the canonical concurrency exercise because the naive version deadlocks under load and the fix is a one-line discipline. We will build it in six moves.

1 · The schema

sql

CREATE TABLE accounts (
  id      bigint  PRIMARY KEY,
  balance numeric NOT NULL CHECK (balance >= 0)
);

Note the CHECK: the database itself refuses a negative balance, so an overdrawn transfer aborts even if the application's own guard slips. Correctness backstops live in the schema, not just in code.

2 · The task

Move an amount from one account to another, under heavy concurrency, without ever losing money, going negative, or deadlocking.

3 · The naive version, and why it deadlocks

The obvious code locks the "from" account, then the "to" account:

sql · naive — locks in payment order

BEGIN;
SELECT balance FROM accounts WHERE id = $1 FOR UPDATE;   -- lock "from" ($1) first
SELECT balance FROM accounts WHERE id = $2 FOR UPDATE;   -- then "to" ($2)
UPDATE accounts SET balance = balance - $3 WHERE id = $1;
UPDATE accounts SET balance = balance + $3 WHERE id = $2;
COMMIT;

Now run two transfers in opposite directions at the same moment — one 1 → 2, one 2 → 1 — and watch the interleave:

the interleaving

-- time   Tx A  (1 -> 2)                 Tx B  (2 -> 1)
--  t1    lock row 1  ok
--  t2                                   lock row 2  ok
--  t3    want row 2  -> waits (B has it)
--  t4                                   want row 1  -> waits (A has it)
--  --    cycle: each waits on the other -> one is aborted with 40P01

Each transaction locked its own "from" account first, so under this direction pair they grabbed rows 1 and 2 in opposite orders — the exact recipe from FIG. 2.

4 · The fix: one consistent lock order

Lock every row the transaction needs up front, in a fixed canonical order — ascending id — before touching anything. A single SELECT … ORDER BY id FOR UPDATE does exactly that:

sql · the fix — ordered locking

BEGIN;
-- lock BOTH rows in one statement, always in ascending id order
SELECT id, balance
  FROM accounts
 WHERE id IN ($1, $2)
 ORDER BY id
   FOR UPDATE;
-- both rows are ours now; apply the transfer
UPDATE accounts SET balance = balance - $3 WHERE id = $1;   -- debit "from"
UPDATE accounts SET balance = balance + $3 WHERE id = $2;   -- credit "to"
COMMIT;

5 · Why it is now safe

Both transfers, regardless of direction, ask for the lower id first. So the transaction that wins row 1 also goes on to get row 2; the other simply waits for both. There is no way to build a cycle when every transaction reaches for locks in the same order — the pre-condition for this class of deadlock is gone. The CHECK (balance >= 0) handles the other risk: a transfer that would overdraw the source aborts on the debit, and atomicity rolls the whole thing back.

6 · Narrate it

In an interview you would say it like this: "The transfer touches two rows, and two concurrent transfers in opposite directions is the textbook deadlock. I take both row locks in a single SELECT … FOR UPDATE with ORDER BY id, so every transaction acquires its locks low-id-first — that makes a wait cycle impossible. The CHECK (balance >= 0) constraint backstops overdrafts. And I still wrap the whole thing in a retry loop that catches 40P01, with a lock_timeout so a stuck lock fails fast instead of hanging a connection — belt and suspenders."

lock_timeout and a retry loop still belong here

Ordered locking removes this deadlock, but it can't promise no other code path ever locks these rows in a different order — a bulk job, a report, a future feature. So keep the cheap insurance: a short lock_timeout to bound the wait, and a loop that catches 40P01 (and lock-timeout errors) and re-runs the transaction from the top. You do the ordering to make deadlocks rare; you keep the retry to make them harmless.

27 Drills & traps

Graded drills, then the traps

Read each challenge, write your answer, then open the solution. No peeking — the value is in the attempt.

Drill 1 — read-modify-write vs the lost update

Add a $20 credit to account 1. Write it so two concurrent credits cannot lose each other's money — then show the version that does lose one.

Try it first, then read

sql · correct

BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;    -- lock + read
UPDATE accounts SET balance = balance + 20 WHERE id = 1;   -- relative write
COMMIT;

sql · lost update

SELECT balance FROM accounts WHERE id = 1;               -- reads 100, no lock
-- a concurrent tx also read 100 and committed 120...
UPDATE accounts SET balance = 120 WHERE id = 1;         -- clobbers it: should be 140

Why: FOR UPDATE serializes the two writers, and balance = balance + 20 applies the delta on top of whatever committed first — so both credits land.

Drill 2 — kill a deadlock with lock ordering

A nightly job locks rows in id order; a new feature locks the same rows in reverse to "process newest first." QA reports random 40P01s. Fix it without slowing the job.

Try it first, then read

Standardize the lock-acquisition order across both paths; the order you process results in is independent and free to differ. Keep FOR UPDATE … ORDER BY id everywhere, then re-sort the output however you like afterward:

sql

SELECT * FROM tasks WHERE id IN (…) ORDER BY id FOR UPDATE;  -- lock low -> high
-- then process the locked rows newest-first in the app, if you want

Why: deadlocks come from the order locks are acquired, not the order rows are used. Standardize the former; the latter costs nothing.

Drill 3 — don't wait at all (preview of L28)

A pool of workers each want the next unclaimed job row. You don't want a worker to block on a row another worker already locked — it should just take a different one. What clause?

Try it first, then read

sql

SELECT id FROM jobs
 WHERE state = 'ready'
 ORDER BY id
 FOR UPDATE SKIP LOCKED
 LIMIT 1;

Why: SKIP LOCKED silently steps over rows another transaction holds, so each worker grabs a different job with zero waiting — a lock-free work queue. (NOWAIT would instead error on a locked row; SKIP LOCKED just ignores it.) This queue pattern is the whole of L28.

Drill 4 — bound a wait with lock_timeout

One report query occasionally sits behind a long transaction's lock for minutes, exhausting the connection pool. Make it give up after 3 seconds instead of hanging.

Try it first, then read

sql

SET lock_timeout = '3s';    -- session-wide (or SET LOCAL inside one txn)
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;  -- errors after 3s if still blocked

Why: lock_timeout caps how long any single lock acquisition may block, turning an unbounded hang into a fast, catchable error you can retry or surface to the user.

The traps

  • Inconsistent lock order — the deadlock generator. Two code paths taking the same rows in different orders will eventually cycle. Enforce one canonical order (ascending id) everywhere.
  • Long transactions holding locks — a lock lives until COMMIT/ROLLBACK. A transaction that locks a row and then does slow work (an HTTP call, user think-time) blocks every other writer to that row. Keep the locked window short.
  • Read-modify-write with no FOR UPDATE — the silent lost update. If the "check" and the "write" are separate statements, lock the row (or fold it into a single relative UPDATE) so nobody can slip between them.
  • DDL at peak — ALTER/DROP/TRUNCATE take ACCESS EXCLUSIVE and block every query on the table. Run migrations off-peak, with a short lock_timeout, and see Phase 9, L52.
★ Review

Summary & self-test

The whole lesson compresses to one idea: locks are the tool you reach for when MVCC's optimism isn't enough — when two writers hit one row, or an invariant spans your read and your write. Take them deliberately, in a consistent order, and hold them briefly, and a deadlock becomes something you design out rather than debug.

01MVCC firstReaders and writers don't block each other. Reach for a manual lock only for same-row write contention or a read-modify-write invariant.
02FOR UPDATETakes an exclusive row lock while it reads. A second writer of that row waits until you commit or roll back — it never clobbers.
03The lock ladderFOR KEY SHARE < FOR SHARE < FOR NO KEY UPDATE (a plain UPDATE) < FOR UPDATE.
04Table locksACCESS SHARE for a SELECT up to ACCESS EXCLUSIVE for DDL. Readers share; DDL on a busy table blocks everything.
05A deadlock is a cycleTwo transactions each holding what the other wants. The detector fires after deadlock_timeout and aborts a victim with 40P01.
06Order your locksGrab rows in one canonical order (ascending id, via ORDER BY id FOR UPDATE) and a cycle can't form.
07Fail fastNOWAIT errors instead of waiting; SKIP LOCKED steps over locked rows; lock_timeout bounds the wait. All beat hanging.
08Retry the victim40P01 is normal and recoverable: catch it and re-run the transaction. Keep the retry even after you've ordered your locks.
