Statistics, Selectivity & Bad Plans

The planner cannot run your query to decide how to run it — so it estimates how many rows each step will produce, from statistics it keeps about your data, and costs the competing plans on those estimates. When the estimates are good, you get the fast plan. When they are wrong, you get the disasters of Concept 20. This lesson opens the black box: what statistics Postgres stores, how they become a row estimate, why that estimate sometimes lands orders of magnitude off, and how you repair it.

Original study notes. Written for engineers who want to reason about the query planner instead of fighting it. Examples are PostgreSQL (PG 17/18); the plan output shown is illustrative but uses real node types and columns. Contains three interactive diagrams (press Play or step through with Next). 00 The premise

The planner is an estimator, not an oracle

Here is the constraint that shapes everything in this lesson: to run a query well, the planner must first decide how to run it — but it cannot run it to find out. Deciding whether an index scan beats a sequential scan, or whether to join with a nested loop or a hash join, depends on how many rows each step will handle. And the only way to know that for certain would be to execute the query, which is the very thing it is trying to plan. So it does the next best thing: it estimates.

The mechanism is a cost-based optimizer. The planner enumerates candidate plans, and for each one it assigns a cost — an abstract number built from two ingredients: per-operation costs (reading a page, processing a tuple) and, critically, the estimated number of rows flowing through each node, called the cardinality. It then picks the plan with the lowest total cost. The per-operation constants rarely cause trouble. The row estimates cause almost all of it.

You can see the estimate directly — it is the rows= figure in every EXPLAIN line:

sql

EXPLAIN SELECT * FROM events WHERE city = 'Portland';

illustrative

                          QUERY PLAN
-----------------------------------------------------------------
 Seq Scan on events  (cost=0.00..18334.00 rows=9873 width=68)
   Filter: (city = 'Portland')

That rows=9873 is not a fact the database looked up; it is a prediction the planner made from stored statistics, before executing anything. On a million-row table, believing the answer is ~10,000 rows versus ~10 rows changes the whole plan: ten rows argue for chasing an index; ten thousand argue for a plain scan. Get the prediction right and the plan is right. Get it wrong and, as Concept 20 showed, the same query can run in ten milliseconds or ten seconds.

The chain to hold onto

statistics → selectivity → row estimate → plan choice. Every link is mechanical and every link can be inspected. When a query is mysteriously slow, you are almost never looking at a bug in the planner's logic — you are looking at bad inputs to it. This lesson walks the chain forward, then shows you how to repair each link. Cost units, by the way, are abstract — not milliseconds — so never compare a cost number to a wall-clock time.

01 The catalog

What statistics Postgres keeps ▸

The statistics live in the system catalog pg_statistic, with one row per analyzed column. They are gathered by the ANALYZE command — which you can run by hand, but which autovacuum also runs automatically after a table changes enough. ANALYZE doesn't read the whole table; it takes a random sample (its size scales with default_statistics_target, 100 by default) and builds a compact statistical profile from it. For each column it stores, roughly, five things:

  • n_distinct — how many different values the column holds (a positive count, or a negative fraction of the table when it scales with row count).
  • Most-common-values (MCV) list — the handful of values that appear most often, each paired with its measured frequency. This is where skew is recorded.
  • Histogram — equal-frequency buckets describing the spread of every value not in the MCV list. This powers range predicates (<, >, BETWEEN).
  • Null fraction — what share of the column is NULL.
  • Physical correlation — how closely the on-disk row order tracks the sorted value order (this is what makes a BRIN index or an ordered scan viable).

You read them through the human-friendly view pg_stats (a formatted layer over pg_statistic):

sql

ANALYZE events;  -- refresh the sample & recompute stats

SELECT attname, n_distinct, null_frac, correlation,
       most_common_vals, most_common_freqs
FROM pg_stats
WHERE tablename = 'events' AND attname = 'city';

Now watch how those stored numbers turn into a row estimate for a single equality predicate. The key insight is that the same column gives two very different estimates depending on whether the value you ask about is in the MCV list.

The takeaway is that an estimate is only as good as the sample behind it. An MCV hit is nearly exact — Postgres measured that frequency directly. A non-MCV value is a smoothed guess: the leftover probability spread evenly over the remaining distinct values, (1 − ΣMCV) / (n_distinct − n_MCV). Raising default_statistics_target (or the per-column target) buys a bigger sample, a longer MCV list, and a finer histogram — sharper estimates in exchange for a slightly slower ANALYZE and slightly more planning time.

Why the MCV list matters so much

Skewed columns — a status that is 98% 'closed', a country dominated by one value — are exactly where a naive "1 / n_distinct" estimate fails hardest. The MCV list is what saves those cases: it lets the planner know that status = 'closed' matches almost everything (so scan) while status = 'error' matches almost nothing (so use the index). Lose the MCV list to a too-small sample and both queries get the same wrong average.

02 The core quantity

Selectivity drives everything above it

The bridge from statistics to a plan is one number: selectivity — the fraction of a table's rows that a predicate keeps, between 0 and 1. Multiply selectivity by the row count and you have the row estimate. That single quantity is what the planner threads through the entire plan.

Each predicate shape draws its selectivity from a different piece of the profile you just saw:

Equality, MCV value

  • city = 'Metropolis'
  • Reads the exact frequency off the MCV list.
  • Near-exact: sel = 0.42.

Equality, other value

  • city = 'Ankh'
  • Smoothed over the non-MCV tail.
  • Estimated: ≈ 0.0026.

Range

  • ts >= '2026-01-01'
  • Measured from the histogram buckets.
  • Interpolated across the boundaries.

Now the part that makes estimation fragile: combining predicates. For WHERE a AND b, the planner multiplies the two selectivities — sel(a & b) = sel(a) × sel(b). For OR it adds and subtracts the overlap. That multiplication is not a fact about your data; it is an assumption — that the two columns are statistically independent. When they are, the math is right. When they aren't, it can be wrong by orders of magnitude, and the error only grows as you AND more columns together.

Why does one wrong number matter so much? Because plans are trees, and the planner reads them bottom-up. The row estimate at a leaf scan feeds the cost of the join above it, which feeds the join above that. If the leaf says "200 rows" when reality is "10,000," every decision stacked on top was made for a table 50× smaller than the one that actually shows up at runtime — join methods, join order, whether to sort, whether to materialize. A wrong estimate at the bottom poisons every choice above it. That is the mechanism behind almost every catastrophic plan.

The one diagnostic that matters

Everything in this lesson reduces to a single check you run with EXPLAIN ANALYZE: for each node, compare the estimated rows= against the actual rows=. If they are close, the planner had good information and its choice was reasonable. If they diverge by 10×, 100×, 1000×, you have found the poisoned node — and the fix is almost always about statistics, not about rewriting the query.

03 Failure modes

Why estimates go wrong ▸

Estimates drift from reality in four recognizable ways. Learn to name them and diagnosis becomes fast:

  • Stale statistics. You bulk-loaded or deleted a lot of rows and autovacuum hasn't re-ANALYZEd yet. The planner is reasoning about a table that no longer exists — often estimating far too few (or too many) rows.
  • Correlated columns. The independence assumption from Concept 02 breaks. The planner computes sel(a) × sel(b), but a and b move together, so the true selectivity is closer to sel(a) alone. This is the classic, most damaging failure.
  • Skew past the MCV list. A value common enough to matter but not in the (finite) MCV list gets the smoothed average — badly wrong if the true distribution has a long, lumpy tail.
  • Expressions the planner can't estimate. WHERE lower(email) = ... or WHERE date(created_at) = ... has no column statistics at all, so Postgres falls back to a fixed default guess.

Watch the correlated-columns case, because it is the one that turns a healthy database into a support ticket. A table of a million events; a filter on city and state. Both look selective on their own — but every Portland is already in Oregon.

Here is the same story in a real plan. Run EXPLAIN (ANALYZE, BUFFERS) — in PostgreSQL 18 BUFFERS is on by default — and read the estimated-vs-actual gap:

sql

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM events e
JOIN venues v ON v.id = e.venue_id
WHERE e.city = 'Portland' AND e.state = 'OR';

illustrative

Nested Loop  (cost=0.42..18492.11 rows=200 width=124)
             (actual time=0.05..118.734 rows=10000 loops=1)
  Buffers: shared hit=40210 read=8334
  ->  Seq Scan on events e  (cost=0.00..18334.00 rows=200 width=96)
             (actual time=0.011..92.400 rows=10000 loops=1)
        Filter: ((city = 'Portland') AND (state = 'OR'))
        Rows Removed by Filter: 990000
        Buffers: shared read=8334
  ->  Index Scan using venues_pkey on venues v
             (cost=0.42..0.79 rows=1 width=28)
             (actual time=0.002..0.002 rows=1 loops=10000)
        Index Cond: (id = e.venue_id)
        Buffers: shared hit=40210
 Planning Time: 0.210 ms
 Execution Time: 121.900 ms

Read it bottom-up and the crime is obvious. The Seq Scan was estimated at rows=200 but produced rows=10000 — a 50× miss, because 0.01 × 0.02 assumed independence that isn't there. Believing "200 rows," the planner chose a Nested Loop: for each outer row, probe the venues index once. Cheap for 200 probes. But loops=10000 means the inner index scan actually ran ten thousand times. The plan didn't misbehave — it faithfully executed a strategy chosen for a table 50× smaller than the real one.

The tell: loops and Rows Removed

Two numbers expose this instantly. An inner node with a big loops= count (10000 here, not the estimated 200) means the planner under-estimated the outer side and picked a nested loop it now regrets. And Rows Removed by Filter: 990000 confirms the scan waded through the whole table to find the 10,000 matches. When estimate and actual disagree at a leaf, trust the actual — and go fix the statistics that produced the estimate.

04 The repair

Fixing the estimate ▸

Because Postgres has no query hints, you never tell the planner which plan to use. You improve its inputs and let it re-decide. Four tools, applied to the right failure mode:

  • ANALYZE (or wait for autovacuum) — the cure for stale stats. Re-samples and recomputes. Always the first thing to try, and useless against the other three failure modes.
  • Raise the per-column statistics target — ALTER TABLE ... ALTER COLUMN ... SET STATISTICS n. A bigger sample, longer MCV list, finer histogram. The cure for skew past the MCV list.
  • Extended statistics — CREATE STATISTICS. The cure for correlated columns: it teaches the planner the relationship between columns so it stops multiplying blindly.
  • Index an expression — CREATE INDEX ON t (lower(email)). Building the index also gives that expression its own statistics, curing the un-estimable expression case.

For our Portland problem the right tool is the third. Extended statistics come in three kinds: dependencies (functional dependencies — "city determines state"), ndistinct (the joint distinct count across columns, which fixes multi-column GROUP BY estimates), and mcv (a multi-column most-common-values list). We declare all three over the correlated pair, then re-analyze:

sql

CREATE STATISTICS events_city_state (dependencies, ndistinct, mcv)
  ON city, state FROM events;

ANALYZE events;  -- build the extended stats from a fresh sample

Re-run the query and the plan has changed on its own. The scan now estimates rows=10000, matching reality, so a nested loop looks expensive and the planner switches to a Hash Join — build a hash of venues once, probe it while streaming the events:

illustrative

Hash Join  (cost=64.00..19010.00 rows=10000 width=124)
           (actual time=1.40..70.900 rows=10000 loops=1)
  Hash Cond: (e.venue_id = v.id)
  Buffers: shared hit=210 read=8334
  ->  Seq Scan on events e  (cost=0.00..18334.00 rows=10000 width=96)
             (actual time=0.010..40.100 rows=10000 loops=1)
        Filter: ((city = 'Portland') AND (state = 'OR'))
        Rows Removed by Filter: 990000
  ->  Hash  (cost=39.00..39.00 rows=2000 width=28)
             (actual time=1.20..1.20 rows=2000 loops=1)
        ->  Seq Scan on venues v  (cost=0.00..39.00 rows=2000 width=28)
 Execution Time: 74.300 ms

Nothing about the SQL changed. We didn't add an index, didn't rewrite the join, didn't reach for a hint that Postgres doesn't have. We handed the planner an accurate estimate — rows=10000 instead of 200 — and it independently reached the better plan. That is the whole discipline: correct the inputs; trust the optimizer to correct the output.

Match the tool to the mode

ANALYZE fixes staleness. A higher stats target fixes skew (a longer MCV list, a finer histogram). CREATE STATISTICS fixes correlation between columns. An expression index fixes un-estimable expressions. Reaching for the wrong one — raising the stats target to fix a correlation problem, as steps 2–3 show — burns time and moves the estimate not at all. Diagnose the mode first, then pick the tool.

05 The loop

Reason about it

Put the whole lesson into the loop you'll actually run at the terminal. It is short, and it always starts the same way — not by editing the query, but by measuring it.

  • 1. Reproduce with the truth. Run EXPLAIN (ANALYZE, BUFFERS) on the slow query. Estimates alone lie; you need ANALYZE to see what really happened. (For writes, wrap in BEGIN; ... ROLLBACK; so the measurement doesn't persist.)
  • 2. Walk the tree bottom-up, comparing estimated rows vs actual rows. Find the lowest node where they diverge badly. That node — not the one at the top where the time is reported — is the root cause.
  • 3. Name the failure mode. Did a lot of data change recently (stale)? Are two AND-ed columns related (correlation)? Is a common value missing from the MCV list (skew)? Is there a function on the column (un-estimable expression)?
  • 4. Apply the matching input fix — ANALYZE, a higher stats target, CREATE STATISTICS, or an expression index — and re-measure. The estimate and the plan should move together.

The reflex this builds is worth stating plainly: when estimate and actual are far apart, it is a statistics problem first, not a query-rewrite problem. Engineers waste hours reshuffling joins and adding OFFSET tricks to a query whose only real defect is that the planner was handed a 50×-wrong row count. Fix the count and the "clever" rewrite becomes unnecessary. And remember the hard boundary from step 04: PostgreSQL exposes no hint to force a plan. Your leverage is entirely on the inputs — the statistics the planner reads and the indexes it can choose from. Improve those, and the plan follows.

There is also a maintenance dimension. Statistics don't stay fresh by themselves after heavy churn; the cadence of VACUUM and ANALYZE — and the autovacuum thresholds that trigger them — is what keeps the planner honest over time. A database that plans beautifully on Monday can plan terribly on Friday for no reason but a month of un-analyzed inserts.

★ Review

Summary & self-test

The whole lesson compresses to one idea: the planner can't run your query to plan it, so it estimates row counts from stored statistics — and when those estimates are wrong, the plan is wrong. You don't hint the plan; you repair the estimate. Read EXPLAIN ANALYZE for the node where estimated and actual rows diverge, name the failure mode, and fix the input that produced it.
