SELECT & the Query Pipeline

A query is written SELECT-first, but it is evaluated almost SELECT-last. Once you internalize the true evaluation order — FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT — a dozen confusing "why won't this work?" errors stop being mysteries and become predictions. This lesson builds that pipeline in your head so the rest of the SQL phase clicks.

Original study notes. Written from scratch for engineers, using PostgreSQL (PG 17/18). Every SQL snippet is runnable; the error messages quoted are the ones Postgres actually prints. Contains three interactive diagrams (press Play or step through with Next). This is a concept lesson — no SQL drill; it builds the mental model the rest of the phase writes against.
00 Orientation

You write it in the wrong order

Here is the anchor idea for the whole lesson: the order you type a query is not the order the database runs it. You always write the clauses in one fixed sequence — SELECT comes first on the page — but Postgres evaluates them in a completely different, equally fixed sequence, and SELECT lands near the end. That single mismatch is the hidden cause behind most beginner (and plenty of senior) SQL errors.

Written order (how you type it)

  • SELECT — the columns you want
  • FROM / JOIN — the tables
  • WHERE — row filter
  • GROUP BY — grouping keys
  • HAVING — group filter
  • ORDER BY — sort
  • LIMIT / OFFSET — slice

Logical order (how it runs)

  • FROM / JOIN — build the row-set
  • WHERE — filter rows
  • GROUP BY — form groups
  • HAVING — filter groups
  • SELECT — project & name (aliases)
  • DISTINCT — drop duplicates
  • ORDER BY — sort the result
  • LIMIT / OFFSET — slice the result

Read the right-hand column top to bottom and every classic error explains itself. "Column net does not exist" when you use a SELECT alias in WHERE? Of course — WHERE ran four stages before SELECT created that name. "Aggregate functions are not allowed in WHERE"? Naturally — grouping hasn't happened yet at WHERE time. "Column must appear in the GROUP BY clause"? That rule lives at the grouping stage. None of these are arbitrary; they all fall out of one ordering.

Logical order vs the physical plan

This evaluation order is the logical (semantic) model — it defines what the result must be. The planner (Phase 4) is then free to execute things in a different physical order for speed: it may push a WHERE filter down into an index, apply LIMIT early to stop a sort short, or reorder joins. Those optimizations never change the answer, because the answer is pinned by the logical order you're about to learn. Think of it like a compiler: source order defines meaning, the optimizer picks the machine steps.

01 The pipeline

The logical evaluation order ▸

The cleanest way to hold this is as a pipeline: a stack of stages, each one taking a set of rows in and handing a transformed set of rows out. The data flows straight down. Every stage can only see what the stages above it produced — that "can only see above me" rule is the entire secret to predicting SQL behavior. Step through them in evaluation order (SELECT and DISTINCT share a box):

Notice the shape of it. The two rust stages — WHERE and HAVING — are the filters, and they sit on opposite sides of grouping: WHERE filters rows before groups form, HAVING filters groups after. The garnet stage in the middle — SELECT — is where columns are finally computed and aliases are born, which is why nothing above it can use an alias. And the last two stages, ORDER BY and LIMIT, work on the already-projected result, which is exactly why ORDER BY can use an alias. Keep this picture; the next three sections just zoom into pieces of it.

02 Build then filter rows

FROM & WHERE — assemble, then filter

The first two stages produce the raw material everything else works on. FROM (with its JOINs) assembles the working set of rows. If you join orders to customers, the output of this stage is the combined, widened rows — every order paired with its customer's columns. This is the source; it may be far bigger than the answer you ultimately want.

Then WHERE filters that set one row at a time. It looks at each individual row and keeps it only if the predicate is TRUE. Two consequences follow directly from where it sits in the pipeline — and both are exam favorites:

  • No aggregates in WHERE. Grouping hasn't happened yet, so there is no such thing as sum(amount) for a group at this point. Writing WHERE sum(amount) > 100 earns "aggregate functions are not allowed in WHERE". Aggregate filters belong in HAVING.
  • No SELECT aliases in WHERE. The SELECT list runs three stages later, so a name you invented there doesn't exist yet. You must repeat the underlying expression.

sql

-- WHERE sees one row at a time, before any grouping
SELECT o.id, o.amount
FROM   orders o
JOIN   customers c ON c.id = o.customer_id
WHERE  o.status = 'paid'
  AND  c.country = 'DE';

Because WHERE runs so early — before grouping, sorting, or projection — it is also your single biggest performance lever. The fewer rows survive this stage, the less work every later stage does. That is why the planner tries so hard to satisfy WHERE from an index: a predicate like o.status = 'paid' can jump straight to matching rows if an index on status exists.

Sargability, previewed

A predicate the index can use is called sargable (Search ARGument-able). WHERE created_at >= '2026-01-01' is sargable — the index on created_at can seek to that point. But wrap the column in a function — WHERE date(created_at) = '2026-01-01' or WHERE lower(email) = '...' — and you hide the raw column from its plain index, forcing a full scan. Keep the column bare on one side of the comparison. We'll make this rigorous, with EXPLAIN, in Phase 4; for now just file it next to "WHERE runs first."

03 Collapse then filter groups

GROUP BY & HAVING ▸

After WHERE has thinned the rows, GROUP BY collapses the survivors into groups — one output row per distinct combination of the grouping keys. Once rows are grouped, the only things you can talk about per group are (a) the grouping keys themselves and (b) aggregates computed over each group: count(), sum(), avg(), max(), and so on. Then HAVING filters those groups, post-aggregation — it is WHERE for groups. Watch the row-set shrink twice, once for rows and once for groups:

The diagram makes the two filters concrete. WHERE status = 'paid' dropped the void games row before grouping, so that $50 never reaches any total. HAVING sum(amount) > 100 then dropped whole groups after totals were computed. Confuse the two and you get the wrong number: put the group condition in WHERE and Postgres rejects it; put the row condition in HAVING and it either errors or scans far more than it needed to. The query behind the figure:

sql

SELECT   category, sum(amount) AS revenue
FROM     orders
WHERE    status = 'paid'            -- filter ROWS (pre-group)
GROUP BY category
HAVING   sum(amount) > 100       -- filter GROUPS (post-aggregate)
ORDER BY revenue DESC;

Two rules govern this whole stage, and they're worth memorizing verbatim. Rule 1: filter rows in WHERE, filter groups in HAVING. Rule 2: every column in the SELECT list that is not inside an aggregate must appear in GROUP BY. The reason for Rule 2 is physical: a group is many rows squeezed into one output row, so a non-grouped, non-aggregated column has no single value to show — which of the group's rows would it pick? Postgres refuses to guess: "column must appear in the GROUP BY clause or be used in an aggregate function."

Aggregates and NULL — a detail that bites

Aggregates skip NULLs. That makes count(*), count(col), and count(DISTINCT col) three different questions: count(*) counts rows in the group; count(col) counts rows where col is not null; count(DISTINCT col) counts the distinct non-null values. Likewise avg(col) divides by the non-null count, not the row count — so a column full of NULLs quietly changes the average. We give aggregation and NULL their own lessons (L11 and L12); note the trap here.

04 Project, sort, slice

SELECT, ORDER BY — and why an alias fails in WHERE ▸

Now the payoff stage. SELECT runs fifth — after FROM, WHERE, GROUP BY, and HAVING. This is where columns are finally projected: expressions are computed, functions applied, window functions evaluated, and results given names with AS. Those names — aliases — do not exist until this moment. Then DISTINCT removes duplicate output rows, ORDER BY sorts what's left, and LIMIT/OFFSET slice off a page.

This ordering is the whole reason a single alias can be legal in one clause and an error in another. Follow the alias net as the query descends through the stages:

The takeaway is sharp: an alias is born in SELECT, so the clauses that run before SELECT can't use it, and the clauses that run after it can. The three "before" filters — WHERE, GROUP BY's expressions, HAVING — must instead repeat the underlying expression. ORDER BY, running last, is the one clause that gets to name it directly:

sql

-- alias in WHERE: ERROR  "column \"net\" does not exist"
SELECT amount - fee AS net FROM sales WHERE net > 0;

-- fix: repeat the expression in WHERE
SELECT amount - fee AS net FROM sales WHERE amount - fee > 0;

-- alias in ORDER BY: fine — ORDER BY runs after SELECT
SELECT amount - fee AS net FROM sales ORDER BY net DESC;

The same clock explains the other two headline errors. An aggregate in WHERE fails because grouping hasn't run yet; move it to HAVING. A non-grouped column in SELECT fails because the grouping stage already collapsed the rows; add it to GROUP BY or wrap it in an aggregate.

sql

-- aggregate in WHERE: ERROR "aggregate functions are not allowed in WHERE"
SELECT category, sum(amount) FROM sales WHERE sum(amount) > 100 GROUP BY category;
-- fix: filter groups in HAVING
SELECT category, sum(amount) FROM sales GROUP BY category HAVING sum(amount) > 100;
A real Postgres exception: aliases in GROUP BY & ORDER BY

The pure logical model says the alias isn't born until SELECT, so it should be illegal in every earlier clause. But PostgreSQL, as a non-standard convenience, does resolve an output-column alias in GROUP BY and ORDER BY — not in WHERE or HAVING. So GROUP BY day below works even though day is a SELECT alias. Don't rely on it in portable SQL, but recognize it, and know the strict boundary: WHERE and HAVING will always reject the alias.

sql

-- Postgres extension: an output alias is accepted in GROUP BY / ORDER BY
SELECT date_trunc('day', created_at) AS day, count(*)
FROM   sales
GROUP BY day        -- works in Postgres (not standard SQL)
ORDER BY day;
05 Reason about it

Reason about it: narrate a query in evaluation order

Here is the skill this lesson is really teaching — the one that makes you fast at reading and debugging SQL. When you see a query, don't read it top to bottom as written; replay it in evaluation order in your head. Take this one:

sql

SELECT   c.country, count(*) AS n, sum(o.amount) AS revenue
FROM     orders o
JOIN     customers c ON c.id = o.customer_id
WHERE    o.status = 'paid'
GROUP BY c.country
HAVING   sum(o.amount) > 1000
ORDER BY revenue DESC
LIMIT    10;

Narrate the stages aloud, and the answer — and every rule — falls out:

  • FROM / JOIN. Build the row-set: each paid-or-not order paired with its customer. This is the widest the data ever gets.
  • WHERE. Keep only rows where o.status = 'paid'. Row-level, one at a time. (Try WHERE revenue > 0 here and you'd instantly know why it fails: revenue isn't born yet.)
  • GROUP BY. Collapse the survivors into one group per c.country. From here on, only c.country and aggregates are namable — which is exactly why count(*) and sum(o.amount) are legal and a stray o.id in the SELECT would not be.
  • HAVING. Keep only groups whose sum(o.amount) > 1000. Note we repeat the aggregate; we can't write HAVING revenue > 1000, because the alias still isn't born.
  • SELECT. Now project c.country, count(*) AS n, sum(o.amount) AS revenue. The names n and revenue come into existence right here.
  • ORDER BY. Sort by revenue DESC — legal, because SELECT already created revenue.
  • LIMIT. Slice off the top 10 sorted groups. Done.

That narration is a diagnostic engine. Any "why won't this work?" becomes a single question: at the stage where I used this name, had it been created yet, and was the thing I'm referring to a row or a group? Alias in WHERE → not born yet. Aggregate in WHERE → no groups yet. Bare column in a grouped SELECT → the group has no single value for it. One model, all three answers.

Where this shows up next

This pipeline is the spine of the whole SQL phase. L10 zooms into the FROM/JOIN stage (nested loop vs hash vs merge joins). L11 lives in the GROUP BY stage (aggregation in depth). L12 is about the values that flow through every stage — NULL and three-valued logic, which is why WHERE keeps only TRUE. Window functions (Phase 3) run inside the SELECT stage, which is precisely why you can't filter on a window result in WHERE and must wrap the query. ★ Review

Summary & self-test

The whole lesson compresses to one idea: a query is written SELECT-first but evaluated FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT — and every stage can only see what the stages above it produced. Hold that, and SQL's error messages turn from riddles into predictions.

03WHERE filters rowsBefore grouping, one row at a time. No aggregates, no SELECT aliases — neither exists yet.
04HAVING filters groupsAfter aggregation. It's WHERE for groups; the group condition belongs here, not in WHERE.
