ORM Pitfalls

An ORM turns tables into objects and makes CRUD feel like plain code — and that convenience is exactly what makes it dangerous. Every property access can secretly be a query, every list can secretly be a loop of queries, and the SQL it emits is invisible until you go looking. This lesson names the recurring traps — N+1, lazy loading across transaction boundaries, over-fetching, and unreviewed generated SQL — and drills the habit of reading the query log the ORM would rather you ignore.

Original study notes. Written for engineers who ship on an ORM (ActiveRecord, Hibernate/JPA, Django, SQLAlchemy, Prisma, Sequelize) but interview and debug on raw SQL. Examples target PostgreSQL (PG 17/18); the ORM snippets are deliberately framework-agnostic pseudocode. Contains three interactive diagrams (press Play or step with Next). This is a practice lesson: it ends in a worked SQL problem and a set of graded drills so the fixes become reflex, not trivia.
00 Orientation

The abstraction that hides the SQL

An ORM (object–relational mapper) exists to close a gap: your code thinks in objects and collections, your database thinks in rows and joins. The ORM translates between them so you can write user.orders instead of hand-rolling a SELECT. That is genuinely great — it removes boilerplate, gives you migrations and identity maps, and lets a team move fast. The problem is never that the ORM is wrong; it usually emits perfectly valid SQL. The problem is that it emits SQL you didn't see, at moments you didn't choose.

Because a mapped object looks like an ordinary object, engineers stop thinking about the wire. A field access that costs a network round trip reads exactly like a field access that costs nothing. Multiply that by a loop and by a request handler that runs a thousand times a second, and the same abstraction that saved you an afternoon of typing quietly becomes the top entry in your slow-query log. Four traps account for the overwhelming majority of ORM-caused pain:

What the ORM gives you

  • Objects and collections instead of rows — less boilerplate.
  • Migrations, an identity map, dirty tracking, associations.
  • Portability and a uniform API across databases.
  • Fast iteration for straightforward CRUD.

What it hides — the four traps

  • N+1: a list load, then one query per row.
  • Lazy loading firing outside the intended transaction.
  • Over-fetching: whole entities / SELECT * when you needed two columns.
  • Unreviewed SQL: generated queries and migrations nobody read.

The cure is not "drop the ORM." The cure is a posture: treat the query log as part of the code. Turn on SQL logging in development, watch the count of statements per request, and stay fluent enough in SQL that when you see the ORM do something dumb you can reach for the escape hatch. The rest of this lesson is that posture, one trap at a time.

The one habit

For any endpoint, ask a single question: how many SQL statements does one request run, and does that number grow with the data? A handler that runs 3 queries for 10 rows and 3 for 10,000 is healthy. One that runs 11 for 10 rows and 10,001 for 10,000 has an N+1 and will fall over in production. Every trap below is a variation on watching that number.

01 The classic trap

The N+1 query ▸

The N+1 query problem is the single most common database performance bug, and the ORM practically invites it. You load a list of parent rows — that's the 1 query. Then you loop over them and touch a related object on each — and each of those lazy accesses fires its own query, giving you N more. Total: 1 + N statements to render one page, almost all of them tiny, near-identical, and dominated by round-trip latency rather than real work.

Here is the shape in framework-agnostic pseudocode — it looks completely innocent:

pseudocode · the trap

# 1 query: load the list of users
users = User.limit(5)

for u in users:
    # each u.orders is a LAZY relation -> +1 query PER user (N)
    print(u.name, u.orders.count)

The insidious part is that N+1 is invisible in development. With 5 seed rows the page is fast and the bug is silent; in production with 500 rows the same code fires 501 queries and the endpoint times out. The fix is to tell the ORM you want the relation up front — eager loading. Every ORM has a word for it: JOIN/includes (ActiveRecord), select_related/prefetch_related (Django), JOIN FETCH or an entity graph (JPA/Hibernate), joinedload/selectinload (SQLAlchemy), include (Prisma). Under the hood it resolves to one of two constant-query strategies: a single JOIN, or a two-step batch load with WHERE id = ANY(...).

1 JOIN vs 2 batched queries

Both fixes are correct; they trade differently. A single JOIN is one round trip but multiplies parent columns across every child row (wide result, worse for many-to-many). A batched load (selectinload, prefetch_related) runs exactly 2 queries — parents, then all children via WHERE parent_id = ANY(ARRAY[...]) — and avoids the row explosion. The rule that matters: either way the query count is constant, not proportional to the number of rows.

02 Where the query fires

Lazy loading & transaction boundaries ▸

Lazy loading is the mechanism behind N+1, but it causes a second, subtler class of bug: the query doesn't just fire too often — it fires at the wrong time, outside the transaction you thought you were in. A lazy association is a placeholder proxy; it runs its SELECT the first moment you touch it. If that touch happens after your service method returned and the transaction committed — say, while a view template renders — the query lands on a different snapshot, on a different connection, or on a session that's already closed.

This is the open-session-in-view anti-pattern: frameworks keep the persistence session open for the whole HTTP request so lazy loads in the view "just work," which hides N+1s and stretches transactions across rendering. Follow where the boundary actually is versus where the query fires:

Two distinct failures live in that last-but-one box. In stacks that close the session at the service boundary (classic JPA/Hibernate), touching a lazy relation afterward throws a LazyInitializationException outright — a hard crash. In stacks that keep the session open through rendering, it silently works but reads on a later, possibly inconsistent snapshot than the rest of your logic saw, and it does so one row at a time. Either way the root cause is the same: you let the ORM decide when to query, and it chose a moment your transaction no longer covered.

Make the boundary explicit

Decide, per use case, exactly what data the response needs and load all of it inside one transaction, eagerly. Return plain DTOs/values from the service layer so the view has nothing left to lazy-load. Treat open-session-in-view as off by default. The transaction boundary is a design decision — when you let lazy loading move it for you, you've lost the isolation and atomicity guarantees you opened a transaction to get (see Phase 5).

03 The rest of the field

The other four traps

N+1 and lazy boundaries are the headline acts, but the same "the object hides the SQL" root cause produces a handful more. None of these needs a diagram — each is a habit to build.

Over-fetching — loading columns you never use

By default an ORM hydrates the whole entity: SELECT * on every column, including the fat text/bytea/jsonb ones you didn't need. Two costs follow. First, you ship bytes over the wire and build objects for nothing. Second, and more subtle, SELECT * defeats an index-only scan: if you only need id and email and there's a covering index on (id, email), selecting just those two lets Postgres answer from the index alone — but ask for every column and it must visit the heap for each row (see Phase 4 / L22). Reach for the ORM's column projection: select(:id, :email), .only()/.values(), a DTO/constructor-expression query, or Prisma's select.

Missing indexes the ORM won't add for you

ORMs generate tables and, usually, an index on the primary key and on declared foreign keys — but they do not know your query patterns. The index that makes WHERE status = 'active' AND created_at > ... fast, or the composite/partial index your hottest endpoint needs, is your job. The ORM cheerfully runs a sequential scan forever and never warns you. Read the plan of your important queries with EXPLAIN and add indexes by hand in a migration.

Unreviewed generated migrations and SQL

Auto-generated migrations are a convenience, not a safety net. A one-line model change can emit an ALTER TABLE that takes an ACCESS EXCLUSIVE lock, or a plain CREATE INDEX that blocks writes for the whole build, or a NOT NULL-with-backfill that rewrites a huge table — each an outage on a live system (see L52 on zero-downtime migrations). Read every generated migration before it ships. Prefer CREATE INDEX CONCURRENTLY, ADD COLUMN with no volatile default, and NOT NULL via CHECK ... NOT VALID then VALIDATE.

Fighting the pooler — and knowing the escape hatch

Two operational realities. First, ORM connection pools interact with an external pooler (PgBouncer in transaction mode, see L38): server-side prepared statements, SET, advisory locks, and session state don't survive across transactions, so an ORM that leans on them can break behind a transaction-mode pooler unless configured for it. Second — and the release valve for everything above — when the ORM's generated SQL is wrong, slow, or contorted, drop to raw SQL. Every ORM has an escape hatch (find_by_sql, @Query(nativeQuery), session.execute(text(...)), $queryRaw). Using it is not a failure of the ORM; it's using the ORM correctly.

The through-line

Every trap here is the same mistake wearing a different hat: you stopped looking at the SQL. Over-fetching, the missing index, the dangerous migration, the pooler mismatch — each is caught the instant you read the generated statement and its plan. The ORM is a great typist and a poor DBA; you have to be the DBA.

04 Worked problem

Kill a pathological N+1 ▸

Time to fix a real one end to end — from the query log, to the rewrite, to the plan.

1 · The schema

sql

CREATE TABLE authors (
  id    bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  name  text NOT NULL
);

CREATE TABLE posts (
  id         bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  author_id  bigint NOT NULL REFERENCES authors(id),
  title      text NOT NULL,
  body       text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- indexes for the access pattern
CREATE INDEX posts_created_at_idx ON posts (created_at DESC);
CREATE INDEX posts_author_id_idx  ON posts (author_id);

2 · The task

Render the 50 most recent posts, each line showing the post title and its author's name. Straightforward — and a perfect N+1 trap.

3 · The naive attempt — and why it's slow

pseudocode · ORM, as written

posts = Post.order(created_at: :desc).limit(50)   # 1 query
for p in posts:
    render(p.title, p.author.name)                # p.author is lazy -> +1 query each

The generated query log tells the whole story:

generated sql · the log

SELECT * FROM posts ORDER BY created_at DESC LIMIT 50;
SELECT * FROM authors WHERE id = 7;
SELECT * FROM authors WHERE id = 3;
SELECT * FROM authors WHERE id = 7;   -- id 7 again: duplicate work
-- ... 47 more single-row author lookups ...

Why it hurts: that's 1 + 50 = 51 statements for one page. Each is a full network round trip; the total wall time is dominated by 51 × latency, not by any real database work. Worse, many author lookups repeat the same id, so you re-fetch rows you already have. It benchmarks fine on 5 seed posts and melts under a real feed.

4 · The fix — eager load

Tell the ORM you need the author with the post. It resolves to a single joined query:

sql · the rewrite (one query)

SELECT p.id, p.title, a.name AS author
FROM posts p
JOIN authors a ON a.id = p.author_id
ORDER BY p.created_at DESC
LIMIT 50;

In ORM terms that's Post.includes(:author) / select_related('author') / JOIN FETCH p.author / include:{author:true}. If you'd rather avoid widening every post row with author columns, the batched form is two queries and just as constant:

sql · the batched alternative (two queries)

SELECT id, title, author_id FROM posts ORDER BY created_at DESC LIMIT 50;
SELECT id, name FROM authors WHERE id = ANY(ARRAY[7,3,9, /* distinct ids */]);

5 · Why it's better — the plan

The rewrite goes from 51 round trips to 1, and the join happens inside the engine with no network cost per author. The plan for the JOIN version:

EXPLAIN ANALYZE · illustrative

Limit  (actual time=0.05..0.42 rows=50 loops=1)
  ->  Nested Loop  (actual time=0.04..0.36 rows=50 loops=1)
        ->  Index Scan Backward using posts_created_at_idx on posts p
              (actual time=0.02..0.10 rows=50 loops=1)
        ->  Index Scan using authors_pkey on authors a
              (actual time=0.004..0.004 rows=1 loops=50)
              Index Cond: (id = p.author_id)
Planning Time: 0.20 ms
Execution Time: 0.51 ms

Read it carefully: the inner Index Scan on authors_pkey still runs loops=50 — one primary-key lookup per post. The win is not that Postgres does less index work; it's that all 50 lookups happen in a single query, on one connection, on one snapshot, with zero client round trips between them. The Index Scan Backward on posts_created_at_idx also serves the ORDER BY ... LIMIT 50 without a sort. One statement, sub-millisecond, constant in the number of authors.

6 · Narrate it

“The endpoint loads 50 posts, then lazily touches post.author on each row, so the ORM fires one authors lookup per post — 1 + 50 = 51 statements, all round-trip-bound and many of them duplicates. I eager-load the author with includes(:author), which the ORM emits as a single JOIN ordered by created_at DESC LIMIT 50. The plan is a Nested Loop whose inner side is 50 primary-key index lookups — same index work, but one query on one snapshot instead of 51 network trips. Query count is now constant in the number of posts.”

05 Drills

Graded drills & traps

Four drills, increasing in difficulty. Try each before opening the solution — say the fix out loud, then check.

Drill 1 — spot the N+1

An endpoint renders a team roster:

pseudocode

members = TeamMember.where(team_id: 42)   # how many queries?
for m in members:
    render(m.user.full_name, m.user.avatar_url)

How many statements does this run for a 30-person team, and how do you make it constant?

Try it first, then read

1 + 30 = 31 queries: one for the members, then one users lookup per member (both m.user accesses hit the same already-loaded row, so it's per-member not per-access). Fix: eager-load the association — TeamMember.where(team_id: 42).includes(:user) (or select_related('user') / JOIN FETCH). Now it's a constant 1–2 queries regardless of team size. Why: the relation is loaded up front in one join/batch instead of on first touch per row.

Drill 2 — over-fetching kills the index-only scan

You need only each user's id and email for an export, and there's a covering index ON users (id, email). The ORM runs User.all and the plan shows a Seq Scan reading every column (including a big bio text). Two changes to get an Index Only Scan?

Try it first, then read

(1) Project only the columns you need so the query is satisfiable from the index: User.select(:id, :email) / .values('id','email') / a DTO query — emitting SELECT id, email FROM users instead of SELECT *. (2) Ensure the covering index exists and the table is reasonably vacuumed so the visibility map lets Postgres skip the heap. The plan flips from Seq Scan to Index Only Scan using users_id_email_idx. Why: SELECT * forces a heap visit for the unindexed columns, defeating the index-only path.

Drill 3 — the lazy load that crashes after commit

A service method loads an order, commits, and returns it. A JSON serializer then reads order.line_items and the app throws could not initialize proxy / session closed. What happened, and what are the two clean fixes?

Try it first, then read

line_items is a lazy relation that was never loaded inside the transaction; touching it during serialization — after the session/txn closed — has no session to run the SELECT, so it errors (a LazyInitializationException-class failure). Fixes: (a) eager-fetch inside the boundary — JOIN FETCH o.line_items / includes(:line_items) / select_related+prefetch_related — so the data is present before commit; or (b) return a DTO/plain value from the service with the items already materialized, giving the serializer nothing to lazy-load. Why: a lazy relation must be resolved while the session is open; decide what the response needs and load it in-transaction. Avoid papering over it with open-session-in-view.

Drill 4 — the migration that locks production

Your ORM auto-generates this migration for a 200-million-row table:

generated sql

CREATE INDEX idx_events_user ON events (user_id);
ALTER TABLE events ADD COLUMN is_archived boolean NOT NULL DEFAULT false;

Which statement is dangerous on a live table, which is safe, and how do you ship the index without downtime?

Try it first, then read

The ADD COLUMN ... NOT NULL DEFAULT false is safe: a constant (non-volatile) default is a metadata-only change in modern Postgres — instant, no rewrite. The plain CREATE INDEX is dangerous: it takes a SHARE lock that blocks all writes to events for the entire (long) build. Fix: build it concurrently — CREATE INDEX CONCURRENTLY idx_events_user ON events (user_id); — which doesn't block writes. Because CONCURRENTLY cannot run inside a transaction block, disable the migration's automatic transaction wrapper (e.g. Rails disable_ddl_transaction! + algorithm: :concurrently). Why: auto-generated DDL doesn't account for table size or live traffic — you must review it.

Traps to remember

  • N+1 is invisible in dev. Five seed rows hide it; assert on query count in tests, not just correctness.
  • Eager-loading everything is its own bug. A blanket includes can pull huge unused graphs — load what the response needs, no more.
  • includes that you then filter on may silently switch strategy. Filtering on an eager-loaded association can force a single big JOIN (and even a references requirement in ActiveRecord) — check the emitted SQL.
  • SELECT * is the default and it kills index-only scans. Project columns for hot read paths.
  • Counting/aggregating in app code. records.size after loading all rows fetches everything; use a COUNT(*) query (.count) instead.
  • Never ship an auto-generated migration unread. Check for table locks, rewrites, and non-concurrent index builds first.
  • Trusting the ORM's SQL blindly. Turn on statement logging in dev; when the SQL is wrong or slow, use the raw-SQL escape hatch without guilt.
★ Review

Summary & self-test

One idea underneath every trap: an ORM makes a query look like a field access, so the discipline it demands is to keep watching the SQL — how many statements run, when they fire, and which columns they touch. Keep the query log open, keep the transaction boundary explicit, and keep raw SQL within reach.
