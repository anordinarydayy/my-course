Keys & Relationships

A key answers one question — which row is this? A relationship answers another — how is this row connected to that one? Get those two right and the rest of a schema almost designs itself; get them wrong and every query afterward fights the data. This lesson turns the previews from Lesson 01 into decisions you can defend: surrogate versus natural primary keys, what a foreign key should do when its parent disappears, and the three shapes every relationship takes.

Original study notes. Written from scratch for engineers who want database depth that pays off in interviews and in real systems. The examples target PostgreSQL 17/18, but keys, foreign keys, and cardinality are universal relational ideas. Contains three interactive diagrams (press Play or step through with Next). This is a concept lesson — no SQL drill; it builds the mental model you'll reach for every time you sit down to design a table.
00 Foundations

Keys identify, relationships connect

Start with the vocabulary, because two words do almost all the work. A candidate key is any column — or set of columns — whose value is guaranteed unique across every row, so it can single out exactly one row. A table often has several candidates. The one you promote to be the row's official identity is the primary key: the handle the rest of the database uses to point at this row. Every other candidate you still want enforced becomes a UNIQUE constraint.

A relationship, then, is almost embarrassingly simple: it is a key value stored in another table. When an orders row carries the id of the users row it belongs to, the two tables are related — not by a wire or a pointer in memory, but by a matching value the database can check and join on. That column holding someone else's key is a foreign key. Identity lives in the primary key; connection lives in the foreign key; that is the entire subject in one sentence.

The frame for this lesson

Lesson 01 told you tables link by value. This lesson is the set of decisions that fact forces on you: (1) what to use as a primary key, (2) what a foreign key should do when the row it points at is deleted, and (3) how many rows on each side a relationship allows. Nail these three and your schema is already most of the way to correct.

A quick note on why identity matters so much. Once a value is a row's identity, other tables copy it, application caches store it, URLs embed it, log lines mention it. A primary key is therefore a promise you can never comfortably break — which is exactly why the very first decision, natural versus surrogate, deserves real thought.

01 Choosing identity

Surrogate vs natural keys ▸

A natural key is a value that already exists in the real world and happens to be unique: an email address, an ISBN, a country's two-letter iso_code, a national ID. A surrogate key is a value the database invents purely to be an identifier and nothing else — a bigint from an identity sequence, or a UUID. It carries no meaning; its only job is to be stable and unique. Watch a country table get its key chosen:

The trade-off is real and worth stating plainly. A natural key is meaningful and saves a join sometimes (you already have the ISO code, so why look up an id?). But real-world values change — people re-marry and change emails, ISBNs get reissued, a company renames a product code — and when a primary key changes, every foreign key referencing it must change too, which is a migration nightmare. Natural keys also leak information and can be wide (a full email as a key, copied into a dozen child tables, is a lot of bytes). Surrogates dodge all of that: they are stable (a row's id never changes), compact (a bigint is 8 bytes), and join-friendly (fixed-width integer comparisons).

sql

-- The pragmatic default: surrogate PK, plus the natural key kept UNIQUE.
CREATE TABLE country (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  iso_code    char(2) NOT NULL UNIQUE,   -- natural key still enforced
  name        text   NOT NULL,
  population  bigint
);

Prefer GENERATED ALWAYS AS IDENTITY over the old serial for new designs — it is the SQL-standard spelling and avoids serial's surprising ownership and permission quirks. Note one subtlety: an identity column is NOT NULL but not unique on its own; the PRIMARY KEY above is what makes it unique. If you only wrote GENERATED ALWAYS AS IDENTITY with no key constraint, you could still get duplicate ids by overriding the sequence.

When you do pick a surrogate, there are three common shapes, and the choice matters more than people expect because it decides how the values sort inside an index:

bigint IDENTITY

  • Smallest: 8 bytes, fastest to compare and index.
  • Monotonic — new rows append to the right of the B-tree.
  • But guessable / enumerable: id 41 implies a 42.
  • Needs the DB to hand it out (a round-trip on insert).

uuidv7()

  • 16 bytes, but time-ordered (a timestamp prefix).
  • Sorts roughly by creation time → index stays compact.
  • Client can generate it — no round-trip, easy sharding.
  • Native uuidv7() ships in PostgreSQL 18.

uuidv4 (random)

  • 16 bytes, fully random — unguessable.
  • But random inserts scatter across the index → page splits, fragmentation, poor cache locality.
  • Fine for low write rates; painful at high volume.
The default worth memorizing

For most tables: a bigint GENERATED ALWAYS AS IDENTITY primary key, plus a UNIQUE constraint on the real-world natural key if one exists. Reach for uuidv7() when you need ids that clients can generate offline or that you don't want to expose as sequential counts. Avoid random uuidv4 as a primary key on a high-write table — its index fragmentation is a classic, avoidable performance tax.

02 Enforced links

Foreign keys & referential actions ▸

A foreign key (FK) is a constraint that says: this value must exist over there. Declare book.author_id REFERENCES author(id) and Postgres will refuse any book whose author_id points at no real author. That guarantee — referential integrity — is checked on three events: when you INSERT or UPDATE a child row (the referenced parent must exist), and when you DELETE or UPDATE a parent row that children still point at. It's that last case — deleting a parent — where you have a decision to make.

The ON DELETE clause tells Postgres what to do when someone tries to delete a parent that still has children. Step through the four rows and three policies:

Each policy is a different answer to "what happens to the children?"

  • RESTRICT and NO ACTION both block the delete while children exist — the safe default. The difference is timing: NO ACTION checks at the end of the statement (so it can be DEFERRABLE), while RESTRICT checks immediately and cannot be deferred.
  • CASCADE deletes the children too. Powerful and correct for true ownership (delete an order → delete its line items), but dangerous if you're wrong about ownership — one delete can silently sweep away thousands of rows.
  • SET NULL keeps the children but nulls their FK, orphaning them safely (the column must be nullable). Good when a child can meaningfully exist without a parent — a comment whose author was deleted becomes an anonymous comment.
  • SET DEFAULT is the rarer cousin: point orphans at a default row (e.g. a "deleted user" placeholder that must itself exist).

sql

CREATE TABLE book (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title      text NOT NULL,
  author_id  bigint NOT NULL
               REFERENCES author (id) ON DELETE RESTRICT
);
-- swap RESTRICT for CASCADE (delete the books too)
-- or SET NULL (keep books, null the link — then author_id must be nullable)
Pick the policy from the meaning, not the convenience

The right action follows from one question: can this child exist without this parent? If no and the parent owns the child → CASCADE. If no but the child is independent data → RESTRICT (force the human to deal with it). If yes → SET NULL. Reaching for CASCADE just to avoid a "violates foreign key constraint" error is how people accidentally delete production data — treat it with respect.

03 Shapes of a relationship

Cardinality: 1:M, M:N, 1:1 ▸

Cardinality is just "how many rows on each side." There are only three shapes, and each has a standard way to model it in tables. Knowing which one you're looking at tells you exactly where the foreign key goes — or whether you need an extra table. Build the classic students-and-courses example up from a simple link to a full many-to-many:

One-to-many (1:M) is the everyday case: one author, many books; one user, many orders. The rule is a reflex worth burning in — the foreign key lives on the "many" side. A book points at its one author; you never store a list of book ids on the author.

Many-to-many (M:N) can't be expressed with a single FK, because both sides are "many." A student takes many courses and a course has many students — there's no column on either table that could hold the link. The fix is a third table, a junction (or join / associative) table, that holds one row per pairing, with two foreign keys:

sql

CREATE TABLE enrollment (
  student_id  bigint NOT NULL REFERENCES student (id),
  course_id   bigint NOT NULL REFERENCES course (id),
  enrolled_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (student_id, course_id)   -- composite PK: one row per pair
);

That composite PRIMARY KEY (student_id, course_id) does two jobs at once: it makes the pairing unique (a student can't enroll in the same course twice) and it identifies each junction row. A junction table is also the natural home for facts about the relationship itself — here, enrolled_at, or a grade, or a role. That's a good reason to name it after the relationship (enrollment) rather than mashing the table names together.

One-to-one (1:1) is the rare shape: one row here maps to at most one row there. You model it by having the child's primary key be the foreign key — a shared PK — or by putting a UNIQUE constraint on an ordinary FK:

sql

CREATE TABLE profile (
  user_id  bigint PRIMARY KEY REFERENCES app_user (id),
  bio      text
);   -- PK is also the FK → exactly one profile per user, at most
Read cardinality off the sentence

Say the relationship out loud in both directions. "A book has one author; an author has many books" → 1:M, FK on book. "A student has many courses; a course has many students" → M:N, junction table. "A user has one profile; a profile belongs to one user" → 1:1, shared PK. If either direction says "many," and both do, you need a junction.

04 Sharp edges

The gotchas that bite in production

The mechanics above are clean; the reality has a few sharp edges. Four are worth knowing before you design anything real.

Composite (multi-column) keys — use sparingly

A key can span several columns, and in a junction table like enrollment the composite PK is exactly right. Elsewhere, be cautious. When a table's primary key is composite, every child that references it must carry all of those columns as its foreign key — the width propagates, joins get wordier, and one more column added to the key later is a painful migration. A surrogate bigint on an entity table sidesteps all of that. Rule of thumb: composite keys are great for pure link tables and natural for a few genuinely composite identities, but for ordinary entities a single surrogate key ages better.

Self-referential foreign keys — a table pointing at itself

A foreign key can reference the very table it lives in. The canonical case is a tree: an employee has a manager who is also an employee.

sql

CREATE TABLE employee (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name        text NOT NULL,
  manager_id  bigint REFERENCES employee (id)   -- NULL = top of the tree
);

The same shape models categories with sub-categories, threaded comments (a comment's parent_id), and any hierarchy. A nullable self-FK gives you the root for free: the CEO's manager_id is NULL. (Walking such a tree in one query is what recursive CTEs are for — a Phase 3 topic.)

DEFERRABLE constraints — check at commit, not at statement

Normally a foreign key is checked the instant a statement runs. Sometimes that's too strict — inserting two rows that reference each other, or reordering ids in a batch, momentarily violates the constraint even though the final state is valid. Declaring a constraint DEFERRABLE INITIALLY DEFERRED tells Postgres to postpone the check until COMMIT, so the data may be inconsistent mid-transaction but must be consistent by the end. Use it deliberately; it's a scalpel, not a default.

The big one: Postgres does NOT index foreign-key columns for you

This is the single most common keys-and-relationships mistake, and it surprises nearly everyone. Declaring a foreign key creates the constraint, but Postgres does not create an index on the referencing column. (It indexes the referenced side automatically, because that side is a primary key or unique — but not the child's FK column.) Two things then get slow:

  • Joins and lookups the "child" way — "all books by author 1" scans the whole book table without an index on book.author_id.
  • Parent deletes and updates — to enforce the FK, Postgres must find child rows that reference the parent. With no index on the child's FK column, that check is a sequential scan on the child table for every parent row you touch.

sql

-- Always add this yourself after declaring the FK:
CREATE INDEX ON book (author_id);
Make it a habit, not a debugging session

Every time you write REFERENCES, ask "is the referencing column already the left-most column of an index?" If not, add one. The only common exception is a junction table whose composite PK already starts with that column — PRIMARY KEY (student_id, course_id) gives you an index usable for student_id lookups for free, but not for course_id, which still needs its own index. We'll measure exactly why in Phase 4.

05 Reason about it

Model a small social schema

Let's put every decision together on a domain small enough to hold in your head: users write posts, posts carry tags, and users like posts. Walk the reasoning the way you would at a whiteboard, out loud.

Entities and their keys. Three real entities — user, post, tag — each gets a surrogate bigint primary key, because ids get copied everywhere and must never change. Each also keeps its natural key as a UNIQUE constraint where one exists: a user's handle, a tag's name. Nothing exotic yet.

The relationships, one at a time. A user writes many posts and a post has one author → that's 1:M, so the FK author_id lives on post. Posts and tags are many-to-many (a post has many tags, a tag labels many posts) → a junction, post_tag. Likes are also many-to-many between users and posts (a user likes many posts, a post is liked by many users) → another junction, post_like, which is a fine place to also record liked_at.

sql

CREATE TABLE app_user (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  handle  text NOT NULL UNIQUE
);
CREATE TABLE post (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  author_id  bigint NOT NULL REFERENCES app_user (id) ON DELETE CASCADE,
  body       text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE tag (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL UNIQUE
);
CREATE TABLE post_tag (            -- M:N: posts ↔ tags
  post_id  bigint NOT NULL REFERENCES post (id) ON DELETE CASCADE,
  tag_id   bigint NOT NULL REFERENCES tag (id)  ON DELETE CASCADE,
  PRIMARY KEY (post_id, tag_id)
);
CREATE TABLE post_like (           -- M:N: users ↔ posts
  user_id  bigint NOT NULL REFERENCES app_user (id) ON DELETE CASCADE,
  post_id  bigint NOT NULL REFERENCES post (id)     ON DELETE CASCADE,
  liked_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, post_id)    -- a user can like a post once
);

Referential actions, chosen from meaning. Delete a user and their posts should go too (ON DELETE CASCADE on post.author_id) — a post can't exist without its author here. Delete a post and its tag-links and likes must go with it (CASCADE on both junctions) — those rows are meaningless without the post. Deleting a tag cascades to remove its post_tag links but leaves the posts themselves untouched. Notice how the policy falls out of the sentence "can the child exist without the parent?"

Now the indexes — the step most people forget. Every junction's composite PK indexes its first column only, and Postgres indexes none of the FK columns automatically. So walk each FK column and ask "is it the left-most column of an existing index?":

sql

-- post.author_id: 1:M FK, no index yet → "posts by this user" would scan
CREATE INDEX ON post (author_id);
-- post_tag: PK(post_id, tag_id) covers post_id; tag_id is uncovered
CREATE INDEX ON post_tag (tag_id);      -- "posts with tag X"
-- post_like: PK(user_id, post_id) covers user_id; post_id is uncovered
CREATE INDEX ON post_like (post_id);     -- "who liked this post" + fast post deletes

Narrate it. Three entities, each with a stable surrogate key and its natural key kept unique. Two junctions turn the two many-to-many relationships into pairs of one-to-many links, each with a composite PK that both identifies the row and forbids duplicates. Cascades chosen so that deleting a parent cleans up exactly the rows that can't live without it. And three hand-added indexes on the FK columns the primary keys didn't already cover — which is the difference between a "find posts with this tag" query that uses an index and one that scans the whole junction table. That last sentence is the whole lesson in miniature.

Where this shows up next

You may have wondered why the data splits into these particular tables rather than one big posts table with tag and like columns — that's normalization, Lesson 06, next. Getting data back out of these joined tables — the joins and aggregates over post, post_tag, and post_like — is Phase 2 (SQL). ★ Review

Summary & self-test

The whole lesson compresses to one idea: a primary key gives a row a stable identity, a foreign key connects one row to another by copying that identity, and every relationship is just how many rows sit on each side of such a link — so choose surrogate keys for stability, choose the delete action from meaning, and always index the referencing column.

01Candidate → primaryAny uniquely-identifying column is a candidate key; the one you promote is the primary key. Keep other candidates as UNIQUE.
02Surrogate by defaultPrefer a bigint GENERATED ALWAYS AS IDENTITY PK: stable, compact, join-friendly. Keep the natural key as a UNIQUE constraint.
03uuidv7 over uuidv4Need a UUID? Time-ordered uuidv7() (PG 18) keeps the index compact; random uuidv4 fragments it.
04FK = "must exist there"A foreign key enforces referential integrity on insert, update, and parent delete. It's a checked link, not a pointer.
05Delete action = meaningCan the child live without the parent? No + owned → CASCADE. No + independent → RESTRICT. Yes → SET NULL.
06Three cardinalities1:M → FK on the many side. M:N → junction table with two FKs + composite PK. 1:1 → shared PK or UNIQUE FK.
07Index your FK columnsPostgres does NOT auto-index the referencing column. Unindexed FKs make joins and parent deletes scan. Add the index yourself.
08Self-FK builds treesA column referencing its own table (manager_id, parent_id) models hierarchies; a NULL marks the root.
