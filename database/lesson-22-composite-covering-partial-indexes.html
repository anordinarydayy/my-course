Composite, Covering & Partial Indexes

A pile of single-column indexes is rarely the right answer. The craft of indexing is shaping one index to a query — choosing the column order so the index serves both the filter and the sort, appending payload columns with INCLUDE so the whole query is answered from the index, and restricting it with a partial or expression predicate so it stays small and matches exactly the rows a query wants. This lesson builds the exact index a real dashboard query needs, one decision at a time.

Original study notes. Written from scratch, grounded in PostgreSQL 17/18 behaviour (index-only scans, partial and expression indexes, INCLUDE, and PG18's default BUFFERS in EXPLAIN ANALYZE). 00 Orientation

Design the index to the query

By now you can create a B-tree and read an EXPLAIN plan. The instinct most people carry from that is wrong in a subtle way: they see a slow WHERE and add an index on that one column, then see a slow ORDER BY and add an index on that one column, and end up with a drawer full of single-column indexes that each help a little and collectively cost a lot. A good index is not aimed at a column — it is aimed at a query, and it tries to satisfy the query's filter, its sort, and its output all at once.

Three levers turn a generic index into a purpose-built one, and this lesson takes them in order:

  • Column order in a composite index decides which queries it can serve at all — the leftmost-prefix rule. Get the order right and one index covers a family of queries; get it wrong and it sits unused.
  • Covering the query with INCLUDE appends the columns a query reads (not just filters on) into the index, so Postgres can answer straight from the index — an Index Only Scan — without ever touching the table.
  • Predicates shrink the index to the rows that matter: a partial index (WHERE status='open') indexes only the hot subset, and an expression index (lower(email)) indexes a computed value so a function in your WHERE can still use it.

Put together, these let you replace three mediocre indexes with one sharp one that makes the target query's plan collapse to Limit → Index Only Scan reading a handful of pages. That is the whole game, and the worked problem in §04 walks it end to end.

The reframe

Stop asking "which column is slow?" and start asking "what is the exact shape of the query I need to serve — its filter, its order, and its output — and what single index satisfies all three?" An index is a data structure you design for a workload, not a checkbox you tick per column.

01 Column order

Composite column order — the leftmost prefix ▸

A composite index on (customer_id, created_at) is one B-tree whose entries are sorted by customer_id first and, only within a given customer_id, by created_at. Think of a phone book sorted by last name, then first name: you can find everyone named "Ng", and within them everyone named "Ng, Ana" — but you cannot efficiently find everyone whose first name is "Ana" regardless of last name, because those entries are scattered all through the book.

That is the leftmost-prefix rule: an index on (a, b) can serve any query that uses a left-to-right prefix of its columns — WHERE a, WHERE a AND b, and ORDER BY a, b — but not WHERE b alone. Step through which queries the index can and cannot serve:

The practical consequence is a design rule you can apply almost mechanically: put equality columns first, then the single range or sort column last. A query that filters customer_id = 42 (equality) and orders by created_at (sort) wants the index (customer_id, created_at) — the equality pins one contiguous slice, and within it the rows are already in created_at order, so the sort is free. Flip the order to (created_at, customer_id) and neither the filter nor the sort lands cleanly.

PG18 skip scan — a caveat, not an escape

PostgreSQL 18 added B-tree skip scan, which can sometimes use (a, b) for a query on b alone by internally "skipping" through each distinct value of a. It only pays off when a has few distinct values (so there are few skips). Treat it as a bonus for a leading column of low cardinality, never as a reason to stop caring about column order — for a high-cardinality leading column, WHERE b alone is still effectively a Seq Scan.

02 Covering

Covering indexes & index-only scans ▸

A plain index scan does its work in two hops: walk the B-tree to find the matching leaf entries, then follow each leaf's TID pointer into the heap to fetch the actual row (random I/O). The second hop exists because the leaf holds only the key columns plus a pointer — not the rest of the row. A covering index removes that second hop for a specific query by carrying every column the query touches inside the index itself.

The tool is INCLUDE: CREATE INDEX … ON t (a, b) INCLUDE (c, d) keeps a, b as ordered key columns and staples c, d onto each leaf as unordered payload. If every column a query reads and filters is present in the index — and the heap page is marked all-visible in the visibility map (kept current by VACUUM, from L19) — Postgres skips the heap entirely: an Index Only Scan with Heap Fetches: 0. Two things make or break this. First, SELECT * defeats it: the moment the query reads one column the index doesn't carry, Postgres must visit the heap for every row, and you are back to an ordinary Index Scan. Select only the columns you actually render. Second, key vs payload matters: put columns you filter or sort on in the key list (where their order obeys the leftmost-prefix rule), and columns you only return in INCLUDE — payload columns are smaller-footprint and don't bloat the key, and they can't be used for searching or ordering anyway.

Covering is a trade, not a free win

Every INCLUDE column makes the index bigger and every write must maintain it. Add payload to cover a hot, specific query, not speculatively. And remember the visibility-map dependency: on a table with heavy churn that VACUUM can't keep all-visible, an "index only" scan degrades to real Heap Fetches — check the number in EXPLAIN ANALYZE rather than assuming.

03 Predicates & expressions

Partial & expression indexes ▸

The last two levers shrink and sharpen an index by putting logic into the index definition. A partial index carries a WHERE clause: CREATE INDEX … WHERE status='open' indexes only the rows that satisfy the predicate. This is the perfect tool for a low-cardinality column with a hot minority value — an orders table where 98% of rows are closed and you only ever query the open ones. A full index on status would be large and barely selective; the partial index is a fraction of the size, sidesteps the low-cardinality column entirely, and its pages stay cache-hot.

An expression index indexes the result of a function: CREATE INDEX ON t (lower(email)). This exists because a function wrapped around an indexed column defeats a plain index — WHERE lower(email) = 'a@x.com' can't use an index on raw email, because the index stores Ana@X.com, not ana@x.com. Index the expression and the planner can match it. Step through both:

Partial indexes have a second, quieter superpower: the partial UNIQUE. CREATE UNIQUE INDEX … (email) WHERE deleted_at IS NULL enforces uniqueness only among live rows, so a soft-deleted account can free up its email for reuse while active accounts stay unique — a constraint a plain UNIQUE(email) can't express. And for both partial and expression indexes there is one rule the planner is strict about: the query has to mention the same shape. A partial index WHERE status='open' is only usable when the planner can prove your query's rows fall inside status='open'; an expression index on lower(email) is only usable when your predicate is literally lower(email) = ….

The predicate must be provably implied

A partial index on WHERE status = 'open' serves WHERE status = 'open' but not WHERE status = $1 — at plan time the planner can't prove the parameter equals 'open', so it won't use the index. Constants and simple IS NULL predicates are safe; opaque parameters and volatile functions are not. When a partial index "isn't being used," a mismatch between its predicate and the query's WHERE is the usual culprit.

04 Worked problem

Worked: one index for a dashboard query

Time to put all three levers on a single, realistic query and watch the plan improve at each step. This is the pattern to internalise: start from the query, read the plan, and let each weakness in the plan tell you the next design move.

1 · The schema and the task

sql

CREATE TABLE orders (
    id          bigint        PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    customer_id bigint        NOT NULL,
    status      text          NOT NULL,   -- 'open' | 'shipped' | 'closed'
    created_at  timestamptz   NOT NULL DEFAULT now(),
    total       numeric(10,2) NOT NULL
);

The customer's order dashboard runs one query constantly — the 20 most recent open orders for a customer, newest first:

sql

SELECT id, created_at, total
FROM orders
WHERE customer_id = 42 AND status = 'open'
ORDER BY created_at DESC
LIMIT 20;

The table has millions of rows; customer 42 has thousands of orders, most of them long since closed. We will build the index up in three moves.

2 · Attempt one — a plain (customer_id) index

sql

CREATE INDEX orders_cust_idx ON orders (customer_id);

EXPLAIN ANALYZE · illustrative

Limit  (cost=1240.66..1240.71 rows=20 width=20) (actual time=3.1..3.1 rows=20 loops=1)
  ->  Sort  (cost=1240.66..1243.10 rows=974 width=20) (actual time=3.0..3.1 rows=20 loops=1)
        Sort Key: created_at DESC
        ->  Bitmap Heap Scan on orders  (cost=25.64..1214.80 rows=974 width=20) (actual time=0.4..2.6 rows=974 loops=1)
              Recheck Cond: (customer_id = 42)
              Filter: (status = 'open'::text)
              Rows Removed by Filter: 3106
              ->  Bitmap Index Scan on orders_cust_idx  (cost=0.00..25.40 rows=4080 width=0)
                    Index Cond: (customer_id = 42)

Read it bottom-up. The index finds all 4080 of customer 42's rows; the Bitmap Heap Scan fetches every one of them and the Filter throws away 3106 non-open rows; then a Sort orders the surviving 974 by created_at DESC so LIMIT can take 20. We read thousands of heap rows and sorted hundreds to return twenty. The index only helped with the customer half of the filter — the status filter and the sort are pure overhead.

3 · Attempt two — a composite (customer_id, created_at DESC)

sql

DROP INDEX orders_cust_idx;
CREATE INDEX orders_cust_created_idx
    ON orders (customer_id, created_at DESC);

EXPLAIN ANALYZE · illustrative

Limit  (cost=0.43..34.19 rows=20 width=20) (actual time=0.03..0.16 rows=20 loops=1)
  ->  Index Scan using orders_cust_created_idx on orders  (cost=0.43..1643.20 rows=974 width=20) (actual time=0.03..0.15 rows=20 loops=1)
        Index Cond: (customer_id = 42)
        Filter: (status = 'open'::text)
        Rows Removed by Filter: 71

The Sort node is gone. Because the index is already ordered by created_at DESC within a customer, the Index Scan yields rows in exactly the requested order, so LIMIT can stop after gathering 20 open ones — note the total cost now starts at 0.43 and the Limit's estimate collapsed from 1240 to 34. Equality-then-sort column order did that. What remains: the index has no idea about status, so it still fetches heap rows and discards a few non-open ones (Rows Removed by Filter: 71), and it still touches the heap for every candidate row.

4 · Attempt three — partial + covering

Two weaknesses are left: the wasted heap fetches for non-open rows, and the heap fetches for the columns we return. A partial predicate removes the first; INCLUDE removes the second:

sql

DROP INDEX orders_cust_created_idx;
CREATE INDEX orders_open_dash_idx
    ON orders (customer_id, created_at DESC)
    INCLUDE (id, total)
    WHERE status = 'open';

EXPLAIN (ANALYZE, BUFFERS) · illustrative · PG18

Limit  (cost=0.29..4.83 rows=20 width=20) (actual time=0.020..0.047 rows=20 loops=1)
  Buffers: shared hit=5
  ->  Index Only Scan using orders_open_dash_idx on orders  (cost=0.29..14.31 rows=974 width=20) (actual time=0.017..0.039 rows=20 loops=1)
        Index Cond: (customer_id = 42)
        Heap Fetches: 0
        Buffers: shared hit=5
Planning Time: 0.11 ms
Execution Time: 0.07 ms

Everything collapses. The partial predicate WHERE status='open' means the index only contains open rows, so the planner drops the status Filter entirely (no Rows Removed). The DESC keys keep the sort free. And because INCLUDE (id, total) carries the two columns we return — on top of the key columns customer_id, created_at — every column the query touches is in the index: Index Only Scan, Heap Fetches: 0, five buffer pages read to answer the whole thing. Note we did not select *; a single extra column would have forced heap fetches and broken the index-only scan.

5 · Narrate the design

Three decisions, each answering a specific line in the plan:

  • Equality first, sort last — (customer_id, created_at DESC): the equality column pins one contiguous slice, and the trailing column, matching the ORDER BY … DESC, kills the Sort.
  • Partial on the hot status — WHERE status='open': the index holds only the rows the dashboard ever wants, so it is tiny and the status filter vanishes. (The predicate is a constant, so the planner can prove the query's rows fall inside it.)
  • INCLUDE to cover — INCLUDE (id, total): the returned columns ride along in the leaf so no heap visit is needed, turning it into an Index Only Scan.

Two operational notes close the loop. First, drop the indexes you replaced and any that go unused — every index taxes each INSERT/UPDATE/DELETE. Find dead weight with pg_stat_user_indexes:

sql

SELECT indexrelid::regclass AS index, idx_scan
FROM   pg_stat_user_indexes
WHERE  idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

Second, on a live table build the new index with CREATE INDEX CONCURRENTLY so it doesn't lock out writes while it builds (it is slower and can't run inside a transaction block — the operational details are Phase 9, L52).

The design loop

Query → EXPLAIN → find the plan's biggest waste (a Sort, a big Rows Removed by Filter, heap fetches) → make the one index change that removes it → re-EXPLAIN. You did it three times here, and each move erased exactly one line of waste. That loop — not memorised rules — is what index design actually is.

05 Practice

Graded drills & traps

Four drills, increasing in difficulty. Try each one on paper — write the index (and, where asked, the query) — before opening the solution.

Drill 1 — the trailing column alone

You have an index on orders (customer_id, created_at). A reporting query filters only on the second column and is slow:

sql

SELECT * FROM orders WHERE created_at >= '2026-07-01';

Why won't the existing index help, and what do you do?

Try it first, then read

Leftmost-prefix: created_at is the trailing column, scattered all through the index, so there is no contiguous range to scan — the index can't serve created_at alone. Add a dedicated index:

sql

CREATE INDEX orders_created_idx ON orders (created_at);

Why: the range predicate now has a leading indexed column. (PG18 skip scan might use the composite if customer_id had very few distinct values — here it doesn't, so don't rely on it.)

Drill 2 — make it index-only

This lookup is on the hot path and you want zero heap fetches:

sql

SELECT id, email FROM users WHERE tenant_id = 7;

Design one index that yields an Index Only Scan.

Try it first, then read

Put the filter column in the key and the returned columns in INCLUDE:

sql

CREATE INDEX users_tenant_idx ON users (tenant_id) INCLUDE (id, email);

Why: every column the query touches (tenant_id to filter, id and email to return) now lives in the index, so on all-visible pages it's an Index Only Scan. Do not switch to SELECT * — one uncovered column reintroduces the heap fetch.

Drill 3 — soft deletes, and the partial UNIQUE

Rows are soft-deleted with a deleted_at timestamp (NULL = live). Almost every query wants only live rows, and business rules say email must be unique among live users — a deleted user's email may be reused. Write both indexes.

Try it first, then read

sql

-- keep the working index small: only live rows
CREATE INDEX users_live_tenant_idx
    ON users (tenant_id) WHERE deleted_at IS NULL;

-- uniqueness enforced only among live rows
CREATE UNIQUE INDEX users_email_live_uq
    ON users (lower(email)) WHERE deleted_at IS NULL;

Why: a plain UNIQUE(email) would forbid a deleted user's email from ever being reused. The partial UNIQUE applies the constraint only where deleted_at IS NULL. Bonus: it's also an expression index on lower(email), so it enforces case-insensitive uniqueness too.

Drill 4 — a function in the WHERE

Case-insensitive login does a full-table scan despite an index on email:

sql

SELECT id FROM users WHERE lower(email) = lower('Ana@Shop.com');

Explain the Seq Scan and fix it.

Try it first, then read

The index stores raw email values (Ana@Shop.com); the predicate asks for lower(email) (ana@shop.com). Postgres can't match a function's output to a plain-column index, so it scans. Index the expression instead:

sql

CREATE INDEX users_lower_email_idx ON users (lower(email));

Why: now the index stores the computed lower(email), and the predicate is literally that expression, so the planner matches it. The query must use the same expression — WHERE email = … would not use this index.

Traps to avoid

1. Wrong composite order. (a, b) does not serve WHERE b alone — leftmost-prefix. Equality columns first, the range/sort column last.
2. Too many overlapping indexes. Each one slows every write and can confuse the planner into a worse choice. Prefer one well-shaped composite over three singles, and drop the ones with idx_scan = 0.
3. SELECT * defeats INCLUDE. An Index Only Scan needs every selected column in the index; one stray column brings the heap fetch back. Select only what you render.
4. Partial predicate mismatch. A partial index's WHERE must be provably implied by the query's WHERE. WHERE status='open' won't serve WHERE status = $1.

★ Review

Summary & self-test

One idea ties the lesson together: an index is a data structure you design for a specific query — its column order serves the filter and the sort, INCLUDE covers the output, and a partial or expression predicate makes it small and exact — and you prove you got it right by reading the plan.

02Leftmost prefixAn index on (a, b) serves a, a AND b, and ORDER BY a, b — never b alone.
