Upserts & RETURNING

An upsert — insert this row, or update it if it already exists — is one of the most common writes an application makes, and one of the easiest to get wrong under concurrency. Postgres gives you two atomic answers: INSERT … ON CONFLICT for the everyday insert-or-update, and MERGE for the complex, multi-branch cases. This practice lesson wires both to RETURNING, so a single statement changes the data and hands the affected rows back — no second round-trip, and no race.

00 The problem

Insert-or-update, atomically

Many of the writes an application makes are idempotent by intent: “make sure this user exists,” “record that we’ve seen this event,” “bump this counter.” Each is a write that may or may not already be there — insert it if it’s new, update it if it isn’t. The single name for that combined operation is an upsert.

The obvious way to write it is also the classic bug. You check, then act:

sql · naive, do not ship

-- application flow, two separate round-trips:
SELECT id FROM users WHERE email = 'ana@x.io';   -- does it exist?
-- if a row came back:
UPDATE users SET name = 'Ana' WHERE email = 'ana@x.io';
-- else:
INSERT INTO users (email, name) VALUES ('ana@x.io', 'Ana');

Between the SELECT and the write there is a gap, and in that gap another session can act. This check-then-act pattern (a time-of-check to time-of-use, or TOCTOU, race) breaks two different ways under concurrency:

  • Race A — duplicate insert. Two sessions run the SELECT at the same instant, both see “not found,” and both INSERT. If email has a UNIQUE constraint (recall Lesson 04), one insert wins and the other errors with a duplicate-key violation. If it doesn’t, you now have two rows for one email — silent corruption you may not notice for weeks.
  • Race B — lost update. Two counter bumps both read the current value, both compute value + 1, and both write it back. One increment is silently lost — the exact lost update from Lesson 00, now living inside your upsert.

The fix is not “add a lock and hope.” It is to hand the whole decision to the database as one atomic statement anchored on a real unique constraint. Postgres has two of them:

INSERT … ON CONFLICT

  • Purpose-built for insert-or-update on one unique key.
  • Atomic and concurrency-safe — the unique index serializes racers.
  • Your default upsert.

MERGE

  • General multi-branch logic: match / not-matched / delete.
  • Can join a source table.
  • NOT race-safe for a plain upsert — more on that in §03.
The mental reframe

An upsert is not “a SELECT followed by an INSERT or an UPDATE.” That framing is the bug — it leaves a gap. An upsert is a single write that resolves the conflict itself, using a unique index the database already maintains. Everything in this lesson is about expressing that as one statement.

01 The core tool

INSERT … ON CONFLICT ▸

The syntax reads like a plan: try to insert, and if the insert would collide with a named unique index, do something else instead.

sql

INSERT INTO users (email, name)
VALUES ('ana@x.io', 'Ana')
ON CONFLICT (email)                 -- the conflict target = the arbiter index
DO UPDATE SET name = EXCLUDED.name;   -- EXCLUDED = the row that failed to insert

Three pieces carry the whole feature:

  • The conflict target — (email) here — must name a unique constraint or unique index (the docs call it the arbiter). You can give the column list, a partial-index predicate, or ON CONFLICT ON CONSTRAINT users_email_key. It is not an arbitrary WHERE filter; there has to be a real unique index behind it.
  • The action — DO NOTHING (skip the conflicting row silently) or DO UPDATE SET … (merge it in).
  • EXCLUDED — inside DO UPDATE, a virtual row holding the values you tried to insert. You reference the existing, stored row by the table name/alias (users.name) and the incoming row as EXCLUDED.name. Mixing those two up is the single most common upsert bug.

DO UPDATE even takes its own WHERE to make the update conditional — skip a write that would change nothing:

sql

INSERT INTO users (email, name)
VALUES ('ana@x.io', 'Ana')
ON CONFLICT (email) DO UPDATE
  SET name = EXCLUDED.name
  WHERE users.name IS DISTINCT FROM EXCLUDED.name;   -- no-op writes avoided

Step through what actually happens at the arbiter index when a row arrives — the fork between insert, DO NOTHING, and DO UPDATE:

Notice the two failure-shaped outcomes are expected, not errors: a conflict never raises — it routes. And every branch runs inside one statement holding the right index locks, so two sessions racing on the same key can’t both slip through. That is what makes ON CONFLICT the correct answer to §00’s races.

DO NOTHING returns nothing

Keep this in your pocket for §02 and the drills: on a conflict, DO NOTHING changes no row and therefore returns no row — a RETURNING clause yields an empty result for the conflicting insert. If you need the existing row’s data back, DO NOTHING won’t give it to you.

02 One round-trip

RETURNING the rows back

A write normally tells you only how many rows it touched. RETURNING makes it tell you which rows — with any expression over them — in the same statement. It works on INSERT, UPDATE, DELETE, and (since PG 17) MERGE. The classic use is grabbing a generated key without a follow-up SELECT:

sql

INSERT INTO orders (user_id, total)
VALUES (42, 99.50)
RETURNING id, created_at;   -- serial/identity id + DEFAULT now(), in one trip

Because it’s just a projection, RETURNING can compute. The most useful upsert idiom asks the returned row a question: was this an insert or an update? The trick uses a hidden system column, xmax:

sql

INSERT INTO users (email, name)
VALUES ('ana@x.io', 'Ana')
ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name
RETURNING id, (xmax = 0) AS was_insert;

Every row version carries xmax, the id of the transaction that deleted or updated it. A brand-new tuple has xmax = 0. After ON CONFLICT, the row you get back is either the one you just inserted (xmax = 0 → was_insert = true) or the one you just updated (the update locked/superseded a version, so xmax ≠ 0 → false). One statement, and you know which path fired.

You can also feed the returned rows straight into more SQL with a data-modifying CTE — the whole thing is still one round-trip and one transaction:

sql

WITH ins AS (
  INSERT INTO users (email) VALUES ('ana@x.io')
  ON CONFLICT (email) DO NOTHING
  RETURNING id
)
INSERT INTO audit (user_id, action)
SELECT id, 'created' FROM ins;   -- only logs on a real insert (ins is empty on conflict)
PG 18: OLD and NEW in RETURNING

Postgres 18 lets RETURNING reference both OLD.* and NEW.*, so an upsert can report exactly what it changed — before and after — in one shot:

sql · pg 18

INSERT INTO inventory (sku, qty) VALUES ('A1', 5)
ON CONFLICT (sku) DO UPDATE SET qty = inventory.qty + EXCLUDED.qty
RETURNING sku, OLD.qty AS before, NEW.qty AS after;   -- OLD is NULL on a fresh insert
03 Choosing the tool

ON CONFLICT vs MERGE ▸

PostgreSQL 15 added MERGE, the SQL-standard statement for “look at a source, and for each row decide what to do to a target.” It is strictly more expressive than ON CONFLICT — and, for the plain upsert, strictly more dangerous. Know when to reach for each.

MERGE joins a source to a target on any condition, then runs the first matching WHEN branch per row:

sql

MERGE INTO inventory AS t
USING shipment AS s ON t.sku = s.sku
WHEN MATCHED AND s.qty = 0 THEN DELETE
WHEN MATCHED THEN UPDATE SET qty = t.qty + s.qty
WHEN NOT MATCHED THEN INSERT (sku, qty) VALUES (s.sku, s.qty);

That is three outcomes — delete, update, insert — over a join, which ON CONFLICT simply cannot express (it has no source table and no delete branch). MERGE also supports WHEN NOT MATCHED BY SOURCE (rows in the target with no source match) for full two-way syncs. But now the trade-off you must remember:

INSERT … ON CONFLICT

  • One target, one unique arbiter index.
  • Two outcomes: nothing / update.
  • Atomic & concurrency-safe — guaranteed insert-or-update under a race.
  • EXCLUDED for the rejected row.
  • The everyday upsert.

MERGE (PG 15+)

  • Arbitrary join condition, a source table.
  • Many WHEN branches, incl. DELETE and BY SOURCE/TARGET.
  • NOT concurrency-safe for the plain upsert — a race can raise a unique violation.
  • RETURNING since PG 17; OLD/NEW since PG 18.
  • Batch sync & complex conditional logic.

Walk the decision, including the caution that trips people up:

Why MERGE races and ON CONFLICT doesn’t

MERGE evaluates its join once. Two concurrent MERGEs for a brand-new key can both find no match, both take the WHEN NOT MATCHED THEN INSERT branch, and the second insert then violates the unique index — a runtime error you must catch and retry. ON CONFLICT has no such gap: the conflict is resolved at the index, so a loser is routed to DO UPDATE instead of erroring. Rule of thumb: simple insert-or-update on a unique key → ON CONFLICT; multi-branch / join a source / delete-on-match → MERGE (in a batch, or with retry).

04 Worked problem

Worked: idempotent event ingest ▸

A queue can deliver the same message more than once (“at-least-once” semantics). Your consumer must process each event exactly once even when duplicates or two workers arrive together. This is the classic inbox pattern, and it is a pure upsert. Here is the table:

sql · schema

CREATE TABLE inbox (
  event_id   uuid PRIMARY KEY,                      -- the natural idempotency key
  payload    jsonb,
  seen_count int         NOT NULL DEFAULT 1,       -- how many times we've received it
  first_seen timestamptz NOT NULL DEFAULT now()
);

Task. Ingest an event exactly once; on a repeat, bump seen_count instead of re-processing; and return whether this call was the one that newly inserted it.

The naive attempt, and why it’s wrong

The tempting version is a check-then-act again:

sql · racy

SELECT 1 FROM inbox WHERE event_id = $1;   -- seen before?
-- if found: UPDATE inbox SET seen_count = seen_count + 1 WHERE event_id = $1;
-- else:     INSERT INTO inbox (event_id, payload) VALUES ($1, $2);

Two workers get the same event_id, both SELECT “not found,” both INSERT. The PRIMARY KEY saves you from a duplicate row — but one worker now crashes with a unique-violation error instead of quietly recording a repeat, and you’ve paid for two round-trips. The check and the act must be one atomic statement.

The correct query

sql

INSERT INTO inbox (event_id, payload)
VALUES ($1, $2)
ON CONFLICT (event_id)
DO UPDATE SET seen_count = inbox.seen_count + 1
RETURNING (xmax = 0) AS was_insert;

One statement does everything: insert on first sight, bump the counter on every repeat, and hand back was_insert so the app knows whether to run the (once-only) side effects. Note inbox.seen_count reads the stored value — using EXCLUDED.seen_count here would wrongly re-apply the default of 1 every time.

The plan that runs it

The PRIMARY KEY already gives us the unique index we need — inbox_pkey is the arbiter, so no extra index is required. On a repeat event the plan looks like this:

explain · illustrative

-- EXPLAIN (ANALYZE) on a duplicate ingest:
Insert on inbox  (cost=0.00..0.01 rows=1 width=56) (actual time=0.052..0.053 rows=1)
  Conflict Resolution: UPDATE
  Conflict Arbiter Indexes: inbox_pkey
  Tuples Inserted: 0
  Conflicting Tuples: 1
  ->  Result  (cost=0.00..0.01 rows=1 width=56) (actual time=0.004..0.004 rows=1)
Planning Time: 0.070 ms
Execution Time: 0.088 ms

Read it top-down. There is no separate SELECT node — the single Insert on inbox node probes inbox_pkey itself, finds the collision (Conflicting Tuples: 1, Tuples Inserted: 0), and applies the update in place. Conflict Resolution: UPDATE confirms the DO UPDATE branch fired, and Conflict Arbiter Indexes: inbox_pkey names the unique index doing the arbitration. On a first-sight event the same node would instead report Tuples Inserted: 1, Conflicting Tuples: 0.

The concurrency guarantee lives in that arbiter index. When two workers race, the unique index on event_id serializes them: exactly one acquires the right to insert the new key; the other blocks, then — because the key now exists — is routed into DO UPDATE and bumps the counter. Watch it happen:

Narrate it. “Both workers run the same INSERT … ON CONFLICT (event_id) DO UPDATE. The primary-key index lets exactly one of them insert; the other blocks on that key, and once the winner commits it is routed to the update branch and increments seen_count. Each returns was_insert correctly — true for the inserter, false for the updater — so my side effects run exactly once. There’s no SELECT, no application lock, and no duplicate row: the database’s own unique index is the concurrency control.” This inbox is exactly the idempotency mechanism we build on again in Phase 8 (Lesson 47).

05 Practice

Graded drills & traps

Write each query before you open the solution. Assume the obvious unique constraints exist unless a drill says otherwise.

Drill 1 — a counter row (DO UPDATE)

Table counters(name text PRIMARY KEY, n int NOT NULL DEFAULT 0). In one statement, either create 'signups' with n = 1 or increment its existing n, and return the new value.

Try it first, then read

sql

INSERT INTO counters (name, n) VALUES ('signups', 1)
ON CONFLICT (name) DO UPDATE SET n = counters.n + 1
RETURNING n;

Why: reference the stored row (counters.n) to accumulate. EXCLUDED.n is only the 1 you tried to insert — use it when you want to add the incoming amount (counters.n + EXCLUDED.n).

Drill 2 — detect a duplicate (DO NOTHING + RETURNING)

Insert a new users(email). Return the new id only if the row was actually created; a conflict should quietly produce nothing.

Try it first, then read

sql

INSERT INTO users (email) VALUES ($1)
ON CONFLICT (email) DO NOTHING
RETURNING id;

Why: a returned row means a fresh insert; an empty result means the email already existed. If you also need the existing id back on conflict, swap in a harmless DO UPDATE SET email = EXCLUDED.email RETURNING id (a no-op update still returns its row).

Drill 3 — multi-branch sync with a delete (MERGE)

Reconcile products against a staging table keyed by sku: update prices for matches, insert new SKUs, and delete a product whose staging row has discontinued = true.

Try it first, then read

sql

MERGE INTO products AS t
USING staging AS s ON t.sku = s.sku
WHEN MATCHED AND s.discontinued THEN DELETE
WHEN MATCHED THEN UPDATE SET price = s.price
WHEN NOT MATCHED THEN INSERT (sku, price) VALUES (s.sku, s.price);

Why: three outcomes over a join — branch order matters, and the delete branch is something ON CONFLICT can’t do. Run this as a batch job, not on a hot concurrent path.

Drill 4 — return a generated id to the app

Insert an orders row and hand the application the server-generated id and the DEFAULT timestamp — without a second query.

Try it first, then read

sql

INSERT INTO orders (user_id, total) VALUES (42, 99.50)
RETURNING id, created_at;

Why: RETURNING gives you the identity/serial id and the now() default in the same round-trip — no currval() and no follow-up SELECT.

Traps to avoid

• ON CONFLICT needs a real unique index, not a WHERE. Without a matching unique constraint you get “there is no unique or exclusion constraint matching the ON CONFLICT specification.”
• EXCLUDED vs the target alias. EXCLUDED.col is the rejected incoming row; tablename.col is the stored row. Swapping them silently computes the wrong value.
• Don’t use MERGE for a simple high-concurrency upsert. Two racing MERGEs can both hit NOT MATCHED and one raises a unique violation — use ON CONFLICT.
• DO NOTHING returns no row. On a conflict its RETURNING yields nothing, so don’t rely on it to fetch the existing row.

★ Review

Summary & self-test

One idea to carry: an upsert is a single atomic write anchored on a unique index — INSERT … ON CONFLICT for the everyday insert-or-update, MERGE for complex multi-branch logic — and RETURNING hands the affected rows back in the same round-trip.
