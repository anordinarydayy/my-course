Logical Replication & CDC

Physical replication copies the WAL byte-for-byte to make an identical clone. Logical replication does something stranger and more useful: it decodes the same WAL into row-level changes — INSERT, UPDATE, DELETE — that you can filter, transform, ship to a different major version, and feed into systems that aren't even Postgres. That decoding is the engine of Change Data Capture, the modern way to keep a warehouse, a search index, or a cache in sync with your database of record — without the dual-write bugs that plague the naive approach.

00 Orientation

Two ways to copy a database

Postgres can replicate itself in two fundamentally different ways, and the whole lesson turns on the distinction. Physical (streaming) replication — the subject of L41 — ships the raw WAL byte-stream and the standby replays it, producing a block-for-block identical copy of the entire cluster. It is simple and fast, but it is also rigid: the standby is read-only, must be the same major version, and copies everything, whether you wanted that table or not.

Logical replication starts from the same WAL but runs it through a decoder first. Instead of "apply these bytes to that disk block," it emits "row 42 in orders changed from this to that." Those row-level changes can be filtered to specific tables, replayed on a different major version, and applied to a target that is a normal, writable database. Everything you'll build in the rest of Phase 8 — feeding a warehouse, a search index, a cache — rides on that difference.

Physical / streaming (L41)

  • Ships WAL bytes; standby replays block-for-block.
  • Whole cluster, all databases & tables — no picking.
  • Standby is read-only; same major version.
  • Great for HA and read scaling; a faithful clone.

Logical / decoded

  • Decodes WAL into row-level changes (I/U/D).
  • Selective: chosen tables, rows, even columns.
  • Target is writable; works cross-version.
  • The basis of CDC — feed non-Postgres systems.

Change Data Capture (CDC) is the pattern that falls out of this: tap the stream of committed row changes and use it to drive other systems, so your database stays the single source of truth and everything downstream is a derived copy that follows along. Postgres provides the raw capability — logical decoding — and tools like Debezium build the full pipeline on top of it.

Same WAL, two readers

There is only ever one write-ahead log. Physical replication and logical decoding are two different consumers of it: one wants the bytes to make an identical block image; the other wants the meaning — which row, which table, which operation. Understanding that both start from the same WAL is the key that makes replication, CDC, and even backup/PITR (L36–L37) click together.

01 The wiring

Publications & subscriptions ▸

Native logical replication is configured with two objects. On the source (the publisher) you create a PUBLICATION — a named set of tables whose changes you want to expose. On the target (the subscriber) you create a SUBSCRIPTION that connects to that publication and starts pulling changes. The one prerequisite is server-side: wal_level = logical in postgresql.conf (a restart), which tells Postgres to log enough extra detail for decoding.

sql

-- PUBLISHER (source): postgresql.conf -> wal_level = logical  (needs a restart)
CREATE PUBLICATION pub_sales FOR TABLE orders, customers;

-- SUBSCRIBER (target): the tables must already exist with matching columns
CREATE SUBSCRIPTION sub_sales
  CONNECTION 'host=source dbname=shop user=repl password=...'
  PUBLICATION pub_sales;

Creating the subscription does three things in sequence: it opens a logical replication slot on the publisher (which will retain WAL until the subscriber has consumed it), takes an initial snapshot of the existing rows in the published tables, and then switches to streaming ongoing changes. Step through exactly what flows — and, just as importantly, what doesn't:

The important word is selective. A publication can name specific tables (FOR TABLE), every table in a schema (FOR TABLES IN SCHEMA sales, PG15+), or the whole database (FOR ALL TABLES). Since PG15 you can even attach a row filter (WHERE (region = 'EU')) and a column list, so the subscriber receives only the slice it needs. Nothing outside the publication is ever decoded or sent.

Selective by design

Because publications choose tables (and rows, and columns), logical replication is how you build a subscriber that holds only part of the source — a reporting replica with just the public tables, a per-region copy, or a consolidation target that merges several shards into one. That flexibility is impossible with physical replication, which always copies the entire cluster verbatim.

02 The mechanism

Logical decoding and how CDC is built on it ▸

Native subscriptions are the friendly front end. Underneath sits logical decoding: a replication slot plus an output plugin that reads the WAL and reconstructs row-level change events. Postgres ships pgoutput (the compact binary format native replication and Debezium use) and test_decoding (a human-readable format, perfect for seeing the stream). You can tap a slot directly — no second database required — with pg_recvlogical or the SQL functions:

sql

-- create a logical slot using the human-readable test_decoding plugin
SELECT pg_create_logical_replication_slot('cdc_demo', 'test_decoding');

-- PEEK at the changes (does NOT advance the slot; *_get_* would consume them)
SELECT lsn, data
FROM pg_logical_slot_peek_changes('cdc_demo', NULL, NULL);

After an INSERT, an UPDATE, and a DELETE on orders commit in one transaction, the decoded stream looks like this — ordered, framed by BEGIN/COMMIT, one line per row change:

illustrative · test_decoding output

    lsn     | data
------------+----------------------------------------------------------
 0/1A2B3C0  | BEGIN 742
 0/1A2B3D8  | table public.orders: INSERT: id[bigint]:10 total[integer]:40
 0/1A2B420  | table public.orders: UPDATE: id[bigint]:10 total[integer]:55
 0/1A2B468  | table public.orders: DELETE: id[bigint]:10
 0/1A2B490  | COMMIT 742

Three properties make this stream the perfect input for CDC: it is ordered (changes appear in commit order), transactional (you see whole committed transactions, never half of one), and durable to resume (the slot remembers the last position the consumer confirmed, so a crashed consumer picks up where it left off). This is the mental model behind every CDC tool. Debezium is the most common: it runs as a Kafka Connect connector, reads a Postgres slot with pgoutput, and publishes each change as a message onto a Kafka topic. From there, sink connectors (or your own consumers) push the changes into a data warehouse, an Elasticsearch index, or a Redis cache — every downstream system an eventually-consistent, derived copy of what Postgres committed.

pgoutput vs test_decoding

Use test_decoding to read the stream with your eyes while learning or debugging — it prints the plain-text lines above. Use pgoutput in production: it's the built-in binary protocol that native subscriptions and Debezium speak, and it needs no extra extension installed on managed services like RDS or Cloud SQL. Same slot machinery underneath; different wire format.

03 Uses & limits

Where it shines, and the rules that bite

Logical replication earns its keep in a handful of high-value situations, and it comes with a matching set of sharp edges you must respect.

What it's for

  • Near-zero-downtime major upgrades. Replicate PG 16 → PG 18 logically, let the new version catch up, then cut over — because logical works across major versions where physical cannot. PG17's pg_createsubscriber can even convert an existing physical standby into a logical subscriber almost instantly, avoiding a fresh full copy.
  • Cross-version / cross-platform migration and consolidating several databases (or shards) into one reporting target.
  • Feeding derived systems (CDC): warehouses, search indexes, caches, and event streams — the focus of the worked problem next.

The rules that bite

  • REPLICA IDENTITY. To replicate an UPDATE or DELETE, the subscriber must know which row to touch. The table's replica identity supplies that key: DEFAULT uses the primary key; USING INDEX a chosen unique, non-partial, NOT NULL index; FULL logs the entire old row (expensive, but the only option when there's no unique key); NOTHING blocks updates/deletes entirely. A table with no PK and DEFAULT identity will error on the first update.
  • No DDL, no sequences. Only row-level DML replicates. ALTER TABLE, new indexes, and other schema changes are not propagated — you apply them to the subscriber yourself, in expand/contract order (L44-style migrations). Sequence values aren't replicated either, so after a switchover you must re-align identity counters. (TRUNCATE is replicated since PG11.)
  • Slots retain WAL. A slot pins WAL at its restart_lsn until the consumer confirms it. An idle or forgotten slot therefore keeps WAL forever and can fill the primary's disk — a classic outage. Cap the damage with max_slot_wal_keep_size and monitor pg_replication_slots.
  • Failover used to break CDC. Logical slots lived only on the primary and weren't copied to standbys, so a failover orphaned every slot — the promoted node had no idea where the consumer was, forcing a full re-snapshot.

sql

-- when a table has no primary key, give it an identity for U/D replication
ALTER TABLE orders REPLICA IDENTITY FULL;        -- or USING INDEX orders_uk

-- PG17: keep the logical slot synchronized to standbys so CDC survives failover
CREATE SUBSCRIPTION sub_sales
  CONNECTION '...' PUBLICATION pub_sales
  WITH (failover = true);

-- watch WAL a slot is retaining (an inactive slot here is a red flag)
SELECT slot_name, active, wal_status,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots;
PG17 failover slots — CDC that survives HA

PG17 makes logical slots synchronizable: create the subscription (or slot) with failover = true, and set synchronized_standby_slots so the primary only advances the logical slot after the standby has the same WAL. Now when a standby is promoted, it carries a copy of the slot at the right position and your Debezium pipeline resumes without re-snapshotting the whole database. This closed the biggest operational gap in production CDC.

04 Worked problem

Keep a search index in sync with CDC ▸

Time to build the real thing. You run an e-commerce catalog in Postgres, and product search is served by Elasticsearch. When a price or stock flag changes in Postgres, search results must reflect it within a few seconds — without the fragile "write the DB, then write ES" code that so often loses updates.

1 · The schema

sql

CREATE TABLE products (
  product_id   bigint PRIMARY KEY,
  title        text        NOT NULL,
  price_cents  integer     NOT NULL,
  in_stock     boolean     NOT NULL DEFAULT true,
  updated_at   timestamptz NOT NULL DEFAULT now()
);

2 · The task

Every committed change to products — insert, price update, stock toggle, delete — must be reflected in the Elasticsearch products index promptly, reliably, and without blocking the write path or losing events on a crash.

3 · The naive attempt (and why it's wrong)

The obvious code writes both stores in the application:

pseudo-code · the dual write

// application request handler
db.execute("UPDATE products SET price_cents=1999 WHERE product_id=42");
db.commit();                                  // (1) Postgres committed
es.index("products", 42, {price_cents: 1999});    // (2) now update search

This is the dual-write problem. There is no transaction spanning Postgres and Elasticsearch, so any of these interleavings corrupts the index:

  • The process crashes between (1) and (2) → Postgres has the new price, search is permanently stale.
  • The ES call fails (timeout, ES down) after the DB commit → same stale index, and now you're writing rollback/retry logic by hand.
  • Two concurrent updates commit as A→B in the DB but their ES calls race and land B→A → the index ends on the older value (a write-write / invalidation race).

You cannot fix this with more retries or a bigger try/catch: the fault is structural — two independent systems, no shared commit. (L46's transactional outbox is the other principled cure; here we use CDC.)

4 · The fix: drive the index from CDC

Make Postgres the single source of truth and let the search index follow the WAL. The application writes only to Postgres; a CDC pipeline carries every committed change to Elasticsearch.

sql

-- 0) postgresql.conf: wal_level = logical   (restart once)

-- 1) publish the table whose changes drive search
CREATE PUBLICATION pub_products FOR TABLE products;

-- 2) REPLICA IDENTITY defaults to the PK (product_id), so every
--    UPDATE and DELETE event already carries the id the sink keys on.
--    (Use FULL only if a downstream transform needs old non-key columns.)

-- 3) a Debezium (pgoutput) connector reads the slot and emits, per change:
--    { op:'u', after:{ product_id:42, price_cents:1999, in_stock:true, ... } }
--    keyed by product_id; a consumer upserts it into Elasticsearch.

5 · Why it's better

There is now exactly one write in the request path — the Postgres commit — and it is impossible to lose a change, because every committed change is in the WAL and the slot guarantees the consumer will eventually see it. Delivery is at-least-once: a consumer that crashes after applying but before acking will be re-sent the same event. That's why the sink must be idempotent — an upsert keyed by product_id re-applied is a harmless no-op, so at-least-once + idempotent = effectively once.

Idempotency at the consumer often uses a tiny dedup table (an "inbox") keyed by the event's LSN, so a replay is a cheap no-op. That check is a primary-key conflict — here's the plan Postgres runs for it:

sql

CREATE TABLE search_inbox (event_lsn pg_lsn PRIMARY KEY);

EXPLAIN ANALYZE
INSERT INTO search_inbox (event_lsn) VALUES ('0/1A2B420')
ON CONFLICT (event_lsn) DO NOTHING;

illustrative · a redelivered event = a no-op

Insert on search_inbox  (cost=0.00..0.01 rows=0 width=0)
                        (actual time=0.041..0.041 rows=0 loops=1)
  Conflict Resolution: NOTHING
  Conflict Arbiter Indexes: search_inbox_pkey
  Tuples Inserted: 0
  Conflicting Tuples: 1
  ->  Result  (cost=0.00..0.01 rows=1 width=8)
              (actual time=0.002..0.002 rows=1 loops=1)
 Planning Time: 0.058 ms
 Execution Time: 0.071 ms

Read it: Tuples Inserted: 0, Conflicting Tuples: 1. The duplicate hit the search_inbox_pkey arbiter index and was dropped — the second delivery did nothing, exactly what idempotency requires. Ordering, meanwhile, comes from partitioning the Kafka topic by product_id, so all changes to one product stay in order relative to each other even under concurrency.

6 · Narrate it

"The app writes only Postgres. A publication exposes products; because its replica identity is the primary key, every update and delete event carries product_id. Debezium reads the logical slot and drops keyed change events on a Kafka topic partitioned by product_id, preserving per-product order. An indexer upserts each event into Elasticsearch using product_id as the document id. Delivery is at-least-once, so I made the sink idempotent — a re-delivered event upserts the same doc, a no-op. No dual write, no lost updates; search is an eventually-consistent derived view of the WAL." That last idea — a cache or index as a derived, eventually-consistent copy of the database of record — is exactly what L48 generalizes.

05 Drills

Graded drills & the traps list

Work each drill before opening its solution. They rise in difficulty and target the exact places logical replication and CDC go wrong in production.

Drill 1 · The updates that won't replicate

You publish a table and INSERTs replicate perfectly, but the first UPDATE fails with cannot update table ... because it does not have a replica identity and publishes updates. What's wrong, and the one-line fix?

Try it first, then read

The table has no primary key, so its default replica identity can't tell the subscriber which row an UPDATE/DELETE targets. INSERTs work because they carry the whole new row; U/D need a key. Fix: give it one — ALTER TABLE t REPLICA IDENTITY FULL; (logs the whole old row) or, better, add a unique NOT NULL index and ALTER TABLE t REPLICA IDENTITY USING INDEX t_uk;. Why: logical replication identifies rows by the replica identity, and without a PK you must supply one explicitly.

Drill 2 · The column that vanished downstream

You ran ALTER TABLE products ADD COLUMN brand text on the publisher. Later an app INSERT that sets brand starts erroring on the subscriber, and the subscriber's products has no brand column at all. Why, and what's the correct rollout?

Try it first, then read

Logical replication does not replicate DDL — only row changes. Your ADD COLUMN never reached the subscriber, so when the publisher streams an INSERT that includes brand, the apply worker can't map it and the subscription stalls. Correct order (expand/contract): add the column on the subscriber first (compatibly, e.g. nullable), then on the publisher, then start writing the new column. Why: schema must lead on the consumer side because the stream carries data, not structure.

Drill 3 · The disk that keeps filling

Your primary's disk usage climbs steadily even though write volume is flat, and pg_wal won't shrink after checkpoints. pg_replication_slots shows a slot with active = false and a huge retained_wal. Diagnose and fix — and name the guardrail.

Try it first, then read

An inactive logical slot is pinning WAL at its restart_lsn: Postgres can't recycle any WAL the (dead or disconnected) consumer never confirmed, so pg_wal grows without bound — a classic outage. Fix: restart the consumer so it drains and advances the slot, or if it's truly abandoned, SELECT pg_drop_replication_slot('slot_name');. Guardrail: set max_slot_wal_keep_size so a lagging slot is invalidated instead of filling the disk, and alert on slot lag. Why: slots trade retained WAL for reliable resume — an orphaned one keeps the promise forever.

Drill 4 · CDC that survives a failover

Your Debezium pipeline feeds search off a logical slot on the primary. A planned failover promotes a standby; afterward the connector can't find its slot and wants to re-snapshot the entire database. On a fresh (PG17) cluster, how do you make CDC survive promotion, and why does it work?

Try it first, then read

Historically logical slots existed only on the primary and weren't copied to standbys, so a promotion orphaned CDC. On PG17: create the slot/subscription with failover = true and set synchronized_standby_slots so the primary advances the logical slot only after the standby has that WAL; the standby then keeps a synchronized copy of the slot. (pg_createsubscriber can also stand up a subscriber from a standby.) After promotion the new primary resumes from the synchronized position — no re-snapshot. Why: the slot's confirmed position is now durable on the standby, not just the failed primary.

Traps to keep on a card

• Missing REPLICA IDENTITY → UPDATE/DELETE break (no PK) or ship too little (need FULL for old-column transforms).
• DDL & sequences don't replicate → roll schema out on the subscriber first; re-align identity counters after switchover.
• Idle/forgotten slot → retained WAL fills the disk; monitor slots, cap with max_slot_wal_keep_size.
• The initial snapshot → a big table's first sync COPYs the whole table and can take hours / add load; plan it (or copy_data = false + a manual load).
• "Exactly-once" is a myth → it's at-least-once + an idempotent consumer; expect duplicates and cross-key reordering.
• Replication is not a backup → a bad DELETE is replicated faithfully to every downstream copy.

★ Review

Summary & self-test

One idea to carry: logical replication decodes the WAL into row-level changes you can filter, transform, and ship anywhere — and that decoded stream is exactly what CDC taps to keep derived systems (warehouse, search, cache) in sync with the database of record, at-least-once, without dual writes.
