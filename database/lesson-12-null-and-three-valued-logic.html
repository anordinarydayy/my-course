NULL & Three-Valued Logic

SQL's NULL is the most misunderstood token in the language. It is not zero, not the empty string, and not even equal to itself — it means “unknown”. That single idea turns ordinary two-valued boolean logic into a three-valued logic (TRUE / FALSE / UNKNOWN), and that third value quietly breaks =, IN, NOT IN, joins, aggregates, and uniqueness. This lesson builds the mental model and the safe idioms so those surprises stop being surprises.

00 The core idea

NULL is not a value — it is “unknown”

Start with the definition that fixes everything else: NULL is not a value; it is a marker meaning “this information is missing or does not apply.” A column that is NULL is not holding zero, and it is not holding an empty string — it is holding nothing we can compare. The moment you treat NULL as “a special value” you will get bitten; the moment you read it as the word unknown, the rules become obvious.

Because NULL is unknown, any operation that touches it inherits that uncertainty. Arithmetic, string concatenation, comparisons — feed one NULL in and an unknown comes out:

sql

SELECT 5 + NULL;        -- → NULL   (5 plus an unknown is still unknown)
SELECT 'hi' || NULL;    -- → NULL   (text concatenated with unknown is unknown)
SELECT NULL = NULL;     -- → NULL   (NOT true! two unknowns are not "equal")

That last line is the one to sear into memory. If you ask “is this unknown the same as that unknown?” the only honest answer is “I don't know” — so NULL = NULL is neither TRUE nor FALSE, it is UNKNOWN. NULL fails to be equal even to itself, which is exactly why equality can never be the tool you reach for to test it.

SQL also folds two subtly different ideas into the one NULL marker, and it helps to keep them distinct in your head even though the database cannot:

“Unknown”

  • The value exists but we haven't recorded it.
  • A customer's birth_date we never collected.
  • One day it may be filled in with a real value.

“Inapplicable”

  • The attribute does not apply to this row.
  • A middle_name for someone who has none.
  • There will never be a meaningful value here.

Postgres stores both cases as the same NULL and gives you no way to tell them apart — a modeling wrinkle we return to in the final section. For now, whenever you see NULL, mentally substitute the word unknown and every rule in this lesson will follow.

The one substitution that unlocks everything

Read NULL as the word “unknown”, out loud, every time. “salary > 50000 where salary is unknown” obviously can't be answered TRUE or FALSE — it's UNKNOWN. “Is unknown equal to unknown?” — unknown. Do this consistently and you will never again be surprised by a query that returns zero rows for no visible reason.

01 The logic

Three-valued logic: TRUE, FALSE, UNKNOWN ▸

Ordinary boolean logic has two values, TRUE and FALSE. SQL has three: it adds UNKNOWN, the truth value that any comparison to NULL produces. Every AND, OR, and NOT in the language is defined over all three, and the tables have a satisfying internal logic once you see them.

The rule that generates the whole set: a known value can only “win” an operator when it settles the result by itself. FALSE wins an AND (anything AND false is false), and TRUE wins an OR (anything OR true is true) — in those cases the unknown never gets a vote. Everywhere else, the unknown leaks through. Step the truth tables:

The last step is the one that matters in practice. A filter keeps a row only when its predicate is TRUE. WHERE, JOIN ... ON, and HAVING all share this rule, and it means UNKNOWN is discarded exactly like FALSE — a row whose predicate is UNKNOWN simply vanishes, silently, with no error. Almost every “my query lost rows I expected” bug traces back to a predicate that quietly evaluated to UNKNOWN because a NULL wandered into it.

TRUE is the only ticket in

Do not think of a WHERE clause as “keep rows that aren't FALSE.” Think “keep rows that are TRUE.” FALSE and UNKNOWN are both dropped, but they arrive at that fate for different reasons — and a CHECK constraint flips the emphasis: a check passes unless it is FALSE, so a NULL (UNKNOWN) satisfies a CHECK. Same three-valued logic, opposite default. We meet that again with constraints.

02 Testing for NULL

= NULL never matches — use IS NULL

Now the most common NULL bug in the world, and it follows directly from the truth tables. Since any comparison to NULL is UNKNOWN, both x = NULL and x <> NULL are UNKNOWN — and a WHERE clause drops UNKNOWN — so WHERE col = NULL matches nothing, ever. Not an error, just an empty result:

sql

-- The bug: this returns ZERO rows, always, no matter the data.
SELECT * FROM member WHERE email = NULL;

-- The fix: the dedicated NULL predicates.
SELECT * FROM member WHERE email IS NULL;
SELECT * FROM member WHERE email IS NOT NULL;

IS NULL and IS NOT NULL are the only tests that return a clean TRUE/FALSE for NULL — they never produce UNKNOWN. When you genuinely need “equality, but treat two NULLs as the same,” SQL gives you a NULL-safe pair, IS DISTINCT FROM and IS NOT DISTINCT FROM, which also always return TRUE or FALSE:

sql

-- NULL-safe comparison: never UNKNOWN, always TRUE or FALSE.
--   NULL IS NOT DISTINCT FROM NULL  → TRUE   (treated as the same)
--   1    IS DISTINCT FROM     NULL  → TRUE   (a value differs from unknown)
SELECT old.status IS DISTINCT FROM new.status AS changed
FROM audit;

That last pattern — “did this column actually change?” — is where IS DISTINCT FROM earns its keep. Plain old.status <> new.status would report UNKNOWN (and so, effectively, “no change”) whenever either side is NULL, hiding a real transition into or out of NULL. The NULL-safe operator catches it.

A trap hiding in your application code

This bug loves to sneak in through parameter binding. Application code that builds WHERE email = $1 and passes a NULL value for $1 silently returns nothing — the driver does not rewrite it to IS NULL for you. If a column can be NULL and you're comparing to a variable that can be NULL, reach for IS NOT DISTINCT FROM $1, which does the right thing whether the parameter is a value or NULL.

03 The classic trap

The NOT IN trap ▸

Here is a bug that has cost real teams real hours, because it looks completely innocent and fails silently. NOT IN (subquery) is one of the most natural things to write — and if that subquery ever returns a single NULL among its values, the whole query returns nothing. No error, no warning, just an empty result where you expected rows.

Why? Because x NOT IN (a, b, c) is defined as x <> a AND x <> b AND x <> c. If one of those values is NULL, that term becomes x <> NULL = UNKNOWN, and (from the AND table) anything AND UNKNOWN can never be TRUE — the best it reaches is UNKNOWN, which WHERE drops. Watch a single NULL flip the entire result set to empty:

Two robust fixes, and the code for both:

sql

-- Trap: if any discontinued_id is NULL, this returns NOTHING.
SELECT * FROM product p
WHERE p.id NOT IN (SELECT discontinued_id FROM promo);

-- Fix A (preferred): NOT EXISTS is a NULL-safe anti-join.
SELECT * FROM product p
WHERE NOT EXISTS (
  SELECT 1 FROM promo d WHERE d.discontinued_id = p.id
);

-- Fix B: strip NULLs from the subquery first.
SELECT * FROM product p
WHERE p.id NOT IN (
  SELECT discontinued_id FROM promo WHERE discontinued_id IS NOT NULL
);

NOT EXISTS works because it is built on row existence, not on three-valued equality: for each product it asks “does a matching promo row exist?” and a NULL that never matches simply contributes no match — it can't poison the answer. That's why it's the idiom to reach for by default. Note the asymmetry with plain IN, which is far more forgiving:

sql

-- IN tolerates NULL: a genuine match still yields TRUE.
SELECT 1 WHERE 5 IN (5, NULL);        -- → row returned  (5 = 5 is TRUE)
-- NOT IN does not: one NULL makes the whole test UNKNOWN.
SELECT 1 WHERE 5 NOT IN (1, 2, NULL);  -- → no row      (T AND T AND UNKNOWN)

IN is an OR of equalities, so a real match produces TRUE OR UNKNOWN = TRUE and survives. NOT IN is an AND of inequalities, so any UNKNOWN drags the whole thing down. Same NULL, opposite outcome — and that is precisely why NOT IN is the dangerous member of the family.

04 The blast radius

Where else NULL bites ▸

The three-valued logic in section 01 is the root cause, but NULL surfaces in several other places with behavior worth memorizing individually. Take one small table — members left-joined to their latest order — and read its NULLs through four different lenses:

Each lens has a rule and a fix. In code:

sql

-- UNIQUE allows MANY NULLs: each unknown differs from all others.
CREATE TABLE member (
  id    bigint PRIMARY KEY,
  email text UNIQUE                       -- many rows may have email = NULL
);

-- Postgres 15+: opt in to "at most one NULL" when you want it.
CREATE TABLE member2 (
  id    bigint PRIMARY KEY,
  email text UNIQUE NULLS NOT DISTINCT     -- now only ONE NULL allowed
);

sql

-- Aggregates SKIP NULL: avg divides by the count of non-NULLs.
SELECT avg(total)   AS avg_total,   -- (40+15+25)/3 = 26.7, ignores the NULL
       count(*)     AS rows_all,    -- 4  — counts rows
       count(total) AS rows_total   -- 3  — counts non-NULL values
FROM members;

-- ORDER BY: NULLs sort LAST in ASC (Postgres ranks NULL highest), FIRST in DESC.
SELECT name, total FROM members ORDER BY total DESC NULLS LAST;

-- Tame them (two separate idioms). COALESCE supplies a fallback for a NULL column:
SELECT name, coalesce(total, 0) AS total_or_zero   -- a NULL total shows as 0
FROM members;

-- NULLIF makes a deliberate NULL — here to guard a divide-by-zero:
SELECT sum(amount) / nullif(count(*), 0) AS safe_avg  -- 0 rows → NULL, not a crash
FROM orders;
The exception that trips everyone: GROUP BY treats NULLs as equal

Here's an inconsistency to file away. Under =, no two NULLs are equal — yet GROUP BY, DISTINCT, and UNION all treat NULLs as the same and collapse them into a single group/row. So GROUP BY city puts every NULL city together in one bucket, and SELECT DISTINCT city returns NULL once. It's the standard's deliberate choice (“grouping” uses is-not-distinct semantics, not equality) — but it means NULL behaves one way in WHERE and the opposite way in GROUP BY. Memorize the split.

05 Reason about it

Reason about it: when NULL is the right choice

You now know how NULL behaves; the harder skill is deciding when to allow it at all. Walk the reasoning with a concrete column and you'll have a repeatable method. Suppose you're modeling employee.manager_id. Should it be nullable?

Ask the diagnostic question: is there a row for which this attribute genuinely has no value? The CEO has no manager — not “a manager we forgot,” but truly inapplicable. That is exactly what NULL is for, so manager_id should be nullable. Contrast with employee.email: if every employee must have one, a NULL there represents missing data you'd rather forbid outright — so make it NOT NULL, and the database stops the bad row at the door. The decision tree:

Allow NULL

  • The value is genuinely unknown or inapplicable for some rows.
  • “No manager,” “no end date yet,” “middle name absent.”
  • You've decided what UNKNOWN means here and documented it.

NOT NULL + default

  • Every row must have a value; a sensible default exists.
  • status DEFAULT 'active', balance DEFAULT 0, counters.
  • Turns “forgot to set it” into a known, safe value.

Separate table

  • The attribute applies to only a few rows (sparse).
  • Optional 1-to-1 detail, or a rare sub-type's fields.
  • Model it as its own table; absence = no row, not a NULL.

The third option is underused. When a column would be NULL for the overwhelming majority of rows — a “gift message” that 2% of orders carry — a wall of NULLs is a smell that the attribute belongs in its own optional table, where presence of a row models “this applies” far more honestly than a NULL does. That also sidesteps every ambiguity in this lesson: a table you either join to or don't has no three-valued logic to trip over.

Two disciplines make NULL survivable once you've allowed it. First, write NULL-safe predicates on purpose: reach for IS NULL, IS DISTINCT FROM, and NOT EXISTS reflexively on any nullable column, rather than discovering the UNKNOWN the hard way in production. Second, default to NOT NULL and make nullability a deliberate, documented exception — a column that can be NULL is a promise every future query must remember to handle, so each one should earn it. When you do allow NULL, write down in the schema comment which meaning it carries (unknown vs inapplicable), because the database won't.

Where this shows up next

This concept is load-bearing for much of what follows. L04 (constraints) is where NOT NULL and CHECK turn these rules into enforced guarantees — remember a CHECK passes on UNKNOWN. L10 (outer joins) is where you'll deliberately manufacture NULLs and then filter on them (mind the WHERE-vs-ON distinction). L11 (aggregation) leans on “aggregates skip NULL” and COALESCE constantly. And in Phase 4 (indexing) you'll see that B-tree indexes do store NULLs (so IS NULL can use an index), that a WHERE col IS NOT NULL partial index is a common tool, and that NULLS FIRST/LAST is part of an index's sort definition.

★ Review

Summary & self-test

The whole lesson compresses to one idea: NULL means “unknown,” so it turns boolean logic into three-valued logic (TRUE / FALSE / UNKNOWN) — and because filters keep only TRUE, that third value quietly drops rows, empties NOT IN queries, and behaves inconsistently across =, GROUP BY, aggregates, uniqueness, and sorting. Master the safe idioms and none of it can surprise you.
