Query-Tuning Playbook

Slow-query firefighting looks like art, but it is really a checklist. This capstone ties Phase 4 together into one repeatable loop — reproduce, measure, isolate the single most expensive node, form one hypothesis, change one thing, re-measure — and catalogues the anti-patterns that silently turn an index-backed query into a full-table scan. By the end you can walk a real dashboard query from two seconds down to two milliseconds, and explain every step of why.

Original study notes. Written from scratch for engineers preparing for interviews and on-call. Examples are PostgreSQL 17/18-correct and runnable; EXPLAIN output is labelled illustrative (real plan nodes and shapes, representative numbers). Contains three interactive diagrams (press Play or step with Next). This is a practice lesson — it ends in a fully worked SQL problem and a set of graded drills. The one habit to carry out of it: measure, don't guess.
00 The mindset

A method, not guesses

The single biggest mistake in query tuning is changing something before you have measured anything. An engineer sees a slow endpoint, decides "it probably needs an index," adds one, and either gets lucky or — far more often — adds an index the planner never uses, ships it, and moves on while the query stays slow. Tuning is not pattern-matching on the SQL text. It is a short, boring, repeatable loop, and the discipline is doing it in order instead of jumping to a fix.

Here is the whole loop. Everything else in this lesson is detail on one of these steps:

  • Reproduce. Get a query and parameters that are reliably slow. A query that is slow "sometimes" is usually slow for specific parameter values (a skewed WHERE), and you need those exact values to measure anything.
  • Measure. Run EXPLAIN (ANALYZE, BUFFERS) and read the plan tree bottom-up. Do not read the SQL and imagine what Postgres does — read what it actually did.
  • Find the single hottest node. One node almost always dominates the actual time (or the buffer reads). Ignore the cheap nodes; they are noise.
  • Form ONE hypothesis. Why is that node expensive? Pick exactly one cause: a missing index, stale statistics, an index-defeating query shape, or the wrong grain (returning far more rows than you need).
  • Change ONE thing. Add the one index, rewrite the one predicate, run ANALYZE. One change per iteration — so the re-measurement tells you unambiguously whether that change helped.
  • Re-measure. Run the same EXPLAIN (ANALYZE, BUFFERS). Keep the change if it helped; revert it if it did not. Then loop.

sql

-- the only measurement that matters: what the query ACTUALLY did.
-- ANALYZE runs it; BUFFERS shows cache hits vs disk reads (default in PG18).
EXPLAIN (ANALYZE, BUFFERS) SELECT … FROM events WHERE … ORDER BY …;

-- writes? wrap in a transaction so ANALYZE doesn't persist the change:
BEGIN; EXPLAIN (ANALYZE) UPDATE events SET status = 'closed' WHERE id = 42; ROLLBACK;

Two numbers do most of the diagnosis. The first is estimated rows vs actual rows on each node: when the planner expected 5 rows and got 500,000, it chose its plan on a lie — the cause is bad statistics, and the fix is ANALYZE or better stats, not an index. The second is buffers: a node with read=48211 touched 48,211 eight-kilobyte pages from disk (~386 MB) — that is what "slow" physically is. Cost numbers (the cost=0.00..247489.00 figures) are abstract planner units, useful only for comparing plans, never a time in milliseconds.

Measure, don't guess

Before you touch anything, you should be able to point at one node and say a sentence: "this Seq Scan reads 48k pages and removes 4.9M rows by filter — because the predicate isn't sargable." If you can't say that sentence, you haven't measured yet, and any index you add is a guess. Postgres has no query hints — you cannot order the planner to use an index. You change the facts it plans on (indexes, statistics, query shape) and let it re-decide. That is why measuring first is not optional: the fix is always aimed at a specific measured cause.

01 The loop

The tuning loop ▸

Draw the loop once and it stops feeling like firefighting. You are never "trying things" — you are always at a known station in a cycle, and each lap either improves the slow node or teaches you that your hypothesis was wrong (which is also progress). Play it through:

Two rules give the loop its power. One change per lap is not fussiness — if you add an index and rewrite the predicate and raise the stats target all at once and the query gets faster, you have learned nothing about which of the three mattered, and you will carry two useless changes forever. Re-measure every lap because the planner's choice can flip: an index that helps at one row-count is ignored at another, and a rewrite that looks obviously better can lose to a plan you didn't expect. The loop is short on purpose so that running it many times is cheap.

The loop ends, too

Stop when the hottest node is cheap enough that the next most expensive node dominates — and that node is already as cheap as the query can be. Chasing a 0.3 ms Sort while a 2000 ms Seq Scan sits above it is the classic beginner error; so is polishing a query that is already fast. Tuning has a finish line: when the plan is doing the minimal work the result actually requires, you are done.

02 Sargability

Index-defeating anti-patterns ▸

Most "missing index" bugs are not missing indexes at all — the index exists, and the query is written in a way that the index cannot serve. The word for a predicate an index can use is sargable (from "Search ARGument-able"): the indexed column appears bare on one side of a comparison the B-tree understands (=, <, >, BETWEEN, range). The instant you wrap the column in a function, the B-tree — which is ordered by the column's raw value, not by lower(column) or date(column) — is useless, and the planner falls back to a Seq Scan.

sql

-- ✗ a function on the indexed column: the btree on email is ordered by
--   email, not by lower(email), so it cannot be used → Seq Scan.
SELECT * FROM users WHERE lower(email) = 'ana@x.io';

-- ✓ fix A: index the expression itself (gives it its own ordered structure)
CREATE INDEX ix_users_lower_email ON users (lower(email));

-- ✓ fix B: don't wrap the column at all — store/compare it already-normalized
SELECT * FROM users WHERE email = 'ana@x.io';

The most common offender is a date function used to mean "on this day." date(created_at) = DATE '2026-07-03' reads naturally but wraps the column. The sargable rewrite is a half-open range on the bare column — same result, and now a plain B-tree on created_at serves it. Step through the transformation and watch the plan flip from Seq Scan to Index Scan:

The same shape of bug wears several disguises. Learn to spot the column-not-bare pattern under each of them:

sql

-- ✗ leading wildcard: a btree is ordered left-to-right, so it can't start
--   a search in the middle of the string. Trigram GIN can.
SELECT * FROM users WHERE name LIKE '%ana%';         -- Seq Scan
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX ix_users_name_trgm ON users USING gin (name gin_trgm_ops);

-- ✗ a cast on the COLUMN side (user_id is bigint) defeats its index
SELECT * FROM orders WHERE user_id::text = '42';         -- cast the literal, not the column:
SELECT * FROM orders WHERE user_id = 42;

-- ✗ OR across two columns often forces one scan; UNION lets each arm use its index
SELECT * FROM users WHERE email = $1 OR phone = $1;
SELECT * FROM users WHERE email = $1
UNION
SELECT * FROM users WHERE phone = $1;
The test in one sentence

Ask: is the indexed column sitting bare on one side of the comparison? If it is wrapped in a function, cast, or expression — or if the pattern has a leading % — a plain B-tree cannot help, and you have exactly two moves: rewrite the predicate so the column is bare (a range instead of date(), the literal cast instead of the column), or build an index that matches the expression (an expression index, or a trigram/GIN index for the wildcard case).

03 The catalogue

The usual suspects

Sargability is one family. A handful of other patterns account for most of the remaining slow queries you will meet. Each has a recognisable signature in the plan and a standard fix — learn the pairs and half your diagnoses are done before you finish reading the EXPLAIN.

N+1 — the loop that should have been a set

The application fetches a list, then loops and runs one more query per row: 1 query for 100 users, then 100 queries for their orders. Each round-trip is cheap; a hundred of them is not. This is the single most common performance bug in application code, and it is invisible in any one EXPLAIN — you only see it in the query log or an APM trace showing the same statement run 100 times. The fix is the set-based version from Lesson 00: ask once.

sql

-- ✗ N+1: app loops and runs this once per user id
SELECT * FROM orders WHERE user_id = $1;   -- × 100

-- ✓ one round-trip: hand the whole set to the database
SELECT * FROM orders WHERE user_id = ANY($1);   -- $1 = array of ids
-- ✓ or a single JOIN when you want users and orders together
SELECT u.id, o.* FROM users u JOIN orders o ON o.user_id = u.id
WHERE u.id = ANY($1);

SELECT * — over-fetch

  • Ships columns you never read — bytes over the wire, memory in the client.
  • Defeats index-only scans: pulling every column forces a heap fetch even when the index held all you needed.
  • Fix: select only the columns you use; let a covering index (INCLUDE) serve them.

Unindexed FK join

  • Postgres indexes the parent key automatically, but not the child's foreign-key column.
  • Joining or deleting on a bare FK column → a Seq Scan or a Nested Loop with a scan on the inner side (recap Lesson 05).
  • Fix: CREATE INDEX ON orders (user_id) — index every FK you join or cascade on.

OFFSET-deep pagination

OFFSET 10000 LIMIT 20 does not skip 10,000 rows for free — the executor must produce and then discard all 10,020, every page getting slower than the last (recap Lesson 14). Keyset (seek) pagination replaces the offset with a WHERE on the last row you saw, so every page reads exactly LIMIT rows through the index:

sql

-- ✗ deep offset: produces and throws away 10,020 rows
SELECT id, created_at FROM events ORDER BY created_at DESC OFFSET 10000 LIMIT 20;

-- ✓ keyset: carry the last row's sort key; read only 20 rows
SELECT id, created_at FROM events
WHERE (created_at, id) < ($last_created_at, $last_id)
ORDER BY created_at DESC, id DESC LIMIT 20;

One more suspect is the opposite of a missing index: an index the planner rightly refuses. An index on a low-selectivity column — status where 90% of rows are 'open' — is worse than a Seq Scan, because an Index Scan that matches most rows does a random heap fetch for nearly every row, which is slower than reading the pages sequentially once. When you add an index and EXPLAIN still shows a Seq Scan, the planner is very often correct: your index isn't selective enough to be worth it. That is not a bug to fight; it is the planner doing its job. (A partial index on just the hot subset can rescue the case — more on that next.)

Diagnose by signature

N+1 → same statement N times in the log. SELECT * → a Heap Fetch / no Index Only Scan where one was possible. Unindexed FK → Seq Scan on the child inside a join. Deep OFFSET → a plan whose actual rows at the scan node far exceed your LIMIT. Unselective index → the index exists but the plan won't use it. Each signature points straight at its fix — which is why you read the plan first.

04 Worked problem

Worked: two seconds → two milliseconds ▸

Now the whole method on one realistic query — a dashboard's "open events" feed that combines all three problems: a function on the column, a missing index, and a deep offset. We fix them one at a time, re-measuring each lap, and watch the plan collapse.

1 · The schema

sql

CREATE TABLE events (
    id          bigserial PRIMARY KEY,
    user_id     bigint      NOT NULL,
    status      text        NOT NULL,   -- 'open' | 'closed' | 'archived'
    payload     jsonb,
    created_at  timestamptz NOT NULL DEFAULT now()
);
-- ~5,000,000 rows; ~52k have status='open'; only the implicit PK index exists.

2 · The task

Power the "open events" feed: the newest open events from the last 30 days, paginated. The user has scrolled deep — page ~500, so OFFSET 10000. Here is what shipped:

sql

SELECT id, user_id, status, created_at
FROM events
WHERE status = 'open'
  AND date_trunc('day', created_at) >= current_date - 30
ORDER BY created_at DESC
OFFSET 10000 LIMIT 20;

3 · Measure — why it takes ~2 seconds

illustrative

Limit  (cost=612480.10..612480.15 rows=20 width=40) (actual time=2074.559..2074.567 rows=20 loops=1)
  Buffers: shared hit=192 read=48211
  ->  Sort  (cost=612455.10..612575.63 rows=48213 width=40) (actual time=2068.244..2072.930 rows=10020 loops=1)
        Sort Key: created_at DESC
        Sort Method: top-N heapsort  Memory: 1893kB
        Buffers: shared hit=192 read=48211
        ->  Seq Scan on events  (cost=0.00..611170.00 rows=48213 width=40) (actual time=0.028..2011.590 rows=51902 loops=1)
              Filter: ((status = 'open'::text) AND (date_trunc('day'::text, created_at) >= (CURRENT_DATE - 30)))
              Rows Removed by Filter: 4948098
              Buffers: shared hit=192 read=48211
Planning Time: 0.211 ms
Execution Time: 2075.140 ms

Read it bottom-up. The Seq Scan is the hot node: it reads read=48211 pages and throws away 4,948,098 rows by filter — it visits the entire 5-million-row table because date_trunc(...) makes the predicate non-sargable, so no index could be used even if one existed. Its 51,902 survivors then hit a bounded top-N heapsort — the OFFSET 10000 LIMIT 20 lets it keep only the top ~10,020 in memory rather than spilling to disk — but it must still sort all 51,902 and then discard the first 10,000 to reach the 20 you asked for. Three problems, stacked. Fix them one lap at a time:

4 · The fixes, one lap at a time

  • Fix 1 — make the predicate sargable. Replace date_trunc('day', created_at) >= current_date - 30 with the exactly-equivalent bare-column range created_at >= current_date - interval '30 days' (both cut at midnight 30 days ago). Re-measure: still ~2 s and still a Seq Scan — because there is no index yet. This lap looks like a failure, but it unlocked the next one: the predicate is now index-ready.
  • Fix 2 — add the composite, partial index. Only status='open' rows matter and we sort by created_at, so index exactly that hot subset:

    sql

    CREATE INDEX ix_events_open ON events (created_at DESC, id DESC)
    WHERE status = 'open';
    Now the index supplies rows already in created_at DESC order, so the Sort disappears and the scan becomes an Index Scan. Re-measure: ~140 ms. Better — but OFFSET 10000 still forces the executor to walk 10,020 index tuples before returning 20.
  • Fix 3 — swap OFFSET for keyset. Carry the last row's (created_at, id) and seek past it, so the index jumps straight to your page:

    sql

    SELECT id, user_id, status, created_at
FROM events
WHERE status = 'open'
  AND created_at >= now() - interval '30 days'
  AND (created_at, id) < ($last_created_at, $last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;

5 · Re-measure — the plan collapses

illustrative

Limit  (cost=0.43..4.02 rows=20 width=40) (actual time=0.041..2.104 rows=20 loops=1)
  Buffers: shared hit=26
  ->  Index Scan using ix_events_open on events  (cost=0.43..9218.55 rows=48213 width=40) (actual time=0.036..2.061 rows=20 loops=1)
        Index Cond: ((created_at >= (now() - '30 days'::interval)) AND (ROW(created_at, id) < ROW('2026-06-14 09:14:57+00'::timestamptz, 918234::bigint)))
        Buffers: shared hit=26
Planning Time: 0.180 ms
Execution Time: 2.171 ms

No Seq Scan, no Sort, no discarded rows. The Index Scan descends the partial index (already in DESC order, so no Backward needed), seeks straight to the keyset boundary, and reads actual rows=20 — exactly the page. Buffers drops from read=48211 (386 MB off disk) to hit=26 (208 KB, all cached). Execution time: 2075 ms → 2.171 ms, roughly a 950× improvement.

6 · Narrate it

The diagnosis was mechanical, not clever. Measure → the Seq Scan dominates (48k pages, 4.9M rows removed) → hypothesis: the date_trunc predicate is non-sargable so no index can help → make it sargable (lap 1: no faster yet, but now indexable) → hypothesis: with a bare column, a partial index on the hot subset lets the index supply order → add it (lap 2: Sort gone, 140 ms, but OFFSET still walks 10k) → hypothesis: the deep OFFSET is now the hot cost → keyset (lap 3: reads only the 20 rows returned). Three laps, one change each, re-measured every time. Nobody guessed; each fix was aimed at a node the plan had just shown to be expensive.

The pattern to remember

A big win often needs several fixes, but you still change one thing per lap. Fix 1 alone didn't move the clock — and that's fine: its job was to make the column sargable so Fix 2 could work. If you had bundled all three changes together and it got fast, you'd never know the rewrite was load-bearing or that the keyset (not the index) killed the last 138 ms. One change, one measurement, every time.

05 Practice

Graded drills & traps

Four drills of increasing difficulty. For each, write the diagnosis and the fix before opening the solution — say the one-sentence "why" out loud, the way you would in an interview. Assume PostgreSQL 17/18 and a table with an existing B-tree where noted.

Drill 1 — the daily filter

There is a B-tree on events(created_at), yet this "today's events" query does a Seq Scan. Make it use the index without changing the result.

sql

SELECT * FROM events WHERE date(created_at) = current_date;
Try it first, then read

Solution. Rewrite the wrapped column into a bare-column half-open range:

SELECT * FROM events
WHERE created_at >= current_date
  AND created_at < current_date + 1;

Why: date(created_at) wraps the column so the B-tree (ordered by raw created_at) can't be searched; the range leaves the column bare, so it becomes an Index Scan / Bitmap Index Scan. (Alternative: CREATE INDEX ON events (date(created_at)) to index the expression instead.)

Drill 2 — the substring search

A search box filters products by any substring of the name. The B-tree on products(name) is never used. Make the substring search index-backed.

sql

SELECT * FROM products WHERE name ILIKE '%widget%';
Try it first, then read

Solution. A leading wildcard can't use a B-tree; a trigram GIN index can:

CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX ix_products_name_trgm ON products USING gin (name gin_trgm_ops);

Why: a B-tree is ordered left-to-right, so '%widget%' gives it no prefix to seek on. A trigram index breaks each name into 3-character grams, so any substring (and ILIKE) becomes a fast Bitmap Index Scan.

Drill 3 — the N+1 report

A report loops over 500 selected users and, for each, runs one query for their order count — 501 round-trips. Collapse it to one query that returns each user's count.

sql

-- runs once per user id (× 500)
SELECT count(*) FROM orders WHERE user_id = $1;
Try it first, then read

Solution. Hand the whole id set to the database and let it aggregate once:

SELECT u.id, count(o.id) AS orders
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE u.id = ANY($1)          -- $1 = array of the 500 ids
GROUP BY u.id;

Why: one set-based query with a LEFT JOIN (so zero-order users still appear) plus GROUP BY replaces 500 round-trips with one, and lets the planner use an index on orders(user_id). Make sure that FK index exists.

Drill 4 — the deep page

An infinite-scroll feed paginates with OFFSET, and page 800 crawls. There is an index on posts(created_at DESC, id DESC). Make every page cost the same.

sql

SELECT id, created_at FROM posts
ORDER BY created_at DESC, id DESC OFFSET 16000 LIMIT 20;
Try it first, then read

Solution. Keyset: seek past the last row of the previous page instead of counting to it.

SELECT id, created_at FROM posts
WHERE (created_at, id) < ($last_created_at, $last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;

Why: the composite index matches the (created_at, id) row comparison and the ORDER BY, so the Index Scan jumps directly to your page and reads exactly 20 rows — page 800 costs the same as page 1. The tradeoff: you lose random "jump to page N" access, which infinite scroll doesn't need.

Traps — the five ways tuning goes wrong

1. Guessing before measuring. Adding an index off the SQL text without an EXPLAIN (ANALYZE) — you fix a node that was never the bottleneck.
2. Adding an index the planner won't use. An index on a low-selectivity column (status, a boolean) is refused for good reason; a Seq Scan beats random heap fetches for most rows. A partial index on the hot subset is the fix.
3. Optimizing a cheap node. Shaving a 0.3 ms Sort while a 2000 ms Seq Scan sits above it. Always attack the node with the largest actual time or buffers.
4. Changing several things at once. Three changes, one measurement — you can't tell which mattered, and you keep the useless ones forever.
5. SELECT * defeating index-only scans. Pulling every column forces a heap fetch even when a covering index held all you needed. Select only what you use.

★ Review

Summary & self-test

The whole lesson compresses to one habit: tuning is a loop, not a guess — reproduce, measure with EXPLAIN (ANALYZE, BUFFERS), isolate the single hottest node, form one hypothesis, change one thing, re-measure. The anti-patterns are just the hypotheses you reach for most: a non-sargable predicate, a missing index, an over-fetch, a deep offset. Fix the measured cause, not the query text you assume is guilty.
