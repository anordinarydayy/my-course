Triggers & Server-side Logic

A trigger is application logic that lives inside the database and fires automatically on INSERT, UPDATE, or DELETE. Used well, it enforces invariants no client can bypass — an audit trail that can't be forged, a counter that can't drift, all committed in the very same transaction as the change. Used carelessly, it hides behaviour from every engineer who later reads the SQL and pays a per-row cost at scale. This lesson builds both the mechanism and the judgement: how a trigger fires, and when a constraint or generated column is the better tool.

00 Orientation

When logic belongs inside the database

Most of your business logic lives in the application. Sometimes, though, a rule is so tightly bound to the data that it should live with the data — enforced no matter which service, script, or admin console does the write. That is what a trigger gives you: a function the database runs automatically whenever a table changes, inside the same transaction, that no client can forget or skip.

A trigger has two parts. First, a trigger function — a small procedure, almost always written in PL/pgSQL, that returns the special type trigger and can read the special variables NEW (the incoming row) and OLD (the pre-change row). Second, a trigger object that binds that function to a table, a timing, and an event. Here is the smallest useful one — stamp updated_at on every update:

sql

CREATE FUNCTION stamp_updated_at() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at := now();   -- change the row on its way in
  RETURN NEW;
END;
$$;

CREATE TRIGGER products_stamp
BEFORE UPDATE ON products
FOR EACH ROW EXECUTE FUNCTION stamp_updated_at();

Every trigger picks one value from each of three dials, and those choices are the whole vocabulary:

Timing

  • BEFORE — runs before the row is stored; may change NEW or reject the row.
  • AFTER — runs after the row is final; for side effects (audit, outbox).
  • INSTEAD OF — only on views; redirects the write to base tables.

Granularity

  • FOR EACH ROW — fires once per affected row; sees NEW/OLD.
  • FOR EACH STATEMENT — fires once per statement, whatever the row count.
  • Statement triggers can read all changes via transition tables.

Event

  • INSERT — NEW is set, OLD is null.
  • UPDATE — both NEW and OLD are set.
  • DELETE — OLD is set, NEW is null.

When does server-side logic pay? When the rule is a data invariant that must hold across every write path (an audit log that can't be forged, a derived count that can't drift, an outbox row written atomically with the change). When is it dangerous? When it hides ordinary business logic where no reader expects it — a plain INSERT that silently emails a customer, mutates three other tables, and re-fires itself. The rest of the lesson is about telling those two cases apart.

The one-line test

Reach for a trigger when the rule must be true regardless of who writes and must commit atomically with the change. If the rule is really "this one service does this one thing," keep it in that service — a trigger there just buys you invisible surprises.

01 The mechanism

How a trigger actually fires ▸

Everything else in this lesson rests on one picture: the exact order in which things happen when a statement changes a row. The two facts that trip people up are timing (a BEFORE trigger can still change the row; an AFTER trigger cannot) and granularity (row-level fires once per row; statement-level fires once per statement). Step through the whole chain:

Two rules fall straight out of that order. Put row-shaping work in a BEFORE trigger — defaulting a column, normalising a value, rejecting a bad row — because that's the only moment the row can still change. Put side effects in an AFTER trigger — an audit record, an outbox event, a counter bump — because by then the row is committed-to and final, so what you record is real. Assigning NEW in an AFTER trigger is a silent no-op, and it's a classic beginner bug.

Row vs statement is a cost lever

A FOR EACH ROW trigger on a bulk INSERT ... SELECT of a million rows runs your function a million times. If you only need one summary action per statement, a FOR EACH STATEMENT trigger — reading all changes at once through a transition table (REFERENCING NEW TABLE AS ...) — turns a million invocations into one. We'll list this among the traps in s5.

02 First real use

A worked audit trigger ▸

The canonical "logic that belongs in the database" is an audit trail: a record of who changed what, when. Doing it in the app is fragile — every write path must remember to log, and a forgotten one leaves a silent gap. Doing it in an AFTER trigger makes it impossible to bypass and atomic with the change. Here is the pattern in full — a history table, and one function that handles all three events:

sql

CREATE TABLE products_audit (
  audit_id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  product_id bigint,
  op         text        NOT NULL,
  old_price  numeric,
  new_price  numeric,
  changed_at timestamptz NOT NULL DEFAULT now(),
  changed_by text        NOT NULL DEFAULT current_user
);

sql

CREATE FUNCTION audit_products() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    INSERT INTO products_audit(product_id, op, old_price, new_price)
    VALUES (NEW.id, 'INSERT', NULL, NEW.price);
  ELSIF TG_OP = 'UPDATE' THEN
    INSERT INTO products_audit(product_id, op, old_price, new_price)
    VALUES (NEW.id, 'UPDATE', OLD.price, NEW.price);
  ELSIF TG_OP = 'DELETE' THEN
    INSERT INTO products_audit(product_id, op, old_price, new_price)
    VALUES (OLD.id, 'DELETE', OLD.price, NULL);
  END IF;
  RETURN NULL;   -- AFTER trigger: the return value is ignored
END;
$$;

CREATE TRIGGER products_audit_trg
AFTER INSERT OR UPDATE OR DELETE ON products
FOR EACH ROW EXECUTE FUNCTION audit_products();

Watch it work across an insert, an update, and a delete. The point to feel is the last step: the audit rows are written by the same transaction that changed products, so the log can never disagree with reality.

Notice what the trigger did not require: not one line changed in the application, and no code path could route around it. That is the real value of putting this rule in the database — it holds for the ORM, for the ad-hoc psql session, and for the migration script alike. In production you'd usually capture the whole row as jsonb (to_jsonb(OLD) / to_jsonb(NEW)) so one audit table serves every table, but the shape is identical.

Why AFTER, and why same-transaction

AFTER, because you want to audit what actually happened — a BEFORE trigger's row might still be changed by a later BEFORE trigger or rejected by a constraint. Same-transaction, because if the change rolls back, the audit row must roll back with it — otherwise you'd log edits that never happened. This atomic coupling is the exact property the counter in s4 relies on too.

03 Restraint

Declarative first — reach for a trigger last

Triggers are powerful, and that is precisely why the discipline is to try not to use one. Postgres can enforce a great many rules declaratively — you state the rule, the engine enforces it, and it shows up plainly in \d for the next reader. Declarative rules are cheaper, harder to get wrong, and impossible to forget. Exhaust them before writing procedural code.

Generated columns replace derived-value triggers

If a column is a pure function of other columns in the same row, you don't need a BEFORE trigger to maintain it — you need a generated column. Postgres keeps it correct for you:

sql

CREATE TABLE order_lines (
  qty        integer NOT NULL,
  unit_price numeric NOT NULL,
  total      numeric GENERATED ALWAYS AS (qty * unit_price) STORED
);

The STORED form computes the value on write and saves it (indexable, read-cheap). PG 18 adds VIRTUAL generated columns, computed on read (no storage, always fresh — the new default when you don't say which). Either way the engine owns correctness: there is no function to test, no timing to get wrong, and no way to bypass it. That is a strictly better tool than a trigger for same-row derived values.

Constraints replace validation triggers

A rule like "price must be non-negative" or "sku is unique" is a CHECK or a UNIQUE constraint, not a trigger. Constraints are declarative, self-documenting, and the planner even knows about them. When a check must be deferred to the end of a transaction — say a running balance that may dip mid-transaction but must be valid at commit — that is the one place a constraint trigger earns its keep:

sql

CREATE CONSTRAINT TRIGGER check_balance
AFTER INSERT OR UPDATE ON ledger
DEFERRABLE INITIALLY DEFERRED
FOR EACH ROW EXECUTE FUNCTION assert_balance_nonneg();

So what is genuinely left for an ordinary trigger? Rules that span rows or tables and must be atomic with the change: an audit trail (s2), a maintained cross-table counter (s4), a transactional outbox row, a LISTEN/NOTIFY ping. Those cannot be expressed as a single-row generated column or a constraint — they need procedural code.

The honest costs of a trigger

Before you write one, price it in. Hidden logic: a reader of an INSERT cannot see the trigger fire — behaviour lives somewhere they won't look. Per-row cost: FOR EACH ROW multiplies by the row count. Ordering: multiple triggers of the same timing fire in alphabetical name order, not creation order. Testing: the logic is now split between app and database. Recursion: a trigger that writes its own table re-fires itself. SECURITY DEFINER: a trigger function marked so runs with the owner's privileges — pin a safe search_path or you've opened a privilege-escalation hole.

04 Worked problem

Maintain a counter and an audit trail, correctly ▸

Now the full exercise, the kind an interviewer or a real backlog hands you. It ties together everything above and revisits the count-cache idea from L07 — but this time we make it drift-proof.

1 · The schema

A forum. Threads have many replies. Reading "how many replies?" on every thread listing is hot, so we keep a denormalised reply_count on threads rather than counting rows each time.

sql

CREATE TABLE threads (
  id          bigint  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title       text    NOT NULL,
  reply_count integer NOT NULL DEFAULT 0
);

CREATE TABLE replies (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  thread_id bigint NOT NULL REFERENCES threads(id) ON DELETE CASCADE,
  body      text   NOT NULL
);

2 · The task

Keep threads.reply_count exactly equal to the number of live rows in replies for that thread — cheap to read, and correct no matter who inserts or deletes a reply — and keep an audit trail of reply activity. Both must be impossible to bypass and impossible to leave inconsistent.

3 · The naive attempt (and why it fails)

The instinct is to have the application do both writes:

sql

-- application code, two separate statements
INSERT INTO replies(thread_id, body) VALUES (1, 'nice post');
UPDATE threads SET reply_count = reply_count + 1 WHERE id = 1;

This drifts, three ways. It is not atomic against forgetting: the moment a second write path appears — a bulk import, an admin "delete reply" button, a data-fix script — someone omits the UPDATE and the count is wrong forever. It is not atomic against failure unless both run in one transaction, and even in a transaction it depends on the developer remembering every time. And computing it the other way — SELECT count(*) on every read — is O(n) over a hot table, which is the very cost we set out to avoid. The rule "the count tracks the children" belongs to the data, not to one caller.

4 · The fix: a trigger that owns the invariant

Move the maintenance into an AFTER trigger on replies, so every insert and delete — from any client — updates the count in the same transaction:

sql

CREATE FUNCTION bump_reply_count() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    UPDATE threads SET reply_count = reply_count + 1
    WHERE id = NEW.thread_id;
  ELSIF TG_OP = 'DELETE' THEN
    UPDATE threads SET reply_count = reply_count - 1
    WHERE id = OLD.thread_id;
  END IF;
  RETURN NULL;   -- AFTER row trigger
END;
$$;

CREATE TRIGGER replies_count_trg
AFTER INSERT OR DELETE ON replies
FOR EACH ROW EXECUTE FUNCTION bump_reply_count();

Trace the guarantee in the diagram: every insert or delete moves the count atomically, in lockstep with the child row.

5 · Why it's better

Reads are now O(1): a single column on the thread row, not an aggregate over its replies. The difference is stark in the plan. Reading the cache is one index lookup:

explain (illustrative)

Index Scan using threads_pkey on threads
    (cost=0.29..8.30 rows=1 width=4) (actual time=0.017..0.018 rows=1 loops=1)
  Index Cond: (id = 1)
Execution Time: 0.03 ms

while recomputing it from scratch must scan and aggregate every reply on the thread:

explain (illustrative)

Aggregate  (cost=98.66..98.67 rows=1 width=8)
           (actual time=1.82..1.82 rows=1 loops=1)
  ->  Index Scan using replies_thread_id_idx on replies
          (cost=0.43..87.10 rows=4623 width=0)
          (actual time=0.021..1.41 rows=4623 loops=1)
        Index Cond: (thread_id = 1)
Execution Time: 1.86 ms

And crucially, the cache is correct by construction: because the +1 commits in the same transaction as the reply, there is no window in which a reply exists without its increment. A crash or ROLLBACK undoes both together. That is the property the naive app-side version could never guarantee.

6 · Narrate it

"I keep a denormalised reply_count on threads so listing pages read a column instead of aggregating. To stop it drifting, I don't trust the application to maintain it — I attach an AFTER INSERT OR DELETE row trigger on replies that adjusts the parent's count in the same transaction. Because the child write and the count change commit atomically, the cache always equals COUNT(*); a rollback rolls back both. The one cost I accept knowingly is contention: every reply to the same thread takes a row lock on that thread while it updates the count, so a single very hot thread serialises its writes. For most workloads that's fine; if it weren't, I'd batch with a statement-level trigger and transition tables, or move to a periodic reconciliation."

05 Drills & traps

Graded drills

Attempt each before opening the solution. They climb in difficulty and hit the mistakes that actually bite in production.

Drill 1 — the AFTER that does nothing (warm-up)

A colleague wants updated_at refreshed on every update to products. They wrote a trigger function that does NEW.updated_at := now(); RETURN NEW; but bound it AFTER UPDATE — and the column never changes. Why, and what's the one-word fix?

Try it first, then read

An AFTER trigger runs after the row is already written, so assigning NEW is a no-op. Only a BEFORE trigger can still change the row:

CREATE TRIGGER products_stamp
BEFORE UPDATE ON products   -- BEFORE, not AFTER
FOR EACH ROW EXECUTE FUNCTION stamp_updated_at();

Why: shaping the row is only possible before it's stored — that's the whole meaning of BEFORE vs AFTER.

Drill 2 — the trigger that never stops (recursion)

Someone adds an AFTER UPDATE trigger on threads that recomputes a field and writes it back into threads. Each write re-fires the trigger; the statement errors out with a stack-depth limit. Make it safe.

Try it first, then read

A trigger that writes its own table re-fires itself. Gate the write so it stops once nothing actually changes — or don't fire at all when the watched column is unchanged, via a WHEN clause:

CREATE TRIGGER threads_recalc
AFTER UPDATE ON threads
FOR EACH ROW WHEN (NEW.title IS DISTINCT FROM OLD.title)
EXECUTE FUNCTION recalc_threads();

Inside the function you can also guard with IF NEW.x IS DISTINCT FROM OLD.x THEN ... END IF;, or check pg_trigger_depth() to skip nested firings. Why: recursion halts the instant a re-fire has no effect, so the chain terminates.

Drill 3 — the reply that changes threads (correctness)

Your bump_reply_count from s4 handles INSERT and DELETE. A moderator runs UPDATE replies SET thread_id = 9 WHERE id = 101 to move a reply. Both threads' counts are now wrong. Extend the trigger.

Try it first, then read

A moved child must decrement the old parent and increment the new one — and you must add UPDATE to the trigger's event list:

  ELSIF TG_OP = 'UPDATE' AND NEW.thread_id IS DISTINCT FROM OLD.thread_id THEN
    UPDATE threads SET reply_count = reply_count - 1 WHERE id = OLD.thread_id;
    UPDATE threads SET reply_count = reply_count + 1 WHERE id = NEW.thread_id;
CREATE TRIGGER replies_count_trg
AFTER INSERT OR UPDATE OR DELETE ON replies
FOR EACH ROW EXECUTE FUNCTION bump_reply_count();

Why: the IS DISTINCT FROM guard skips the two writes when thread_id didn't move, so ordinary edits stay cheap. This is exactly the edge case denormalised counters are infamous for missing.

Drill 4 — the un-writable view (stretch)

You expose a view active_products (products where archived = false, joined to their category). The app tries INSERT INTO active_products ... and gets "cannot insert into view." Make the view writable without letting the app touch base tables directly.

Try it first, then read

Complex views aren't auto-updatable, but an INSTEAD OF trigger translates writes on the view into writes on the base table:

CREATE FUNCTION ins_active_products() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO products(id, price, archived)
  VALUES (NEW.id, NEW.price, false);
  RETURN NEW;
END;
$$;

CREATE TRIGGER active_products_ins
INSTEAD OF INSERT ON active_products
FOR EACH ROW EXECUTE FUNCTION ins_active_products();

Why: INSTEAD OF triggers exist only on views; they replace the impossible direct write with an explicit mapping to the underlying tables. (A simple single-table filtered view is auto-updatable and needs none of this.)

Traps to keep in your head

  • Recursion. A trigger writing its own table re-fires; guard with IS DISTINCT FROM, a WHEN clause, or pg_trigger_depth().
  • Hidden logic. A plain INSERT shows no sign of a trigger. Name triggers clearly and document their side effects, or the next engineer debugs a ghost.
  • Per-row cost at scale. FOR EACH ROW fires once per row — a million-row load pays a million invocations. For bulk work, a FOR EACH STATEMENT trigger with transition tables runs once.
  • Firing order. Triggers of the same timing fire in alphabetical name order, not creation order. Never rely on accidental ordering.
  • Declarative first. A CHECK, UNIQUE, foreign key, or GENERATED column is engine-enforced, visible, and cheaper. Use a trigger only for cross-row/cross-table effects.
  • BEFORE returning NULL drops the row silently — an easy way to lose data by accident. AFTER can't change the row — assigning NEW there does nothing.
  • SECURITY DEFINER runs the function as its owner; set an explicit search_path or invite privilege escalation.
★ Review

Summary & self-test

One idea to carry out: a trigger moves a rule into the database so it fires automatically and commits atomically with the change — priceless for invariants that must hold across every write path, but a liability when it hides ordinary logic. Prove you can't do it declaratively first; if you can't, keep the trigger small, atomic, and named for what it does.
