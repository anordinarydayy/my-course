How an Index Works

An index is the single biggest performance lever in a database: it turns "read every page to find one row" into a handful of page hops. This lesson opens the B-tree, follows a lookup from the root down to the actual heap row, and shows the two things every engineer eventually gets bitten by — why an index sometimes gets skipped, and what every index quietly costs you on every write.

Original study notes. Written from scratch for engineers who want database depth that pays off in interviews and in production. Examples target PostgreSQL (PG 17/18) and every plan node is real. 00 The problem

Finding a row without reading them all

Start with how a table is actually stored. In PostgreSQL a table is a heap: a set of fixed-size 8 KB pages, and rows are packed into whatever page had room when they were written. The heap is unordered — there is no promise that row 5 sits near row 6, or that anything is sorted by anything. It is a bag of pages. That is deliberate: it makes inserts cheap (drop the row on a page with free space) and keeps the storage simple.

The cost of that simplicity shows up the instant you ask a question. Run WHERE id = 84217 on a table with no index, and Postgres has no idea which page holds that row. Its only option is a Sequential Scan: read every page, top to bottom, and check each row against the filter. On a million-row table that is thousands of pages read just to return a single row.

sql

EXPLAIN ANALYZE SELECT * FROM orders WHERE id = 84217;

illustrative · PG18 EXPLAIN ANALYZE

Seq Scan on orders  (cost=0.00..18584.00 rows=1 width=68)
                    (actual time=0.41..92.30 rows=1 loops=1)
  Filter: (id = 84217)
  Rows Removed by Filter: 999999
  Buffers: shared hit=8334
Planning Time: 0.075 ms
Execution Time: 92.34 ms

Read that plan and the whole problem is visible. Seq Scan means it read the entire heap. Rows Removed by Filter: 999999 is the confession: it examined a million rows to keep one. Buffers: shared hit=8334 is the entire table — 8,334 pages — touched to answer a question about a single row. (In PG 18 those Buffers lines appear in EXPLAIN ANALYZE by default; hit means the page was already in cache, read means it came from disk.)

An index is the fix, and the mental model is simple: it is a separate, ordered data structure that sits beside the heap and lets Postgres go straight to the rows it wants instead of walking the whole thing. The heap stays an unordered bag; the index is the sorted directory that points into it. Building one is a single statement:

sql

CREATE INDEX ON orders (id);
The one-line intuition

The heap is the book; the index is the book's index at the back. Without it, "find every mention of Codd" means reading every page. With it, you flip to the sorted index, find the entry, and jump straight to the pages listed. You are not searching the text — you are searching a small, ordered structure that points into the text.

01 The structure

The B-tree: a lookup in a handful of hops ▸

The default PostgreSQL index — the one you get from CREATE INDEX with no type specified — is a B-tree (technically a B+-tree). It is a balanced tree of 8 KB pages arranged in three roles: a single root page at the top, one or more layers of internal pages in the middle, and the leaf pages at the bottom. Every internal page holds sorted separator keys and pointers to child pages; a search descends by comparing your key against those separators and following the one pointer that can possibly contain it.

Because each page holds hundreds of keys, the tree is extraordinarily shallow. With a fan-out of, say, 200 children per page, one level addresses 200 rows, two levels 40,000, three levels 8 million, four levels 1.6 billion. That is the whole magic: a lookup is O(log n), and for realistic tables that logarithm is just 4 or 5 page hops — a billion rows resolved in a handful of reads instead of millions. Step through a search for id = 57:

Two properties of the leaves matter for the rest of your career. First, a leaf entry is not the row — it is the key plus a TID (a tuple identifier, the ctid: a page number and an item number that pins the exact physical row in the heap). Second, the leaves are sorted and linked into a doubly-linked list. That second fact is why a B-tree gives you range queries and ordering essentially for free: to serve WHERE id BETWEEN 40 AND 80 or ORDER BY id, Postgres finds the first leaf and then just walks the chain, already in order — no separate sort required.

Why "balanced" is the whole point

A B-tree stays balanced no matter the insert order — every leaf sits at the same depth, so every lookup costs the same small number of hops. That worst-case guarantee is what makes it trustworthy at scale: there is no pathological input that turns it into a linked list, the way a naive binary search tree can degrade. Same shape, same cost, whether the key is the first row or the billionth.

02 The double read

Index scan, then heap fetch

Here is the subtlety the diagram hinted at: for most queries, using an index is a two-step, double read. The index tells you where the row is, but not what it contains. So Postgres does an Index Scan: descend the B-tree to the matching leaves (a few sequential-ish page reads), collect the TIDs, and then — for each TID — jump into the heap to fetch the actual row. That second step is random I/O: the matching rows can live on scattered pages, so it is a series of unpredictable jumps, not a smooth sweep.

sql

CREATE INDEX ON orders (customer_id);

EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 4217;

illustrative · PG18

Index Scan using orders_customer_id_idx on orders
        (cost=0.42..38.65 rows=12 width=68)
        (actual time=0.028..0.061 rows=11 loops=1)
  Index Cond: (customer_id = 4217)
  Buffers: shared hit=14
Planning Time: 0.093 ms
Execution Time: 0.079 ms

Compare that to the Seq Scan from section 00: 14 pages instead of 8,334, and under a tenth of a millisecond instead of 92. The Index Cond line is the tell — that is the predicate the index itself resolved, before touching the heap at all. Those 14 buffers break down as a few index pages to walk the tree, plus a heap page per matching row for the fetch step. When only a handful of rows match, the random fetches are cheap and the index is a massive win.

That last clause is the hinge of the entire indexing chapter: the index wins when few rows match. Because sorted leaves make ranges and ordering cheap, a B-tree also accelerates <, >, BETWEEN, ORDER BY, and prefix matches like LIKE 'abc%' (for text columns, that prefix trick needs the C collation or a text_pattern_ops index) — anything that maps to "a contiguous run of leaves." What it cannot help is a predicate that matches a large fraction of the table, because then the random heap fetches pile up faster than a plain sequential sweep would have cost. We will make that crossover concrete in section 04.

Index Scan is really two operations

Whenever you read Index Scan, picture two phases: (1) walk the B-tree to find leaves (cheap, ordered), then (2) a random heap fetch per matching row (the part that scales with how many rows matched). Keep them separate in your head — nearly every indexing decision, from covering indexes to selectivity, is really a decision about how to shrink or eliminate that second phase.

03 Skipping the heap

Index-only scans & the visibility map ▸

If the second phase — the random heap fetch — is the expensive part, the natural question is: can we skip it? Sometimes, yes. If the index already carries every column the query needs, then the leaf entry is the answer, and there is nothing left to fetch from the heap. Postgres calls this an Index Only Scan, and it is one of the highest-leverage tricks in the whole toolkit. You enable it by making the index cover the query — often with INCLUDE, which bolts non-key payload columns onto the leaves:

sql

-- carry `total` in the leaves so a lookup by customer_id needs no heap
CREATE INDEX ON orders (customer_id) INCLUDE (total);

SELECT total FROM orders WHERE customer_id = 4217;

But there is a catch, and it is the reason this topic trips people up. PostgreSQL uses MVCC: a row can have multiple versions, and whether a given tuple is visible to your transaction is recorded in the heap, not in the index. So even when the index has all the data, Postgres must still be sure the row is visible — and normally that check requires reading the heap, which would defeat the whole point. The escape hatch is the visibility map (VM): a per-page all-visible bit that, when set, promises "every tuple on this page is visible to everyone." If the page is marked all-visible, Postgres trusts the bit and skips the heap. If not, it falls back to a heap fetch just to confirm visibility. The VM is kept current by VACUUM. Watch both branches:

Here are the two plans side by side. After a fresh VACUUM the pages are all-visible and the heap is never touched:

illustrative · after VACUUM

Index Only Scan using orders_customer_id_total_idx on orders
        (cost=0.42..8.53 rows=12 width=8)
        (actual time=0.020..0.030 rows=11 loops=1)
  Index Cond: (customer_id = 4217)
  Heap Fetches: 0
  Buffers: shared hit=4
Execution Time: 0.041 ms

But run the same query right after a burst of writes, before autovacuum catches up, and the bit is unset — so it still reports Index Only Scan, yet quietly pays for heap fetches:

illustrative · not yet vacuumed

Index Only Scan using orders_customer_id_total_idx on orders
        (cost=0.42..38.65 rows=12 width=8)
        (actual time=0.030..0.088 rows=11 loops=1)
  Index Cond: (customer_id = 4217)
  Heap Fetches: 11
  Buffers: shared hit=15
Execution Time: 0.104 ms

Same query, same index — the only difference is whether VACUUM had marked those pages all-visible. That is why Heap Fetches is the number to watch: a high count means your index-only scan is secretly a plain index scan. Two practical corollaries: keep the table adequately vacuumed (Lesson 29), and never write SELECT * when you want index-only — the moment the query asks for a column the index does not carry, Postgres must visit the heap, and the optimization is gone.

The visibility map ties indexing to VACUUM

This is the first place two phases of the course meet. An index-only scan is a read optimization, but it only fires when VACUUM — a maintenance job — has recently set the all-visible bits. On an append-mostly table the bits stay set and index-only scans hum along; on a hot, heavily-updated table they flip off constantly and your fast plan silently degrades. We return to exactly this in Lesson 29.

04 The bill

What an index costs ▸

Indexes are not free, and understanding the bill is what separates "add an index" from "add the right index." There are three costs, and every one of them is a reason not to reach for another index reflexively.

Write amplification. An index is a second data structure describing the same rows, so it has to be kept in sync. Every INSERT must add a leaf entry to every index on the table, and an UPDATE that changes an indexed column must insert new entries for the new row version (a plain DELETE, by contrast, only stamps the heap tuple — its now-dead index entries are reclaimed later by VACUUM). One logical insert becomes one heap write plus N index writes. Watch a single insert fan out:

Disk and memory. Each index is a real structure on disk, often a meaningful fraction of the table's own size, and its hot pages compete for the same shared-buffer cache the table wants. A table with eight indexes can easily be more index than data.

Selectivity — the counter-intuitive one. An index only helps when the predicate is selective: when it matches a small slice of the table. If a predicate matches, say, 40% of rows, using the index means doing hundreds of thousands of random heap fetches — and random reads are far slower per page than a smooth sequential sweep. Past a crossover point (roughly a single-digit percentage of the table, depending on row width and correlation) a plain Seq Scan is genuinely faster, and the planner knows it. So it ignores the index on purpose:

sql

-- index exists on status, yet ~40% of rows are 'shipped'
EXPLAIN SELECT * FROM orders WHERE status = 'shipped';

illustrative

Seq Scan on orders  (cost=0.00..18584.00 rows=400000 width=68)
  Filter: (status = 'shipped')

That is not a bug and not a missing index — it is the planner correctly costing 400,000 random fetches against one sequential pass and choosing the sweep. An unselective index is worse than no index for that query, and forcing it would only make things slower. (This is also why PostgreSQL deliberately has no query hints: you fix the inputs — statistics and indexes — not the plan.)

One important relief valve on the write cost is the HOT update (Heap-Only Tuple). When an UPDATE changes no indexed column, Postgres can place the new row version on the same heap page and chain it off the old one, so the indexes still point at the old line pointer and need no update at all. That is why "which columns are indexed" quietly governs your update cost — and why blindly indexing a frequently-changing column can be expensive twice over.

Every index is a bet

Adding an index is a wager: you pay a fixed tax on every write and some disk, betting it will earn that back on reads. The bet pays off when the indexed column is selective and appears in your WHERE, JOIN, or ORDER BY clauses often. It loses when the column is low-cardinality, rarely queried, or frequently updated. "More indexes" is not a strategy — the right small set is.

05 Reason about it

Reasoning your way to the right index

You now have every piece needed to answer the real question — not "should I add an index?" but "will this index earn its keep on this query?" Walk a candidate through four questions, in order, and the answer usually falls out.

  • Does the query filter, join, or sort on the column? Indexes accelerate exactly the columns that appear in WHERE, JOIN ... ON, and ORDER BY. If a column never shows up there, an index on it does nothing but cost you writes. (Unindexed join columns are a classic slow-query cause — the join side has to scan.)
  • Is the predicate selective? High cardinality — a column with many distinct values, like email or user_id — means any given value matches few rows, and the index shines. Low cardinality — a boolean, a status with three values — means each value matches a huge slice, and the planner will skip the index anyway. Index the needle-in-a-haystack columns.
  • Is the table big enough to matter? On a 200-row lookup table, a Seq Scan is a single page read; an index just adds write cost for no benefit. Indexes earn their keep at scale, where "read every page" becomes thousands of reads.
  • Can I afford the write tax? On a write-heavy table, every index slows every insert and update. Weigh the read you are speeding up against the writes you are taxing. When in doubt, add the index, EXPLAIN ANALYZE a representative query, and confirm the planner actually uses it — measure, do not guess.

Run the account-lookup example through it. A query is WHERE email = $1 on a ten-million-row users table, run on every login. Filter column? Yes, in WHERE. Selective? Extremely — email is unique. Big table? Yes. Write cost acceptable? Users log in far more than they change email, so an index on email is an easy yes. Now flip one detail: the app queries WHERE lower(email) = lower($1) for case-insensitivity. A plain index on email will not be used — wrapping the column in a function defeats it — so you would index the expression instead: CREATE INDEX ON users (lower(email)). That single wrinkle is a preview of the anti-patterns and index-shaping tools the next few lessons formalize.

★ Review

Summary & self-test

The whole lesson compresses to one idea: an index is a separate, ordered B-tree that lets Postgres jump to a few rows instead of scanning every page — a huge win on selective reads, paid for by a tax on every write. Everything else is a refinement of that trade: how the tree finds rows, when it can skip the heap, and when the planner rightly declines to use it.
