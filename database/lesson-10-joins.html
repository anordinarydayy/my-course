Joins

A join is the relational model's engine: it takes two tables and builds a new one by matching rows that satisfy a condition. Master three layers and joins stop being scary — the types (who is kept), the mental model (a join can multiply rows), and the physical algorithms Postgres uses to run them. Then we work a real problem end to end and drill the traps interviewers love.

00 The core idea

A join matches rows by a condition

Strip away the syntax and a join is one sentence: take every row of table a, pair it with every row of table b, and keep the pairs where a condition is true. That condition is the join predicate, and it lives in the ON clause. The result is not a view into the originals — it is a brand-new relation, a table of combined rows you can filter, group, order, or join again.

sql

SELECT c.name, o.amount
FROM   customers c
JOIN   orders    o  ON o.customer_id = c.id;   -- the predicate

Read that as: for each customer, find the orders whose customer_id equals that customer's id, and emit one row per match. The predicate is almost always an equality on a key (an equi-join), because that is how foreign keys wire tables together — but it can be any boolean expression (>, a range, a function). The word JOIN on its own means INNER JOIN; we will meet the other flavors in the next section.

The one thing to never forget: a join can multiply rows

If one customer has three orders, that customer's row appears three times in the result — once per matching order. This is a one-to-many join, and it is completely correct. But it is also the source of the single most common SQL bug: you join to the “many” side and then sum or count a column from the “one” side, and every value gets counted once per child row. We give this fan-out its own drill in §05 — for now, just carve it into your brain: a join changes the grain of your data.

Because the result is itself a relation, joins compose. You can join three, four, ten tables in one query, each JOIN narrowing or widening the working set. The planner is free to reorder them for cost — you state which tables relate and how; it decides the order and the algorithm. Keep that separation in mind: the rest of this lesson is really two questions, “which rows survive?” (the type) and “how are they matched?” (the algorithm).

01 Who gets kept

The join types ▸

All joins pair rows on a predicate; the type decides what happens to rows that find no partner. There are five, and the whole family fits in one table of two: users and orders. Watch which result rows appear as you switch types — matched pairs turn green; rows kept but padded with NULLs turn garnet.

Here is the whole family, ranked by how much they keep:

INNER

  • Only rows with a match on both sides.
  • Unmatched rows on either side vanish.
  • The default: JOIN = INNER JOIN.

LEFT / RIGHT OUTER

  • LEFT: keep all left rows; missing right side becomes NULL.
  • RIGHT: the mirror — keep all right rows.
  • “OUTER” is optional noise; LEFT JOIN is enough.

FULL / CROSS

  • FULL: keep everything from both; pad both sides with NULL.
  • CROSS: every pair — the Cartesian product, no ON.
  • CROSS of 1k×1k rows = a million rows.

sql

FROM a INNER JOIN b ON a.k = b.k   -- only matching pairs
FROM a LEFT  JOIN b ON a.k = b.k   -- all a; unmatched b → NULL
FROM a RIGHT JOIN b ON a.k = b.k   -- all b; unmatched a → NULL
FROM a FULL  JOIN b ON a.k = b.k   -- all a and all b
FROM a CROSS JOIN b                -- every pair (no ON)

Two practical notes. First, LEFT and RIGHT are the same operation with the tables swapped, so in practice everyone writes LEFT and puts the “must-keep-all” table on the left — it reads top-to-bottom and never confuses you. Second, a CROSS JOIN is rarely what you want on purpose; when you see a query returning suspiciously many rows, the first suspect is an accidental cross join from a forgotten or mistyped ON.

02 Three special shapes

Semi-joins, anti-joins & self-joins

Three join shapes come up constantly but hide behind other syntax. Naming them makes half of “which query do I write?” disappear.

Semi-join — “does a match exist?”

A semi-join returns rows from the left table that have at least one match on the right — but only the left columns, and each left row at most once. You write it with EXISTS or IN. This is the crucial contrast with an inner join: an inner join to the many side multiplies rows; a semi-join does not. If a user has 50 orders, an inner join emits 50 rows for that user; WHERE EXISTS (…) emits exactly one.

Anti-join — “prove no match exists”

An anti-join is the negation: left rows with no match on the right. You write it with NOT EXISTS. It is how you answer “customers who never ordered,” “products never sold,” “users with no login.”

sql

-- SEMI-join: users who have at least one order (no row multiplication)
SELECT u.* FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

-- ANTI-join: users with no order at all
SELECT u.* FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
Prefer NOT EXISTS over NOT IN for anti-joins

NOT IN (SELECT col …) has a landmine: if any value of col is NULL, the whole predicate collapses to UNKNOWN and the query returns zero rows — silently. It is the NULL = UNKNOWN rule biting: x NOT IN (1, NULL) can never be proven true. NOT EXISTS has no such trap and the planner turns it into a clean anti-join. Make it your default.

Self-join — a table joined to itself

Nothing says the two sides of a join must be different tables. A self-join joins a table to itself under two aliases, to relate rows within the same set — the textbook case is an employees table where manager_id points back at employees.id. Give the table two names and it behaves like two tables:

sql

-- SELF-join: pair each employee with their manager
SELECT e.name AS employee, m.name AS manager
FROM   employees e
JOIN   employees m ON m.id = e.manager_id;

The alias is doing all the work: e is “the employee,” m is “the same table, viewed as the manager.” Use an INNER JOIN and employees with no manager (the CEO) drop out; use a LEFT JOIN and they stay with a NULL manager. Self-joins power hierarchies, “find pairs in the same group,” and comparisons of a row to its neighbors.

03 Under the hood

How Postgres actually joins ▸

The join type is what you asked for; the join algorithm is how Postgres delivers it. There are three, and knowing them is the difference between reading an EXPLAIN plan with understanding and staring at it. Crucially, you never choose the algorithm — the planner does, per query, by estimated cost. Step through the three mechanics:

Nested Loop

  • For each outer row, scan the inner for matches.
  • Great when the inner has an index on the join key.
  • Memoize (PG14+) caches repeated inner lookups.
  • Best for a small outer / selective query.

Hash Join

  • Build a hash table on the smaller input.
  • Probe it with every row of the larger input.
  • Best for big equi-joins that fit in work_mem.
  • Equality only — no help for range predicates.

Merge Join

  • Sort both inputs on the key, then zip them together.
  • Great when inputs already arrive sorted (an index).
  • Scales to huge inputs without a big hash.
  • Pays the sort cost if the data isn't pre-sorted.

The planner weighs these using its statistics: estimated row counts on each side, whether the rows are already sorted (an index it can walk in order), and how much memory (work_mem) a hash or sort may use. A tiny lookup joined to an indexed table becomes a Nested Loop with an Index Scan; two big unsorted tables become a Hash Join; two already-sorted streams become a Merge Join. This is exactly why your job when a join is slow is not to “pick a better join” but to give the planner a better option — usually an index on the join key, or fresher statistics.

This connects straight to indexing

An index on the foreign-key column (say orders(customer_id)) is what unlocks the cheap Nested Loop / Index Scan path for selective joins. Without it, Postgres often has no choice but to Seq Scan the whole child table and hash it. Missing FK indexes are one of the most common causes of a mysteriously slow join — and one of the easiest fixes. You will meet the EXPLAIN details in the worked problem next.

04 Worked problem

Worked: each customer's total spend ▸

Time to put it together on a problem that trips up a huge fraction of candidates precisely because it looks trivial. We will follow the exact interview shape: schema, task, a wrong first attempt and why it's wrong, the correct query, the index that helps, and how to say the answer out loud.

1 · The schema

sql

CREATE TABLE customers (
  id   bigint PRIMARY KEY,
  name text NOT NULL
);

CREATE TABLE orders (
  id          bigint PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers(id),
  amount      numeric(10,2) NOT NULL
);

2 · The task

For every customer, report their total spend — and keep customers who have never ordered, showing them as 0.

3 · The naive attempt — and why it's wrong

sql

-- WRONG: silently drops customers who never ordered
SELECT c.name, sum(o.amount) AS total
FROM   customers c
JOIN   orders    o ON o.customer_id = c.id
GROUP BY c.name;

Two bugs, one fatal. The fatal one: a plain JOIN is an inner join, so a customer with no matching order produces no rows at all and disappears from the result. The task explicitly wanted those customers, shown as 0 — the naive query answers a different question (“spend of customers who ordered”). The second, quieter bug: GROUP BY c.name merges two different customers who happen to share a name. Group by the primary key instead. Here is the illustrative plan on a full-table run:

explain (illustrative)

-- EXPLAIN — plan shape, numbers vary
HashAggregate  (cost=41.9..44.4 rows=3 width=40)
  Group Key: c.name
  ->  Hash Join  (cost=1.07..40.4 rows=300 width=36)
        Hash Cond: (o.customer_id = c.id)
        ->  Seq Scan on orders o     (cost=0.00..29.0 rows=300 width=14)
        ->  Hash  (cost=1.03..1.03 rows=3 width=36)
              ->  Seq Scan on customers c  (cost=0.00..1.03 rows=3 width=36)

Read it bottom-up: Postgres scans the small customers table, builds a hash on c.id, then scans orders and probes the hash — a textbook Hash Join for two unindexed inputs — and finally aggregates. Correct as a plan; the query is still answering the wrong question because of the inner join.

4 · The correct query

sql

SELECT c.id, c.name,
       coalesce(sum(o.amount), 0) AS total
FROM   customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY total DESC;

Three fixes, each earning its place. LEFT JOIN keeps every customer, matched or not. For an unmatched customer the orders columns are all NULL, and sum() over a group of nothing-but-NULL returns NULL (aggregates skip NULLs) — not 0 — so coalesce(sum(...), 0) converts that NULL to the 0 the task demanded. And GROUP BY c.id, c.name groups by identity, immune to duplicate names. Step through exactly how the rows flow:

5 · The index that helps + the improved plan

The foreign-key column has no index by default, so joins and per-customer lookups fall back to scanning all of orders. Add one:

sql

CREATE INDEX ON orders (customer_id);

For the whole-table aggregate, the Hash Join over two sequential scans is often still the cheapest plan — the index doesn't change that. Where it pays off is a selective query — a report for a handful of customers. Now the planner can drive a Nested Loop from the small customer set straight into an Index Scan on orders, touching only the matching rows instead of the whole table:

explain (illustrative)

-- after the index, for WHERE c.id = ANY('{1,2}') — plan shape only
GroupAggregate  (cost=0.58..16.8 rows=2 width=40)
  Group Key: c.id, c.name
  ->  Nested Loop Left Join  (cost=0.58..16.7 rows=4 width=36)
        ->  Index Scan using customers_pkey on customers c
              Index Cond: (id = ANY ('{1,2}'::bigint[]))
        ->  Index Scan using orders_customer_id_idx on orders o
              Index Cond: (customer_id = c.id)

Both scans are now Index Scans, the join is a Nested Loop Left Join (the Left preserves the zero-order customers), and because the outer Index Scan already delivers customers ordered by id, Postgres can use a streaming GroupAggregate instead of building a hash. No sequential scan of orders in sight.

6 · Narrate it

Here is how you would say it aloud in an interview: “The trap is that a plain join is an inner join, so customers with no orders vanish — but the task wants them shown as zero. I use a LEFT JOIN from customers to orders to keep every customer, group by the customer's primary key, and sum the amount. Since sum over a customer with no orders returns NULL, not zero, I wrap it in coalesce(sum(amount), 0). To make it fast for per-customer reports I'd add an index on orders(customer_id), which lets the planner switch from hashing the whole orders table to a nested-loop index scan that only touches the rows it needs.” That sentence hits the type, the NULL subtlety, and the index — everything the question is testing.

05 Practice

Graded drills & traps

Four drills, easy to hard. Write each yourself first, then open the answer. Assume the tables from §04 plus a users, a logins(user_id, created_at), an order_items(id, order_id, qty), and an employees(id, name, salary, manager_id).

Drill 1 — inner vs left

Report every user with the timestamp of their latest login, including users who have never logged in (show NULL for them).

Try it first, then read

sql

SELECT u.id, u.name, max(l.created_at) AS last_login
FROM   users u
LEFT JOIN logins l ON l.user_id = u.id
GROUP BY u.id, u.name;

Why: LEFT JOIN keeps never-logged-in users (their last_login is NULL); a plain JOIN would silently drop them — the exact bug from the worked problem.

Drill 2 — the fan-out double-count

Someone wrote SELECT sum(o.amount) FROM orders o JOIN order_items i ON i.order_id = o.id; to get total revenue, and the number is way too high. Explain why, and give a correct total plus a correct per-order item count.

Try it first, then read

Why it's wrong: joining orders to its order_items multiplies each order row by its number of items, so sum(o.amount) counts every order's amount once per item — a classic fan-out double-count. Fix by summing at the right grain (don't join to get the total), and aggregate items in a subquery when you need both:

sql

-- correct revenue: the amount lives at the order grain — don't fan it out
SELECT sum(amount) AS revenue FROM orders;

-- both figures at once: pre-aggregate items, then join one row per order
SELECT o.id, o.amount, coalesce(i.n_items, 0) AS n_items
FROM   orders o
LEFT JOIN (
  SELECT order_id, count(*) AS n_items
  FROM   order_items
  GROUP BY order_id
) i ON i.order_id = o.id;

Why: the subquery collapses items to one row per order before the join, so the join no longer changes the order grain and nothing is double-counted.

Drill 3 — anti-join

List every customer who has never placed an order.

Try it first, then read

sql

SELECT c.id, c.name
FROM   customers c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.customer_id = c.id
);

Why: NOT EXISTS is a true anti-join and is NULL-safe; NOT IN (SELECT customer_id FROM orders) would return nothing if any customer_id were NULL. (A LEFT JOIN … WHERE o.id IS NULL also works and is a fine alternative.)

Drill 4 — self-join

Find every employee who earns more than their own manager, showing both salaries.

Try it first, then read

sql

SELECT e.name AS employee, e.salary,
       m.name AS manager,  m.salary AS mgr_salary
FROM   employees e
JOIN   employees m ON m.id = e.manager_id
WHERE e.salary > m.salary;

Why: alias the one table twice — e the report, m the manager via e.manager_id — then filter on the two salary columns. The INNER JOIN is right here: employees with no manager can't out-earn one.

Traps checklist — the three that bite everyone

1. The accidental CROSS join. Forget or mistype the ON clause and you get every pair — the row count explodes and totals go haywire. If a result is unexpectedly huge, check your join conditions first.
2. Join-then-aggregate double-counting (fan-out). Any time you sum/count a parent column after joining to a child, you count it once per child. Aggregate the child in a subquery first, or aggregate at the correct grain.
3. Filtering an outer join's right table in WHERE. Writing LEFT JOIN orders o … WHERE o.amount > 100 throws away the NULL-filled rows and quietly turns your LEFT JOIN back into an INNER JOIN. If the predicate is about the optional side, put it in the ON clause, not WHERE.

★ Review

Summary & self-test

One idea to carry out: a join matches rows by a predicate to build a new relation — the type decides who survives without a partner, the join can multiply rows (mind the grain), and the algorithm is the planner's choice that you influence with indexes. Everything else is a variation on those three.

01Join = match on a predicatePair rows of two tables, keep the ones where ON is true. The result is a new relation you can join again.
02Joins multiply rowsOne-to-many means the “one” side repeats per child — the source of fan-out double-counts when you aggregate.
03Type = who survivesINNER keeps matches only; LEFT/RIGHT keep one whole side with NULL fill; FULL keeps both; CROSS is every pair.
04Semi vs innerEXISTS/IN is a semi-join: at-least-one match, no multiplication. Inner to the many side multiplies.
05Anti-join = NOT EXISTS“No match” questions. Prefer NOT EXISTS — NOT IN with a NULL returns zero rows.
06Three algorithmsNested Loop (indexed inner), Hash Join (big equi-joins in work_mem), Merge Join (sorted inputs). The planner picks.
07Keep-all-then-COALESCELEFT JOIN + coalesce(sum(x),0): sum over no rows is NULL, not 0 — convert it explicitly.
08WHERE breaks outer joinsFiltering the optional table in WHERE turns a LEFT JOIN into an INNER JOIN. Put that predicate in ON.
