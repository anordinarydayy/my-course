Modeling Patterns

Most schema problems are not new. Hierarchies, statuses, soft deletes, many-to-many links, multi-tenancy — the same handful of shapes recur across almost every application you will ever build. This lesson is a catalog of those shapes with known-good solutions, so that instead of reinventing a design (and stumbling into the classic anti-patterns), you reach for a pattern you already trust and adapt it. We build up to a full, worked multi-tenant schema and then drill it.

Original study notes. Written from scratch, targeting PostgreSQL 17/18. This is a practice lesson: it collects reusable modeling patterns, then ends in a worked SQL problem and graded drills you should attempt before reading the answer. 00 Orientation

Patterns you reach for again and again

By now you can turn a domain into normalized tables with the right types, keys, and constraints. This lesson is the layer on top of that skill: a working memory of recurring shapes and the solution each one has settled on. The value is twofold. First, speed — you stop deriving a design from first principles every time. Second, and more important, avoiding known traps: nearly every pattern here exists precisely because the naive version has a sharp edge, and the pattern is the shape that files that edge off.

A modeling pattern is just a recurring problem paired with a schema shape that is known to hold up: it stays correct under concurrency, it indexes well, and it does not paint you into a corner when requirements shift. Think of them exactly the way you think of data structures. You do not re-derive a hash map every time you need fast lookups; you recognize the need and reach for the structure — knowing its costs. Schema patterns work the same way.

Here is the catalog this lesson covers, and the trap each one dodges:

  • Hierarchies & trees — categories, org charts, threaded comments. The trap: modeling a tree so that reading a whole subtree needs an unbounded pile of queries.
  • Constrained status fields — order state, task state. The trap: letting any string into a column that is meant to hold one of five values.
  • Soft deletes & audit columns — keeping history instead of destroying it. The trap: a plain uniqueness rule that then blocks you from ever reusing a value.
  • Many-to-many & multi-tenancy — tags on tasks, users scoped to a team. The trap: forgetting the junction table, or forgetting the tenant key on every row.
How to use this lesson

Read each pattern as a decision, not a recipe. The goal is not to memorize one schema but to hold the trade-offs in your head, so that when the interviewer says "model a comment thread" or "we need to archive orders, not delete them," you already know which shapes are on the table and which one fits the constraints in front of you. The worked problem in section 04 assembles several patterns into one design; the drills in 05 make you do it yourself.

01 Trees

Hierarchies & trees ▸

A huge share of real data is a tree: product categories nested inside categories, employees reporting to managers, comments replying to comments, folders inside folders. The relational model has no native "tree" type, so you represent one with ordinary rows — and the choice of how is one of the most common modeling decisions you will make.

The default, and the one to reach for first, is the adjacency list: each row stores a parent_id pointing at its parent, a foreign key back into the same table. It is trivial to write, trivial to keep correct, and perfect for "who is my parent?" and "who are my direct children?". Its weakness is depth: to read an entire subtree you must walk it level by level. Step through that walk on a small category tree:

That hand-walk is exactly what a recursive CTE automates in a single statement (a WITH RECURSIVE query, previewed properly in Phase 3): it starts at an anchor row and keeps joining children back onto itself until it runs out. So the adjacency list plus a recursive CTE is a complete, production-grade answer for most trees. Reach for an alternative only when subtree reads are hot and the tree is deep:

Recursive CTE

  • Keeps the plain adjacency list.
  • One WITH RECURSIVE walks any depth.
  • Best default for reads that aren't ultra-hot.

Closure table

  • A second table storing every ancestor–descendant pair.
  • Subtree read becomes one flat JOIN — very fast.
  • Cost: extra rows to maintain on every move.

ltree extension

  • A materialized path like 1.2.4 in an ltree column.
  • Purpose-built operators + GiST index for subtree queries.
  • Postgres-specific; great for taxonomy-style trees.
Start simple, escalate on evidence

Begin with the adjacency list every time — it is the least code and the least that can go wrong. Only when a query plan shows subtree reads dominating do you add a closure table or ltree, and you keep the parent_id either way as the source of truth. Reaching for the fancy structure first is a classic case of optimizing before you have measured.

02 Constrained values

Status: enum vs lookup table vs CHECK

The next pattern is everywhere: a column that must hold exactly one of a small, known set of values — an order that is pending, paid, shipped, or cancelled; a task that is open, in_progress, done. The wrong answer is a bare text column, because nothing then stops "Shipped", "shpped", or "in progress " from landing in it and quietly splitting your data. You have three good, constrained options; the choice hinges on how often the set of values changes and whether each value needs metadata.

enum type

  • CREATE TYPE ... AS ENUM (...); compact on disk and fast to compare.
  • Has a natural sort order (declaration order).
  • Cost: adding a value is a schema change (ALTER TYPE ... ADD VALUE); removing or reordering is painful.
  • Use when the set is stable and code-owned.

lookup table + FK

  • A statuses table; the column is an FK to it.
  • Add values with a plain INSERT — no migration, no lock.
  • Each value can carry metadata: label, colour, sort key, is_terminal.
  • Use when the set grows, is user/admin-managed, or needs attributes.

CHECK (IN ...)

  • A plain text/varchar column plus CHECK (status IN (...)).
  • Simplest to write; readable in the schema.
  • Cost: editing the allowed set is a migration on the constraint.
  • Use when the set is tiny and rarely changes and you want zero extra objects.

A useful rule of thumb: if the set is defined by your code and changes only when you deploy (order states, task states), an enum or a CHECK is honest and cheap — the constraint lives with the schema. If the set is data that an admin might extend at runtime, or if each value needs to carry attributes you will query or join on, promote it to a lookup table. When unsure, the lookup table is the most flexible and the easiest to evolve; you rarely regret it, whereas an enum you have outgrown is a genuine chore to widen.

sql

-- enum: stable, code-owned set
CREATE TYPE order_status AS ENUM ('pending', 'paid', 'shipped', 'cancelled');

-- CHECK: simplest, constraint lives in the schema
status text NOT NULL CHECK (status IN ('open', 'in_progress', 'done')),

-- lookup table: extensible + carries metadata
CREATE TABLE task_statuses (
  code       text PRIMARY KEY,        -- 'open', 'in_progress', ...
  label      text NOT NULL,           -- 'In progress'
  sort_order int  NOT NULL,
  is_terminal boolean NOT NULL DEFAULT false
);
-- then: status text NOT NULL REFERENCES task_statuses(code)
Whatever you pick, constrain it

The one unacceptable option is an unconstrained text column. All three patterns above make an illegal value impossible to store, which is the whole point — an invalid status that is already in the table is far more expensive to clean up than a migration was to avoid. Correct-by-construction beats validate-later every time.

03 Keeping history

Soft deletes & audit columns ▸

Very often "delete" does not really mean destroy. A user "deletes" their account but you must keep the order history; a task is "removed" but compliance wants a trail. The pattern is the soft delete: instead of DELETE, you set a deleted_at timestamptz column, and every normal query adds WHERE deleted_at IS NULL. The row stays on disk, invisible to the app but available for audit and undo. Pair it with an audit trail of columns — created_at, updated_at, and often created_by — so every row can answer "when, and by whom?".

There is one classic trap, and it is worth internalizing because interviewers love it. A plain UNIQUE(email) constraint counts the soft-deleted row too, so once Ana's account is soft-deleted, nobody — not even Ana — can ever sign up with that email again: the dead row still occupies it. The fix is a partial unique index that only indexes live rows. Watch the whole lifecycle:

The general shape is CREATE UNIQUE INDEX ... ON users (email) WHERE deleted_at IS NULL. The index only contains rows that are currently live, so a soft-deleted row's email no longer participates in uniqueness — the moment it is retired, the value is free to reuse. This is a small, load-bearing pattern: partial indexes are also how you enforce "at most one default address per user" or "one active subscription per account". Any "unique among the ones that matter" rule is a partial unique index.

Soft delete is a decision, not a default

It has real costs: every query must remember the WHERE deleted_at IS NULL filter (miss it and you leak "deleted" data), indexes must often be partial to stay useful, and the table only grows. Apply it where history or undo genuinely matters, and let truly transient data be hard-deleted. Keep updated_at honest with a trigger or your ORM, since Postgres will not touch it for you. This filter-everywhere burden is exactly the thing an interviewer probes when they ask "what breaks with soft deletes?".

04 Worked problem

Worked: model a multi-tenant task tracker ▸

Time to assemble the patterns into one design. Here is the brief, exactly as an interviewer might phrase it.

Requirements. Build the schema for a task tracker used by many customer organizations on one shared database. Concretely: teams are the tenants; users belong to exactly one team; tasks belong to a team and carry a constrained status; tasks can have many tags and a tag can be on many tasks (many-to-many); deletions are soft; rows carry audit columns; and every tenant's data must be isolated — no query should ever be able to see another team's rows by accident.

Read those requirements and the patterns almost name themselves: a status field (section 02), soft deletes with a partial unique index (section 03), a junction table for the M:N link, and a team_id on every row for tenant isolation. Watch the schema come together table by table, junction last:

The schema

sql

CREATE TYPE task_status AS ENUM ('open', 'in_progress', 'done', 'archived');

CREATE TABLE teams (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name       text        NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE users (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  team_id    bigint      NOT NULL REFERENCES teams(id),   -- tenant key
  email      text        NOT NULL,
  name       text        NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  deleted_at timestamptz                             -- NULL = live; soft delete
);
-- one LIVE email per tenant; dead rows drop out, so the email can be reused
CREATE UNIQUE INDEX users_team_email_live
  ON users (team_id, email) WHERE deleted_at IS NULL;

CREATE TABLE tasks (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  team_id    bigint      NOT NULL REFERENCES teams(id),   -- tenant key
  title      text        NOT NULL,
  status     task_status NOT NULL DEFAULT 'open',
  created_by bigint      REFERENCES users(id),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  deleted_at timestamptz
);

CREATE TABLE tags (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  team_id bigint NOT NULL REFERENCES teams(id),
  label   text   NOT NULL,
  UNIQUE (team_id, label)                          -- tags are per-tenant
);

-- the M:N junction: two FKs form the composite primary key
CREATE TABLE task_tags (
  task_id bigint NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  tag_id  bigint NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
  PRIMARY KEY (task_id, tag_id)
);

The key query

The hot path is "show one team's open tasks with their tags". A tenant-scoped read that folds each task's tags into an array:

sql

SELECT t.id, t.title,
       array_agg(g.label ORDER BY g.label) FILTER (WHERE g.label IS NOT NULL) AS tags
FROM tasks t
LEFT JOIN task_tags tt ON tt.task_id = t.id
LEFT JOIN tags g       ON g.id = tt.tag_id
WHERE t.team_id = $1            -- tenant isolation, always first
  AND t.status = 'open'
  AND t.deleted_at IS NULL       -- hide soft-deleted
GROUP BY t.id, t.title
ORDER BY t.id;

The indexes it needs

Remember: Postgres does not auto-index foreign-key columns — you add them yourself, or joins and tenant filters fall back to sequential scans. The queries above want:

sql

-- FKs are not indexed automatically — index every one you filter/join on
CREATE INDEX ON users (team_id);
CREATE INDEX ON tasks (team_id);
CREATE INDEX ON tasks (created_by);
CREATE INDEX ON task_tags (tag_id);   -- PK already covers (task_id, tag_id)

-- partial index matching the hot "open tasks for a team" query exactly
CREATE INDEX tasks_team_open ON tasks (team_id)
  WHERE status = 'open' AND deleted_at IS NULL;

Narrate it

The design's spine is the tenant key: every data table carries team_id, so isolation is a WHERE team_id = $1 that the application always prepends (and, in production, a Row-Level Security policy enforces so a forgotten filter cannot leak data across tenants — a Phase 7 topic). Status is an enum because the set is code-owned and stable; had the brief said "admins define their own workflow states," it would become a lookup table instead. Soft delete plus the partial unique index keeps history while still letting a tenant reuse an email. The junction task_tags gives a clean many-to-many with a composite primary key that also prevents duplicate tag assignments for free. The trade-off you are accepting: a little more filtering discipline (tenant + deleted_at on nearly every query) in exchange for isolation, auditability, and flexible tagging — a bargain that scales far better than one table per tenant.

05 Drills

Graded drills & anti-patterns

Now you drive. Each drill is a short modeling brief. Sketch the tables, keys, and constraints on paper first — actually write the CREATE TABLEs — and only then open the reveal to compare. The point is not a single "right" answer but whether your shape avoids the traps.

Drill 1 — Product categories as a tree

Model an e-commerce category hierarchy of arbitrary depth (Electronics → Phones → Accessories → ...). Support "list a category's direct children" and "list an entire subtree". Which shape do you start with?

Try first, then read

Start with an adjacency list: categories(id PK, parent_id bigint REFERENCES categories(id), name text NOT NULL). Direct children is WHERE parent_id = $1; the whole subtree is a WITH RECURSIVE walk anchored at $1. Add an index on parent_id (it's an FK — not auto-indexed). Only if subtree reads become a proven bottleneck do you layer on a closure table or ltree; do not start there.

Drill 2 — An order with line items and a captured price

Model a customer order containing several products, each with a quantity. Crucially, the price on the order must be the price at the time of purchase, even if the product's catalogue price changes tomorrow. Where does the price live?

Try first, then read

An orders header plus an order_items line table: order_items(order_id FK, product_id FK, quantity int NOT NULL CHECK (quantity > 0), unit_price numeric(12,2) NOT NULL, PRIMARY KEY (order_id, product_id)). The trap is reading the price by joining to products at display time — that shows today's price, not the one paid. You must copy unit_price (and often the name) onto the line item at purchase — a deliberate, correct denormalization for a captured historical fact. Use numeric, never float, for money.

Drill 3 — Followers (self many-to-many on users)

Model a social "follow" relationship: a user can follow many users and be followed by many. Support "who do I follow?" and "who follows me?", and forbid following yourself and following the same person twice.

Try first, then read

A self-referencing junction: follows(follower_id bigint REFERENCES users(id), followee_id bigint REFERENCES users(id), created_at timestamptz NOT NULL DEFAULT now(), PRIMARY KEY (follower_id, followee_id)). The composite PK forbids duplicate follows. Add CHECK (follower_id <> followee_id) to forbid self-follows. "Who I follow" indexes on follower_id (the PK covers it); "who follows me" needs its own index on followee_id. The direction of the relationship is entirely in which column you filter.

Drill 4 — Per-user feature-flag override

Flags have a global default (on/off). Individual users may override a specific flag. Model it so that "is flag X on for user U?" resolves cleanly, and a user with no override simply inherits the default.

Try first, then read

Two tables: feature_flags(key text PRIMARY KEY, default_enabled boolean NOT NULL) and user_flag_overrides(user_id FK, flag_key text REFERENCES feature_flags(key), enabled boolean NOT NULL, PRIMARY KEY (user_id, flag_key)). Resolution is a LEFT JOIN from the override table with COALESCE(o.enabled, f.default_enabled). The composite PK guarantees at most one override per (user, flag). Resist the tempting anti-pattern of a wide users table with one boolean column per flag — that needs a schema migration for every new flag.

Anti-patterns to recognize on sight

  • EAV (entity–attribute–value). One giant (entity, attribute, value text) table to store "anything". It defeats types, constraints, and the planner; every read becomes a self-join pile-up. If attributes are semi-structured, a jsonb column (Phase 6) is the honest tool — not a fake schema.
  • The God table. One 80-column table modelling several distinct concepts at once. It means constant NULLs, contradictory rows, and locks fighting each other. Split by concept; that is what normalization is for.
  • CSV-in-a-column. Storing "4,7,12" as text to fake a list. You cannot index it, join it, or enforce that those ids exist. A junction table (or a real array with a constraint) is the answer.
  • No timestamps. Tables with no created_at/updated_at. You only notice when you desperately need to know "when did this happen?" and the answer is gone forever. Add them from day one.
  • Natural keys that change. Using email, username, or an SSN as a primary key. When it changes (and it will), every foreign key referencing it must change too. Prefer a stable surrogate identity key; keep the natural value as a UNIQUE column.
★ Review

Summary & self-test

The whole lesson compresses to one idea: most schema problems have a known-good shape — a tree, a constrained status, a soft delete with a partial index, a junction plus a tenant key — and modeling well is mostly recognizing which shape fits and knowing the trap each one dodges.

01Patterns, not first principlesRecurring shapes have settled solutions. Recognize the problem, reach for the shape, know its cost — like a data structure.
02Trees start as adjacency listsA self-referencing parent_id plus a recursive CTE handles most trees. Escalate to closure table or ltree only on evidence.
03Constrain every statusenum (stable, code-owned), lookup table (extensible, has metadata), or CHECK (tiny, simple). Never a bare text column.
04Soft delete = deleted_atSet a timestamp instead of DELETE; filter WHERE deleted_at IS NULL everywhere. Keeps history and enables undo.
05Partial unique indexA plain UNIQUE blocks reusing a soft-deleted value. UNIQUE(email) WHERE deleted_at IS NULL indexes only live rows.
06M:N needs a junctionTwo FKs as a composite PK give a clean many-to-many and forbid duplicate links for free.
07Multi-tenant = team_id everywhereEvery data row carries the tenant key; every query filters by it. Index the FKs — Postgres won't do it for you.
08Know the anti-patternsEAV, the God table, CSV-in-a-column, no timestamps, mutable natural keys. Spotting them is half of modeling well.
Self-test before you move on

Cover the notes and answer aloud:
(1) You must model threaded comments of unbounded depth. Which shape do you start with, what one query reads a whole thread, and when would you switch shapes?
(2) A column holds one of five order states. Give the three constrained options and the single question that decides between them.
(3) Why does a plain UNIQUE(email) break with soft deletes, and what exact index fixes it?
(4) Sketch the tables for tags-on-tasks (M:N). What does the junction's composite primary key buy you?
(5) In a multi-tenant design, what carries isolation, and which foreign keys must you remember to index by hand?
(6) Name three anti-patterns and, for each, the honest pattern that replaces it.
